                RetryPolicy:         &temporal.RetryPolicy{MaximumAttempts: 5},

            defer func() {
                if err == nil {
                    return

                dctx, _ := workflow.NewDisconnectedContext(ctx)
                for i := len(undo) - 1; i >= 0; i-- { // newest first
                    _ = undo[i](dctx)
                }

        // checkout/saga.rs: an orchestrator that writes every step to a saga log
        const STEPS: [Step; 4] = [Step::CreateOrder, Step::ReserveStock, Step::Charge, Step::BookCourier];

        pub async fn place_order(db: &PgPool, svc: &Services, o: &Order) -> anyhow::Result<()> {
            for (i, step) in STEPS.iter().enumerate() {
                log(db, &o.id, i, Status::Started).await?; // durable before the call
                match svc.run(*step, o).await {
                    Ok(()) => log(db, &o.id, i, Status::Done).await?,
                    Err(e) => {
                        log(db, &o.id, i, Status::Failed).await?;
                        compensate(db, svc, o, i).await?;
                        return Err(e);
                    }
                }
            }
            svc.approve_and_confirm(o).await
        }

        /// Undo every step that completed, newest first. The recovery loop also calls
        /// this for sagas whose log ends in Started or Failed after a crash.
        pub async fn compensate(db: &PgPool, svc: &Services, o: &Order, failed: usize) -> anyhow::Result<()> {
            for i in (0..failed).rev() {
                svc.undo(STEPS[i], o).await?; // Refund, ReleaseStock, RejectOrder: each idempotent
                log(db, &o.id, i, Status::Compensated).await?;

            Ok(())

        pub async fn charge(&self, o: &Order) -> anyhow::Result<()> {
            self.client.charge(&o.id, o.cents, &format!("charge-{}", o.id)).await

reference:
  roles:
    - role: Coordinator
      example: the order saga, as a workflow or an orchestrator service
      job: Runs the steps in order, records each one durably, and runs the compensations in reverse on failure. Absent in choreography.
    - role: Participant
      example: Inventory, Payments, Shipping
      job: Runs one local transaction per step, and offers an idempotent compensating action for it.
    - role: Saga log
      example: the workflow history, or a saga_steps table
      job: Survives crashes so the saga can be resumed or undone.
    - role: Events and commands
      example: ReserveStock, PaymentFailed
      job: Carry the workflow between services. Published with an outbox so they are never lost after a commit.
  useWhen:
    - A business operation changes data owned by several services, and a distributed transaction is not available or not wanted.
    - Steps can be undone semantically, by a refund, a release or a cancellation.
    - Orchestration when the flow has many steps, branches or deadlines and someone must answer "where is order 1042?".
    - Choreography when the flow is short, stable and each service only needs to react to one or two events.
  avoidWhen:
    - The data can live in one service and one database. One local transaction is simpler than any saga.
    - Readers cannot tolerate seeing intermediate states and no countermeasure, such as a pending status, fits.
  tradeoffs:
    - No isolation. Other transactions see the order half done, and can act on it, until the saga finishes or compensates.
    - Every step needs an idempotent compensation, written and tested by hand. Some actions have none.
    - Orchestration couples the flow to one coordinator; choreography spreads it across subscriptions that nobody sees whole.
    - Messages arrive at least once, so every step and compensation must deduplicate by key.
  lookalikes:
    - name: Two-phase commit
      how: Atomic across participants, with locks held until the coordinator decides. Sagas give up atomicity and isolation to avoid the locks and the blocking.
    - name: Transactional outbox
      how: Makes one step's commit and its event atomic. A building block of a saga, not a saga.
    - name: Workflow engine
      how: Temporal, AWS Step Functions and similar run orchestrated sagas, keeping the log and the retries for you.

## [concept] Sagas

**A workflow that changes several services cannot roll back as one transaction. A saga runs it as a sequence of local transactions, and for every step that succeeded it has a compensating action to run if a later step fails.**

A <Term id="saga">saga</Term> trades atomicity for independence. Each service commits its own step. If step four fails, the saga runs the <Term id="compensating-transaction">compensations</Term> for steps three, two and one, newest first, and the system becomes consistent again, eventually.

<Depth level={2}>
Someone has to drive the steps. In <Term id="orchestration">orchestration</Term>, one coordinator tells each service what to do and keeps the state of the workflow. In <Term id="choreography">choreography</Term>, there is no coordinator: each service reacts to another's event and publishes its own. Orchestration makes the flow visible and the failure handling explicit, at the price of a central component. Choreography couples services less and scales well, at the price of a flow that exists only in who subscribes to what.
</Depth>

<Depth level={3}>
Hector Garcia-Molina and Kenneth Salem introduced sagas at SIGMOD in 1987, for long-lived transactions inside one database: break the long transaction into short ones that other transactions may interleave with, and pair each with a compensation. Microservices adopted the idea because each service owns its own database, so a long transaction across them is not possible at all.
</Depth>

## [problem] A local transaction around remote calls

PlaceOrder opens a database transaction, inserts the order, calls Inventory to reserve the items, calls Payments to charge the card, and commits. If anything returns an error, the deferred rollback runs. It reads as all-or-nothing, and in tests where nothing fails, it is.

<Depth level={2}>
The rollback only covers the order row in checkout's own database. The reservation lives in Inventory's database and the charge in Payments'. Neither is part of the transaction, whatever the indentation suggests.
</Depth>

<Depth level={3}>
The remote calls also run while the local transaction holds its locks and its connection. A slow payment provider now holds a row lock in checkout's database for seconds.
</Depth>

## [pain] Then a change request arrives

**Change request:** book a courier after the payment. If no courier serves the address, cancel the order and refund the customer.

The courier call goes after the charge. The first time it fails, the rollback deletes the order row, and that is all it does. The card is charged, the stock is reserved, and there is no order to refund against. Support finds customers charged for orders the system has no record of.

<Depth level={2}>
The bug was there before the change: a declined card already left stock reserved for an order that was rolled back. The new step made it costlier and more frequent, because it fails after the money has moved.
</Depth>

<Depth level={3}>
Retrying does not help. "No courier for this postcode" is a business failure, not a transient one; it will fail the same way every time. The only way forward is back, step by step.
</Depth>

## [morph] Every step brings its own undo

Drag the slider. The order becomes a durable workflow. Each step runs as its own local transaction in its own service, and the moment a step succeeds, its compensation goes onto an undo stack. On failure, the stack runs newest first.

Hover a box in the diagram to see its code.

<Depth level={2}>
Two details make it safe. Each step and each compensation is idempotent, keyed by the order id, because a retry after a lost reply would otherwise charge or refund twice; the <Term id="idempotency-key">idempotency key</Term> from the distributed-systems track does that job here. And the workflow's progress is recorded in a <Term id="saga-log">saga log</Term>, so a crash in the middle resumes or compensates instead of forgetting.
</Depth>

<Depth level={3}>
A step whose call timed out may or may not have taken effect. A careful saga compensates the failed step too when its outcome is unknown, which is safe only because refunding an order that was never charged is a no-op for an idempotent Payments service.
</Depth>

## [walk] Follow one failed order

One order whose courier booking fails, from the start of the saga to the last compensation. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">The deferred function sees the named result `err`, so it runs the stack only on failure. It uses a disconnected context, so compensations still run if the workflow itself was cancelled.</Lang>
<Lang only="python">The `except ActivityError` block runs the stack and re-raises, so the workflow ends failed and its history shows both the failure and every compensation.</Lang>
<Lang only="typescript">`undo.reverse()` walks the stack newest first. An activity failure reaches the workflow as an `ActivityFailure` and lands in the `catch`.</Lang>
<Lang only="rust">The log is written before each call, so after a crash a saga whose last entry is Started is exactly one whose outcome is unknown, and the recovery loop knows where to begin compensating.</Lang>
</Depth>

## [again] The same request, the second time

The courier fails, as it will for some postcodes. The saga refunds the card, releases the stock and rejects the order, and the customer gets a cancellation email instead of a charge for nothing. The test above fails the courier on purpose and asserts the three compensations, in reverse order.

<Depth level={2}>
Between the charge and the refund, the order was visible as pending with a real charge behind it. That is the price of a saga: no isolation. A report run at that moment would count it. Pending statuses, which other code treats as not yet real, are the usual countermeasure.
</Depth>

<Depth level={3}>
The choreographed version of the same saga works without a coordinator. Payments listens for CourierUnavailable and refunds, Inventory listens for PaymentRefunded and releases, Orders listens for both and rejects. Each publishes through a <Term id="transactional-outbox">transactional outbox</Term> so an event is never lost after its commit. The flow is the same; it lives in four services' subscriptions instead of one function.
</Depth>

### Choosing orchestration or choreography

Count who must change when the workflow changes. Adding a fraud check between the reservation and the charge is one edit to an orchestrator, plus the new service. In choreography, Payments must now listen for FraudApproved instead of StockReserved, the fraud service must listen for StockReserved, and Inventory and Orders must learn FraudRejected so they can compensate. Short, stable flows suit choreography. Flows that grow steps, branches and deadlines, or that support staff must be able to inspect, suit an orchestrator.
