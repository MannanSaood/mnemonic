        type Order struct {
            Lines    []Line
            Customer Customer
            Coupon   *Coupon
        }

        type Discount interface {
            Amount(o *Order, eligible Money) Money
        }

        var Discounts = []Discount{Over100{}, CouponOff{}, GoldTier{}}

        func (o *Order) Eligible() Money {
            var m Money
            for _, l := range o.Lines {
                if !l.GiftCard {
                    m += l.Price * Money(l.Qty)
                }
            }
            return m
        }

            eligible, d := o.Eligible(), Money(0)
            for _, rule := range Discounts {
                d += rule.Amount(o, eligible)

            return o.Subtotal() - min(d, eligible/5) // one cap, after every rule

  overview:
    question: Which style organises business logic as one procedure per user action?
    options:
      - text: Transaction Script.
        correct: true
        why: Right. Each request gets a procedure that reads, decides and writes. Simple, and fast to write while the rules are few.
      - text: Domain Model.
        why: A domain model puts rules on objects that represent the business, and many actions share them.
      - text: Service Layer.
        why: A service layer is the set of operations the application offers. It can call scripts or a domain model, but it is not where the rules live.

        why: Helpers stop copy-paste of each rule, but the order the rules run in, and how they combine, is still repeated in every script. Caps and exclusions break there.
      - text: A stored procedure, so every application shares it.
        why: It is one copy for code that can reach a row. Callers without one, such as a cart preview, need another copy, and every change becomes a migration.
  deep:
    question: What is the anemic domain model problem?
    options:
      - text: The objects carry only data and services hold every rule, so nothing guards the object's invariants and rules repeat across services.
        correct: true
        why: Right. You pay for a domain model's objects and mapping and get transaction scripts in disguise. Fowler's 2003 entry calls it a design that looks like a domain model but has no behaviour.
      - text: The domain objects have too many methods, which slows the ORM down.
        why: The problem is the opposite, too few methods. Behaviour belongs with the data.
      - text: The domain model is too small for the database it maps to.
        why: Size is not the point. Anemic means the objects have no behaviour of their own.

reference:
  roles:
    - role: Presentation
      example: the checkout and cart controllers
      job: Turns requests into calls on the service layer and results into responses.
    - role: Service layer
      example: PlaceOrder, QuoteCart
      job: Defines the application's operations. Opens the transaction, loads and saves, calls the domain. Holds no business rule.
    - role: Domain
      example: Order and its Discount policies
      job: Holds the business rules, each in one place, with the data they use.
    - role: Data source
      example: the Order mapper or repository
      job: Moves data between the database and the domain objects.
  useWhen:
    - Transaction scripts while rules are few and independent, such as an admin tool or a CRUD service.
    - A domain model when rules interact, change often, or are shared by several entry points.
    - A thin service layer in either case, so the transaction and the use case's steps have one home.
  avoidWhen:
    - A domain model for a service with no real rules. The mapper and the objects cost more than the logic.
    - Business rules in the database when callers price things that have no row yet, or when the rules need unit tests.
  tradeoffs:
    - A domain model needs a mapping between objects and tables, and a team that knows how to keep rules on the objects.
    - Transaction scripts are easy to read one at a time, and duplication creeps in between them.
    - A Table Module fits tools built around record sets, with one object per table instead of one per row.
    - Each layer boundary adds mapping and copying. Keep calls between layers inside one process.
  lookalikes:
    - name: Active Record
      how: A row object with domain logic and its own save(). A domain model and its data source merged into one class; fine while the model and the table look alike.
    - name: Table Module
      how: One instance per table, working on all its rows. Sits between scripts and a domain model.
    - name: Layered vs hexagonal
      how: Classic layering puts the domain above the data source, so the domain imports it. The Dependency Rule inverts that edge, so the data source depends on the domain.

## [concept] Layering and domain logic styles

**Split an application into layers, presentation, domain and data source, and then choose how the domain layer holds its rules: one script per action, or a model of objects that carry the rules with their data.**

Martin Fowler's *Patterns of Enterprise Application Architecture* names three ways to organise the rules. A <Term id="transaction-script">transaction script</Term> is one procedure per request. A <Term id="domain-model">domain model</Term> is a web of objects that hold both data and behaviour. A <Term id="table-module">table module</Term> is one object per table that works on all its rows. Around any of them sits a <Term id="service-layer">service layer</Term>, the set of operations the application offers.

<Depth level={2}>
None of the styles is better in general. Scripts are quick to write and to read while the rules are few. A domain model costs more at the start, because objects need mapping to tables, and pays off when rules multiply and interact. The skill is to notice which side of that line the code is on, and to move when it crosses.
</Depth>

<Depth level={3}>
A <Term id="layer">layer</Term> is logical, a tier is physical. Presentation, domain and data source can all run in one process, and usually should: every hop between tiers adds a network call where a layer boundary would add a function call.
</Depth>

## [problem] Two scripts price the same cart

Checkout's PlaceOrder script loads the cart, applies 10% off orders over $100 and any coupon, inserts the order and commits. The cart preview's QuoteCart script loads the same cart and applies the same two rules, so the customer sees the price they will pay.

<Depth level={2}>
Each script reads well on its own. The duplication is small, and it was a fair call when there were two rules: one copy each, side by side.
</Depth>

<Depth level={3}>
The rules are written in terms of local variables: subtotal and discount. There is no Order object to put a rule on, so the only place a new rule can go is into each script that prices something.
</Depth>

## [pain] Then a change request arrives

**Change request:** gold members get 5% off, and discounts must never add up to more than 20% of the order.

The gold rule goes into both scripts. The cap is worse. It has to run after every other rule, so in each script it goes at the end and has to know every discount above it. Miss one script and the preview shows one price while checkout charges another.

<Depth level={2}>
The cost of a rule now depends on how many rules exist and how many scripts price an order. Reorder and the invoice PDF price orders too, so the real count is four copies, not two.
</Depth>

<Depth level={3}>
Shared helper functions remove the copy-paste of each rule but not the sequencing. "Eligible amount first, then percentages, then fixed amounts, then the cap" is itself a rule, and each script repeats it.
</Depth>

## [morph] Rules move onto the Order

Drag the slider. The two scripts become a thin service layer. The pricing math moves onto an Order object, with each discount as its own small type and the cap applied once in Order.Total. A mapper loads and saves the Order.

Hover a box in the diagram to see its code.

<Depth level={2}>
The service layer keeps what is not a business rule: the transaction, loading and saving, and the order of steps in one use case. If a rule creeps into a service method, it will be copied into the next service method. That is how a domain model turns <Term id="anemic-domain-model">anemic</Term>.
</Depth>

<Depth level={3}>
With a domain model, the transaction usually opens in the service layer and a Unit of Work tracks which objects changed. Rich objects also need to be persistence-ignorant, so they can be built and tested in memory, as the test below does.
</Depth>

### Moving from scripts to a model

You rarely start with a domain model, and you rarely need to rewrite to get one. When the same rule shows up in a second script, extract it into a function that takes a small value type, such as an Order with its lines. When a third rule needs to know about the first two, give that type a method that applies them in order. The scripts shrink into service methods one at a time, and the model grows only where the rules are.
