## [concept] The Dependency Rule

**Source code dependencies point only inward, toward the business rules. The database, the web framework and the mail server are details that plug in from outside.**

Draw the code as rings. <Term id="use-case">Use cases</Term> and entities sit in the middle; adapters, frameworks and drivers sit outside. The <Term id="dependency-rule">Dependency Rule</Term> says nothing in an inner ring may name anything in an outer ring: no import, no type, no data format.

<Depth level={2}>
Control still flows outward: the use case calls the database. The trick that reconciles the two is <Term id="dependency-inversion">dependency inversion</Term>. The use case declares the interface it needs, and the outer code implements it. That is <Term id="ports-and-adapters">ports and adapters</Term>: ports are the inner ring's own interfaces, and an adapter connects one port to one technology. Driving adapters (an HTTP handler, a CLI) call the use case. Driven adapters (a repository, a mailer) implement its ports.
</Depth>

<Depth level={3}>
Robert C. Martin named the rule in a 2012 blog post and his 2017 book *Clean Architecture*. He presented it as the shared idea behind several earlier architectures: Alistair Cockburn's hexagonal architecture, Jeffrey Palermo's onion architecture, and Ivar Jacobson's boundary-control-entity. The four named rings are an example, not a law. What matters is the direction of the arrows.
</Depth>

## [problem] One handler that does everything

The refund endpoint parses JSON, loads the order with SQL, checks the 30-day rule, updates the row and sends an email, all in one handler function. It is short, it works, and its integration test passes against a real database.

<Depth level={2}>
The business rule, "within 30 days and never more than was paid", sits between a framework call and a driver call. To run it, you need both.
</Depth>

<Depth level={3}>
The handler also decides the data format of the rule. It reads columns into local variables, so the rule is written in terms of the table's shape, not an Order type of its own.
</Depth>

## [pain] Then a change request arrives

**Change request:** support needs a command-line tool that issues refunds, and CI must run the refund tests without Postgres.

The CLI cannot call the handler without faking an HTTP request, so someone copies the SELECT, the rule, the UPDATE and the email into a second function. Now the 30-day rule lives in two places. And no test of the rule can run without a database, because the rule only exists inside code that queries one.

<Depth level={2}>
Neither request touched the refund rule, yet both have to go through the code that holds it. The next policy change, say 60 days for gold customers, must be made twice and tested against Postgres twice.
</Depth>

<Depth level={3}>
<Lang only="go">The handler takes a `*gin.Context`. A CLI would have to build a gin context or copy the code; there is no third option.</Lang>
<Lang only="python">The view reads `flask.request`, a context-local. Calling it from a CLI needs `app.test_request_context()`, which is a test tool, not an architecture.</Lang>
<Lang only="typescript">The route closes over Express's `req` and `res`. The CLI would have to fake both objects, including `res.status().json()` chaining.</Lang>
<Lang only="rust">The handler's arguments are `web::Data` and `web::Json` extractors. Outside actix-web there is nothing to pass it.</Lang>
</Depth>

## [again] The same request, the second time

The CLI is one new file: a second driving adapter that builds the same use case and calls it. The test of the 30-day rule passes an in-memory Orders and a notifier that does nothing. Neither the entity nor the use case changed.

<Depth level={2}>
Main is the <Term id="composition-root">composition root</Term>, and there can be more than one. The API's main and the CLI's main wire the same use case to the same adapters, or to different ones.
</Depth>

<Depth level={3}>
Martin treats tests as the outermost ring: they depend inward on the use case, and nothing depends on them. A test written against the use case's API survives a change of framework. A test that drives the HTTP handler and checks the database does not.
</Depth>

## [lens] How each language enforces it

### When the full rule costs too much

The rule has a price: a port per dependency, a mapper per boundary, and more files to read. A service that stores and returns records with almost no rules gains little from it. Start where the rules are. A single Orders port, used by the two use cases that have real policy, buys most of the testability for a fraction of the ceremony, and the rest of the service can stay a thin handler over the database until it grows rules of its own.
