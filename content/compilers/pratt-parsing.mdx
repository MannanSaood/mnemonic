        correct: true
        why: Right. A lower minimum lets the inner call take the next ** too, so a ** b ** c becomes a ** (b ** c). Nothing else changes.

        why: That is the function-per-level design. It works, but each new level means another function and rewiring its neighbours.

        why: With the right side parsed at the operator's own power, equal operators group to the left. Right associativity needs the lower power.

    - role: parseExpr(minBP)
      example: { go: "parseExpr(minBP int)", python: "parse_expr(min_bp)", typescript: "parseExpr(minBp)", rust: "parse_expr(min_bp)" }
      job: Parses an operand, then takes operators while their power is above minBP.
    - role: Binding power table
      example: "or 1 · and 2 · compare 4 · + - 5 · * / 6"
      job: The whole operator grammar as data. Adding an operator is a row.
    - role: Prefix parse
      example: names, numbers, strings, (, not, unary -
      job: What a token means at the start of an expression.
    - role: Infix step
      example: a binary operator
      job: What a token means after a complete left operand. Builds a node from left and right.
    - role: Right-side power
      example: bp (left-assoc) or bp - 1 (right-assoc)
      job: Decides how a chain of equal operators groups.
  useWhen:
    - Expressions with many operators and levels, as in rule, query, filter and formula languages.
    - You want to add operators without rewiring the parser.
    - You are writing a parser by hand and want good error messages, which generated parsers make harder.
  avoidWhen:
    - The language has an existing parser (CEL, SQL, JSON Logic). Use it.
    - Expressions have one or two operators. A function per level is just as clear.
  tradeoffs:
    - The table is compact, but precedence is now numbers, so reviews need a written table and tests of known groupings.
    - Prefix, infix and postfix (calls, indexing) all fit one loop, which makes it easy to keep growing the language.
    - Precedence climbing is the same loop for binary operators only. Pratt adds per-token prefix and infix behaviour.
  lookalikes:
    - name: Recursive descent, one function per level
      how: Same trees. The levels are a chain of calls, so the order of the chain is the precedence.
    - name: Shunting-yard
      how: Dijkstra's algorithm uses explicit operator and output stacks instead of recursion; the call stack plays that role in Pratt.
    - name: LR parsing
      how: Generated tables also resolve precedence, through declarations such as %left in yacc and bison.

## [concept] One loop and a table of numbers

**A Pratt parser handles every operator with one loop and a table of <Term id="binding-power">binding powers</Term>. When an operand sits between two operators, the one with the higher power takes it.**

`cpu > 0.95 or mem > 0.9 and env == "prod"` has `mem > 0.9` in the middle of `or` and `and`. `and` has the higher power, so it takes `mem > 0.9`. The rule means what it means in Python, SQL and most other languages: CPU above 95%, or memory above 90% in production.

<Depth level={2}>
The loop is `parseExpr(minBP)`. It reads one operand, the prefix part, then looks at the next token. If it is an operator whose power is above `minBP`, the loop takes it, parses the right side with a recursive call, builds a node and repeats. If the power is not above `minBP`, the loop returns what it has, and the caller decides what to do with that operator. Each token can have a prefix meaning (a name, a number, `(`, `not`, unary minus) and an infix meaning (a binary operator), and both live in tables.
</Depth>

<Depth level={3}>
Vaughan Pratt described the technique in Top Down Operator Precedence at the first POPL symposium in 1973. He presented it as a mix of recursive descent and Floyd's operator precedence. Textbooks mostly skipped it. It spread through hand-written parsers such as Douglas Crockford's JSLint and through Crafting Interpreters. For binary operators alone it is the same algorithm as <Term id="precedence-climbing">precedence climbing</Term>, which is what `go/parser` does.
</Depth>

## [problem] A parser that folds left to right

The alerting service parses rules with a small hand-written parser. A rule is conditions joined by `and` and `or`, and each condition is exactly three tokens: a metric, a comparison and a value. The parser reads conditions and folds them from left to right.

All the existing rules use only `and`, or only `or`, so every test passes.

<Depth level={2}>
The fold has no notion of precedence. With one kind of connective, grouping does not change the answer, so the tests cannot tell. The fixed shape of a condition also means there is no arithmetic. That was fine while every rule compared one metric with one number.
</Depth>

<Depth level={3}>
The fold builds `((a op b) op c) op d`, a left-leaning tree. That is correct for a chain of one associative operator and wrong as soon as two operators with different precedence meet.
</Depth>

## [pain] Ratio alerts, and and/or mixed

**Change request:** SRE wants ratio alerts such as `errors / requests > 0.05`, mixed with `and` and `or` the way every other language mixes them.

Two lines show the problem. `errors / requests > 0.05` is rejected, because a condition must be metric, comparison, value. Worse, `cpu > 0.95 or mem > 0.9 and env == "prod"` already saves today and means the wrong thing: `(cpu > 0.95 or mem > 0.9) and env == "prod"`. A staging host at 97% CPU never pages, and nothing in the UI says why.

<Depth level={2}>
The usual fix is recursive descent with a function per precedence level: `parseOr` calls `parseAnd`, which calls `parseComparison`, then `parseSum`, `parseProduct`, `parseUnary` and `parsePrimary`. It works, but the precedence is hidden in which function calls which, and each new level is a new function wired between two others.
</Depth>

<Depth level={3}>
Changing the meaning of a saved rule is a migration problem too. Every rule that mixes `and` and `or` now means something else. Find them first and add explicit parentheses, so the change of grouping does not silently change who gets paged.
</Depth>

## [morph] Replace the fold with a power table

Drag the slider. The fold and the fixed three-token condition give way to one loop and a table. Every operator, logical, comparison and arithmetic, is a row with a number.

Hover a box in the diagram to see its code.

<Depth level={2}>
The prefix step makes operands general: a name, a number, a string, a parenthesised expression, or `not` and `-` applied to an operand. Because the right side of every operator is a full recursive `parseExpr`, `errors / requests` can appear wherever a metric could.
</Depth>

<Depth level={3}>
<Lang only="go">The table is a `map[string]int`, and a missing key means "not an infix operator", which ends the loop. Go's own `go/parser` uses the same shape with `token.Token.Precedence()`, and it returns when the operator is below `prec1` and recurses with `oprec+1`. That is the same rule as returning when the power is not above `minBP` and recursing with the power itself.</Lang>
<Lang only="python">`INFIX_BP.get` returns `None` for anything that is not an operator, which ends the loop. Recursion depth follows the expression's nesting, so a machine-generated rule with thousands of nested parentheses can hit `RecursionError`; cap the nesting when the rule is saved.</Lang>
<Lang only="typescript">The tree is a discriminated union, so later passes (type check, evaluate, compile) switch on `kind` and the compiler checks the cases. The `Map` lookup returns `undefined` for non-operators, which ends the loop.</Lang>
<Lang only="rust">The table is a `match` that returns `Option<u8>`, and the `Some(bp) if bp > min_bp` guard is the whole precedence rule. `t.text` is a `&'a str` borrowed from the source, so the tree holds slices of the rule and copies nothing.</Lang>
</Depth>

## [walk] Parse one mixed rule

`cpu > 0.95 or mem > 0.9 and env == "prod"`, one decision at a time. Step through it with the numbered buttons.

<Depth level={3}>
<Term id="associativity">Associativity</Term> comes from the power passed to the right side. Pass the operator's own power and an equal operator stops the inner call, so `a - b - c` is `(a - b) - c`. Pass one less and the inner call keeps going, so `a ** b ** c` is `a ** (b ** c)`. matklad's version gives each operator a pair of left and right powers, which says the same thing with two numbers.
</Depth>

## [again] Ratio alerts, the second time

The same change request against the table. `/` is already a row, so `errors / requests > 0.05` parses with no new code. The mixed rule now groups as `cpu > 0.95 or (mem > 0.9 and env == "prod")`, and the staging host at 97% CPU pages.

<Depth level={2}>
Write the table down in the rule language's documentation, and keep tests of known groupings: `a or b and c`, `a - b - c`, `not a == b`. A wrong number does not cause a parse error. It produces a different legal tree.
</Depth>

<Depth level={3}>
Postfix operators and calls fit the same loop. `f(x)` and `labels["env"]` are infix steps for `(` and `[` with a high power, whose right side is an argument list or an index instead of one expression.
</Depth>

## [play] Change a number, change the tree

Step the parser through a rule and watch each operator compare its power with the caller's minimum. Then change the numbers in the table and see the same tokens parse into a different tree, and the alert change its answer.

## [lens] How each language parses its own operators

Go's parser is this loop. CPython's grammar spells precedence as a chain of rules. JavaScript parsers use a precedence loop with special cases. rustc parses by precedence, and rust-analyzer names its function after binding power.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={2}>
Unary minus is where languages disagree. Python reads `-2 ** 2` as `-(2 ** 2)`. JavaScript refuses to guess and makes it a syntax error. Choose a prefix power on purpose, and test it.
</Depth>
