        type Stamp struct {
            L      uint64 // Lamport time
            Server uint16 // breaks ties, so the order is total
        }

        func (a Stamp) Less(b Stamp) bool {
            if a.L != b.L {
                return a.L < b.L
            }
            return a.Server < b.Server
        }

        type Message struct {
            ID    string
            Room  string
            Text  string
            Stamp Stamp
        }

        // Clock is a Lamport clock: one counter per server.
        type Clock struct {
            mu sync.Mutex
            l  uint64

        // Tick stamps an event. seen is the largest Lamport time it depends on (0 if none).
        func (c *Clock) Tick(seen uint64) uint64 {

      - text: "9: it copies the sender's value."
        why: Then the receive and the send would share a number. Every event after a cause must be strictly larger.
  engineer:
    question: Event a has Lamport time 5 and event b has Lamport time 9, on different servers. What do you know?
    options:
      - text: b did not happen before a. Whether a caused b is unknown.
        correct: true
        why: Right. If b had happened before a, b's number would be smaller. A smaller number for a is consistent with a causing b and with the two being concurrent.
      - text: a happened before b.
        why: The clock guarantees only one direction. Two servers that never talked can reach 5 and 9 on their own.
      - text: They are concurrent, because they are on different servers.
        why: Events on different servers are linked whenever a chain of messages connects them. The numbers alone cannot tell you whether one does.
  deep:
    question: A user posts on server A, then phones a colleague, who posts on server B. B's post gets the smaller Lamport time and sorts first. What went wrong?
    options:
      - text: The causal link went through the phone call, outside the system, so no message carried A's time to B.
        correct: true

        why: Lamport times never read a wall clock, so skew cannot change them.
      - text: The tie-break by server id was applied the wrong way round.
        why: A tie-break only decides between equal times. Here B's time was strictly smaller.

      job: Travels with the message and sorts by L, then by server id.
    - role: Seen time
      example: the largest L the client has shown the user
      job: Carries a causal link that does not travel as a server message, such as a user reading before replying.
  useWhen:
    - Every replica must show the same order, and that order must never put an effect before its cause.
    - Breaking ties between concurrent updates deterministically, for example in last-write-wins or in sequence CRDTs.
    - Totally ordered broadcast or mutual exclusion, as in Lamport's original paper.
  avoidWhen:
    - You need to know whether two events were concurrent. Use vector clocks.
    - The order must match real time for things outside the system, such as audit logs a regulator reads. Use synchronised clocks or a hybrid logical clock.
    - One leader already numbers every write. Its sequence number is a simpler total order.
  tradeoffs:
    - Costs one integer per message and no extra round trips.
    - The order is consistent with causality but arbitrary between concurrent events.
    - Causal links outside the system, like a phone call or a client that skips seen, are invisible unless you carry the stamp across.
  lookalikes:
    - name: Wall-clock timestamp
      how: Close to real time but wrong under skew, and a cause can carry the later time.
    - name: Vector clock
      how: One counter per server. Detects concurrency, at the price of a vector on every message.
    - name: Hybrid logical clock
      how: A physical time plus a logical counter. Keeps the clock condition and stays within the clock skew of real time.
    - name: Raft term
      how: Also a number that only grows and is pushed forward by messages, but it counts elections, not events.

## [concept] Lamport clocks

**Give every event a counter instead of a time. Each server ticks on every event and jumps past any number a message brings, so a cause always gets the smaller number.**

Servers cannot agree on the time. Their clocks drift and disagree by milliseconds, which is plenty for a reply to look older than its question. A <Term id="lamport-clock">Lamport clock</Term> gives up on time and counts events instead, in a way that respects cause and effect.

<Depth level={2}>
Two rules. Every server increments its counter between any two of its events. Every message carries the sender's counter, and the receiver sets its own to max(own, message) + 1. Then if event a <Term id="happened-before">happened before</Term> b, the number of a is smaller. Sort by (counter, server id) and every server computes the same <Term id="total-order">total order</Term>.
</Depth>

<Depth level={3}>
Lamport's 1978 paper calls these rules IR1 and IR2, and calls the guarantee the <Term id="clock-condition">clock condition</Term>: a → b implies C(a) < C(b). The paper notes the converse cannot hold, since it would force any two <Term id="concurrent-events">concurrent</Term> events to share a time. The tie-break is any fixed order of the processes, and different valid clocks give different total orders. Only the happened-before partial order is fixed by the run.
</Depth>

## [problem] Sort by the server's timestamp

A team chat runs on three servers, one per region. Each server stamps the messages it accepts with its own clock and replicates them to the others. The timeline sorts by that stamp. In testing, on one laptop, it is perfect.

Read it once. The sort assumes the stamps of two servers can be compared.

<Depth level={2}>
They can only be compared if the clocks agree to better than the time between two related messages. A reply typed 60 ms after a question needs clocks that agree within 60 ms, every time, on every pair of servers.
</Depth>

<Depth level={3}>
NTP over a WAN typically keeps clocks within milliseconds to tens of milliseconds, and a correction can step a clock or slew it. Leap second handling, a VM pause or a bad time source can widen the gap to seconds. None of that raises an error. The stamps are simply wrong.
</Depth>

## [pain] Then a change request arrives

**Change request:** a reply must never show above the message it answers.

Users in one region report replies above the questions they answer, mostly in fast back-and-forth threads. The server there runs 80 ms behind. Someone moves the stamp to an NTP-disciplined clock, the marked line. Fewer reports. They do not stop.

<Depth level={2}>
<Term id="clock-skew">Clock skew</Term> shrinks with better sync but never reaches zero, and a reply can follow its question by less than any bound you pick. The bug is the assumption that two machines' times order two events. They only do when the gap between the events is larger than the skew.
</Depth>

<Depth level={3}>
Google's Spanner shows what it costs to make physical time safe: TrueTime returns an interval, and a commit waits out the uncertainty, a few milliseconds, before it becomes visible. A chat server does not need real time at all. It needs causes before effects.
</Depth>

## [morph] Count events instead of reading clocks

Drag the slider. A Lamport clock appears between the server and its stamp, and a receive path appears that pushes the clock forward.

The stamp is now (L, server), where L comes from the counter. The client sends the highest L it has shown the user, because reading the question before replying is the causal link, and the server ticks past it.

<Depth level={2}>
The `seen` parameter is the part people forget. The question reached B as a replicated message, which already moved B's clock. But a client can talk to a different server than the one that replicated to it, and only the client knows what it showed. Carrying `seen` makes the user's read part of the system.
</Depth>

<Depth level={3}>
<Lang only="go">`Stamp.Less` is the only comparison anyone should use. A second copy with the tie-break reversed would give two servers different orders.</Lang>
<Lang only="python">`Stamp` is a `NamedTuple`, so `sorted(..., key=lambda m: m.stamp)` compares L first and the server id second with no comparator code.</Lang>
<Lang only="typescript">`byStamp` returns a negative, zero or positive number, as `Array.prototype.sort` expects. The `||` falls through to the server id only when the Lamport times are equal.</Lang>
<Lang only="rust">`#[derive(PartialOrd, Ord)]` on `Stamp` orders by `lamport`, then `server`, so `sort_by_key(|m| m.stamp)` is the whole timeline.</Lang>
</Depth>

## [walk] Follow one reply across two servers

A question on server A, a reply on server B, whose wall clock is 80 ms slow. Use the numbered buttons.

<Depth level={2}>
Notice that B's clock jumped from 2 to 6. That is normal: a server that has been quiet catches up the moment it hears from a busier one. Lamport times say nothing about how much time passed.
</Depth>

<Depth level={3}>
<Lang only="go">Tick holds a mutex for two instructions. Under contention a CAS loop on `atomic.Uint64` avoids parking goroutines, but the mutex is rarely the bottleneck next to a network round trip.</Lang>
<Lang only="python">The lock matters with threads because `max` and the assignment are separate bytecodes, and another thread can run between them.</Lang>
<Lang only="typescript">Node never interrupts synchronous code, so `tick` is atomic by construction. Worker threads would each need their own clock or a shared `Atomics` cell.</Lang>
<Lang only="rust">`fetch_update` returns the previous value, so the new one is recomputed as `prev.max(seen) + 1`, the same value the closure stored.</Lang>
</Depth>

## [again] The same skew, with Lamport time

The same cluster, the same 80 ms skew, the same question and reply. The test passes: the question sorts first on every server, and nothing reads a wall clock any more.

<Depth level={2}>
The skew is still there. It just no longer matters for order. Keep wall-clock time in the message as a display field ("sent 14:02"), and never sort by it.
</Depth>

<Depth level={3}>
What the order still cannot do is honour links outside the system. If one user posts and then phones a colleague, who posts on another server, the second post can sort first. Lamport's paper names this anomalous behaviour and gives two fixes: carry the timestamp across yourself, or use physical clocks synchronised well enough to respect the outside link.
</Depth>

## [lens] How each language holds the clock

The clock is one integer and one function in every language. The differences are in how you make `tick` atomic and how you get one comparator that every server shares.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Lamport times usually live inside a protocol rather than in your code. Sequence CRDTs such as Automerge use them to order concurrent inserts, and last-write-wins registers use them as the "time". In both, the server or actor id is the tie-break, exactly as here.
</Depth>

<Depth level={3}>
Hybrid logical clocks combine the two kinds of time: take the physical clock, but never go below the largest timestamp seen, and add a counter when the physical part does not move. CockroachDB orders transactions with one. The result stays within the clock skew of real time and still satisfies the clock condition.
</Depth>
