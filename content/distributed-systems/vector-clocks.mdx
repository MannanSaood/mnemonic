        type VV map[string]uint64 // one counter per replica that wrote

        type Version struct {
            Items map[string]int
            VV    VV
        }

        // Add records a local write: tick this replica's own entry.
        func (v *Version) Add(self, sku string) {
            v.Items[sku]++
            v.VV[self]++
        }

        // Compare says whether a happened before b, after it, or neither (concurrent).
        func Compare(a, b VV) Order {
            less, more := false, false
            for k, x := range a {
                if x > b[k] {
                    more = true
                }
            }
            for k, y := range b {
                if y > a[k] {
                    less = true
                }
            }
            switch {
            case less && more:
                return Concurrent
            case less:
                return Before
            case more:
                return After
            }
            return Equal
        }

  engineer:
    question: Two versions of a cart carry the vectors [2,1,0] and [1,2,0]. What is their relation?
    options:
      - text: Concurrent. Each is ahead of the other in one entry.
        correct: true
        why: Right. The first is ahead in A's entry, the second in B's. Neither saw all of the other's writes, so a store must keep both or merge them.
      - text: The first happened before the second, because its first entry is larger.
        why: Happened-before needs every entry to be smaller or equal, with at least one smaller. One larger entry is not enough.
      - text: They are equal, because the entries add up to the same total.
        why: Totals mean nothing. [2,1,0] and [1,2,0] record different writes on different replicas.
  deep:
    question: Dynamo kept a timestamp with each (node, counter) pair and dropped the oldest pair once a vector reached about ten entries. What can go wrong?
    options:
      - text: After truncation the store may not see that one version descends from another, and reports a conflict that is not real.
        correct: true
        why: Right. A dropped entry looks like a 0, so a descendant can seem to be missing a write. The result is a false conflict, extra siblings for the app to merge, and no data loss. The Dynamo paper notes this risk and that it had not surfaced in production.

        why: Dropping an entry can only make vectors look less ordered, not more. A missing entry never makes one vector dominate another that it did not dominate before.
      - text: The clocks drift, because the timestamps are used to order versions.
        why: The timestamps only pick which pair to drop. Ordering still comes from the counters.

  useWhen:
    - Several replicas or devices accept writes for the same data without a leader, and losing a write silently is not acceptable.
    - You need to know whether a message or update could have caused another, for debugging, tracing or causal delivery.
    - Syncing peers that should exchange only what the other is missing.
  avoidWhen:
    - A single leader orders all writes. One sequence number (an LSN or a revision) already gives a total order.
    - Thousands of writers per item. Vectors grow with the number of writers; use per-replica entries or dotted version vectors.
    - The data has a merge that needs no history, such as a counter or a set designed as a CRDT.
  tradeoffs:
    - One entry per writer travels with every version, so size grows with the number of replicas that ever wrote.
    - Detecting a conflict is not resolving it. Someone must write the merge, and a union can bring deleted items back.
    - Pruning old entries keeps vectors small and can turn ordered versions into false conflicts.
  lookalikes:
    - name: Lamport clock
      how: One counter for everyone. Consistent with causality, so a cause always has the smaller number, but it cannot detect concurrency.
    - name: Last-write-wins timestamp
      how: Picks one version by time and drops the other. Simple and lossy when writes are concurrent.
    - name: Hybrid logical clock
      how: A physical timestamp plus a counter. It orders events close to real time and respects causality, but it is still one number and cannot detect concurrency.
    - name: CRDT
      how: Builds the merge into the data type so concurrent versions always combine without conflicts. Many CRDTs use version vectors inside.

## [concept] Vector clocks and version vectors

**Keep one counter per node instead of one per system. Comparing two vectors entry by entry tells you whether one event saw the other, or whether they were concurrent.**

A <Term id="lamport-clock">Lamport clock</Term> gives every event one number. If one event caused another, the cause has the smaller number. The reverse does not hold, so a smaller number tells you nothing about cause. A <Term id="vector-clock">vector clock</Term> fixes that by keeping a separate counter for each node.

<Depth level={2}>
The rules are short. On every local event, a node ticks its own entry. A message carries the sender's vector, and the receiver takes the entry-wise maximum with its own before ticking. To compare two vectors: if every entry of a is ≤ the matching entry of b, and one is smaller, then a <Term id="happened-before">happened before</Term> b. If each is ahead somewhere, they are <Term id="concurrent-events">concurrent</Term>. A <Term id="version-vector">version vector</Term> applies the same idea to data: it is attached to a version of a key and ticks only on writes.
</Depth>

<Depth level={3}>
Lamport defined happened-before and the scalar clock in 1978, and proved the clock condition: if a happened before b, then C(a) < C(b). Vector clocks came a decade later, from Fidge and from Mattern independently, around 1988. With vectors the relation is exact in both directions: a happened before b if and only if V(a) < V(b). Version vectors for replicated files are older still (Parker and others, 1983), designed to detect conflicting copies in a partitioned file system.
</Depth>

## [problem] Keep the newer cart

A shop's cart syncs between replicas: a phone app that works offline, a laptop, and a store node. When one replica receives another's cart, it keeps whichever has the later `updated_at`. It is the obvious rule, and it works whenever one device is used at a time.

Read it once. The rule assumes one of the two carts is newer.

<Depth level={2}>
"Newer" here means "has a later wall-clock timestamp". Two devices can each change the cart while offline. When they sync, one of them has the later clock, and its cart replaces the other completely, including items the other added.
</Depth>

<Depth level={3}>
Wall clocks make it worse: phones drift and get corrected by NTP, so the device that wrote later can carry the earlier timestamp. But the bug is not the clock. Even with perfect clocks, two independent edits have no "newer" one.
</Depth>

## [pain] Then a change request arrives

**Change request:** carts edited on two devices while offline must keep every item.

Support has tickets about items vanishing from carts after a phone comes back online. Someone reads that wall clocks skew and swaps the timestamp for a Lamport counter, the marked lines. Clock skew is gone. Items still vanish.

<Depth level={2}>
The Lamport counter does give an order consistent with causality: if the phone saw the laptop's cart before editing, the phone's counter is larger. But when neither saw the other, the counters still compare as smaller or larger, and the "smaller" cart is dropped. The code cannot tell "this replaced that" from "these happened apart".
</Depth>

<Depth level={3}>
Every last-write-wins rule has this shape, whatever it compares: wall time, Lamport time, or a hybrid logical clock. It turns a partial order into a total one by inventing a winner, and the loser's write disappears without an error.
</Depth>

## [morph] Give every replica its own counter

Drag the slider. A version vector appears between the store and its decision, and a third outcome appears: siblings.

Each version now carries one counter per replica. Comparing two vectors gives one of three answers. Theirs saw ours, so replace. Ours saw theirs, so ignore. Neither saw the other, so keep both as <Term id="siblings">siblings</Term> and merge them later.

<Depth level={2}>
The vector ticks only on writes, not on every message. That is the difference between a version vector and a vector clock: two replicas that exchange the same cart end up with the same vector, so the second sync compares as equal and does nothing.
</Depth>

<Depth level={3}>
<Lang only="go">Maps make the vector sparse: a replica that never wrote has no key, and reading it gives 0. That also means a new device needs no schema change.</Lang>
<Lang only="python">A dict makes the vector sparse: a replica that never wrote has no key, and `.get(k, 0)` reads it as 0. A new device needs no schema change.</Lang>
<Lang only="typescript">A record makes the vector sparse: a replica that never wrote has no key, and `?? 0` reads it as 0. A new device needs no schema change, and the vector is plain JSON.</Lang>
<Lang only="rust">`compare` returns `Option<Ordering>`, the same shape as `PartialOrd::partial_cmp`. That is the honest type: version vectors are partially ordered, and `None` is the concurrent case the old code could not express.</Lang>
</Depth>

## [walk] Follow two offline edits to one cart

Two devices, one cart, no connection between them for a while. Step through what happens when they sync. Use the numbered buttons.

<Depth level={2}>
Siblings move the conflict to the place that knows how to resolve it. For a cart, take the union of items. For a document, show both and ask. The store's job is to never pick for you.
</Depth>

<Depth level={3}>
Union has a known cost. An item removed on one device and untouched on the other comes back after the merge, because the union cannot tell "removed" from "never added". The Dynamo paper reports exactly this for Amazon's cart: an add is never lost, and a removed item can reappear. To fix it, record removals too, which is what CRDT sets such as an observed-remove set do.
</Depth>

## [again] The same request, from a third device

The same request comes from a customer with a tablet as well. No code above changes. The tablet's writes appear as a new key in the vector, Compare already treats a missing key as 0, and the merge function in the new file handles any number of siblings.

<Depth level={2}>
The merged vector is the entry-wise maximum of the siblings, plus one tick for the replica doing the merge. It is therefore ahead of every sibling, so the merge replaces them everywhere it goes.
</Depth>

<Depth level={3}>
Vectors grow with every replica that ever wrote. Riak first gave each client an entry, and vectors grew with every client. Per-replica entries keep them small, but then the store cannot tell apart the writes of many clients going through one replica, and siblings pile up. Riak's users called it sibling explosion. <Term id="dotted-version-vector">Dotted version vectors</Term>, used by Riak from 2.0, add one extra pair naming the exact write, which keeps vectors small and conflicts real.
</Depth>

## [lens] How each language holds a vector

Every language can implement this in a page of code, as above. The differences are in how a missing entry reads, and in whether the map iterates in a stable order, which matters as soon as you hash a vector or send it over the wire.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Most databases that use version vectors hide them behind an opaque context. Riak returned a vector clock with each read and expected it back on the next write, so the server could tell whether the write had seen the siblings. Treat such a context as an opaque token, and always send back the one you read.
</Depth>

<Depth level={3}>
Collaborative editors use the same idea for sync. A Yjs peer sends its state vector, one counter per client, and the other peer replies with only the updates that vector has not seen. The vector is not deciding conflicts there; the CRDT does. It is answering "what are you missing?" exactly.
</Depth>

### Vector clock or version vector

They look the same and answer different questions. A vector clock ticks on every event, including sends and receives, and orders events in a run. A version vector ticks only when data changes, and orders versions of that data. Use a vector clock to reason about messages, for example in a trace or a debugger like ShiViz. Use a version vector to decide whether a replica's copy replaces, ignores or conflicts with another.
