            seq  uint64

        // A PN-Counter: one entry per replica for increments, one for decrements.
        type Counter struct {
            P, N map[string]uint64
        }

        func (c *Counter) Inc(me string) { c.P[me]++ }
        func (c *Counter) Dec(me string) { c.N[me]++ }

        func (c *Counter) Value() int64 {
            var v int64
            for _, x := range c.P {
                v += int64(x)
            }
            for _, x := range c.N {
                v -= int64(x)
            }
            return v
        }

# ---------------------------------------------------------------- checks, one per depth
checks:
  overview:
    question: Two replicas of a CRDT have each received every update, in different orders. What is guaranteed?
    options:
      - text: They hold identical state.
        correct: true
        why: Right. That is strong eventual consistency. The merge does not depend on order or repetition, so the same updates give the same state.
      - text: They hold the value with the latest wall-clock time.
        why: Only an LWW-Register picks by timestamp, and even it uses a logical time with a tie-break. Counters and sets keep every update.
      - text: They agree only if updates arrived in the same order on both.
        why: That is what CRDTs remove. Commutative merges make the order irrelevant.
  engineer:
    question: Why does an OR-Set give every add its own tag?
    options:
      - text: So a remove deletes only the adds it has seen, and a concurrent add of the same item survives.
        correct: true
        why: Right. With names alone, a merge cannot tell "removed after you added" from "added after I removed". Tags make each add distinct.
      - text: So the set can be sorted by when items were added.
        why: Tags are unique, not ordered in time. The set's value ignores them except to decide what is live.
      - text: So the set uses less memory than storing the names.
        why: It uses more. Each add keeps a tag, and each removed tag stays as a tombstone until it can be collected.
  deep:
    question: A prepaid balance is a PN-Counter, and each replica refuses a withdrawal that would take its local balance below zero. What can happen?
    options:
      - text: Two replicas each approve a withdrawal of the last funds, and after the merge the balance is negative.
        correct: true
        why: Right. Each check saw only local state. Invariants like "never below zero" or "unique username" need coordination, or a share of the budget handed to each replica in advance.
      - text: The merge clamps the balance at zero.
        why: Clamping would break the merge laws and lose information. The merge is a per-replica max, and the value is whatever the sums say.
      - text: The second withdrawal is rejected when the replicas merge.
        why: Merges never reject. Both decrements are already applied locally, and the merge only combines them.

# ---------------------------------------------------------------- reference page
reference:
  roles:
    - role: Replica
      example: a phone, a laptop, a region
      job: Applies edits to its own copy at once, with no coordination.
    - role: State (payload)
      example: P and N vectors; tags and tombstones; (value, timestamp)
      job: Records enough history that two copies can be combined without guessing.
    - role: Merge
      example: { go: "Merge(other)", python: "merge(other)", typescript: "merge(other)", rust: "merge(&other)" }
      job: Combines two states into their least upper bound, so it is commutative, associative and idempotent.
    - role: Value
      example: sum(P) − sum(N); items with a live tag
      job: What the app shows, computed from the state.
  useWhen:
    - Devices or regions must accept writes while disconnected, and sync later in any order.
    - The data has a natural merge, such as counters, sets, maps of these, or collaborative text.
    - Sync runs over unreliable transport, where messages are duplicated, reordered or relayed through other peers.
  avoidWhen:
    - An invariant spans replicas, such as a balance that must stay non-negative or a unique username. That needs coordination.
    - Users expect one winner chosen with intent, and silently discarding the other (LWW) would be wrong.
    - Metadata growth matters and there is no way to collect tombstones, for example with replicas that may stay offline for months.
  tradeoffs:
    - State grows with history (tags, tombstones, one entry per replica); garbage collection needs to know every replica has seen a removal.
    - Convergence is guaranteed; matching what users meant is not. Add-wins, remove-wins and LWW are product decisions.
    - State-based CRDTs send whole states, which is simple and tolerant of loss; op-based or delta CRDTs send less but need stronger delivery guarantees.

## [concept] CRDTs

**Design the data type so that any two replicas can merge without asking anyone. If the merge is commutative, associative and idempotent, every replica that has seen the same edits holds the same state.**

A <Term id="crdt">CRDT</Term> (conflict-free replicated data type) is a counter, register, set, map or text type that any replica can edit offline. Two replicas exchange state, merge it, and come out identical. No leader decides the order and no person resolves a conflict.

<Depth level={2}>
The guarantee is <Term id="strong-eventual-consistency">strong eventual consistency</Term>: replicas that have received the same updates are in the same state. <Term id="eventual-consistency">Eventual consistency</Term> alone only promises that replicas agree once writes stop. The price is that each type has fixed rules for concurrent edits. A <Term id="pn-counter">PN-Counter</Term> keeps every increment. An <Term id="or-set">OR-Set</Term> lets an add win over a concurrent remove. An <Term id="lww-register">LWW-Register</Term> keeps one value and drops the other.
</Depth>

<Depth level={3}>
Shapiro, Preguiça, Baquero and Zawirski formalised two families in 2011. State-based CRDTs (CvRDTs) ship whole states. The states form a join semilattice, merge computes the least upper bound, and every update moves the state up. That makes merge commutative, associative and idempotent, so lost, reordered and duplicated messages are all harmless. Op-based CRDTs (CmRDTs) ship operations instead. Concurrent operations must commute, and the network must deliver them reliably, in causal order where the type requires it.
</Depth>

## [problem] Union the lists

A grocery app shares a household's shopping list across phones that are often offline in the shop. When a phone reconnects, it sends its copy and the server merges: the union of the items, so that no add is ever lost. Each phone does the same with what it gets back.

Read it once. The merge assumes that an item missing from one copy means "not added yet".

<Depth level={2}>
It can also mean "removed". A set of names cannot tell the two apart. The previous lesson met the same problem: merging siblings by union can bring deleted items back. Amazon's Dynamo paper reports exactly this for its shopping cart.
</Depth>

<Depth level={3}>
A counter has the mirror-image problem. A plain number merged by max loses one side's concurrent increments. Merged by sum, it counts the same increment again on every repeated sync. Neither merge is both correct and idempotent, because the number has forgotten who incremented.
</Depth>

## [pain] Then a change request arrives

**Change request:** removing an item on one phone must stick, and two people adding eggs offline must both count.

Users report deleted items coming back after a sync. Someone adds a `removed` set and subtracts it on every merge, the marked lines. Deleted items stay deleted. Now a user who removes bread can never put bread back on the list, on any phone, ever.

<Depth level={2}>
That fix is a two-phase set: remove wins, forever. It converges, but it encodes a rule no user expects. Names are the wrong identity. The second "bread" is a new add and needs an identity of its own.
</Depth>

<Depth level={3}>
Shapiro et al. call this the 2P-Set and contrast it with the OR-Set, which gives the opposite answer for a concurrent add and remove of the same element. Neither is wrong as a CRDT; the choice is about meaning. The paper picks the OR-Set for its shopping cart example because it minimises anomalies.
</Depth>

## [morph] Tag every add, tombstone what you saw

Drag the slider. The OR-Set state appears between the merge and the list: tags on adds, tombstones for removes, and a value computed from them.

Every add gets a tag that no other add will ever use, such as the replica name and a local sequence number. A remove tombstones the tags of that item which this replica can see. An item is on the list while it has at least one tag that no tombstone covers. Merge is a plain union of tags and of tombstones.

<Depth level={2}>
Union is the whole merge, and union is commutative, associative and idempotent. That is why you never have to think about sync order or duplicate deliveries again. All the thinking moved into the state, which now remembers which add each remove saw.
</Depth>

<Depth level={3}>
<Lang only="go">`Tag` is a comparable struct, so it can key a map directly. `map[Tag]struct{}` is the idiomatic set; the empty struct takes no space.</Lang>
<Lang only="python">A tuple is hashable, so `(replica, seq)` keys a dict and fills a set. `dict |= dict` and `set |= set` are the merge, in place.</Lang>
<Lang only="typescript">A template literal type, `` `${string}:${number}` ``, keeps tags as strings that `Map` and `Set` compare by value. Tuples would be compared by reference.</Lang>
<Lang only="rust">`BTreeMap` and `BTreeSet` keep tags sorted, so two equal states serialise to the same bytes. `extend` with cloned entries is the union.</Lang>
</Depth>

## [walk] Follow one concurrent remove and add

Two phones, both holding bread, both offline. One removes it; the other removes it and adds it again. Use the numbered buttons.

<Depth level={2}>
Add-wins is a product decision. For a shopping list it is what people expect: if anyone asked for bread, buy bread. For an access-control list, you might want remove-wins instead, so a revoked permission cannot come back through a concurrent grant.
</Depth>

<Depth level={3}>
Tombstones accumulate. They can be dropped only once every replica has seen the removal, which needs to know every replica and to hear from it; Shapiro et al. describe this with vector clocks. Optimised designs such as ORSWOT (OR-Set without tombstones) replace the tombstone set with a version vector per replica and a dot per element.
</Depth>

## [again] The same request, for quantities

The second half of the request: two people bumping the egg count offline. A new field gets its own CRDT, a PN-Counter, with one entry per replica for increments and one for decrements. The document's merge merges each field with its own rule. Nothing in the list code changes.

<Depth level={2}>
Merge takes the maximum of each entry, never the sum. Each replica only ever raises its own entry, so the maximum is always the latest value for that replica, and merging the same state twice gives the same result.
</Depth>

<Depth level={3}>
This composition is how real CRDT documents work: a map of registers, counters, lists and text, each merging by its own rules. Jake Lazaroff's interactive introduction builds an LWW map this way, one register per key. What no composition can give you is an invariant across replicas. Two phones that each remove the last egg will merge to −1.
</Depth>

## [play] Edit offline, then sync

Three replicas of one shopping list, each with a delivery slot (LWW-Register), an egg count (PN-Counter) and the items (OR-Set). Nothing syncs until you press a Sync button. Under each replica, a naive merge runs on the same edits so you can see what it would show.

Make every challenge happen, then sync in any order and watch the merge laws hold.

## [lens] How each language gets CRDTs

You can write a counter or a set in a page, as above. For documents and text, use a library: the sequence types are hard to get right and the good libraries compress their metadata heavily.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Yjs and Automerge are the two widely used document libraries. Both sync by exchanging what the other side is missing: Yjs sends a state vector, Automerge exchanges change hashes. Both run in the browser and on servers, and Automerge's core is Rust.
</Depth>

<Depth level={3}>
Text is where CRDT design gets subtle. Concurrent inserts at the same position must interleave the same way on every replica, and some algorithms interleave runs of characters from two typists. Each insert gets an identifier ordered by a Lamport-style counter and a replica id, which is the lesson before last at work inside the data type.
</Depth>

### What each type does with concurrent edits

| Type | State | Merge | Concurrent edits |
|---|---|---|---|
| G-Counter | one count per replica | max per entry | every increment kept |
| PN-Counter | two G-Counters | max per entry, both | every increment and decrement kept; no bound holds |
| LWW-Register | value + (Lamport, replica) | larger stamp wins | one assignment silently dropped |
| 2P-Set | adds + removes | union, both | remove wins forever; no re-add |
| OR-Set | tagged adds + tombstones | union, both | add wins over a concurrent remove |

The playground's idea of two replicas editing offline and syncing by hand comes from Jake Lazaroff's [An Interactive Intro to CRDTs](https://jakelazaroff.com/words/an-interactive-intro-to-crdts/), which builds an LWW register and map step by step. It is the best next read.
