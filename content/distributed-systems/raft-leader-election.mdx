        func (n *Node) run(ctx context.Context) {
            for {
                timeout := 150*time.Millisecond + rand.N(150*time.Millisecond)
                select {
                case <-n.heartbeat: // AppendEntries from a current leader, or a vote granted
                case <-time.After(timeout):
                    if !n.isLeader() {
                        n.startElection(ctx)
                    }
                case <-ctx.Done():
                    return
                }
            }
        }

        func (n *Node) startElection(ctx context.Context) {
            n.mu.Lock()
            n.term++
            n.votedFor = n.id
            n.role = Candidate
            n.persist() // term and vote must survive a crash
            term, votes := n.term, 1
            req := VoteRequest{Term: term, Candidate: n.id, LastLogIndex: n.lastIndex(), LastLogTerm: n.lastTerm()}
            n.mu.Unlock()
            for _, p := range n.peers {
                go func() {
                    reply, err := p.RequestVote(ctx, req)
                    if err != nil {
                        return // unreachable: its vote never arrives
                    }
                    n.mu.Lock()
                    defer n.mu.Unlock()
                    if reply.Term > n.term {
                        n.becomeFollower(reply.Term) // someone is ahead: step down
                    } else if reply.Granted && n.term == term && n.role == Candidate {
                        votes++
                        if votes > (len(n.peers)+1)/2 {
                            n.becomeLeader() // starts sending heartbeats at once
                        }
                    }
                }()
            }
        }

        // HandleRequestVote: one vote per term, first come, first served
        func (n *Node) HandleRequestVote(req VoteRequest) VoteReply {
            n.mu.Lock()
            defer n.mu.Unlock()
            if req.Term > n.term {
                n.becomeFollower(req.Term)
            }
            free := n.votedFor == None || n.votedFor == req.Candidate
            if req.Term < n.term || !free || !n.logUpToDate(req.LastLogIndex, req.LastLogTerm) {
                return VoteReply{Term: n.term, Granted: false}
            }
            n.votedFor = req.Candidate
            n.persist()
            n.resetElectionTimer() // granting a vote resets the election timer
            return VoteReply{Term: n.term, Granted: true}
        }

# ---------------------------------------------------------------- checks
checks:
  overview:
    question: A five-server Raft cluster loses its leader. How many votes does a candidate need to win?
    options:
      - text: "3, a majority of all five, counting its own vote"
        correct: true
        why: Right. A majority of the whole cluster, floor(5/2) + 1. Any two majorities of five share a server, and that server votes only once per term.
      - text: "2, a majority of the four servers still running"
        why: The majority is of the full cluster, not of whoever is reachable. Otherwise both sides of a partition could each find a majority of what they can see.
      - text: "5, every server"
        why: Then one crashed server would stop all elections. A majority is enough, which is why five servers tolerate two failures.
  engineer:
    question: Why does each Raft server pick its election timeout at random from a range, such as 150 to 300 ms?
    options:
      - text: So that one server usually times out first and collects its votes before the others become candidates.
        correct: true
        why: Right. With equal timeouts, followers time out together, each votes for itself, and the vote splits. The randomness must be larger than the time a vote request takes to arrive.
      - text: So that the leader can tell which follower is the fastest.
        why: The leader does not use timeouts to rank anyone. Timeouts only decide when a follower gives up waiting and stands.
      - text: To spread heartbeat traffic over time.
        why: Heartbeats come from the leader on its own fixed interval. The randomness is in the followers' election timers.
  deep:
    question: Why must a server write its current term and vote to disk before it replies to RequestVote?
    options:
      - text: If it crashed and restarted without them, it could vote again in the same term, and two candidates could each count it toward a majority.
        correct: true
        why: Right. One vote per term is what makes two leaders in one term impossible. Forgetting a vote after a restart breaks that, so the vote must be durable before it leaves.
      - text: So that the new leader can read the votes from the followers' disks.
        why: Votes are only sent to the candidate. Nobody reads them back from disk except the server itself after a restart.
      - text: Because the log entries must be written in the same file.
        why: Where it is stored does not matter; that it survives a crash before the reply is sent does.

# ---------------------------------------------------------------- reference page
reference:
  roles:
    - role: Follower
      example: S1, S2, S4, S5 between elections
      job: Answers the leader and candidates. Votes once per term. Becomes a candidate when its election timer runs out.
    - role: Candidate
      example: S3 after its timeout
      job: Raises the term, votes for itself, asks everyone else. Wins with a majority, steps down on a higher term, or times out and tries again.
    - role: Leader
      example: S3 in term 5
      job: Sends heartbeats so nobody else stands. Steps down the moment it sees a higher term.
    - role: Term
      example: a number on every message
      job: A logical clock. Each term has at most one leader; stale servers recognise they are behind by the number.
  useWhen:
    - Several servers must agree on one leader for a replicated log, configuration store or lock service, and must keep working when a minority fails.
    - You can run an odd number of servers (3 or 5) on reasonably reliable, low-latency links.
  avoidWhen:
    - You only need a leader for a background job and already run etcd, ZooKeeper or Kubernetes. Use their leases or election APIs rather than embedding Raft.
    - The servers are spread across continents. Elections and every commit wait on round trips to a majority.
  tradeoffs:
    - Five servers tolerate two failures, three tolerate one. Four also tolerate only one, so even sizes add cost without adding tolerance.
    - The election timeout trades failover time against false elections. It must be well above the time to reach every server, and well below the time between failures.
    - In basic Raft a leader cut off in a minority keeps believing it leads until it hears a higher term. CheckQuorum makes it step down by itself.
    - A server returning from a partition with an inflated term disrupts a healthy leader. Pre-Vote prevents that.
  lookalikes:
    - name: Bully algorithm
      how: The highest or lowest id that is alive wins. It needs accurate failure detection, which a partition breaks; Raft needs only a majority.
    - name: Leases
      how: A leader holds a time-limited lock from a coordination service. Often built on top of Raft (etcd) or Zab (ZooKeeper).
    - name: Paxos

## [concept] Raft: leader election

**Raft servers elect one leader per numbered <Term id="raft-term">term</Term>. A candidate needs votes from a <Term id="majority-quorum">majority</Term> of the cluster, and each server votes at most once per term, so no term can have two leaders.**

A follower that hears nothing from a leader for its <Term id="election-timeout">election timeout</Term> becomes a candidate: it raises the term, votes for itself and asks the others. The leader keeps everyone else quiet with <Term id="raft-heartbeat">heartbeats</Term>.

<Depth level={2}>
Three outcomes end an election. The candidate wins a majority and becomes leader. It hears from a leader whose term is at least its own and goes back to being a follower. Or nobody wins, a <Term id="split-vote">split vote</Term>, and the candidates time out and try again in a new term. Random timeouts make the third case rare: one server usually wakes first and wins before the others stand.
</Depth>

<Depth level={3}>
The term is the safety net for everything else. Every message carries one; a server that sees a higher term adopts it and becomes a follower, and a message with a lower term is rejected. A deposed leader never needs to be told it lost: the first message from the new term tells it.
</Depth>

## [problem] Replicas that take over on their own

A database has one primary and two replicas. Each replica watches the primary's heartbeats, and if it hears nothing for 3 seconds it promotes itself. In testing, kill the primary and a replica takes over within seconds.

<Depth level={2}>
Each replica decides alone, from what it can see. That is the flaw: "the primary is dead" and "I cannot reach the primary" look the same from inside one server.
</Depth>

<Depth level={3}>
This is a failure detector with no agreement step. A timeout can only ever say "I have not heard"; turning that into "and therefore I lead" needs everyone else's view too.
</Depth>

## [pain] Then a change request arrives

**Change request:** two replicas promoted themselves in the same second last week. Make failover deterministic, so the lowest-numbered live replica takes over.

The fix works for crashes. Then a switch fails and splits the network. The primary can still reach one replica, the other replica can reach neither. That replica is the lowest live id it can see, so it promotes itself. Two primaries accept writes for twenty minutes: a <Term id="split-brain">split brain</Term>.

<Depth level={2}>
"Lowest live id" is decided from each server's own view of who is alive, and a partition gives each side a different view. Any rule that each server evaluates alone has the same hole.
</Depth>

<Depth level={3}>
The repair is worse than the outage: two divergent histories of writes, and no record of which came first. Fencing tokens (the previous lesson) stop a stale primary's writes from landing; they do not stop two from being elected.
</Depth>

## [morph] Ask for votes instead of deciding alone

Drag the slider. The fixed watchdog becomes a random election timer, the replica becomes a candidate that must collect votes, and taking over needs 3 of 5.

Hover a box in the diagram to see its code.

<Depth level={2}>
In the partition above, only the side with a majority can elect. The side without one keeps timing out and raising its term, but it can never collect enough votes. The paper's timing rule ties the numbers together: the time to reach every server must be much less than the election timeout, which must be much less than the time between failures. It suggests 150 to 300 ms as a conservative range; etcd defaults to a 100 ms heartbeat and a 1000 ms election timeout.
</Depth>

<Depth level={3}>
Votes have one more condition, covered fully in the next lesson: a server refuses its vote if its own log is more up to date than the candidate's, comparing the term of the last entry and then its index. That is what stops a server missing committed entries from becoming leader.
</Depth>

## [again] The same partition, with Raft

The same switch failure: two servers on one side, three on the other. The side of three elects a leader in a higher term within a few hundred milliseconds. The side of two can never get three votes. If the old leader was on that side it can still think it leads, but it cannot commit anything, and it steps down the moment the network heals.

<Depth level={2}>
Two extensions make partitions smoother. <Term id="check-quorum">CheckQuorum</Term> makes a leader step down when it has not heard from a majority for an election timeout. <Term id="pre-vote">Pre-Vote</Term> makes a server ask whether it could win before raising its term, so a server returning from a partition does not depose a healthy leader.
</Depth>

<Depth level={3}>
The paper measured this. With no randomness, elections in their five-server cluster took more than 10 seconds because of repeated split votes; adding just 5 ms of randomness brought the median down to 287 ms. In the playground messages take 15 to 21 ms, so it needs more randomness than that to see the same effect.
</Depth>

### Why odd numbers

A majority of 3 is 2, so 3 servers survive 1 failure. A majority of 4 is 3, so 4 servers also survive only 1, and every election and commit waits for one more server. A majority of 5 is 3, so 5 servers survive 2. That is why clusters are sized 3 or 5, and rarely more: each extra pair adds one more tolerated failure and makes every commit wait on more servers.
