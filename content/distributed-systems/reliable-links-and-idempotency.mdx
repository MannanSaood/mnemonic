    question: A payment request times out after 2 seconds. What does the checkout know?
    options:
      - text: Nothing certain. The request may have been lost, or the charge may have happened and the reply been lost.
        correct: true
        why: Right. Silence looks the same in both cases, which is why a plain retry can charge twice.
      - text: The charge did not happen, because the service never answered.
        why: The service may have charged the card and then had its reply dropped, or be slower than the timeout.
      - text: The charge happened, because TCP guarantees delivery.
        why: TCP only guarantees delivery inside one connection while it stays up. A timeout or a reset tells you nothing about what the service did.
  engineer:
    question: How do you make POST /charges safe to retry?
    options:
      - text: The client creates one key per payment and sends it on every attempt. The server stores the key with the result and returns the stored result for a repeat.
        correct: true
        why: Right. The key names the intent, not the attempt, so the server can tell a retry from a new payment.
      - text: The client creates a fresh key for each attempt, so every request is unique.
        why: Then every retry looks like a new payment, and the key does nothing.
      - text: The server rejects a second charge of the same amount on the same card within a minute.
        why: That blocks a customer who really does buy the same thing twice, and still lets a retry through after a minute.
  deep:
    question: Why must the server save the idempotency key in the same transaction as the charge?
    options:
      - text: If it crashes between the two, a charge exists without its key, and the retry charges again.
        correct: true
        why: Right. The check-and-record has to be atomic with the effect. Saving the key first has the opposite bug, a key with no charge, so the retry is told it succeeded.
      - text: Because a transaction makes the query faster.
        why: Speed is not the point. The point is that the charge and the key exist together or not at all.
      - text: So that two different payments can never share a key.
        why: A unique constraint on the key does that. The transaction is about crashes between the two writes.

# ---------------------------------------------------------------- reference page
reference:
  roles:
    - role: Sender
      example: the checkout client
      job: Sends, starts a timer, and resends with the same key when no reply arrives.
    - role: Link
      example: the network, proxies and load balancers in between
      job: Delivers, drops, delays or duplicates messages. Promises nothing.
    - role: Receiver
      example: the payment service
      job: Does the work and records the key with the result, in one transaction.
    - role: Deduplication store
      example: the idempotency_keys table
      job: Maps each key to the first result for long enough to cover every retry.
  useWhen:
    - Any request that changes state and might be retried by a client, a proxy, a queue or a person pressing the button again.
    - Consumers of a queue with at-least-once delivery, where every message can arrive twice.
  avoidWhen:
    - The operation is already idempotent, such as setting a status or a PUT of the whole resource. Retry it as is.
    - Reads. A GET is safe to repeat without a key.
  tradeoffs:
    - The server must store keys and results, and decide how long to keep them. A retry after the key expires is treated as new.
    - A second request with the same key but different parameters must be rejected, or a bug in the client goes unnoticed.
    - Two attempts arriving at once need a unique constraint or a lock, or both can pass the lookup.
    - Retries cost extra messages and latency, and need timeouts and backoff, which are the next lesson.
  lookalikes:
    - name: TCP sequence numbers
      how: The same idea inside one connection. TCP drops duplicate segments, but its guarantee ends when the connection breaks.
    - name: Transactional outbox
      how: Solves the sending side. It makes sure a message is sent at least once after a commit; the receiver still needs deduplication.
    - name: Exactly-once in stream processors
      how: Systems such as Kafka transactions get an exactly-once effect by committing offsets and outputs atomically, the same trick as storing the key with the charge.

## [concept] Reliable links and idempotency

**On a real network, a sender that hears nothing cannot tell whether its request was lost or the reply was. Retrying until acknowledged makes delivery reliable, and the receiver makes the repeats harmless.**

Retries turn a lossy link into <Term id="at-least-once-delivery">at-least-once delivery</Term>. The receiver then needs a way to recognise a request it has already handled, usually an <Term id="idempotency-key">idempotency key</Term>.

<Depth level={2}>
There are three delivery policies. Send once and never retry: <Term id="at-most-once-delivery">at most once</Term>, no duplicates, but lost messages stay lost. Resend until acknowledged (<Term id="retransmission">retransmission</Term>): at least once, nothing lost, but some messages arrive twice. Add deduplication at the receiver and you get an <Term id="exactly-once-effect">exactly-once effect</Term>. Exactly-once *delivery* does not exist; exactly-once *processing* does.
</Depth>

<Depth level={3}>
The impossibility is the Two Generals problem in miniature. To know that the request arrived, the sender needs an acknowledgement; to know the acknowledgement arrived, the receiver needs one back, and so on with no last message. Some operations need no key because they are <Term id="idempotent-operation">idempotent</Term> already: "set the order status to paid" can run twice safely, "charge $40" cannot.
</Depth>

## [problem] A checkout that calls the payment service once

The checkout calls the payment service with a 5 second timeout. The service inserts a charge and returns its id. In tests, on a local network, every request gets a reply.

<Depth level={2}>
The timeout is good practice: without it a lost packet would hang the request forever. But the code treats a timeout as "the charge failed", which is only half the possibilities.
</Depth>

<Depth level={3}>
TCP retransmits lost segments and drops duplicates, so inside one healthy connection nothing is lost or doubled. The trouble starts above it: the connection resets, a proxy times out, the client gives up, or the service crashes after committing. None of that is TCP's to fix.
</Depth>

## [pain] Then a change request arrives

**Change request:** customers on mobile networks keep seeing payment errors. Make the checkout retry when the payment call times out.

The retry is two lines and it works: the errors drop. A week later, support finds customers charged twice for one order. Each double charge is a request whose reply was lost: the service charged the card, the checkout saw a timeout, and the retry was charged as a new payment.

<Depth level={2}>
The retry did not create the ambiguity; it made it visible in the ledger. Before the change, the same lost replies showed customers an error for a payment that had gone through. Neither version can be right, because neither lets the service tell a retry from a new payment.
</Depth>

<Depth level={3}>
Retries also happen where you did not write them: a load balancer that retries on a reset, a mobile app that resends on reconnect, a customer who presses Pay again. Each is another copy of the same request reaching the service.
</Depth>

## [morph] Give every payment a key

Drag the slider. The checkout now creates one key per payment and sends it on every attempt. The service checks the key first, in the same transaction that writes the charge.

Hover a box in the diagram to see its code.

<Depth level={2}>
Three things make it work. The key is made once per intent, before the first attempt. The lookup and the insert happen in one transaction, with a unique constraint on the key, so two attempts racing each other cannot both charge. And the service returns the stored result, so the retry gets the same answer the lost reply carried.
</Depth>

<Depth level={3}>
Stripe works this way: it saves the status code and body of the first request for a key and returns them for retries, compares the parameters and errors if they differ, and lets keys be pruned once they are at least 24 hours old. A retry after that window is treated as a new request, so the window must outlast every retry policy that can reach the service.
</Depth>

## [walk] Follow one payment with a lost reply

One payment whose first reply is lost, step by step. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`database/sql` gives you `BeginTx` and `Rollback` on defer. At Postgres's default isolation, two twins can both miss the key in the `SELECT`; the unique constraint makes the second `INSERT` into `idempotency_keys` fail, and its rollback removes its charge too.</Lang>
<Lang only="python">`with db.transaction():` in psycopg commits when the block exits normally and rolls back on an exception, so the charge and the key commit together. A racing twin fails on the unique key and its charge rolls back.</Lang>
<Lang only="typescript">With `pg`, a transaction is one checked-out client running `BEGIN` and `COMMIT`. Using `db.query` directly would send each statement on whichever pooled connection is free, outside any transaction.</Lang>
<Lang only="rust">An `sqlx` transaction rolls back when it is dropped without `commit()`, so every early `?` return undoes the charge. A racing twin fails on the unique key and its charge goes with it.</Lang>
</Depth>

## [again] The retry, the second time

The same change request after the refactor: retries are on, replies still get lost, and each lost reply costs one extra round trip instead of a second charge. The test above loses a reply on purpose and asserts one charge.

<Depth level={2}>
The client still needs limits. Retries need a timeout per attempt, a cap on attempts and spacing between them, or a slow service gets buried under its own retries. That is the next lesson.
</Depth>

<Depth level={3}>
The same pattern protects queue consumers. A broker with at-least-once delivery will redeliver a message whose acknowledgement was lost; the consumer stores the message id with its effect, in one transaction, and skips ids it has seen.
</Depth>

## [lens] How each language does it

None of the four standard HTTP clients retries a POST for you, and all four leave the key to you. What differs is how you bound an attempt: a context deadline in Go, a timeout argument in Python, an `AbortSignal` in TypeScript, a request timeout or `tokio::time::timeout` in Rust.

### Idempotent by design

Before adding a key, ask whether the operation can be made idempotent on its own. "Set the subscription to Pro" is safe to repeat; "add one month" is not. "Charge order 1042" with a unique constraint on the order id is safe; "charge $40" is not. A natural key from the domain often does the job of an idempotency key, and it survives client restarts that would lose a random one.
