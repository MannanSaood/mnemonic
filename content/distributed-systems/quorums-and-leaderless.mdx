    question: N = 3, W = 2, R = 2 with a sloppy quorum. Two home replicas are down during a write, so the write lands on two stand-in nodes. What can a reader see once the home replicas are back?
    options:
      - text: A quorum read of the home replicas can miss the write until hinted handoff delivers it.
        correct: true
        why: Right. The overlap argument counts the N home replicas. The write went to nodes outside that set, so a read of the home replicas has nothing to overlap with.
      - text: The new value, because R + W > N holds.
        why: R + W > N only works when both sets come from the same N replicas. A sloppy quorum breaks that assumption on purpose, to stay available.
      - text: An error, because the write did not reach its home replicas.
        why: The read succeeds. Two home replicas answer, and both are behind. Nothing tells the reader the newest version is elsewhere.
  deep:
    question: A QUORUM write reaches one replica of three, then times out, and the client is told it failed. What can later QUORUM reads return?
    options:
      - text: Sometimes the old value and sometimes the new one, until read repair or anti-entropy copies the new one everywhere and makes it stick.
        correct: true
        why: Right. Nothing rolls back the replica that took the write. A read that includes it returns the newer value; one that does not returns the older one. Repair then spreads the failed write.

        why: Leaderless stores do not roll back. A timeout means unknown, not undone, and the one replica that took the write keeps it.
      - text: An error until an operator repairs the key.
        why: Reads still succeed with two replies. Which version they return depends on which replicas answer.

reference:
  roles:
    - role: Coordinator
      example: whichever node the driver picked
      job: Forwards the request to the N replicas of the key and counts the answers.
    - role: Replica
      example: the 3 nodes that own the cart's partition
      job: Stores the key and answers reads with its newest version.
    - role: Quorum
      example: W = 2, R = 2 for N = 3
      job: How many answers make a write succeed or a read complete.
    - role: Stand-in node
      example: the next healthy node on the ring
      job: Holds a hinted write for a down replica in a sloppy quorum.
  useWhen:
    - Writes must keep working while any one node is down, without a leader election.
    - Data partitioned across many nodes, where per-key replication is cheaper than one leader per partition.
    - Reads that must see recent writes, but can tolerate an occasional stale answer during failures.
  avoidWhen:
    - Operations that need a single winner, like a unique username or a balance check. Use a lightweight transaction (Paxos) or a store with a leader.
    - Data that is updated concurrently in place and cannot be merged. Last-write-wins will drop updates silently.
  tradeoffs:
    - A higher W makes writes slower and less available; a higher R does the same for reads. W = N or R = N fails whenever one replica is down.
    - Quorum reads cost R round trips worth of load and wait for the slowest of the first R replies.
    - Sloppy quorums keep writes available during outages and give up the overlap guarantee until hints are delivered.
    - Failed writes are not rolled back. A timeout means the write may or may not be there.
  lookalikes:
    - name: Leader-follower replication
      how: One node orders all writes. Reads from the leader see everything; reads from followers lag. No quorum math, but a failover when the leader dies.
    - name: Raft and Paxos
      how: Also use majorities, but to agree on one order of operations. That gives linearizable reads; quorum reads alone do not.
    - name: Read repair and anti-entropy
      how: How the replicas converge after a quorum write missed some of them. They make the system eventually consistent; the quorum only makes single reads fresher.

## [concept] Quorums and leaderless replication

**Write each key to N replicas and wait for W of them. Read from R of them. If R + W > N, every read set shares a replica with every write set.**

There is no leader. Any node can take a request and act as the <Term id="coordinator">coordinator</Term>. It forwards the request to the key's N replicas (the <Term id="replication-factor">replication factor</Term>) and counts the answers. The read keeps the newest version it sees, so if one replica in the read set took the latest write, the read returns it.

<Depth level={2}>
The numbers are a trade. With N = 3, W = 2 and R = 2 (a majority <Term id="quorum">quorum</Term> on both sides), writes and reads keep working with one replica down. W = 1 makes writes fast and reads risky; R = 1 does the opposite. W = N or R = N makes every replica a single point of failure for that operation. The overlap only holds when R + W > N, and only for the N home replicas of the key.
</Depth>

<Depth level={3}>
Amazon's Dynamo paper (2007) made this design popular. Its services typically ran with N, R, W = 3, 2, 2. Cassandra, Riak and ScyllaDB follow the same model. Dynamo also used a <Term id="sloppy-quorum">sloppy quorum</Term>: requests go to the first N healthy nodes on the key's preference list, which may not be the home replicas, so writes stay available during failures. Those stand-ins keep the write with a hint and return it later through <Term id="hinted-handoff">hinted handoff</Term>.
</Depth>

## [problem] A cart written and read at ONE

A shop keeps carts in Cassandra with a replication factor of 3. The cart service writes and reads at consistency level ONE: the first replica to answer wins. It is fast, and in testing every replica was always up.

Read it once. The write succeeds as soon as one replica has it, and the read is satisfied by any one replica.

<Depth level={2}>
ONE for both means W = 1 and R = 1, so R + W = 2, which is not more than 3. A write can land only on replica 1, and the next read can be answered only by replica 3. Normally the other replicas catch up within milliseconds, so the window is small. When a replica is down or overloaded, the window is as long as the outage.
</Depth>

<Depth level={3}>
The DataStax drivers for Python and Node.js default to LOCAL_ONE, so many services run at R = W = 1 without anyone choosing it. Rows written in one place and read from another (a cart, a session, a draft) are exactly the data that shows the gap.
</Depth>

## [pain] Then a change request arrives

**Change request:** checkout must show every item the customer added to the cart, even while a node is down.

A node was restarted for a kernel patch. For the few minutes it was down, customers added items, went to checkout, and some items were missing. The obvious fix is the marked line: read at ALL.

<Depth level={2}>
ALL is R = N, so the read now sees every replica, and every write. It also needs every replica to answer. The next time one node of three is down, every checkout fails. The fix traded stale carts for an outage.
</Depth>

<Depth level={3}>
ALL also waits for the slowest replica. One replica in a long garbage collection pause sets the latency of every checkout, which is the opposite of why the cluster has three replicas.
</Depth>

## [morph] Make the read set and the write set overlap

Drag the slider. A quorum appears between the coordinator and the replicas.

Both the write and the read now use QUORUM, which is 2 of 3. Two plus two is more than three, so the two replicas that took the write and the two that answer the read share at least one. One replica can be down and both still work.

<Depth level={2}>
The change is one constant per language, and both paths must use it. Raising only the reads to QUORUM while writes stay at ONE gives R + W = 3, no overlap, and the same missing items. Treat the read and write levels as one setting.
</Depth>

<Depth level={3}>
Majority quorums are not the only overlapping pair. Any read and write quorums that must intersect work, which is why some systems make writes cheap (W = 1) and reads expensive (R = N), or the reverse. Flexible Paxos uses the same observation for consensus. What matters is that the sets come from the same N nodes.
</Depth>

## [walk] Follow one item into the cart and out again

One write and one read, with replica 3 down for the write and back for the read. Use the numbered buttons.

<Depth level={2}>
When the read sees replicas disagree, Cassandra can write the newer value back to the replica that was behind. That is <Term id="read-repair">read repair</Term>. It makes the next read cheaper, and it is how the overlap slowly turns into all three replicas agreeing.
</Depth>

<Depth level={3}>
Cassandra decides "newest" per cell, by the write timestamp the coordinator or client attached. That is <Term id="last-write-wins">last-write-wins</Term>. Two writes to the same cell at about the same time keep only the higher timestamp, even if its clock was wrong. Different cart items are different rows here, so adding two items at once is safe; changing the same item's quantity from two devices at once is not.
</Depth>

## [again] The same request, in a second region

The shop opens a second datacenter. QUORUM would now count replicas in both regions, and every checkout would wait on a cross-region round trip. The change is one setting: LOCAL_QUORUM, a majority of the replicas in the local datacenter, plus a driver policy that prefers local nodes.

<Depth level={2}>
LOCAL_QUORUM gives the overlap inside each region. A cart written in Europe and read in America straight after can still be stale, because the two regions' quorums do not overlap. Route a customer's requests to one home region, or accept the cross-region wait with QUORUM or EACH_QUORUM for that path.
</Depth>

<Depth level={3}>
Quorum arithmetic is per datacenter for LOCAL_QUORUM: with 3 replicas in each of two regions, a local quorum is 2 of the local 3. The global QUORUM would be 4 of 6.
</Depth>

## [lens] How each driver sets R and W

In Cassandra-style stores you never set R and W as numbers. You pick a consistency level per request, and the driver sends it to the coordinator. The coordinator turns it into a count. ONE, QUORUM, LOCAL_QUORUM and ALL exist in every driver; what differs is where you set them and what the default is.

### What R + W > N does not give you

It is not linearizability. A sloppy quorum can put the write outside the N replicas. A write that fails partway leaves its value on some replicas, where later reads may or may not find it. Two concurrent writes are resolved by timestamp, and one of them is lost. Two readers racing a write can see the new value and then the old one. For a single winner (a username, a seat, a balance), use a lightweight transaction or a store built on consensus.
