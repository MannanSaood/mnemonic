      - text: A copy of the data that a follower keeps for reads.

      - text: The lock service blocks its write.
        why: Writes go to storage, not through the lock service. The lock service has no say in them.

    question: Where must the fencing token be checked?
    options:
      - text: At the resource being protected, on every write.
        correct: true
        why: Right. Only the resource sees writes from both holders, so only it can tell that 33 arrived after 34.
      - text: In the lock service, when the holder renews.

      - text: In the worker, just before it sends the write.

  roles:
    - role: Lock service
      example: etcd, ZooKeeper, Consul, the Kubernetes Lease object
      job: Grants one lease at a time, expires it when not renewed, and issues a larger token with every grant.
    - role: Leader (lease holder)
      example: the worker running the invoice export
      job: Renews the lease while it works and sends its token with every write.
    - role: Fencing token
      example: { go: "Election.Rev()", python: "creation zxid of the lock znode", typescript: "lease.token", rust: "header revision" }
      job: A number that only grows, so a later holder always has a larger one.
    - role: Protected resource
      example: the export bucket, a database row, a file server
      job: Remembers the highest token it has accepted and rejects any write with a lower one.
  useWhen:
    - Exactly one worker should run a job, own a partition or act as primary, and two at once would corrupt data.
    - Holders can pause, be partitioned or be slow, which is every process on every real machine.
    - The resource can store one number and compare it on each write, such as a database row, an object store with conditional writes, or a service you control.
  avoidWhen:
    - The lock only saves work, like deduplicating a cache refill. An occasional double run is fine, and a TTL lock is enough.
    - The resource cannot check a token. Then you need idempotent writes or a resource that does its own concurrency control.
    - You need agreement on a sequence of values. That is consensus; use Raft rather than building it from locks.
  tradeoffs:
    - Shorter leases mean faster failover and more spurious failovers when a holder is merely slow.
    - Fencing needs the resource's cooperation; a third-party API that ignores the token gives no protection.
    - The lock service itself must be consistent (consensus-backed), or two holders can get the same token.
  lookalikes:
    - name: Raft term
      how: The same idea inside a protocol. A leader from an older term is ignored by servers that have seen a newer one.
    - name: Compare-and-swap write
      how: Writes only if the version is still what you read. It fences one row, without a lock service.
    - name: Redlock
      how: A lease across several Redis nodes. Kleppmann's analysis shows it relies on timing assumptions and produces no fencing token.
    - name: Cache lease
      how: A token that lets one client fill a missing cache key. It saves work rather than protecting correctness.

## [concept] Leader election, leases and fencing

**Elect a leader by giving it a lease, a lock that expires. A paused leader can outlive its lease without knowing it, so every write carries a fencing token and the storage rejects old ones.**

Many jobs need exactly one worker at a time: the nightly invoice export, the scheduler, the primary of a database. A lock service elects one by handing out a <Term id="lease">lease</Term>. The expiry is what lets the system recover when the holder dies. It is also what lets two workers both believe they hold it.

<Depth level={2}>
A worker that is merely paused looks dead from outside. Its lease expires, another worker takes over, and then the first one wakes up and carries on where it was. A <Term id="fencing-token">fencing token</Term> closes that gap. The lock service attaches a number to each grant, larger every time. Every write carries it, and the resource rejects a number smaller than one it has already accepted.
</Depth>

<Depth level={3}>
The lock service has to be right about who holds the lease, which makes it a consensus problem: etcd and ZooKeeper keep that state in a <Term id="majority-quorum">majority quorum</Term>. The token generalises the <Term id="raft-term">term</Term> of Raft or the epoch of ZAB. A number that only grows, checked on every message, makes a stale leader harmless without anyone having to tell it that it is stale.
</Depth>

## [problem] Hold the lease, then write

The billing service exports each day's invoices to object storage. Two workers run for availability, and a lock service decides which one does the export: whoever holds the `invoice-export` lease. The client library renews the lease in the background every few seconds. In staging, failover works perfectly.

Read it once. The code assumes that while it holds the lease, nobody else does.

<Depth level={2}>
That holds only while the worker keeps running. The lease is a promise about time, kept by the lock service's clock. The worker's view of it is only as fresh as its last renewal, and a worker that is not running is not renewing.
</Depth>

<Depth level={3}>
Kleppmann's 2016 article on distributed locking lists what can stop a process: stop-the-world GC, page faults that hit swap, a SIGSTOP, CPU contention, a VM migration. A delayed network packet has the same effect on the write. None of these is a crash, so nothing reports them.
</Depth>

## [pain] Then a change request arrives

**Change request:** an invoice export must never be overwritten by a worker that has lost its lease.

Last Tuesday a customer's export came out with yesterday's totals. The logs show worker A in a 15 s GC pause; B took over and wrote the correct file; A woke up and overwrote it. Someone adds a check of the lease right before the write, the marked lines. Two weeks later it happens again.

<Depth level={2}>
The check runs, passes, and the pause lands on the next line. Checking more often makes the window smaller and never closes it, because there is always a gap between the last check and the moment the bytes reach storage. Meanwhile both workers believe they lead: a small, silent <Term id="split-brain">split brain</Term>.
</Depth>

<Depth level={3}>
Jepsen's 2020 analysis of etcd 3.4.3 found that etcd's locks did not guarantee mutual exclusion under pauses and partitions, and in one test lost about 18% of acknowledged updates guarded by a lock. Its advice matches Kleppmann's: treat a lease as an optimisation, and protect the resource with a token it can check.
</Depth>

## [morph] Let the storage decide who is current

Drag the slider. A fencing token appears between the worker and the storage, and the lease check moves out of the worker into the storage.

The worker reads its token once, when it gets the lease, and sends it with every write. The storage keeps the highest token it has accepted and refuses lower ones. A paused worker can still send a stale write; it just cannot land.

<Depth level={2}>
Fence per resource that the lock protects, not per key. If the stale holder writes a key the new holder has not touched yet, a per-key check would let it through. Here the whole export bucket shares one highest token. Equal tokens are accepted, because the current holder writes many times.
</Depth>

<Depth level={3}>
<Lang only="go">`errors.Is(err, ErrStaleToken)` separates "someone newer leads" from a transient storage error. Only the second deserves a retry.</Lang>
<Lang only="python">`StaleToken` is its own exception class, so `except StaleToken` stops the loop while other errors still propagate.</Lang>
<Lang only="typescript">`put` returns `"ok" | "stale"`, a union the compiler makes the caller look at, instead of a rejection that a generic retry wrapper might swallow.</Lang>
<Lang only="rust">`Error::StaleToken { got, highest }` is its own variant, and the `match` handles it before `other?` propagates everything else.</Lang>
</Depth>

## [walk] Follow one pause through the system

A holds the lease with token 33; B is standing by. Use the numbered buttons.

<Depth level={2}>
Fencing does not stop A from believing it leads, and it does not shorten failover. It changes what a wrong belief costs: from overwritten data to one refused write and a log line.
</Depth>

<Depth level={3}>
The token must come from the same consensus that decides the holder. In etcd the revision of the lock key is assigned by the Raft log, so two grants can never share one and a later grant always has a larger one. A token from a separate counter, or from a random value as in Redlock, does not have that property.
</Depth>

## [again] The same pause, with tokens

The same 15 s pause on the same worker. B writes batch 12 with token 34; A wakes and sends batch 11 with 33; the store refuses it. The test pins that down.

<Depth level={2}>
Nothing about the lease changed: same TTL, same renewal. You can still tune the TTL for how fast failover should be, without it being a safety setting. Shorter leases fail over faster and cause more needless takeovers when a holder is slow; the token keeps both cases correct.
</Depth>

<Depth level={3}>
If the resource cannot check tokens, as with many third-party APIs, the next best tools are conditional writes (write only if the object's version is still the one you read) and idempotent operations. Both let the resource itself refuse a write that no longer makes sense.
</Depth>

## [lens] How each language meets a pause

Every runtime can pause, with or without a garbage collector, and every lock client library gives you a lease and a number that grows. What differs is where the pauses come from and what the library calls the number.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Look for the token in the library before you invent one. In etcd it is the revision of your lock or election key; in ZooKeeper, the zxid of your lock znode; in a database, a row version. Pass it all the way to the write, and make the resource compare it.
</Depth>

<Depth level={3}>
Kubernetes shows the pattern at scale. Controllers elect a leader with a Lease object and client-go's `leaderelection`, whose documentation says plainly that it does not fence. The API server does: every object carries a `resourceVersion`, and an update with a stale one is rejected. The lease decides who should work; the version check decides whose write counts.
</Depth>
