        impl Breaker {
            fn allow(&self) -> bool {
                let mut s = self.state.lock().unwrap();
                match *s {
                    State::Open { until } if Instant::now() < until => false,
                    State::Open { .. } => { *s = State::HalfOpen; true } // let a probe through

                let mut s = self.state.lock().unwrap();

                    (_, true) => State::Closed { failures: 0 },
                    (State::Closed { failures }, false) if *failures < 4 => State::Closed { failures: failures + 1 },
                    _ => State::Open { until: Instant::now() + Duration::from_secs(5) },

    question: Why add random jitter to the wait between retries?
    options:
      - text: So that clients that failed at the same moment do not all retry at the same moment.
        correct: true
        why: Right. Without jitter, a burst of failures comes back as a burst of retries, again and again.
      - text: So that each retry has a better chance of succeeding on its own.
        why: Randomness does not make one call more likely to succeed. It spreads many calls out over time.
      - text: To reduce the total number of retries.
        why: Jitter changes when retries happen, not how many. Limiting the count or using a budget reduces the total.

      - text: "27"
        correct: true
        why: Right. Each layer multiplies by 3, so 3 × 3 × 3. That is why you retry at one layer, usually the one closest to the user or the one that knows the call is safe.
      - text: "9"

      - text: "3"

    - role: Circuit breaker
      example: { go: "sony/gobreaker", python: "pybreaker", typescript: "cockatiel circuitBreaker", rust: "a small enum state machine" }
      job: Stops calling a dependency that is failing, fails fast instead, and probes for recovery.
    - role: Fallback
      example: the page without recommendations
      job: What users get while the dependency is unavailable.
  useWhen:
    - Every network call. A timeout is never optional; the default in most clients is to wait forever or for a long time.
    - Retries for brief, isolated failures of idempotent calls, at one layer of the stack.
    - A breaker and fallback for dependencies whose failure should cost a feature, not the whole page.
  avoidWhen:
    - Retrying calls that are not safe to repeat, unless they carry an idempotency key.
    - Retrying at every layer of a deep call chain.
    - A breaker on a dependency you cannot do without, where failing fast just fails faster; there, shed load or queue instead.
  tradeoffs:
    - A timeout too short fails calls that would have succeeded; too long and a slowdown fills your worker pool. AWS picks it from the latency percentile that matches an acceptable false-timeout rate, such as p99.9.
    - Backoff spreads retries out but does not reduce them when new requests keep arriving. Only fewer retries, or less load, does that.
    - A breaker adds a mode that is hard to test and can delay recovery. A retry budget is a simpler alternative many teams prefer.
    - Each mechanism needs metrics, or the first sign of it working is an angry user.
  lookalikes:
    - name: Bulkhead
      how: Gives each dependency its own pool of workers or connections, so one slow dependency cannot use them all.
    - name: Load shedding
      how: The server's side of the same problem. It rejects some requests early to keep the rest fast.
    - name: Rate limiting
      how: Caps how fast a caller may send, whether or not anything is failing.
    - name: Idempotency keys
      how: Make a retry safe. They say nothing about whether a retry is wise.

## [concept] Timeouts, retries, circuit breakers

**Every call to another service needs a bound on how long it may wait, a limit on how often it is repeated, and a way to stop calling when the other side is failing.**

Timeouts protect your workers. Retries hide brief failures. A <Term id="circuit-breaker">circuit breaker</Term> protects the dependency, and a <Term id="graceful-degradation">fallback</Term> protects your users.

<Depth level={2}>
The order matters. Without a timeout nothing ever fails, so retries never fire and a breaker never trips: requests just pile up. Retries without limits turn a dependency's bad minute into a <Term id="retry-storm">retry storm</Term>. Space them with <Term id="exponential-backoff">exponential backoff</Term> and <Term id="jitter">jitter</Term>, cap them, or give them a <Term id="retry-budget">budget</Term>.
</Depth>

<Depth level={3}>
The worst outcome is a <Term id="metastable-failure">metastable failure</Term>: the slowdown ends, but the load it caused does not. The dependency spends its recovered capacity on requests whose callers gave up long ago, those callers retry, and the loop holds itself up. Something has to cut the load: a breaker, a budget, load shedding, or servers that drop work whose <Term id="deadline-propagation">deadline</Term> has passed.
</Depth>

## [problem] A product page that waits on recommendations

Every product page calls a recommendations service for its carousel. The call has no timeout, and errors fall back to an empty list. It has worked for a year.

<Depth level={2}>
The error handling looks defensive, but it only covers errors. A call that hangs never errors. It holds one of the API's workers for as long as the recommendations service takes.
</Depth>

<Depth level={3}>
Default clients differ. Go's `http.DefaultClient` and Python's `requests` wait forever, `fetch` waits as long as the server does, and `httpx` gives up after 5 seconds. Few defaults match what a product page can afford.
</Depth>

## [pain] Then a change request arrives

**Change request:** recommendation calls sometimes hang and take the product page with them. Add a timeout, and retry so the carousel still shows.

The marked lines add a 1 second timeout and three immediate retries. Pages stop hanging. Then the recommendations database has a 15-second slowdown, and the whole product API is down for far longer than that. Every page made four calls instead of one, at the moment the service could handle fewest.

<Depth level={2}>
The retries tripled the load on a service that was already behind, and the queue it built kept every answer late after it recovered. Late answers look like timeouts, so the retries never stopped. Spacing the retries out would not have saved it: new pages keep arriving, so the total stays the same.
</Depth>

<Depth level={3}>
AWS gives the multiplication rule: with five layers that each retry three times, a failing database at the bottom can see 243 times the load. Retries also count when no one wrote them: load balancers, SDKs and clients all retry by default.
</Depth>

## [morph] Bound it, cap it, and let it break

Drag the slider. Each attempt gets a deadline, there is one retry with a random wait, and a breaker sits in front of the call with a fallback behind it.

Hover a box in the diagram to see its code.

<Depth level={2}>
Pick the timeout from data: the dependency's p99 or p99.9 latency, plus room for the network. Retry once, at one layer. Trip the breaker on a failure rate over a window, not on a single error, and keep it open long enough for the dependency to drain its queue.
</Depth>

<Depth level={3}>
The breaker is a small state machine. Closed: calls pass and failures are counted. Open: calls fail at once until a timer runs out. Half-open: a few probe calls pass; success closes it, failure opens it again. Its weakness is the open state itself, a mode that is rarely exercised, which is why the AWS Builders' Library prefers a local token-bucket retry budget.
</Depth>

<Lang only="python">`tenacity` re-raises the last error with `reraise=True`, so the breaker counts one failure per page, not one per attempt. Without it the breaker would see a `RetryError`.</Lang>
<Lang only="typescript">`TimeoutStrategy.Aggressive` rejects at the deadline even if the function ignores its signal; `Cooperative` waits for the function to honour the abort. Passing `signal` to `fetch` makes both stop the request.</Lang>
<Lang only="rust">Dropping the future that `timeout` returns cancels the call: tokio futures are cancelled by being dropped. Any work the server already started still runs.</Lang>
</Depth>

Measure it. Count calls by outcome (ok, timeout, breaker open, fallback served) and alert on the breaker opening. A fallback that hides an outage for a week is its own incident.

The dependency can help too. If it drops requests whose deadline has passed, and sheds load when its queue is long, it never spends capacity on callers who have left.

## [play] Brown out a dependency

An API with 100 users a second calls a dependency that can handle 150 calls a second. You choose the client's settings, slow the dependency down, and run one minute. Every run is kept, so you can compare settings on the same outage.

## [lens] How each language does it

Go builds timeouts into every call through `context`. Python, TypeScript and Rust each have a per-call timeout and a library ecosystem for retries and breakers. None of the four retries for you, except in SDKs that choose to.

</Depth>

### Backoff with jitter, in one line

Full jitter waits a random time between zero and the exponential backoff: `sleep = random(0, min(cap, base × 2^attempt))`. Marc Brooker's simulations for AWS found it does about as well as more elaborate schemes and much better than backoff without jitter. Backoff of any kind reduces total work only when a fixed set of clients waits for each answer before sending again. When new requests keep arriving, the way out of overload is less load.
