      - text: The reload was served by a follower that had not applied the save yet.

      - text: The save was lost when the leader crashed.

      - text: The browser cached the old page.
        why: A cache could do this too, but the page was fetched again. The read hit a replica that was behind, which is the usual cause in a replicated setup.
  engineer:
    question: You pin each user's session to one follower, chosen by hashing the session id. What do you get?
    options:
      - text: Monotonic reads. A user can still miss their own write while their follower lags.
        correct: true
        why: Right. One follower applies the log in order, so it never shows something older than it showed before. But it can be behind, so a write the user just made can be missing.
      - text: Read-your-writes, because the user always talks to the same server.
        why: The writes go to the leader, not to the pinned follower. The follower gets them after its lag.
      - text: Nothing, because followers apply writes in any order.
        why: A follower replays the leader's log in order. That is exactly why pinning stops time going backwards.
  deep:
    question: The handler takes the token with pg_current_wal_lsn() after the UPDATE has committed, as a separate statement. Why not inside the same transaction, before COMMIT?
    options:
      - text: Before COMMIT, the log position is earlier than the commit record, so a replica could reach it and still not show the new row.
        correct: true
        why: Right. A replica makes a change visible when it replays the commit record. A token taken before that record exists can be satisfied by a replica that has not replayed it.
      - text: pg_current_wal_lsn() cannot be called inside a transaction.
        why: It can. It just reports the position at that moment, which is before this transaction's commit record.
      - text: Replicas reject tokens that came from an open transaction.
        why: A token is only a log position. The replica compares it with how far it has replayed; it does not know where the token came from.

  roles:
    - role: Leader
      example: PostgreSQL primary
      job: Takes every write and ships its log to the followers.
    - role: Follower
      example: hot standby replicas
      job: Replays the leader's log in order, some time later, and serves reads.
    - role: Read router
      example: { go: "Handler.reader", python: "reader()", typescript: "reader()", rust: "reader()" }
      job: Picks a node for each read, given what the session has already seen.
    - role: Token
      example: the seen_lsn cookie
      job: The newest log position the session wrote or read. A read must come from a node at or past it.
  useWhen:
    - Reads go to asynchronous followers and users read data they just wrote (profiles, settings, comments, carts).
    - Requests from one user can land on different followers, for example behind a load balancer.
    - The same user is active on several devices, so the token must live on the server, not in one cookie.
  avoidWhen:
    - Data that nobody just wrote and nobody compares over time, like a public catalogue or a dashboard, can read from any follower.
    - If every read must see every write from every user, a session guarantee is too weak. Read from the leader or use a linearizable store.
  tradeoffs:
    - Reads that fall back to the leader add load to the one node that also takes all the writes.
    - The router checks follower positions before reading. Cache those positions for a few hundred milliseconds to keep this cheap.
    - A fixed window (read from the leader for N seconds after a write) is simpler, and breaks silently when lag exceeds N.
    - Sticky sessions give monotonic reads cheaply, and lose them when the pinned follower is replaced or fails over.
  lookalikes:
    - name: Synchronous replication (remote_apply)
      how: Makes every commit wait until the synchronous standbys have applied it. Every reader of those standbys sees the write, and every write pays the wait.
    - name: Causal consistency
      how: Stronger than a session guarantee. It also orders writes that depend on what other users read. MongoDB's causally consistent sessions are a practical form.
    - name: Linearizability
      how: Every read sees the latest completed write, for every client. It needs the leader or consensus on the read path.
    - name: Cache invalidation
      how: The same symptom from a different layer. A stale cache entry can hide a write even with a single database.

## [concept] Replication lag and session guarantees

**A follower applies the leader's writes a little later, so a read from it can show you the past, even your own last write.**

That gap is <Term id="replication-lag">replication lag</Term>. With asynchronous followers it is always there. Usually it is milliseconds. When a follower is busy, catching up after a restart, or far away, it grows to seconds or minutes.

<Depth level={2}>
Most apps do not need every read to see every write. They need two narrower promises for each user, called <Term id="session-guarantee">session guarantees</Term>. <Term id="read-your-writes">Read-your-writes</Term>: after I save something, I see it. <Term id="monotonic-reads">Monotonic reads</Term>: once I have seen something, I never see an older version again. A third, <Term id="consistent-prefix">consistent prefix reads</Term>, says I see writes in the order they happened. All three can be kept on top of lagging followers, if reads are routed with care.
</Depth>

<Depth level={3}>
The guarantees come from the Bayou project at Xerox PARC (Terry and others, 1994), which named four: read-your-writes, monotonic reads, writes-follow-reads and monotonic writes. Bayou kept, for each session, the set of writes it had written and read, summarised as version vectors, and only let a server answer if it had all of them. The token in this lesson is the same idea with a single number: one leader means one log, so one log position stands for "everything up to here".
</Depth>

## [problem] Write to the leader, read from any replica

A profile service runs on PostgreSQL with one primary and two streaming replicas. Writes go to the primary. To spread load, every read goes to the next replica in turn. It is the standard setup, and it passed every test, because the test database had no replicas.

Read it once. Nothing in the read path knows that a write just happened.

<Depth level={2}>
Streaming replication is asynchronous by default. The primary commits, answers the client, and ships the log to the replicas afterwards. Each replica replays that log in order. The lag is the time between the commit on the primary and the replay on the replica.
</Depth>

<Depth level={3}>
You can watch the lag on the primary in `pg_stat_replication` (`write_lag`, `flush_lag`, `replay_lag`), and on a replica by comparing `pg_last_wal_replay_lsn()` with the primary's `pg_current_wal_lsn()`. Under normal load both are small, which is why the bug hides until the day they are not.
</Depth>

## [pain] Then a change request arrives

**Change request:** make the profile page show a user's new display name right after they save it.

Support has tickets: users save a new name, the reload shows the old one, they save again, and sometimes the name flips back and forth between reloads. The obvious fix is the marked line. It sleeps half a second before the redirect.

<Depth level={2}>
The sleep makes every save slower, and it still fails whenever lag is over half a second, which is exactly when the replicas are under the most load. It also does nothing for the second symptom. One reload hits a replica that has the new name, the next hits one that does not, and the name goes back. That breaks monotonic reads, and no sleep fixes it.
</Depth>

<Depth level={3}>
A sleep is a guess about lag, written into the code. Every fix of this shape, including "read from the primary for N seconds after a write", has the same flaw. It holds while lag is below the guess, and fails silently above it, with no error in any log.
</Depth>

## [morph] Route each read by what the session has seen

Drag the slider. A read router appears between the handler and the replicas.

The save now returns a <Term id="lsn">log sequence number</Term> (LSN) from the primary. The browser keeps it in a cookie. On every read, the router sends the query only to a replica that has replayed at least that far, and to the primary if none has.

<Depth level={2}>
This gives read-your-writes without guessing the lag. If you also raise the token to the highest position a read has returned, the same check gives monotonic reads: a later read can never come from a replica behind an earlier one. When replicas are caught up, which is most of the time, reads still spread across them, and only the unlucky ones fall back to the primary.
</Depth>

<Depth level={3}>
<Lang only="go">The check is one query per replica tried. In production, poll each replica's `pg_last_wal_replay_lsn()` every 100 ms or so in a background goroutine and keep the latest value in an `atomic.Value`, so routing costs nothing on the request path.</Lang>
<Lang only="python">The check is one query per replica tried. In production, poll each replica's `pg_last_wal_replay_lsn()` every 100 ms or so in a background thread or task and route against the cached values.</Lang>
<Lang only="typescript">The check is one query per replica tried. In production, poll each replica's `pg_last_wal_replay_lsn()` every 100 ms or so with a `setInterval` and route against the cached values, so the request path makes no extra round trip.</Lang>
<Lang only="rust">The check is one query per replica tried. In production, poll each replica's `pg_last_wal_replay_lsn()` every 100 ms or so in a spawned tokio task and publish the values through a `tokio::sync::watch` channel.</Lang>
</Depth>

## [walk] Follow one save and one reload

One save and the reload after it, step by step. Use the numbered buttons.

<Depth level={2}>
The order matters on the write side. The handler asks for the log position after the commit, so the position is at or past the commit record. A replica only shows the new row once it has replayed that record.
</Depth>

<Depth level={3}>
The comparison `pg_last_wal_replay_lsn() >= $1::pg_lsn` works because `pg_lsn` values are ordered byte positions in one log. That is only true with a single leader. With several leaders, or leaderless replicas, there is no single log, and the token becomes a vector of positions, one per writer. That is the version vector of a later lesson.
</Depth>

## [again] Same request, from the phone

The same request comes back from support: the new name is missing on the user's phone. The token lived in the laptop's cookie, so the phone had none. The fix is small. Store the token on the server, keyed by user, and the router reads it from there. No new mechanism, and no sleep.

<Depth level={2}>
Keep the per-user token only for as long as lag can plausibly last, a minute here. After that every replica has the write anyway. If the token store is down, fall back to the primary, not to any replica.
</Depth>

<Depth level={3}>
This is cross-device read-your-writes. It needs some shared place that every device's requests consult. Pinning a user to one replica cannot give it, because the laptop and the phone may be routed differently, and the pinned replica may change at failover.
</Depth>

## [lens] How each language's clients choose a replica

The SQL is the same everywhere. What differs is how much the driver or framework does for you. PostgreSQL drivers in all four languages leave routing to you. MongoDB drivers have read preferences and causally consistent sessions built in, which carry the token for you.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
MongoDB's version of the token is the session's `operationTime` and `clusterTime`. With `readConcern: "majority"` and `writeConcern: { w: "majority" }`, a causally consistent session gives read-your-writes, monotonic reads, monotonic writes and writes-follow-reads, even when it reads from secondaries.
</Depth>

<Depth level={3}>
Cassandra and other leaderless stores have no log position to carry. There, read-your-writes comes from quorum overlap instead: write to W replicas, read from R, with R + W greater than the replication factor. That is the next lesson.
</Depth>

### Eventual consistency is not a deadline

<Term id="eventual-consistency">Eventual consistency</Term> means that if writes stop, the replicas end up equal. It does not say when, and it says nothing about what a reader sees in the meantime. Session guarantees are the cheapest useful promises you can add on top: they cost one token per session, and they remove the anomalies users actually notice.
