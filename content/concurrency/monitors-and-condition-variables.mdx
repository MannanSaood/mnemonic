checks:
  overview:
    question: Why should a thread call wait() inside a while loop that checks its condition?
    options:
      - text: When wait() returns, the condition may be false again. Another thread may have changed it first, or the wakeup was spurious.
        correct: true
        why: Right. A wakeup is a hint to look again, not a promise. The loop looks again and waits once more if it has to.
      - text: Because wait() can return before it has taken the lock back.
        why: wait() always holds the lock again when it returns. The problem is what other threads did while it was waiting for the lock.
      - text: Because one wait() call can miss the signal, so the loop waits twice to be sure.
        why: The loop does not catch missed signals. It catches wakeups that arrive when the condition no longer holds.
  engineer:
    question: One uploader and two workers share one condition variable, with while loops and signal (wake one). Sometimes all three sleep forever. Why?
    options:
      - text: A worker's signal can wake the other worker instead of the waiting uploader. That worker finds nothing, waits again, and nobody is left to wake the uploader.
        correct: true
        why: Right. With one condition for two predicates, signal may reach a thread that cannot use it. Use broadcast, or one condition per predicate such as not_full and not_empty.
      - text: The while loops spin and use up the CPU, starving the uploader.
        why: A waiting thread sleeps and uses no CPU. The loop runs once per wakeup.
      - text: signal() does nothing if called while holding the lock.
        why: Signalling while holding the lock is normal and works. In Python it is required.
  deep:
    question: What does wait() do with the lock, and why must that be a single step?
    options:
      - text: It releases the lock and joins the wait set atomically, so a signal sent just after the release cannot fall into a gap and be lost.
        correct: true
        why: Right. If releasing and sleeping were two steps, a thread could change the state and signal in between, and the waiter would sleep through the only wakeup it was going to get.
      - text: It keeps the lock while asleep so that nobody can change the state.
        why: Then nobody could ever make the condition true, and every wait would deadlock.
      - text: It releases the lock, then starts listening; the gap is harmless because signals are stored until someone waits.
        why: Signals are not stored. A signal with nobody in the wait set does nothing, which is exactly how a gap would lose it.

## [concept] Waiting for state to change

**A condition variable lets a thread sleep, inside a lock, until another thread changes the shared state.** `wait()` gives up the lock and sleeps in one step, and takes the lock back before it returns.

Waking up only means "look again". By the time the woken thread holds the lock, the state may have changed back.

<Depth level={2}>
A <Term id="monitor">monitor</Term> is a lock bundled with the state it guards and one or more <Term id="condition-variable">condition variables</Term>. Each condition has a <Term id="wait-set">wait set</Term> of sleeping threads. Signal wakes one of them, broadcast wakes all. The pattern always has the same shape: take the lock, loop while the condition is false calling wait, act, signal whoever might now be able to proceed, release the lock.
</Depth>

<Depth level={3}>
Real condition variables use <Term id="mesa-semantics">Mesa semantics</Term>: signal marks a waiter runnable and the signaller keeps going. The woken thread then competes for the lock like anyone else, and a thread that was never asleep can get there first. The alternative, Hoare semantics, hands the lock straight to the woken thread so the condition still holds, but it costs extra context switches and almost no library offers it. POSIX threads and Rust's `Condvar` also allow a <Term id="spurious-wakeup">spurious wakeup</Term>, a return from wait with no signal at all.
</Depth>

## [problem] A queue for thumbnail jobs

An upload service puts a thumbnail job on an in-memory queue for every image, and a worker thread takes jobs off it. The queue is bounded so a burst of uploads cannot use up memory: when it is full, the uploader waits. When it is empty, the worker waits. One condition variable covers both.

With one uploader and one worker, it works. Each side waits only when it must, and the other side's notify always wakes it.

<Depth level={2}>
The mental model is that `wait()` returns when the thing you were waiting for has happened. With one thread on each side that is close enough: when the worker wakes, nobody else could have taken the job. The `if` around `wait()` reads naturally: if there is nothing, wait for something, then take it.
</Depth>

<Depth level={3}>
The single condition is also safe with one thread per side. Whoever notifies, the only possible waiter is the other side, which is exactly the thread that can use the change.
</Depth>

## [pain] A second worker per host

**What happened:** thumbnails fell behind, so each host started a second worker thread. Within an hour, workers began dying with an empty-queue error, and on some hosts uploads stopped entirely while the queue sat full.

The marked lines are two bugs. The `if` lets a woken worker take from the queue without looking: if the other worker took the job while this one waited for the lock, it takes from an empty queue. And with two workers sharing one condition with the uploader, a worker's notify can wake the other worker instead of the uploader waiting on a full queue.

<Depth level={2}>
The second bug is a <Term id="lost-wakeup">lost wakeup</Term>. The uploader waits on a full queue. A worker takes the job and notifies, which wakes the other worker, asleep because the queue was empty. That worker checks, finds it empty again, and waits. The first worker comes back for more and waits too. Now all three sleep, the uploader was never told there is room, and nobody is left to tell it.
</Depth>

<Depth level={3}>
The crash needs a narrow interleaving: a worker that was not asleep reaching the lock between the notify and the woken worker's return from wait. The stall needs the wait set to hold a worker ahead of the uploader when a worker notifies. Both depend on timing, which is why one worker per host never showed them.
</Depth>

## [morph] From "wait until" to "wait, then look again"

Drag the slider. The queue you imagined, where `wait()` returns when a job is there, becomes the real monitor: a lock, the queue, and two wait sets, one for the uploader and one for the workers.

The code changes in two ways. Every `if` around `wait()` becomes `while`, so a woken thread looks again. And the single condition splits in two, `not_full` for the uploader and `not_empty` for the workers, both on the same lock, so each notify reaches a thread that can use it.

<Depth level={2}>
Broadcast instead of signal on the one shared condition also fixes the stall, because the uploader is always among those woken. It is a reasonable quick fix, but every take wakes every sleeping thread, and all but one go straight back to sleep. Two conditions wake only the side that can act. Keep the `while` either way; it is what makes any wakeup safe.
</Depth>

<Depth level={3}>
Why `wait()` must release the lock and join the wait set as one step: if a thread released the lock and then, separately, went to sleep, another thread could change the state and signal in the gap. The signal would find an empty wait set and do nothing, and the waiter would sleep through the only wakeup it was going to get. That is the classic lost wakeup, and it is also why the state must be checked and changed only under the lock: a signal is not remembered, only the state is.
</Depth>

## [walk] Follow one job

One job travels from the uploader to a worker while the second worker competes for it. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`sync.Cond` keeps waiters in a ticket list, and `Signal` wakes the goroutine that has waited longest. `Wait` unlocks `c.L`, parks, and locks `c.L` again before returning, so the loop's check runs under the lock.</Lang>
<Lang only="python">CPython's `Condition` keeps a deque of per-waiter locks. `wait()` adds a fresh lock to the deque, releases the condition's lock and blocks on its own lock; `notify()` releases the first n waiters' locks. That is why waiters wake in FIFO order and why notify must be called while holding the lock.</Lang>
<Lang only="typescript">Resolving a Promise schedules the code after its `await` as a microtask. Anything already queued ahead of it, such as another worker resuming from its own await, runs first and can take the job.</Lang>
<Lang only="rust">On Linux, std's `Condvar` is built on a futex. A futex wait can return without a matching wake, which is one source of the spurious wakeups the docs warn about. `wait_while` hides them by checking the predicate in a loop.</Lang>
</Depth>

## [again] The same busy day, again

Two workers per host, the same stream of uploads. When a woken worker finds its job already taken, the loop sends it back to sleep. When a worker takes a job, it wakes the uploader through `not_full`, which no worker ever waits on. Nothing crashes and nothing sleeps forever.

<Depth level={2}>
Scale the workers to eight and nothing changes. The queue's correctness no longer depends on how many threads sit on each side, which is the property the original code quietly lacked.
</Depth>

<Depth level={3}>
Signalling before or after releasing the lock are both correct with Mesa semantics. Signalling inside the lock is simpler to reason about and required by Python. Signalling just after the unlock can save the woken thread from waking only to block on the lock, but it is rarely worth the harder reasoning; measure first.
</Depth>

Python and Rust give you the raw monitor and expect you to write the loop, or use `wait_for` and `wait_while`. Go has `sync.Cond` but steers you to channels. Node has no threads to block, but the same bug appears with Promises.

### The other lost wakeup

The playground shows a signal that reaches the wrong thread. The older form of the bug is a signal sent before anyone waits. A thread checks a flag without the lock, sees it false, and is about to call wait; another thread sets the flag and signals into an empty wait set; the first thread then waits forever. The cure is the rule in this lesson: check and change the state only while holding the lock, so the check and the wait happen with nothing in between.
