    - role: Scheduler
      example: OS, Go runtime, CPU cores
      job: Decides the interleaving. You do not control it, so code must be right for every order.
  useWhen:
    - An atomic counter, for one number that many threads update, such as a metric or a sequence number.
    - A lock, when an update touches more than one value or must keep an invariant between them.
    - Confinement, when only one thread or task ever touches the state and others send it messages.
  avoidWhen:
    - Do not rely on a test passing as proof. A race shows up under timing your test does not produce.

    - An atomic add costs more than a plain one, because the core must own the cache line. Under heavy contention many cores fight over one line.

    - Not sharing at all is the cheapest fix when the design allows it.
  lookalikes:
    - name: Data race
      how: Unsynchronised access to the same memory with at least one write. Undefined or corrupt results in Go, C, C++ and Rust's unsafe code.
    - name: Race condition
      how: Any bug that depends on timing. Atomics remove data races but not race conditions between two atomic steps.
    - name: Check-then-act
      how: The same bug with an if, such as if stock > 0 then stock--. Two threads both see 1 and both sell it.

## [concept] Two threads, one counter

**`calls++` is three steps: read the value, add one, write it back.** When two threads run it at the same time, another thread can run between those steps, and one of the two updates disappears.

Every concurrency bug in this track grows from that fact. A line of code is not one step, and the scheduler, not you, decides how the steps of different threads are merged.

<Depth level={2}>
The bug is a <Term id="race-condition">race condition</Term>: the result depends on the order in which threads happen to run. Each possible merged order is an <Term id="interleaving">interleaving</Term>. `calls++` is a <Term id="read-modify-write">read-modify-write</Term>, and when two of them interleave, the second write lands on a value computed from a stale read. That is a <Term id="lost-update">lost update</Term>.

<Term id="concurrency-vs-parallelism">Concurrency and parallelism</Term> are different things. Concurrency means the tasks may overlap. Parallelism means they actually run at the same instant on different cores. A race needs only concurrency: one core switching threads at the wrong moment is enough. Parallelism makes the wrong moment far more common.
</Depth>

<Depth level={3}>
At the machine level, `calls++` on a field compiles to a load into a register, an add on the register, and a store. Each thread has its own registers, so two threads can each hold 41, each make it 42, and each store 42. Compilers and CPUs may also reorder and cache plain memory accesses, so without synchronisation one thread may see another's writes late or out of order. A <Term id="data-race">data race</Term> is the formal name for unsynchronised access to the same memory with at least one write. In Go and C it makes the program's behaviour undefined, and a race on a multi-word value such as a Go slice or interface can tear it into a value nobody wrote.
</Depth>

## [problem] A meter that counts every call

An API bills customers per call. Each request handler records one call on an in-memory meter, and once a minute a flusher sends the count to billing and resets it to zero.

It is the simplest code imaginable, and it works. On a developer laptop, and in a load test, the meter matches the access log exactly.

<Depth level={2}>
The mental model behind the code is that a line runs all at once. `calls++` looks like one action, and in a single-threaded program it is. The meter was written as if requests took turns.
</Depth>

<Depth level={3}>
The load test passed because the window is tiny. The three instructions take a few nanoseconds, and on a lightly loaded machine a thread is rarely interrupted or overlapped in exactly that window. The test was correct only for the interleavings it happened to produce.
</Depth>

## [pain] The invoices come out short

**What happened:** the API moved to a 16-core host, and finance found that the busiest customers' invoices were about 0.3% below the access logs. Roughly one call in 300 was never billed.

The marked lines are both read-modify-writes. In `Record`, two requests on two cores read the same count and both write count + 1. In `Flush`, a request that records between the read and the reset is wiped out with the reset.

<Depth level={2}>
The loss grows with load and with cores, which is why it appeared after the move. More requests in flight means more pairs of threads inside the window at once. Nothing crashes and nothing is logged. The only symptom is a number that is slightly too low, found weeks later by someone reconciling two systems.
</Depth>

<Depth level={3}>
In Go the before code is a data race, and `go test -race` reports it the first time a test runs two `Record` calls concurrently. In Python the outcome depends on where the interpreter switches threads, which differs between versions, so the bug can come and go with an upgrade. In Rust the compiler refused a plain `u64`, so the code uses an atomic, but splits the update into a load and a store, which brings the lost update straight back.
</Depth>

## [morph] From one step to three

Drag the slider. The single step you imagined splits into what each core does: read calls into its own register, add one there, write it back. Between those steps the other request can do the same.

The code changes the update into one <Term id="atomic-operation">atomic operation</Term>. An atomic add, or a lock around the three steps, means other threads see the increment either not started or finished, never in the middle. Flush becomes one swap, which reads the count and resets it in the same step.

<Depth level={2}>
Pick the smallest guard that covers the whole update. One number updated on its own: an atomic add or swap. Several values that must change together, such as a count and a total: a lock around all of them. Do not mix the two on the same data. A plain read next to atomic writes is still a race.
</Depth>

<Depth level={3}>
On x86, `atomic.Int64.Add`, `fetch_add` and `Atomics.add` compile to one `LOCK XADD` instruction. The core takes the cache line in exclusive state and keeps it for the whole read-modify-write, so no other core can write it in between. On ARMv8.1 and later it is a single `LDADD`; older ARM cores use a load-exclusive and store-exclusive loop that retries if another core touched the line.
</Depth>

## [walk] Follow two requests

Two requests record a call at the same moment, and then the flusher runs. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`atomic.Int64` also guarantees that the value is 8-byte aligned, which plain `int64` fields on 32-bit platforms do not, and the old `atomic.AddInt64` function needs. The race detector understands `sync/atomic`, so it stays quiet about the fixed meter.</Lang>
<Lang only="python">Python has no public atomic integer. A `threading.Lock` costs well under a microsecond to take when nobody else holds it, which is small next to handling a request.</Lang>
<Lang only="typescript">`Atomics` works only on integer typed arrays that view a `SharedArrayBuffer`. A plain object or a normal `ArrayBuffer` cannot be shared between workers at all; it is copied or transferred by `postMessage`.</Lang>
<Lang only="rust">`Ordering::Relaxed` is enough for a counter: a read-modify-write always acts on the latest value of that one variable. Stronger orderings matter when the counter is used to publish other data, which a later lesson covers.</Lang>
</Depth>

## [again] The same busy hour, again

The same 16 cores and the same 8,000 requests a second. Every increment is now one indivisible step, so every pair of concurrent requests ends with both counted. The meter matches the access log to the call.

<Depth level={2}>
Keep the race detector in CI for Go and run it on tests that actually exercise concurrency. It only sees races that a test executes, but when it sees one it is never a false alarm.
</Depth>

<Depth level={3}>
Under very heavy load, one atomic counter that every core updates becomes a hot cache line that moves between cores on every add. The fix then is a counter per core or per shard, summed at flush time. That is a later lesson; correctness comes first.
</Depth>

## [lens] How each language meets it

Go and Rust run threads in parallel on every core. Python runs one thread at a time on the standard build, and in parallel on the optional free-threaded build. Node runs your code on one thread unless you start workers.

The question in each language is the same: can two threads reach this line at the same time, and is the line one step? Go: yes and no, use `sync/atomic` or a mutex, and run `-race`. Python: yes and no, use a lock. Node: only across `await` or between workers. Rust: the compiler forces a lock or an atomic, but you can still split the update.

### Race condition or data race

A data race is about memory: two unsynchronised accesses to the same location, at least one a write. A race condition is about logic: a result that depends on timing. Each can happen without the other. Two atomic operations used as a pair, such as checking a stock level and then decrementing it, have no data race but are still a race condition. Removing data races, with a race detector or with Rust's type system, is necessary but not enough.
