## [concept] Two locks, opposite orders

**A deadlock is a loop of waiting: each thread holds a lock and waits for one that another thread in the loop holds.** Nothing inside the program will ever break it.

Two transfers between the same two accounts are enough. One locks A and wants B. The other locks B and wants A. Neither gives anything back.

<Depth level={2}>
A <Term id="deadlock">deadlock</Term> is one of three liveness failures, where the program stops making progress without crashing. In a <Term id="livelock">livelock</Term>, threads keep running and reacting to each other but nothing gets done. In <Term id="starvation">starvation</Term>, the program as a whole progresses but one thread never gets its turn. All three look the same from outside: requests that never finish.

The tool for reasoning about deadlock is the <Term id="wait-for-graph">wait-for graph</Term>: an arrow from each blocked thread to the thread holding what it wants. A deadlock is a cycle in that graph. Prevent the cycle and you prevent the deadlock.
</Depth>

<Depth level={3}>
A deadlock needs all four <Term id="coffman-conditions">Coffman conditions</Term> at once. Mutual exclusion: a lock has one holder. Hold and wait: a thread holds one lock while waiting for another. No preemption: nobody can take a lock away from its holder. Circular wait: the waiting forms a cycle. Every practical fix removes one. <Term id="lock-ordering">Lock ordering</Term> removes circular wait. <Term id="try-lock">Try-lock</Term> with release removes hold and wait. Database deadlock detectors preempt, by aborting one transaction.
</Depth>

## [problem] A transfer between two accounts

A ledger keeps each account's balance in memory, guarded by a lock per account, so transfers between unrelated accounts can run in parallel. A transfer locks the account it takes money from, then the one it pays into, then moves the money.

The code is short and obviously correct. Each account is protected, the check and the move happen under both locks, and no money can be created or lost. In testing, every transfer goes through.

<Depth level={2}>
The mental model is that a lock is a short wait: if the account is busy, you wait a moment and then carry on. That holds for one lock. With two, the order you take them in matters, and here the order depends on which way the money goes.
</Depth>

<Depth level={3}>
Tests rarely run two transfers in opposite directions between the same two accounts at the same instant. When they do, one thread usually gets both locks before the other starts. The deadlock needs a narrow interleaving: each thread past its first lock before either reaches its second.
</Depth>

## [pain] Two transfers hang

**What happened:** customers started sending money to each other. Twice a day, two transfers between the same pair of accounts hang until the service is restarted, and every later transfer touching those accounts queues behind them.

The marked lines are the whole story. Thread 1 sends A to B and locks A. Thread 2 sends B to A and locks B. Now thread 1 waits for B and thread 2 waits for A. Both wait forever.

<Depth level={2}>
Nothing reports it. CPU is idle, logs are quiet, and the rest of the service runs normally, so it is a <Term id="partial-deadlock">partial deadlock</Term>. The only symptoms are timeouts on the two requests and a growing queue of transfers waiting on A or B. A client-side timeout does not help: the client stops waiting, but the threads keep their locks.
</Depth>

<Depth level={3}>
The diagnosis tool is a thread dump: every thread's stack at one moment. It shows two threads parked in a lock call, each at the second lock line of `transfer`, and a lock-aware tool shows which thread owns which lock. Draw the arrows and the cycle is there.
</Depth>

## [morph] From a short wait to a cycle

Drag the slider. The picture you had, two threads briefly queueing for a lock, becomes the wait-for graph: thread 1 holds A and waits for B, thread 2 holds B and waits for A.

The fix adds one rule. Every transfer sorts its two accounts by id and locks the lower id first, whichever way the money flows. The money still moves from `from` to `to`; only the order of the locks changes.

<Depth level={2}>
With one global order, any thread waiting for a lock holds only locks earlier in the order. Arrows in the wait-for graph always point from lower to higher, so they cannot close into a loop. Order by something stable and unique, such as a database id. Do not order by memory address in languages where objects can move, and do not order by argument position, which is exactly what went wrong here.
</Depth>

<Depth level={3}>
When there is no natural order, or the set of locks is only known as you go, the alternative is to give up hold and wait: take the first lock, try the second, and if it is taken release the first and retry later. That trades deadlock for retries, and two threads that back off for exactly the same time can retry in step forever. Adding random <Term id="jitter">jitter</Term> to the wait breaks the lockstep.
</Depth>

## [walk] Follow two transfers

Two transfers in opposite directions start together on two cores. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`sync.Mutex` is not fair by default: a goroutine that has just unlocked can lock again before a woken waiter runs. To stop a waiter starving, a mutex switches to starvation mode when a waiter has waited more than 1 ms, and then hands the lock directly to the oldest waiter.</Lang>
<Lang only="python">`with first.lock, second.lock:` acquires left to right and releases in reverse, exactly like two nested `with` blocks. If acquiring the second lock raises, the first is released.</Lang>
<Lang only="typescript">An async lock is a queue of promises. `lock()` resolves at once if the lock is free; otherwise its `resolve` waits in the queue until the holder calls its release function. A deadlock leaves two of those promises pending forever, which uses no CPU and never throws.</Lang>
<Lang only="rust">The `if` returns both guards, so both locks stay held until `src` and `dst` go out of scope at the end of the function. The order of unlocking does not matter for deadlock; only the order of locking does.</Lang>
</Depth>

## [again] The same busy day, again

The same pair of accounts, the same transfers in both directions at once. Both threads now want A first. The one that loses waits while holding nothing, so it blocks nobody, and it gets both locks as soon as the winner is done. Nothing hangs.

<Depth level={2}>
The order has to hold on every path that takes two account locks: refunds, fee collection, account merges, admin tools. Put it in one helper that locks a pair of accounts, and make that the only way to get two at once.
</Depth>

<Depth level={3}>
A transfer from an account to itself locks the same lock twice. Go's `sync.Mutex`, Python's `threading.Lock` and Rust's `std::sync::Mutex` are not reentrant, so the thread deadlocks with itself. Reject same-account transfers before taking any lock.
</Depth>

## [play] Make it hang, then fix it

Two threads keep transferring between A and B in opposite directions. Step one thread at a time, or tick both cores at once, and watch the wait-for graph in the middle.

Predict first. Then create the cycle, fix it with a lock order, and try the other fix, try-lock with backoff, with and without jitter.

## [lens] How each language meets it

Every language with locks can deadlock, including Rust, whose type system stops data races but not this. Node has no threads by default, but async locks deadlock in the same way.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

What differs is how you find out. Go reports a deadlock only when every goroutine is blocked. Python and Rust report nothing. In Node the stuck work is a pending promise, invisible until a request times out. In all four, a dump of what every thread or task is waiting on is the diagnosis.

### Deadlocks without two locks

The same cycle forms with any resource that one party holds while waiting for another. A worker in a fixed-size pool that submits a subtask to the same pool and waits for it can deadlock when every worker is doing the same: all workers wait for subtasks that no free worker can run. A goroutine that sends on an unbuffered channel while holding a mutex that the receiver needs is a cycle between a lock and a channel. The fix is the same idea: find the cycle in what waits for what, and remove one edge.
