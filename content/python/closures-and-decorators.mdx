        # retrying.py
        def retry(times: int = 3, on: type[Exception] = httpx.TransportError):
            def decorate(fn):
                @functools.wraps(fn)
                def wrapper(*args, **kwargs):
                    for attempt in range(times):
                        try:
                            return fn(*args, **kwargs)
                        except on:
                            if attempt == times - 1:
                                raise
                            time.sleep(0.2 * 2**attempt)
                return wrapper
            return decorate


        def timed(fn):
            @functools.wraps(fn)
            def wrapper(*args, **kwargs):
                start = time.perf_counter()
                try:
                    return fn(*args, **kwargs)
                finally:
                    metrics.observe(fn.__name__, time.perf_counter() - start)
            return wrapper

        // middleware.go
        type Fetch[T any] func(ctx context.Context, id string) (T, error)

        func Retry[T any](times int, next Fetch[T]) Fetch[T] {
        	return func(ctx context.Context, id string) (T, error) {
        		v, err := next(ctx, id)
        		for attempt := 1; attempt < times && isTransient(err); attempt++ {
        			time.Sleep(100 * time.Millisecond << attempt)
        			v, err = next(ctx, id)
        		}
        		return v, err
        	}
        }

        func Timed[T any](name string, next Fetch[T]) Fetch[T] {
        	return func(ctx context.Context, id string) (T, error) {
        		start := time.Now()

        // middleware.rs
        fn retry<T, E: Transient>(times: u32, f: impl Fn(&str) -> Result<T, E>) -> impl Fn(&str) -> Result<T, E> {
            move |id: &str| {
                let mut attempt = 0;
                loop {
                    match f(id) {
                        Err(e) if e.is_transient() && attempt + 1 < times => {
                            thread::sleep(Duration::from_millis(200 << attempt));
                            attempt += 1;
                        }
                        result => return result,
                    }
                }
            }
        }

        fn timed<T>(name: &'static str, f: impl Fn(&str) -> T) -> impl Fn(&str) -> T {
            move |id: &str| {
                let start = Instant::now();
                let out = f(id);
                metrics::observe(name, start.elapsed());
                out
            }
        }

    - role: Closure cell
      example: "wrapper.__closure__[0].cell_contents"
      job: Keeps a captured variable alive for as long as the wrapper exists.
  useWhen:
    - The same before-and-after logic (retry, timing, caching, auth, logging) is copied into many functions.
    - The behaviour should be switchable per function by adding or removing one line.
    - You need to register functions in a table at import time (routes, CLI commands, plug-ins).
  avoidWhen:
    - Only one function needs the behaviour, and it is short. Inline code is easier to read and debug.
    - The wrapper must change the function's arguments or return type in ways callers cannot see from its signature.
  tradeoffs:
    - Every layer is one more frame in tracebacks and profiles, named wrapper unless @wraps is used.
    - The order of the lines is behaviour. A reviewer must read the stack, not just each decorator.
    - lru_cache returns the same object to every caller. A caller that mutates a cached dict changes it for everyone.
  lookalikes:
    - name: The Decorator pattern
      how: Wraps objects that share an interface. Python's @ syntax wraps functions, at definition time; the idea is the same, the mechanism differs.
    - name: Middleware
      how: Decorators applied to request handlers by a framework, usually configured as a list instead of stacked @ lines.
    - name: Context manager
      how: Wraps a block of code inside one function with with, instead of wrapping every call of a function.

## [concept] Closures and decorators

**A <Term id="closure">closure</Term> is a function that keeps the variables it was created with. A <Term id="function-decorator">decorator</Term> is a function that takes a function and returns a closure that wraps it, so retry, timing and caching are written once and stacked on any call.**

Python functions are <Term id="first-class-function">first-class</Term>: you can pass one to another function and get a new one back. `@timed` above `def fetch_invoice` means `fetch_invoice = timed(fetch_invoice)`. From then on, the name refers to the wrapper.

<Depth level={2}>
Two moments matter. At definition time, when `def` runs (usually at import), the decorators run once, bottom-up, and the name is rebound to the outermost result. At call time, every call goes through the wrappers top-down, like the layers of an <Term id="middleware-onion">onion</Term>. A <Term id="decorator-factory">decorator factory</Term> such as `retry(times=3)` adds one level: it is called first and returns the real decorator. Put `@functools.wraps(fn)` on every inner wrapper, or the wrapper's own name, `wrapper`, is what logs, metrics and `help()` will show.
</Depth>

<Depth level={3}>
A variable used in an inner function but assigned in the enclosing one is a free variable. CPython stores it in a <Term id="cell-object">cell</Term>: the outer frame and every inner function that uses it share the cell, listed in `fn.__code__.co_freevars` and `fn.__closure__`. That is why a closure sees later assignments to the variable, and why `nonlocal` is needed to assign to it from inside. It is also the source of <Term id="late-binding">late binding</Term>:

```python
handlers = {}
for path in ("/invoices", "/customers"):
    handlers[path] = lambda id: http.get(f"{path}/{id}")   # both read path later

handlers["/invoices"]("42")   # requests /customers/42
```

Bind the value when the closure is made, with `lambda id, path=path: ...` or `functools.partial`.
</Depth>

## [problem] Two API calls that both retry and time themselves

A billing job fetches invoices and customers from an internal API. The network drops connections now and then, so each fetch retries with exponential backoff, and each one reports its latency. It works, and it is tested.

Read it once. The retry loop and the timer are copied into both functions, and each copy has to get the `try`/`finally` right so failures are timed too.

<Depth level={2}>
The interesting code is three lines per function: the GET, the status check, the JSON. The other ten are policy: how many attempts, which errors, how long to wait, what to measure. Policy changes for the whole client at once, and here it lives in every function.
</Depth>

<Depth level={3}>
<Lang only="python">The metric name is a string literal in each copy. When someone copies `fetch_customer` to make `fetch_payment` and forgets to edit it, the payment latency lands in the customer series.</Lang>
<Lang only="go">The `defer` reads `start` through a closure, so the timer is right even on early returns. Each new fetch has to repeat that idiom.</Lang>
<Lang only="typescript">The `finally` block runs after the awaited promise settles, because the `return await` is inside the `try`. Drop the `await` and the timer stops before the request finishes.</Lang>
<Lang only="rust">The `loop` with `break result` keeps both the success and the final error. Every new endpoint repeats the match arms.</Lang>
</Depth>

## [morph] Turn the policy into wrappers

Drag the slider. The retry loop and the timer leave the fetches and become two decorators with the same call shape as the function they wrap. The fetches shrink to one GET each, and the stack of lines above `def` says which policy applies.

Hover a box in the diagram to see its code.

<Depth level={2}>
`retry` is a factory: `retry(times=3)` returns `decorate`, which returns `wrapper`. Three levels, because the settings, the function and the call arguments arrive at three different times. `timed` needs no settings, so it has two levels and reads the metric name from `fn.__name__`, which only works because `retry` used `@wraps`.
</Depth>

<Depth level={3}>
<Lang only="python">`functools.wraps(fn)` calls `update_wrapper`, which copies `__module__`, `__name__`, `__qualname__`, `__annotations__`, `__type_params__` and `__doc__`, updates `__dict__`, and sets `wrapper.__wrapped__ = fn`. `inspect.signature` follows `__wrapped__`, so tools see the real parameters.</Lang>
<Lang only="go">`Retry` and `Timed` are generic over the result type, so one wrapper serves `Invoice` and `Customer`. The metric name is a parameter, because a Go function value has no name to read.</Lang>
<Lang only="typescript">`retry(3)` returns a generic function, so `retry(3)(getInvoice)` infers `Fetch<Invoice>`. Each layer awaits the next inside `try`, so errors and timing pass through correctly.</Lang>
<Lang only="rust">`retry` returns `impl Fn(&str) -> Result<T, E>`. The `move` closure owns `f` and `times`, so the wrapper can outlive the function that built it.</Lang>
</Depth>

## [walk] Follow one call through the stack

From import to one fetch, through three wrappers. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="python">`lru_cache` is written in C in CPython. It calls `update_wrapper` itself, so it reports the name of whatever it wraps, and its `cache_info()` and `cache_clear()` are methods of the wrapper object. An outer `@wraps` copies `__dict__`, not methods, so they are reachable only when the cache is the outermost line.</Lang>
<Lang only="go">Each layer is a call through a func value: an indirect call, which the compiler usually cannot inline. For an HTTP fetch that cost is invisible.</Lang>
<Lang only="typescript">Each layer adds a promise and a microtask hop. A call through three async wrappers settles three promises from the inside out.</Lang>
<Lang only="rust">The full stack is one concrete type built from three closure types, so the calls between layers are static and can be inlined.</Lang>
</Depth>

## [again] Jitter, the second time

The same request after the refactor. One line in `retry`, and every function decorated with it gets jitter, including the ones added next quarter.

## [play] Stack the decorators, replay the calls

`lru_cache`, `timed` and `retry` wrap `fetch_invoice`, in an order that looks reasonable, and `retry` forgot `@wraps`. The same three calls replay every time you change the stack: a fetch that needs one retry, the same fetch again, and a fetch whose shard is down.

## [lens] How each language writes it

Every language here has closures. Only Python has syntax for wrapping a plain function at its definition; the others compose wrappers where the function value is defined.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={2}>
Late binding exists wherever closures capture variables. Go fixed the loop case in 1.22 with per-iteration loop variables. JavaScript fixed it for `let` but not `var`. Python has not changed it: bind with a default or `partial`.
</Depth>

<Depth level={3}>
Rust is the one place a closure's capture mode is visible in its type. A closure that only reads is `Fn`, one that mutates a capture is `FnMut`, and one that moves a capture out is `FnOnce`. `move` decides whether it borrows or owns what it captured.
</Depth>
