## [concept] Threads, processes, async and the GIL

**On the standard CPython build only the thread holding the <Term id="gil">GIL</Term> runs Python bytecode. Threads and asyncio overlap waiting; only processes, or the <Term id="free-threaded-build">free-threaded build</Term>, overlap computing.**

Python has three ways to do several things at once. Threads share memory and the GIL. Processes each have their own interpreter. asyncio runs many tasks on one thread with an <Term id="event-loop">event loop</Term>. Which one helps depends on what the work spends its time on.

<Depth level={2}>
That is the difference between <Term id="concurrency-vs-parallelism">concurrency and parallelism</Term>. Waiting on a socket needs no CPU, so a thread that waits releases the GIL and a task that waits returns to the loop. A thousand webhooks can wait at once on either. Computing needs a core and, on the standard build, the GIL, so pure-Python CPU work on threads takes turns on one core. A <Term id="process-pool">process pool</Term> gives each worker its own GIL and its own core.
</Depth>

<Depth level={3}>
The GIL protects the interpreter's own state, above all the reference counts in every object header, which are updated without atomics on the standard build. A thread that wants the GIL waits for the <Term id="switch-interval">switch interval</Term>, 5 ms by default, then sets a drop request; the holder notices at its next check between bytecodes, releases the GIL, and the operating system decides which waiting thread gets it. Blocking I/O and long C routines (hashing, compression, NumPy) release it around the call.
</Depth>

## [problem] A webhook worker on a thread pool

A worker delivers events to customers' webhooks. Each delivery is an HTTP POST that takes about 120 ms, nearly all of it waiting for the other side. A thread pool of 16 sends them concurrently. It works, and it is tested.

Read it with the usual model: 16 threads on a 4-core machine means 16 things happening at once.

<Depth level={2}>
For this workload the model is good enough. The threads spend almost all their time inside `http.post`, waiting on a socket with the GIL released. 16 waits overlap, and throughput is about 16 times one thread's.
</Depth>

<Depth level={3}>
Each delivery still needs a few milliseconds of Python: building the request, parsing the reply. Those parts take turns on the GIL, which is why the speed-up is a little under 16, not exactly 16.
</Depth>

## [pain] Then a change request arrives

**Change request:** validate every event against its JSON schema before delivering it.

The marked line is pure Python and takes about 40 ms of CPU for a large payload. After the deploy, the worker's throughput falls to about 20 events a second, `top` shows the process at 100% of one core while three sit idle, and the health check gets slower.

<Depth level={2}>
The naive model says 16 threads should validate 16 events at once. On the standard build they validate one at a time, and the others queue for the GIL. Adding threads makes nothing faster; it adds handovers. The deliveries suffer too: each one that returns from its socket must wait for the GIL before it can read the reply.
</Depth>

<Depth level={3}>
That last effect is the convoy David Beazley measured in 2010 and others have reproduced since: an I/O thread that finishes a quick operation can wait up to a switch interval to get the GIL back from a CPU-bound thread, every time. Lowering `sys.setswitchinterval` shortens the wait and adds switching overhead. Moving the CPU work out of the process removes it.
</Depth>

## [morph] From 16 parallel threads to one GIL and a pool per kind of work

Drag the slider. The picture of 16 threads on 4 cores gives way to what CPython does: one GIL, threads that release it while they wait, and a separate process pool, one interpreter per core, for the validation.

The code morphs to send validation to processes and keep delivery on threads.

Hover a box in the diagram to see its code.

<Depth level={2}>
Two pools, sized by what they do. CPU work gets one process per core: more only adds switching. I/O work gets as many threads as you want concurrent requests in flight, bounded by what the other side can take. The process pool pickles the event type and payload on the way in and the result on the way out, so keep the arguments small.
</Depth>

<Depth level={3}>
<Lang only="python">Since 3.14 the default start method on Linux is `forkserver` instead of `fork`, as it has long been `spawn` on macOS and Windows. Workers import your module fresh, so `SCHEMAS` is built once per worker, and anything not picklable cannot be an argument. Python 3.14 also added `InterpreterPoolExecutor`: subinterpreters in one process, each with its own GIL.</Lang>
<Lang only="go">Go needs no new pool to run validation in parallel. The slot channel sized by `runtime.GOMAXPROCS(0)` limits CPU work to one per P, so 16 validations do not crowd out the goroutines waiting to deliver.</Lang>
<Lang only="typescript">Piscina keeps a pool of `worker_threads`, each with its own V8 isolate and event loop. The main loop only sends messages and awaits replies.</Lang>
<Lang only="rust">`spawn_blocking` moves the closure to tokio's blocking pool. For sustained CPU work a dedicated rayon pool is a better fit, because the blocking pool is sized for waiting threads, up to 512 by default.</Lang>
</Depth>

</Depth>

## [again] Validation, the second time

The same change after the refactor. Validation runs in four processes at once, about four times the CPU throughput of the thread pool, and the delivery threads only ever wait for sockets. The health check is fast again, because the main process is no longer computing.

<Depth level={2}>
Measure which kind of work you have before choosing. `py-spy top` shows whether threads are running Python or idle in I/O, and a process stuck at 100% of one core with idle siblings is the GIL signature.
</Depth>

<Depth level={3}>
The free-threaded build is the other way out. It was experimental in 3.13, became officially supported but optional in 3.14 (PEP 779), and is still not the default. Single-threaded code runs a few percent slower, and importing a C extension that is not marked safe for it turns the GIL back on with a warning. `sys._is_gil_enabled()` tells you which you got.
</Depth>

## [lens] How each language meets it

Every language here overlaps waiting cheaply. They differ in what it takes to overlap computing: nothing in Go, a separate thread or isolate in Node, the right pool in Rust, and a process (or the free-threaded build) in Python.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={2}>
asyncio, Node and async Rust share one rule: a task gives up its thread only at an await, which is <Term id="cooperative-scheduling">cooperative scheduling</Term>. CPU work without awaits blocks everything else on that thread.
</Depth>

<Depth level={3}>
Removing the GIL does not remove races. `hits += 1` is a <Term id="read-modify-write">read-modify-write</Term> in every language here; Go and Rust make it visible (the race detector, `Send`/`Sync`), Python leaves it to you.
</Depth>

### Choosing by what the work waits on

Profile first, then pick. Work that waits (HTTP, databases, files) overlaps on threads or asyncio; use asyncio when every library on the path is async, threads when they are not. Work that computes in pure Python needs processes on the standard build: one per core, with small arguments. Work in C extensions that release the GIL (hashing, compression, NumPy) can run in parallel on threads. Never compute or block inside a coroutine; hand it to an executor.
