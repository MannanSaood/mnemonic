reference:
  roles:
    - role: Local run queue
      example: "P0's runq, 256 slots"
      job: Runnable goroutines for one P. The owner adds and takes without a lock; thieves claim from the head with an atomic operation.
    - role: runnext
      example: the goroutine just created
      job: Runs next on this P, ahead of the queue. Stolen only as a last resort.
    - role: Global run queue
      example: overflow and woken goroutines
      job: Shared by all Ps behind a lock. Checked once every 61 schedules and whenever a local queue is empty.
    - role: Thief
      example: an idle P
      job: Tries other Ps in random order and takes half of a non-empty queue.
  useWhen:
    - Deciding how to split CPU work. Many goroutines, bounded, let stealing balance them.
    - A CPU profile or trace shows some Ps idle while others have long queues.
  avoidWhen:
    - Work must stay in order per key. Stealing reorders across goroutines, so keep one goroutine (or a sub-shard) per key and accept the cap.
  tradeoffs:
    - Each steal touches another P's queue, which costs an atomic operation and cache traffic. Stealing half keeps steals rare.
    - Work created on one P runs there first, which is good for cache locality, until stealing moves it.
    - Very small goroutines cost more in creating, queueing and stealing than they do in work. Batch them.
  lookalikes:
    - name: One shared queue
      how: Python's ProcessPoolExecutor and Node worker pools hand out work from one queue. Simple, but every take contends on it.
    - name: Static sharding
      how: Each key to a fixed worker. Keeps order per key, but one hot key caps at one core.
    - name: tokio and rayon
      how: The same idea in Rust. Tokio's queues and steal-half policy were modelled on Go's.

## [concept] Work stealing and run queues

**Each P has its own <Term id="run-queue">run queue</Term>. A P that runs out of work takes half of another P's queue. That is <Term id="work-stealing">work stealing</Term>, and it keeps every core busy without a central queue.**

New goroutines start on the P that created them. They spread out only when idle Ps come and take them.

<Depth level={2}>
Without one central queue, Ps rarely wait on each other: a P adds to and takes from its own queue without a lock. The <Term id="global-run-queue">global run queue</Term> still exists, behind a lock, for overflow and for goroutines that have no P to go to. The cost of the design is that work starts unbalanced, and stealing has to fix it.
</Depth>

<Depth level={3}>
`findRunnable` looks for work in a fixed order. Every 61st schedule it checks the global queue first, so goroutines there cannot starve. Then it tries its own <Term id="runnext">runnext</Term> slot and local queue, the global queue, the network poller, and finally `stealWork`: up to four passes over all Ps in random order, taking half of a victim's queue. Only on the last pass may it steal a victim's runnext.
</Depth>

## [problem] An ingest service sharded by tenant

A log-ingest service parses batches of log lines. To use every core, the team made one worker goroutine per core and routed each tenant to a fixed worker by its ID. It keeps each tenant's lines in order, and it is tested.

Read it with the model behind it: each worker owns a core, and the hash spreads tenants evenly, so the cores share the work.

<Depth level={2}>
For many small tenants of similar size this holds well enough. The hash gives each worker about the same number of tenants, and each tenant about the same traffic.
</Depth>

<Depth level={3}>
The sharding also does the scheduler's job by hand. Each worker is a single goroutine with a channel in front of it, so the runtime sees GOMAXPROCS long-lived goroutines and nothing to move.
</Depth>

## [morph] From fixed shards to stealing

Drag the slider. The shard router, one worker per core, becomes many parse goroutines queued on the P that made them, and idle Ps that steal from it.

The code morphs from a fixed worker per shard to a bounded goroutine per batch.

<Depth level={2}>
Order is the price. Two batches from Acme can now finish in either order. If order matters, give each key several sub-shards, or tag batches with sequence numbers and reorder where they are stored.
</Depth>

<Depth level={3}>
<Lang only="go">The `slots` channel bounds the batches in flight, so a burst cannot create millions of goroutines and their buffers. Size it to a small multiple of GOMAXPROCS.</Lang>
<Lang only="python">Python has no stealing, so the fix is one shared queue: `ProcessPoolExecutor` sends each task to whichever worker process asks next.</Lang>
<Lang only="typescript">Node has no stealing either. Piscina's single queue gives the next batch to whichever worker thread is idle.</Lang>
<Lang only="rust">`rayon::spawn` called from outside the pool pushes the job into rayon's global injector queue. Rayon threads take from it and steal from each other's deques.</Lang>
</Depth>

## [walk] Follow one burst

One burst from Acme's connection, from `go` to every core. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">A P's local queue is a ring of 256 slots indexed by a head and a tail. The owner writes the tail; thieves advance the head with a compare-and-swap in `runqgrab`, which takes `n - n/2`. When the ring is full, `runqputslow` moves half of it, plus the new goroutine, to the global queue. At most half the busy Ps' threads may be spinning in search of work at once, which limits the CPU spent looking.</Lang>
<Lang only="python">`ProcessPoolExecutor` feeds a call queue from a management thread; workers take items when they are free. The queue sits behind locks and pipes, which is fine when each task is milliseconds long.</Lang>
<Lang only="typescript">Piscina keeps its task queue on the main thread and posts a task to a worker when one is free, so balancing costs a message per task.</Lang>
<Lang only="rust">crossbeam's deque gives the owner a cheap push and pop at one end, and thieves steal from the other end. Tokio uses its own fixed-size queues and steals half, with a LIFO slot for the most recently woken task, similar to Go's runnext.</Lang>
</Depth>

### Why not one shared queue

One queue for all cores is simple, and it balances perfectly. Every take, though, goes through the same lock or the same atomic counter, and at high rates the cores spend their time waiting on it. Per-P queues make the common case private. Stealing pays the shared cost only when a P has run dry, and stealing half makes that rare.
