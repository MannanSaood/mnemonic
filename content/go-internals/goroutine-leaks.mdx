# ---------------------------------------------------------------- checks, one per depth
checks:
  overview:
    question: A handler starts three goroutines that send their answers on an unbuffered channel, reads the first answer and returns. What happens to the two slower goroutines?
    options:
      - text: They park on the send forever, keeping their stacks and their answers in memory.
        correct: true
        why: Right. Nobody will ever receive again, so their sends can never finish. A goroutine that cannot finish is a leak.
      - text: The garbage collector frees them once the handler has returned.
        why: The garbage collector never frees a goroutine. A parked goroutine is a root, so its stack and everything it points to stay alive.
      - text: They panic, because the channel's reader has gone.
        why: Only a send on a closed channel panics. Nobody closed this one; the reader just stopped reading.
  engineer:
    question: That handler leaks. A colleague changes make(chan *Profile) to make(chan *Profile, 1). What happens now?
    options:
      - text: It still leaks. One loser fills the slot and the other parks; on a timeout, two park.
        correct: true
        why: Right. A buffer of 1 fixes a single sender. With three senders and at most one read, you need a slot for each sender, and a context to stop work nobody wants.
      - text: The leak is gone, because no send can block on a buffered channel.
        why: A send on a buffered channel blocks when the buffer is full. One slot fills after the first late send.
      - text: The handler now blocks, because it has to drain the buffer before returning.
        why: Nothing forces the handler to drain the channel. It returns after one read, and the channel is collected later.
  deep:
    question: A toy program that blocks every goroutine prints "all goroutines are asleep - deadlock!". Why does the leaking server never print it?
    options:
      - text: The runtime only reports a deadlock when no goroutine can run. In the server, others keep running and could in principle still wake the stuck ones.
        correct: true
        why: Right. This is a partial deadlock. Proving that nobody can ever wake a goroutine needs more work, which is what the newer goroutineleak profile does with the garbage collector's reachability pass.
      - text: Deadlock detection is turned off in builds without the race detector.
        why: The check is part of every Go runtime. It simply does not apply while some goroutines can still run.
      - text: The garbage collector frees the stuck goroutines before the check runs.
        why: Blocked goroutines are never freed. That is exactly why leaks grow memory.

    - Fan-out that takes the first answer. Give the channel one slot per sender and cancel the rest.
    - Any goroutine whose result may go unread. Give it a slot to send into or a context to watch.
    - Long-lived workers and tickers. Give them a stop signal, and make sure something sends it.
  avoidWhen:
    - A goroutine that waits for a close that never comes, such as a range over a channel. A bigger buffer does not help; close the channel.

  tradeoffs:
    - A buffer as big as the number of senders holds unread answers until the channel is collected.
    - Cancellation only works if every call on the path accepts the context and checks it.
    - goleak catches leaks in tests, but only on the paths the tests run.
    - The goroutine profile shows leaks in production only after they have happened.

## [concept] Goroutine leaks

**A goroutine that waits for something that can no longer happen never exits.** It keeps its stack and everything it points to, and the number of them only goes up.

That is a <Term id="goroutine-leak">goroutine leak</Term>. It shows up as memory that climbs all day and a goroutine count that looks like a ramp.

<Depth level={2}>
The usual cause is a goroutine <Term id="goroutine-park">parked</Term> on a channel operation whose partner has gone: a send after the reader returned, a receive on a channel nobody will close, a worker with no stop signal. Every `go` statement needs an answer to one question: how does this goroutine end, in every case, including errors and timeouts?
</Depth>

<Depth level={3}>
The runtime cannot help by itself. A parked goroutine is a garbage-collection root, so it is never collected, and the runtime only reports a deadlock when every goroutine is blocked. A leak in a running server is a <Term id="partial-deadlock">partial deadlock</Term>: some goroutines are stuck forever, others are serving traffic.
</Depth>

## [problem] Ask three, take the first

The profile service reads from a primary and two replicas. To keep latency low, the handler asks all three at once and returns whichever answers first, or gives up after 100 ms.

It is fast and it passes every test. Each test makes one request, checks the answer and exits.

<Depth level={2}>
The mental model is that the slower goroutines will just finish on their own after the handler returns. They do finish their backend calls. Then they reach `ch <- p`.
</Depth>

<Depth level={3}>
The tests do not see the problem because the test process exits after each test, taking the stuck goroutines with it. A long-running server keeps every one of them.
</Depth>

## [pain] Memory that only goes up

**What happened:** the profile service's memory climbs all day, and the pods are OOM-killed every few hours.

The marked lines are the leak. The handler reads one value and returns. The two slower goroutines then run `ch <- p` on an unbuffered channel that nobody will ever read again, so they park forever. When a request times out, all three do.

<Depth level={2}>
At 50 requests a second, close to two leaked goroutines per request is about 95 a second, or 340,000 an hour. Each keeps at least a 2 KiB stack plus the profile it was trying to send. CPU stays flat, because parked goroutines do not run, so nothing looks wrong until memory runs out.
</Depth>

<Depth level={3}>
The <Term id="goroutine-profile">goroutine profile</Term> gives it away. `curl /debug/pprof/goroutine?debug=1` groups goroutines by identical stack, and one group, parked in `chan send` at `profile.go:8`, holds almost all of them and grows between snapshots.
</Depth>

## [morph] Give every goroutine a way out

Drag the slider. The unbuffered channel that is read once becomes a channel with one slot per sender, and a context appears that tells the losers to stop.

Two changes, each closing one way out. The buffer means a late sender always has somewhere to put its answer. The context means a sender still waiting on its backend is told to give up.

<Depth level={2}>
Either change alone leaves a gap. A buffer of 3 stops the leak, but the losers still finish their backend calls, which is wasted load on the replicas. A context alone stops the calls in flight, but a goroutine that already has its answer when the cancel arrives still sends, and on an unbuffered channel it parks.
</Depth>

<Depth level={3}>
`context.WithTimeout` also replaces `time.After`. Before Go 1.23, a `time.After` timer that had not fired stayed in memory until it did; since Go 1.23, timers that nothing refers to can be collected early. The context version is better for another reason: the same deadline travels into `b.Get`.
</Depth>

## [walk] Follow one request

One request through the fixed handler, from fan-out to the last goroutine exiting. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Cancelling closes the context's Done channel, and every goroutine parked in a `select` on it wakes up. A call such as `http.NewRequestWithContext` or a database driver's `QueryContext` watches that channel and returns `context.Canceled`. Code that never looks at `ctx` keeps running; cancellation is a request, not a kill.</Lang>
<Lang only="python">`task.cancel()` schedules a `CancelledError` to be thrown into the coroutine at its next `await`. A task that is in the middle of CPU work keeps running until it reaches one.</Lang>
<Lang only="typescript">`ac.abort()` fires the signal's `abort` event. `fetch` listens for it, rejects with an `AbortError` and closes the connection. Code that ignores the signal keeps running.</Lang>
<Lang only="rust">Aborting a tokio task marks it cancelled. The next time the scheduler would poll it, it drops the future instead, which runs the destructors of everything the future owned, such as open connections.</Lang>
</Depth>

## [again] The same traffic, again

The same 1,000 requests, with the same backend latencies. This time nothing is left parked. The goroutine count after the burst is the same as before it, and memory stays flat.

<Depth level={2}>
Make it stay fixed. Add `goleak.VerifyNone(t)` to the handler's tests, or `goleak.VerifyTestMain(m)` for the whole package, so a test fails if it leaves a goroutine behind. In production, graph `runtime.NumGoroutine()` next to request rate: under steady load it should be flat.
</Depth>

<Depth level={3}>
The Go team added a `goroutineleak` profile to `runtime/pprof`, experimental in Go 1.26 and, per the Go blog, arriving in Go 1.27. It runs a special garbage collection in which only runnable goroutines are roots. A blocked goroutine whose channel or lock is never reached from them can never be woken, so it is reported as leaked.
</Depth>

## [lens] How each language meets it

Every language with background tasks can leak them. What differs is what a leak costs and who notices.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={2}>
Go parks a whole goroutine and keeps it forever. Python keeps only weak references to tasks, so a stuck task is eventually destroyed with a warning. In Node a stuck Promise holds only its closures, but losing requests keep running. In Rust a dropped receiver turns a blocked send into an error, so tasks tend to exit, but a spawned task runs to completion unless something aborts it.

### Finding leaks

In tests, use `go.uber.org/goleak`. In production, watch `runtime.NumGoroutine()` over time and take the goroutine profile (`/debug/pprof/goroutine?debug=1`) twice, a few minutes apart: the group whose count grows, all parked on the same line, is the leak. Typical lines are `chan send`, `chan receive` on a channel nobody closes, and `select` with no case that can ever fire.
