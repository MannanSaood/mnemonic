## [concept] Inside a channel

**A channel is a locked ring buffer plus two queues of parked goroutines.** A send hands its value to a receiver that is already waiting, or drops it into a free slot, or parks the sender until there is room.

That one rule tells you, for any line with `<-` in it, whether your goroutine keeps running.

<Depth level={2}>
The runtime object behind `make(chan T, n)` is an <Term id="hchan">hchan</Term>. It holds a lock, a buffer of `n` slots with a send index and a receive index, a `closed` flag, and two wait queues: `recvq` for goroutines parked in a receive and `sendq` for goroutines parked in a send. To <Term id="goroutine-park">park</Term> a goroutine means taking it off its thread until another goroutine wakes it. A parked goroutine uses no CPU, but it keeps its stack and holds up whoever is waiting for it.
</Depth>

<Depth level={3}>
In `runtime/chan.go`, `chansend` checks in a fixed order. A nil channel blocks forever. A closed channel panics. A receiver on `recvq` gets the value copied straight onto its stack and is made runnable. A free slot takes a copy at `sendx`. Otherwise the sender wraps itself in a <Term id="sudog">sudog</Term>, joins `sendq` and calls `gopark`. `chanrecv` mirrors it, and `closechan` wakes every waiter at once.
</Depth>

## [problem] A send that looked free

A checkout handler records an analytics event for every order. Shipping the event takes a network call, so the handler puts it on a channel and a background goroutine ships it. The handler should never wait on analytics.

It works. In testing the collector answers in 3 ms, and nobody notices the send at all.

<Depth level={2}>
The mental model behind this code is that a channel is a mailbox: drop a letter in, walk away. On an unbuffered channel that is wrong. There is no slot to drop anything into. A send can only finish at the moment a receiver takes the value.
</Depth>

<Depth level={3}>
The test hid it because `shipEvents` is almost always parked in its receive, waiting. Every send finds it on `recvq` and hands the value over in microseconds. The handler only waits when the shipper is busy, and in testing it is never busy for long.
</Depth>

## [pain] The collector has a slow minute

**What happened:** the analytics collector slowed to 400 ms per event, and checkout latency went from 40 ms to several seconds.

The marked lines are the whole story. While `shipEvents` is inside `analytics.Send`, nobody is waiting to receive. Each checkout reaches the send, finds no receiver and no buffer, and parks on `sendq`. They leave one at a time, each 400 ms after the last.

<Depth level={2}>
At 200 checkouts a second and 2.5 shipped events a second, the queue of parked handlers grows by almost 200 a second. Each new checkout waits for every one ahead of it, so latency climbs until load balancers time requests out. The payment went through, but the customer saw an error. The send that was meant to decouple checkout from analytics coupled them completely.
</Depth>

<Depth level={3}>
A goroutine dump during the incident shows hundreds of goroutines in `chan send`, all on the same line. They are not using CPU, so CPU graphs look calm. The runtime does not report it: other goroutines are still running, so this is not the "all goroutines are asleep" deadlock it can detect.
</Depth>

## [morph] From mailbox to hchan

Drag the slider. The mailbox you imagined becomes what the runtime has: a header with a lock, a ring buffer, and two queues of parked goroutines.

The code changes in two ways. The channel gets a buffer sized for the slowdowns you expect, and the send becomes a try that never parks the handler. If the buffer is full, the event is dropped and counted.

<Depth level={2}>
Size the buffer from numbers: inflow per second times the longest slowdown you want to absorb. 200 events a second for 20 seconds is 4,096 slots, a few hundred kilobytes. Then decide what happens when it is full anyway. For analytics, dropping and counting is right. For a payment ledger it is not; there you want <Term id="backpressure">backpressure</Term> or a durable queue.
</Depth>

<Depth level={3}>
A `select` with a `default` case compiles to a non-blocking channel operation. `chansend` is called with `block == false`, and if the channel is full it can even return without taking the lock, after a quick check of the count. The handler never reaches `gopark`.
</Depth>

One event from the handler to the shipper, through the real mechanism. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">When a receiver is parked, the send takes the receiver's sudog off `recvq`, copies the value to the address the sudog records (a variable on the receiver's stack), and calls `goready`. This <Term id="direct-handoff">direct handoff</Term> is why an unbuffered channel can be faster than a buffered one when a receiver is always waiting: one copy instead of two. When the buffer is full and a sender is parked, a receive takes the oldest value and puts the parked sender's value into the same slot, so order is kept.</Lang>
<Lang only="python">An `asyncio.Queue` is not locked, because one thread runs the event loop. Waiting getters and putters are futures in two deques. `put_nowait` stores the item and wakes the first getter's future; the getter resumes on a later loop iteration and takes the item.</Lang>
<Lang only="typescript">Resolving a Promise does not run the waiting code at once. The continuation after `await` is queued as a microtask and runs after the current function returns. Nothing here can run in parallel, so the array needs no lock.</Lang>
<Lang only="rust">A tokio bounded channel counts free slots with a semaphore. `try_send` tries to take a permit and returns `Full` if there is none. A parked receiver is a task whose `Waker` the channel stored; sending wakes it, and the scheduler polls it again.</Lang>
</Depth>

## [again] The same slow minute, again

The collector slows to 400 ms for eight seconds, exactly as before. This time every checkout finds a free slot and returns at once. The buffer reaches about 1,580 events and drains in about twelve seconds once the collector recovers. Nobody waits, and nothing is dropped.

<Depth level={2}>
Export `len(events)` and `dropped` as metrics. The buffer turns a latency incident into a number that grows quietly, so you need to see that number. An alert on the queue length warns you long before drops begin.
</Depth>

<Depth level={3}>
`len(ch)` reads `qcount` without taking the lock. That is fine for a gauge, but never use it to decide whether a send will block; by the time you send, it may have changed. Use `select` with `default` for that decision.
</Depth>

## [lens] How each language meets it

Go builds channels into the language and the runtime. Python and Rust ship queues in the library. Node has no channel type at all, and rarely needs one.

### Close, nil and the zero value

Closing a channel wakes every parked receiver with the zero value and `ok == false`, and every parked sender with a panic. Values already in the buffer are still delivered first; only then do receives start returning the zero value. A nil channel is different: a send or receive on it blocks forever. That sounds useless, but inside a `select` it switches a case off, which is how you stop listening to a channel that has been drained.
