      job: Sets the heap target as live heap × (1 + GOGC/100). Off disables it.
    - role: GOMEMLIMIT
      example: "GOMEMLIMIT=460MiB, debug.SetMemoryLimit"
      job: Caps the target so total runtime memory stays under the limit, softly.
    - role: Pacer
      example: runtime/mgcpacer.go
      job: Computes the target and starts each cycle so marking ends near it.
    - role: GC CPU limiter
      example: about 50% over a short window
      job: Stops the GC from taking more, letting memory exceed the limit instead.
  useWhen:
    - A Go service runs in a container with a memory limit (set GOMEMLIMIT a little under it).
    - GC CPU is high and memory is plentiful (raise GOGC, or GOGC=off with a limit if the process owns its container).
    - A profile shows the live heap itself is near the limit (cut what you hold; no knob will help).
  avoidWhen:
    - The program shares memory with other processes it does not control, such as a CLI tool or a desktop app. A limit there can push the GC into thrashing.
    - You have not profiled allocations yet. Fewer allocations beat any setting.
  tradeoffs:
    - Higher GOGC means less GC CPU and more memory, all the time.
    - A memory limit costs nothing until memory is short, then costs GC CPU, up to about half of it.
    - GOGC=off with a limit gives the fewest cycles, but a growing live heap goes straight into the death spiral.

    - name: "Node's --max-old-space-size"

    - name: "JVM -Xmx and GC ergonomics"

    - name: "CPython gc.set_threshold"

## [concept] Tuning the GC

**<Term id="gogc">GOGC</Term> decides how big the heap may grow between cycles, as a multiple of the live heap. <Term id="gomemlimit">GOMEMLIMIT</Term> caps that size, so the GC runs more often only when memory is short.**

More memory means fewer cycles and less GC CPU. Less memory means the reverse. The two knobs choose where on that line you sit.

<Depth level={2}>
The <Term id="gc-pacer">pacer</Term> sets the target at the end of each cycle: live heap plus (live heap plus roots) times GOGC/100. With the default of 100 the heap may double. GOMEMLIMIT, added in Go 1.19, is a soft cap on all memory the runtime manages. Most services in containers should set the limit a little under the container's and leave GOGC alone.
</Depth>

<Depth level={3}>
The GC's CPU cost per cycle depends mostly on the live heap it must mark. Its frequency depends on how fast you allocate and how much room the target leaves. Double GOGC and you roughly halve the cycles, and so the GC CPU, at the price of more memory. A memory limit shrinks the room only when total memory approaches it.
</Depth>

## [problem] An ingest worker in a container

A worker pulls records from a queue in batches, decodes them, and inserts them into a database. It runs on Kubernetes with a 512 MiB memory limit and no GC settings. With 10,000-record batches its live heap peaks around 60 MiB, and memory never comes near the limit.

The model behind it: the GC frees memory, so the process uses about as much as it holds.

<Depth level={2}>
At that size the default target of twice the live heap is far below 512 MiB. Nobody had a reason to think about GOGC.
</Depth>

<Depth level={3}>
The Go runtime does not read the container's memory limit. Unless told, the GC sizes the heap only from the live heap and GOGC.
</Depth>

## [pain] Then a change request arrives

**Change request:** fetch batches of 50,000 records instead of 10,000, to cut queue round trips.

The marked line is the only change. Now the live heap peaks near 300 MiB during a burst. The pacer sets the next target at about 600 MiB, plus stacks and runtime memory, and the heap grows toward it. At 512 MiB the kernel's <Term id="oom-killer">OOM killer</Term> ends the process. The pod restarts with `OOMKilled`, picks up the same batch, and dies again.

<Depth level={2}>
The confusing part: GC CPU was low the whole time, and the live heap was only 300 MiB. The GC did exactly what GOGC told it to. It had no idea the <Term id="memory-cgroup">memory cgroup</Term> would kill it first.
</Depth>

<Depth level={3}>
Lowering GOGC to 50 also fits the burst, but it makes every cycle come sooner all the time, quiet periods included. Setting GOMEMLIMIT changes nothing until memory is actually short.
</Depth>

## [morph] From "the GC keeps memory low" to "the GC grows to a target"

Drag the slider. The picture of a GC that keeps memory close to live data becomes the pacer: it lets the heap grow to a target set from the live heap and GOGC, and only a memory limit makes that target notice the container.

The code sets the limit from the container's cgroup at 90%, and keeps GOGC at its default.

<Depth level={2}>
Leave headroom. The limit counts memory the Go runtime manages: heap, stacks, runtime structures. It does not count memory used by C libraries through cgo, or the parts of the binary mapped from disk. The GC guide suggests 5 to 10% headroom.
</Depth>

<Depth level={3}>
<Lang only="go">`GOMEMLIMIT=460MiB` in the environment does the same as `debug.SetMemoryLimit`. Setting it from code lets you read the cgroup's `memory.max` at startup, so one image works with any container size.</Lang>
<Lang only="python">There is no heap target to cap. The fix is to hold less at once: decode and insert in chunks, and let reference counting free each chunk as soon as it is replaced.</Lang>
<Lang only="typescript">`--max-old-space-size` is in MiB. It limits V8's old space only; buffers, new space and native memory come on top, which is why 384 leaves room under a 512Mi container.</Lang>
<Lang only="rust">There is nothing to configure. Memory is set by what the code holds, so the fix is the same as in Python: process in chunks.</Lang>
</Depth>

## [walk] Follow the heap through a burst

One burst, from the pacer setting a target to the limit stepping in, and what happens if the live heap keeps climbing. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">The target formula and the minimum heap of 4 MiB are in the GC guide; the code is `runtime/mgcpacer.go`. When the memory limit is lower than the GOGC target, the pacer uses the limit minus memory it cannot free. The CPU limiter, `gcCPULimiter`, caps GC CPU at about 50% over a window of 2 × GOMAXPROCS CPU-seconds, so a bad limit slows a program by about 2× at most.</Lang>
<Lang only="python">CPython's cycle collector triggers on allocation counts, not on memory size: the youngest generation is collected when allocations minus deallocations of tracked objects pass its threshold, which `gc.get_threshold()` shows.</Lang>
<Lang only="typescript">As old space nears `--max-old-space-size`, V8 runs full mark-compacts more and more often, then gives up with "Ineffective mark-compacts near heap limit".</Lang>
<Lang only="rust">The global allocator (the system malloc, jemalloc or mimalloc) may keep freed pages for reuse, so RSS can stay above live data after a burst. That is a fragmentation and return-to-OS question, not a GC one.</Lang>
</Depth>

## [again] The 50,000-record batch, the second time

The same burst with GOMEMLIMIT at 460 MiB. The heap target stops at the limit, so cycles come about twice as often during the burst. Memory peaks near 460 MiB, GC CPU stays under a fifth, and the pod survives. Between bursts, the GC runs exactly as it did before.

<Depth level={2}>
Watch `/gc/heap/goal:bytes` and `/gc/gomemlimit:bytes` from `runtime/metrics`. If the goal sits at the limit for long stretches, the live heap is too close to it, and the next step is to hold less, not to tune more.
</Depth>

<Depth level={3}>
If the live heap rises to the limit, the GC enters the <Term id="gc-death-spiral">death spiral</Term>: every cycle frees almost nothing and the next is due at once. The CPU limiter keeps the program alive at about half speed and lets memory exceed the limit. Alert on GC CPU, not only on memory.
</Depth>

## [lens] How each language handles memory pressure

Go gives you a heap target and a soft limit. Node gives you a hard heap limit. Python and Rust have no heap target at all: memory follows what you hold.

### Which knob for which problem

| Symptom | Setting |
|---|---|
| OOM-killed in a container, live heap well under the limit | GOMEMLIMIT about 10% under the container limit |
| GC CPU high, plenty of spare memory | Raise GOGC, or GOGC=off with GOMEMLIMIT if the process owns its container |
| Memory too high, CPU to spare, no container limit | Lower GOGC |
| Live heap close to the limit, GC CPU near 50% | No knob helps: hold less, or give the container more memory |
