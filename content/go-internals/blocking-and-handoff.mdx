    question: A goroutine waits on a channel that has no value yet. What happens to the OS thread it was running on?
    options:
      - text: The goroutine is parked and the thread runs another goroutine straight away.
        correct: true
        why: Right. Channel waits, mutex waits, sleeps and network reads all park the goroutine inside the runtime. The thread and the P carry on.
      - text: The thread sleeps until the channel gets a value.
        why: That is what a blocking system call does. A channel wait never leaves the Go runtime, so no thread has to wait.
      - text: The runtime creates a new thread for the other goroutines.
        why: Not needed. The thread is free already; a new one is started only when a thread is stuck in the kernel.
  engineer:
    question: A Go service with GOMAXPROCS 8 shows 3,000 OS threads while its NFS mount is slow. What is going on?
    options:
      - text: Each goroutine in a file read holds a thread in the kernel, and the runtime starts new threads so the Ps keep running other goroutines.
        correct: true
        why: Right. File reads are blocking system calls. Bound them with a semaphore; at 10,000 threads the runtime crashes the program.
      - text: GOMAXPROCS is being ignored, so every goroutine gets its own thread.
        why: GOMAXPROCS still holds. It limits threads running Go code, and threads blocked in system calls do not count against it.
      - text: The netpoller creates one thread per open file.
        why: The netpoller handles sockets and pipes with one epoll or kqueue instance. Regular files cannot be polled, which is why their reads block a thread.
  deep:
    question: A goroutine's read syscall returns after 30 s. Its P was handed off long ago and every P is busy. What does the runtime do?
    options:
      - text: It puts the goroutine on the global run queue and parks the thread as an idle M.
        correct: true
        why: Right. That is exitsyscall's slow path. The goroutine runs when some P picks it from the global queue, and the parked thread is reused later instead of being destroyed.
      - text: It takes a P back from whichever thread is running a goroutine.
        why: No. A P is only taken from a thread that is itself stuck in a system call. A running goroutine is never robbed of its P this way.
      - text: The thread keeps running the goroutine without a P until it blocks again.
        why: No. A thread must hold a P to run Go code. Without one, it can only hand the goroutine back and wait.

    - role: Parked goroutine
      example: "<-jobs, mu.Lock(), conn.Read"
      job: Waits inside the runtime. Costs a stack, no thread.
    - role: Netpoller
      example: epoll, kqueue or IOCP
      job: Tells the scheduler which sockets are ready, so their goroutines can run again.
    - role: Thread in a syscall
      example: "f.Read, a cgo call"
      job: Waits in the kernel with its goroutine. Holds an M until the call returns.
    - role: sysmon
      example: a runtime thread with no P
      job: Retakes Ps from threads stuck in syscalls and hands them to other threads.
  useWhen:
    - A service reads files, calls cgo, or uses a syscall that can block for long.
    - The thread count is far above GOMAXPROCS and you need to know why.
    - Deciding whether a wait needs a bound (file and cgo) or not (network, channels).
  avoidWhen:
    - The wait is network I/O, a channel or a lock. Those park the goroutine; one goroutine per connection is fine.
  tradeoffs:
    - A hand-off keeps throughput but costs an OS thread per blocked call, each with its own stack and kernel bookkeeping.
    - sysmon only looks every 20 µs to 10 ms, so a P can sit idle briefly before the hand-off.
    - A semaphore around file reads turns a thread explosion into queued requests and 503s, which is better, but still visible to users.
  lookalikes:
    - name: Node's libuv thread pool
      how: Runs file reads on a small fixed pool (4 threads by default) instead of creating threads; a stall fills the pool instead of growing it.
    - name: "tokio's spawn_blocking"
      how: A separate pool for blocking calls, up to 512 threads by default. The async workers never hand off; you must move blocking work there yourself.
    - name: Python asyncio executors
      how: Blocking calls go to a thread pool through to_thread or run_in_executor; otherwise they freeze the event loop.

## [concept] When a goroutine blocks

**A goroutine that waits on a channel, a lock or a socket is <Term id="goroutine-park">parked</Term>, and its thread runs the next goroutine. A goroutine in a <Term id="blocking-syscall">blocking system call</Term> keeps its thread, so the runtime gives that thread's P to another thread.**

Blocking looks the same in your code. In the runtime there are three different paths, and only one of them costs an OS thread.

<Depth level={2}>
Parked waits (channels, `sync.Mutex`, `time.Sleep`, `select`) never leave the runtime. Network reads and writes go through the <Term id="netpoller">netpoller</Term>: the socket is non-blocking, the goroutine parks, and the runtime learns from epoll, kqueue or IOCP when it is ready. File reads and cgo calls are real blocking calls: the thread waits in the kernel. That is when <Term id="sysmon">sysmon</Term> and the <Term id="p-handoff">P hand-off</Term> matter.
</Depth>

<Depth level={3}>
A regular file is always "ready" as far as epoll is concerned, and Linux refuses to register one, so Go reads files with plain blocking syscalls. The runtime brackets every syscall with `entersyscall` and `exitsyscall`. In between, the goroutine is in the `_Gsyscall` state: it has an M, and the P is attached but not owned, so sysmon may take it.
</Depth>

## [problem] A thumbnail handler that reads from disk

A media service serves thumbnails straight from disk. Each request runs in its own goroutine, reads one file, and writes it out. On local SSD a read takes well under a millisecond. It works, and it is tested.

Read it with the usual model: goroutines are cheap, blocking is cheap, and the runtime handles the rest.

<Depth level={2}>
That model is right for the network side of this handler. Thousands of idle keep-alive connections cost goroutine stacks and nothing more, because they wait on the netpoller.
</Depth>

<Depth level={3}>
The file read is the one call here that takes a thread into the kernel. On a fast disk the call returns before anyone notices, so the cost never shows.
</Depth>

## [pain] Then a change request arrives

**Change request:** serve thumbnails from the archive too, which is mounted over NFS.

The marked line is the only change. Weeks later the NFS server stalls for 30 seconds. Requests keep arriving, each goroutine blocks in `read`, and each one holds an OS thread. The runtime keeps starting threads so the Ps can serve other routes. The thread count climbs into the thousands, and at 10,000 the runtime stops the program with a fatal error.

<Depth level={2}>
The naive model says a blocked goroutine costs nothing. That is true for channels and sockets and false for file reads. GOMAXPROCS does not help: it limits threads running Go code, and threads stuck in system calls do not count against it.
</Depth>

<Depth level={3}>
The 10,000 limit is the runtime's default `maxmcount`, changeable with `debug.SetMaxThreads`. Raising it only moves the crash: each thread has its own stack and kernel structures, and the process may hit the kernel's own thread or memory limits first.
</Depth>

## [morph] From "every wait is the same" to three paths

Drag the slider. The single picture of a parked goroutine splits into what really happens for a file read: the goroutine and its M wait in the kernel, sysmon retakes the P, and another thread runs it.

The code morphs to put a bound on how many handlers can be inside a file read at once.

<Depth level={2}>
The bound turns a thread explosion into a queue. Requests beyond the limit wait on the `fileSlots` channel, which parks them without a thread, and give up with a 503 after two seconds. Pick the limit from what the storage can serve, not from GOMAXPROCS.
</Depth>

<Depth level={3}>
<Lang only="go">A blocked `read` cannot be cancelled from Go; the context only lets a waiting request give up before it starts the read. For a mount that can hang, `O_NONBLOCK` does not help either, because Linux ignores it for regular files.</Lang>
<Lang only="python">`asyncio.to_thread` runs the call in the loop's default `ThreadPoolExecutor`. Its size is `min(32, os.cpu_count() + 4)`, so a limit of 16 leaves threads free for other blocking calls.</Lang>
<Lang only="typescript">`readFile` from `fs/promises` queues the read on libuv's thread pool. The pool is shared with `dns.lookup`, `zlib` and some `crypto` calls, so reserve some of it.</Lang>
<Lang only="rust">`tokio::fs::read` wraps `std::fs::read` in `spawn_blocking`. The semaphore keeps the blocking pool from filling with stuck reads.</Lang>
</Depth>

## [walk] Follow one stuck read

One file read on the stalled mount, from the syscall to the hand-off and back. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">sysmon sleeps 20 µs at first, and starts doubling its sleep up to 10 ms once it has been idle for a while. In `retake`, it takes a P only if the P has stayed in the same syscall for more than one of its ticks. It leaves the P alone if the P has no work, other Ps are idle or spinning, and the call is younger than 10 ms. `handoffp` then starts an M when the P has work to run.</Lang>
<Lang only="python">CPython releases the GIL around blocking I/O, so the executor thread waits in the kernel while other threads, including the event loop's, keep running Python.</Lang>
<Lang only="typescript">libuv's thread pool has a fixed size, set once from `UV_THREADPOOL_SIZE` when it starts. When all its threads are stuck, new work simply waits in its queue; no thread is added.</Lang>
<Lang only="rust">Tokio's blocking pool grows on demand up to `max_blocking_threads` and keeps idle threads for a while before they exit. Beyond the cap, new blocking tasks queue.</Lang>
</Depth>

## [again] The NFS stall, the second time

The same 30-second stall with the bound in place. At most 64 threads wait in the kernel. Every other request either waits on the channel, which costs nothing, or gets a fast 503. Other routes keep their full speed, because their goroutines never need a file slot.

<Depth level={2}>
Watch `/sched/threads/total:threads` from `runtime/metrics`, or the thread count in your process metrics. A thread count far above GOMAXPROCS plus your bound means some blocking call is not behind it.
</Depth>

<Depth level={3}>
cgo calls go through the same `entersyscall` path, so a slow C library call is a blocking syscall as far as the scheduler is concerned. Bound those the same way.
</Depth>

## [lens] How each language handles a blocking call

Go detects the blocking call and adds a thread for you. Python, Node and tokio give you an event loop and expect you to move blocking calls off it yourself.

### Which waits cost a thread

- Channel, `select`, `sync.Mutex`, `time.Sleep`: the goroutine waits in a runtime wait queue. No thread is held.
- Socket read or write: the goroutine waits on the netpoller. No thread is held.
- Regular file read or write: the goroutine and its thread wait in the kernel. A thread is held until the call returns.
- cgo call: the thread runs or waits in C code, treated as a syscall. A thread is held.
