      - text: One, because Go runs goroutines on a single thread unless you ask for more.

  engineer:
    question: A Go 1.24 service runs in a container limited to 2 CPUs on a 32-core host. Latency is spiky and the container is CPU-throttled. What is the likely cause?
    options:
      - text: GOMAXPROCS defaulted to 32, so up to 32 threads run Go code and burn the 2-CPU quota in bursts.
        correct: true
        why: Right. Before Go 1.25 the default ignored the cgroup CPU limit. Set GOMAXPROCS to the limit, or move to Go 1.25+, where the default follows the cgroup CPU bandwidth limit.
      - text: The service has too many goroutines, and each one needs its own thread.
        why: Goroutines do not need their own threads. The number of threads running Go code follows GOMAXPROCS, not the goroutine count.
      - text: The garbage collector is limited to one CPU inside containers.
        why: No such limit exists. GC work is spread over the Ps like other work.
  deep:
    question: Why does every P have its own local run queue instead of all Ms sharing one queue?
    options:
      - text: So that putting and taking goroutines usually touches only the P's own queue, without a lock shared by every thread.
        correct: true
        why: Right. The local queue is a fixed ring of 256 slots that the owner uses without a lock. The global queue, behind a lock, is only for overflow and fairness, checked once every 61 schedules.
      - text: So that each goroutine always runs on the same core for its whole life.
        why: No. Goroutines move between Ps when idle Ps steal work or when they come back from the global queue.
      - text: Because the kernel requires one queue per thread.
        why: The kernel knows nothing about goroutines or Ps. The run queues are the Go runtime's own data structures.

## [concept] G, M and P

**Go runs many <Term id="goroutine">goroutines</Term> on a few <Term id="os-thread">OS threads</Term>. A thread may run Go code only while it holds a <Term id="go-p">P</Term>, and there are <Term id="gomaxprocs">GOMAXPROCS</Term> of them.**

So at any instant, at most GOMAXPROCS goroutines are running. Every other goroutine that is ready waits in a <Term id="run-queue">run queue</Term>.

<Depth level={2}>
Three roles. A **G** is a goroutine: a function and its stack. An **M** (machine) is an OS thread that the kernel schedules onto a core. A **P** (processor) is the permission to run Go code, plus a local queue of runnable Gs. An M with a P runs Gs from that P's queue. GOMAXPROCS sets the number of Ps. It defaults to the number of CPUs the process may use, and since Go 1.25 on Linux it also respects a lower cgroup CPU limit.
</Depth>

<Depth level={3}>
The runtime source (`runtime/proc.go`) describes P as "a resource that is required to execute Go code". Each P owns a run queue of 256 slots, used without a lock by its owner, and a `runnext` slot for a goroutine that should run next. A global run queue, protected by a lock, takes overflow and is checked once every 61 schedules so nothing there starves. Threads blocked in system calls do not hold a P, so the number of Ms can be larger than GOMAXPROCS; the package docs say there is no limit on those threads (the runtime stops at 10,000 by default).
</Depth>

## [problem] An exporter that starts a goroutine per image

A media service renders thumbnails every night. The exporter starts one goroutine per image and waits for all of them. The same process serves the API and `/healthz`. It works, and it is tested with a few hundred images.

Read it with the mental model most people start with: each goroutine is a small thread, they all run at once, so more goroutines mean more done in parallel.

<Depth level={2}>
For I/O this style is fine: goroutines that wait on the network cost a few kilobytes each and no thread. Resizing is CPU work. Twenty milliseconds of it per image keeps a core busy, whoever runs it.
</Depth>

<Depth level={3}>
Each goroutine also holds its decoded image for as long as it lives. With one goroutine per image, a preempted goroutine keeps its half-done image in memory while it waits, so peak memory follows the number of started goroutines, not the number of cores.
</Depth>

## [pain] Then a change request arrives

**Change request:** the nightly export must cover whole tenants, 50,000 images per run instead of 500.

The marked line is the only change. That night the load balancer marks the pod unhealthy: `/healthz` takes seconds to answer, while the export itself is no faster than before per image. The naive model cannot explain it. If every goroutine runs at once, why does a tiny handler wait?

<Depth level={2}>
On a 4-core node with GOMAXPROCS 4, four goroutines run at a time. The other 49,996 are runnable and wait in the run queues. A goroutine runs for up to about 10 ms before it is <Term id="preemption">preempted</Term>, so a handler goroutine that joins the back of a queue of 256 waits roughly 256 × 10 ms, about 2.5 s, before its first instruction. That estimate is ours, from the queue size and the time slice; measure your own with `runtime/metrics`.
</Depth>

<Depth level={3}>
The cost meter shows the health check's wait. The export's total time is set by the CPU work, 50,000 × 20 ms spread over 4 cores, whatever the number of goroutines.
</Depth>

## [morph] From threads at once to G, M and P

Drag the slider. The kernel running every goroutine at once becomes what the runtime actually does: goroutines queue on Ps, an M holds each P, and each M runs on a core.

The code morphs from one goroutine per image to one worker per P, fed through a channel.

<Depth level={2}>
The batch takes the same time either way, because the cores are the limit. What changes is the length of the run queues: with GOMAXPROCS workers they stay nearly empty, so any other goroutine, such as the health check, gets a P within about one time slice.
</Depth>

<Depth level={3}>
<Lang only="go">`runtime.GOMAXPROCS(0)` reads the setting without changing it. `for range n` over an integer needs Go 1.22. For mixed work, size the pool by the CPU part, or split CPU and I/O into separate stages with their own limits.</Lang>
<Lang only="python">`ProcessPoolExecutor` runs each task in a separate process with its own interpreter and its own GIL. `chunksize=64` sends images in batches, so 50,000 tasks do not mean 50,000 round trips between processes.</Lang>
<Lang only="typescript">Piscina keeps a fixed set of `worker_threads` and queues tasks in the main thread. `os.availableParallelism()` is the Node API meant for sizing such pools.</Lang>
<Lang only="rust">`spawn_blocking` moves the batch off tokio's async workers onto its blocking pool, and rayon splits the iterator over its own pool of one thread per core.</Lang>
</Depth>

## [walk] Follow one goroutine

One goroutine from `go` to a CPU core, and the health check behind it. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`newproc` puts the new G in the creating P's `runnext` slot, and the G that was there moves to the back of the local queue. When the local queue is full, `runqputslow` moves half of it to the global queue. `findRunnable` looks at the local queue, then the global queue, then the network poller, then tries to steal from other Ps. Preemption after 10 ms has been asynchronous, signal-based, since Go 1.14, so even a tight loop without function calls can be stopped.</Lang>
<Lang only="python">CPython threads are real OS threads scheduled by the kernel. The GIL decides which one may run bytecode: a thread that wants it asks, and the holder drops it at the next switch interval. There is no run queue in Python itself.</Lang>
<Lang only="typescript">Node's event loop runs callbacks one at a time. A worker thread has its own event loop and V8 heap; messages between threads are copied with the structured clone algorithm unless you transfer or share buffers.</Lang>
<Lang only="rust">Tokio's scheduler gives each worker a local queue and a LIFO slot for the most recently woken task, much like Go's `runnext`. Because tasks are not preempted, tokio also gives each task a budget of operations, after which its resources report "not ready" so the task yields at its next `.await`.</Lang>
</Depth>

## [again] 50,000 images, the second time

The same request with workers sized to GOMAXPROCS. The batch takes as long as the CPU work needs. The run queues stay short, so `/healthz` waits about one time slice instead of seconds, and memory holds four decoded images instead of thousands.

<Depth level={2}>
In containers, check what GOMAXPROCS the process got. Go 1.25+ follows the cgroup CPU bandwidth limit and updates it if the limit changes. On older versions, set the `GOMAXPROCS` environment variable to the CPU limit.
</Depth>

<Depth level={3}>
Setting `GOMAXPROCS` yourself, with the environment variable or `runtime.GOMAXPROCS`, turns off the automatic container-aware default and its updates.
</Depth>

### Seeing the scheduler in a real program

Run with `GODEBUG=schedtrace=1000` and the runtime prints one line per second with GOMAXPROCS, idle Ps, thread counts, the global queue length and each P's local queue length. Long local queues under CPU load mean more runnable goroutines than Ps. `go tool trace` shows the same thing per P on a timeline.
