## [concept] Garbage collection

**Go's collector finds live objects by starting at the <Term id="gc-root">roots</Term> and following every pointer. It colours objects white, grey and black as it goes, and frees what stays white. Most of this runs while your program runs.**

That is <Term id="tricolor-marking">tri-colour marking</Term>. It is cheap when little is live, and costly when much is live, however little garbage there is.

<Depth level={2}>
The collector is concurrent, non-moving and not generational. It stops the world twice per cycle, each time for well under a millisecond. In between, background workers use about a quarter of the CPU to mark, and goroutines that allocate quickly can be drafted to help, which is <Term id="mark-assist">mark assist</Term>. Sweeping happens lazily, as new memory is needed.
</Depth>

<Depth level={3}>
Marking concurrently with a running program only works because of the <Term id="write-barrier">write barrier</Term>. Go's is a hybrid: on each pointer store during marking it shades the object being overwritten (Yuasa's deletion barrier) and, while the storing goroutine's stack is not yet scanned, the object being stored (Dijkstra's insertion barrier). This lets Go scan each stack once, without the re-scan that older versions needed at mark termination.
</Depth>

## [problem] An in-memory session store

A shop keeps logged-in sessions in a map, keyed by session id. Each session holds the user id, a slice of roles, an expiry time and a pointer to the cart. Sessions last 24 hours, so about 400,000 are alive at any time. It is simple and fast, and the GC barely shows in profiles.

The model behind it: the GC cleans up garbage, so data you keep costs memory and nothing else.

<Depth level={2}>
At 400,000 sessions the live heap is a few hundred megabytes at most, and each cycle marks it in a few milliseconds of CPU spread across the workers.
</Depth>

<Depth level={3}>
Each session is several heap objects: the struct, the user id string's bytes, the roles slice's array and each role string, the cart. Every one of them is a pointer the marker follows on every cycle.
</Depth>

## [pain] Then a change request arrives

**Change request:** keep sessions for 30 days instead of 24 hours.

The marked line is the only change. Live sessions grow to 12 million. Nothing leaks and the garbage rate is the same, yet GC CPU climbs, and p99 latency on every endpoint grows. Profiles show `gcBgMarkWorker` and `gcAssistAlloc` near the top. Request handlers that allocate are paying for marking sessions they never touch.

<Depth level={2}>
Each cycle must mark every live session again, because the collector has no memory of what was live last time. Thirty times the live objects is about thirty times the marking. Raising GOGC makes cycles rarer, but each one is just as long.
</Depth>

<Depth level={3}>
Mark assist is what turns GC cost into latency. The pacer gives each allocating goroutine a debt in proportion to what it allocates; when background workers fall behind, a goroutine pays its debt by scanning objects before `mallocgc` returns.
</Depth>

## [morph] From "GC cleans garbage" to "GC marks what is live"

Drag the slider. The picture of a collector that stops the world and frees garbage becomes the real cycle: roots shade objects grey, workers scan them black, and the write barrier watches every pointer store your handlers make.

The code changes the sessions to records with no pointers: fixed-size bytes and integers in one big array, indexed by a map whose keys and values hold no pointers either.

<Depth level={2}>
The GC knows from each type whether it contains pointers, and puts pointer-free objects in spans it marks without reading. A 12-million-entry array of such records is a handful of objects to the collector. bigcache uses the same trick for its index.
</Depth>

<Depth level={3}>
<Lang only="go">The map counts too: when neither the key nor the value type has pointers, its tables are allocated as pointer-free memory. A `map[string]*Session` has pointers in both.</Lang>
<Lang only="python">A packed `bytearray` is one object to CPython. The index dict holds only strings and ints, and CPython stops tracking a dict whose keys and values cannot form cycles.</Lang>
<Lang only="typescript">An `ArrayBuffer`'s contents are raw bytes. V8 marks the buffer object and never looks inside the data.</Lang>
<Lang only="rust">Nothing to scan either way; the compact record roughly halves memory by removing the `String` and `Vec` headers and their separate heap blocks.</Lang>
</Depth>

## [walk] Follow one GC cycle

One cycle, from the first stop-the-world to sweep, with handlers running throughout. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">The phases are named in `runtime/mgc.go`: sweep termination (stop the world, finish any sweeping, turn the barrier on), concurrent mark, mark termination (stop the world, turn the barrier off), and concurrent sweep. Objects allocated during marking are allocated black. Since Go 1.26 the default Green Tea collector scans small objects a whole page at a time for better memory locality; the colours and the barrier work the same way.</Lang>
<Lang only="python">CPython's cycle collector works per generation. For each tracked container it subtracts internal references from the reference counts; objects left with a count above zero are reachable from outside, and anything not reachable from them is a cycle of garbage.</Lang>
<Lang only="typescript">V8's scavenger copies live young objects to a new space and promotes those that survive twice. Old space is marked concurrently by helper threads, with a write barrier much like Go's, and then swept or compacted.</Lang>
<Lang only="rust">Dropping a value runs its `Drop` and frees its memory in place. A `HashMap::insert` that replaces a value returns the old one, which is dropped at the end of the statement.</Lang>
</Depth>

## [again] Thirty-day sessions, the second time

The same 12 million sessions as pointer-free records. Each cycle marks the array and the map's tables as live and never reads inside them. Mark time is back to what it was at 400,000 sessions, mark assists stop landing on requests, and p99 returns to normal.

<Depth level={2}>
Check it with `/gc/scan/heap:bytes` from `runtime/metrics`, the heap bytes the GC actually scanned in the last cycle. It should drop by roughly the size of the session data.
</Depth>

<Depth level={3}>
The trade is code: you manage slots by hand, reuse freed ones, and copy strings in and out. Do it for the few structures that dominate the live heap, not everywhere.
</Depth>

## [play] Mark it while it moves

You are the collector. Press grey objects to scan them while a login handler moves a pointer. Turn the barrier off to watch a live object get freed, then on to see it saved.

## [lens] How each language reclaims memory

Go traces the live heap each cycle. Python counts references and traces only for cycles. V8 traces too, but by generation. Rust frees at compile-time-known points and never traces.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={2}>
The common lesson: in every traced runtime, large long-lived object graphs cost work on every major collection. Packing hot, long-lived data into flat, pointer-free storage helps in all three.
</Depth>
