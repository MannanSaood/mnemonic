  deep:
    question: The signal arrives while the goroutine is in the middle of a write barrier sequence. What does the runtime do?

      - text: It leaves the goroutine running and tries again later, because that instruction is not an async safe point.
        correct: true

## [concept] Preemption

**<Term id="preemption">Preemption</Term> is the runtime stopping a goroutine that has run long enough, so others can have its P. Since Go 1.14 it can stop any goroutine, anywhere safe, by sending a signal to its thread.**

Before 1.14, a goroutine could only be stopped when it called a function. A loop with no calls inside could not be stopped at all.

<Depth level={2}>
Two things need preemption. The scheduler needs it to share a P fairly: <Term id="sysmon">sysmon</Term> asks any goroutine that has run for 10 ms to yield. The garbage collector needs it to <Term id="stop-the-world">stop the world</Term>: twice per cycle, every goroutine must stop at a <Term id="safe-point">safe point</Term> before the GC can move on. One goroutine that will not stop holds up all the others.
</Depth>

<Depth level={3}>
The runtime has two ways to stop a goroutine. The cooperative one reuses the stack check at the start of almost every function: the runtime sets the goroutine's stack guard to a value that makes the check fail, and the stack-growth code sees the request and yields. The asynchronous one, added in 1.14, sends SIGURG to the thread and lets the signal handler switch the goroutine out, as long as it stopped at an instruction where the compiler recorded which registers hold pointers.
</Depth>

## [problem] A fingerprint loop in a backup service

A backup service deduplicates uploaded blocks. For each 4 MiB block it computes an FNV-1a fingerprint in a hand-written loop, and looks it up in a set. The hash is written inline for speed, so the loop has no function calls. The same process serves `/healthz` and the upload API.

The model behind it: goroutines take turns, so a long loop just takes longer. The service was built with Go 1.13, and a block takes about 4 ms.

<Depth level={2}>
At 4 ms per block, the loop finishes long before anything notices. The service runs with GOMAXPROCS 2, so even while one P is hashing, the other serves requests.
</Depth>

<Depth level={3}>
On Go 1.13, the only way to stop this goroutine is to wait for it to call a function. The loop calls nothing, so it stops being stoppable for as long as it runs.
</Depth>

## [pain] Then a change request arrives

**Change request:** deduplicate whole 1 GiB VM images, not only 4 MiB blocks.

The marked line is the only change. Now one fingerprint runs for about a second. During that second the garbage collector starts a cycle and asks every goroutine to stop. The P serving requests stops at once. The P running the loop cannot stop until the loop ends. For the rest of that second, nothing runs: no requests, no health checks. Liveness probes start to time out, and after a few failures Kubernetes restarts the pod.

<Depth level={2}>
The spare P did not help, which is what makes the symptom so confusing. CPU usage shows one busy core, yet the whole process is frozen. An execution trace shows the other P idle, waiting for the GC to start.
</Depth>

<Depth level={3}>
The same stall happens without a GC. Anything else that stops the world, such as `runtime.ReadMemStats` or `runtime.GOMAXPROCS(n)`, also waits for every goroutine to stop. On one P, it is worse: other goroutines simply never run until the loop ends.
</Depth>

## [morph] From "goroutines take turns" to "goroutines stop at safe points"

Drag the slider. The picture of a runtime that time-slices every goroutine becomes the real path: sysmon notices the long run, sends SIGURG, and the signal handler stops the loop at a safe point. The GC uses the same path to stop the world.

The code changes the toolchain to a current Go, where the loop is preemptible, and adds a limit so fingerprints never take the last P.

<Depth level={2}>
Upgrading fixes the freeze. The limit fixes what is left: a preempted loop still holds its P for whole 10 ms slices, and a request that lands behind it waits for one. Keeping one P free of CPU-heavy work keeps request latency flat.
</Depth>

<Depth level={3}>
<Lang only="go">Before 1.14, the usual fix was a `runtime.Gosched()` every few thousand iterations, or a call to a function the compiler would not inline. Both work, and both are now unnecessary on platforms with asynchronous preemption.</Lang>
<Lang only="python">`hashlib` releases the GIL while it hashes inputs of 2 KiB or more, so the worker thread hashes in parallel with the event loop thread. A pure-Python loop would hold the GIL, and the loop thread would get it back only every 5 ms.</Lang>
<Lang only="typescript">Each `for await` step waits for the next chunk from the socket. Hashing is faster than the network, so the loop spends that time serving other requests.</Lang>
<Lang only="rust">`spawn_blocking` moves the call to tokio's blocking pool, where the kernel time-slices it like any thread. The async workers never see it.</Lang>
</Depth>

## [walk] Follow one interrupted loop

One 10 ms slice of the fingerprint loop, from sysmon noticing it to the scheduler running the next goroutine. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">The 10 ms is `forcePreemptNS` in `runtime/proc.go`. sysmon's `retake` calls `preemptone`, which sets `gp.preempt`, sets `gp.stackguard0` to `stackPreempt`, and, unless `asyncpreemptoff=1`, calls `preemptM` to send the signal. The handler, `doSigPreempt`, checks `wantAsyncPreempt` and `isAsyncSafePoint`, then injects a call to `asyncPreempt`. The GC's `suspendG` uses the same requests when it needs to scan a running goroutine's stack.</Lang>
<Lang only="python">The GIL switch is a request too: a waiting thread sets a flag after the switch interval, and the running thread checks it at regular points in the bytecode loop. A long C call that keeps the GIL is never interrupted.</Lang>
<Lang only="typescript">V8 checks for interrupts at function entries and loop back edges, for its own work such as GC and termination. It never uses them to run another JavaScript callback.</Lang>
<Lang only="rust">The kernel's scheduler interrupts a thread with a timer, saves all its registers and runs another thread. No safe-point rules apply, because there is no garbage collector that needs to read the stack.</Lang>
</Depth>

## [again] The 1 GiB image, the second time

The same image on Go 1.22. sysmon interrupts the loop every 10 ms. When the GC starts, it signals the loop's thread and the world stops in well under a millisecond. With one P kept free of fingerprints, `/healthz` never waits behind one at all.

<Depth level={2}>
The loop now finishes a little later, because it shares its P with whatever else is queued. That is the trade you want: a fingerprint that takes 5% longer instead of a pod that restarts.
</Depth>

<Depth level={3}>
Asynchronous preemption cannot stop a goroutine inside a sequence the compiler marked unsafe, such as a write barrier or `unsafe.Pointer` arithmetic. The handler returns and the request is retried, so a stop is delayed by a few instructions, never by a whole loop.
</Depth>

## [lens] How each language stops a long computation

Go preempts goroutines for you. Python switches threads through the GIL but never coroutines. Node runs each callback to the end. Rust leaves threads to the kernel and async tasks to you.

### What stops a goroutine

| Stopping point | Since | When it happens |
|---|---|---|
| Blocking (channel, lock, sleep, I/O) | always | The goroutine parks; nothing has to interrupt it. |
| Function call with a poisoned stack guard | always | sysmon or the GC asked; the next call notices. |
| Signal at an async safe point | Go 1.14 | sysmon or the GC sent SIGURG; works inside loops with no calls. |
| `runtime.Gosched()` | always | The goroutine yields on purpose. Rarely needed now. |
