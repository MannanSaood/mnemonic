checks:
  overview:
    question: A handler cancels its context while a goroutine it started is in a CPU loop that never looks at ctx. What happens to that goroutine?
    options:
      - text: It keeps running until its loop ends. Cancelling only closes the context's Done channel.
        correct: true
        why: Right. Cancellation is cooperative. Nothing in Go can stop a goroutine from outside; it stops when its own code checks ctx and returns.
      - text: The runtime stops it at the next function call.
        why: The runtime never stops goroutines on a context's behalf. A context is an ordinary value with a channel inside.
      - text: It panics with context.Canceled.
        why: context.Canceled is an error value that ctx.Err() returns. Nothing panics, and nothing happens to code that never asks.
  engineer:
    question: In an errgroup, pricing fails at 60 ms, but the error response goes out at 250 ms. Why?
    options:
      - text: g.Wait() waits for every goroutine in the group to return, and fraud.Score ignores gctx.
        correct: true
        why: Right. errgroup cancels gctx at the first error, but Wait still waits for every function passed to Go. One goroutine that ignores ctx holds up the response.
      - text: errgroup only cancels the context after Wait returns.
        why: It cancels the derived context the first time a function returns a non-nil error, and again when Wait returns. The cancel happened at 60 ms.
      - text: The 300 ms deadline has to pass before an error can be returned.
        why: The deadline is an upper bound. Any earlier cancel closes the same Done channel.
  deep:
    question: What does a cancelCtx do if cancel runs before anyone has called Done?
    options:
      - text: It stores a shared channel that is already closed, because Done creates its channel lazily and nobody has asked for one yet.
        correct: true
        why: Right. Many contexts are never waited on, so context.go only makes the channel on the first Done call. If cancel comes first, later Done calls get the shared closed channel.
      - text: It creates a new channel and closes it at once.
        why: That would allocate a channel per cancelled context. The package keeps one closed channel and reuses it.
      - text: Nothing; Done will block forever because its channel was never created.
        why: That would break every late caller of Done. The cancel records the shared closed channel so they return at once.

  useWhen:
    - Any request-scoped work that does I/O or runs longer than a few milliseconds.
    - Fan-out where one failure makes the other results useless.
    - Deadlines that must hold across several calls and services.
  avoidWhen:
    - Storing a context in a struct field. Pass it as the first argument of each call.
    - Passing optional parameters through WithValue. Use it only for request-scoped data such as trace IDs.

    - Every function on the path must take ctx and honour it, or the chain breaks at that function.

    - Cancellation stops work; it does not undo it. A reservation made before the cancel still needs releasing.

## [concept] Context and cancellation

**A context carries a cancel signal, a deadline and request values down a tree of calls.** Cancelling one closes a channel. Only the code that checks that channel stops.

Every context you derive is a child of the one you derived it from. That makes a <Term id="context-tree">context tree</Term>, and cancelling any node cancels everything below it.

<Depth level={2}>
The signal is the <Term id="done-channel">Done channel</Term>. `ctx.Done()` returns it, and it is closed when the context is cancelled, its deadline passes, or its parent is cancelled. `ctx.Err()` then says why: `context.Canceled` or `context.DeadlineExceeded`. This is <Term id="cooperative-cancellation">cooperative cancellation</Term>: nothing stops a goroutine from outside. Work stops because its own code looks at `ctx` and returns.
</Depth>

<Depth level={3}>
In `context/context.go`, a `cancelCtx` holds a mutex, a lazily created `done` channel, a set of children, and the error. `cancel` stores the error, closes `done` (or, if nobody ever asked for it, stores one shared closed channel), then calls `cancel` on each child and removes itself from its parent. A `timerCtx` adds a deadline and uses `time.AfterFunc` to call the same `cancel` when it passes.
</Depth>

## [problem] Three checks, one quote

A checkout quote needs three answers: inventory reserves the items, pricing quotes the total, and a fraud model scores the cart. They are independent, so the handler runs them at the same time and waits for all three. It also warms the recommendations cache, and writes an audit record at the end.

When every backend answers, it is fast: about 250 ms, set by the fraud model.

<Depth level={2}>
The mental model is that a request ends when the handler returns, and everything it started ends with it. In Go that is never true. A goroutine ends when its own function returns, and nothing here ever tells the others to stop.
</Depth>

<Depth level={3}>
`context.Background()` in the recs call is a deliberate choice: someone did not want a slow client to cut cache warming short. It works, but it also takes recs out of the request's tree, so nothing can ever stop it.
</Depth>

## [pain] Pricing goes down

**What happened:** during a pricing outage, checkout errors took 250 ms instead of 60, and CPU on the checkout pods went to scoring carts nobody would buy.

Pricing fails at 60 ms. Nothing stops the other two: `wg.Wait()` waits for inventory and for the full 250 ms of fraud scoring, then returns the error. The recs goroutine runs on for its full 500 ms after the response has gone.

<Depth level={2}>
Under load it gets worse. Every failed request still pays for a full fraud score, so during the outage the pods spend most of their CPU on answers that will be thrown away, and healthy requests queue behind them. Retries from clients double it.
</Depth>

<Depth level={3}>
None of this shows up as an error. The goroutines all finish, so there is no leak, and the CPU profile shows `fraud.Score` as the hottest function, as it always is. You only see it by comparing when the error happened with when it was sent.
</Depth>

## [morph] Put the request in a tree

Drag the slider. The flat group of goroutines becomes a tree: the request's context at the root, the handler's deadline below it, the errgroup's context below that, and each call hanging off the context it should stop with.

The code changes in four places. `ctx` gets a deadline and a `defer cancel()`. The three calls move into an errgroup and take `gctx`. The fraud loop checks `ctx.Err()`. And recs takes `ctx`, while the audit write takes `context.WithoutCancel(ctx)` on purpose.

<Depth level={2}>
`defer cancel()` matters even when nothing goes wrong. Until a derived context is cancelled, its parent keeps a reference to it, and a `WithTimeout` keeps its timer. `go vet` warns when a cancel function is not called on every path.
</Depth>

<Depth level={3}>
When the parent is a context from this package, `propagateCancel` simply adds the child to the parent's children set. For a parent of some other type, it registers through the parent's `AfterFunc` if it has one, and otherwise starts a goroutine that waits on the parent's Done channel. That fallback is one reason to avoid custom Context implementations.
</Depth>

## [walk] Follow the failure

The pricing failure, traced through the fixed handler, from the root context to the audit write. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Closing a channel wakes every goroutine parked on it at once, so cancelling a context with a thousand waiting goroutines costs one close, not a thousand sends. `http.Client` watches the request's context and closes the connection when Done closes; `database/sql` asks the driver to cancel the query.</Lang>
<Lang only="python">`task.cancel()` only requests cancellation. The `CancelledError` is thrown at the task's next `await`, and a task can catch it and refuse. `TaskGroup` re-raises the original error as part of an `ExceptionGroup` once all its tasks have finished.</Lang>
<Lang only="typescript">`AbortSignal.any` returns a signal that fires when any of its inputs fires. Listeners run synchronously in `abort()`, so `fetch` closes its connection before `abort()` returns.</Lang>
<Lang only="rust">Dropping a future runs the destructors of everything it owns, which closes connections and releases locks at once. That only reaches futures. A thread from `spawn_blocking` keeps running until its closure returns.</Lang>
</Depth>

## [again] Pricing goes down again

The same outage. The error goes out at 65 ms: the failure at 60 ms, plus up to one fraud-loop check. Inventory's request is aborted, fraud stops at its next check, recs stops when the handler returns, and only the audit write runs on, as it should.

<Depth level={2}>
Check it in tests. Give a fake backend a context-aware method that blocks until `ctx.Done()`, cancel the context, and assert the handler returns within a few milliseconds. A goroutine that ignores ctx fails the test by timing out.
</Depth>

<Depth level={3}>
`context.WithCancelCause` (Go 1.20) records why a context was cancelled, and `context.Cause(ctx)` returns it, so logs can say "pricing failed" instead of "context canceled". `context.AfterFunc` (Go 1.21) runs a function when a context is done, without a goroutine waiting on it.
</Depth>

## [lens] How each language meets it

Every language here cancels cooperatively. They differ in what carries the signal and in which work cannot hear it.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={2}>
Go passes `ctx` by hand and cancels nothing automatically. Python throws `CancelledError` into a task at its next `await`. TypeScript passes an `AbortSignal` to the APIs that accept one. Rust cancels a future by dropping it. In all four, threads and CPU loops only stop if they check.
</Depth>

### Values and causes

`context.WithValue` carries request-scoped data, such as a trace ID or the authenticated user, through APIs that do not know about it. Use a private key type so packages cannot collide, and never use it for optional parameters. `WithoutCancel` keeps these values while dropping cancellation, which is why the audit write uses it rather than `context.Background()`: the audit record still gets the trace ID.
