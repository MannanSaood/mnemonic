reference:
  roles:
    - role: CPU request
      example: "cpu: 1"
      job: Reserved by the scheduler; becomes cpu.weight, which decides shares only when CPUs are contended.
    - role: CPU limit
      example: "cpu: 2"
      job: Becomes cpu.max, a quota per 100 ms period. Above it the container's threads wait, even on an idle node.
    - role: Memory request
      example: "memory: 1Gi"
      job: Reserved by the scheduler; decides eviction order and the Burstable oom_score_adj. Guarantees nothing in the kernel by default.
    - role: Memory limit
      example: "memory: 1Gi"
      job: Becomes memory.max. Above it the kernel reclaims, then kills the container, which shows as OOMKilled with exit code 137.
    - role: QoS class
      example: Burstable
      job: A summary of the above. Guaranteed when every request equals its limit, BestEffort when nothing is set. It sets oom_score_adj.
  useWhen:
    - Set requests on every container, from measured usage at a normal peak, so that scheduling and eviction reflect reality.
    - Set a memory limit equal to the memory request for services that must not be evicted or surprise the node; memory is not compressible.
    - Use a CPU limit for batch work you want to cap, or where your platform requires it.
  avoidWhen:
    - Avoid tight CPU limits on latency-sensitive, multi-threaded services. They throttle bursts on idle nodes; many teams set only a CPU request for such services.
    - Avoid sizing thread pools, worker counts and caches from the node's CPU and memory. The container sees the node's numbers unless the runtime reads its cgroup.
  tradeoffs:
    - Requests above real usage waste capacity, because the scheduler reserves them all the time. Requests below it overcommit the node, and the risk arrives together with the peak.
    - Guaranteed pods are the safest from eviction and the most expensive in reserved capacity.
    - A CPU limit gives predictable performance and caps noisy neighbours, at the cost of throttling when a pod could have used idle CPU.
  lookalikes:
    - name: ResourceQuota
      how: Caps the total requests and limits in a namespace. It limits what teams can ask for, not what containers use.
    - name: LimitRange
      how: Sets default requests and limits, and minimums and maximums, for containers in a namespace that do not set their own.
    - name: VM sizing
      how: A VM's CPUs and memory are its own. A container's are a cgroup's share of a node it shares with other pods, which the runtime cannot see unless it reads the cgroup.

## [concept] Requests, limits and QoS classes

**A <Term id="resource-request">request</Term> is what the scheduler reserves for a container. A <Term id="resource-limit">limit</Term> is what the kernel enforces. Over its CPU limit a container is slowed; over its memory limit it is killed. When the whole node runs short of memory, the kubelet evicts pods that use more than they requested first.**

The scheduler fits pods by adding up requests against each node's <Term id="node-allocatable">allocatable</Term> resources. It never looks at usage. Limits are written into the container's cgroup, and the kernel acts on them whatever the scheduler thought.

<Depth level={2}>
The two resources behave differently because CPU can be taken back and memory cannot. A CPU limit becomes a <Term id="cfs-quota">CFS quota</Term>: so much CPU time per 100 ms period, after which every thread in the container waits. A memory limit becomes the cgroup's memory.max, and a container above it is OOM-killed. The pod's <Term id="qos-class">QoS class</Term> is derived from these numbers: Guaranteed, Burstable or BestEffort.
</Depth>

<Depth level={3}>
On cgroup v2 the CPU request becomes cpu.weight, which only matters when CPUs are contended: then each busy container gets time in proportion to its weight. The CPU limit becomes cpu.max, a quota and a period. The memory request reserves nothing in the kernel by default; it shapes scheduling, eviction order and oom_score_adj. The memory limit becomes memory.max of the container's <Term id="memory-cgroup">memory cgroup</Term>.
</Depth>

## [problem] A service sized for its VM

The pricing API ran on two 32-core VMs for years. Its startup code sizes everything from the machine: one worker per core, and a quote cache of five million entries, because there was memory to spare. It is fast and stable.

<Depth level={2}>
Nothing in the code is wrong for a VM. The assumption is that the CPUs and memory the process can see are its own. Inside a container, the process still sees the whole node.
</Depth>

<Depth level={3}>
`/proc/cpuinfo`, `nproc` without a quota-aware runtime, and the CPU counts most standard libraries report come from the node or from CPU affinity, not from cpu.max. A container limited to 2 CPUs on a 32-core node sees 32.
</Depth>

## [pain] Then a change request arrives

**Change request:** move the pricing API from its two VMs onto the shared cluster, as ten pods with 2 CPUs and 1 GiB each.

The pods start, and the dashboards look calm: CPU at about 35% of the limit. But p99 latency is 410 ms where it used to be 90 ms, and in the evening, at the traffic peak, pods restart with exit code 137 and the reason OOMKilled. The nodes have plenty of free memory.

<Depth level={2}>
Thirty-two threads share a quota of 200 ms per 100 ms period. A burst on all of them spends it in about 6 ms, and then every thread waits more than 90 ms for the next period. The average stays low because most periods are quiet. Memory is simpler: a cache sized for a VM grows past 1 GiB, and the cgroup's memory.max kills the container, whatever the node has free.
</Depth>

<Depth level={3}>
The evidence is in the cgroup. cpu.stat shows nr_throttled rising with each burst, and throttled_usec adds up the waiting. memory.events shows oom_kill, and the pod's last state shows OOMKilled with exit code 137, which is 128 plus SIGKILL's 9.
</Depth>

<Depth level={2}>
The pod spec becomes requests of 1 CPU and 1 GiB, and limits of 2 CPUs and 1 GiB. The CPU request is what the service needs at a normal peak; the higher CPU limit leaves room for bursts. Memory request and limit are equal, because memory cannot be taken back: a pod that requests what it can use is evicted last, and the node is never surprised.
</Depth>

Some teams drop CPU limits altogether for latency-sensitive services and rely on requests, which still guarantee each container its share under contention. </Depth>

<Lang only="go">Go 1.25 reads cpu.max at startup and again periodically, so GOMAXPROCS follows the limit if it changes. GOMEMLIMIT is a soft limit for the garbage collector only; the cgroup's memory.max stays the hard one.</Lang>
<Lang only="python">The downward API's `limits.cpu` with the default divisor of 1 is rounded up to a whole number, so a 1.5 CPU limit gives `CPU_LIMIT=2`. Each gunicorn worker is a separate interpreter with its own memory, so memory budgets divide by the worker count.</Lang>
<Lang only="typescript">With `node:cluster`, each worker is a full process with its own V8 heap. V8's heap limit is per process, so the start script divides the memory limit by the number of workers.</Lang>
<Lang only="rust">`available_parallelism` returns the smaller of the CPU affinity count and what the cgroup quota allows. A tokio runtime sized from it keeps its worker threads within what the kernel will run.</Lang>
</Depth>

## [again] The same peak, with honest numbers

The same evening peak. Two threads share the 200 ms quota, and a burst is spread over the period instead of crammed into its first few milliseconds: nr_throttled rises in a handful of periods, and p99 is back at 95 ms. The cache is sized from the memory budget, the garbage collector works harder near GOMEMLIMIT, and nothing is OOMKilled.

<Depth level={2}>
Watch nr_throttled divided by nr_periods next to latency, not CPU averages. A few percent of throttled periods during a peak is normal; a steady double-digit share means the limit is too low for how the service bursts.
</Depth>

<Depth level={3}>
If the node runs short of memory anyway, the order is fixed by the requests. The kubelet checks memory.available periodically and evicts pods above their requests first. If memory runs out faster than it checks, the kernel's <Term id="oom-killer">OOM killer</Term> acts first, choosing by usage plus <Term id="oom-score-adj">oom_score_adj</Term>: -997 for Guaranteed, 1000 for BestEffort, and in between for Burstable, lower for larger memory requests. That is <Term id="node-pressure-eviction">node-pressure eviction</Term> and the OOM killer working as a pair.
</Depth>

## [lens] How each language does it

Go now reads its CPU limit by itself, and has GOMEMLIMIT for memory. Rust's `available_parallelism` reads the CPU quota, but memory budgets are yours. Python and Node.js count the node's CPUs, so worker counts and per-worker memory must come from the pod spec, usually through the downward API.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

Whatever the runtime, check three numbers inside a running container: how many threads or workers it started, what heap or cache budget it chose, and what `/sys/fs/cgroup/cpu.max` and `memory.max` say. When they disagree, the kernel wins.
</Depth>
