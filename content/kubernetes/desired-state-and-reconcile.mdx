        func (r *PoolReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
            var pool billingv1.WorkerPool
            if err := r.Get(ctx, req.NamespacedName, &pool); err != nil {
                return ctrl.Result{}, client.IgnoreNotFound(err)
            }
            var pods corev1.PodList
            if err := r.List(ctx, &pods, client.InNamespace(req.Namespace),
                client.MatchingLabels{"pool": pool.Name}); err != nil {
                return ctrl.Result{}, err
            }
            active := activePods(pods.Items) // skips pods already being deleted
            diff := int(pool.Spec.Replicas) - len(active)
            for i := 0; i < diff; i++ {
                if err := r.Create(ctx, r.workerPod(&pool)); err != nil { // sets the owner reference
                    return ctrl.Result{}, err // requeued with backoff
                }
            }
            for _, p := range newestFirst(active)[:max(0, -diff)] {
                if err := r.Delete(ctx, &p); client.IgnoreNotFound(err) != nil {
                    return ctrl.Result{}, err
                }
            }
            pool.Status.Replicas = int32(len(active))
            return ctrl.Result{}, r.Status().Update(ctx, &pool) // a stale resourceVersion fails and is retried
        }

        # reconciler.py: compare desired with observed, fix the difference
        def reconcile(pool: dict) -> None:
            name, ns = pool["metadata"]["name"], pool["metadata"]["namespace"]
            want = pool["spec"]["replicas"]
            pods = v1.list_namespaced_pod(ns, label_selector=f"pool={name}").items
            active = [p for p in pods if p.metadata.deletion_timestamp is None]
            diff = want - len(active)
            for _ in range(diff):
                v1.create_namespaced_pod(ns, worker_pod(pool))  # sets the owner reference
            for p in newest_first(active)[: max(0, -diff)]:
                v1.delete_namespaced_pod(p.metadata.name, ns)
            crd.patch_namespaced_custom_object_status(
                GROUP, "v1", ns, "workerpools", name, {"status": {"replicas": len(active)}})

        async fn reconcile(pool: Arc<WorkerPool>, ctx: Arc<Ctx>) -> Result<Action, Error> {
            let pods: Api<Pod> = Api::namespaced(ctx.client.clone(), &pool.namespace().unwrap());
            let lp = ListParams::default().labels(&format!("pool={}", pool.name_any()));
            let active: Vec<Pod> = pods.list(&lp).await?.items.into_iter()

    options:
      - text: The controller sees 2 pods where 3 are wanted and creates one.
        correct: true
        why: Right. The spec still says 3. The controller compares that with the 2 it observes and closes the gap.
      - text: Nothing. You deleted it, so the cluster now wants 2.
        why: Deleting a pod changes what exists, not what is wanted. To run 2, you change spec.replicas.
      - text: The pod restarts on the same node.
        why: A deleted pod is gone for good. A new pod with a new name is created and scheduled, perhaps on another node.
  engineer:
    question: Your controller was down for ten minutes during a deploy, and missed every event in that time. What happens when it starts again?
    options:
      - text: It lists the current state, compares it with each spec, and fixes any gap. Nothing is lost.
        correct: true
        why: Right. A level-triggered controller does not need the events it missed, because their results are visible in the current state.
      - text: The API server replays the missed events to it, in order.
        why: A watch can resume from a recent resourceVersion, but old history is compacted away and a resume may fail with 410 Gone. Controllers do not depend on replay; they re-list.
      - text: The changes made in those ten minutes are lost until someone edits the objects again.
        why: That is what happens to an edge-triggered script. A reconcile loop needs only the present state.
  deep:
    question: The ReplicaSet controller creates 2 pods, and before its informer cache shows them, another event wakes it for the same ReplicaSet. Why does it not create 2 more?
    options:
      - text: It records how many creates and deletes it expects to observe, and skips a pass until the cache has caught up with them.
        correct: true
        why: Right. These expectations protect against acting on a stale cache. Without them, a fast loop over a lagging cache overshoots.
      - text: The API server rejects the second set of creates because of resourceVersion.
        why: resourceVersion protects updates to one object. Creating new pods with generated names does not conflict with anything.
      - text: Events for one object are always delivered after the cache is fully up to date.
        why: The cache is updated by the same watch, but a wake-up can come from the owner or another pod before the new pods arrive. The controller has to allow for that.

# ---------------------------------------------------------------- reference page
reference:
  roles:
    - role: Spec
      example: "spec.replicas: 8"
      job: The desired state. You (or another controller) write it; the controller only reads it.
    - role: Status
      example: "status.replicas: 5"
      job: The observed state, written by the controller. Useful for people and other controllers; never trusted as the truth by the controller itself.
    - role: Informer
      example: the pod cache
      job: Lists once, then watches. Keeps a local copy of objects, re-lists when the watch breaks, and turns changes into wake-ups.
    - role: Work queue
      example: "billing/invoices"
      job: Holds names of objects to reconcile. De-duplicates them, and retries failures with rate-limited backoff.
    - role: Reconcile
      example: Reconcile(ctx, req)
      job: Reads desired and observed state, and acts on the difference. Idempotent, so it is safe to run at any time and any number of times.
  useWhen:
    - Something must stay true over time, such as a number of replicas, a DNS record, or a certificate that must not expire.
    - Failures and restarts are normal, and you would rather repair the state on the next pass than keep a perfect history of events.
    - You extend Kubernetes with your own resource: an operator is a reconcile loop for that resource.
  avoidWhen:
    - A Deployment, StatefulSet, Job or CronJob already does it. Write a controller only for what the built-in ones do not.
    - The work is a one-off action with no state to keep true, such as sending an email when something happens. That is an event handler, and it needs idempotency keys rather than reconciliation.
  tradeoffs:
    - A pass lists and compares everything it owns, so it costs more than handling one event. Informer caches make that read local and cheap.
    - The loop converges eventually, not at once. A node failure takes about 50 s to be noticed and 5 more minutes before its pods are evicted.
    - Two controllers that want different things for the same field fight forever, each undoing the other. Nothing reports it as an error.
    - Reconcile must be idempotent and must not assume the order of events, since wake-ups are merged, repeated and reordered.
  lookalikes:
    - name: Event-driven handler
      how: Acts on each event. Fine when events are complete and ordered, which a network and restarting processes do not guarantee.
    - name: Cron job that fixes drift
      how: A reconcile loop with only a timer for a wake-up. Correct, but slow to react; controllers add watches for speed and keep periodic passes as a safety net.
    - name: Terraform apply
      how: The same compare-and-act idea, run once by a person instead of continuously by a controller.

## [concept] Desired state and the reconcile loop

**In Kubernetes you write down the <Term id="desired-state">desired state</Term>, and controllers keep comparing it with what they observe and act on the difference. Each pass of the <Term id="reconcile-loop">reconcile loop</Term> looks at the whole present state, so it does not matter what happened in between.**

You do not say "start a pod on node 2". You say "three replicas". If a pod dies, the controller counts two and starts a third. If someone asks for eight, it counts three and starts five. The same code handles both.

<Depth level={2}>
Controllers are <Term id="level-triggered">level-triggered</Term>. They act on the present gap, not on remembered events, so a missed event is repaired on the next pass. Events still matter: they are how a controller knows to look again soon. But an event is a wake-up, never an instruction.
</Depth>

<Depth level={3}>
The split between spec and status is the contract. You write the spec; the controller writes the status from what it observed. Every built-in workload controller (ReplicaSet, Deployment, Job, StatefulSet) runs this loop inside kube-controller-manager, each watching its own kind of object, and they cooperate only through objects in the API server.
</Depth>

## [problem] A script that keeps the workers running

The billing team runs invoice workers on Kubernetes. A small script starts three worker pods, then watches pods and starts a new one each time a worker is deleted. In testing it works: delete a worker and a new one appears within seconds.

<Depth level={2}>
The script is <Term id="edge-triggered">edge-triggered</Term>. It is correct only if it sees every event exactly once, and it remembers its own idea of how many workers exist instead of counting them.
</Depth>

<Depth level={3}>
A watch is a long-lived HTTP stream. It ends when the API server restarts, when a load balancer times out an idle connection, or when the script's own pod is rescheduled. Anything that happens before it reconnects is invisible to it, unless it lists again.
</Depth>

## [pain] Then a change request arrives

**Change request:** at month end, run eight invoice workers instead of three, and keep them running through node failures.

The team adds a watch on the config and creates the difference when the number goes up. On the night of month end the watch connection drops during an API server upgrade, and the config change arrives while the script is reconnecting, so the five extra workers are never created. Later a node fails, and its worker is evicted without a DELETED event. In the morning two workers are running, the queue is six hours behind, and nothing in the script's logs looks wrong.

<Depth level={2}>
Every fix adds another event to handle: reconnects, config changes, evictions, pods stuck terminating. Each one needs its own code path, and the script still cannot tell what it missed. The state it remembers drifts away from the state that exists.
</Depth>

<Depth level={3}>
Resuming a watch from the last resourceVersion it saw helps only for short gaps. The API server keeps a limited window of history; ask for something older and it answers 410 Gone, and the only way back is a full list. That list is the comparison the script never made.
</Depth>

## [morph] Compare, then act

Drag the slider. The script's event handlers become one function that reads the spec, counts the pods, and closes the gap. The watch becomes an <Term id="informer">informer</Term> whose events only say "look again".

Hover a box in the diagram to see its code.

<Depth level={2}>
The month-end change is now one field: replicas 8. It does not matter whether the controller was running when it changed, or how many events were lost. On its next pass it sees 8 wanted and however many exist, and acts. Errors return to the work queue, which retries with <Term id="exponential-backoff">exponential backoff</Term>.
</Depth>

<Depth level={3}>
The pods carry an <Term id="owner-reference">owner reference</Term> to the pool, which lets the controller map a pod event to its owner and lets the garbage collector delete the pods with the pool. Status updates carry the object's <Term id="resource-version">resourceVersion</Term>: if someone else changed the object since it was read, the update fails with a conflict and the pass runs again on fresh data.
</Depth>

## [walk] Follow one pass

The pool wants 8 pods and has 5. Follow one pass from the wake-up to the status update. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">controller-runtime de-duplicates requests on the work queue, so ten pod events in a burst become one Reconcile. It never runs two passes for the same object at once.</Lang>
<Lang only="python">The watch stream ends after `timeout_seconds`, and the loop re-lists. That turns a long-lived watch into a periodic full pass for free.</Lang>
<Lang only="typescript">An informer's error handler is not optional: without a restart, a broken watch leaves the cache frozen and the controller silent.</Lang>
<Lang only="rust">`Controller` merges wake-ups for the same object and runs `reconcile` again when the returned `Action` says so, so a periodic pass needs no extra code.</Lang>
</Depth>

## [again] The same night, with a reconcile loop

The node fails and the watch drops in the same upgrade. When the controller reconnects it re-lists, sees 8 wanted, counts what is running, and creates the difference. When the node's pods are finally evicted, it counts fewer and creates more. By morning eight workers are running, and the only trace is a few lines of log.

<Depth level={2}>
Running the pass twice does nothing the second time, because it is an <Term id="idempotent-operation">idempotent operation</Term>: it states a target, not a step. That is why it can be triggered by any event, by a timer, or by a restart, and why duplicated or reordered events are harmless.
</Depth>

<Depth level={3}>
The cache can lag the API server. Right after creating pods, a second wake-up may see the old count and create them again. The ReplicaSet controller guards against this with expectations: it records the creates and deletes it made and skips passes until the cache has observed them. controller-runtime leaves this to you; generated names and checking for pods already pending are the usual answers.
</Depth>

## [play] Lose some events

Two copies of the same cluster get exactly the same trouble. The top one is kept alive by the event script, the bottom one by a reconcile loop. Delete pods, change replicas, kill nodes, stop the controllers and drop the watch, and see which one is right afterwards.

## [lens] How each language does it

Go is where Kubernetes controllers live: client-go and controller-runtime give you informers, work queues and leader election. Rust has kube-rs with a complete `Controller`. Python has kopf and the official client. TypeScript has informers in `@kubernetes/client-node` and leaves the queue to you.

<Depth level={2}>
Whatever the language, the same rules hold. Read state at the start of every pass. Act on the difference. Make every write safe to repeat. Return errors so the pass runs again, rather than logging them and moving on.
</Depth>

### Why a dead node takes minutes

A node that stops reporting is not declared dead at once. The node lifecycle controller marks it NotReady after `node-monitor-grace-period` (50 seconds by default) and taints it. Every pod carries a default toleration of 300 seconds for that taint, so its pods are evicted about five minutes later. Only then do they stop counting toward their ReplicaSet, and only then are replacements created. Shorter values react faster and evict more pods during brief network blips.
