reference:
  roles:
    - role: Declared type
      example: "body: unknown"
      job: What the variable may ever hold. Narrowing never goes beyond it.
    - role: Narrowing check
      example: typeof, in, instanceof, ===, truthiness
      job: A condition the compiler understands. On each branch it keeps only the members that can pass.
    - role: Type predicate
      example: "isPaymentEvent(x): x is PaymentEvent"
      job: A function whose true result narrows its argument. Trusted, not verified.
    - role: Exit
      example: return badRequest()
      job: Removes the rejected values from everything below it, which is what lets the code after a guard rely on it.
  useWhen:
    - A value comes in as unknown, from JSON, a message queue, a catch block or postMessage.
    - A union needs different handling per member.
    - A property may be null or undefined and some paths need it present.
  avoidWhen:
    - You are about to write `as T` on unvalidated data. That is a cast, not a narrowing; it checks nothing.
    - The same narrowing appears in ten places. Parse once at the boundary into a precise type and pass that around.
  tradeoffs:
    - Narrowing follows one function body. Callbacks, other functions and plugins can change a property without the compiler noticing.
    - Hand-written guards are fast to write and easy to get wrong. A schema library such as zod or valibot generates the check and the type together.
    - Early returns keep the narrowed path flat but scatter the exits. Name the guard well so the reader sees what was ruled out.
  lookalikes:
    - name: Type assertion (as)
      how: Changes the type without any check. Narrowing changes it because of a check the compiler saw.
    - name: Assertion function
      how: "asserts x is T: narrows the code after the call instead of a branch, and throws if the check fails."
    - name: Pattern matching
      how: Rust match, Python match and Go type switches narrow by destructuring. TypeScript narrows ordinary if and switch statements instead.

## [concept] Control-flow narrowing

**The checker follows your if statements. After typeof, in, instanceof, an equality test or a type guard, a variable's type is the subset that can still reach that line.**

A value typed `unknown` can be anything. Write `if (typeof body !== "object" || body === null) return;` and on the next line the compiler knows `body` is an object. You did not change the declared type; you changed which values can get there.

<Depth level={2}>
This is <Term id="control-flow-narrowing">control-flow narrowing</Term>. The compiler understands `typeof`, `instanceof`, the `in` operator, `===` and `!==` against literals and null, truthiness, and functions whose return type is a <Term id="type-predicate">type predicate</Term> such as `x is PaymentEvent`. Each one splits a type in two: the part that passes and the part that does not. Read it with the set picture from the previous lesson. A <Term id="union-type">union</Term> shrinks member by member, and the <Term id="top-type">top type</Term> `unknown` shrinks to `object`, then to an object with known properties.
</Depth>

<Depth level={3}>
The checker builds a control-flow graph for each function. Every reference to a variable or property path such as `body.data.customer` looks back along the graph to the assignments and conditions that reach it, and computes its type there. Two rules limit how far that goes. A narrowing is dropped when the variable or property path is assigned. And the checker is optimistic about calls: it assumes a function call does not undo a narrowing, a deliberate trade-off recorded in TypeScript issue 9998. Closures are the other edge. Since TypeScript 5.4, a `let` variable or parameter keeps its narrowing inside a closure created after its last assignment, but not if any nested function assigns it.
</Depth>

## [problem] A webhook handler with a cast

A payment provider posts JSON events to a handler. The handler parses the body, casts it to `PaymentEvent`, and marks the invoice paid when a payment succeeds.

It works. The provider's sample events pass, and the dashboard shows paid invoices.

<Depth level={2}>
`as PaymentEvent` is not a check. It tells the compiler to treat the value as a `PaymentEvent` from now on, whatever arrived. The declared type says `customer: Customer`, because every sample event the team saw had one. Nothing in the program confirms that real events agree.
</Depth>

<Depth level={3}>
`req.json()` is typed `Promise<any>` in lib.dom, so even the cast is optional; `any` flows into anything. Starting from `unknown` and narrowing is the only path where the compiler checks what you do.
</Depth>

## [pain] Then a change request arrives

**Change request:** email the customer when a payment fails. Guest checkouts send the event with customer set to null.

The new branch compiles. The type says `customer: Customer`, so `event.data.customer.email` looks safe. The first guest checkout that fails throws a TypeError, the handler answers 500, and the provider retries the event, which fails the same way.

<Depth level={2}>
The compiler was not wrong; it was told something false. Every line after the cast inherits the lie, and the non-null assertion on `failureCode!` adds a second one. Nothing marks either line as risky in review.
</Depth>

<Depth level={3}>
Providers typically retry failed deliveries with backoff for hours or days. A handler that crashes on one shape of event turns into a queue of retries for every event of that shape.
</Depth>

### What each check narrows

| Check | Narrows | Watch out for |
|---|---|---|
| `typeof x === "string"` | primitives, `"object"`, `"function"` | `typeof null` is `"object"` |
| `x instanceof SyntaxError` | class instances | fails across realms, such as iframes and some test runners |
| `"type" in x` | unions by property; adds `Record<"type", unknown>` (4.9+) | the right side must be an object; optional properties stay on both branches |
| `x.type === "payment.failed"` | unions with a literal tag | the tag must be a literal type, not `string` |
| `x !== null`, `x != null` | removes null (and undefined with `!=`) | a call in between does not undo it |
| `isT(x): x is T` | whatever the predicate claims | the body is never checked against the claim |
