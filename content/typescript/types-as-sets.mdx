title: Types are sets of values
track: typescript
group: Types
order: 2
summary: Read every type as the set of values it allows. A union is a bigger set, an intersection a smaller one, and "assignable to" means "is a subset of".
intent: A parameter typed string accepts every string ever written, so the checker cannot tell your four valid methods from a typo or a dangerous one.
changeRequest: Add PATCH for partial invoice updates. PATCH is not idempotent, so it must never go through the retry helper.

# ---------------------------------------------------------------- checks, one per depth
checks:
  overview:
    question: Which type accepts the value "PATCH"?
    options:
      - text: '"GET" | "PATCH"'
        correct: true
        why: Right. A union holds every value of either side, and "PATCH" is one of them.
      - text: '"GET" & "PATCH"'
        why: An intersection holds only values in both sets. No string is both "GET" and "PATCH", so this type is never.
      - text: '"GET" | "HEAD" | "PUT" | "DELETE"'
        why: That is the Idempotent set from the lesson. "PATCH" is not one of its four members.
  engineer:
    question: "type Account = { id: string } and type Customer = { id: string; email: string }. Which is true?"
    options:
      - text: Customer is assignable to Account. Every value with an id and an email also has an id, so Customer is the smaller set.
        correct: true
        why: Right. More required properties means fewer values. An object literal with extra properties can still trip the separate excess property check, but a Customer variable passes as an Account.
      - text: Account is assignable to Customer, because it has fewer requirements.
        why: Fewer requirements means a bigger set. An Account may have no email, so it cannot stand in where a Customer is needed.
      - text: Neither, because they are declared separately and TypeScript compares names.
        why: TypeScript compares shapes, not names. That is structural typing.
  deep:
    question: "With A = { id: string; email: string } and B = { id: string; phone: string }, what is keyof (A | B)?"
    options:
      - text: '"id"'
        correct: true
        why: Right. A value of A | B may be either one, so only keys both members have are safe to read. Bigger set, fewer guaranteed keys.
      - text: '"id" | "email" | "phone"'
        why: That is keyof (A & B). An intersection guarantees every key of both sides, which is why it holds fewer values.
      - text: never
        why: The members share id, so the result is not empty. keyof would be never only if no key were common.

# ---------------------------------------------------------------- reference page
reference:
  roles:
    - role: Universe
      example: unknown
      job: The set of every value. Every type is assignable to it, and you must narrow it before you use it.
    - role: Empty set
      example: never
      job: The set with no values. Assignable to every type; nothing but never is assignable to it.
    - role: Literal type
      example: '"POST", 503'
      job: A set with exactly one member.
    - role: Union
      example: Idempotent | "POST"
      job: Every value in either set. Bigger set, fewer properties you can rely on.
    - role: Intersection
      example: Req & { method Idempotent }
      job: Only values in both sets. Smaller set, more properties you can rely on.
  useWhen:
    - A parameter accepts a handful of known values. Name the set as a union of literals instead of string or number.
    - Some operations are only safe for part of a set. Give that part its own name, as Idempotent is to Method.
    - You need to reason about assignability. Ask whether every value of one type is in the other.
  avoidWhen:
    - The values are open-ended, such as user names or URLs. A union of literals cannot list them.
    - The set comes from runtime data, such as feature flags in a database. The checker only knows what is written in the source.
  tradeoffs:
    - Precise sets catch more mistakes at compile time, but every new member is a source change and a deploy.
    - A union reads naturally but tells you less about each value, so you must narrow before you use member-specific properties.
    - The types vanish at runtime. Values arriving over the network still need checking at the boundary.
  lookalikes:
    - name: Enum
      how: TypeScript enums are a runtime object plus a type. A union of string literals is only a type, so it adds no code and works with plain strings from JSON.
    - name: Subclass
      how: In nominal languages, a subtype is declared with extends. In TypeScript any value with the right shape is in the set, declared or not.
    - name: Go type sets
      how: Go defines interfaces by their type sets, but unions are allowed only in generic constraints, not as ordinary parameter types.

## [concept] Types are sets of values

**Read every type as the set of values it allows. A union is a bigger set, an intersection a smaller one, and "assignable to" means "is a subset of".**

`string` is the set of every string. The <Term id="literal-type">literal type</Term> `"POST"` is a set with one member. When the checker asks whether one type is assignable to another, it asks whether every value of the first is also in the second.

<Depth level={2}>
Two operators build new sets. A <Term id="union-type">union</Term> `A | B` holds every value of either side, so it is at least as big as each. An <Term id="intersection-type">intersection</Term> `A & B` holds only values in both, so it is at most as big as the smaller side. For object types this feels backwards at first: `A & B` has more properties than A, because a value must pass both tests, and passing more tests leaves fewer values. Two types close the picture. `unknown` is the <Term id="top-type">top type</Term>, the set of everything. `never` is the <Term id="bottom-type">bottom type</Term>, the empty set.
</Depth>

<Depth level={3}>
The checker does not list values. It decides <Term id="assignability">assignability</Term> by comparing structure: literal to its base type, each union member against the target, and each property of an object type against the target's properties. The set reading is the model that structural comparison approximates. Because TypeScript uses <Term id="structural-typing">structural typing</Term>, an object type is the set of every value with at least those properties, declared anywhere or not at all. The checker also simplifies as a set would: `"GET" | string` reduces to `string`, `"GET" & string` to `"GET"`, and since TypeScript 3.9 an intersection of object types whose literal properties conflict reduces to `never` itself.
</Depth>

## [problem] A retry helper that takes any string

An HTTP client wraps `fetch` with a retry helper. Retrying is only safe for idempotent methods, where sending the request twice has the same effect as sending it once. So the helper checks the method against a list of four and throws for anything else.

It works. The tests send GET and PUT, and both retry on a 503.

<Depth level={2}>
Look at the parameter type. `method: string` is the set of every string: `"GET"`, `"get"`, `"PTACH"`, `"POST"`. The function handles four of them correctly and rejects the rest at runtime. The checker cannot help, because every one of those strings is a legal `string`. The call in billing that retries a POST compiles, and it only fails when that code path runs.
</Depth>

<Depth level={3}>
The list on line 2 is the real type, written as data. The rule "only these four" exists, but in a form the compiler cannot read.
</Depth>

## [pain] Then a change request arrives

**Change request:** add PATCH for partial invoice updates. PATCH is not idempotent, so it must never go through the retry helper.

With `string` parameters there is nowhere to write that rule in the types. The team adds a second runtime list and a check in `send`, and then someone has to read all 23 callers of the retry helper to make sure none of them will ever pass PATCH.

<Depth level={2}>
Nothing marks the risky calls. A caller that builds the method from a variable, such as `sendWithRetry(op.method, …)`, passes review because the reviewer cannot see the value. The mistake shows up as a duplicated charge or a duplicated invoice line, long after the deploy.
</Depth>

<Depth level={3}>
Retrying a non-idempotent request is a classic way to double-charge. Many payment APIs add an idempotency key header for exactly this reason. The type system can enforce the simpler half of the rule: which methods may be retried at all.
</Depth>

## [morph] Give the sets names

Drag the slider. The one big box, `string`, becomes two named sets: `Idempotent` with four members, inside `Method`, which adds POST. The helper accepts only the inner set.

Hover a box in the diagram to see its code.

<Depth level={2}>
`RetryableReq` is `Req & { method: Idempotent }`. The intersection adds a requirement, so it holds fewer requests: only the ones whose method is retry-safe. Because it is a subset of `Req`, the helper can still pass it to `send` without a cast.
</Depth>

<Depth level={3}>
<Lang only="typescript">The `method` property of the intersection has the type `Method & Idempotent`, which the checker reduces to `Idempotent`, because `Idempotent` already sits inside `Method`.</Lang>
<Lang only="go">Go cannot write `Method | "POST"`, so the subset gets its own struct type. The unexported field means other packages cannot construct one with a value, only use the four variables `httpx` exports.</Lang>
<Lang only="python">`Literal["GET", "HEAD", "PUT", "DELETE"]` is a set of four strings to the checker. At runtime `send_with_retry("POST", …)` still runs; only mypy or pyright will stop it.</Lang>
<Lang only="rust">Rust has no unions of types, so `Method` wraps `Idempotent` as one of its variants. The `From` impl is the subset relation, written by hand once.</Lang>
</Depth>

## [walk] Follow one bad call

Billing tries to retry a POST. Step through what the checker does with the numbered buttons.

<Depth level={3}>
<Lang only="typescript">The checker compares the object literal property by property. `url` is a `string`, fine; `method` is `"POST"`, and `"POST"` is not assignable to `Idempotent`. The error points at the property, not the whole call.</Lang>

</Depth>

## [again] PATCH, the second time

The same request, after the refactor. PATCH joins `Method` and nothing else. `send` accepts it. Every call that tries to retry it is a compile error, listed by the compiler with file and line. Nobody reads 23 call sites.

<Depth level={2}>
The rule lives in one place: which set a method belongs to. Had PATCH been added to `Idempotent` by mistake, the review would show exactly that one-line decision.
</Depth>

<Depth level={3}>
The types prove nothing about values that arrive at runtime. A method read from a job queue is a `string` until a check moves it into `Method`. That check is narrowing, the next lesson.
</Depth>

## [lens] How each language writes it

TypeScript reasons about types as sets more directly than most languages. Python's checkers come close, Go thinks in sets only for generics, and Rust keeps every type disjoint and makes you convert explicitly.

### The set laws you will use

| Expression | Same set as | Why |
|---|---|---|
| `T \| never` | `T` | Adding the empty set adds nothing |
| `T & unknown` | `T` | Everything is in unknown, so the test always passes |
| `T \| unknown` | `unknown` | Nothing is outside unknown |
| `T & never` | `never` | No value is in the empty set |
| `"GET" \| string` | `string` | The literal is already a string |
| `"GET" & "POST"` | `never` | No value is both |
| `keyof (A \| B)` | `keyof A & keyof B` | Only shared keys are safe on a value that may be either |
