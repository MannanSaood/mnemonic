      - text: The members share no properties at all.
        why: Then there is nothing to switch on. The shared tag property is what makes the union usable.

      - text: It compiles. Every requires_action payment is labelled Processing until someone notices.

      - text: The compiler flags the switch because requires_action has no case.

  deep:
    question: Why does assertNever(p) in the default branch compile today but fail after you add a member?
    options:
      - text: In the default branch, p has the type of the members no case handled. With all handled, that is never, which is assignable to never; a new member leaves a non-empty type, which is not.
        correct: true
        why: Right. Each case removes its members from p's type by narrowing on the literal tag. The default sees what is left, and the parameter type never accepts only the empty set.

        why: There is no counting. It is ordinary narrowing plus an assignability check against never.
      - text: assertNever is a compiler built-in that checks the switch it appears in.
        why: It is an ordinary function you write. Its parameter type, never, does all the work.

reference:
  roles:
    - role: Union
      example: Payment
      job: Lists every state the value can be in, and nothing else.
    - role: Tag (discriminant)
      example: status
      job: A property every member has, with a different literal type in each. Comparing it narrows to one member.
    - role: Member
      example: "{ status: \"captured\"; capturedAt: Date }"
      job: One state with exactly the fields that state has, all required.
    - role: Exhaustiveness check
      example: assertNever(p) in default
      job: Fails to compile while any member is unhandled, so a new member is flagged at every switch.
  useWhen:
    - A value moves through states, and each state has different data, such as payments, uploads, fetches or deploys.
    - You decode tagged JSON events or messages.
    - You expect new variants over time and want the compiler to list every place that must handle them.
  avoidWhen:
    - The variants differ only in behaviour that changes together. An interface with one method per operation may be simpler.
    - Other teams add variants you cannot see, such as plugins. A closed union cannot be extended from outside.
  tradeoffs:
    - Every switch must change when you add a member. That is the point, but in a large codebase it is a real cost.
    - Adding a new operation is cheap (one more switch). Adding a new member touches every switch. This is the expression problem, the mirror image of class hierarchies.
    - The union shapes data in memory only. Values from the network still need a check at the boundary to become a Payment.
  lookalikes:
    - name: Optional fields
      how: One object type with many optional properties. Flexible, but it allows impossible combinations and gives the compiler no list of states to check.
    - name: State pattern
      how: Each state is a class with its own methods. Adding a state is one class; adding an operation touches every class. Unions make the opposite trade.
    - name: Enum
      how: A TypeScript enum or a union of strings names the states but carries no per-state data. A discriminated union attaches data to each state.

## [concept] Tagged unions and exhaustiveness

**Model each state as its own member of a union, tagged with a literal field. Switch on the tag, end with assertNever, and every new state becomes a compile error wherever it is not handled yet.**

A captured payment has a capture date. A failed one has a reason. In a <Term id="discriminated-union">discriminated union</Term> each state is its own type with exactly those fields, and a shared `status` field says which state this is.

<Depth level={2}>
The shared field is the <Term id="discriminant">discriminant</Term>. Its type in each member is a <Term id="literal-type">literal type</Term>, so `p.status === "captured"` narrows `p` to the captured member. Code inside that branch reads `p.capturedAt` as a `Date`, never `undefined`. The union lists the states of a <Term id="finite-state-machine">finite-state machine</Term>, and each member carries only the data its state can have, so a payment that is both failed and captured cannot be written.
</Depth>

<Depth level={3}>
This is a <Term id="sum-type">sum type</Term>, the same idea as a Rust enum or an ML variant. TypeScript builds it from parts it already has: unions, literal types and narrowing. The exhaustiveness check is the last part. Each `case` removes its members from the type of `p`, so the `default` branch sees what is left. When nothing is left, `p` there is `never`, the <Term id="bottom-type">bottom type</Term>, and only `never` can be passed to a parameter of type `never`. That one assignment turns the switch into an <Term id="exhaustive-match">exhaustive match</Term>.
</Depth>

## [problem] A payment made of optional fields

A shop keeps each payment as one object: an id plus optional fields that fill in as the payment moves along. Five functions in five files read it: fulfillment, the status badge, refunds, the receipt email and a retry job.

It works. Each function checks the fields it cares about, and the tests cover the five statuses the payment provider sends.

<Depth level={2}>
Look at what the type allows. Four optional fields make 16 combinations, and only five of them are real payments. A refunded payment without a capture date, or a failed one with an auth code, type-checks just as well. Each function infers the state from whichever fields it happens to test, and each one infers it a little differently.
</Depth>

<Depth level={3}>
`readyToShip` relies on a comment: checkout waits for authorization, so a pending payment never reaches fulfillment. That assumption is invisible to the compiler and true only for the flows that existed when it was written.
</Depth>

## [pain] Then a change request arrives

**Change request:** support 3-D Secure. A payment can now wait in requires_action while the customer confirms it with their bank.

Add one optional field, `redirectUrl`. Everything compiles. Checkout now returns to the customer before authorization, so 3-D Secure payments reach fulfillment, and `readyToShip` says true: the warehouse ships an order nobody has paid for. The badge says Processing, the receipt says Pending, and neither shows the link the customer needs.

<Depth level={2}>
The marked lines are the ones that misbehave, and nothing marks them. Two of the five functions happen to do the right thing, by luck. To find the three that do not, someone has to read all five, and every function added since.
</Depth>

<Depth level={3}>
Five optional fields make 32 combinations. Each new optional field doubles the shapes the type allows, while the business gained one state.
</Depth>

## [morph] One member per state

Drag the slider. The optional fields move into five member types, one per state, each tagged by `status`. The functions switch on the tag and end with `assertNever`.

Hover a box in the diagram to see its code.

<Depth level={2}>
Fields that were optional become required where they belong. `capturedAt` exists only on the captured member, so `readyToShip` and every other function can stop guessing the state from which fields are set.
</Depth>

<Depth level={3}>
<Lang only="typescript">`assertNever` does two jobs. At compile time its parameter type proves the switch is complete. At runtime it throws if a value outside the union arrives anyway, for example from an API that started sending a new status before you deployed.</Lang>
<Lang only="go">The sealed interface keeps other packages from adding members, which is what makes a list of cases meaningful. The compiler still does not check the list; the `//go-sumtype:decl` comment lets the linter do it.</Lang>
<Lang only="python">Frozen dataclasses make each state immutable, so moving between states means building a new object, which keeps the old one honest. `assert_never` both satisfies the checker and raises at runtime.</Lang>
<Lang only="rust">Rust needs no helper. A `match` without a catch-all arm is already exhaustive, and the compiler refuses to build one that misses a variant.</Lang>
</Depth>

## [walk] Follow one switch

`readyToShip` receives a payment. Step through the switch with the numbered buttons, and watch what the compiler knows about `p` at each case.

<Depth level={3}>
<Lang only="typescript">A `switch` on a string tag compiles to ordinary JavaScript comparisons; the union and the narrowing are erased. The check costs nothing at runtime, and protects nothing at runtime except through the throw in `assertNever`.</Lang>
<Lang only="go">A type switch compares the interface's type word against each case's type. Order matters only for readability, since each concrete type matches one case.</Lang>
<Lang only="python">Class patterns call `isinstance` in order. The checker's narrowing is static; at runtime the `case _` arm really runs `assert_never`, which raises `AssertionError`.</Lang>
<Lang only="rust">The match compiles to a jump on the discriminant. Exhaustiveness is checked before code generation, so a missing variant never reaches a binary.</Lang>
</Depth>

## [again] 3-D Secure, the second time

The same request, after the refactor. Add one member, `requires_action`, with a required `redirectUrl`. The compiler stops at every switch that ends in `assertNever`, with the file and line. Each one gets a case, and someone decides, in that place, what a payment waiting for the bank means there.

<Depth level={2}>
Not every switch is flagged. One that ends in `default: return "Processing"` compiles and quietly treats the new state like the default. Keep defaults for switches over open sets, such as strings from outside; over your own union, end with `assertNever`.
</Depth>

<Depth level={3}>
The trade-off is the <Term id="exhaustive-match">exhaustive match</Term>'s mirror image: adding a member touches every switch, while adding a new operation is one new function. Classes make the opposite trade. Pick the one that matches what changes more often in your domain.
</Depth>

## [lens] How each language writes it

Rust has sum types and exhaustive matching built in. TypeScript and Python assemble them from unions, tags and a never-typed check. Go has neither, and leans on a sealed interface and a linter.

### Three ways to write the exhaustiveness check

| Form | Example | Notes |
|---|---|---|
| Helper function | `default: return assertNever(p);` | Fails to compile on a new member, and throws at runtime if a bad value slips in |
| `satisfies never` | `default: p satisfies never; throw new Error();` | Needs TypeScript 4.9+; no helper to import |
| Return-type check | no default; the function returns `boolean` | With `strictNullChecks`, a missing case means the function can end without returning, which is an error. Weaker: it says nothing about switches with side effects only |
