        type OrderState interface {
            Pay(o *Order) error
            Ship(o *Order) error
            Deliver(o *Order) error
            Cancel(o *Order) error
        }

        type Order struct{ state OrderState }

        func NewOrder() *Order { return &Order{state: Pending{}} }

        func (o *Order) Pay() error     { return o.state.Pay(o) }
        func (o *Order) Ship() error    { return o.state.Ship(o) }
        func (o *Order) Deliver() error { return o.state.Deliver(o) }
        func (o *Order) Cancel() error  { return o.state.Cancel(o) }

        // next moves to s only if the side effect succeeded.
        func (o *Order) next(s OrderState, err error) error {
            if err == nil {
                o.state = s

            return err

        why: Right. Each instance loads its own copy of the order and both see Paid. State organises the rules for one copy; across processes you need the database, a lock or a single owner per order to make the transition atomic.
      - text: The default reject. The second event reaches Cancelled and is refused.
        why: Only on the instance that already moved to Cancelled. The other instance still holds its own Paid copy, so both events pass.
      - text: State objects carry no fields, so they are safe to share between instances.
        why: Sharing state objects saves allocations. The order's current state is still a separate copy per instance, and that copy is what races.
  deep:
    question: The state types here have no fields. What does that let you do?
    options:
      - text: Create one instance of each state and share it among every order, so a transition allocates nothing.
        correct: true
        why: Right. The catalogue notes that a state with no fields is a flyweight. In Go `Paid{}` is a zero-size value, and in Rust each state is just an enum tag. In Python and TypeScript you can keep module-level singletons instead of calling `Paid()` each time.
      - text: Let the compiler reject illegal transitions.
        why: No. Fieldless states are still checked at runtime. Compile-time checks need the state in the type of the order itself, which is typestate.
      - text: Make each order safe to use from several threads at once.
        why: No. The order's state field is still mutable and shared. Fieldless state objects do not add any synchronisation.

  roles:
    - role: Context
      example: Order
      job: Holds the current state and forwards every request to it. Keeps no flags of its own.
    - role: State
      example: { go: "OrderState (interface) + reject", python: "OrderState (base class)", typescript: "OrderState (abstract class)", rust: "OrderState (enum)" }
      job: Names every request the context accepts, and refuses each one by default.
    - role: Concrete state
      example: Pending, Paid, Shipped, Delivered, Cancelled
      job: Handles the requests that are legal in that state, and picks the next state.
    - role: Client
      example: Payment webhook, warehouse scanner, support tool
      job: Sends requests to the context. Never sees the state objects.
  useWhen:
    - An object has a lifecycle, and the same request means different things, or is illegal, depending on where it is.
    - Several methods each branch on the same set of flags or status values.
    - Events come from systems that do not coordinate, so they can arrive late, twice or out of order.
  avoidWhen:
    - There are two or three states and the rules fit in one readable switch. An enum and a switch are clearer.
    - The states differ only in data, not behaviour. A status field and a transition table say it with less code.
  tradeoffs:
    - One type per state, so a small machine gets spread across many small classes.
    - States that pick their successor know about each other, which couples them.
    - The pattern guards one in-memory object. Concurrent processes still need a database constraint or a lock.
    - The rules for one event are spread across the states. To see the whole machine at once, draw it or keep a table next to the code.
  lookalikes:
    - name: Strategy
      how: Same shape, a context delegating to an object behind an interface. In Strategy the caller picks the object and it stays put; in State the object replaces itself as events arrive.
    - name: Transition table
      how: A map from (state, event) to the next state. Best when states differ in where they go but not in what they do. The catalogue describes it as the alternative to State.
    - name: Typestate
      how: Moves the state into the type, so illegal calls do not compile. Works when the state is known at compile time, not when it is loaded from a database.

## [concept] State

**Give each state of an object its own object, and let the current one decide what every request does, including refusing it.**

From the outside, the object seems to change its class as it moves through its lifecycle. Inside, it swaps one field.

<Depth level={2}>
The lifecycle is a <Term id="finite-state-machine">finite-state machine</Term>: a fixed set of states and the events each one accepts. The **context** (`Order`) holds the current state and forwards every request to it. The **state** interface lists every request and refuses each one by default. Each **concrete state** overrides only the requests that are legal for it, does the work, and names the next state. Anything a state did not list is refused without anyone writing that check.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files State under object behavioural patterns, with a TCP connection as its example, and gives it the alias Objects for States. It names three consequences. State-specific behaviour is collected in one place per state. Transitions become explicit, a single assignment instead of several variables changing one by one. And states with no fields can be shared between contexts. It also leaves open who picks the next state: the context or the states themselves.
</Depth>

## [problem] An order made of flags

An online shop tracks each order with four booleans: paid, shipped, delivered and cancelled. Each method checks the flags it needs and sets one more. It works, and the tests for the normal path pass.

Read the four guards. Each one asks about one or two flags. None asks about all four.

<Depth level={2}>
Events reach the order from different systems. The payment provider sends a webhook when a charge succeeds, the warehouse scanner calls Ship, support cancels. Webhooks use <Term id="at-least-once-delivery">at-least-once delivery</Term>, so the same event can arrive twice. Nothing stops Ship arriving after Cancel.
</Depth>

<Depth level={3}>
Four booleans make 16 combinations, and only six of them are real orders. The other ten are states the business never defined, and the code reaches some of them. Cancel a paid order, then Ship: Ship checks only `paid`, which is still true, so a refunded order leaves the warehouse.
</Depth>

## [pain] Then a change request arrives

**Change request:** the fraud team needs to hold risky orders for review before they ship.

One new flag means a new guard in Ship, two new methods, and a question for every other method: what should it do when the order is on hold? Five flags make 32 combinations.

<Depth level={2}>
The marked lines are the ones we remembered. Should Deliver check the hold? Can a held order be cancelled, and is it refunded then? Each answer is another guard, and a guard nobody wrote is a bug nobody sees until the event arrives in the wrong order.
</Depth>

<Depth level={3}>
The existing bugs stay too. Ship still never checks `cancelled`, and Cancel still refunds twice if the webhook is retried. Each new flag multiplies the cases every guard must think about.
</Depth>

## [morph] Turn each lifecycle state into an object

Drag the slider. The four flags become five state types behind one interface, and Order keeps a single field: the current state.

Hover a box in the diagram to see its code.

<Depth level={2}>
Now each state lists what it accepts. Pending accepts Pay and Cancel, Paid accepts Ship and Cancel, Shipped accepts Deliver. Everything else falls through to the default and is refused. The impossible combinations are gone, because a single field can hold only one state.
</Depth>

<Depth level={3}>
<Lang only="go">Go has no inheritance, so the refusing defaults come from embedding. `Pending` embeds `reject`, which promotes all four methods; `Pending` then defines its own `Pay` and `Cancel`, which take precedence over the promoted ones.</Lang>
<Lang only="python">The base class supplies the refusing methods, and each subclass overrides only what it accepts. Method lookup follows the class's MRO, so an override always wins over the default.</Lang>
<Lang only="typescript">The abstract base class supplies the refusing methods. Its parameters are prefixed with `_` because the defaults ignore them. Subclasses override only the events they accept.</Lang>
<Lang only="rust">An enum and one `match` replace the state classes. The compiler checks that the match covers every `(state, event)` pair, so refusing is a deliberate catch-all arm, not a forgotten case.</Lang>
</Depth>

## [walk] Follow one cancellation

A paid order is cancelled, and then a late Ship arrives. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Each call through `o.state` is an interface call through the <Term id="itab">itab</Term>. The state values are zero-size structs, so `o.state = Paid{}` allocates nothing.</Lang>
<Lang only="python">Each call is an attribute lookup on the current state object, then a call. `Paid()` allocates a small object each time; module-level instances would avoid that, since the states hold no data.</Lang>
<Lang only="typescript">Between `await refund(o)` and the assignment, the event loop can run another event for the same order, and it still sees Paid. If events for one order can overlap, queue them per order so they run one at a time.</Lang>
<Lang only="rust">The match compiles to a jump on two small integers, the enum tags. No allocation and no <Term id="dynamic-dispatch">dynamic dispatch</Term>, and `OrderState` is `Copy`, so reading it out of `self` borrows nothing.</Lang>
</Depth>

## [again] The fraud hold, the second time

The same request, after the refactor. You add one state, OnHold, and Paid gains one method that moves into it. OnHold lists Release and Cancel. It does not list Ship, so a held order cannot ship, and nobody had to remember that.

<Depth level={2}>
The interface does grow: Hold and Release are new events, so the state interface and its refusing defaults gain two methods. Every existing state inherits the refusal and none of them changes. This follows the <Term id="open-closed">open/closed principle</Term>.
</Depth>

<Depth level={3}>
Tests follow the machine. For each state, test the events it accepts and one it refuses. The number of tests grows with states times events, not with the 2 to the n flag combinations.
</Depth>

### Persisting the state

A real order lives in a database, so the state object is rebuilt from a status column on every request. Keep the column a single enum, never several booleans, and make each transition a conditional write such as `UPDATE orders SET status = 'cancelled' WHERE id = $1 AND status = 'paid'`. If no row changed, another event got there first, and the request is refused just as the state object would refuse it.
