        export interface Command {
          readonly name: string;
          execute(billing: Billing): Promise<void>;
          undo?(billing: Billing): Promise<void>;
        }

        export class Refund implements Command {
          readonly name = "refund";
          constructor(
            readonly orderId: string,
            readonly cents: number,
            readonly key: string = crypto.randomUUID(),
          ) {}

          execute(billing: Billing): Promise<void> {
            return billing.refund(this.orderId, this.cents, { idempotencyKey: this.key });
          }
        }

          private queue: Command[] = [];
          constructor(private billing: Billing, private audit: AuditLog) {}

          enqueue(c: Command): void {
            this.queue.push(c);

            const c = this.queue.shift();
            if (!c) return;
            const error = await retry(3, () => c.execute(this.billing)).then(() => null, (e: unknown) => e);

        pub enum Command {
            Refund { order_id: String, cents: u64, key: Uuid },
            ChangePlan { account: String, plan: Plan },
            AddCredit { account: String, cents: u64, key: Uuid },
        }

                match self {
                    Command::Refund { order_id, cents, key } => b.refund(order_id, *cents, *key),
                    Command::ChangePlan { account, plan } => b.set_plan(account, *plan),
                    Command::AddCredit { account, cents, key } => b.add_credit(account, *cents, *key),

            queue: VecDeque<Command>,

## [concept] Command

**Turn a request into an object that holds everything needed to carry it out, so it can be queued, retried, logged or undone later.**

A method call happens once, now, and leaves nothing behind. A command is the same call written down: which action, with which arguments.

<Depth level={2}>
Five roles share the work. The **command** is the <Term id="interface">interface</Term> every action implements, usually one method, `Execute`. Each **concrete command** (Refund, ChangePlan) holds its arguments. The <Term id="command-invoker">invoker</Term> (the worker) runs commands without knowing what they do, which is where queueing, retries and logging live. The <Term id="command-receiver">receiver</Term> (the billing client) does the real work. The **client** (the admin console) builds commands and hands them over.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue also calls it Action or Transaction. It describes commands as an object-oriented replacement for callbacks, and lists four uses: parameterising objects by an action, queueing and running requests at a different time, undo through an Unexecute operation and a history list, and logging changes so they can be replayed after a crash. It notes that a command may need to store the receiver's old state to undo itself.
</Depth>

## [problem] An admin console that calls billing directly

Support staff use an admin console to refund orders, change plans and add credit. Each button posts to a handler, and each handler calls the billing client straight away.

Read it once. It is simple and it works, because each action happens once, right now, while the support agent waits.

<Depth level={2}>
Every action is a method with its own name and signature. Nothing outside those methods can see an action before it runs, store it, or run it again.
</Depth>

<Depth level={3}>
If the billing API is down, the agent gets an error and tries again later by hand. That is acceptable for one refund. It stops being acceptable when there are hundreds.
</Depth>

## [pain] Then a change request arrives

**Change request:** support needs bulk refunds that run in the background, retry when the billing API times out, and appear in the audit log.

The marked lines add an audit call and a retry to every method. The same two lines are pasted three times, and the next action must remember to paste them again.

<Depth level={2}>
The edit is the easy part. The background queue cannot be written at all: a method call is not something you can put in a table and run tonight. You would need a new job type per action, and a worker that knows every one of them.
</Depth>

<Depth level={3}>
Retrying a refund blindly is also dangerous. If the API timed out after it sent the money, the retry sends it again. The method signature gives you nowhere to carry the information that would prevent that.
</Depth>

## [morph] Turn each method into an object

Drag the slider. Each action becomes a small type that holds its arguments. The worker holds a queue of them and runs each one through the same interface.

Hover a box in the diagram to see its code.

<Depth level={2}>
Queueing, retries and the audit log now live in one place, the worker, and apply to every command. Adding an action means adding a command type; the worker does not change. The command is also where an <Term id="idempotency-key">idempotency key</Term> belongs: it is chosen once, when the command is created, and travels with every attempt.
</Depth>

<Depth level={3}>
<Lang only="go">A `chan Command` is an in-process queue: the console sends, the worker's `for range` receives. It is lost when the process stops. For bulk refunds that must survive a deploy, store the commands in a table and let the worker read them; that is why they hold IDs and amounts, not pointers.</Lang>
<Lang only="python">`deque.popleft()` is O(1), unlike `list.pop(0)`, which shifts every item. A frozen dataclass cannot be changed after it is queued, so the command that runs is the command that was logged.</Lang>
<Lang only="typescript">The array is an in-memory queue and dies with the process. A real job queue such as BullMQ stores each job as JSON, so the class instance becomes plain data on the way in and must be rebuilt by `kind` on the way out.</Lang>
<Lang only="rust">An `enum` makes the set of commands closed: adding a variant makes the compiler point at every `match` that must handle it. With `serde`, the same enum is the queue message format.</Lang>
</Depth>

## [walk] Follow one refund

One refund through the design, from the console to the audit log. Step through it with the numbered buttons.

<Depth level={2}>
Retries make delivery <Term id="at-least-once-delivery">at least once</Term>: if the worker cannot tell whether an attempt succeeded, it must try again. That is only safe when running the command twice has the same effect as once. Setting a plan to Pro is like that by nature. Refunds and credits add to something, so they need the key.
</Depth>

<Depth level={3}>
Payment APIs support this directly. Stripe, for example, accepts an `Idempotency-Key` header, stores the first response for that key and returns it again for any repeat. The key must come from the command, not from the attempt; a key generated inside the retry loop is a new key every time and protects nothing.
</Depth>

## [again] Bulk refunds, the second time

The same request after the refactor. A bulk refund is a loop that queues one command per order. The worker already retries and logs every command, so nothing else changes.

<Depth level={2}>
The key is built from the order ID. If the bulk job itself crashes halfway and is run again, each refund gets the same key as before, and the provider skips the ones already done.
</Depth>

<Depth level={3}>
Undo comes the same way. A ChangePlan command can save the old plan when it runs and set it back in `Undo`. A refund cannot be undone by the system at all: the money has left, and taking it back is a new charge that needs the customer's consent. Commands make undo possible; they do not make every action reversible.
</Depth>

### When the command is just a function

In memory, a function value or closure already is a command: Go's `func(ctx) error`, Python's `functools.partial`, a JavaScript arrow function, a Rust closure. Start there. Move to a named type when the command must be stored, sent to another process, shown in a log or undone, because a closure cannot be serialised or inspected and has nowhere to keep an idempotency key or the old value for undo.
