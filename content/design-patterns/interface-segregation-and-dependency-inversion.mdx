    question: GdprExporter needs FindByID, ExportAll and Delete. A teammate proposes three interfaces, Finder, Exporter and Deleter. What do you suggest?

      - text: One GdprStore interface with exactly those three methods, named for what the exporter needs.

    options:
      - text: Only the Postgres adapter and main. No business package imports the adapter or the driver, so their cached builds and test results are still valid.
        correct: true
        why: Right. Build tools such as Go's build cache, cargo and tsc's incremental mode reuse work for packages whose imports did not change. Source dependencies, not runtime calls, decide what rebuilds.

    - role: Role interface

    - role: Composition root
      example: main

  useWhen:
    - Several clients use different slices of one big interface, and its changes keep rippling to all of them.
    - Business code imports a driver, an SDK or a framework type, even just for an error check.
    - You want fast unit tests with tiny fakes, and the ability to swap the storage for local development.
  avoidWhen:
    - One client and one implementation, both owned by the same team, with no test pain. An interface there is just indirection.
    - Stable platform code. Depending on the standard library's string or time types directly is fine; invert dependencies on volatile code.
  tradeoffs:
    - More, smaller interfaces, and some methods appear in several of them.
    - Adapters must translate errors and types at the boundary, which is code to write and test.
    - The wiring in main grows with every adapter.

## [concept] Interface segregation and dependency inversion

**Give each client an interface of only what it uses. Then let the business code own that interface, so the database code depends on it, not the other way round.**

The <Term id="interface-segregation">interface segregation principle</Term> says no code should be forced to depend on methods it does not use. The <Term id="dependency-inversion">dependency inversion principle</Term> says high-level policy should not depend on low-level details; both should depend on abstractions, and the abstraction belongs with the policy.

<Depth level={2}>
Together they decide where a change stops. A small <Term id="role-interface">role interface</Term> per client means a new method for the admin console touches only the admin console. An interface owned by the business code means a driver upgrade touches only the database adapter. Each principle fixes one ripple, and you usually want both.
</Depth>

<Depth level={3}>
Robert C. Martin published both in *C++ Report* in 1996. The interface segregation principle came from consulting for Xerox, where one Job class served every kind of job in a new printer system. Stapling and printing code depended on each other's methods, and even a small change meant an hour-long redeployment. Dependency inversion is named after the structured design of the time, where high-level modules imported low-level ones; in the inverted design, the source-code dependency points against the flow of control. In *Clean Architecture* that one-way crossing becomes the Dependency Rule.
</Depth>

## [problem] One fat repository, and a driver in the business code

Four services share one UserRepository with ten methods. It lives in package postgres, next to its implementation. SignupService uses two of the ten methods, and it checks the driver's error to spot a duplicate email.

Read it once. SignupService imports package postgres for the interface, and the driver for the error.

<Depth level={2}>
Every service that holds a UserRepository depends on all ten methods. Every test fake for any of them implements all ten, even when the test calls one.
</Depth>

<Depth level={3}>
The driver check is the subtle part. SQLSTATE 23505 is Postgres's unique-violation code, and the business rule "an email can register only once" is now written in terms of one database's error format.
</Depth>

## [pain] Then a change request arrives

**Change request:** admins need a BulkBan, and local development moves signup to an in-memory user store.

BulkBan goes into UserRepository, so every implementation and every fake must add it, including the ones for signup, which will never call it. The in-memory store reports duplicates its own way, so SignupService learns a second error from a second store.

<Depth level={2}>
Neither request came from signup, and signup's code changes for both. That is the cost of depending on more than you use, and on details you do not own.
</Depth>

<Depth level={3}>
<Lang only="go">The new store must implement all eleven methods to be a UserRepository, nine of them as stubs that panic. Go would let a fake embed the interface to skip methods, but a nil embedded interface panics when an unexpected method is called.</Lang>
<Lang only="python">mypy rejects the in-memory store as a UserRepository until it has all eleven methods, so it grows stubs that raise NotImplementedError.</Lang>
<Lang only="typescript">The in-memory store must declare all eleven methods to satisfy UserRepository, and every test fake object literal grows a `bulkBan` it never calls.</Lang>
<Lang only="rust">The trait's methods return `sqlx::Error`, so the in-memory store must invent sqlx errors to report anything. The driver's types leaked into a trait that was meant to hide it.</Lang>
</Depth>

## [morph] Small interfaces, owned by the code that uses them

Drag the slider. The ten-method interface becomes a two-method UserStore that lives in package signup. The Postgres repository implements it and translates the driver's error into signup's own. The driver check leaves the business code.

Hover a box in the diagram to see its code.

<Depth level={2}>
Owning the interface means owning its words: its method names, its types and its errors. `EmailTaken` belongs to signup, and every store, Postgres or in-memory, speaks it.
</Depth>

<Depth level={3}>
<Lang only="go">The adapter imports `signup` for `User` and `ErrEmailTaken`, and satisfies `signup.UserStore` without naming it. Go's convention, define interfaces where they are used, is the inversion by default.</Lang>
<Lang only="python">A Protocol is structural, so `PgUserRepository` matches `UserStore` without importing it. It still imports `EmailTaken`, which is the dependency that points from postgres to signup.</Lang>
<Lang only="typescript">`implements UserStore` is optional because of structural typing; it is there so the compiler checks the adapter where it is written.</Lang>
<Lang only="rust">The adapter crate implements a trait from the signup crate for its own type, which the orphan rule allows. The error type is now `StoreError`, owned by signup.</Lang>
</Depth>

### Injection is not inversion

<Term id="dependency-injection">Dependency injection</Term> hands a collaborator in from outside. Dependency inversion decides who owns the type of that collaborator. Injecting a concrete `PgUserRepository`, or an interface that lives in package postgres, is injection without inversion: the business code still imports the database code. The test is simple. Look at the import lines of the business code. If a driver or a database package appears there, the dependency has not been inverted.
