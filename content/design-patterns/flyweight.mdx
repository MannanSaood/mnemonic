  deep:
    question: The pool keeps every LogMeta it has ever handed out, in a Python dict, a TypeScript Map or a Rust HashSet. What happens when old lines are evicted from the store?
    options:
      - text: The pool still references each LogMeta, so unused ones stay in memory until you remove them. Go's unique package avoids this by holding its values through weak pointers.
        correct: true
        why: Right. A strong map keeps everything alive. Use weak references (Python's `weakref.WeakValueDictionary`, JavaScript's `WeakRef`) or evict from the pool when lines go, if the set of shared values keeps changing.
      - text: The runtime frees each LogMeta as soon as no line uses it, whatever pool holds it.
        why: No. A reference from the pool is a reference like any other. Garbage collectors and reference counts only free values that nothing points to.
      - text: Each evicted line takes its own copy of LogMeta with it, so the pool shrinks automatically.
        why: No. Lines hold references to one shared copy. Evicting a line drops a reference; it does not touch the pool.

  roles:
    - role: Flyweight
      example: LogMeta
      job: The shared object. Holds only intrinsic state and is never modified.
    - role: Flyweight factory
      example: { go: "unique.Make", python: "the _metas dict", typescript: "the metas Map", rust: "HashSet<Arc<LogMeta>>" }
      job: Hands out the existing shared object for a key, or creates and stores it the first time.
    - role: Context
      example: LogLine
      job: Holds the extrinsic state (time, trace id, args) and a reference to its flyweight.
    - role: Client
      example: ingest
      job: Splits incoming data into the shared key and the per-object part, and asks the factory.
  useWhen:
    - You hold very many objects, and memory is the limit.
    - Most of each object's data repeats across objects and can be separated out.
    - The shared part never changes after it is created.
  avoidWhen:
    - Objects are few, or the repeated data is small. The pool and the indirection cost more than they save.
    - The data you would share changes per object over time.
    - Code depends on object identity: with sharing, two different lines can hold the identical shared object.
  tradeoffs:
    - Every read of a shared field follows one more pointer.
    - Creating an object costs a lookup in the factory.
    - The factory can keep unused shared objects alive unless it uses weak references or eviction.
    - Shared state must be immutable, which rules out some convenient setters.
  lookalikes:
    - name: Object pool
      how: Reuses objects one user at a time, and they hold changing state. A flyweight is used by many at once and never changes.
    - name: Singleton
      how: Exactly one instance of a type. A flyweight factory keeps one instance per distinct value, which can be thousands.
    - name: Prototype
      how: Copies an existing object to make a new one. Flyweight avoids the copy and shares the original.

## [concept] Flyweight

**When millions of objects carry the same heavy data, store that data once and let every object point at the shared copy.**

Memory then grows with the number of *different* shared values, which is usually small, instead of with the number of objects.

<Depth level={2}>
The pattern splits each object's data in two. <Term id="intrinsic-state">Intrinsic state</Term> is the same wherever the object is used (here, service, host, region, version and the log template), so it goes into a shared flyweight. <Term id="extrinsic-state">Extrinsic state</Term> differs per use (the timestamp, the trace id, the arguments) and stays with each line. A <Term id="flyweight-factory">flyweight factory</Term> makes sure equal intrinsic state is stored once.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Flyweight as an object structural pattern. Its example is a document editor with one object per character: the character code is shared, and position and style come from the context. The book applies the pattern only when all of these hold: very many objects, high storage cost, most state can be made extrinsic, few shared objects remain once it is, and the program does not depend on object identity. It also notes that the savings are largest when extrinsic state can be computed instead of stored.
</Depth>

## [problem] A log store that repeats itself

A log search service keeps the most recent lines in memory, so support can filter them instantly. Each line stores nine fields.

Read it once. Six of the fields repeat across lines: there are 40 services, 600 hosts and 320 log templates, but a million lines.

<Depth level={2}>
Each repeated value is its own string per line. A million lines each carry their own copy of `checkout-api`, of `eu-west-1`, and of the 60-character template they were logged from.
</Depth>

<Depth level={3}>
<Lang only="go">Strings parsed from a buffer are often substrings that share bytes with that buffer, which can keep a whole read buffer alive per line. Copying them fixes that and leaves you with millions of small, separate copies instead.</Lang>
<Lang only="python">`json.loads` reuses repeated object keys within one call, but not values. Every `"checkout-api"` you parse is a new `str` object with its own header.</Lang>
<Lang only="typescript">V8 interns string literals and property names, but strings built at runtime, such as parsed log fields, are separate heap objects even when equal.</Lang>
<Lang only="rust">Each `String` owns its own heap buffer. Ten million lines with six owned strings each means sixty million small allocations, plus a 24-byte `String` header for each.</Lang>
</Depth>

## [pain] Then a change request arrives

**Change request:** support wants a whole day of logs searchable, so the store must hold 10 million lines instead of 1 million.

One number changes. Memory goes from about 320 MB to 3.2 GB, and the pod's limit is 2 GB. The service is killed for running out of memory.

<Depth level={2}>
Buying a bigger pod works once. The cost is linear in lines, so the next retention request doubles it again. The waste is the six fields: they make up about two thirds of every line.
</Depth>

<Depth level={3}>
The fix has to change how a line is stored, not how many are kept. Nothing about the data says that `checkout-api` needs to exist ten million times.
</Depth>

## [morph] Split the line in two

Drag the slider. The six repeating fields leave `LogLine` and become one shared `LogMeta`. Each line keeps its own time, trace id and arguments, plus one reference.

Hover a box in the diagram to see its code.

<Depth level={2}>
The split is the design decision. A field belongs in the shared part only if it is the same for many lines and never changes after the line is written. Put a per-line field in there by mistake and every shared object becomes unique again.
</Depth>

<Depth level={3}>
<Lang only="go">`unique.Make` needs a comparable type, which a struct of strings is. Comparing two `unique.Handle` values is a pointer compare, so filtering by `Meta == wanted` is cheaper than comparing six strings.</Lang>
<Lang only="python">`frozen=True` makes `LogMeta` hashable and turns accidental writes into a `FrozenInstanceError`. `slots=True` removes each instance's `__dict__`, which matters for the ten million `LogLine` objects even more than for the shared ones.</Lang>
<Lang only="typescript">`readonly` stops writes at compile time, and `Object.freeze` stops them at runtime. Both matter here, because one write through a shared object changes every line that uses it.</Lang>
<Lang only="rust">`Arc<LogMeta>` gives shared ownership with no way to get `&mut LogMeta` while other lines hold it. The borrow checker enforces the rule the pattern depends on.</Lang>
</Depth>

## [walk] Follow one line in

One log line, from parsing to storage. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">The `unique` package keeps its canonical values in a concurrent map and refers to them through weak pointers. When no handle to a value remains, the entry becomes eligible for removal after a garbage collection.</Lang>
<Lang only="python">The temporary `key` object is built for every line and discarded when it already exists in the pool. That costs an allocation per line during ingest, but nothing per line in what you keep.</Lang>
<Lang only="typescript">The string key is built per line and dropped after the lookup. Only the first `LogMeta` for each key survives, and every line refers to it.</Lang>
<Lang only="rust">The `key` is moved into the new `Arc` the first time, and dropped otherwise. Each line holds a clone of the `Arc`: one pointer, plus an atomic increment of the shared reference count.</Lang>
</Depth>

## [again] Ten million lines, the second time

The same change after the refactor: one number. Ten million lines now take about 1 GB, and the pool holds about 14,400 shared objects, around 4 MB.

<Depth level={2}>
The remaining gigabyte is the extrinsic state: timestamps, trace ids and arguments. Flyweight cannot shrink data that is different on every line. To go further you would change that data itself, for example by storing arguments compressed.
</Depth>

<Depth level={3}>
Growth is now in two parts. Lines add about 100 bytes each, and new combinations of host, template and version add one shared object each. Watch the second number: a field that seems to repeat but does not, such as a pod name in a fast-scaling deployment, slowly turns the pool into one object per line.
</Depth>

## [play] Decide what to share

A log line with nine fields, and a store that holds up to ten million of them. Move fields between the line and the shared part, change how many lines are loaded, and measure each split.

Look for the split that saves the most, the one that costs more than no sharing, and what happens when someone writes to a shared object.

### Interning is Flyweight for values

<Term id="interning">Interning</Term> is the most common flyweight: one canonical copy of each distinct string or value, handed out to everyone who needs it. Go has `unique.Make` (1.23), Python has `sys.intern`, and Rust programs use `Arc<str>` or an interning crate. Before you design a flyweight class, check whether interning the few heavy fields gets you most of the saving.
