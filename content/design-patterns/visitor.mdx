    question: Your team adds a new resource type every sprint and a new operation about once a year. How should the operations be laid out?
    options:
      - text: As methods on each resource type, behind an interface every type implements.
        correct: true
        why: Right. A new type is then one new file. The rare new operation costs an edit to every type, which you pay once a year instead of every sprint.
      - text: As visitors, one per operation.
        why: Each sprint's new type would edit the Visitor interface and every visitor. Visitor optimises the change you rarely make.
      - text: As visitors with empty default methods, so new types do not break the build.
        why: The build stays green while the operations silently skip the new type. A cost estimate that leaves out a resource is worse than a compile error.
  deep:
    question: In Java or C#, why does Visitor use accept instead of overloads visit(Bucket), visit(Database) called as v.visit(r) on a Resource r?
    options:
      - text: Overloads are chosen at compile time from the static type, which is Resource. Inside Bucket's accept, this has the static type Bucket, so the right overload is picked.
        correct: true

        why: No. Traversal can live in the structure, in the visitor or in an iterator. accept exists to recover the concrete type.

  useWhen:
    - The set of types is stable and new operations keep arriving, as in compilers, linters and plan tools.
    - Operations would otherwise mix unrelated concerns, such as cost, rendering and validation, inside every type.
    - An operation needs to gather state across the whole structure, such as a total or a list of errors.
  avoidWhen:
    - New types arrive more often than new operations. Every new type edits every visitor.
    - The types are owned by other teams or plugins that cannot edit your visitors.

    - Adding an element type is expensive. The Visitor interface and every visitor change.
    - Visitors often need access to element internals, which weakens encapsulation.

## [concept] Visitor

**Put each operation over a set of types in its own object, with one method per type, so new operations need no edits to the types.**

A stack of infrastructure resources needs many operations: validate, render, estimate cost. With Visitor, each operation lives in one place, and the resource types stay small and stable.

<Depth level={2}>
The pattern trades one kind of change for another. A new operation is one new visitor. A new type edits every visitor. With a table of types against operations, a design can make adding columns or adding rows cheap, not both: the <Term id="expression-problem">expression problem</Term>. Visitor picks rows (operations), so use it where the types are stable.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Visitor as an object behavioral pattern for operations over an object structure, often a Composite. It names the mechanism <Term id="double-dispatch">double dispatch</Term>: the code that runs depends on two runtime types, the element's and the visitor's. Languages that only dispatch on the receiver get it from two calls, `accept` and then `visit`. The catalogue notes that languages with multiple dispatch, such as CLOS, need the pattern less, and that it can force elements to expose state the visitor reads.
</Depth>

## [problem] Every resource knows every operation

A deployment tool models infrastructure as typed resources: buckets, databases and networks that contain the others. Each type validates itself and renders itself into the plan the cloud provider receives.

Read it once. Every operation is spread across every type. Validation rules live in three files, and so does rendering.

<Depth level={2}>
Each resource type mixes concerns that change for different reasons. The database file holds naming rules, plan output and soon pricing, owned by three different people. The <Term id="open-closed">open/closed principle</Term> holds for new types here, not for new operations.
</Depth>

<Depth level={3}>
The network is a composite: its methods loop over the children. Every new operation repeats that loop, once per operation, in the network type.
</Depth>

## [pain] Then a change request arrives

**Change request:** Finance wants a monthly cost estimate for every stack before it deploys.

The marked lines add a cost method to the interface and to every resource type. Pricing is one concern, yet it ends up in four files, next to validation and rendering code it has nothing to do with.

<Depth level={2}>
Each edited file is owned and reviewed by someone else, and each change re-runs those types' tests. Next quarter brings a drift check and a security scan, and the same four files change again.
</Depth>

<Depth level={3}>
In Go, TypeScript and Rust, the build fails until every type implements the new method. That is helpful, but it means the cost feature cannot land in pieces: all four files ship together.
</Depth>

## [morph] Move each operation into a visitor

Drag the slider. Each operation leaves the resource types and becomes a visitor with one method per type. Each resource type keeps one small method that hands itself to the visitor.

Hover a box in the diagram to see its code.

<Depth level={2}>
Decide who walks the tree. Here the network's accept visits its children, so every visitor gets the traversal for free. Put the walk in the visitor instead when the order depends on results, such as skipping a subtree that failed validation.
</Depth>

<Depth level={3}>
<Lang only="go">Go has no overloading, so the methods are `VisitBucket`, `VisitDatabase` and `VisitNetwork`. Adding `VisitQueue` to the interface makes every visitor that lacks it fail to compile where it is passed as a `Visitor`.</Lang>
<Lang only="python">Python skips `accept`. The base class builds the method name from the resource's class, `visit_database`, and looks it up with `getattr`. It is less code, and a missing method shows up only at runtime.</Lang>
<Lang only="typescript">`Validate implements Visitor` makes the compiler check all three methods. Because types are structural, any object with those three methods is a visitor, with or without `implements`.</Lang>
<Lang only="rust">`accept` takes `&mut dyn Visitor`, so visitors can keep state, such as a list of errors, while the tree is walked by shared reference.</Lang>
</Depth>

## [walk] Follow one validation through the stack

One validation, from the plan command down to the database. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Each dispatch is an interface call through an <Term id="itab">itab</Term>: one on `Resource` to reach `Accept`, one on `Visitor` to reach `VisitDatabase`. Two indirect calls per node.</Lang>
<Lang only="python">`getattr` with a built string runs on every node. It is a dictionary lookup on the class, cheap next to the work a real check does, and easy to break with a typo in a method name.</Lang>
<Lang only="typescript">Both calls are property lookups on objects. While one call site only sees a few classes, V8's inline caches keep them fast.</Lang>
<Lang only="rust">Both calls go through vtables: `&dyn Resource` to reach `accept`, `&mut dyn Visitor` to reach `visit_database`. With an enum and `match`, there is no vtable at all: the compiler branches on the tag.</Lang>
</Depth>

## [lens] How each language writes it

Go, TypeScript and Rust can write the classic form with `accept`. Python looks visit methods up by name. In Rust and TypeScript, an <Term id="exhaustive-match">exhaustive match</Term> over an enum or a union often replaces the pattern entirely.

### When a match is the visitor

If the language has closed sum types, write the types as one enum or union and each operation as one function with a match: `fn cost(r: &Resource) -> f64 { match r { … } }` in Rust, or `switch (r.kind)` with a `never` check in TypeScript. Each operation still lives in one place, a new operation is still one new function, and a new type still flags every operation at compile time. That is Visitor's trade-off without `accept`, interfaces or <Term id="dynamic-dispatch">dynamic dispatch</Term>. Reach for a visitor trait or interface when the tree is large and most visitors only care about a few node types, as in `syn`.
