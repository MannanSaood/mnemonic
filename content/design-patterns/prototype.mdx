## [concept] Prototype

**Make new objects by copying a configured example, and let the object's own clone() decide which parts the copy gets fresh and which it shares.**

Only the object knows which of its parts are data to copy and which are services to share. Copying belongs to the object.

<Depth level={2}>
A <Term id="shallow-copy">shallow copy</Term> makes a new outer object whose fields still point at the original's nested objects. A <Term id="deep-copy">deep copy</Term> copies everything it can reach, including things that should be shared. Neither is right on its own. A job needs its own env map and the same HTTP pool as every other job. The prototype's `clone()` writes that decision down once, next to the fields.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Prototype as an object creational pattern. Its example is a graphical editor whose palette tools create notes by cloning an example note, so the framework never names the note classes. It suggests a prototype manager, a registry of examples by name, when the set of prototypes changes at runtime. It calls implementing clone the hardest part of the pattern, precisely because of the shallow versus deep copy question, and notes that some clones need re-initialising after the copy.
</Depth>

## [problem] Three places that copy a job

A job scheduler runs nightly billing for many tenants. Ops configure a template once in an admin UI, and the code makes each tenant's job by copying the template and changing a few fields. A backfill tool and a dry-run preview copy templates too.

Read it once. Each copy site knows that the env map must be copied separately. Someone learned that the hard way.

<Depth level={2}>
The knowledge "env is a map, copy it" lives in three functions, far from the struct that defines env. Each one must also know what *not* to copy: the HTTP client is shared on purpose.
</Depth>

<Depth level={3}>
<Lang only="go">In Go, `job := *t` copies the struct, but a map field is a pointer to the map's data. Two structs with the same map field share one map, and writes through either are seen by both.</Lang>
<Lang only="python">In Python, `copy.copy` creates a new instance whose attributes refer to the same objects. `job.env` and `t.env` are one dict until something replaces the attribute.</Lang>
<Lang only="typescript">In TypeScript, `{ ...t }` copies own properties one level deep. `job.env` and `t.env` are the same object until the spread is applied to `env` too.</Lang>
<Lang only="rust">In Rust there is no shared map to worry about here: cloning a `HashMap` copies it. The cost is visible instead. Each site writes out a full struct literal and has to remember to `Arc::clone` the client.</Lang>
</Depth>

## [pain] Then a change request arrives

**Change request:** jobs get a labels map for cost tracking.

Each copy site needs one more line. Miss one, and every job made there shares a single labels map with the template.

<Depth level={2}>
The miss is silent. A label set on one tenant's job appears on the template and on every job copied from it. The cost report quietly charges tenants for each other's runs. Tests that copy one job and check it pass.
</Depth>

<Depth level={3}>
<Lang only="rust">Rust's struct literals must name every field, so a missing `labels` is a compile error at each site. That is safe, but still three edits for one new field.</Lang>
<Lang only="go">Go's struct copy includes the new field automatically, which is exactly the problem: it is included as a shared map.</Lang>
<Lang only="python">`copy.copy` includes the new attribute automatically, as a reference to the template's dict.</Lang>
<Lang only="typescript">The spread includes the new property automatically, as a reference to the template's object.</Lang>
</Depth>

<Depth level={3}>
<Lang only="go">The `Clone` method sits next to the struct, so the next person to add a map field sees the method that must change. A test that clones, mutates the clone and checks the original is cheap insurance.</Lang>
<Lang only="python">`dataclasses.replace` creates the new instance through `__init__`, so `__post_init__` validation runs for clones too. Python 3.13 adds `copy.replace`, which calls the same machinery.</Lang>
<Lang only="typescript">`Object.create(JobConfig.prototype)` keeps the class, so the clone still has `clone()` and any other methods. A spread would return a plain object.</Lang>
<Lang only="rust">`#[derive(Clone)]` generates the method from the field list, so a new field is cloned with no further edits. The `Arc` field makes sharing explicit in the type.</Lang>

### Shallow, deep, or the object's own clone

A shallow copy shares every nested object, which causes <Term id="aliasing">aliasing</Term> bugs when the copy is changed. A deep copy shares nothing, which duplicates pools, caches and clients that should be shared, and fails on sockets and cycles. Python's own documentation lists that second problem. Write `clone()` on the class, copy what a copy may change, share what every copy should use, and test it.
