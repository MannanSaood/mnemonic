        // rule.go: one type per grammar rule; a rule is a tree of them
        type Expr interface{ Eval(u User) bool }

        type And []Expr
        type Or []Expr
        type Not struct{ X Expr }
        type In struct {
            Attr   string
            Values []string
        }
        type AtLeast struct {
            Attr string
            N    int
        }

        func (a And) Eval(u User) bool {
            for _, x := range a {
                if !x.Eval(u) {
                    return false
                }
            }
            return true
        }

        func (o Or) Eval(u User) bool {
            for _, x := range o {
                if x.Eval(u) {
                    return true
                }
            }
            return false
        }

        func (n Not) Eval(u User) bool     { return !n.X.Eval(u) }
        func (in In) Eval(u User) bool     { return slices.Contains(in.Values, u.Text(in.Attr)) }

        # rules.py: one class per grammar rule; a rule is a tree of them
        from dataclasses import dataclass
        from typing import Protocol

        class Expr(Protocol):
            def eval(self, u: User) -> bool: ...

        @dataclass
        class And:
            parts: list[Expr]
            def eval(self, u: User) -> bool:
                return all(p.eval(u) for p in self.parts)

        @dataclass
        class Or:
            parts: list[Expr]
            def eval(self, u: User) -> bool:
                return any(p.eval(u) for p in self.parts)

        @dataclass
        class Not:
            part: Expr
            def eval(self, u: User) -> bool:
                return not self.part.eval(u)

        @dataclass
        class In:
            attr: str
            values: set[object]

        type Expr =
          | { op: "and"; args: Expr[] }
          | { op: "or"; args: Expr[] }
          | { op: "not"; arg: Expr }
          | { op: "in"; attr: keyof User; values: unknown[] }
          | { op: "atLeast"; attr: keyof User; n: number };

    - role: Terminal expression
      example: In, AtLeast
      job: A leaf. Reads the input and answers directly.
    - role: Context
      example: The user being evaluated
      job: The input every node can read.
    - role: Client
      example: The flag service
      job: Gets the tree (built by a parser or decoded from JSON) and calls evaluate on its root.
  useWhen:
    - Rules change more often than the code, and the people changing them should not need a deploy.
    - The language is small, a handful of operators, and you can represent a sentence as a tree.
    - You need to do several things with the same rules, such as evaluate, print, validate or explain.
  avoidWhen:
    - The grammar is large. Use an existing language such as CEL, or a parser generator, instead of one class per rule.
    - Evaluation is on a hot path and the rules rarely change. Hard-code them or compile them.
  tradeoffs:
    - Parsing is a separate problem the pattern does not solve. JSON as the syntax avoids most of it.
    - Each new operation over the tree (print, check, explain) touches every node type, which is when Visitor helps.
    - Tree-walking is slower than compiled code. Compile once at save time if it matters.
    - A broken rule fails at runtime, often only for some inputs, unless the tree is checked when it is saved.
  lookalikes:
    - name: Composite
      how: The same tree of parts and wholes. Interpreter is a Composite whose nodes are rules of a language with an evaluate operation.
    - name: Visitor
      how: Moves operations such as evaluate, print and check out of the node types into separate objects, so adding an operation does not touch every node.
    - name: Strategy
      how: Swaps one fixed behaviour. Interpreter lets you build new behaviour by combining nodes.

## [concept] Interpreter

**Give each rule of a small language its own node type with an evaluate method, and run a sentence by evaluating its tree.**

A sentence such as `country in [DE, FR] and (plan = pro or seats >= 50)` becomes a tree of small objects. Each node evaluates itself by asking its children. A new sentence is a new tree, not new code.

<Depth level={2}>
The tree is an <Term id="abstract-syntax-tree">abstract syntax tree</Term>. Two kinds of node do the work. **Nonterminal** nodes (And, Or, Not) combine other expressions and evaluate them recursively. **Terminal** nodes (In, AtLeast) read the input, which the catalogue calls the context, and answer directly. All of them share one abstract **expression** type. Building the tree is a separate step. A parser can do it, or, as here, a JSON decoder.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Interpreter under class behavioural patterns, using regular expressions as its example. It says the pattern works best for simple grammars where efficiency is not critical. It notes that efficient interpreters usually translate the tree into another form first, such as a state machine for a regular expression. It also says the pattern does not address parsing. And it points to Visitor once you keep adding new operations over the same tree.
</Depth>

## [problem] A function per flag

A SaaS product ships features behind flags. Each flag's targeting rule is a Go, Python, TypeScript or Rust function in the flag service: which countries, which plans, how many seats, minus anyone who opted out of betas.

The code is fine. It is short, typed and tested. The rules just do not belong to the people who write it.

<Depth level={2}>
Sales, support and product ask for targeting changes every week: another country, a bigger seat threshold, one more customer. Each one is a code change, a review, a build and a deploy, done by an engineer who has to translate a sentence from a ticket into boolean logic.
</Depth>

<Depth level={3}>
The web and mobile apps also need the same rules to hide or show UI before they ask the server. With functions, each client gets its own copy of the logic in its own language, and the copies drift.
</Depth>

## [pain] Then a change request arrives

**Change request:** sales wants the new checkout in Japan too, for pro accounts or teams of 50 seats and up.

One marked line. The edit is trivial, and it still costs a ticket, a pull request, a review, a build and a deploy to every instance, plus a matching release of each client that copies the rule.

<Depth level={2}>
Multiply by forty flags and a few requests a week each. The flag service becomes a queue of one-line pull requests, and the people who own the rules wait on the people who own the code.
</Depth>

<Depth level={3}>
The ad hoc fix is to load the country list from config. Then the seat threshold, then the plan list, then a flag for whether it is "or" or "and". Each new knob is another special case in code. A small language with three or four operators covers all of them at once.
</Depth>

## [morph] Turn the operators into node types

Drag the slider. Each operator in the hard-coded function becomes a type: `&&` becomes And, `||` becomes Or, `!` becomes Not, and the comparisons become In and AtLeast. The rule itself moves out of the code into a tree of those types.

Hover a box in the diagram to see its code.

<Depth level={2}>
The node types change rarely, only when the language gains an operator. The trees change all the time and are stored as data. Every client that can decode the JSON and has the same few node types gets the same rule.
</Depth>

<Depth level={3}>
<Lang only="go">Each node type implements the one-method `Expr` interface. `And` and `Or` are slice types, so a rule literal reads almost like the sentence. Decoding from JSON needs a small custom `UnmarshalJSON` that looks at the `op` field and picks the type.</Lang>
<Lang only="python">Each node is a dataclass with an `eval` method, and `Expr` is a `Protocol`, so the nodes need no common base class. A parser for the JSON form is a dozen lines that look at `op` and build the right class.</Lang>
<Lang only="typescript">Here the nodes are not classes. A discriminated union describes the tree, and that union is also the JSON format. One `evaluate` function holds every node's behaviour. This is the Interpreter's structure with the operation pulled out of the nodes.</Lang>
<Lang only="rust">The enum is the grammar and `serde` builds the tree straight from JSON, using the `op` field as the tag. `Not` boxes its child; `And` and `Or` hold a `Vec<Expr>`, which already adds the indirection a recursive type needs.</Lang>
</Depth>

## [walk] Follow one evaluation

One user, one flag check. Step through it with the numbered buttons.

<Depth level={3}>
And and Or use <Term id="short-circuit-evaluation">short-circuit evaluation</Term>: an And stops at its first false child. Put cheap and selective checks first. A country check that fails for most users saves evaluating everything behind it. Short-circuiting also hides errors: a broken node is only reached by some users. Validate the whole tree when it is saved.
</Depth>

## [again] Japan, the second time

The same request, after the refactor. Someone with access to the flag store adds "JP" to the country list. No code changes, no build, no deploy, and every client that evaluates the tree sees the same rule.

<Depth level={2}>
Rules are now data, so treat them like data. Validate on save, keep a history so a bad rule can be rolled back, and let the people who own the rule preview who it matches before saving.
</Depth>

<Depth level={3}>
The engineering work moves to the language. Adding an operator such as `startsWith` is still a code change, in every evaluator. Keep the language small and stable, and push complexity into the trees, not into new operators.
</Depth>

### Before you write your own

Most teams should not invent a rule language. CEL (Common Expression Language) is used by Kubernetes and Google Cloud. JsonLogic is a small JSON format with libraries in many languages. Feature-flag products ship their own targeting rules. Write your own only when the language is tiny and you control every evaluator. Even then, borrow one of these formats so the rules outlive your code.
