    - Shared code knows when it needs an object and what to do with it, but not which class to create.
    - Other teams or users extend your code, and you want them to add variants without editing or copying it.

    - In class-based languages, each product can need its own creator subclass.

    - The product interface must cover what the creator needs from every variant.
  lookalikes:
    - name: Abstract Factory
      how: An object whose several factory methods create a family of related products that must match. Factory Method is one method making one product.
    - name: Template Method
      how: A fixed algorithm with steps subclasses fill in. A factory method is often one of those steps; its only job is to create an object.
    - name: Strategy
      how: Swaps how a step is done. A factory method only decides which object to create; what the object then does is up to it.
    - name: Simple factory
      how: One function with a switch that returns the right class. Useful, and often enough, but every new variant edits that function.

## [concept] Factory Method

**Let the code that runs a job ask a method for the object it needs, and let each variant of the job decide which class that method creates.**

The code that *uses* the object should not have to name its concrete class. It knows *when* it needs one and what to do with it. Somebody else decides *which* one.

<Depth level={2}>
Four roles. The <Term id="creator-role">creator</Term> (`ExportJob`) does the real work and calls the **factory method** whenever it needs an object. The <Term id="product-role">product</Term> (`RowWriter`) is the <Term id="interface">interface</Term> the creator works with. Each **concrete creator** supplies the factory method for one variant, and returns a **concrete product** such as `ParquetWriter`.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Factory Method as a *class* creational pattern, because it varies the created class through inheritance, and gives it a second name, Virtual Constructor. Its motivating case is a framework that must create documents but only knows the abstract document class. The book names the cost too: you may end up subclassing the creator just to choose a product. Languages with <Term id="first-class-function">first-class functions</Term> usually avoid that cost by passing the factory in.
</Depth>

## [problem] An export job that names every writer

A data platform runs nightly exports for customers in CSV, JSON or Parquet, chosen per customer in config. The same job also renders a 100-row preview in the UI.

Read it once. The list of writer classes appears three times: in Run, in Preview and in the config list.

<Depth level={2}>
Run and Preview each build their own writer. Both switches have to stay identical, or the preview shows one format while the export delivers another.
</Depth>

<Depth level={3}>
The job also depends on every writer library at once. A Parquet writer pulls in a columnar encoding library, and the export job imports it even for customers who only ever get CSV.
</Depth>

## [pain] Then a change request arrives

**Change request:** Finance needs the nightly export as XLSX.

The marked lines must change, in three places. None of them is about writing a spreadsheet. They are about choosing a class.

<Depth level={2}>
Now suppose the job belongs to a platform team and Finance's request comes from the Billing team. Billing cannot add a case without a PR into code it does not own, and the platform team becomes a queue for every new format in the company.

<Depth level={3}>

## [morph] Move the choice into one method

Drag the slider. Both switches collapse into one method that creates the writer, and each format moves out into its own creator.

Hover a box in the diagram to see its code.

<Depth level={2}>
The job now depends on the `RowWriter` interface and on one creation method. A new format extends the job without editing it, the <Term id="open-closed">open/closed principle</Term> applied to object creation. Run and Preview share the method, so they cannot disagree about the format.
</Depth>

<Depth level={3}>
<Lang only="go">Go has no inheritance, so the factory method becomes a function value stored in the job. Function types must match exactly: `NewCSVWriter` has to return `RowWriter`, not `*csvWriter`, to fit `WriterFactory`.</Lang>
<Lang only="python">`@abstractmethod` stops anyone from creating a bare `ExportJob`: Python raises `TypeError` when you call `ExportJob(schema)`. The check happens when the object is created, not when the method is called.</Lang>
<Lang only="typescript">`protected abstract` makes the compiler reject any subclass that forgets `createWriter`, and keeps outside code from calling it directly.</Lang>
<Lang only="rust">The trait holds both halves: `create_writer` has no body, so every job type must write one, and `run` and `preview` have default bodies that every job type gets for free.</Lang>
</Depth>

One Parquet export through the design, start to finish. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`j.NewWriter(out, j.Schema)` is an indirect call through a function value. The compiler cannot inline it, which costs nanoseconds per export, not per row.</Lang>
<Lang only="python">`self.create_writer(out)` looks the method up on the object's class first, so `ParquetExport`'s version wins over the abstract one. That lookup follows the class's method resolution order.</Lang>
<Lang only="typescript">`this.createWriter` is looked up along the prototype chain at runtime. `ParquetExport.prototype` has its own `createWriter`, so the base version is never reached.</Lang>
<Lang only="rust">Through `Box<dyn ExportJob>`, the call to `run` goes through a vtable, and inside the default `run`, `self.create_writer` does too: <Term id="dynamic-dispatch">dynamic dispatch</Term> on both calls.</Lang>
</Depth>

## [again] XLSX, the second time

The same request after the refactor. You add one creator that makes an XLSX writer, and register it in the map. The job itself does not change, so Run and Preview pick up the new format together.

<Depth level={2}>
The map from a config string to a creator is a parameterized factory, and it is the one place left that names every format. Keep it next to `main`. The catalogue describes this variant too: a factory method that takes an identifier and returns the matching product.
</Depth>

<Depth level={3}>
Tests get the same seam. A test creator can return an in-memory writer, so `Run` can be tested without a disk, a bucket or a Parquet library. Michael Feathers calls this move Extract and Override Factory Method.
</Depth>

### A factory method or a factory function?

A factory function picks a class from a parameter, and every new variant edits it. A factory method lets each variant supply its own creation code, and nothing shared is edited. Start with the function when you own all the variants. Move to the method, or to passing a constructor in, when other people need to add variants to code they cannot change.
