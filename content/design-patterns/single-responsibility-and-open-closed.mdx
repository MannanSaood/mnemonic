## [concept] Single responsibility and open/closed

**Keep code that different people ask to change in different modules. Then make each module grow by adding code, not by editing it.**

The <Term id="single-responsibility">single responsibility principle</Term> says where the lines between modules go: around each <Term id="actor">actor</Term>, the group of people who ask for one kind of change. The <Term id="open-closed">open/closed principle</Term> says what a good line looks like: new variants arrive as new code behind an <Term id="interface">interface</Term>, and the code that already works stays closed.

<Depth level={2}>
The two principles answer two different change problems. SRP stops one team's change from landing in another team's code: no shared merges, no surprise regressions. OCP stops a stream of new variants, like countries with their own tax, from editing a switch that already works for every other country. Both are judged by the changes you actually get, so apply them where change keeps arriving, not everywhere.
</Depth>

<Depth level={3}>
Bertrand Meyer named the open/closed principle in *Object-Oriented Software Construction* (1988), where the mechanism was inheritance. Robert C. Martin restated it around abstract interfaces in the 1990s and made it part of SOLID. He has phrased the SRP several ways: first as "one reason to change", then, because "reason" was misread, as "responsible to one, and only one, actor" in *Clean Architecture* (2017). He is explicit that "a function should do one thing" is a different, lower-level rule.
</Depth>

## [problem] One class, three teams

An invoice service computes the total with tax, renders a PDF and emails it. All three live in one class, and the class works.

Read it once. Three groups of people care about this file: Finance about `Total`, Brand about the PDF, Customer Ops about the email.

<Depth level={2}>
The tax switch has a case per country. Every new country edits it, and each edit re-tests every country that already works. The PDF also calls `Total`, so the PDF's tests depend on tax rules too.
</Depth>

<Depth level={3}>
Nothing here is wrong in a one-person project. The cost appears with parallel work: two teams editing the same file in the same sprint get merge conflicts, and a change one team asks for can alter what another team ships without anyone on that team asking.
</Depth>

## [pain] Then a change request arrives

**Change request:** in the same sprint, Finance adds Canadian tax and Brand puts the new logo on the invoice PDF.

Two teams, two unrelated changes, one file. The marked lines collide in review, and the Canada case edits a switch that already handles real money for Germany and France.

<Depth level={2}>
Each team now has to review the other's change, and each deploy carries both. If Brand's release is rolled back because the logo renders badly, Finance's Canada tax rolls back with it.
</Depth>

<Depth level={3}>
This is what Martin calls the merge symptom: different actors' code in one file means different people changing the same file for different reasons. Version control can merge most text, but it cannot tell you that two correct changes are wrong together.
</Depth>

## [morph] Split by team, then open the tax rules

Drag the slider. InvoiceService splits into three types, one per team, and the tax switch becomes a TaxRule interface with one implementation per kind of rule.

Hover a box in the diagram to see its code.

<Depth level={2}>
The split follows who asks for changes. That is why the PDF and the mailer are separate even though both are small, and why `VAT` serves both Germany and France: they differ only in a number, so they are one rule with two settings.
</Depth>

<Depth level={3}>
<Lang only="go">Go draws the clearest lines at package level. If each team's code is its own package, Go's build cache only recompiles the packages a change actually reaches.</Lang>
<Lang only="python">A `Protocol` is checked by mypy or pyright, not at runtime. `VAT` matches `TaxRule` because it has an `apply` method with the right signature; it never inherits from `TaxRule`.</Lang>
<Lang only="typescript">`vat(19)` returns a plain object that matches `TaxRule` by shape. No class is needed for a rule with no state beyond its rate.</Lang>
<Lang only="rust">`Box<dyn TaxRule>` lets the map hold different rule types side by side. If the rules were fixed at compile time, an `enum` with exhaustive `match` would be simpler; the trait is for rules added from outside the module.</Lang>
</Depth>

The call path is longer than before: three objects instead of one. Each hop is a direct method call except the last, which goes through the TaxRule interface. The extra cost is nanoseconds next to rendering a PDF and talking to a mail server.

## [again] The same sprint, the second time

Finance adds `CanadaTax` in a new file. Brand changes the logo in `InvoicePdf`, a file Finance never opens. The two pull requests touch no file in common, so they cannot conflict, and neither can break the other.

<Depth level={2}>
One line of wiring remains: `main` registers `"CA"`. Keep all registration in one place and it stays one line. That place is meant to know every concrete rule; the calculator is not.
</Depth>

<Depth level={3}>
Tests follow the split. `CanadaTax` gets its own table of provinces and expected totals. The calculator's tests use a fake rule and never change when a country is added, and the PDF's tests use a calculator with one simple rule.
</Depth>

### Code that looks the same is not always the same

The hardest part of the SRP is resisting a merge. When two teams' code contains the same few lines, it is tempting to share one helper. If the two teams can want different things from those lines, keep two copies. Martin calls the shared version <Term id="accidental-duplication">accidental duplication</Term>: it saves a few lines today and couples two teams for good.
