    - You want callers to stay the same when the storage changes, from a slice to pages to a database cursor.
  avoidWhen:

      how: Runs an operation on each element of a structure. An iterator only hands the elements out; the loop decides what to do.
    - name: Observer
      how: The source pushes each new event to subscribers as it happens. An iterator hands out elements when the consumer asks.

## [concept] Iterator

**Give callers a way to walk a collection one element at a time, without showing them how it is stored or fetched.**

The loop asks for the next element. Whether it comes from memory, from the next page of an API or from a database cursor is the iterator's business.

<Depth level={2}>
Four roles. The **iterator** answers one question: what is the next element, if any. The **concrete iterator** keeps the position, here the current page and the token for the next one. The **aggregate** (the API client) creates iterators. The **client** loops and decides when to stop. Because the iterator only does work when asked, it is <Term id="lazy-evaluation">lazy</Term>: a loop that stops early stops the fetching too.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue also calls it Cursor. Its consequences are that the same collection can be walked in different ways, that the collection's own interface stays small, and that several traversals can be in progress at once because each iterator keeps its own state. It separates external iterators, where the client asks for each element, from internal ones, where the iterator calls the client's code for each element. Today these are called pull and push iterators (<Term id="push-pull-iterator">push and pull</Term>).
</Depth>

## [problem] A client that loads every invoice

The billing API returns invoices 100 at a time, with a token for the next page. The client hides the paging: `ListAll` fetches every page into one list and returns it. The export loops over the list.

Read it once. For a few thousand invoices it is fine, and the callers never see a page token.

<Depth level={2}>
Every caller pays for every page, whether it needs them or not. The loop cannot start until the last page has arrived, and the whole list sits in memory while it runs.
</Depth>

<Depth level={3}>
An error on the last page throws away the work of every page before it. The function returns nothing but the error, so a caller cannot even keep what was fetched.
</Depth>

## [pain] Then a change request arrives

**Change request:** the dashboard needs only the 20 newest invoices, and the nightly export must cope with 2 million of them.

The marked lines add a `limit` parameter for the dashboard. The export still holds 2 million invoices in memory, and fixing that needs a second function with a callback or a page loop in every caller.

<Depth level={2}>
Each new kind of caller asks for its own variant: stop after n, stop at the first match, stop on the first error, skip drafts. The list-returning function grows a parameter per caller, or the paging logic gets copied out to all of them.
</Depth>

<Depth level={3}>
At 2 KB an invoice, 2 million invoices are about 4 GB before the export writes a line. On a worker with a memory limit, the job is killed partway through and retried, and killed again.
</Depth>

## [morph] Turn the list into an iterator

Drag the slider. The list disappears. The client returns an iterator that keeps one page and a cursor, and fetches the next page only when the loop reaches the end of the current one.

Hover a box in the diagram to see its code.

<Depth level={2}>
The callers keep their loops; only what they loop over changes. Each caller stops when it has what it needs, and the iterator stops with it. Memory holds one page whatever the total. An error arrives in the loop at the point where it happened, after the earlier invoices were processed.
</Depth>

<Depth level={3}>
<Lang only="go">Go's range-over-func turns the loop body into the `yield` function. The compiler rewrites `break` and `return` inside the body so that `yield` returns false, and the iterator must return when it does. That is why the inner loop checks `!yield(...)`.</Lang>
<Lang only="python">A <Term id="generator">generator</Term> keeps its local variables, `token` and `page`, in a suspended frame between calls to `next()`. That frame is the concrete iterator, written for you by the language.</Lang>
<Lang only="typescript">An async generator keeps its local variables in a suspended frame between calls to `next()`, and each `next()` returns a promise. `yield*` delegates to the page array one element at a time.</Lang>
<Lang only="rust">The struct is the concrete iterator, written out by hand: the current page as a `vec::IntoIter`, and the cursor. It borrows the client for `'a`, so the borrow checker stops the client from being dropped while an iteration is in progress.</Lang>
</Depth>

<Depth level={2}>
Iterators make each loop step potentially slow, because it may be a network call. When throughput matters, fetch the next page while the loop works on the current one. Do it inside the iterator, so callers still see one invoice at a time.
</Depth>

<Depth level={3}>
The iterator must page correctly when data changes underneath it. With newest-first ordering, new invoices push every row down, so `?offset=200` returns rows that were on the previous page. <Term id="cursor-pagination">Cursor pagination</Term> asks for rows after the last one seen, and stays correct. The catalogue calls this the robustness of an iterator.
</Depth>

The same request after the refactor. The dashboard takes 20 invoices and stops; the iterator fetched one page. The export walks all 2 million invoices holding one page at a time. Nothing in the client changed.

<Depth level={2}>
Combinators replace the `limit` parameter. Taking the first n, filtering, and stopping at the first match are loop logic or library functions over any iterator, so the client does not need to know about any of them.
</Depth>

<Depth level={3}>
An iterator that holds a resource must release it when the loop ends early. A Go push iterator does it naturally, with `defer` inside the function. Python generators run their `finally` blocks when closed, JavaScript generators when `return()` is called, and Rust iterators when dropped. Go's `iter.Pull` is the exception: you must call `stop`.
</Depth>

### Push or pull

There are two ways to hand out elements. A pull iterator waits to be asked: Python's `next()`, JavaScript's `next()`, Rust's `Iterator::next`, Go's `bufio.Scanner`. A push iterator calls your code for each element: Go 1.23's `iter.Seq` and the old `forEach` callbacks. Pull iterators are easier to combine, for example to walk two sequences in step. Push iterators are easier to write, because the traversal is ordinary code with its own local variables and `defer`. Go's `iter.Pull` converts a push iterator to a pull one when you need both.
