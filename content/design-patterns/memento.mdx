  deep:
    question: A gateway config with 50,000 routes is saved before each of 200 changes a day. Which keeps both the memory and the time to restore any version small?
    options:
      - text: Store the routes in a persistent map, so each snapshot shares every unchanged entry with the previous one.
        correct: true
        why: Right. Each save costs about as much as the changed entries, like a diff, and a restore is a pointer swap, like a full snapshot. Clojure's maps, Immutable.js and Rust's im crate work this way.

        why: Memory is small, but restoring a version from the morning means replaying every diff since, in order, and one bad diff breaks every restore behind it.
      - text: Store full snapshots, compressed.
        why: Each save still walks and copies 50,000 entries, and each restore decompresses them. Compression cuts the bytes kept, not the work per save.

reference:
  roles:
    - role: Originator
      example: Config
      job: Makes snapshots of its own state and restores itself from them. The only code that reads a snapshot.
    - role: Memento
      example: { go: "Snapshot (unexported fields)", python: "Snapshot (frozen dataclass)", typescript: "Snapshot (branded type)", rust: "Snapshot (private fields)" }
      job: Holds the saved state. Opaque to everyone except the originator.
    - role: Caretaker
      example: Deployer
      job: Asks for snapshots, keeps them in order and hands them back. Never looks inside.
  useWhen:
    - You need rollback, undo or checkpoints, and the object's internals should stay private.
    - The state has parts that need care to copy, such as maps, lists or nested objects.
    - The fields change over time, and the history code lives somewhere else.
  avoidWhen:
    - The state is small and already immutable. Keep the old value; it is the snapshot.
    - Each change has a cheap, exact inverse. An undo command is lighter than a copy of the whole state.
  tradeoffs:
    - Full snapshots cost memory in proportion to state size times history length.
    - Diffs are small but restore by replaying in order, and every diff in the chain must be correct.
    - The caretaker cannot tell how big a snapshot is, so it needs a limit on history length.
    - In Python and JavaScript the opacity is a convention or a type trick, not something the runtime enforces.
  lookalikes:
    - name: Command
      how: Undoes by running an inverse operation instead of restoring saved state. The two combine when an inverse is hard to compute.
    - name: Prototype
      how: Clones an object to create a new one. Memento copies state in order to return the same object to it later.
    - name: Event sourcing
      how: Rebuilds state by replaying a log of changes, the diff end of the same trade-off. Snapshots are often added to it to shorten the replay.

## [concept] Memento

**Let an object hand out a sealed snapshot of its own state, so others can store it and give it back later without reading it.**

Whoever keeps the history only holds the snapshots. Only the object that made a snapshot knows what is inside and how to restore it.

<Depth level={2}>
Three roles. The **originator** (`Config`) makes snapshots and restores itself from them. The **memento** (`Snapshot`) holds the saved state and shows nothing to anyone else. The **caretaker** (`Deployer`) asks for snapshots before risky changes, keeps them in order, and hands one back to roll back. The caretaker decides when; the originator decides what.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue lists Memento under object behavioural patterns, also known as Token. It describes two interfaces on the memento: a wide one for the originator and a narrow one, little more than "hold me", for everyone else. It warns that snapshots can be expensive and that a caretaker cannot see how much it is storing. It also suggests storing only the incremental change when snapshots are restored in a predictable order, as with an undo history.
</Depth>

## [problem] A rollback that copies fields

An API gateway reads its routing config from a config object. The deploy tool supports rollback: before each change it copies the config's fields into its own history, and to roll back it writes them back.

To make that possible, the config exposes its fields. The deploy tool now depends on exactly which fields a config has.

<Depth level={2}>
Look at how the routes are saved. In Go, Python and TypeScript, assigning a map copies a reference to it, not its contents. Every saved entry points at the live map, so an edit made in place changes every snapshot too. Rolling back a route change restores nothing. Timeout rollbacks work, because a number is copied by value, and that is the case the tests happened to cover.
</Depth>

<Depth level={3}>
<Lang only="rust">In Rust the aliasing bug cannot compile: holding a reference into `self.cfg` while `change` mutates it is rejected by the borrow checker, so the deploy tool has to `clone()`. The other bug remains. The snapshot covers only the fields the tool knew about when it was written.</Lang>
<Lang only="go">The fix looks easy, `maps.Clone(d.cfg.Routes)`. But the deploy tool would have to know, for every field, whether it is a value or holds a reference. It would have to stay right as the config changes in another package.</Lang>
<Lang only="python">The fix looks easy, `dict(self.cfg.routes)` or `copy.deepcopy`. But the deploy tool would have to know, for every attribute, how deep to copy. It would have to stay right as the config class changes in another module.</Lang>
<Lang only="typescript">The fix looks easy, `new Map(this.cfg.routes)` or `structuredClone`. But the deploy tool would have to know, for every field, how deep to copy. It would have to stay right as the config class changes in another module.</Lang>
</Depth>

## [pain] Then a change request arrives

**Change request:** the gateway config gets per-route rate limits, and rollback must restore them too.

The config team adds one field. The marked lines show what else must change, and they sit in another team's code: the saved record, the save, and the restore.

<Depth level={2}>
Nothing forces anyone to make those edits. The config change compiles and ships, the deploy tool keeps working, and rollbacks quietly stop restoring rate limits. Someone notices during an incident, when a bad limit cannot be rolled back.
</Depth>

<Depth level={3}>
The exposed fields are also a cost of their own. Any code can now write `Routes` or `Timeout` directly and skip the matcher rebuild. The fields were made public only for the rollback, and every other caller gets that access too.
</Depth>

## [morph] Let the config make its own snapshot

Drag the slider. The fields go private again. The config gains `Save` and `Restore`, the snapshot becomes a sealed value, and the deploy tool only stores it.

Hover a box in the diagram to see its code.

<Depth level={2}>
The deploy tool now depends on two methods and one opaque type. It cannot copy a field wrongly, because it copies nothing. The config decides which fields need a deep copy, which can be rebuilt instead of saved (the matcher), and whether to store a full copy or a diff.
</Depth>

<Depth level={3}>
<Lang only="go">Opacity comes from Go's package rule: the deploy package can hold a `gateway.Snapshot`, pass it around and hand it back, but cannot name its lowercase fields.</Lang>
<Lang only="python">Python has no access control. The leading underscores and the docstring state the rule, and type checkers and reviewers enforce it. `frozen=True` stops reassignment of the snapshot's fields, not mutation of the dict inside.</Lang>
<Lang only="typescript">The branded `Snapshot` type has no readable fields, so the compiler stops the deploy tool from reading it. At runtime it is still a plain object, so the opacity is a compile-time agreement.</Lang>
<Lang only="rust">Rust's privacy is per module, so `deploy` can store a `Snapshot` but not read `routes` or `timeout`. `#[derive(Clone)]` lets the caretaker duplicate a snapshot if it needs to, still without seeing inside.</Lang>
</Depth>

## [again] Rate limits, the second time

The same request, after the refactor. The new field, its copy in `Save` and its restore all live in the config's own file. The deploy tool does not change and cannot be forgotten.

<Depth level={2}>
Review is easier too. Whoever adds a field sees `Save` and `Restore` a few lines below, and a test in the same package can check that a save and restore round-trips every field.
</Depth>

<Depth level={3}>
Snapshots of old versions can outlive a deploy if the history is persisted. Once snapshots are stored or sent elsewhere, version their format, because a newer config may have to restore a snapshot made by an older one.
</Depth>

### Snapshots, diffs, or both

A full snapshot restores in one step but costs memory for every change. A diff costs little memory but restores by replaying, in order, every diff back to the target. Most real systems mix them: databases write a log of changes plus periodic checkpoints, and editors keep diffs with a full copy every so often. A <Term id="persistent-data-structure">persistent data structure</Term> gets close to both at once, since each version shares its unchanged parts with the last.
