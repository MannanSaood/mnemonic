# ---------------------------------------------------------------- checks
checks:
  overview:
    question: Which of these situations calls for a Template Method?
    options:
      - text: Three report exporters all open a file, write a header, write the rows and close it. Only the way one row is written differs.
        correct: true
        why: Right. The sequence is the same for all three and only one step varies. Write the sequence once and let each exporter supply its row writer.
      - text: A checkout must pay through Stripe, PayPal or Adyen, chosen from config for each region.
        why: That is Strategy. The whole payment step is swapped, and the caller picks which one at runtime.
      - text: An infrastructure tool needs cost estimates, validation and rendering over a fixed set of resource types, without editing those types.
        why: That is Visitor. It adds new operations over a set of types. Template Method fixes one operation's steps and varies some of them.
  engineer:
    question: Bank statements must have their opening balance checked before loading. The other importers have no balances. What is the cleanest change?
    options:
      - text: Add a before_load hook with an empty default to the base, call it in run, and override it in the statement importer.
        correct: true
        why: Right. The order stays in one place, the other importers are untouched, and the extension point is named. The cost is an edit to the shared run method.
      - text: Override run in the statement importer, copy its body and add the check in the middle.
        why: That re-creates a copy of the pipeline. The next fix to the shared run will miss bank statements, which is the drift the pattern removed.
      - text: In the base run, check whether self is a statement importer and call the balance check if so.
        why: Now the base knows its subclasses by name. Each special case adds another branch to code that every importer runs.
  deep:
    question: In Python, a developer overrides the hook as before_lod, a typo for before_load. What happens when the statement importer runs?
    options:
      - text: The import succeeds. run calls the base's empty before_load, and the balance check never runs.
        correct: true
        why: Right. ABC only checks that abstract methods exist; before_load is not abstract, so the typo is just a new, unused method. `@typing.override` (Python 3.12) lets a type checker catch it. Rust rejects a method that is not in the trait, and TypeScript catches it with the `override` keyword and `noImplicitOverride`.
      - text: Creating a StatementImporter raises TypeError, because ABC sees a method the base does not declare.
        why: No. ABC raises TypeError only when an abstract method is missing. Extra methods are allowed.
      - text: run raises AttributeError when it reaches before_load.
        why: No. The base class defines before_load, so the lookup finds the empty default.

    - role: Hook
      example: before_load
      job: An optional step with a default, usually empty. Variants may override it.
    - role: Concrete class
      example: "CSV, JSON, Statement"
      job: Supplies the primitive steps, and overrides hooks when it needs to.
    - role: Client
      example: the scheduler
      job: Calls the template method. Never calls the steps one by one.
  useWhen:
    - Several variants run the same steps in the same order and differ in one or two of them.
    - Copies of a pipeline have started to drift, and fixes land in one copy but not the others.
    - A framework must keep control of the order, such as setup before a test and teardown after it.
  avoidWhen:
    - The variants differ in more steps than they share. The template becomes a list of hooks, and the order it enforces means little.
    - You need to swap the behaviour at runtime or combine variants. Pass the step in as a function or strategy instead.
    - There are only two variants and little shared code. A small helper function is enough.
  tradeoffs:
    - The order of steps is fixed for every variant. A variant that needs a different order or an extra step forces an edit to the template.
    - With inheritance, subclasses depend on the base's internals, and a change to the base can break them (the fragile base class problem).
    - Readers must jump between the base and the subclass to follow one run.
    - Hooks fail silently when misnamed or when the template never calls them.
  lookalikes:
    - name: Strategy
      how: Swaps a whole step by passing in an object, chosen at runtime. Template Method varies part of an algorithm through inheritance or a trait, fixed when the type is written.
    - name: Factory Method
      how: A factory method is often one of the steps a template method calls. It is a template step whose job is to create an object.
    - name: Composition over inheritance
      how: The Go form of this pattern, a function that takes an interface of steps, is Template Method built by composition. It keeps the fixed order without a base class.

## [concept] Template Method

**Write the order of an algorithm's steps once, and let each variant fill in only the steps that differ.**

The base owns the sequence. Each variant supplies the few steps that are its own, and gets the rest, including every future fix to them, for free.

<Depth level={2}>
The method that runs the sequence is the <Term id="template-method-role">template method</Term>. The steps every variant must write are <Term id="primitive-operation">primitive operations</Term>. Steps a variant may change but does not have to are <Term id="hook-method">hooks</Term>, with a default that usually does nothing. Control is inverted: the base calls the variant's code, not the other way round. This is the <Term id="hollywood-principle">Hollywood principle</Term>.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Template Method as a class behavioral pattern, because it varies behaviour through subclassing. It contrasts it with Strategy: a template uses inheritance to vary part of an algorithm, a strategy uses delegation to vary all of it. The catalogue also says the template method itself should not be overridden, and that a good template asks subclasses for as few primitive operations as possible. Languages without class inheritance get the same shape another way: a Go function that takes an <Term id="interface">interface</Term>, or a Rust trait with default methods.
</Depth>

## [problem] Three importers, written one after another

A finance service imports transactions from partners. The CSV importer came first. When a partner sent JSON, someone copied it and swapped the parser. Bank statements came later, copied again.

Read the three. They all open a file, parse it, validate the rows, convert them to ledger entries and load them. Only the parse call differs. And the statement copy has already drifted: it no longer checks the date.

<Depth level={2}>
Nobody chose to drop the date check. The statement importer was copied from an older version, or someone simplified it while fixing something else. Copies drift because each one is maintained on its own, by whoever got the ticket.
</Depth>

<Depth level={3}>
The copies are also tested separately. A test that a row with a missing date is rejected exists for CSV and JSON, and passes. The same test was never written for statements, so nothing shows that the copies disagree.
</Depth>

## [pain] Then a change request arrives

**Change request:** Finance found duplicate transactions in the ledger. Every importer must skip rows whose transaction id it has already loaded.

The ticket names the CSV importer, because that is where the duplicate was spotted. The fix belongs in all three copies, and the statement copy needs a different edit, because it has drifted.

<Depth level={2}>
Fix CSV and the ticket closes. Tests pass. Next month the same duplicates arrive through a bank statement, and someone opens a new ticket for a bug that was already fixed once. Each copy turns one bug into several, found one at a time.
</Depth>

<Depth level={3}>
Search does not save you either. The copies use different names and shapes (a loop in one, a filter or comprehension in another), so a grep for the old condition finds some of them and not all.
</Depth>

## [morph] Pull the shared steps into one template

Drag the slider. The three pipelines collapse into one template method. Each importer shrinks to the one step that is really its own: parse.

Hover a box in the diagram to see its code.

<Depth level={2}>
Make the varying steps as few as possible. Here only parse varies; validate, transform and load are shared. Every step you make overridable is one more way for an importer to drift, so start with none and add a hook when a real importer needs one.
</Depth>

<Depth level={3}>
<Lang only="go">Go has no inheritance, so there is no base class. The template is a plain function, `Import`, and the varying step is a one-method interface. Nobody can override `Import`, so the order is truly fixed. An optional hook is a second interface the function checks with a type assertion, the way `io.Copy` looks for `WriterTo`.</Lang>
<Lang only="python">`Importer` is an abstract base class. Python raises `TypeError` when you instantiate a subclass that has not implemented `parse`, so a forgotten step fails when the importer is created, not halfway through a file.</Lang>
<Lang only="typescript">`Importer` is an abstract class and `parse` is `protected abstract`. The compiler rejects a concrete subclass that does not implement it, and callers outside the class hierarchy cannot call the steps directly.</Lang>
<Lang only="rust">`Importer` is a trait. `parse` is a required method; `validate`, `before_load` and `run` are provided methods with default bodies. The compiler rejects an `impl Importer` that leaves out `parse`.</Lang>
</Depth>

## [walk] Follow one bank statement

One statement through the template, from the scheduler to the ledger. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`f.Parse(raw)` is a call through an interface: Go loads the method from the <Term id="itab">itab</Term> and calls it indirectly. `validate` is an ordinary function call that the compiler can inline.</Lang>
<Lang only="python">`self.parse` is looked up on the instance's class first, following the method resolution order, so the subclass's `parse` wins. The lookup happens on every call; there is no table built ahead of time.</Lang>
<Lang only="typescript">`run` lives on `Importer.prototype` and `parse` on `StatementImporter.prototype`. `this.parse` walks the prototype chain from the instance and finds the subclass's method first.</Lang>
<Lang only="rust">Called on a concrete `Statement`, `run` is compiled for that type, and its call to `parse` is static and can be inlined. Through a `&dyn Importer`, the provided methods sit in the vtable next to the required one, and every call goes through it.</Lang>
</Depth>

### When the template is just a function

If only one step varies, you may not need a class at all. A function that takes the varying step as a function argument, `run_import(path, parse=parse_csv)`, is Template Method without inheritance. It keeps the order in one place and is easier to read. Move to a base class or trait when there are several steps to supply, or hooks with defaults.
