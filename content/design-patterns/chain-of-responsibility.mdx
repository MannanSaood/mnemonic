        type Handler interface {
            Handle(t Ticket) (Desk, bool)
        }

        type Chain []Handler

        func (c Chain) Assign(t Ticket) (Desk, error) {
            for _, h := range c {
                if d, ok := h.Handle(t); ok {
                    return d, nil
                }
            }
            return nil, fmt.Errorf("ticket %d: %w", t.ID, ErrUnhandled)

    - role: Handler
      example: { go: "Handler (interface)", python: "Handler (a Callable type)", typescript: "Handler (function type)", rust: "Handler (trait)" }

    - role: Concrete handler

      job: Knows one rule, and nothing about the other handlers.
    - role: Chain
      example: "Chain (a list), or each handler's successor"
      job: Offers the request to each handler in order, and decides what happens when nobody takes it.
    - role: Client
      example: intake
      job: Builds the chain and sends requests into it.
  useWhen:
    - Several objects could handle a request and the request itself decides which one does.
    - The set or order of handlers differs by configuration, customer or environment.
    - Each step of a pipeline may stop the request, as in HTTP middleware and validation.
  avoidWhen:
    - The rules are few, fixed and read best side by side. A switch or a decision table is clearer.
    - Every handler must see every request. That is Observer, or a plain pipeline.
    - Handlers depend on each other's decisions. A chain hides those dependencies in its order.
  tradeoffs:
    - Nothing guarantees a request is handled. You must design the end of the chain.
    - The order is policy, and it is not visible inside any one handler.
    - Finding out who handled a request takes logging; the code no longer says.
    - A request may visit many handlers before one takes it.
  lookalikes:
    - name: Decorator
      how: Wraps an object and always calls it, adding behaviour around it. A chain handler usually stops the request instead of passing it on.
    - name: Observer
      how: Every subscriber gets the event. In a chain, the first handler that takes the request ends it.
    - name: Command
      how: Makes the request an object. The thing travelling down a chain is often a command.

## [concept] Chain of Responsibility

**Pass a request along a line of handlers. Each one either handles it or passes it to the next, so the sender never has to know who will take it.**

Each handler knows one rule. The chain decides the order in which the rules are tried.

<Depth level={2}>
Three parts make a chain. The **handler** is a one-method <Term id="interface">interface</Term>: take this request, or say no. Each **concrete handler** knows one rule and nothing about the others. The **chain** offers the request to each handler in turn, or each handler holds a link to its <Term id="cor-successor">successor</Term>. The **client** builds the chain and sends requests into it.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files it under object behavioral patterns. Its benefits are reduced coupling, because the sender knows only the first link, and the freedom to add or rearrange handlers at runtime. Its main liability is that receipt is not guaranteed: a request can fall off the end of the chain without being handled, including when the chain is wired wrong. The book also notes that a chain can reuse links that already exist, such as each widget's parent in a UI tree.
</Depth>

## [problem] One function that routes every ticket

A support system assigns each new ticket to a desk: the help bot, Tier 1, Tier 2 billing or the engineering on-call. One function holds every rule, in order.

Read it once. It is short and clear, and for a single support team it is the right design.

<Depth level={2}>
The order of the checks matters. A $60 refund matches both the Tier 1 rule and the Tier 2 rule; it goes to Tier 1 only because that check comes first.
</Depth>

<Depth level={3}>
The last line is easy to miss and important. A ticket that matches no rule gets an error. Without it, the function would fall through and return nothing, and the ticket would sit unassigned.
</Depth>

## [pain] Then a change request arrives

**Change request:** enterprise customers' tickets go to their account manager first, if the manager is on shift, and follow the normal route otherwise.

The marked lines add an enterprise rule at the top of a function every customer goes through, and change the refund limit for everyone to depend on the plan.

<Depth level={2}>
Each new kind of customer adds conditions to the same shared function, and each condition can change where other customers' tickets go. Testing the standard route now means setting up enterprise data to prove it is not used.
</Depth>

<Depth level={3}>
Next quarter, the EU office wants its own route with a privacy desk first, and the night shift wants Tier 2 skipped. One function cannot hold three routes without becoming a tangle of flags.
</Depth>

## [morph] Turn each rule into a handler

Drag the slider. Each branch of the switch becomes a small handler that knows one rule. The chain is a list of them, tried in order.

Hover a box in the diagram to see its code.

<Depth level={2}>
A route is now configuration: a list of handlers. Different customers get different lists built from the same parts, and each handler is tested alone. The last link is a <Term id="catch-all-handler">catch-all handler</Term>, so the end of the chain is a decision you can see.
</Depth>

<Depth level={3}>
This is the list form of the pattern: a loop owns the order. The catalogue's form links each handler to its successor and has it forward the request itself. HTTP <Term id="middleware-onion">middleware</Term> is that second form, with the successor passed in as `next`; a layer that answers without calling `next` is a <Term id="short-circuit-response">short-circuit</Term>. The list form makes the order visible in one place; the linked form lets a handler do work both before and after the rest of the chain.
</Depth>

<Depth level={2}>
Log which handler took each request. With a switch, reading the code told you where a ticket would go. With a chain, the answer depends on configuration, and the log is how you find out.

<Depth level={3}>
<Lang only="go">`range` over a slice of interfaces calls each `Handle` through the interface's method table. A chain of five handlers is five indirect calls at most, nothing next to a database write. Wrapping `ErrUnhandled` with `%w` lets callers test for it with `errors.Is`.</Lang>
<Lang only="python">The walrus operator `:=` assigns and tests in one expression. Compare with `is not None`, not truthiness, so a handler can return a falsy but valid result.</Lang>

<Lang only="rust">`find_map` stops at the first `Some` and never calls the remaining handlers. `ok_or` turns the `None` at the end into the `Unhandled` error, so the type system makes the caller deal with an unhandled ticket.</Lang>
</Depth>

## [again] The account manager, the second time

The same request after the refactor. The account manager is one new handler. Enterprise customers get a chain that starts with it and continues with the standard links. The standard chain does not change, so ordinary customers cannot be affected.

<Depth level={2}>
Where the new handler goes is the real decision. At the front, the manager sees every enterprise ticket first. After the help bot, password resets stay automatic. The handler code is the same either way; only the list changes.
</Depth>

<Depth level={3}>
Chains built from configuration can be wrong in ways the compiler cannot see: a missing catch-all, a broad handler before a narrow one. Test each configured chain with one request of every kind, and assert that none comes back unhandled.
</Depth>

### Design the end of the chain

A chain answers "who handles this?" with "whoever comes first and says yes", and sometimes the answer is nobody. Decide what nobody means before you ship: a catch-all handler that sends the request to a person, or an unhandled error that is logged and alerted. A handler in the middle that neither handles nor passes on is the same failure in disguise. In Express, a middleware that neither responds nor calls `next()` leaves the request hanging until the client gives up.
