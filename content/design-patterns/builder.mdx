checks:
  overview:
    question: Which of these situations calls for a Builder?
    options:
      - text: An HTTP client takes a base URL plus an optional timeout, retry policy, proxy, TLS settings and default headers. Most callers set two or three of them.
        correct: true
        why: Right. Many optional settings, a few required ones, and a finished client that should be valid from the start.
      - text: A service creates an S3 or a GCS client depending on which cloud it runs in.
        why: That is a choice of class, which a factory handles. Builder is about assembling one object with many parts.
      - text: Each new nightly job starts as a copy of a template job, with two fields changed.
        why: That is Prototype. You start from an existing object and copy it, instead of assembling one from scratch.
  engineer:
    question: Your builder validates cpu and memory in build(). A teammate adds a Resources(cpu, memory string) step to save a line at call sites. What is the risk?
    options:
      - text: It brings back positional arguments of the same type, so a swapped pair compiles and reads plausibly in review again.
        correct: true
        why: Right. The builder's benefit is that every value sits next to its name. A step that takes two same-typed values gives that up for the pair.
      - text: None. build() validates, so the order of arguments cannot matter.
        why: Validation catches impossible values, such as half a byte of memory. It cannot catch two plausible values in the wrong places, such as cpu "1" and memory "2Gi" against cpu "2" and memory "1Gi".
      - text: Go and Rust do not allow a method to take two arguments of the same type.
        why: They do. The compiler only checks types, which is exactly why the swap goes unnoticed.
  deep:
    question: How can a Rust builder make a missing .image() a compile error instead of an Err from build()?
    options:
      - text: Track the field in the builder's type. DeploymentBuilder<NoImage> has no build method, and .image() returns a DeploymentBuilder<HasImage>, which does.
        correct: true
        why: Right. This is the typestate pattern. A zero-sized marker type parameter costs nothing at runtime, and calling build() too early does not type-check.
      - text: Mark the image field with #[must_use].
        why: '#[must_use] warns when a returned value is ignored. It says nothing about whether a method was called.'
      - text: Make build() a const fn, so the checks run at compile time.
        why: A const fn can run at compile time only with constant inputs. A builder filled from config at runtime still needs runtime checks, or types that rule the mistake out.

# ---------------------------------------------------------------- reference page
reference:
  roles:
    - role: Builder
      example: { go: DeploymentBuilder, python: "Deployment (kw-only dataclass)", typescript: "DeploymentSpec (options object)", rust: DeploymentBuilder }
      job: Collects the values, one named step or field at a time.
    - role: build()
      example: { go: "Build()", python: "__post_init__", typescript: "deployment()", rust: "build()" }
      job: Checks the whole object once and returns it, or fails.
    - role: Product
      example: Deployment
      job: The finished object. Complete, valid, and usually immutable.
    - role: Director (optional)
      example: "a helper such as webServiceDefaults(b)"
      job: Runs a fixed sequence of steps, so common configurations are written once.
  useWhen:
    - A constructor needs more than three or four arguments, especially several of the same type.
    - Many fields are optional and most callers set only a few.
    - An object must be valid as a whole, with rules that span fields, and should never be seen half built.
    - The object should be immutable once created, but is assembled step by step.
  avoidWhen:
    - The language has named and default arguments and construction is one call. Use them instead.
    - The object has two or three required fields. A plain constructor is clearer.
  tradeoffs:
    - A second type to write and keep in sync with the product.
    - Required fields are easy to forget unless build() checks them, or the type system does.
    - In Go, zero values make "not set" and "set to zero" look the same.
  lookalikes:
    - name: Abstract Factory
      how: Returns finished products right away, one per call, chosen by family. A builder assembles one product over several calls.
    - name: Factory Method
      how: Decides which class to create. A builder decides how one object is put together.
    - name: Prototype
      how: Starts from a copy of an existing object. A builder starts from nothing.
    - name: Fluent interface
      how: Method chaining as a style. Many builders are fluent, but a fluent API is not necessarily building anything.

## [concept] Builder

**Build a complex object through named steps and one final build() that checks the whole thing, so callers never pass a long row of arguments and never hold a half-built object.**

Every value sits next to its name. The object does not exist until it is complete and valid.

<Depth level={2}>
Two problems usually lead here. A <Term id="telescoping-constructor">telescoping constructor</Term> takes a long row of positional arguments, and same-typed ones can swap without the compiler noticing. A mutable object filled in by setters exists before it is ready, so code can see it half built. A builder fixes both. It gathers values by name and only hands over an <Term id="immutable-object">immutable object</Term> once `build()` has checked it.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue meant something broader: separate how an object is constructed from how it is represented, so the same construction steps can produce different results. Its example is an RTF reader driving interchangeable converters to plain text, TeX or a text widget, with a director running the steps. The everyday form today, a fluent builder for one object with many optional parts, was popularised later by Joshua Bloch's *Effective Java*. Both share the core move: construction becomes a sequence of named steps behind one interface.
</Depth>

## [problem] A constructor with seven arguments

A platform team's deploy tooling creates Kubernetes Deployments from code. One constructor takes every setting; a second one, with a probe, was added later. Twenty-three services call one or the other.

Read the call sites. Without the signature open next to them, you cannot tell which number is the replica count.

<Depth level={2}>
Replicas and port are both integers. CPU and memory are both strings. Swap either pair and the code compiles, the tests that do not deploy pass, and the reviewer sees a plausible row of values.
</Depth>

<Depth level={3}>
Kubernetes accepts many wrong values too. A memory limit of `500m` is a legal quantity: half a byte, because lowercase `m` means milli. A CPU request of `256Mi` is legal as well, and asks for hundreds of millions of cores. The cluster reports these as Pending pods or killed containers, long after the code was merged.
</Depth>

## [pain] Then a change request arrives

**Change request:** platform requires a priority class on every production Deployment.

Both constructors grow a parameter, and every one of the 23 call sites has to change, even the ones for services that will use the default.

<Depth level={2}>
The order of parameters becomes a hazard of its own. A required parameter has to go before the optional probe, so the new value lands in the middle of the row. In Python and TypeScript, a call site that nobody updated now passes `"/healthz"` as the priority class, and both are strings, so nothing complains.
</Depth>

<Depth level={3}>
The usual escape is another constructor, `NewDeploymentWithProbeAndPriority`. Each new optional setting doubles the number of possible combinations, and the family of constructors grows to match.
</Depth>

## [morph] Give every value a name

Drag the slider. The row of positional arguments turns into named steps, and one `build()` at the end checks the whole object.

Hover a box in the diagram to see its code.

<Depth level={2}>
Defaults move into the builder, so callers only mention what they change. Rules that span fields, such as "a probe needs a port", live in one place. And because the product only comes out of `build()`, there is no moment when a Deployment exists without an image.
</Depth>

<Depth level={3}>
<Lang only="go">Go has no named arguments, so the builder supplies them as methods. Each step returns the same `*DeploymentBuilder` to allow chaining. `Build` returns a copy of the struct, so changing the builder afterwards does not change a Deployment already built, apart from shared pointers such as the probe.</Lang>
<Lang only="python">Python already has names at the call site through <Term id="keyword-argument">keyword arguments</Term>. `kw_only=True` makes every field keyword-only, and it is what lets `port` follow the defaulted `replicas` without a `TypeError` at class definition.</Lang>
<Lang only="typescript">The options object gives names at the call site, and the type checker requires `name`, `image`, `port`, `cpu` and `memory`. `Object.freeze` makes the result read-only at runtime, while `Readonly<…>` does the same at compile time.</Lang>
<Lang only="rust">Each step takes `self` by value and returns it, so the chain moves one builder along. After `build(self)` the builder is gone: the compiler rejects any later use of it.</Lang>
</Depth>

## [walk] Follow one Deployment being built

One Deployment from the first call to a finished object. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Chained calls on a pointer receiver mutate one builder in place. The builder usually lives on the stack or is freed right after `Build`; the cost is a few stores, nothing to measure.</Lang>
<Lang only="python">A frozen dataclass sets its fields through `object.__setattr__` inside the generated `__init__`, then runs `__post_init__`. After that, assigning a field raises `FrozenInstanceError`.</Lang>
<Lang only="typescript">The spread `{ replicas: 1, ...spec }` creates one new object, so the caller's spec is not modified. `Object.freeze` is shallow: nested objects would need freezing too.</Lang>
<Lang only="rust">Moving the builder through each call is free in practice: the optimiser usually builds it in place. A <Term id="typestate">typestate</Term> version adds a marker type parameter per required field, which also costs nothing at runtime.</Lang>
</Depth>

## [again] Priority class, the second time

The same request after the refactor. The builder gets one new step and a default. Services that need a priority add one line at their call site; the other call sites do not change and cannot shift.

<Depth level={2}>
If production must always set it, add the rule to `build()`: in production, a missing priority class is an error. The rule lives in one place, and the error names the missing field instead of shifting arguments.
</Depth>

<Depth level={3}>
Common configurations can be captured as functions that run a fixed sequence of steps, such as `webServiceDefaults(b)` setting probes and resources for every HTTP service. That is the director role from the original catalogue, in its modern small form.
</Depth>

## [lens] How each language writes it

How much you need a builder depends on what the language gives you for free. Rust has no named or default arguments, so builders are everywhere. Python has both, so it rarely needs one.

### Builder, options object or keyword arguments?

All three put a name next to every value. Use keyword arguments where the language has them, and an options object where it has object literals and a type checker. Reach for a real builder when the language has neither, when the object is assembled across several functions, or when the steps themselves matter, as in a query builder.
