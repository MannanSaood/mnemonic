    - role: Abstraction
      example: Alert
      job: Defines what the client uses, and holds a reference to an implementor.
    - role: Refined abstraction
      example: "IncidentAlert, DigestAlert, ReminderAlert"
      job: One kind of alert. Builds its behaviour on the implementor's primitives.
    - role: Implementor
      example: { go: "Channel (interface)", python: "Channel (Protocol)", typescript: "Channel (interface)", rust: "Channel (trait)" }
      job: The primitive operations every implementation offers. Often lower-level than the abstraction.
    - role: Concrete implementor
      example: "Slack, Email, PagerDuty, SMS"
      job: One way to carry out the primitives.
  useWhen:
    - Two dimensions vary independently and both lists grow, such as message kinds and delivery channels, or reports and export formats.
    - The implementation must be chosen at runtime, per object, from config.
    - You see a class per combination, named like IncidentSlack, DigestEmail.
  avoidWhen:
    - Only one dimension varies. Use Strategy, or a plain interface.
    - The combinations are few and fixed. A handful of small classes is easier to read than two hierarchies.
    - The two sides cannot agree on a stable set of primitives. The joint would change with every new implementation.
  tradeoffs:
    - N + M classes instead of N × M, and each change lands on one side.
    - The implementor interface is a contract both sides depend on. Adding a primitive touches every implementation.
    - Implementations with special powers (Slack buttons, PagerDuty escalation) are only reachable through primitives the interface offers.
    - One more indirection to follow when reading the code.
  lookalikes:
    - name: Adapter
      how: Makes an existing class fit an interface after the fact. A bridge is designed up front so two sides can vary independently.
    - name: Strategy
      how: Same shape on one side. Strategy swaps one algorithm in a context; Bridge splits a whole hierarchy into two that both grow.
    - name: Abstract Factory
      how: Can create the right implementor for a platform or a config, and hand it to the abstraction.
    - name: State
      how: Also holds an object it delegates to, but the object replaces itself as the state changes.

## [concept] Bridge

**Split two dimensions that vary independently into two hierarchies, and let one hold a reference to the other.**

Alerts vary in what they say (incident, digest, reminder) and in where they go (Slack, email, PagerDuty). With one class per pair, every new kind or channel multiplies the class count. A bridge keeps the two apart: an Alert decides what to say, and holds a Channel that decides how to deliver it.

<Depth level={2}>
Four roles. The **abstraction** (`Alert`) is what clients use, and holds a reference to an **<Term id="bridge-implementor">implementor</Term>** (`Channel`). **Refined abstractions** (`IncidentAlert`, `DigestAlert`) are the kinds. **Concrete implementors** (`Slack`, `Email`, `PagerDuty`) are the channels. The reference between the two sides is the bridge. Passing a channel in when the alert is built is <Term id="dependency-injection">dependency injection</Term>.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Bridge as an object structural pattern. Its intent is to decouple an abstraction from its implementation so the two can vary independently. It warns against a <Term id="pair-class-explosion">class per combination</Term>, and notes that the implementor interface need not mirror the abstraction's. Typically the implementor offers primitive operations, and the abstraction builds higher-level operations on them. Listed consequences: the implementation can be chosen or changed at runtime, both sides can be extended independently, and clients are shielded from implementation details.
</Depth>

## [problem] An alert class for every pair

An on-call system sends three kinds of alert over three channels. Each pair is its own class: `IncidentSlack`, `IncidentEmail`, `DigestSlack`, and six more. It works, and each class is small.

Read it once. The incident's wording is repeated in every Incident class, and Slack's message format is repeated in every Slack class.

<Depth level={2}>
Each class mixes two decisions: what this alert says, and how this channel delivers it. A change to either one is spread across a row or a column of classes.
</Depth>

<Depth level={3}>
The repetition drifts. One incident class gets the new severity label and another does not. One Slack class handles rate limits and another does not. Nothing forces the copies to agree.
</Depth>

## [pain] Then a change request arrives

**Change request:** every alert must also go out by SMS.

The marked lines must be added: one new class per kind of alert, three today. Each one re-formats its alert for SMS from scratch.

<Depth level={2}>
The next request for a new kind of alert costs one class per channel, now four. The class count is kinds × channels, and every request in either direction makes the next one more expensive.
</Depth>

<Depth level={3}>
The pair classes also pin the choice at compile time. Sending a reminder by SMS to some users and by email to others means picking between two classes in the calling code, so the calling code has to know every pair.
</Depth>

## [morph] Split the pairs into two hierarchies

Drag the slider. The nine pair classes split into three alert kinds and three channels, joined by one reference: an Alert holds a Channel.

<Depth level={2}>
Now each request lands on one side. A new channel is one class that implements `Channel`. A new kind of alert is one class that composes a `Message`. Rewording incidents touches `IncidentAlert` only; changing Slack's format touches `Slack` only.
</Depth>

<Depth level={3}>
<Lang only="go">`IncidentAlert` holds a `Channel` interface value. The channel is chosen when the struct is built, so two incident alerts in the same process can use different channels.</Lang>
<Lang only="python">`IncidentAlert` accepts any object with a `deliver` method. A type checker confirms it against the `Channel` protocol; at runtime, any object with the method works.</Lang>
<Lang only="typescript">`IncidentAlert` holds a `Channel`. Any object with a matching `deliver` fits, so a test can pass `{ deliver: async (m) => { sent.push(m); } }` with no class at all.</Lang>
<Lang only="rust">`Box<dyn Channel>` lets the channel be chosen at runtime, which is the binding the pattern wants. Each call goes through the trait object's vtable: <Term id="dynamic-dispatch">dynamic dispatch</Term>.</Lang>
</Depth>

## [walk] Follow one alert across the bridge

One incident, from the alert that composes it to the channel that delivers it. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`a.ch.Deliver(...)` is one interface call. The `Message` is passed by value: a small struct of two strings and a severity, copied cheaply.</Lang>
<Lang only="python">`self.channel.deliver(...)` is an attribute lookup and a call. A frozen dataclass keeps the message immutable, so a channel cannot change it for the next one.</Lang>
<Lang only="typescript">The message is a plain object literal. Nothing at runtime checks it against `Message`; the compiler did that once.</Lang>
<Lang only="rust">The message is passed by reference, `&Message`, so nothing is cloned to deliver it. A generic `IncidentAlert<C: Channel>` would let the compiler inline `deliver` through <Term id="monomorphisation">monomorphisation</Term>, at the cost of fixing the channel at compile time.</Lang>
</Depth>

## [again] SMS, the second time

The same request after the refactor. SMS is one new Channel. Every kind of alert can use it, and no alert class changes.

<Depth level={2}>
A channel with a hard limit exposes the joint. A daily digest that reads fine in Slack is cut at 160 characters in an SMS. The fix belongs in the implementor interface: a primitive such as a maximum length, which the digest uses to shorten itself. Every channel must now implement it. Choosing the primitives carefully is most of the work of a bridge.
</Depth>

<Depth level={3}>
Test each side alone. Alert tests use a fake channel that records the messages it receives. Channel tests send a fixed message and check the API call. Then one or two end-to-end tests cover the pairs that matter most, such as incidents on PagerDuty.
</Depth>

### Bridge, Strategy and Adapter

All three hold an object behind an interface. Strategy has one dimension: the context swaps one algorithm. Bridge has two: both the abstraction and the implementor have hierarchies that grow, and the reference joins them. Adapter is not designed up front at all: it makes an existing class fit an interface it was not written for. If you find yourself writing classes named after two things at once, such as `DigestEmail`, look for a bridge.
