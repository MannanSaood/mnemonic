  engineer:
    question: After two years the checkout mediator is 1,400 lines and every checkout change touches it. What is the best next step?
    options:
      - text: Split it by flow, for example pricing, payment and delivery, each a smaller mediator for the parts it coordinates.
        correct: true
        why: Right. The pattern moves complexity into the mediator on purpose. When it grows into a god object, divide the cooperation into groups that change for different reasons.
      - text: Go back to letting the parts call each other directly.
        why: That brings back the tangle, the edits in many parts per change and the update cascades. The mediator was the right move; it has just grown too big.
      - text: Let each part register callbacks on the mediator, so the rules live in the parts again.
        why: Then each part again encodes what other parts must do. The coupling returns, now hidden behind the mediator.
  deep:
    question: In the wired checkout, Shipping updates Summary, which refreshes the button before Promo has dropped an invalid code. The button briefly shows a wrong total. What is this, and how does the mediator avoid it?
    options:
      - text: A glitch. A dependent recomputed between two of its inputs updating. The mediator applies every rule first and renders once, so nothing sees a half-updated state.
        correct: true
        why: Right. Reactive libraries avoid glitches the same way, by updating in dependency order before anyone reads. It is a single-threaded problem, about the order of synchronous calls.
      - text: A data race between two threads. It needs a mutex around Summary.
        why: There is only one thread. The calls run synchronously, depth first, and the wrong total comes from their order. A lock would not change the order.
      - text: A memory leak, because Summary keeps a reference to the button.
        why: Holding a reference is not a leak, and it does not explain a wrong value. The order of updates does.

# ---------------------------------------------------------------- reference page
reference:
  roles:
    - role: Mediator
      example: Checkout
      job: Knows which parts affect which, applies those rules, and updates each part once.
    - role: Colleague
      example: Shipping, Promo, Payment, Summary, Place order
      job: Does its own job and reports changes to the mediator. Knows no other part.
    - role: Client
      example: The customer, through the page
      job: Changes a part, or sends the change to the mediator.
  useWhen:
    - Several parts must react to each other, and each new part would otherwise be wired to many existing ones.
    - Updates must happen in a fixed order, or the page shows half-updated values.
    - You want to reuse a part in another screen without dragging its neighbours along.
  avoidWhen:
    - Two or three parts with one simple dependency. A direct call is clearer.
    - Events flow one way from one source to many listeners. Observer fits better.
  tradeoffs:
    - The mediator collects all the cooperation, so it can grow into a god object. Split it by flow when it does.
    - To learn what a part does to the rest of the page, you read the mediator, not the part.
    - Each part depends on the mediator, which makes the mediator hard to change without touching every part that calls it.
  lookalikes:
    - name: Facade
      how: Gives callers a simpler interface to a subsystem. The subsystem does not know the facade, and its parts may still talk to each other.
    - name: Observer
      how: One-way notifications from a subject to listeners. A mediator often listens to its parts this way, then coordinates them.
    - name: Event bus
      how: A shared channel where anyone publishes and anyone subscribes. It removes references but not the rules; those end up spread across the subscribers.

## [concept] Mediator

**Let a set of objects talk through one coordinator instead of to each other, so each one knows only the coordinator.**

How the parts affect each other becomes the coordinator's job. Each part does its own work and reports what changed.

<Depth level={2}>
Two roles. The **mediator** (`Checkout`) knows every part and the rules between them: a new country changes the payment methods, an invalid promo is dropped, the total is shown once everything is settled. Each **colleague** (Shipping, Promo, Payment, Summary, Place order) knows only the mediator. With n parts that may all affect each other, direct wiring can need up to n×(n−1)/2 links; through a mediator it needs n.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Mediator under object behavioural patterns, with a font dialog as its example: a list box, an entry field and buttons that enable and fill each other. It names the benefits: colleagues are decoupled and reusable, and many-to-many protocols become one-to-many. It also names the cost plainly. The mediator centralises control and can become a monolith more complex than any colleague. It suggests the mediator can learn of changes through Observer.
</Depth>

## [problem] A checkout page wired to itself

A checkout page has a shipping country, a promo code, a payment picker, a summary and a Place order button. Each part holds pointers to the parts it must update and calls them when it changes.

Read it once. Shipping knows three other parts. Summary knows the button. Every rule about how the page behaves lives inside the part that happens to change first.

<Depth level={2}>
Follow one country change. Shipping updates Summary, which refreshes the button. Then it updates Payment, then Promo, which updates Summary again, which refreshes the button again. The button renders three times for one click, and the first render uses the old discount.
</Depth>

<Depth level={3}>
To test Promo you need a Summary, which needs a PlaceOrder. To reuse Shipping on the address-book page you bring along a checkout's worth of parts. The links are the problem, not any single part.
</Depth>

## [pain] Then a change request arrives

**Change request:** checkout needs a gift card field that lowers the total and can make a payment method unnecessary.

The gift card must reach Summary, Payment and the button, so it holds all three. Summary gains a field and a setter, Payment gains `SetRequired`, and Cart must call the gift card when the basket changes. That is four existing parts edited for one new one.

<Depth level={2}>
Each edit is small, and that is the trap. Nobody owns the question of how the page behaves as a whole. The next request, loyalty points that cannot be combined with a promo code, makes Promo and Loyalty clear each other, and in this design they call each other forever.
</Depth>

<Depth level={3}>
<Lang only="rust">In Rust the tangle shows up early. Every link is an `Rc<RefCell<…>>`, and when Promo and Loyalty call each other, the second `borrow_mut` on an already borrowed cell panics with `BorrowMutError`.</Lang>
<Lang only="go">Go will compile the loop happily. Promo calls Loyalty, which calls Promo, until the goroutine's stack hits its limit and the program dies with a fatal stack overflow.</Lang>
<Lang only="python">Python will run the loop until it raises `RecursionError` after about a thousand nested calls, in the middle of a customer's click.</Lang>
<Lang only="typescript">In the browser the loop ends with `RangeError: Maximum call stack size exceeded`, and the checkout stops responding to that click.</Lang>
</Depth>

## [morph] Route every change through one coordinator

Drag the slider. The links between parts disappear. Each part reports to `Checkout`, and `Checkout` updates the others.

Hover a box in the diagram to see its code.

<Depth level={2}>
The rules did not vanish; they moved. They now sit in one method you can read top to bottom, in the order they run. Each part can be tested alone, and the mediator can be tested with simple fakes.
</Depth>

<Depth level={3}>
The parts are built by the mediator and given a pointer back to it: a small case of <Term id="dependency-injection">dependency injection</Term>. In Rust the back pointer is dropped entirely. The page sends a `Change` message to the mediator, which owns the parts, so there is nothing for the borrow checker to object to.
</Depth>

<Depth level={3}>
Because the mediator applies every rule before it renders, the summary and button never see a half-updated state. In the wired version they did, which is called a <Term id="update-glitch">glitch</Term>. Reactive libraries avoid glitches the same way: they settle all inputs first, then recompute each dependent once.

## [again] The gift card, the second time

The same request, after the refactor. You add one part that knows only the mediator, and two lines in the mediator's render step. Shipping, Promo, Payment, Summary and the button do not change.

<Depth level={2}>
The loyalty request becomes one rule in the mediator, such as "whichever of promo and points the customer touched last wins". A loop between the two parts cannot happen, because neither part calls the other.
</Depth>

<Depth level={3}>
Watch the mediator's size. Each request adds a rule or two, and after a few years it can be the biggest class in the checkout, a <Term id="god-object">god object</Term>. When that happens, split it by flow, with one mediator for pricing and one for payment and delivery, each coordinating fewer parts.
</Depth>

### Orchestration and choreography

In service architectures the same choice has other names. An orchestrator, such as a deploy pipeline or a saga coordinator, is a mediator: services report to it and it decides what runs next. Choreography is the event-bus version, where each service reacts to events and nobody holds the whole flow. Orchestration is easier to read and change in one place. Choreography avoids a central component, but spreads the rules across every subscriber.
