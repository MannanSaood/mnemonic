    options:
      - text: A billing service applies one tax rule per country, chosen from config when the request starts.
        correct: true
        why: Right. The rule varies, the caller picks it, and the rule never switches itself during the request.
      - text: A TCP connection behaves differently in LISTEN, ESTABLISHED and CLOSE_WAIT, and moves between those states by itself.
        why: That is State. It has the same shape, but the object changes its own behaviour as it moves between states. In Strategy, the caller chooses.
      - text: Three exporters all open a file, write a header, write rows and close, and differ only in how they write one row.
        why: That is Template Method. The order of steps is fixed in one place and only one step varies. Strategy swaps the whole step, chosen from outside.
  engineer:
    question: A new provider needs the customer's billing address. The existing providers ignore it. What is the cleanest change?
    options:
      - text: Add the billing address to Order, which every provider already receives.
        correct: true
        why: Right. The interface stays the same, and the providers that do not need the address ignore it. Every strategy getting the same inputs is the known cost of Strategy, and here it is cheap.
      - text: In Checkout, check whether the provider is the new one, and if so look up the address and pass it separately.
        why: That brings back a branch on the provider inside Checkout, the exact thing the pattern removed. The next special case adds another.
      - text: Add a SetBillingAddress method to the PaymentProvider interface.
        why: Every provider would have to implement a method that only one of them uses, and Checkout must remember to call it before Charge.
  deep:
    question: Checkout's provider is chosen from config at startup. Why can a call through the interface cost a little more than a direct call?
    options:
      - text: The target is found at runtime, through a table of method pointers or an attribute lookup, so the call is indirect and usually cannot be inlined.
        correct: true
        why: Right. In Go it is the itab, in Rust the vtable of a trait object, in Python and JavaScript a lookup on the object. For a payment call that waits on the network, the cost is invisible.
      - text: The provider is copied each time a method is called through the interface.
        why: No. The interface value holds a pointer (or a small value), and the call passes the receiver along. Nothing else is copied per call.
      - text: The runtime checks the provider's type with reflection on every call.
        why: No. The method table is set up when the provider is stored in the interface or trait object. No reflection happens on the call path.

    - Several operations must always agree on the same choice, like Pay and Refund here.
    - You want to test each variant alone, and test the context with a fake.
  avoidWhen:
    - There are only two variants and no third in sight. An if is clearer; add the interface when the next real variant arrives.
    - The variants need very different inputs. Forcing them behind one signature makes every strategy receive data it ignores.
  tradeoffs:
    - The caller must know which strategies exist in order to pick one.

    - Every strategy gets the same inputs, even the ones it does not use.
    - In Go, and in Rust with trait objects, a call through the interface is indirect and usually cannot be inlined.

    - name: State

    - name: Template Method
      how: Fixes the order of steps in one place and varies a few of them. Strategy swaps one whole step.
    - name: Decorator
      how: Changes behaviour by wrapping an object in another with the same interface, not by swapping it.
    - name: Dependency injection
      how: The general habit of passing collaborators in. Strategy is one use of it, for a step that varies.

## [concept] Strategy

**Put each way of doing one step behind a shared <Term id="interface">interface</Term>, and let the caller choose which one to plug in.**

The code that *uses* the step should not need to know how many ways there are to do it, or which one it was given.

<Depth level={2}>
Three roles do the work. The <Term id="context-role">context</Term> (`Checkout`) holds a strategy and calls it. The **strategy** (`PaymentProvider`) is the step, named as a type. Each **concrete strategy** (Stripe, PayPal, Adyen) is one way of doing the step. A fourth party, the **client**, picks one and hands it in; usually that is `main` or the config loader. Handing it in is <Term id="dependency-injection">dependency injection</Term>.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Strategy under behavioral patterns, and frames it as an alternative to subclassing: instead of a subclass per algorithm, the algorithm becomes an object of its own. It also names the costs. The client has to know the strategies exist in order to choose one, and every strategy receives the same inputs, even the ones it ignores. In languages where functions are values, a one-method strategy usually shrinks to a function.
</Depth>

## [problem] A checkout that knows every provider

A shop's checkout takes payments through one of three providers, chosen per region in config. It works, and it is tested.

Read it once. The list of providers lives in three places: the branch in Pay, the branch in Refund, and the config list.

<Depth level={2}>
Each branch calls a different client library with different arguments. To test the Adyen path on its own, you still build a whole Checkout and go through the branch.
</Depth>

<Depth level={3}>
Nothing here is wrong yet. Two providers behind an `if` would be perfectly fine. The problem is the rate of change: each new provider edits the same three places, and each edit can break the providers that already work.
</Depth>

## [pain] Then a change request arrives

**Change request:** the EU store needs Klarna, so customers can pay later.

The marked lines must change. None of them is about how Klarna works. They are bookkeeping, spread across three places.

<Depth level={2}>
The two branches can drift apart. Add Klarna to Pay but forget Refund and everything compiles, the tests for the old providers pass, and the first Klarna customer who asks for a refund gets an error.
</Depth>

<Depth level={3}>
The branches also share one test surface. A change to the Klarna branch re-runs the tests of every other provider, and a mistake in it can break them.
</Depth>

## [morph] Turn each branch into its own strategy

Drag the slider. Both branches collapse into one interface, and each provider moves out into its own type.

Hover a box in the diagram to see its code.

<Depth level={2}>
Checkout now depends on two methods instead of on the list of providers. Each provider can be tested on its own, and Checkout can be tested with a fake provider. New providers extend the system without editing it: the <Term id="open-closed">open/closed principle</Term>.
</Depth>

<Depth level={3}>
<Lang only="go">Go interfaces are satisfied implicitly. `Stripe` never says it implements `PaymentProvider`; having the two methods is enough, and the compiler checks it where a `Stripe` is stored in a `PaymentProvider`.</Lang>
<Lang only="python">A `Protocol` is checked by tools such as mypy, not at runtime. Any object with `charge` and `refund` methods works, whatever it inherits from.</Lang>
<Lang only="typescript">TypeScript uses <Term id="structural-typing">structural typing</Term>: a `StripeProvider` fits `PaymentProvider` because it has the right shape, with or without `implements`.</Lang>
<Lang only="rust">Each provider opts in explicitly with `impl PaymentProvider for Stripe`, and the compiler checks the method signatures there.</Lang>
</Depth>

<Depth level={3}>
<Lang only="go">A call through an interface loads the method's address from the <Term id="itab">itab</Term> and makes an indirect call. It costs a few nanoseconds and usually prevents inlining. Next to a network call to a payment provider, that is noise.</Lang>
<Lang only="python">`self.provider.charge(order)` is an attribute lookup on the object followed by a call. There is no interface table: whatever object is stored there is called, and a wrong one fails only when it runs.</Lang>
<Lang only="typescript">The interface exists only at compile time. At runtime `this.provider.charge` is a property lookup on the object; V8's inline caches keep it fast while a call site only ever sees one or two kinds of object.</Lang>
<Lang only="rust">`Box<dyn PaymentProvider>` stores a pointer to the data and a pointer to a vtable, and each call goes through the vtable: <Term id="dynamic-dispatch">dynamic dispatch</Term>. A generic `Checkout<P>` would instead get one compiled copy per provider (<Term id="monomorphisation">monomorphisation</Term>), with calls the compiler can inline.</Lang>
</Depth>

## [again] Klarna, the second time

The same Klarna request, after the refactor. You add one new provider type. Nothing that already exists changes, so nothing that already works can break, and Pay and Refund cannot drift apart.

</Depth>

### When the strategy is just a function

If a strategy has one method and no state, most languages let you pass a function instead of defining a type: `sort.Slice` in Go, `key=` in Python, a comparator in TypeScript, a closure in Rust. Start there. Move to an interface or trait when the strategy needs a second method (here, `Refund`) or carries configuration such as API keys.
