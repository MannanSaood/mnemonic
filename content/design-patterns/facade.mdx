        correct: true

        why: That is Adapter. It makes one object fit an interface that already exists. A facade defines a new, simpler interface over many objects.
      - text: Every call to a slow remote API should be cached, and the callers should not change.
        why: That is Proxy. It stands in for one object with that object's own interface. A facade offers a different, simpler interface over several.
  engineer:
    question: The rollback script must roll out an old image without building or migrating. The Deployer has only Deploy(). What is the cleanest choice?
    options:
      - text: Let the rollback keep calling the Cluster and Notifier directly. Add a Rollback method to the Deployer only once several callers need the same sequence.
        correct: true
        why: Right. A facade is the default path for the common job. Callers with different needs keep using the parts, which stay available.
      - text: Add skipBuild and skipMigrations flags to Deploy.
        why: Each special case adds a flag, and every caller must set all of them right. The facade grows into a god object with one entry point that does everything.
      - text: Make the subsystem's parts private, so everyone has to go through the Deployer.
        why: Then the rollback cannot be written at all. A facade simplifies the common path; it should not remove the others.
  deep:
    question: In a large codebase, why does a facade often reduce how much has to be rebuilt and retested when the subsystem changes?
    options:
      - text: Callers import only the facade. A change inside the subsystem that keeps the facade's signature does not touch anything the callers depend on.
        correct: true
        why: Right. In Go and Rust the callers' packages or crates depend on one exported API; in TypeScript and Python, on one module. Build tools and test selection follow the import graph.
      - text: The facade caches the results of the subsystem, so the parts run less often.
        why: No. A facade forwards calls; it does not cache. Caching in front of one object is a Proxy.
      - text: The facade is a singleton, so it is compiled only once.
        why: No. Facades are often single instances, but that has nothing to do with compilation. The saving comes from fewer import edges.

reference:
  roles:
    - role: Facade
      example: Deployer
      job: Knows which parts handle a request and in what order. Forwards the work to them.
    - role: Subsystem classes
      example: Builder, Registry, Migrator, Cluster, CDN, Notifier
      job: Do the real work. They do not know the facade exists.
    - role: Client
      example: CI pipeline, ChatOps bot, hotfix script
      job: Calls the facade for the common job. May still use the parts directly for anything else.
  useWhen:
    - Several callers drive the same parts of a subsystem in the same order.
    - You want callers to depend on one stable entry point while the parts behind it change.
    - You are layering a system and want one entry point per layer.
  avoidWhen:
    - There is one caller. Its own function already is the facade.
    - Every caller needs a different sequence. A facade with a flag per caller is worse than direct calls.
  tradeoffs:
    - The facade can grow into a god object that every change must pass through. Split it by job when it does.
    - It hides options. Callers who need them must go around it, so keep the parts reachable.
    - One more layer to read when debugging a failure deep in the subsystem.
  lookalikes:
    - name: Adapter
      how: Makes one existing object fit an interface that already exists. A facade defines a new, simpler interface over many objects.
    - name: Mediator
      how: Coordinates objects that talk to each other through it, and they know the mediator. Subsystem classes do not know their facade.
    - name: Proxy
      how: Stands in for one object with the same interface. A facade has its own interface over several objects.

## [concept] Facade

**Give a <Term id="facade-subsystem">subsystem</Term> one simple entry point for the common job, so callers stop orchestrating its parts by hand.**

The order of the steps lives in one place. Callers that only want the common job depend on that place, and nothing else.

<Depth level={2}>
The facade is an ordinary class or function with a small <Term id="interface">interface</Term>, here `Deploy(ref, version)`. Behind it, the subsystem's classes stay as they are, and they do not know the facade exists. Callers with unusual needs, like a rollback, can still use the parts directly. What changes is the <Term id="coupling">coupling</Term>: most callers now depend on one type instead of six.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Facade as an object structural pattern. Its motivating example is a compiler subsystem whose `Compiler` class offers one simple call over the scanner, parser and code generator, while leaving those classes available to the few programs that need them. The book lists three effects: fewer objects for clients to deal with, weaker coupling between clients and the subsystem, and no ban on using the subsystem directly. It also notes that a facade usually needs only one instance.
</Depth>

## [problem] Every caller runs the deploy by hand

A team deploys one service from three places: the CI pipeline, a ChatOps `/deploy` command, and a hotfix script. Each one calls the platform's six parts in order: build, push, migrate, roll out, purge the CDN, announce.

Read it once. The CI version is shown; the other two are copies of it.

<Depth level={2}>
The copies were reasonable when they were made. Each was a few lines, and each caller needed a deploy. Nothing ties them together now, so each drifts on its own schedule.
</Depth>

<Depth level={3}>
Each copy imports every part of the platform: six packages per caller. A change to any part's API is a change to every caller, whether or not that caller cared about the detail.
</Depth>

## [pain] Then a change request arrives

**Change request:** security wants every image scanned before it is pushed.

The scan has to go between build and push in every copy. Miss one and nothing fails. That caller simply ships an unscanned image and reports success.

<Depth level={2}>
Compare a signature change, such as a new region argument on push. A missed copy fails loudly on its next run. A new step is worse: missing it is silent, and you learn about it in an audit.
</Depth>

<Depth level={3}>
The rule "always scan before push" is really a property of the deploy, not of each caller. While the order of steps is copied, the rule exists only in the heads of the people who remember every copy.
</Depth>

## [morph] Give the deploy one entry point

Drag the slider. The six calls move out of the callers into a `Deployer` with one method. Each caller shrinks to one line.

Hover a box in the diagram to see its code.

<Depth level={2}>
The Deployer adds no behaviour of its own. It holds the parts and calls them in order. That is the difference from patterns that wrap one object: a facade sits in front of many, with an interface of its own.
</Depth>

<Depth level={3}>
<Lang only="go">Put `Deployer` in the platform's own package. Callers import that one package; the six part packages drop out of their import lists, and `go build` no longer rebuilds callers when a part's internals change.</Lang>
<Lang only="python">Put `Deployer` (or a plain `deploy` function) in the platform package's `__init__.py`. Callers import one name. The parts stay importable from their submodules.</Lang>
<Lang only="typescript">Export `Deployer` from the platform's `index.ts`. With an `exports` map in `package.json` you can choose which deeper paths stay public for advanced callers.</Lang>
<Lang only="rust">Make `Deployer` public at the crate root and keep the parts in public submodules. `pub use` lets you choose what the short path shows without hiding the rest.</Lang>
</Depth>

<Lang only="go">Errors come back from the first part that fails, and the facade returns them unchanged. Wrap them with `fmt.Errorf("push: %w", err)` if callers need to know which step failed; `errors.Is` still sees the original.</Lang>
<Lang only="python">An exception from any part propagates through `deploy()` to the caller unchanged. If callers need the step name, catch and re-raise with `raise DeployError("push") from err`.</Lang>
<Lang only="typescript">Each `await` rejects on the first failing part, and the facade's promise rejects with the same error. Add `{ cause: err }` to a new `Error` if callers need the step name.</Lang>
<Lang only="rust">The `?` operator returns the first error. If the parts return different error types, `DeployError` needs `From` impls for each, or the facade maps them with `map_err`.</Lang>
</Depth>

## [again] The scan, the second time

The same request after the refactor. One edit inside `Deploy`, right after the build. No caller changes, and every caller that uses the facade scans on its next deploy.

<Depth level={2}>
The rollback script is untouched because it never builds or pushes. That is the other half of the design: callers with different needs were never forced through the facade.
</Depth>

<Depth level={3}>
Tests follow the same split. The Deployer gets one test with fakes for the parts that checks the order of the calls. The callers' tests check that they call `Deploy`, and they no longer change when the order does.
</Depth>

### When the facade grows too big

A facade that takes every caller's special case becomes a <Term id="god-object">god object</Term>: one class with a flag for everything, which every change has to go through. Split it by job instead, such as a `Deployer` and a `Rollbacker`, and let rare callers use the parts directly.
