  overview:
    question: A report exporter has `if format == "csv" … elif format == "xlsx" … elif format == "pdf"` in three functions. What does polymorphism change?
    options:
      - text: Each format becomes a type with the same methods, and the three functions call those methods without checking the format.
        correct: true
        why: Right. The branch moves into the types, once. The three functions stop naming formats, so a new format edits none of them.
      - text: The three if-chains move into one shared helper function that all three call.
        why: That removes duplication, but the helper still names every format. A new format still edits it, and the callers still depend on the full list.
      - text: Each format gets its own copy of the three functions, chosen by a flag at startup.
        why: That duplicates the callers instead of the variants. Polymorphism keeps one caller and many implementations.
  engineer:
    question: Your Notifier interface has Send and WakesPeople. A teammate wants to add RetryPolicy, SupportsAttachments and Cost, because some channels need them. What is the better response?
    options:
      - text: Keep Notifier to what notify() calls. Code that needs attachments or cost should depend on its own small interface.
        correct: true
        why: Right. A small interface is easy to implement, fake and read. Every method you add is a method every channel, and every test fake, must provide.
      - text: Add all three, with defaults that return zero values, so existing channels still compile.
        why: Defaults hide the question of whether a channel really supports a feature. Callers then cannot tell "no" from "nobody implemented this".
      - text: Add them, and use a type check in notify() for the channels that support them.
        why: That brings back the type checks the interface removed. The caller starts naming channels again.
  deep:
    question: A new Slack notifier has send but not wakesPeople. When is the mistake caught?
    options:
      - text: In Go, TypeScript and Rust when the code compiles, where Slack is stored as a Notifier. In Python only when the missing attribute is read at runtime, unless a type checker runs first.
        correct: true
        why: Right. Static languages check the method set where the value is converted to the interface type. Python's Protocol is a hint for mypy or pyright; the interpreter finds out on the line that reads it.
      - text: In all four languages, at runtime, the first time Slack is used.
        why: Go, TypeScript and Rust refuse to compile the conversion. Only Python waits for runtime.
      - text: In all four languages, at compile time, because every one of them has an interface or Protocol type.
        why: Python does not check Protocols when the program runs. Without mypy or pyright, the missing attribute is an AttributeError at runtime.

    - role: Caller
      example: NotificationService.notify
      job: Calls methods on the interface. Never asks which type it holds.
    - role: Interface
      example: { go: "Notifier (interface)", python: "Notifier (Protocol)", typescript: "Notifier (interface)", rust: "Notifier (trait)" }
      job: The few methods the caller needs, named once.
    - role: Implementation
      example: "Email, SMS, Push, WhatsApp"
      job: One way of doing those methods each. Can have more methods; the caller does not see them.
    - role: Wiring
      example: main
      job: The one place that knows the concrete types and plugs them in.
  useWhen:
    - The same decision about a type is made in more than one place (here, quiet hours and sending).
    - New implementations are expected, or you want a fake in tests.
    - Callers only need a few operations from a richer object.
  avoidWhen:
    - There is one implementation and no test that needs another. An interface with one implementation is indirection with nothing on the other side.
    - The set of cases is closed and owned by you, and you want the compiler to force every caller to handle each one. An enum with an exhaustive match does that better.
  tradeoffs:
    - You read one more name (the interface) to find the code that runs.
    - Calls through an interface are indirect and usually not inlined.
    - The interface is a contract. Changing it changes every implementation and every fake.
  lookalikes:
    - name: Strategy
      how: Strategy is this idea applied to one step that varies, chosen by the caller. Interfaces and polymorphism are the mechanism under it and most other patterns.
    - name: Enum with exhaustive match
      how: The opposite trade. Adding a case edits every match, but the compiler finds them all. Good for closed sets such as order states; poor for open sets such as channels.
    - name: Adapter
      how: Makes an existing type with the wrong methods fit an interface, by wrapping it. Useful when the implementation is a library you cannot edit.

## [concept] Interfaces and polymorphism

**Let callers depend on a small <Term id="interface">interface</Term>, so any implementation can be plugged in and the caller never checks which one it got.**

The caller writes one call. Each implementation runs its own code behind it. That is <Term id="polymorphism">polymorphism</Term>, and it replaces the type checks that would otherwise spread through the caller.

<Depth level={2}>
An interface is a promise about methods: "whatever you give me can `send` and can tell me whether it `wakesPeople`". The caller programs against that promise. A new implementation only has to keep it. It never has to be known to the caller, and it can have extra methods the caller ignores.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* book states this as its first principle of reusable design: program to an interface, not an implementation. Its argument is about dependencies. A caller that names concrete classes depends on all of them, and on their number. A caller that names one interface depends on that alone. Something still has to create the concrete objects, which is why that book follows the principle with the creational patterns.
</Depth>

## [problem] A notifier that knows every channel

A notification service sends password resets, shipping updates and login alerts. Each user picks a channel: email, SMS or push. SMS and push wake people up, so at night they wait in a queue until morning.

Read it once. The list of channels appears twice: in the quiet-hours check, and in the switch that sends.

<Depth level={2}>
Each branch calls a different client with different arguments, so the switch is not just noise. But both checks are questions about the channel ("do you wake people?", "how do you send?") that the caller answers on the channel's behalf.
</Depth>

<Depth level={3}>
Testing `Notify` means building a Service with real email, SMS and push clients, or adding a "fake" case to the switch. Neither is good. The first sends real messages or needs network stubs. The second puts test code in production.
</Depth>

## [pain] Then a change request arrives

**Change request:** the Brazil launch needs WhatsApp as a notification channel.

Two places change, and only one of them fails loudly if you forget it. Miss the send switch and WhatsApp users get an error. Miss the quiet-hours list and everything compiles, every test passes, and customers get WhatsApp messages at three in the morning.

<Depth level={2}>
This is the cost of type checks: one fact about WhatsApp (it wakes people) lives in the caller, far from WhatsApp's code. Every new channel has to visit every place the caller branches, and the caller grows with each one.
</Depth>

<Depth level={3}>
<Lang only="rust">A Rust enum with an exhaustive `match` would catch the forgotten arm. Here the channel is a string from the user's settings, so `matches!` and the catch-all arm `other =>` hide the gap.</Lang>
<Lang only="go">Go's `switch` has no exhaustiveness check, and a string switch has nothing to check against anyway. The forgotten case falls through to the default, silently in the quiet-hours switch.</Lang>
<Lang only="python">Python cannot warn here. `user.channel in ("sms", "push")` is simply false for `"whatsapp"`.</Lang>
<Lang only="typescript">If `channel` were a union type, `switch` plus a `never` check could catch the missing case. The `||` chain in the quiet-hours check would still be wrong without a warning.</Lang>
</Depth>

## [morph] Ask the channel instead

Drag the slider. Both checks collapse into two methods on one interface. Each channel answers the questions about itself.

Hover a box in the diagram to see its code.

<Depth level={2}>
`notify` now depends on `Notifier` and on the map it was given, nothing else. Each channel can be tested alone, and `notify` can be tested with a fake that records messages. The map is built in `main`, the one place that has to know concrete types.
</Depth>

<Depth level={3}>
<Lang only="go">`WhatsApp` never says it implements `Notifier`. Having both methods is enough, and the compiler checks it where the value is put in the `map[string]Notifier`.</Lang>
<Lang only="python">`Notifier` is a `Protocol`: a description for type checkers. At runtime, `notify` calls whatever is in the dict. That is <Term id="duck-typing">duck typing</Term>, written down.</Lang>
<Lang only="typescript">TypeScript checks shape, not ancestry (<Term id="structural-typing">structural typing</Term>). A test can pass `{ wakesPeople: false, send: async () => {} }` and it fits.</Lang>
<Lang only="rust">Each type opts in with `impl Notifier for …`. The map stores `Box<dyn Notifier>`, so channels of different types and sizes can live in one collection.</Lang>
</Depth>

## [walk] Follow one message

One SMS, sent at 03:12 and again in the afternoon. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">A call through an interface loads the method address from the <Term id="itab">itab</Term> stored with the value and calls it indirectly: <Term id="dynamic-dispatch">dynamic dispatch</Term>. The itab for each (type, interface) pair is built once and cached.</Lang>
<Lang only="python">`notifier.send(...)` looks up `send` on the object's class at runtime and calls it. There is no table to check against, so a wrong object fails on this line, not earlier.</Lang>
<Lang only="typescript">The interface is erased at compile time. At runtime `n.send` is a property lookup; V8's inline caches keep it fast while a call site sees only a few object shapes.</Lang>
<Lang only="rust">`Box<dyn Notifier>` is a fat pointer: one pointer to the data, one to a vtable with `send` and `wakes_people`. Each call goes through the vtable: <Term id="dynamic-dispatch">dynamic dispatch</Term>.</Lang>
</Depth>

### Small interfaces

Define an interface where it is used, with only the methods that caller needs. The notifier needs `send` and `wakesPeople`, so that is the interface, even if the Twilio client has forty methods. Small interfaces are easy to implement, easy to fake and hard to misuse. If another caller needs more, give it its own interface.
