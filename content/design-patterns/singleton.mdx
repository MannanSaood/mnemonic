    - role: Composition root (the alternative)
      example: main
      job: Creates the one instance and passes it to whatever needs it.
  useWhen:
    - Something really must exist once per process, such as a connection pool, a metrics registry or the process's logger.
    - Creating it twice would waste or exhaust a limited resource.
    - Even then, prefer creating it in main and passing it in. Keep the global accessor for code you do not control.
  avoidWhen:
    - The only reason is to avoid passing a parameter.
    - The object holds settings that tests, tenants or requests need to vary.
    - Tests must run in parallel.
  tradeoffs:
    - Hidden dependencies. A function's signature no longer says what it uses.
    - Tests share state. Order and parallelism start to matter, and resets only fix order.
    - Hard to change later. Going from one to one-per-tenant edits every caller.
    - Lazy initialisation must be thread-safe, or you get more than one.
  lookalikes:
    - name: Dependency injection
      how: Keeps the one instance and drops the global access. It is the usual replacement for a singleton.
    - name: Monostate
      how: Many instances that share their state through static fields. The same coupling, harder to notice.
    - name: Flyweight
      how: Shares instances to save memory, one per distinct value. A singleton is one instance in total.
    - name: Service locator
      how: A global registry you ask for dependencies. It hides dependencies the same way a singleton does.

## [concept] Singleton

**Make sure a class has one instance and give everyone a global way to reach it. Sometimes one instance is right; the global access is usually the part to drop.**

Some things should exist once per process. That does not mean every function should be able to reach them without asking.

<Depth level={2}>
The pattern bundles two ideas. *One instance* is often reasonable: a connection pool, a metrics registry. *Global access* is where it hurts. Any code can read or change <Term id="global-state">global state</Term>, so functions get <Term id="hidden-dependency">hidden dependencies</Term> their signatures do not show, and tests start depending on each other. <Term id="dependency-injection">Dependency injection</Term> keeps the first idea and drops the second.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue presents Singleton as an improvement over global variables: the class controls its sole instance, keeps it out of the global namespace, and can later allow subclasses or more than one instance. Its examples are a print spooler and a file system. The book also describes a registry of singletons for choosing a subclass at runtime. Later practice turned more critical. In 2008 Miško Hevery argued on the Google Testing Blog that singletons let an API lie about its dependencies, and that is now the common view.
</Depth>

## [problem] One config, reachable from anywhere

A pricing service reads its region and feature flags from a config that is loaded once and reached globally. Quote calls it directly, and so do billing, reports and a dozen other places.

Read it once. Nothing in Quote's signature says it depends on configuration.

<Depth level={2}>
Look at the test. To try the new pricing, it changes the global, and it never changes it back. Every test that runs after it in the same process sees the new pricing flag. Each test passes alone, and the suite fails depending on order.
</Depth>

<Depth level={3}>
<Lang only="go">`go test` runs the tests in one package sequentially by default, but `t.Parallel()` and the shared global do not mix. The `-shuffle` flag makes order-dependent failures show up early.</Lang>
<Lang only="python">pytest runs tests in one process, in file order, so the leak is deterministic until the order changes. With pytest-xdist, tests run in several processes, and the failures start to move around.</Lang>
<Lang only="typescript">Jest and Vitest give each test file its own module registry, so the leak stays inside one file. Within that file, it follows the order of the tests.</Lang>
<Lang only="rust">`cargo test` runs tests in parallel threads by default. The `RwLock` keeps the global memory-safe, but two tests can still see each other's settings. `--test-threads=1` hides the problem by giving up parallelism.</Lang>
</Depth>

## [pain] Then a change request arrives

**Change request:** pricing must use each tenant's own region and flags.

One global config cannot be two configs at once. The global turns into a map keyed by tenant, and every caller has to pass a tenant ID it never needed before.

<Depth level={2}>
The hard part is finding the callers. They are not listed in any signature: you search for `config.Get()`, or the import, and hope nothing reaches it indirectly. The cost meter says "every hidden caller" because nobody can count them in advance.
</Depth>

<Depth level={3}>
The tests stay coupled too. They now write into the global map under a tenant ID, which is the same shared state with a longer name.
</Depth>

## [morph] Keep one instance, pass it in

Drag the slider. The global accessor disappears. `main` creates the one config and passes it to Pricing through the constructor.

Hover a box in the diagram to see its code.

<Depth level={2}>
There is still exactly one config in production. What changed is who can reach it: only code that was handed it. The dependency shows up in `NewPricing(cfg)`, tests build their own, and a second config for a second tenant is just another constructor call. The place where `main` wires everything together is often called the composition root.
</Depth>

<Depth level={3}>
<Lang only="go">The `Pricing` struct holds a `*Config`. If the config can change at runtime, make the struct hold an interface or an `atomic.Pointer[Config]` so readers always see a whole config.</Lang>
<Lang only="python">Nothing stops another module from still importing a global, so make the module that builds `Settings` the only one that calls `from_env()`. A linter rule against importing it elsewhere helps.</Lang>
<Lang only="typescript">`private readonly config: Config` is a parameter property: it declares the field and assigns it in one line. Tests can pass a plain object literal, since types are structural.</Lang>
<Lang only="rust">`Arc<Config>` lets many services share one immutable config cheaply. If it must change at runtime, `arc_swap` or an `RwLock<Arc<Config>>` swaps the whole value at once.</Lang>
</Depth>

## [walk] Follow the config from main to a quote

One config, from startup to a price, and then a test. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`sync.Once` uses an atomic flag for the fast path and a mutex for the first call, so later calls cost one atomic load. With injection there is no such cost: the pointer is a struct field.</Lang>
<Lang only="python">A module-level object is created when the module is first imported, under the import lock, and then cached in `sys.modules`. That is why it behaves as a singleton without any code to enforce it.</Lang>
<Lang only="typescript">Node evaluates a module once and caches it by resolved path. The same package resolved to two different paths, for example two versions in `node_modules`, is two modules with two "singletons".</Lang>
<Lang only="rust">`LazyLock` runs its closure on first access and blocks other threads until it finishes. Reading an `Arc<Config>` field afterwards is a plain pointer load.</Lang>
</Depth>

## [again] Per-tenant pricing, the second time

The same request after the refactor. `main` builds one Pricing per tenant, from that tenant's config. Pricing, Quote and their tests do not change at all.

<Depth level={2}>
When one instance really is the right answer, keep it, and make it safely. A connection pool should be created once, with a once-guard: <Term id="once-initialisation">once-initialisation</Term> such as `sync.OnceValue`, a module import, or `OnceLock`. A plain "if nil, create" check is a <Term id="data-race">data race</Term> that can open several pools at a cold start.
</Depth>

<Depth level={3}>
Global singletons still have honest uses: the process's logger and metrics registry, which libraries you do not control need to find, or `stdout`. Even then, prefer handing them to your own code explicitly and keeping the global only as the default.
</Depth>
