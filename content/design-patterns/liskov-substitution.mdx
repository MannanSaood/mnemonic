## [concept] Liskov substitution

**Every implementation of an interface must keep every promise the interface makes. Then callers never need to know which one they were given.**

Barbara Liskov stated it in 1987: a type S is a subtype of T if programs written for T behave the same when given an S. The <Term id="liskov-substitution">Liskov substitution principle</Term> is that rule applied to everyday code. Matching method names and signatures is not enough. The behaviour callers rely on has to match too.

<Depth level={2}>
The promises are a method's <Term id="precondition">preconditions</Term> (what it accepts), its <Term id="postcondition">postconditions</Term> (what it guarantees afterwards) and the errors it may return. An implementation may accept more and promise more. It may not demand more, promise less or fail in new ways. When it does, callers start checking which implementation they hold, and every new one means editing them.
</Depth>

<Depth level={3}>
Liskov gave the substitution property in her OOPSLA 1987 keynote, "Data Abstraction and Hierarchy". In 1994 she and Jeannette Wing defined <Term id="behavioural-subtyping">behavioural subtyping</Term> formally in "A Behavioral Notion of Subtyping": any property provable about objects of the supertype must hold for objects of the subtype. They added the <Term id="history-constraint">history constraint</Term>, so a subtype cannot allow state changes its supertype rules out. Robert C. Martin made it the L in SOLID, and in *Clean Architecture* he applies it beyond classes, to any set of implementations behind one interface, including services behind one REST API.
</Depth>

## [problem] An archive that cannot store

Every store implements BlobStore, and every caller was written against S3. A new ArchiveStore holds closed years in cold storage. Writes there are switched off, so its Put and Delete return a read-only error.

Read it once. It compiles. Nothing in the types says Put might refuse.

<Depth level={2}>
Preview reads an image, makes a smaller copy and caches it with Put. With S3 that always works. With the archive, the read succeeds and the cache write fails, so the preview fails too.
</Depth>

<Depth level={3}>
The archive breaks the contract by adding a failure the callers were never told about. Returning an error value instead of throwing changes nothing: callers written against S3 treat any error from Put as a real failure.
</Depth>

## [pain] Then a change request arrives

**Change request:** compliance moves closed years to cold storage, and the customer portal must still show those invoices with previews.

The quick fix goes into Preview: if the store is the archive, skip the cache. The marked lines show it. The same check goes into every other caller that writes.

<Depth level={2}>
Each check names one implementation, so the callers now depend on the archive. The next read-only store, a legal-hold bucket say, needs the same edits in the same places. Martin's taxi example in *Clean Architecture* ends the same way: one dispatch service that broke the shared REST contract forced special-case code into the system that used them all.
</Depth>

<Depth level={3}>
<Lang only="go">The type assertion `s.(ArchiveStore)` compiles anywhere, so nothing reminds you to add it to the next caller. A wrapper around the archive would also slip past it.</Lang>
<Lang only="python">`isinstance` checks the class, so a wrapper or a second read-only class slips past it.</Lang>
<Lang only="typescript">`instanceof` checks the prototype chain at runtime. A plain object with the same shape, or an archive from another copy of the package, slips past it.</Lang>
<Lang only="rust">There is no cheap runtime type check on a `&dyn BlobStore`, so the fix grows the trait instead. `is_read_only()` now sits on every store, and every new store must answer it.</Lang>
</Depth>

## [again] Cold storage, the second time

The portal passes the archive as the source and S3 as the cache. Preview does not change, and neither does any other caller. A caller that writes cannot be given the archive by mistake, because that no longer builds.

<Depth level={2}>
Not every promise fits in a type. Read-after-write consistency, key limits and timing live in documentation and tests. A shared contract test suite, run against every implementation, is how teams catch those breaks before callers do.
</Depth>

<Depth level={3}>
Contract tests are Liskov's definition made executable: one suite written against the interface, run once per implementation. If the replica fails the "get after put" test, it is not a BlobStore yet, whatever the compiler says.
</Depth>

### The rules, in one place

Liskov and Wing's rules for a behavioural subtype, in the words of this lesson: accept at least the inputs the interface accepts; guarantee at least what it guarantees; fail only in the ways it says it may fail; keep its invariants; and allow no state changes it rules out. Anything else a subtype adds is fine.
