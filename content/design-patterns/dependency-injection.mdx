        why: That works, but it is injection through a global. Every test that sets the variable must unset it, and tests running at the same time see each other's dates.
  engineer:
    question: Where should the real Postgres source and the real clock be created?
    options:
      - text: In main, or the job's entry point, which builds them and passes them down.
        correct: true
        why: Right. That is the composition root. Everything below it receives its dependencies and never decides which ones are real.
      - text: Inside the report, with optional parameters that override them in tests.
        why: The defaults keep the hidden dependencies, so callers can still forget to pass them. Production and tests take different paths through the code.
      - text: In a global registry that the report looks up when it runs.
        why: That is a service locator. The report's signature no longer says what it needs, and a missing registration fails at runtime.
  deep:
    question: A team stubs the clock by swapping a package-level variable in their tests instead of passing it in. Once tests run in parallel, some fail at random. Why?
    options:
      - text: The variable is shared by every test in the process, so one test's fake January date leaks into another test running at the same time.
        correct: true
        why: Right. A global hook is shared mutable state. An argument belongs to one call, so parallel tests cannot see each other's values.
      - text: Parallel tests make the system clock less accurate.
        why: The real clock is fine. The failures come from tests overwriting the same variable.
      - text: The compiler or interpreter caches the old value of the variable.
        why: Nothing is cached. Each read sees whatever value was written last, which is exactly the problem.

  avoidWhen:

    - Signatures grow, and every caller must supply the dependencies.
    - Someone has to build the object graph; in a big application that wiring code is real code to maintain.
    - Fakes can drift from the real implementation, so a few tests against the real database are still needed.

      how: Code asks a global registry for its dependencies. Testable, but the dependencies are hidden from the signature and fail at runtime when missing.

## [concept] Dependency injection

**Pass a function the things it depends on, such as the clock and the database, instead of letting it reach out and grab them.**

Code that asks the system for the time, or opens its own connection, gets whatever the world gives it. Code that receives them as arguments gets whatever the caller chooses, and in a test, the caller is you.

<Depth level={2}>
That is all <Term id="dependency-injection">dependency injection</Term> means. No framework is needed. Dependencies come in as plain values (the date) or as small interfaces (the invoice source). The real ones are created in one place near `main`, the <Term id="composition-root">composition root</Term>. Tests create <Term id="test-double">test doubles</Term> instead.
</Depth>

<Depth level={3}>
Martin Fowler named the pattern in his 2004 article on inversion of control containers, and described three forms: constructor injection, setter injection and interface injection. Constructor (or argument) injection is the one most code uses today. Michael Feathers calls the place where behaviour can be swapped without editing the code a <Term id="seam">seam</Term>; an argument is the simplest seam there is.
</Depth>

## [problem] A report that grabs its own inputs

On the first of each month, a job emails the CFO last month's revenue. The report finds last month from today's date, opens the billing database, and sums the invoices.

Read it once. The two lines that make it hard to test are the first ones: it asks the clock for today, and it opens a connection from an environment variable.

<Depth level={2}>
To test it as written, you need a real Postgres with seeded invoices, and you get today's date whether you like it or not. So it is tested by hand, once, and then trusted.
</Depth>

<Depth level={3}>
The report also mixes two jobs: deciding the period and fetching the data. Each is easy to test alone. Together, behind a clock call and a connection, neither is.
</Depth>

## [pain] Then a change request arrives

**Change request:** Finance found a wrong January report. Add a regression test that runs the report on 5 January.

The marked lines are what it takes without injection: a global hook so the test can fake "now", restored after every test, and a real database seeded with December invoices. The test is slow, it needs infrastructure, and tests that touch the hook cannot run in parallel.

<Depth level={2}>
The usual workaround is a shared staging database. Then the test's answer depends on what other teams left in it, so the same test passes one run and fails the next. Teams learn to ignore it.
</Depth>

<Depth level={3}>
<Lang only="python">`freezegun` or `mock.patch("report.datetime")` can fake the clock without a hook. It works, but it patches by import path: rename an import and the patch silently stops applying.</Lang>
<Lang only="go">A package-level `var nowFunc = time.Now` is a common Go hook. Tests that swap it cannot use `t.Parallel()`, and `go test -race` flags them if they try.</Lang>
<Lang only="typescript">Fake timers can freeze `new Date()` for a test. They also replace `setTimeout` and its relatives, which other code in the test, such as a database driver or a retry loop, may rely on.</Lang>
<Lang only="rust">The test harness runs each test on its own thread, so a thread-local hook stays per test. Under a multi-threaded async runtime, though, the report can run on a worker thread that never saw the hook.</Lang>
</Depth>
