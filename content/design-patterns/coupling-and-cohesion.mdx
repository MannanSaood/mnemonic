    - role: Owner module
      example: Inventory
      job: Keeps its data private and answers questions about it.
    - role: Small API
      example: { go: "Available, Reserve", python: "available, reserve", typescript: "available, reserve", rust: "available, reserve" }

    - role: Callers
      example: Orders, Shipping
      job: Depend on the API only. They never name the data's shape.
  useWhen:
    - Several modules read or write the same data structure, or the same database table.
    - A change in one team's module regularly breaks another team's build or tests.
    - Logic about a piece of data (checks, conversions, formatting) is repeated in the modules that use it.
  avoidWhen:
    - The data really is a plain record passed between steps, such as a DTO or an event. Wrapping every field in getters adds ceremony without hiding a decision.
    - The two pieces always change together and are owned by one person. Merging them is the cohesive move; an API between them is overhead.
  tradeoffs:
    - Callers can only do what the API offers. A new need means a new method on someone else's module.
    - An API that copies the data's shape one getter per field hides nothing; the coupling remains.
    - Moving logic next to its data can make the owner module bigger. That is fine while the logic shares one reason to change.
  lookalikes:
    - name: Single responsibility
      how: Cohesion seen from one class. A class should have one reason to change, which is the same as keeping things that change together in one place.
    - name: Facade
      how: Gives a subsystem one simpler entry point. It lowers coupling to the subsystem as a whole, where this lesson is about each module guarding its own data.
    - name: Law of Demeter
      how: A rule of thumb against long chains like `order.customer.address.zip`. Each dot reaches one level further into someone else's structure.

## [concept] Coupling and cohesion

**Keep the code that changes together in one place, and let other modules ask it questions instead of reaching into its data.**

Two pieces of code are <Term id="coupling">coupled</Term> when changing one forces you to change the other. A module is <Term id="cohesion">cohesive</Term> when the code inside it belongs together, so one change stays inside it.

<Depth level={2}>
The two are linked. If a module's data can be read from anywhere, every reader is coupled to its shape, and the logic about that data spreads to the readers. Keeping the data private (<Term id="encapsulation">encapsulation</Term>) and moving the logic next to it does both at once: fewer couplings, more cohesion. Coupling is always about a change. Two modules can be tightly coupled for one change and independent for another.
</Depth>

<Depth level={3}>
The terms come from Larry Constantine's structured design work, published with Ed Yourdon in *Structured Design* (1979). Kent Beck's *Tidy First?* restates them in terms of change: elements are coupled with respect to a particular change, and a cohesive element keeps the coupled sub-elements together. Meilir Page-Jones later named the kinds of coupling <Term id="connascence">connascence</Term>, ranked from weak (agreeing on a name) to strong (agreeing on positions, timing or values).
</Depth>

## [problem] An order service that shares its stock

An online shop has an Inventory module that tracks units on hand per SKU. Orders checks stock and takes units when a customer buys. Shipping reads stock to promise "ships today". Each is owned by a different team.

Read it once. Inventory is three lines. The logic about stock, checking it and taking units out of it, lives in Orders and Shipping.

<Depth level={2}>
Nothing here is a bug. It is short and fast, and each team wrote the obvious code with the map they could see. The cost is hidden: both teams now depend on the map's exact shape.
</Depth>

<Depth level={3}>
In connascence terms, Orders and Shipping are connascent with Inventory on type (a map from SKU to int) and on meaning (the value is units on hand, everywhere, in one warehouse). Those agreements are written nowhere, so the compiler can only enforce the first.
</Depth>

## [pain] Then a change request arrives

**Change request:** a second warehouse opens, so stock must be kept per warehouse.

Inventory's change is one line. The marked lines in Orders and Shipping must change too, and they belong to two other teams. Both now need a "total across warehouses" helper, so it gets written in Orders and imported by Shipping, and a new coupling appears while you fix the old one.

<Depth level={2}>
The three edits must ship together. If Inventory deploys first, Orders and Shipping index the new nested map with a SKU and get nothing back. Three teams, one release, and a migration for the data in between.
</Depth>

<Depth level={3}>
<Lang only="go">Go catches the type change at compile time in the same module: `o.inv.Stock[l.SKU] < l.Qty` no longer compiles. Across a service boundary, through JSON or a shared table, nothing would catch it.</Lang>
<Lang only="python">Python catches nothing until the code runs. `stock.get(sku, 0)` on the new nested dict returns 0 for every SKU, so every product looks out of stock.</Lang>
<Lang only="typescript">The compiler flags `stock.get(sku)` returning a `Map` where a number was expected, in each file that reads it. That makes the ripple easy to find, not small.</Lang>
<Lang only="rust">The compiler flags every use in every module. The ripple is easy to find, and still three teams' code.</Lang>
</Depth>

## [morph] Move the questions next to the data

Drag the slider. The stock map goes private. The checks and the decrement move into Inventory as two methods, and Orders and Shipping call those.

Hover a box in the diagram to see its code.

<Depth level={2}>
The new methods are shaped by what callers need ("are there enough?", "take these"), not by how stock is stored. That is what makes them survive the change. A getter that returns the map would hide nothing.
</Depth>

<Depth level={3}>
The connascence got weaker. Callers now agree with Inventory only on method names and argument types (connascence of name and type), and those are checked by the compiler. The meaning of the stored numbers is known in one module only.
</Depth>

## [walk] Follow one order

One order placed, one shipping promise made. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">The boundary is the package: `stock` is unexported, so code in package `orders` cannot name it. A method call on `*Inventory` is a direct call, and small methods like `Available` are usually inlined, so the API costs nothing at runtime.</Lang>
<Lang only="python">`_stock` is still reachable; only convention protects it. The call to `available` is an attribute lookup plus a call, a few tens of nanoseconds, next to a database round trip that dominates.</Lang>
<Lang only="typescript">`#stock` is a true private field: the engine stores it outside the object's normal properties, so `Object.keys` and `JSON.stringify` do not see it either.</Lang>
<Lang only="rust">Privacy is per module and checked at compile time. `available` is a plain method call that the optimiser usually inlines, so the boundary has no runtime cost.</Lang>
</Depth>

## [again] Per-warehouse stock, the second time

The same request, after the refactor. Inventory changes its map and the body of `available` and `reserve`. Orders and Shipping do not change, so one team ships it, in one deploy.

<Depth level={2}>
Not every change stays local, and that is fine. Picking which warehouse ships an order is new behaviour that Shipping may need to know about. Then Inventory's API grows a method. That is a conversation about a real feature, not bookkeeping over someone else's map.
</Depth>

<Depth level={3}>
The same reasoning applies across services: a shared database table is the tangled design at a larger scale. Each service owning its data and exposing an API is the cohesive one, with a network call where a method call was.
</Depth>

### A quick test for coupling

Pick a change your team is likely to get next quarter. List every file it would touch, and who owns each one. If the list crosses team lines for a change that is about one thing, find the data or the decision that is shared, and move it behind one owner.
