    - The factory has to be passed to everything that creates products, or the choice leaks back out.
  lookalikes:
    - name: Factory Method

      how: Can implement a factory by cloning a registered example of each product instead of naming classes.

## [concept] Abstract Factory

**Put the creation of a whole family of related objects behind one interface, so code picks the family once and can never mix parts from two families.**

Objects that must work together come from one place, and that place only knows how to make matching sets.

<Depth level={2}>
The **abstract factory** (`CloudFactory`) has one creation method per product: storage, queue, secrets. Each **concrete factory** (AWS, GCP) implements all of them for its own cloud. The service receives one factory through <Term id="dependency-injection">dependency injection</Term> and only ever sees the <Term id="product-role">product</Term> interfaces.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue, where the pattern is also called Kit, uses widget toolkits for its example: one factory per look and feel, so Motif scroll bars never appear next to Presentation Manager buttons. It lists four consequences. The pattern isolates concrete classes, makes exchanging families easy and promotes consistency among products, and it makes supporting new kinds of product difficult. It also notes that an application usually needs only one concrete factory per family.
</Depth>

## [problem] Three settings that must agree

A service stores uploads in object storage. Storage notifies a queue, and a worker reads a database password from the secrets store before it processes the file. Production runs on AWS; the company is moving to GCP.

Read it once. Storage, queue and secrets are each chosen by their own setting and their own switch.

<Depth level={2}>
Each switch is correct on its own. The bug lives between them. Nothing in the code says that S3 can only notify SQS, or that the worker can only read secrets from the cloud it runs in.
</Depth>

<Depth level={3}>
The config can express eight wirings, and two of them are real deployments. Most of the other six fail with an error, but some fail silently: storage from one cloud, a queue from another, and uploads that are accepted and then never processed.
</Depth>

## [pain] Then a change request arrives

**Change request:** the EU region must run on Azure.

Every switch needs an Azure case, and every environment file needs three new values. Miss one value and the code is happy to build a mixed set.

<Depth level={2}>
Look at the env line. It is the kind of slip a reviewer does not catch: two of three settings changed. Azure Blob Storage cannot deliver its events to SQS, so EU uploads succeed and are never processed.
</Depth>

<Depth level={3}>
Tests do not help much. Each switch has its own tests and they all pass. The failure only appears in the combination, and the number of combinations grows with the cube of the number of clouds.
</Depth>

## [morph] Make the family the unit of choice

Drag the slider. The three switches collapse into one interface, and each cloud becomes one type that makes all three products.

Hover a box in the diagram to see its code.

<Depth level={2}>
The choice moves from three settings to one. A family can still be the wrong one for the environment, but then everything fails at once and loudly, which is easy to see and to fix.
</Depth>

<Depth level={3}>
<Lang only="go">Go checks that `GCP` satisfies `CloudFactory` where a `GCP` is passed as one. It does not check that the three products belong together; that comes from writing them in one type.</Lang>
<Lang only="python">mypy checks that `Gcp` fits the `CloudFactory` Protocol. Nothing at runtime ties the products together except that one class builds them all.</Lang>
<Lang only="typescript">The interface is structural, so a test can pass `{ blobStore: () => fakeStore, queue: () => fakeQueue, secrets: () => fakeSecrets }` without any class.</Lang>
<Lang only="rust">Each `impl Cloud` fixes three <Term id="associated-type">associated types</Term> at once. `Service<Gcp>` is a different type from `Service<Aws>`, and their fields can only be that cloud's products.</Lang>
</Depth>

## [walk] Follow the service starting up

One startup on GCP, from the setting to a running service. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Each `f.BlobStore()` call goes through the interface's method table. It happens three times at startup and never again, so the cost does not matter.</Lang>
<Lang only="python">`cloud.blob_store()` is an ordinary method call on whatever object `cloud_for` returned. A `Protocol` adds nothing at runtime.</Lang>
<Lang only="typescript">The interface disappears after compilation. At runtime `cloud.blobStore()` is a property lookup on the object `cloudFor` returned.</Lang>
<Lang only="rust">`Service::new(&Gcp { … })` is compiled for `Gcp` specifically. Every call to `cloud.blob_store()` is static, and the `match` in `main` is the one place where the family is chosen at runtime.</Lang>

## [again] Azure, the second time

The same Azure request after the refactor. You add one type that makes Azure's three products. The switches are gone, and the environment file has one value to set, so there is no setting left to miss.

<Depth level={2}>
The pattern's bill arrives with the other kind of change. If every cloud needs a cache next quarter, the factory interface grows a method and every factory must implement it. Abstract Factory makes new families cheap and new products expensive. Choose it when you expect more of the first.
</Depth>

<Depth level={3}>
Tests benefit too. One fake factory that returns an in-memory store, queue and secrets map lets you test the service without any cloud, and the fakes always come as a matching set.
</Depth>

### Families as configuration
