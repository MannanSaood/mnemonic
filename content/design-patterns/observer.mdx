    - role: Subject
      example: OrderService
      job: Keeps the list of listeners, lets them subscribe and unsubscribe, and notifies all of them.
    - role: Observer
      example: { go: "OrderListener (interface)", python: "Listener (a Callable type)", typescript: "OrderListener (function type)", rust: "OrderListener (trait)" }
      job: The one method every listener has.
    - role: Concrete observer
      example: "Email, Stock, Analytics, Fraud"
      job: Reacts to the event in its own way.
    - role: Client
      example: main
      job: Creates the listeners and subscribes them.
  useWhen:
    - One event, several independent reactions, and the set of reactions changes more often than the event does.
    - The code that raises the event sits lower in the layers than the code that reacts, and should not depend on it.
    - Listeners come and go at runtime, like open UI panels or connected clients.
  avoidWhen:
    - The caller needs an answer or a veto from the reaction. Call it directly.
    - The reactions must happen in a strict order, or all succeed or fail together. Write that sequence out where it can be read.
    - There is exactly one reaction and no second in sight.
  tradeoffs:
    - Reading the subject no longer tells you what happens after the event. You have to find who subscribed.
    - In-process, every listener's time and errors land on the code that raised the event.
    - Every subscribe needs a matching unsubscribe, or the listener lives as long as the subject.
    - A chain of listeners that change other subjects can set off a cascade of updates that is hard to trace.
  lookalikes:
    - name: Publish-subscribe through a broker
      how: The same idea across processes. A broker or outbox sits between publisher and subscribers, so neither waits for the other and messages survive crashes.
    - name: Mediator
      how: Colleagues talk to one hub that decides who does what. Observer only broadcasts; the subject decides nothing about the reactions.
    - name: Chain of Responsibility
      how: The request goes along a chain until one handler takes it. In Observer every subscriber gets the event.

## [concept] Observer

**Let an object announce that something happened, and let any number of other objects subscribe to hear about it, without the announcer knowing who they are.**

The <Term id="observer-subject">subject</Term> keeps a list of listeners and calls each one when the event happens. Adding a new reaction means adding a listener, not editing the subject.

<Depth level={2}>
Four roles do the work. The **subject** (`OrderService`) holds the list and notifies it. The **observer** is the one method every listener has, named as an <Term id="interface">interface</Term> or a function type. Each **concrete observer** (email, stock, analytics) reacts in its own way. The **client**, usually `main`, creates the listeners and subscribes them.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Observer under behavioral patterns and also calls it Dependents or Publish-Subscribe. It names the main benefit as abstract coupling: the subject only knows that its observers have one method. It also names the main cost, unexpected updates: because observers do not know about each other, a harmless-looking change to the subject can set off a costly cascade. The book describes a push model, where the subject sends the details with the notification, and a pull model, where it sends almost nothing and observers ask. Our `OrderPlaced` event is the push model.
</Depth>

## [problem] An order service that calls everyone

When an order is placed, the shop sends a confirmation email, reserves stock and records the sale for analytics. The order service calls all three clients, one after the other.

Read it once. The service knows the name, the method and the arguments of every team that cares about orders.

<Depth level={2}>
Each new reaction adds a field, a constructor argument and a call. The service's tests have to build or fake every client, even to test saving an order.
</Depth>

<Depth level={3}>
The dependencies point the wrong way. Orders are the core of the business. Email, analytics and fraud scoring are supporting features, yet the core module imports all of them, and a change to any of their client libraries can break the build of the order service.
</Depth>

## [pain] Then a change request arrives

**Change request:** the risk team needs every new order sent to their fraud-scoring service.

The marked lines change in three places: a new field, a new call and new wiring. None of them is about orders. The order service is edited because another team needs something.

<Depth level={2}>
The next team asks next month: loyalty points, a warehouse webhook, a Slack alert for large orders. Each one edits the same method, and the order team reviews every change to a module that should be about saving orders.
</Depth>

<Depth level={3}>
It also gets harder to test. The fraud client now has to be faked in every order-service test, including the ones that only check that an order is saved.
</Depth>

## [morph] Turn each call into a subscriber

Drag the slider. The three calls leave the order service. Each becomes a listener that implements one method, and the service keeps a list of them.

Hover a box in the diagram to see its code.

<Depth level={2}>
The order service now depends on one small type, `OrderListener`, instead of on every client library. New reactions extend the system without editing it, the <Term id="open-closed">open/closed principle</Term>. Each listener can be tested alone with a hand-made `OrderPlaced`, and the service can be tested with a fake listener that records what it heard.
</Depth>

<Depth level={3}>
<Lang only="go">Go funcs cannot be compared, so a listener stored as a `func` cannot be found again to remove it. If listeners come and go, have `Subscribe` return a func that removes this subscription, the way `context.AfterFunc` returns `stop`. If they can come and go while orders flow, guard the slice with a `sync.Mutex`, copy it under the lock, and call the listeners after releasing it.</Lang>
<Lang only="python">Bound methods compare equal when they wrap the same function and object, so `list.remove(mailer.on_order_placed)` finds the right entry. The loop iterates over `list(self._listeners)`, a copy, because removing an item from a list while iterating over it makes the loop skip the next item.</Lang>
<Lang only="typescript">Arrow functions are compared by identity. `orders.subscribe((e) => …)` cannot be undone later by passing an identical-looking arrow, because it is a different object. Returning the unsubscribe function avoids the problem. A `Set` keeps insertion order, so listeners are still called in the order they subscribed.</Lang>
<Lang only="rust">The subject owns each listener as a `Box<dyn OrderListener>`. That is the simple case. If a listener needs shared state, give it an `Arc` to that state. If it needs to reach back into the subject, use a `Weak` reference, because two `Rc`s pointing at each other are never freed.</Lang>
</Depth>

## [walk] Follow one order

One order through the design, start to finish. Step through it with the numbered buttons.

<Depth level={2}>
The last step is the one people forget. The subject does not know its listeners, but it still runs them. In-process, the code that raised the event pays for every listener's time and is exposed to every listener's errors. Decide for each listener whether that is acceptable. If it is not, catch and log its errors in the loop, or move it behind a queue.
</Depth>

<Depth level={3}>
<Lang only="go">A panic in a listener unwinds through `PlaceOrder`. `net/http` recovers a panic in a handler and logs it, so the server survives, but the customer's connection is dropped after the order was saved. Recover per listener only if you also log and alert, or the bug goes unseen.</Lang>
<Lang only="python">An exception from one listener leaves the `for` loop and `place_order`. Wrap each call in `try`/`except Exception` and log it if the listeners are independent; let it propagate if a failed listener should fail the request.</Lang>
<Lang only="typescript">Node's `EventEmitter` calls listeners synchronously, in the order they were added, and an exception from one propagates out of `emit`, so later listeners do not run. The DOM's `EventTarget` behaves differently: it reports a listener's exception and goes on to the next listener.</Lang>
<Lang only="rust">A panic in a listener unwinds through `place_order` and skips the rest. `std::panic::catch_unwind` can contain it, but panics are meant for bugs. A listener that can fail should handle and log its own errors, since the trait method returns nothing.</Lang>
</Depth>

## [again] Fraud scoring, the second time

The same request after the refactor. Fraud scoring is one new listener and one line of wiring. The order service does not change, and its tests do not change.

<Depth level={2}>
Decide what each listener may cost before you subscribe it. Fraud scoring calls a remote service; if it is slow or down, the in-process loop makes every checkout slow or failed. Have the listener enqueue a job and return, so the risk team's outage stays the risk team's.
</Depth>

<Depth level={3}>
Once listeners live in other services, the event has to survive crashes. Publishing to a broker after the database commit can lose the event if the process dies between the two. A <Term id="transactional-outbox">transactional outbox</Term> writes the event in the same transaction as the order, and a relay publishes it afterwards. Delivery becomes at least once, so listeners must handle duplicates.
</Depth>

### Unsubscribe, or leak

Every `subscribe` needs a matching unsubscribe. The subject holds a reference to each listener, so a listener nobody removed stays alive as long as the subject does and keeps running on every event. This is the <Term id="lapsed-listener">lapsed listener</Term> problem, and garbage collection does not fix it. Tie each subscription to a lifetime: return an unsubscribe function and call it when the panel, request or connection ends, or use an `AbortSignal` in JavaScript. Some languages offer a <Term id="weak-reference">weak reference</Term> (`weakref.WeakMethod` in Python, `Weak` in Rust) so the subject does not keep listeners alive. Node prints a `MaxListenersExceededWarning` when one event gets more than ten listeners, which is often the first sign of a leak.
