summary: Wrap an object in another object with the same interface, which adds one behaviour and passes the call on.
intent: Add responsibilities such as logging, auth or caching around an object without changing it, and choose which ones, in what order, when you wire it up.

            return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {

    edges: [logging>auth]
    role: outer
  - text: Auth checks the token. Without one it writes a 401 and returns. Nothing inside it runs, so a request it rejects never reaches Cache or the handler.
    nodes: [auth]
    edges: []
    role: reject
  - text: With a valid token, Auth attaches the user and calls the next wrapper. Cache keys on that user, which is why Cache must sit inside Auth.
    nodes: [auth, cache, context]
    edges: [auth>cache, cache>context]
    role: inner
  - text: The response unwinds outward through the same wrappers in reverse. Logging writes its line last, with the final status, whether it was a 200, a cached 200 or a 401.
    nodes: [logging]
    edges: []
    role: out

    question: Which of these situations calls for a Decorator?
    options:
      - text: Every storage client needs retries and metrics, and each deployment turns on a different mix of them.
        correct: true
        why: Right. Each extra is a wrapper with the storage client's own interface, so the mix and the order are chosen at wiring time, and the client itself never changes.
      - text: A legacy payment SDK has a different method signature from the interface the rest of the code expects.
        why: That is Adapter. It changes the interface. A decorator keeps the interface and adds behaviour.
      - text: The service compresses with gzip, zstd or brotli, chosen from config, and uses exactly one of them.
        why: That is Strategy. One algorithm is swapped in. Decorators are stacked, and several run on every call.

    question: In Rust, the stack is the type `Logging<Auth<Cache<Orders>>>`. What does that buy and cost compared with `Box<dyn Handler>` at each layer?
    options:
      - text: Calls between layers are static and can be inlined, but each order is a different type, so routes with different stacks need boxing to share one type.
        correct: true
        why: Right. The compiler monomorphises the nested generics into one concrete type. tower uses this, and offers boxed services such as `BoxCloneService` to erase the type when you need to.
      - text: Each layer allocates on the heap for every request.
        why: No. The nested structs live inside each other in one value, built once at startup. Nothing is allocated per request by the nesting itself.
      - text: The compiler can reorder the layers to run the cheapest check first.
        why: No. The order is part of the program's meaning. The compiler never changes which wrapper sees the request first.

reference:
  roles:
    - role: Component
      example: { go: "http.Handler (interface)", python: "Handler (callable type)", typescript: "Handler (function type)", rust: "Handler (trait)" }
      job: The interface that both the real object and every wrapper have.
    - role: Concrete component
      example: { go: handleOrders, python: handle_orders, typescript: handleOrders, rust: Orders }
      job: The object that does the real work. It knows nothing about the wrappers.
    - role: Decorator
      example: "Logging, RateLimit, Auth, Cache"
      job: Holds the next handler, adds one behaviour before or after calling it, and may answer early instead.
    - role: Client
      example: main, or the router setup
      job: Builds the stack and decides the order.
  useWhen:
    - Several optional extras around the same interface, in combinations that differ by route, deployment or config.
    - The extras are cross-cutting (logging, auth, retries, metrics, caching) and should not live inside business code.
    - You cannot or should not change the wrapped object, for example a client from a library.
  avoidWhen:
    - There is only one extra and it always applies. Put it in the object.
    - A wrapper needs to reach into the wrapped object's internals. That is a sign the behaviour belongs inside it, or that you want Strategy.
    - The stack is so deep that a stack trace through it is hard to read and nobody can say the order from memory.
  tradeoffs:
    - The order is part of the behaviour, but nothing in the type system checks it. Write it in one place and test the important orderings.
    - Many small wrappers. Debugging means stepping through every layer.
    - A wrapper is not the wrapped object. Identity checks, type assertions and extra methods of the inner object do not get through.
    - Each layer adds a call, and with interfaces or trait objects an indirect one. For HTTP this is noise next to the network.
  lookalikes:
    - name: Adapter
      how: Changes the interface of an object. A decorator keeps the interface and adds behaviour.
    - name: Proxy
      how: Same shape, but a proxy controls access to one object (lazy loading, remote calls) and usually creates or owns it. Decorators are stacked freely by the client.
    - name: Chain of Responsibility
      how: Each handler decides whether to pass a request on, and usually exactly one handles it. With decorators, every layer normally runs and wraps the next. HTTP middleware sits between the two.
    - name: Composite
      how: Also recursive, but a composite holds many children and combines their results. A decorator holds exactly one.
    - name: Strategy
      how: Swaps the inside of an object. A decorator changes it from the outside, and several can stack.

## [concept] Decorator

**Wrap an object in another object with the same <Term id="interface">interface</Term>. The wrapper adds one behaviour and passes the call on.**

Because a wrapper looks exactly like the thing it wraps, you can wrap a wrapper. HTTP <Term id="middleware-onion">middleware</Term> is the everyday example: logging, auth, rate limiting and caching each wrap the handler, and you choose which ones, and in what order, when you wire the route.

<Depth level={2}>
Four roles. The **component** is the shared interface (`http.Handler`, a handler function type, a trait). The **concrete component** does the real work (`handleOrders`). Each **decorator** holds the next component, does its own job before or after calling it, and may answer early instead: a <Term id="short-circuit-response">short-circuit</Term> such as a 401. The **client** (`main`, the router setup) builds the stack. The design leans on composition over inheritance: a subclass per combination would need 64 classes for four extras, and fixes the order at compile time.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Decorator as an object structural pattern, also known as Wrapper. It names two benefits: more flexibility than static inheritance, since wrappers can be attached and removed at runtime, and simple classes instead of one class loaded with every optional feature. It also names two costs: a decorated object is not identical to the original, so identity checks fail, and a design built from many small look-alike objects can be hard to learn and debug. It notes that the same decorator can be applied twice, and contrasts Decorator with Strategy: a decorator changes the skin of an object, a strategy its guts.
</Depth>

## [problem] Handlers that do everything

An API has an orders endpoint and a search endpoint. Each one checks the token, logs the request, and the orders one also caches. It works, and it is tested.

Read it once. The token check and the log line are copied into both handlers, and each early return has to remember to log.

<Depth level={2}>
The order of the concerns is hidden in the control flow. Auth runs before the cache because the cache key needs the user, but nothing says so; it is just the order of the `if` statements. Every handler re-decides that order.
</Depth>

<Depth level={3}>
The duplicated code also means duplicated bugs. When the log format changes, or a timing bug is found in the early returns, the fix goes into every handler, and the ones nobody remembers keep the bug.
</Depth>

## [pain] Then a change request arrives

**Change request:** security wants every endpoint rate limited per client IP, before the token check runs.

The marked lines must change, and they go into every handler. Each copy must sit in the right place: after the timer starts, so the 429 is logged, and before the token check, so floods never reach the identity service.

<Depth level={2}>
Two handlers today, more tomorrow. Miss one and it has no rate limit, and nothing fails: the requests still succeed. Put the check after the token check in one handler and that endpoint keeps calling the identity service for every flood request.
</Depth>

<Depth level={3}>
Tests do not catch this well. Each handler's tests must now cover rate limiting too, and the ordering between the limiter and the token check is only visible in tests that count calls to the identity service.
</Depth>

## [morph] Turn each concern into a wrapper

Drag the slider. The inline concerns leave the handler and become wrappers that all have the handler's shape, nested one inside the next.

Hover a box in the diagram to see its code.

<Depth level={2}>
The handler now does one thing. The order lives in one line of wiring per route, where a reviewer can read it from the outside in. Adding a concern means writing one wrapper and adding it to the wiring, without touching the handlers: the <Term id="open-closed">open/closed principle</Term>.
</Depth>

<Depth level={3}>
<Lang only="go">Go middleware is a function `func(http.Handler) http.Handler`. Each wrapper returns an `http.HandlerFunc` closure that captures `next`. Logging wraps the `ResponseWriter` in a small recorder so it can read the status after `next` returns, a second, smaller decorator inside the first.</Lang>
<Lang only="python">Each wrapper is a function that takes a handler and returns a new one, a closure over `inner`. This is the same mechanism the `@` syntax uses, but applied at wiring time, so the stack can differ by route or come from config.</Lang>
<Lang only="typescript">A middleware is a function from `Handler` to `Handler`. TypeScript uses <Term id="structural-typing">structural typing</Term>, so any function with the right parameter and return types fits, with no interface to implement.</Lang>
<Lang only="rust">Each wrapper is a generic struct `Logging<H>` with `impl<H: Handler> Handler for Logging<H>`. The stack's type spells out the order, and the compiler checks at every level that the inner value is a `Handler`.</Lang>
</Depth>

## [walk] Follow one request in and back out

One request through the stack, in and back out. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Each layer is an `http.HandlerFunc` called through the `http.Handler` interface: an indirect call per layer, a few nanoseconds each. The request travels down the Go stack, and the response travels back up it as the calls return.</Lang>
<Lang only="python">Each layer is a closure call: a frame per wrapper. Deep stacks show up in tracebacks as a column of `handle` frames, which is the debugging cost the catalogue warns about.</Lang>
<Lang only="typescript">Each layer awaits the next, so a request through four wrappers creates a chain of promises that resolve from the inside out. Code after `await next(req)` runs on the way out.</Lang>
<Lang only="rust">`Logging<Auth<Cache<Orders>>>` is one concrete type, built by <Term id="monomorphisation">monomorphisation</Term>, so the calls between layers are static and can be inlined. Storing layers as `Box<dyn Handler>` instead would make each call go through a vtable: <Term id="dynamic-dispatch">dynamic dispatch</Term>.</Lang>
</Depth>

## [again] Rate limiting, the second time

The same request after the refactor. You write one new wrapper and add it to the wiring, outside Auth. No handler changes, and every route that uses the shared stack gets it.

<Depth level={2}>
Keep the stack in one place, such as a list of middleware applied by a helper or by the router, so adding a wrapper is one line and the order is reviewed once instead of per route.
</Depth>

<Depth level={3}>
Test each wrapper alone with a fake inner handler: does RateLimit call it the first three times and not the fourth? Then add one test of the whole stack for the orderings that matter, such as "a request without a token never reaches the cache".
</Depth>

### The order is the design

A stack of decorators reads from the outside in, and the request travels the same way. Decide three things for each wrapper: what must already be known when it runs (Cache needs the user, so it sits inside Auth), which requests it must see (Logging must see rejections, so it sits outside them), and what it protects (RateLimit protects the identity service, so it sits outside Auth). Then write the order in one place and test it.
