    - You cannot or should not edit the real object, such as a vendor SDK.
  avoidWhen:

  tradeoffs:

## [concept] Proxy

**Put a stand-in with the same interface in front of an object, so you can control every call to it without changing the callers.**

The callers keep calling the same method. The stand-in decides whether the real object is reached, when, and how often.

<Depth level={2}>
Three roles. The <Term id="subject-role">subject</Term> is the <Term id="interface">interface</Term> callers use (`RateSource`). The <Term id="real-subject">real subject</Term> does the work (the vendor's client). The **proxy** implements the same interface and holds the real subject. Because the types match, `main` can hand callers a proxy instead of the real thing, through <Term id="dependency-injection">dependency injection</Term>, and no caller changes.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Proxy as an object structural pattern, also known as Surrogate. It names four common kinds: a <Term id="remote-proxy">remote proxy</Term> for an object in another address space, a <Term id="virtual-proxy">virtual proxy</Term> that creates an expensive object on demand, a <Term id="protection-proxy">protection proxy</Term> that checks access rights, and a smart reference that does extra work on access, such as counting references. It also describes copy-on-write as an optimisation a proxy can hide.
</Depth>

## [problem] Three callers, one slow vendor

A shop converts prices with a paid exchange-rates API. Each call takes about 300 ms. Checkout and the invoice job each wrapped the client in a small cache. The reports page calls the vendor directly.

Read it once. The cache logic exists twice, and the third caller has none.

<Depth level={2}>
Each caller holds the vendor's client type directly. Nothing stops the next caller from skipping the cache, and the two copies can drift: someone changes the TTL in one and forgets the other.
</Depth>

<Depth level={3}>
Each copy also has its own map, so the same rate is fetched once per caller. Two caches of the same data, filled separately, double the vendor bill and can disagree about the current rate.
</Depth>

## [pain] Then a change request arrives

**Change request:** the rates vendor now bills per call, and finance wants every paid call counted.

The count has to go wherever the vendor is called, and that is in three files. Miss one and the dashboard under-reports the bill without any error.

<Depth level={2}>
Every new caller has to know to cache, and now also to count. The rule lives in people's heads, so it fails the first time someone new adds a fourth caller.
</Depth>

<Depth level={3}>
Tests cannot catch the missing counter either. Each caller's tests pass, because each caller works. The bug is a missing line in code that nobody looks at.
</Depth>

## [morph] Move the extra work into a stand-in

Drag the slider. The two copies of the cache leave the callers and become one `CachedRates` type that implements the same interface as the vendor client.

Hover a box in the diagram to see its code.

<Depth level={2}>
Callers now depend on `RateSource`. `main` decides what sits behind it: the bare client in tests against the sandbox, the client wrapped in a cache in production. The callers' code is the same in both.
</Depth>

<Depth level={3}>
<Lang only="go">Go interfaces are satisfied implicitly, so the vendor's `*fx.Client` fits `RateSource` as long as its `Rate` method has the same signature. You can put a proxy in front of a third-party type without touching it.</Lang>
<Lang only="python">The `Protocol` is checked by tools such as mypy. At runtime any object with a `rate` method works, including the vendor's client and every proxy.</Lang>
<Lang only="typescript">Structural typing means the vendor's `FxClient` fits `RateSource` because it has a `rate` method of the right shape. It never has to declare it.</Lang>
<Lang only="rust">The vendor's client fits only after `impl RateSource for FxClient`. Because `RateSource` is your trait, you are allowed to implement it for their type.</Lang>
</Depth>

## [walk] Follow one request

One rate request through the proxy. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">The `Mutex` is held across the vendor call, so a second request for any pair waits for the first. That keeps the example short. In production, release the lock before the call and use `singleflight` so concurrent misses for the same pair share one request.</Lang>
<Lang only="python">Two threads that miss at the same time both call the vendor; the dict survives it, but you pay twice. A per-key lock, or an `asyncio` task stored in the cache, makes concurrent misses share one call.</Lang>
<Lang only="typescript">Two requests that miss during the same 300 ms both call the vendor. Store the `Promise` in the map instead of the value, and the second request awaits the first one's call.</Lang>
<Lang only="rust">The `Mutex` is held across the vendor call, so a second request for any pair waits. With async code, holding a `std::sync::MutexGuard` across an `.await` is a known mistake; use an async-aware cache or release the lock first.</Lang>
</Depth>

## [again] Counting, the second time

The same request after the refactor. Counting is one more proxy. Put it between the cache and the client, and it sees exactly the calls that reach the vendor, which are the ones you pay for.

<Depth level={2}>
Each proxy does one job and implements the same interface, so they stack. The order is a decision: a counter in front of the cache would count every request, paid or not.
</Depth>

<Depth level={3}>
No caller was edited, and none can forget to count: there is no longer a way for them to reach the vendor except through the chain that `main` built.
</Depth>

### The kinds of proxy

They share one shape and differ in what they decide. A **caching** proxy answers from memory until the <Term id="time-to-live">TTL</Term> runs out. A **virtual** proxy creates or connects the real object on first use. A **protection** proxy checks who is asking. A **remote** proxy turns a method call into a network request. A **smart reference** counts or logs each access. Several can sit in one chain, and the order they sit in is part of the behaviour.
