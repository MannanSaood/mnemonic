        correct: true

        why: That is Decorator. The interface stays the same and behaviour is added around it.
      - text: The vendor SDK needs eight calls to set up a client, and you want the team to call one function instead.
        why: That is Facade. It offers a simpler interface over a complicated subsystem. An adapter matches one existing interface to another.
  engineer:
    question: Acme takes amounts as a decimal string in major units. Where should the conversion from your minor units happen?
    options:
      - text: Inside the adapter, using each currency's number of decimals.
        correct: true
        why: Right. Only the adapter knows Acme's format, and the conversion depends on the currency (0 decimals for JPY, 3 for KWD). Callers keep passing minor units, as they do for every other gateway.
      - text: In Checkout, just before it calls the gateway, when the region is Gulf.
        why: That puts Acme's format back into Checkout, the knowledge the adapter exists to hold. Renewals would need the same code, and so would the next caller.
      - text: Change the Order type to store major units as a decimal string everywhere.
        why: That changes every caller and every other gateway to suit one vendor. The adapter should bend to your interface, not the other way round.
  deep:
    question: When can you skip writing a separate adapter type?
    options:
      - text: When the vendor type already fits structurally (Go, TypeScript), or you can implement your own trait on it directly (Rust), and no state needs to be held.
        correct: true
        why: Right. Go and TypeScript check shape, not declarations. Rust allows impl LocalTrait for ForeignType; only a foreign trait on a foreign type needs a newtype. A type is still worth it when the adapter holds state, such as a client or a lookup cache.
      - text: Never. The catalogue defines Adapter as a class that inherits the target and wraps the adaptee.
        why: The catalogue describes class and object adapters for C++ and Smalltalk. Its point is the translation, not the inheritance. Languages with structural typing or trait impls often need less ceremony.
      - text: When the vendor SDK is written in the same language as your service.
        why: The language does not matter. What matters is whether the names, types, units and errors match your interface.

    - role: Client

    - role: Adaptee
      example: Acme SDK
      job: Useful code with the wrong interface. You do not change it.
    - role: Adapter
      example: { go: AcmeAdapter, python: AcmeAdapter, typescript: AcmeAdapter, rust: "impl PaymentGateway for acme::Client" }
      job: Implements the target by calling the adaptee, translating arguments, results and errors both ways.
  useWhen:
    - A class you cannot or should not change (a vendor SDK, a legacy module) has the wrong interface for your code.
    - Several vendors must sit behind one interface, each with its own quirks.
    - You want tests to use a fake behind your own interface instead of mocking a vendor SDK.
  avoidWhen:
    - You own both sides and can change one of them to match. Change it.
    - The vendor's interface is already the one you want. Use it directly.
    - The mismatch is so deep that the adapter would reimplement half the vendor. Rethink the interface instead.
  tradeoffs:
    - One more type and one more call per operation.
    - The adapter can hide features of the vendor that your interface has no room for.
    - An adapter is only as good as its translation. Units, codes and errors are where the bugs live, so test it against the vendor's sandbox.
    - It is not transparent. The adapter is not an Acme client, so code that needs the vendor type cannot use it.
  lookalikes:
    - name: Decorator
      how: Keeps the interface the same and adds behaviour. An adapter changes the interface.
    - name: Facade
      how: Defines a new, simpler interface over a whole subsystem. An adapter matches one existing interface.
    - name: Proxy
      how: Has the same interface as the object it stands in for. An adapter has a different one.
    - name: Bridge
      how: Similar structure, but designed up front so two sides can vary independently. An adapter is usually added after the fact, to make existing classes fit.

## [concept] Adapter

**Wrap an object whose <Term id="interface">interface</Term> does not fit, so that it looks like the interface your code already uses.**

Your code is written against its own interface. A vendor SDK or a legacy module does the right job with the wrong names, types, units and errors. The adapter sits between them and translates in both directions, so neither side has to change.

<Depth level={2}>
Four roles. The **target** is the interface your code uses (`PaymentGateway`). The **client** calls it (`Checkout`). The **<Term id="adaptee">adaptee</Term>** is the class with the wrong interface (the Acme SDK). The **adapter** implements the target by calling the adaptee. How much work it does varies: sometimes it only renames, often it converts units, maps result codes and errors, and sometimes it supplies behaviour the adaptee lacks.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue describes two forms. A class adapter inherits from both the target and the adaptee, through multiple inheritance. An object adapter holds an adaptee and forwards to it. The object form can adapt an adaptee and all its subclasses, and is the only form available in Go, Python by convention, TypeScript and Rust. The catalogue also notes the spectrum of work an adapter does, from renaming operations to supporting a different set of operations, and describes two-way adapters for when two systems must each see the same object through their own interface.
</Depth>

## [problem] A checkout that speaks two dialects

A shop charges through a `PaymentGateway` interface, and Stripe fits it. The Gulf stores must use a regional acquirer, Acme, whose legacy SDK has its own method names, takes amounts as decimal strings in major units, and has its own result codes. Someone made it work with a branch in Checkout.

Read it once. Checkout now knows two things it should not: which region uses Acme, and how to talk to Acme.

<Depth level={2}>
Testing the Gulf path means mocking Acme's SDK inside Checkout's tests. Every Checkout change runs next to Acme-specific code it has nothing to do with.
</Depth>

<Depth level={3}>
There is also a bug waiting. `%.2f` of the amount divided by 100 is right for euros and wrong for currencies with zero or three decimals. Kuwaiti dinars have three, so a KWD 12.500 payment goes out as KWD 125.00. The playground below shows what that costs.
</Depth>

## [pain] Then a change request arrives

**Change request:** Gulf subscriptions must renew through Acme too, not only Gulf checkouts.

The marked lines must change. Renewals gets a copy of the whole translation, and now two files know Acme's dialect.

<Depth level={2}>
The copies will drift. Fix the decimal bug in Checkout and the renewals copy still has it. Add a result code to one and the other treats it as an error. Each new caller of the gateway makes another copy.
</Depth>

<Depth level={3}>
Error handling drifts too. Checkout's tests expect Acme's exceptions to be wrapped in one way; Renewals' copy may wrap them another way, or not at all, and the retry logic above them behaves differently for the same timeout.

Adding Acme to the system extended it without modifying the callers: the <Term id="open-closed">open/closed principle</Term>.

<Depth level={3}>
<Lang only="go">The adapter is a struct with one field, the Acme client, and one method. Go checks that `AcmeAdapter` satisfies `PaymentGateway` where it is assigned to the `gateway` field, with no `implements` keyword.</Lang>
<Lang only="python">`PaymentGateway` is a `Protocol`. A type checker accepts `AcmeAdapter` because it has a `charge` method of the right signature, not because of inheritance.</Lang>
<Lang only="typescript">`implements PaymentGateway` is optional with <Term id="structural-typing">structural typing</Term>, but it makes the compiler check the class at its definition instead of where it is first used.</Lang>
<Lang only="rust">There is no wrapper struct here. `PaymentGateway` is a local trait, so `impl PaymentGateway for acme::Client` is allowed, and the adapter is that impl block.</Lang>
</Depth>

## [again] Renewals, the second time

The same request after the refactor. Renewals already takes a `PaymentGateway`, so the Gulf renewals get the same adapter in one line of wiring. No Acme code is copied, and a fix to the translation reaches every caller at once.

<Depth level={2}>
Adapters also absorb behaviour the vendor lacks. Acme has no idempotency keys, so a retry after a timeout charges the customer again. The adapter can send your key as Acme's merchant reference and look it up before charging: an <Term id="idempotent-retry">idempotent retry</Term> that every caller gets for free.
</Depth>

<Depth level={3}>
Test the adapter with contract tests: the same suite your Stripe implementation passes, run against Acme's sandbox. A gateway that passes the suite can be swapped in safely; one that does not shows you exactly which translation is wrong.
</Depth>

### An adapter is a translation, not a rename

The work an adapter does runs along a scale: rename a method, convert units, map result codes, map errors, and supply behaviour the vendor lacks. The further along the scale, the more the adapter needs its own tests. Run your interface's contract tests against every implementation, and keep the vendor's types out of the interface so that callers never import the SDK.
