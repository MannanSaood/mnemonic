    - role: Wrapper

    - role: Core
      example: "Http"
      job: Does the real work at the bottom of the stack.
    - role: Assembly
      example: main
      job: Stacks the layers per use, in the order that use needs.
  useWhen:
    - Features are optional and combine freely, like retry, auth, caching, logging or metrics.
    - Different callers need different mixes, or the same features in a different order.
    - You want to reuse behaviour from a type you do not own, which you cannot or should not subclass.
  avoidWhen:
    - There is a real is-a relationship with a stable base, such as a framework's base handler class designed for overriding.
    - There is one variant and no second one coming. A wrapper stack of one is just indirection.
  tradeoffs:
    - Behaviour is spread over several small objects; reading one request means following the stack.
    - Wrappers can only use the interface, so a feature that needs a layer's internals does not fit.
    - Order is now a decision someone has to get right, per stack.
    - More objects at runtime, and in some languages more indirect calls.
  lookalikes:
    - name: Decorator
      how: The pattern this lesson uses. A wrapper with the same interface as what it wraps, adding behaviour around the call.
    - name: Strategy
      how: Also composition, but it swaps one step for another. Wrappers add steps around a call and keep it.
    - name: Bridge
      how: Splits two independent dimensions (such as transport and auth scheme) into two hierarchies joined by composition, to avoid the same product of subclasses.

## [concept] Composition over inheritance

**Build behaviour by wrapping objects that share an interface, instead of writing a subclass for every combination of features.**

With <Term id="inheritance">inheritance</Term>, a class gets its behaviour from one parent. With <Term id="composition">composition</Term>, an object holds other objects and calls them. When features combine freely, the first needs a class per combination and the second needs one piece per feature.

<Depth level={2}>
Each wrapper adds one feature and passes the call on to the object it holds (<Term id="delegation">delegation</Term>). Because every layer has the same <Term id="interface">interface</Term>, any layer can wrap any other, and the caller cannot tell a bare client from a stack of five. You choose the mix and the order where the object is built, per use.
</Depth>

<Depth level={3}>
*Design Patterns* (1994) names this its second principle: favour object composition over class inheritance. Its reasons: inheritance is fixed at compile time, and a subclass sees its parent's internals, so a change inside the parent can break the subclass (often called the <Term id="fragile-base-class">fragile base class</Term> problem). Composition reaches objects only through their interfaces and can be rearranged at runtime. The book adds the cost: more, smaller objects, and behaviour that lives in how they are connected.
</Depth>

## [problem] An HTTP client with a subclass per mix

Several teams call the same internal APIs. Payments needs retries and an auth token. Search needs only retries. Admin needs only the token. Each mix became a client class.

Read it once. There are four classes for three mixes plus the base, and the auth code is written twice: the class that has retries and the class that does not cannot share it.

<Depth level={2}>
Each subclass calls up to its parent for the part it inherits. That fixes the order of the layers in the class tree: auth always sets the header before retries run, for every team that uses that class.
</Depth>

<Depth level={3}>
<Lang only="go">Go has no inheritance; this is the closest imitation, with <Term id="struct-embedding">struct embedding</Term>. Each struct embeds the one below and calls it by name, which is already composition, but over concrete types, so each mix is still its own type.</Lang>
<Lang only="python">`super().send(req)` follows the class hierarchy, so the order of the layers is decided by the inheritance chain, not at the place the client is built.</Lang>
<Lang only="typescript">Single inheritance forces a chain. `AuthClient` cannot extend both `HttpClient` and something shared with `AuthRetryingClient`, so the header code is copied.</Lang>
<Lang only="rust">Rust has no inheritance; the equivalent trap is a concrete struct per mix. `AuthRetryingClient` holds a `RetryingClient` by its concrete type, so it cannot be reused with anything else.</Lang>
</Depth>

## [pain] Then a change request arrives

**Change request:** Security wants every outgoing HTTP request logged with its latency.

Every mix needs a logging version. That is four new classes, each with the same logging lines, and every team changes which class it constructs. Add a fifth feature later and the count doubles again.

<Depth level={2}>
Bugs multiply the same way. A mistake in the logging code is now in four places, and a fix that misses one leaves one team logging wrong. Nothing links the copies.
</Depth>

<Depth level={3}>
The number of possible mixes of *n* optional features is 2<sup>n</sup>. Teams rarely use all of them, but every one they do use needs a class, plus the parents those classes inherit from.
</Depth>

## [morph] One wrapper per feature

Drag the slider. The class tree flattens into small wrappers that each implement the same interface, and each team's client becomes a stack of them.

Hover a box in the diagram to see its code.

<Depth level={2}>
Each wrapper holds the next layer as the interface type, not as a concrete class. That is the step that makes them stack in any order. The same Retry serves Payments and Search.
</Depth>

<Depth level={3}>
<Lang only="go">Go's standard library is built for this: `http.Client` takes any `http.RoundTripper` as its `Transport`, and the RoundTripper contract says not to modify the request, which is why Auth clones it.</Lang>
<Lang only="python">Wrappers are plain classes with a `send` method. The `Transport` Protocol lets a type checker confirm each layer fits; nothing is inherited.</Lang>
<Lang only="typescript">`implements Transport` is optional with structural types, but it puts the error on the wrapper if a method is missing.</Lang>
<Lang only="rust">`Retry<T>` and `Auth<T>` are generic over the inner layer, so `Auth<Retry<Http>>` is a concrete type the compiler can optimise as one.</Lang>
</Depth>

## [walk] Follow one request

One Payments request, with a 503 on the first attempt. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Each layer is called through the `http.RoundTripper` interface, so each hop is an indirect call. Next to a network round trip, three indirect calls cost nothing you can measure.</Lang>
<Lang only="python">Each hop is a method lookup and a call, a fraction of a microsecond. The stack depth shows up in tracebacks, which list every layer the request passed through.</Lang>
<Lang only="typescript">With `async` wrappers, each layer adds a promise and a microtask hop. That is microseconds next to a network call.</Lang>
<Lang only="rust">With generics, `Auth<Retry<Http>>` is one type known at compile time; the calls between layers are direct and usually inlined (<Term id="monomorphisation">monomorphisation</Term>). Use `Box<dyn Transport>` only where the stack is chosen at runtime.</Lang>
</Depth>

## [again] Logging, the second time

The same request, after the refactor. You write one Logging wrapper and add it to each team's stack in `main`. No existing class changes, and each team decides whether Logging goes outside Retry (one line per call) or inside it (one line per attempt).

<Depth level={2}>
Each wrapper is tested alone with a fake inner transport: does Retry retry on 503 and stop on 200, does Auth set the header. The stacks need only a small test each, to check the order.
</Depth>

<Depth level={3}>
The order of the layers is now explicit and per use. In the class tree it was implicit, decided once by which class extended which.
</Depth>

### When inheritance is still right

Inheritance works when the parent was designed to be extended: a framework's base class with documented hooks, or a small closed hierarchy you own. It goes wrong when it is used to mix features, or to reuse code from a class that was never meant to be a parent. Ask whether the new type is a kind of the old one that every caller can use the same way, or just wants some of its code.
