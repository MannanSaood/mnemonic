      - text: Nothing. Having the same methods on every node is strictly better.
        why: A method that always throws is a promise the type does not keep. It moves an error the compiler could catch to runtime.
      - text: Speed. Every call to cost() now has to check whether add_child was called.
        why: No. add_child is a separate method. cost() is unaffected.
  deep:
    question: The tree has 200,000 resources and a dashboard calls org.cost() on every page load. What is the usual fix?
    options:
      - text: Cache each group's total, and invalidate the cached totals up the parent chain when a child changes.
        correct: true
        why: Right. The catalogue suggests exactly this, and it needs parent references so a change can walk up. Reads become one lookup; writes cost one walk to the root.

        why: That removes the risk of a very deep tree overflowing the call stack, but it still visits all 200,000 nodes on every page load.
      - text: Go back to nested loops, which avoid the method calls.
        why: The loops visit the same nodes and only save the call overhead, and they break again on the next new shape.

      example: { go: "Node (interface)", python: "Node (Protocol)", typescript: "CostNode (interface)", rust: "Node (enum)" }
      job: The one interface for leaves and groups.
    - role: Leaf
      example: Resource (a VM, a database, a bucket)
      job: Answers from its own data. Has no children.
    - role: Composite
      example: Group (a team, a project, a folder)
      job: Holds children and answers by asking each of them.
    - role: Client
      example: the cost report, a budget alert
      job: Calls the component interface on any node, never asking which kind it is.
  useWhen:
    - The data is a part-whole tree, such as org units, folders, menus, bundles or syntax trees.
    - The same question must work on one item and on a group of items.
    - The tree's shape changes over time, and code that walks it should not.
  avoidWhen:
    - The structure is flat or has a fixed, shallow depth that will not change.
    - Leaves and groups need very different operations, so the shared interface would be mostly methods that do not apply.
    - You need strict rules about which kinds may hold which. The pattern makes that a runtime check.
  tradeoffs:
    - Transparency against safety. Child management on every node makes nodes uniform but lets callers add children to leaves.
    - Rules such as "a project may not hold a team" move from the type system to runtime checks.
    - Recursive calls visit every node. Large trees need caching, and unbounded depth needs care with the call stack.
    - The tree must stay a tree. A node inside its own subtree makes recursive operations loop forever.
  lookalikes:
    - name: Decorator
      how: Also recursive, but a decorator wraps exactly one object to add behaviour. A composite holds many and combines their results.
    - name: Iterator
      how: Walks the elements of a structure. It is often how you traverse a composite.
    - name: Visitor
      how: Adds new operations over a composite's nodes without adding methods to each node.
    - name: Chain of Responsibility
      how: Often uses a composite's parent links to pass a request up the tree.
    - name: Flyweight
      how: Lets many leaves share one object, which a composite with no parent references allows.

## [concept] Composite

**Give single items and groups of items one <Term id="interface">interface</Term>, so code can ask a whole tree the same question it asks one leaf.**

Cloud bills, folders, menus and org charts are <Term id="part-whole-hierarchy">part-whole hierarchies</Term>: groups that hold items and other groups. With Composite, a VM and a whole department both answer `cost()`. The code that asks never needs to know which one it holds, or how deep the tree goes.

<Depth level={2}>
Three roles plus a client. The **component** is the shared interface (`Node` with `cost()`). A **<Term id="tree-leaf">leaf</Term>** answers from its own data (a VM's monthly price). A **composite** holds children and answers by asking each of them (a team sums its projects). The **client** calls the interface on any node. One design choice matters: where `add_child` lives. On every node it is transparent but unsafe; only on groups it is safe but less uniform.
</Depth>

<Depth level={3}>
The 1994 *Design Patterns* catalogue files Composite as an object structural pattern. It lists the benefits: client code becomes simple because it stops testing which class it holds, and new kinds of leaf or group work with existing code. It also names the main cost: the design becomes overly general, so restricting which components a composite may hold needs runtime checks. Its implementation notes cover parent references, sharing components, the transparency-against-safety choice for child operations, and caching results in composites to make traversal cheaper.
</Depth>

## [problem] A cost report shaped like last year's org chart

Finance totals the monthly cloud bill. The report walks the org as it was when it was written: teams hold projects, projects hold resources. It works, and the numbers match the invoice.

Read it once. The shape of the org is written into the report as nested loops, one per level.

<Depth level={2}>
The budget alert and the tag audit walk the tree the same way, each with its own copy of the loops. The data types fix the shape too: a team can only hold projects.
</Depth>

<Depth level={3}>
Nothing is wrong yet. A fixed three-level structure with three loops is clear code. The trouble starts when the shape changes, and org charts change every reorganisation.
</Depth>

## [pain] Then a change request arrives

**Change request:** teams can now have sub-teams. ML platform moves under Data.

The marked lines must change: a new field, and another set of loops for the sub-teams, in every report. And the new loops only go one level deep.

<Depth level={2}>
The dangerous part is what happens when someone forgets. A report that was not updated does not fail. It skips the sub-team and prints a smaller total. The playground shows how much money disappears that way.
</Depth>

<Depth level={3}>
The next reorganisation brings another shape: a project owned by no team, a sub-team of a sub-team, a resource such as a Kubernetes cluster that has children of its own. Each one adds another loop to every report.
</Depth>

## [morph] Give leaves and groups one interface

Drag the slider. The loops leave the report. A Resource and a Group both implement one interface, and a Group holds any mix of Resources and Groups.

Hover a box in the diagram to see its code.

<Depth level={2}>
Now the report is one call, `org.cost()`. A sub-team is a Group inside a Group, so it needs no code change. New kinds of node work with the existing reports as long as they implement the interface: the <Term id="open-closed">open/closed principle</Term>, applied to the shape of the data.
</Depth>

<Depth level={3}>
<Lang only="go">`Resource` uses a value receiver and `*Group` a pointer receiver, so children can be added to a group in place. Both satisfy `Node` implicitly. `Add` exists only on `*Group`: the safe choice.</Lang>
<Lang only="python">`Group.children` is typed `list[Node]`, and anything with a `cost()` method fits, including future node types nobody has written yet.</Lang>
<Lang only="typescript">`children: CostNode[]` accepts any object with a `name` and a `cost()` method. With <Term id="structural-typing">structural typing</Term>, a node from another module fits without importing `Group` or `Resource`.</Lang>
<Lang only="rust">The composite is an `enum`. The set of node kinds is closed, and `match` checks that `cost` handles every variant. A recursive enum needs indirection, which `Vec<Node>` provides.</Lang>
</Depth>

## [walk] Follow one cost() call down and back up

One call on the org, down to the leaves and back up. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Each `Cost` call goes through the `Node` interface, so it is an indirect call per node. For a tree of thousands of nodes that is microseconds. The call stack grows by one frame per level of depth, not per node.</Lang>
<Lang only="python">The recursion depth equals the tree's depth, not its size. Python's default limit of 1000 frames is far above any org chart, but a tree built from user input needs an explicit stack or a depth check.</Lang>
<Lang only="typescript">`reduce` with a callback per child is fine for thousands of nodes. For very large trees, a plain `for` loop avoids the closure, and an explicit stack avoids deep recursion.</Lang>
<Lang only="rust">`children.iter().map(Node::cost).sum()` compiles to a tight loop with a direct recursive call: no vtable, because the enum is matched in place. Depth is limited by the thread's stack size.</Lang>
</Depth>

## [again] Sub-teams, the second time

The same request after the refactor. ML platform's Group goes into Data's children. No report changes, and no report can forget, because none of them knows the shape.

<Depth level={2}>
The same holds for shapes nobody has asked for yet: a project owned by the whole org, or a cluster that has a fee of its own and also holds namespaces. Anything that answers `cost()` fits.
</Depth>

<Depth level={3}>
Keep the tree a tree. Check in `add` that the new child is not an ancestor of the group, or a reorganisation can create a loop and `cost()` will never return. If you keep parent references for upward walks or caching, set them only in `add` and `remove`, so they cannot go stale.
</Depth>

## [lens] How each language writes it

Object-oriented languages write Composite as an interface with leaf and group classes. Rust and TypeScript often use a recursive sum type instead, which gives the same uniform call and lets the compiler check every kind of node.

### Beyond cost: permissions and policies

Cloud providers use the same shape for access. In Google Cloud, policies set on an organization or folder are inherited by everything below, and a resource's effective policy combines its own with its ancestors'. That is a composite query that walks up the tree instead of down. It is the reason parent references are worth keeping.
