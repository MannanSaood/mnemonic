reference:
  roles:
    - role: Shared reference
      example: "&self.idle, &Conn"
      job: Read access. Any number may exist at once, and while one is alive nobody may write.
    - role: Mutable reference
      example: "&mut self.idle"
      job: Exclusive access. Only one exists at a time, and no shared reference may be used while it is alive.
    - role: Borrow checker
      example: "E0499, E0502, E0505"
      job: Proves at compile time that the two kinds never overlap and that no reference outlives its value.
    - role: Owner
      example: "Pool owns idle"
      job: Cannot be moved, or written through directly, while it is borrowed.
  useWhen:
    - A function needs to read or change a value but not keep it. Pass `&T` or `&mut T` instead of moving.
    - Iterating a collection. Borrow it, and do edits in one exclusive call such as `retain`, `drain` or `entry`.
    - Splitting work over disjoint parts of a value, such as two struct fields or two halves of a slice.
  avoidWhen:
    - The reference must outlive the current call or be stored long term. Own the data, or share it with `Rc` or `Arc`.
    - Several parts of the program must mutate one value in turns that the compiler cannot see. Use `RefCell`, `Mutex` or message passing.
  tradeoffs:
    - Some correct programs are rejected. You reorder, split borrows, or restructure the data.
    - The rule removes data races and iterator invalidation from safe code, at compile time, with no runtime cost.
    - Graph-shaped data with back pointers fights the rule. Arenas with indexes are the usual answer.
  lookalikes:
    - name: Reader-writer lock
      how: The same rule (many readers or one writer), checked at runtime for data shared across threads.
    - name: RefCell
      how: The same rule checked at runtime in one thread. A conflict panics instead of failing to compile.
    - name: C restrict
      how: A promise that pointers do not alias, which lets the compiler optimise. Nothing checks it.

## [concept] References and the borrow checker

**A reference lets code use a value without owning it. At any moment a value has either any number of shared references or exactly one mutable one, and a borrow lasts until its last use.**

The rule is often called aliasing XOR mutability: you may have many names for a value, or you may change it, but not both at the same time.

<Depth level={2}>
`&v` creates a <Term id="shared-reference">shared reference</Term> and `&mut v` a <Term id="mutable-reference">mutable reference</Term>; creating one is a <Term id="borrow">borrow</Term>. The owner stays the owner, but while a shared borrow is alive the owner cannot be changed or moved, and while a mutable borrow is alive the owner cannot be used at all. The Rust Book puts it as two rules: either one mutable reference or any number of immutable ones, and references must always be valid. The same rule makes a <Term id="data-race">data race</Term> impossible in safe code.
</Depth>

<Depth level={3}>
Since Rust 2018 the checker uses <Term id="non-lexical-lifetimes">non-lexical lifetimes</Term>: a borrow is live from where it is created to its last use, computed on the function's control-flow graph, not to the end of the block. That is why moving one line, or deleting one use, can make an error disappear. A conflict is reported where the second borrow starts, with a note pointing at the later use of the first.
</Depth>

## [problem] Sweep stale connections

A database connection pool keeps idle connections in a list. Every 30 seconds a sweeper walks the list and closes connections that have been idle too long, because the database and the load balancer drop idle sockets after a few minutes.

The sweep removes each stale connection as it finds it. In testing there is usually one stale connection at a time, and it is always removed.

<Depth level={2}>
The mental model behind the code is that the list is a thing you can walk and edit at the same time. The loop and the removal both act on one list, through two names: the loop's position in it, and the list itself.
</Depth>

<Depth level={3}>
<Lang only="go">The index loop recomputes `len(p.idle)` each time, so it never runs off the end. After a removal, though, the next connection has moved into slot `i`, and `i++` steps over it.</Lang>
<Lang only="python">A list iterator keeps an integer index. `remove` shifts every later element down by one, so the next element moves into the index the iterator has already passed.</Lang>
<Lang only="typescript">`forEach` decides how many indexes to visit before it starts and visits them in order. `splice` shifts the rest of the array down, so the next connection lands on an index already visited.</Lang>
<Lang only="rust">The Rust version never runs. The `for` loop's iterator holds a shared borrow of `self.idle`, and `remove` needs a mutable one while the iterator is still in use.</Lang>
</Depth>

## [pain] The failover

**What happened:** after a database failover, half the stale connections survived the pool's eviction sweep, and the next requests failed with connection reset.

The marked lines are the whole story. When every connection is stale, each removal shifts the next one into the slot just checked, and the loop steps over it. The sweep removes every other connection. 32 stale connections become 16, and the next 16 requests are handed a dead socket.

<Depth level={2}>
This is <Term id="iterator-invalidation">iterator invalidation</Term>: the collection changed under a loop that was walking it. In Python, Go and TypeScript it is a silent logic error. In C++ it is undefined behaviour, because the iterator may point into storage the removal moved or freed. Nothing failed in testing, because tests rarely have two stale connections next to each other.
</Depth>

<Depth level={3}>
<Lang only="rust">The compiler reports E0502: cannot borrow `self.idle` as mutable because it is also borrowed as immutable. Its notes point at the `for` line twice: once where the iterator borrows `self.idle`, and once where the next turn of the loop uses that borrow again. The bug never ships, so the cost meter shows one compile error.</Lang>
<Lang only="go">No tool flags this. The race detector only looks at concurrent access from different goroutines, and here a single goroutine does everything in order.</Lang>
<Lang only="python">Python raises `RuntimeError` for a dict or set that changes size during iteration, but lists do not check. The loop just ends early.</Lang>
<Lang only="typescript">No error is thrown. The loop visits the indexes it planned to visit, over an array that has shifted under it.</Lang>
</Depth>

## [morph] Many readers or one writer

Drag the slider. The list that everyone edits at will becomes an owner that lends out either shared readers or one exclusive writer, never both at once.

The code changes in one way. The walk only reads, and the edit happens in one exclusive step.

<Depth level={2}>
<Lang only="rust">`retain` takes `&mut self` once and does the walk and the removal inside, where it can do both safely. The closure gets `&Conn` for each element. Removed elements are dropped inside `retain`, so their sockets close.</Lang>
<Lang only="go">`slices.DeleteFunc` is the same idea in Go: the library owns the walk and the compaction, and your callback only answers keep or delete.</Lang>
<Lang only="python">Building `keep` and assigning it once separates the read from the write. A list comprehension does the same in one line if closing is not needed.</Lang>
<Lang only="typescript">Building `keep` and assigning it once separates the read from the write. `filter` does the same in one line if closing is not needed.</Lang>
</Depth>

<Depth level={3}>
<Lang only="rust">The closure reads `self.max_idle` while `retain` holds `&mut self.idle`. That compiles because Rust 2021 closures capture the field `self.max_idle`, not the whole `self`, and two different fields can be borrowed separately.</Lang>
<Lang only="go">Before Go 1.22, `DeleteFunc` left the removed pointers in the backing array past the new length, keeping closed connections reachable until the slice was reused. Now it zeroes them.</Lang>
<Lang only="python">Assigning a new list does not change the old one, so any other code that kept a reference to the old list still sees all 32 connections. Here nothing does.</Lang>
<Lang only="typescript">Assigning a new array leaves the old one unchanged, so any other code that kept a reference to it still sees all 32 connections. Here nothing does.</Lang>
</Depth>

## [walk] Follow one sweep

One sweep through the pool, with the borrows it takes. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="rust">`retain` keeps a read index and a write index into the same buffer. It can do that because it holds the only `&mut`, so no outside reference can see the buffer while elements are half-shifted. If the closure panics, a guard inside `retain` still shifts the remaining elements and fixes the length, so the Vec stays valid during unwinding.</Lang>
<Lang only="go">`DeleteFunc` finds the first element to delete, then copies each kept element down over the deleted ones, in place. It returns the shortened slice; the caller must assign it, or keep using a slice with the old length.</Lang>
<Lang only="python">The `for` loop calls `next()` on a list iterator, which reads the element at its index and adds one. Building a second list costs one pointer per kept connection.</Lang>
<Lang only="typescript">`for...of` uses the array's iterator, which reads `length` afresh each step. Because nothing changes the array during the loop, that makes no difference here.</Lang>
</Depth>

All 32 idle connections are stale, exactly as before. The sweep removes all 32. The next requests open fresh connections, and none of them fails.

<Depth level={2}>
A test that would have caught the original bug: fill the pool with connections that are all stale, run the sweep, and assert the pool is empty. Tests with one stale connection cannot see it.
</Depth>

<Depth level={3}>

### When a borrow ends

A borrow is alive from where it is created to its last use, on every path through the function. Deleting the last use, or moving it above the conflicting line, ends the borrow earlier. Two-phase borrows let `v.push(v.len())` compile: the mutable borrow for `push` is reserved first and only activated after the argument `v.len()` has been evaluated. Borrowing two different fields of a struct at once is fine, and so is `split_at_mut` for two halves of one slice, because the parts cannot overlap.
