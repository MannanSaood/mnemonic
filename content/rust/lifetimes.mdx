    - role: Owned value

      job: The way out when data must outlive what it came from. It costs a copy.
    - role: "'static"
      example: "string literals"
      job: Valid for the whole program. Often suggested by the compiler, and usually the wrong fix.
  useWhen:
    - A function returns a reference into one of its arguments, such as a parser returning slices of its input.
    - A struct holds a reference, such as a request view that borrows the read buffer.
    - Zero-copy processing where the borrowed data clearly outlives the work, within one request or one batch.
  avoidWhen:
    - The result must be stored beyond the input's life, such as in a cache, a map or a background task. Return or store owned data.
    - The lifetimes start spreading through many structs and signatures. Owning a small copy is often simpler and cheap.
  tradeoffs:
    - References avoid copies, but tie the result's life to the input's. The compiler checks the tie, and you design around it.
    - Annotations are only needed where elision cannot decide, but when needed they are part of the public API.
    - In garbage-collected languages the same shape never dangles, and instead can keep a large parent alive behind a small slice.
  lookalikes:
    - name: Garbage collection
      how: Keeps data alive while anything points at it. No dangling, but unbounded retention is possible.
    - name: Rc and Arc
      how: Shared ownership with a count. The data lives as long as any owner, checked at runtime.
    - name: Cow
      how: Borrows when the data outlives the use, and owns a copy when it does not.

## [concept] Lifetimes

**A lifetime names the region of code where a reference must stay valid. Annotations say which inputs a returned reference may borrow from, so the compiler can check every caller against the shortest of them.**

Lifetimes do not change how long anything lives. They describe relationships between references, and the compiler rejects programs that break them.

<Depth level={2}>
A <Term id="lifetime">lifetime</Term> is a region of code. `fn tenant_key<'a>(head: &'a str, default_tenant: &'a str) -> &'a str` says the result is valid only where both inputs are, so it is a <Term id="borrow">borrow</Term> of the shorter one. Most signatures need no annotation, because <Term id="lifetime-elision">lifetime elision</Term> fills them in. They are needed when a function takes two references and returns one, because the compiler cannot guess which input the result borrows from.
</Depth>

<Depth level={3}>
The borrow checker treats each lifetime as a set of points in the function's control-flow graph and collects constraints such as "`'head` must outlive `'a`" from every call and assignment. It then checks that every use of a reference lies inside its region. Lifetimes are erased before code generation, so they cost nothing at runtime and cannot be inspected.
</Depth>

## [problem] Rate limit by tenant

An API gateway rate-limits each tenant. For every request it reads the request head, about 16 KiB of headers, finds the tenant in the `X-Tenant` header, falls back to a default from the config, and takes a token from that tenant's bucket. Buckets live in a map for as long as the server runs.

The tenant lookup avoids copying: it returns a slice of the request head. In load tests memory is flat, and every test passes.

<Depth level={2}>
The mental model behind the code is that the tenant key is a small string of its own. It is in fact a window into the request head. Whether that is fine depends on how long the window is kept, and the limiter keeps it for good.
</Depth>

<Depth level={3}>
<Lang only="go">In Go a substring shares memory with its parent. `head[a:b]` is a pointer into head's bytes plus a length, so a map key made that way keeps all 16 KiB reachable.</Lang>
<Lang only="python">A slice of a `memoryview` is another view on the same buffer. Using it as a dict key keeps a reference to the whole request head.</Lang>
<Lang only="typescript">V8 may represent a substring as a slice of its parent string. Using such a string as a Map key can keep the whole request head alive.</Lang>
<Lang only="rust">The Rust version does not compile. The limiter is declared to hold `&str` keys for its own lifetime, and the key borrows from `head`, which is dropped at the end of `serve`.</Lang>
</Depth>

## [pain] A week in production

**What happened:** the rate limiter's memory grew to 3.4 GB for 2.5 MB of tenant keys, and the service was OOM-killed every few days.

The marked lines are the whole story. Each new tenant key is about 12 bytes, but it points into a 16 KiB request head. 210,000 tenants in a week keep 210,000 request heads alive, about 3.4 GB. Load tests used a few hundred tenants, so they never saw it.

<Depth level={2}>
Nothing dangles in a garbage-collected language: the collector keeps referenced data alive, as promised. The cost is the mirror image of a <Term id="dangling-reference">dangling reference</Term>. A reference that outlives the purpose of its data keeps that data alive, and a small key can hold a large buffer.
</Depth>

<Depth level={3}>
<Lang only="rust">The compiler reports E0597: `head` does not live long enough. Its notes point at `&head` as the borrow, at the `entry(key)` line as the use that needs the borrow to last as long as the limiter, and at the closing brace where `head` is dropped while still borrowed. Nothing ships, so the cost meter shows one compile error.</Lang>
<Lang only="go">A heap profile shows it if you know where to look: the retained bytes are attributed to `ReadHead`, the allocation site of the heads, not to the limiter that keeps them.</Lang>
<Lang only="python">`tracemalloc` attributes the memory to `read_head`, where the buffers were allocated. The dict that pins them is small and looks innocent.</Lang>
<Lang only="typescript">A heap snapshot shows thousands of sliced strings whose parent is a 16 KiB head. Nothing in the source code says they are slices.</Lang>
</Depth>

## [morph] From a string of its own to a borrow with a region

Drag the slider. The tenant key that looked like a value of its own becomes a reference with a region, `'a`, bounded by the request head and the config. The limiter, which outlives every request, stores its own copies.

The code changes in one way. Lookups keep borrowing, and the limiter copies the few bytes of a key when it inserts it.

<Depth level={2}>
<Lang only="rust">`tenant_key` keeps its signature: borrowing is right inside a request. The limiter's map now owns `Box<str>` keys. `get_mut(key)` looks up with a `&str` without allocating, because `Box<str>` implements `Borrow<str>`, and only a new tenant costs an allocation.</Lang>
<Lang only="go">`strings.Clone` exists for exactly this: keep a small part of a large string without keeping the large string. The lookup still uses the substring, so only new tenants cost an allocation.</Lang>
<Lang only="python">`bytes(key)` makes an independent copy for the dict. Lookups keep using the view, which hashes and compares equal to the same bytes.</Lang>
<Lang only="typescript">`Buffer.from(key).toString()` builds a fresh string from the key's bytes, so it cannot be a slice of head. Lookups keep using the original string.</Lang>
</Depth>

<Depth level={3}>
<Lang only="rust">With a single input, `fn tenant(head: &str) -> &str` would need no annotation at all: elision gives the output the input's lifetime. The `'a` is needed here only because there are two reference inputs and the result may come from either.</Lang>
<Lang only="go">`unique.Make` (Go 1.23) is the other option for keys that repeat: it interns the value, so equal keys share one canonical copy.</Lang>
<Lang only="python">A dict keeps the first key object it was given for each key, so the copy made on insert is the one that stays.</Lang>
<Lang only="typescript">Map keys are compared by value for strings, so the fresh copy and the substring find the same entry.</Lang>
</Depth>

## [again] The same week, again

210,000 tenants in a week, as before. The limiter holds 2.5 MB of keys plus map overhead, every request head is freed at the end of its request, and the heap stays flat.

## [lens] How each language meets it

Rust makes the region of every reference part of the type and checks it. Go, Python and TypeScript keep referenced data alive instead, so the same code never dangles and can quietly retain memory.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={2}>
The design question is the same in all four: is this value a view into something else, and does it outlive that thing? Rust forces the answer in the signature. Elsewhere you answer it by knowing which operations share memory: substrings in Go, memoryviews in Python, Buffer views and some substrings in Node.
</Depth>

### Elision and 'static

The compiler fills in lifetimes with three rules. Each reference parameter gets its own lifetime. If there is exactly one input lifetime, it is given to every output. If one input is `&self` or `&mut self`, its lifetime is given to every output. If the output is still ambiguous, you must annotate. The <Term id="static-lifetime">`'static`</Term> lifetime means valid for the whole program; string literals have it. A bound `T: 'static` is different: it means `T` holds no borrowed data with a shorter life, so an owned `String` satisfies it.
