    - role: Move

      job: Hands ownership to another variable, function or channel. The old name becomes unusable.
    - role: Drop
      example: "impl Drop for PooledBuf"
      job: Code the compiler runs once, when the owner's scope ends, on every exit path.
    - role: Clone
      example: "buf.clone()"
      job: An explicit copy of the heap data, with a new owner. You pay for it in the code you write.
  useWhen:
    - A resource must be released exactly once, such as memory, a pooled buffer, a file, a lock or a connection.
    - Data is handed from one stage to the next, such as a parser to a handler to a writer.
    - You want cleanup to happen at a known line, including on errors.
  avoidWhen:
    - Many parts of the program really do share one value for a long time. Use `Rc` or `Arc` and make the sharing explicit.
    - The value is small and plain, such as an id or a timestamp. Derive `Copy` and pass it by value.
  tradeoffs:
    - The compiler rejects programs that a garbage collector would run, some of them correct. You restructure, clone, or share explicitly.
    - Moves are cheap, but clones are easy to sprinkle to silence errors, and each one copies the heap data.
    - Drop order is fixed (reverse order of declaration), which matters for guards and handles that depend on each other.
  lookalikes:
    - name: Garbage collection
      how: Frees memory when nothing points at it, at a time the runtime chooses. Several names may share a value freely.
    - name: Reference counting
      how: Frees when the last reference goes away. Rust offers it explicitly as Rc and Arc; CPython uses it for every object.
    - name: C++ unique_ptr
      how: Single ownership with moves, but using a moved-from pointer compiles and is a null dereference at runtime.

## [concept] Ownership, moves and drop

**Every value in Rust has exactly one owner. Assigning or passing the value moves ownership, and when the owner goes out of scope the value is dropped, once.**

Rust frees memory without a garbage collector and without you calling `free`. It can do that because, at every line, the compiler knows which variable owns each allocation.

<Depth level={2}>
The Rust Book states <Term id="ownership">ownership</Term> as three rules: each value has an owner, there is one owner at a time, and the value is dropped when the owner goes out of scope. A `String` or `Vec<u8>` is a small header on the stack (pointer, length, capacity) pointing at bytes on the heap. `let b = a` copies the header and marks `a` as moved, a <Term id="move-semantics">move</Term>. If both stayed valid, both would free the same bytes at the end of the scope, a <Term id="double-free">double free</Term>. `clone()` copies the heap bytes when you really want two independent values.
</Depth>

<Depth level={3}>
Ownership is tracked by the compiler, not at runtime. Borrow checking runs on MIR, the compiler's control-flow form of each function, and knows on every path whether a variable is initialised, moved, or partly moved. At each scope exit it inserts drop calls for what is still owned, in reverse order of declaration, and skips moved-from variables. A type that implements `Drop` cannot also be `Copy`, because a bitwise copy would give one resource two destructors.
</Depth>

## [problem] Recycle the frame buffer

An event ingest service reads frames of up to 4 KiB from many tenants. To avoid allocating a buffer per frame, it takes one from a pool and returns it when the frame is handled. Every frame also goes to an audit log, written by a background task.

The handler reads the frame, accepts it, sends it to the audit task and gives the buffer back. In testing the audit task writes each entry within microseconds, and every test passes.

<Depth level={2}>
The mental model behind the code is that a buffer is just a value: hand it to whoever needs it, and someone will clean up. Two parties now hold the same bytes, the audit task and the pool, and nothing says which of them is responsible for them.
</Depth>

<Depth level={3}>
<Lang only="go">`defer bufPool.Put(buf)` runs when the handler returns. `buf.Bytes()` is a slice of the buffer's internal array, so the channel carries a view of memory the pool is about to hand to someone else.</Lang>
<Lang only="python">`memoryview(buf)[:n]` is a view into the bytearray, not a copy. The `finally` releases the bytearray to the pool while the view sits in the audit queue.</Lang>
<Lang only="typescript">`buf.subarray(0, n)` shares memory with `buf`. The `finally` releases the Buffer to the pool while the view sits in the audit queue.</Lang>
<Lang only="rust">The Rust version of this code never runs. `send(buf)` moves the buffer into the channel, and the next line tries to use it again. The compiler stops there.</Lang>
</Depth>

## [pain] The audit log under load

**What happened:** audit entries started showing frames from other tenants once traffic passed 2,000 frames a second.

The marked lines are the whole story. The handler returns the buffer to the pool while the audit task still points at its bytes. Under load the audit task falls 30 ms behind, the next frame lands in the recycled buffer first, and the audit task writes that frame instead.

<Depth level={2}>
Nothing crashed and nothing was freed twice. The garbage collector did its job: memory that is referenced stays alive. The bug is that the program reused live memory on purpose, through the pool, and two parties both believed they owned it. About 4 in 10 entries were wrong at peak, and the audit log is the record a customer's compliance team reads.
</Depth>

<Depth level={3}>
<Lang only="rust">The Rust compiler reports `error[E0382]: use of moved value: buf` on the `put` line. The same bug in C would be a <Term id="use-after-free">use after free</Term> or a double free, and in Go, Python or TypeScript it is the data mix-up above. In Rust it is a compile error, so the cost meter shows one error and nothing shipped.</Lang>
<Lang only="go">The race detector does not flag this. The pool hands the buffer over through a synchronised path, so each access is ordered. It is a logic error about who owns the bytes, and Go has no way to state that.</Lang>
<Lang only="python">No exception is raised. The `memoryview` keeps the bytearray alive, exactly as reference counting promises, and the pool writes new bytes into it, which is allowed.</Lang>
<Lang only="typescript">No error is thrown. The view keeps the memory alive, as garbage collection promises, and the next frame is written into it, which is allowed.</Lang>
</Depth>

## [morph] From shared buffer to one owner

Drag the slider. The buffer that everyone could touch becomes a value with one owner at a time: the handler, then the audit task. The last owner returns it to the pool.

The code changes in one way. The buffer is handed on instead of shared, and whoever holds it last gives it back.

<Depth level={2}>
<Lang only="rust">Wrapping the `Vec` in `PooledBuf` with a `Drop` impl means you never write "give it back". Whoever owns the buffer last drops it, on the happy path, on `?`, and on a panic that unwinds. This is <Term id="raii">RAII</Term>, and the move rules make sure exactly one owner exists to do it.</Lang>
<Lang only="go">Go cannot express the transfer, so the code does it by convention. The handler puts the buffer back only on its error paths, and the audit goroutine puts it back after writing. A comment on the channel says who owns what.</Lang>
<Lang only="python">Python cannot express the transfer, so the code does it by convention. The coroutine releases the buffer only on its error path, and the audit task releases it after writing.</Lang>
<Lang only="typescript">TypeScript cannot express the transfer, so the code does it by convention. The function releases the buffer only on its error path, and the audit task releases it after writing.</Lang>
</Depth>

<Depth level={3}>
<Lang only="rust">`std::mem::take(&mut self.bytes)` moves the `Vec` out of the struct and leaves an empty `Vec` behind. `drop` only gets `&mut self`, so it cannot move fields out directly; `take`, `Option::take` and `mem::replace` are the standard ways to do it.</Lang>
<Lang only="go">`sync.Pool` may drop pooled items at any garbage collection, so a pool is a cache, not a fixed set of buffers. That does not change the ownership rule: never use an item after Put.</Lang>
<Lang only="python">A pool keyed by identity would catch a double release: check `buf` is not already in the free list before appending. It catches the symptom at runtime; it cannot stop the early release.</Lang>
<Lang only="typescript">A dev-mode check helps: fill a released Buffer with a marker byte. A view that is still in use then shows the marker instead of plausible data, and tests fail loudly.</Lang>
</Depth>

## [walk] Follow one frame

One frame from the pool to the audit log and back. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="rust">The compiler inserts the drop at each point where `buf` goes out of scope while still initialised. In `ingest`, every path either moves `buf` into the channel or returns early with `buf` still owned, so only the early returns get a drop. When it cannot know statically, after a conditional move, it adds a hidden drop flag on the stack and checks it at the end of the scope.</Lang>
<Lang only="go">Escape analysis puts the `bytes.Buffer` on the heap, because a pointer to it leaves the function through the pool and the channel. The collector frees it only when no goroutine and no pool refers to it.</Lang>
<Lang only="python">Each reference to the bytearray adds to its reference count: the variable, the tuple in the queue, the memoryview. It is freed when the count reaches zero, but the pool keeps one, so it is never freed while pooled.</Lang>
<Lang only="typescript">The Buffer's memory lives outside the JavaScript heap, and the garbage collector frees it once the Buffer object is unreachable. The pool keeps it reachable, so it is reused instead.</Lang>

## [lens] How each language meets it

Rust checks ownership at compile time. Go, Python and TypeScript manage memory for you, so ownership only matters when you reuse memory or release a resource yourself, and then it is a convention you have to keep by hand.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={2}>
The question to ask in every language is the same: who releases this, and can anyone still be using it then? Rust answers it in the type system. Go answers it with <Term id="escape-analysis">escape analysis</Term> and a tracing collector, Python with <Term id="reference-counting">reference counting</Term> plus a cycle collector, and Node with a tracing collector. None of the three can tell you that a pooled buffer is still in use.
</Depth>

### Copy, Clone and moves

Small plain types such as integers, `bool`, `char` and tuples of them implement `Copy`, so assignment duplicates them and the original stays usable. Everything that owns a heap allocation or another resource moves instead. `Clone` is the explicit, possibly expensive copy. A type can be `Copy` only if all its parts are, and never if it implements `Drop`. Passing a value to a function moves it, and returning a value moves it back out, which is how a function can take ownership and hand it back.
