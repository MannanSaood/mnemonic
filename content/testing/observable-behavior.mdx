  useWhen:
    - Always, for unit and integration tests alike. Pick the caller first, then check what that caller sees.
    - A test fails after a refactoring with no behaviour change. Rewrite it through the public goal.
    - An API needs several calls in the right order to do one thing. Give it one operation first, then test that.
  avoidWhen:
    - A piece of internal code is complex and hard to reach through the public API, such as a parser or a pricing rule. Make it a small public unit of its own and test that.
  tradeoffs:
    - Tests through the public API exercise more code per test, so a failure points less precisely at the faulty line.
    - Setting up real collaborators can take more arranging than mocking them. Builders and fakes keep that small.
    - Some outcomes, such as a log line or a metric, are only observable to an operator. Decide whether they are part of the contract before testing them.
  lookalikes:
    - name: Public API
      how: What the language lets anyone call. Often wider than the observable behaviour, because details leak out as public methods.
    - name: Black-box testing
      how: Testing without reading the code. Observable-behaviour tests may be written by someone who knows the code; they just do not depend on it.
    - name: Snapshot tests
      how: Pin the whole output. Useful when the whole output is the contract; brittle when it includes details such as ordering or formatting nobody relies on.

## [concept] Observable behaviour vs implementation detail

**Test what a caller can observe. Everything else is an implementation detail, and a test that depends on it breaks when the details change.**

<Term id="observable-behaviour">Observable behaviour</Term> is what a caller relies on to reach its goal: the value returned, the state it can read afterwards, and the calls that leave the system, such as an email or a courier booking. An <Term id="implementation-detail">implementation detail</Term> is how the code gets there today: helper classes, private functions, the order of internal calls.

A test that checks details fails when someone moves them around, even though nothing a caller sees has changed. That is a <Term id="false-positive-test">false alarm</Term>, and a suite full of them teaches a team to ignore red.

<Depth level={2}>
Observable is not the same as public. A public method that no caller needs is a detail that leaked out; making it private, and testing the goal it serves, fixes both the design and the test. A good API has one operation per goal, so the observable surface is small.
</Depth>

<Depth level={3}>
Vladimir Khorikov calls this a test's resistance to refactoring, and argues it is the one quality you cannot trade away, because a single false alarm costs trust in every test. Kent Beck lists the same property as structure-insensitive in his Test Desiderata. Both apply it at every layer: a test of a service checks the use case, and a test of a domain class checks the smaller goal that class serves.
</Depth>

## [problem] A test that watches every step

`Ship(order)` reserves stock, weighs the parcel, books a courier and marks the order shipped. Its test mocks the weight calculator, spies on the order's setters to check they are called in the right order, and calls the private warehouse helper directly.

It is thorough in one sense: it checks every step. Read it again and ask which line a support agent or a customer would recognise.

<Depth level={2}>
Only the courier booking crosses the system boundary, and the test never checks it with the real weight. The order of `SetStatus` and `SetShippedAt` is something no caller can see. Neither can they see `pickWarehouse`.
</Depth>

<Depth level={3}>
Tests like this often come from writing a test per method, or from mocking every collaborator because a library makes it easy. The London school of TDD mocks collaborators on purpose to design their interfaces; the risk is keeping those mocks for classes that are not at a boundary.
</Depth>

## [pain] Then a change request arrives

**Change request:** Support found shipped orders with no ship date. Make status and date change together in one MarkShipped call.

The order gets a `MarkShipped(at)` method and the setters go away. Every order now ships with a date. The behaviour a caller sees is the same as before, minus the bug, and the test goes red: the marked lines check the setters.

<Depth level={2}>
Worse, this test could not have caught the support ticket's bug. It checked that the setters were called, not that the order ended up with a date. Tests tied to details fail when you improve the code and pass when the result is wrong.
</Depth>

<Depth level={3}>
The playground shows the second half of that sentence. When a piece is mocked, the test sees only what the mock says. A unit mismatch between the service and the real weight calculator, or a reserver that changed how it reports short stock, passes every test that mocks them.
</Depth>

## [morph] Test through the goal

Drag the slider. The test stops reaching into the service. It calls `Ship`, then reads the order's status and ship date, the stock level, and the courier booking. The setters and the weight calculator become internals the test never names.

Hover a box in the diagram to see its code.

<Depth level={2}>
The courier keeps a test double, because the booking leaves the system and a real truck would come. The stock stays real, in memory, because it is your own code. Mock at the boundary, not between your own classes.
</Depth>

<Depth level={3}>
In hexagonal terms, the test drives the application through its port (`Ship`) and observes the adapters on the far side (the courier). What happens between the two is free to change. That is the same rule at the scale of a whole service as at the scale of one class.
</Depth>

The same request, with the behaviour test. The order gets `MarkShipped(at)`, the setters disappear, and the test still reads a shipped order with a ship date. Nobody edits it.

<Depth level={2}>
This test would also have caught the original support ticket: an order marked shipped with no date fails the `ShippedAt` assertion. Checking the result catches the bug that checking the steps let through.
</Depth>

<Depth level={3}>
If a detail is complex enough to deserve its own tests, such as the warehouse table, promote it to a small public unit with its own goal, for example a `Warehouses` type with a `For(country)` method. Then its tests are behaviour tests of that unit, not peeks into the service.
</Depth>

## [play] Refactor, then plant bugs

Two suites test the same shipping service and both pass. Suite A checks each internal step; suite B checks only what a caller can observe.

Apply five refactorings and count the false alarms. Then plant four real bugs and count what each suite misses.

## [lens] How each language writes it

The languages differ in how hard they make it to reach internals from a test: Go and Rust draw a line between package or crate tests and outside tests, TypeScript's `#private` is enforced at runtime, and Python relies on convention.

### A quick test for any test

Read the test name and its assertions to someone who knows the product but not the code. If they can say which requirement it protects, it checks behaviour. If they hear class names and call orders, it checks details, and it will break at the next refactoring.
