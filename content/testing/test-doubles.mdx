  useWhen:
    - The real dependency is slow, shared, costs money or sends something to the outside world (email, payments, a partner's API).
    - You need a case that is hard to stage for real, such as a missing row, a timeout or a declined card.
    - A command leaves the system and its content is the outcome the test is about.
  avoidWhen:
    - The dependency is your own pure code. Use the real thing; a double only hides bugs between the two.
    - You are about to assert on a query's call count or arguments. Feed it with a stub and assert on the result instead.
    - The double would be harder to read than the real dependency, such as a stub chain three calls deep.
  tradeoffs:
    - Every double is a second implementation of the interface that can drift from the real one; keep some tests against the real dependency.
    - Mock libraries make strict expectations cheap to write and expensive to keep.
    - Hand-written fakes cost more up front and less later, because one fake serves every test.
  lookalikes:
    - name: Mocking library
      how: A tool such as unittest.mock, Vitest or mockall that can build any kind of double. Using it does not make the double a mock.
    - name: Monkey patching
      how: Replaces a function by name at runtime. It needs no seam in the code, and breaks when the import path or name changes.
    - name: Contract test
      how: Runs the same tests against the real dependency and its fake, so the fake cannot drift.

## [concept] Mocks, stubs and friends

**A test double stands in for a real dependency in a test. There are five kinds, but only two roles: feed data in, or check what goes out.**

A <Term id="test-double">test double</Term> replaces something the code depends on, such as a database, a mail provider or a clock. A <Term id="dummy">dummy</Term> fills a parameter, a <Term id="stub">stub</Term> answers queries, a <Term id="spy">spy</Term> records calls, a <Term id="mock">mock</Term> expects calls, and a <Term id="fake">fake</Term> really works, in memory.

Group them by role. Stubs (and fakes and dummies) feed data into the code under test. Mocks and spies check the commands it sends out. Pick the role first, and the kind follows.

<Depth level={2}>
The split follows <Term id="command-query-separation">command-query separation</Term>. A query returns data and changes nothing, so how often it is called is the code's own business: stub it. A command changes something outside, such as sending an email or charging a card, and that change is the outcome: check it with a mock or a spy. Never assert on a stub.
</Depth>

<Depth level={3}>
Gerard Meszaros named the five kinds in *xUnit Test Patterns* (2007), and Martin Fowler's article *Mocks Aren't Stubs* made the distinction widely known. Mock objects themselves come from a 2000 paper by Mackinnon, Freeman and Craig, where they were a tool for designing the interfaces between objects. Vladimir Khorikov's *Unit Testing* reduces the five to the two roles used here, and argues that mocks belong only at the edge of the system.
</Depth>

## [problem] A test that checks every call

`SendReceipt` loads an order and its customer from a repository, then emails a receipt through a mail provider. Its test replaces both with mocks and expects every call the service makes: the order loaded twice, the customer loaded once, one email sent.

It looks thorough. It passes. Read which lines are about what a customer gets, and which are about how the service got its data.

<Depth level={2}>
Only the mailer expectation describes an outcome. The two repository expectations describe the service's internal steps. They were copied from what the code did on the day the test was written.
</Depth>

<Depth level={3}>
Strict mock libraries push in this direction. gomock and mockall fail on any call that has no matching expectation, so the author must write an expectation for every query just to get the test to run, and then the counts are frozen in.
</Depth>

## [pain] Then a change request arrives

**Change request:** The database team found that SendReceipt loads every order twice. Load it once.

The fix is one line in the service. The receipt it sends is byte for byte the same. The test goes red anyway, and the marked line has to be edited before the change can merge.

<Depth level={2}>
This is a false alarm: a test that fails when nothing a user can see has changed. Each one costs a little time, and together they teach the team that red means "update the test", not "you broke something". That is how real failures get waved through.
</Depth>

<Depth level={3}>
The next refactoring, replacing two queries with one joined query, breaks the test again. A per-test stub configured for `getOrder` breaks too, because nothing answers the new method. A fake repository that implements the whole interface survives both. The playground lets you count these.
</Depth>

## [morph] Stub what comes in, check what goes out

Drag the slider. The repository becomes a stub that hands over canned data and is never checked. The mailer stays a test double that checks the email, because the email is what the test is about.

Hover a box in the diagram to see its code.

<Depth level={2}>
The test now has one assertion, and it is about the outcome. It still catches every bug that changes the email: a missing send, a wrong address, a double send, a wrong total.
</Depth>

<Depth level={3}>
A stub can still carry a little knowledge of the code, such as which methods it answers. A fake goes further: it is a real implementation, so the test holds no knowledge of how the data was fetched at all. Use fakes for dependencies many tests share.
</Depth>

## [again] Load once, the second time

The same request, with the new test. The service loads the order once. The stub does not care how many times it is asked, and the email is unchanged, so the test stays green and nobody edits it.

## [lens] How each language writes it

Every language here can build all five kinds by hand. They differ in what the standard tools nudge you towards: hand-written doubles in Go, one flexible `Mock` in Python, `vi.fn` in TypeScript, and generated mocks or small trait impls in Rust.

### Mock the edge, not the middle

Mocks are worth their cost where a command leaves your system and someone outside would notice: an email, a payment, a message to another team's service. Between your own classes, use the real objects, and a stub or fake for data that comes from outside. The next lesson, on observable behaviour, explains why.
