## [concept] Red, green, refactor

**Write one test that fails. Make it pass with the smallest change. Clean up while everything is green. Repeat.**

<Term id="red-green-refactor">Red, green, refactor</Term> is the cycle of test-driven development. Red: a new test fails, because the behaviour is not there yet. Green: the quickest change that makes every test pass, even a hard-coded answer. Refactor: improve the code, with the tests proving nothing broke.

Keep a <Term id="test-list">test list</Term> beside you: the behaviours you still need, in plain words. Each cycle turns one item into a test. The steps are small on purpose. When a bar goes red unexpectedly, the cause can only be the last few lines.

<Depth level={2}>
Two rules drive it. Write no new code unless a failing test asks for it. Remove duplication once the tests are green. Do not mix the two: get to green first, then refactor, and never refactor while red. Adjust the step size as you go. After a surprise, take smaller steps; when it is going smoothly, take bigger ones.
</Depth>

<Depth level={3}>
Kent Beck described the cycle in *Test-Driven Development: By Example* (2002). In his 2023 article *Canon TDD* he restated it as a list, then one test, then make it pass, then optionally refactor, and named the common mistakes: writing every test up front, copying the code's output into the expected values, and mixing refactoring into making a test pass. The claims about fewer defects come from practitioners' experience; studies of TDD's effect on defects disagree.
</Depth>

## [problem] Code first, tests after

A ticket asks for a cart total: sum the items, take 10% off from $100.00, let the SAVE5 coupon take $5.00 off, never go below zero. An engineer writes the whole function in one sitting, from memory of the ticket.

Then they write a test for the discount. To get the expected number, they run the code and paste what it returned.

<Depth level={2}>
The test passes, of course. It was written to agree with the code. It never failed, so nobody knows it can, and it checks what the code does rather than what the ticket asked for.
</Depth>

<Depth level={3}>
Coverage tools report the discount line as covered. Coverage says a line ran; it does not say the result was right.
</Depth>

## [pain] Then a change request arrives

**Change request:** Finance found two refunds: a $100.00 order got no discount, and a $3.00 order with SAVE5 was charged -$2.00.

The marked lines are the fixes: `>` should have been `>=`, and the coupon needs a floor at zero. The third marked line is the test, which asserted the bug and has to change too.

<Depth level={2}>
Both cases were in the ticket. They were missed because nothing forced anyone to write them down as examples before the code existed. The boundary case and the negative total are exactly what a test list catches.
</Depth>

<Depth level={3}>
A test written from the code's output can never disagree with the code. That is the failure Beck lists for the green step: copying computed values into the expected values defeats the check.
</Depth>

## [morph] Let failing tests pull the code

Drag the slider. The one-shot function and its pasted test become a loop: take an item from the list, see it fail, make it pass, clean up, take the next.

Hover a box in the diagram to see its code.

<Depth level={2}>
The finished code looks much like the original. The difference is that each line arrived because a test asked for it, and each test was seen to fail first. The exact-$100.00 row and the never-below-zero row are on the list from the start, so the two refunds never happen.
</Depth>

<Depth level={3}>
Refactoring is where design happens in TDD. Extracting `subtotal` and naming the constants did not change any result; the green bar proves it, which is what makes these changes cheap enough to do every cycle.
</Depth>

<Lang only="go">`t.Run` gives each row its own name, so `go test -run 'TestCartTotal/exactly'` reruns only the new case while you work on it, and the full suite before you move on.</Lang>
<Lang only="python">`parametrize` makes each row a separate test with its own id, so a failure names the row. `pytest -x` stops at the first one.</Lang>
<Lang only="typescript">`test.each` interpolates `$items` and `$want` into the name, so the watcher reports exactly which row went red.</Lang>
<Lang only="rust">Rust's red often comes in two stages: first the test does not compile, then it compiles and fails. Both count. The message on `assert_eq!` prints the inputs for the failing case.</Lang>

## [again] The two refunds, the second time

The same request, test first. Two new rows go on the list, and each is run and seen red before any fix. Then the smallest change for each, one at a time, with the whole suite green in between.

<Depth level={2}>
This is also how to handle any bug report in TDD: reproduce it as a failing test first. The test proves you found the bug, proves the fix works, and stays to stop it coming back.
</Depth>

<Depth level={3}>
Notice what did not happen: nobody edited an existing test to make it pass. In a test-first suite, an existing test that must change means the requirement changed, and that is worth a conversation.
</Depth>

### Three ways to get to green

When the answer is obvious, write it. When it is not, return a constant and let the next test force the real code. When you are unsure of the general shape, add a second example and generalise only when both pass. The next lesson covers these three gears and when to switch between them.
