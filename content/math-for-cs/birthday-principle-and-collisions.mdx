## [concept] Birthday principle and collisions

**When you draw n random IDs from d possible values, the chance that some two match is about 1 − e^(−n²/2d). Collisions become likely near √d IDs, far sooner than d, because every pair of IDs is a chance to collide.**

The classic version: in a room of 23 people, two share a birthday more often than not. The same arithmetic decides whether your random IDs, short links or truncated hashes can collide. The <Term id="birthday-bound">birthday bound</Term> turns "4.3 billion values, we will never run out" into "collisions start in the tens of thousands".

<Depth level={2}>
Count pairs, not items. n IDs make n(n−1)/2 pairs, and each pair matches with chance 1/d. By <Term id="linearity-of-expectation">linearity of expectation</Term>, the expected number of matching pairs is n(n−1)/2d, even though the pairs are not independent. While that number is small, it is also roughly the chance of any collision. The chance passes 50% near n = 1.18 √d and 63% at n = √(2d).

To size an ID, solve n²/2d ≤ p for the risk p you accept: d ≥ n²/2p. Only random bits count. A <Term id="uuidv4">UUIDv4</Term> has 122, and a <Term id="uuidv7">UUIDv7</Term> spends 48 bits on a timestamp and keeps 74 random bits for the IDs made in the same millisecond.
</Depth>

<Depth level={3}>
The exact chance of no collision is the product of (1 − i/d) for i from 1 to n − 1: each new ID must avoid all earlier ones. Because 1 − x ≤ e^(−x), the product is at most e^(−n(n−1)/2d), and for n much smaller than d the two agree closely. That bound is how MIT's Mathematics for Computer Science derives the √d rule. The expected number of draws until the first repeat is about √(πd/2), about 1.25 √d.
</Depth>

## [problem] Short random names for uploads

An upload service stores each file in object storage under a random key of 8 hex characters. That is 32 random bits, 4.3 billion possible keys, from the operating system's <Term id="csprng">secure random generator</Term>. Keys go into URLs, so short is nice.

The service holds about 30,000 files. Nobody has seen a collision.

<Depth level={2}>
At 30,000 files the expected number of matching pairs is 30,000² / (2 × 2^32), about 0.1. There is roughly a 1 in 10 chance that a collision has already happened. Nobody would know: a plain put to an existing key replaces the object and returns success.
</Depth>

<Depth level={3}>
The generator is not the problem. crypto/rand, secrets and randomBytes are uniform, which is exactly what the formula assumes. A biased or poorly seeded generator makes it worse: two processes that seed a PRNG with the same clock second produce the same IDs, a collision rate no formula predicts.
</Depth>

## [pain] Then a change request arrives

**Change request:** import 2 million attachments from the old system into the new upload store this weekend.

The marked lines save every old attachment through the same code. 2 million files make about 2 × 10^12 pairs, and each pair matches with chance 1 in 4.3 billion: about 466 matching pairs. The chance of at least one is indistinguishable from 100%. Each match silently replaces a file with another customer's attachment, and the first sign is a support ticket weeks later.

<Depth level={2}>
The intuition that failed is "2 million is tiny next to 4.3 billion". It compares the count to the space. The right comparison is the count squared to twice the space: (2 × 10^6)² / (2 × 4.3 × 10^9) ≈ 466.
</Depth>

<Depth level={3}>
Retrying on collision does not help when the store cannot tell you there was one. The before code has no uniqueness check, so even a perfect retry loop would never run.
</Depth>

## [morph] Size the key for the pairs, then guard it

Drag the slider. "4.3 billion is plenty" becomes a risk computed from the pairs, and the plain put becomes a put that refuses an existing key.

The key grows to 122 or more random bits: a UUID, 16 random bytes, or Go's `rand.Text()`. At 2 million files the chance of any collision falls to about 10^-25. The store is also told to refuse an existing key, so if the improbable happens the save fails and draws a new key instead of destroying a file.

<Depth level={2}>
Both halves matter. Enough bits make collisions too rare to plan around. The guard makes them harmless when they happen anyway, through a bug, a bad generator or a key someone shortened later. The guard alone, with short keys, works too, but every save at scale pays for retries, and a key collision in a URL that was already shared cannot be retried.
</Depth>

<Depth level={3}>
Amazon S3 supports conditional writes with `If-None-Match: *` on PutObject since August 2024 and answers 412 Precondition Failed when the key exists. In a database the same guard is a unique index with `INSERT ... ON CONFLICT DO NOTHING` (PostgreSQL) and a check of the affected row count.
</Depth>

## [walk] Count the pairs

From the pairs to the formula, to the bits, to the guard. Use the numbered buttons.

<Depth level={2}>
The rule sizes more than IDs. A 6-character code from 62 symbols has 62^6 ≈ 5.7 × 10^10 values and reaches even odds of a collision at about 280,000 links. A hash table with m slots sees its first collision around √m keys, which is why every table needs a collision strategy from the start. A 64-bit hash used as a deduplication key becomes risky around 2^32, about 4 billion items.
</Depth>

<Depth level={3}>
For cryptographic hashes the same bound becomes the birthday attack. Finding any two inputs with the same n-bit hash takes about 2^(n/2) tries, so a 128-bit hash offers about 64 bits of collision resistance. That is part of why MD5 was retired and SHA-256 has 256 bits.
</Depth>

## [again] The same import, with wide keys and a guard

The import runs with 2 million 122-to-130-bit keys. The chance of any collision is far below 10^-24, and if one happens the store refuses it and the code retries. The test states the bound for the old and new key sizes, so a future change that shortens the key fails in CI.

<Depth level={2}>
Write the risk calculation down where the key is generated. "122 random bits, 10^-25 at 2 million files, retried on conflict" is a sentence a reviewer can check. "Random string" is not.
</Depth>

<Depth level={3}>
Use `expm1` for the probability. 1 − e^(−x) for x = 10^-25 is 1 − 1 in floating point, which is 0; `expm1(-x)` keeps it as −10^-25. The same care applies to logarithms of probabilities near 1 (`log1p`).
</Depth>

| Bits for n IDs at risk p | log2(n² / 2p) | 89 bits for 10^9 IDs at 10^-9 |
