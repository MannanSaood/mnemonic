        // inv is mult⁻¹ mod space (513_180_409), found once by the extended Euclidean algorithm.
        var inv = func() int64 {

## [concept] Modular arithmetic

**Arithmetic modulo m works on a clock of m ticks: add, subtract or multiply as usual, then keep the remainder. You can undo a multiplication by a only when a and m share no factor, and then you undo it by multiplying by a's inverse.**

<Term id="modular-arithmetic">Modular arithmetic</Term> is in more code than it looks. Ring buffers, hash table slots, round-robin schedulers, check digits, random number generators and every public-key system work on a clock. Two numbers are <Term id="congruence">congruent</Term> mod m when they land on the same tick. A <Term id="modular-inverse">modular inverse</Term> is the clock's version of division.

<Depth level={2}>
Addition, subtraction and multiplication respect remainders: (a · b) mod m equals ((a mod m) · (b mod m)) mod m. You may reduce after every step, which is how code keeps numbers small enough for a machine word. Division does not carry over. a has an inverse mod m exactly when gcd(a, m) = 1, and the <Term id="extended-euclid">extended Euclidean algorithm</Term> finds it in O(log m) steps.

Cancelling needs the same condition. If a · x ≡ a · y (mod m) and gcd(a, m) = 1, then x ≡ y. Without it, 8 · 2 ≡ 8 · 5 (mod 12) yet 2 ≢ 5.
</Depth>

<Depth level={3}>
The extended algorithm keeps an invariant on every row: r ≡ s · a (mod m). The first two rows, (m, 0) and (a, 1), satisfy it trivially. Each new row subtracts q times the previous one from the one before, and congruences survive subtraction. The remainders fall to the gcd and then 0. If the gcd is 1, its row says 1 ≡ s · a, so s is the inverse. The proof that gcd(a, m) = 1 is necessary runs the other way: any common factor d divides every s · a + t · m, so 1 is never reachable.
</Depth>

## [problem] Order numbers that hide the order count

A shop prints a public number on every invoice instead of the database id, so competitors cannot read the sales volume from two invoices. The encoder multiplies the id by a large constant, adds an offset and keeps the last nine digits. Consecutive orders get numbers that look random.

When support needs the order, the tool looks the public number up in an indexed column. It has worked since launch.

<Depth level={2}>
The scheme is a bijection only because the multiplier, 387,420,489 = 3^18, shares no factor with 10^9 = 2^9 · 5^9. Whoever chose it was lucky or careful. A multiplier ending in 0 or 5, or any even one, would have given two orders the same number.
</Depth>

<Depth level={3}>
In TypeScript the encoder is already wrong. `id * MULT` exceeds 2^53 once ids pass about 23 million, and the double rounds the product before `%` sees it. Id 24,000,017 encodes to 374,490,188 instead of 374,490,190. Every other language here computes it exactly in 64-bit integers.
</Depth>

## [pain] Then a change request arrives

**Change request:** the call-centre tool must turn a public order number back into the order id offline, without the orders database.

The marked lines do what algebra suggests: subtract the offset and divide by the multiplier. For order 1,000,042 the public number is 813,002,415, and the "decoded" id is 1. The multiply was followed by a mod that discarded 387,436 full turns of the clock. Ordinary division cannot recover the turns, so the tool shows the wrong order.

<Depth level={2}>
On a clock, multiplication is undone by multiplying again, by the number x with 387,420,489 · x ≡ 1 (mod 10^9). That x exists because the gcd is 1, and the extended Euclidean algorithm computes it once: 513,180,409.
</Depth>

<Depth level={3}>
In Rust the marked line also underflows: `public - OFFSET` is negative for public numbers below the offset, and `u64` subtraction panics in a debug build. The fixed version adds `SPACE` first. In Go and TypeScript the same subtraction gives a negative remainder, because `%` keeps the sign of the dividend; Python's `%` takes the sign of the divisor and gives the clock answer directly.
</Depth>

## [morph] Divide by multiplying

Drag the slider. Encode and divide become encode and multiply-by-inverse, with the inverse computed once at startup.

The decoder no longer needs the database. It subtracts the offset, multiplies by 513,180,409 and keeps the last nine digits. The startup check fails loudly if someone ever changes the multiplier to one that shares a factor with 10^9.

<Depth level={2}>
Keep every intermediate below the modulus and make sure the product of two residues fits your integer type. Here residues are below 10^9 and products below 10^18, so `int64` and `u64` work. For a 64-bit modulus you need a 128-bit product: `u128` in Rust, `bits.Mul64` in Go, Python ints or `BigInt`.
</Depth>

<Depth level={3}>
This scheme hides the order count from casual readers only. Anyone who sees two consecutive invoices learns the multiplier, and anyone who learns the multiplier decodes everything. For a secret mapping use format-preserving encryption (NIST FF1) or an HMAC with a lookup table.
</Depth>

## [walk] Decode one order number

Encode, find the inverse, decode, and the integer width that makes it exact. Use the numbered buttons.

<Depth level={2}>
The same arithmetic explains why hash(key) mod N sharding hurts. A key stays on its shard only when hash mod N equals hash mod (N + 1), which is true for about 1 in N + 1 hash values, so going from 4 shards to 5 moves about 80% of keys. Consistent hashing exists to avoid that.
</Depth>

<Depth level={3}>
<Term id="modular-exponentiation">Modular exponentiation</Term> by repeated squaring computes b^e mod n with about log2(e) squarings, reducing after each. A 2048-bit exponent costs about 2,048 squarings, never a 2^2048-step loop. Fermat's little theorem says a^(p−1) ≡ 1 (mod p) for a prime p and a not divisible by p; Euler's theorem generalises it to a^φ(n) ≡ 1 (mod n) when gcd(a, n) = 1, where <Term id="euler-totient">φ(n)</Term> counts the numbers below n coprime to it.
</Depth>

## [again] The same request, with the inverse

The tool decodes every public number exactly, offline, with two multiplications. The test round-trips a million ids and confirms that no two share a number, which is the bijection the gcd promised.

<Depth level={2}>
Python's `pow(a, -1, m)` and Go's `big.Int.ModInverse` are the one-line versions. In TypeScript and Rust the ten-line loop is short enough to write and test yourself, with the invariant in a comment.
</Depth>

<Depth level={3}>
<Term id="rsa">RSA</Term> is the same lesson one level up. Pick primes p and q, publish n = p · q and an exponent e with gcd(e, φ(n)) = 1, and keep d = e⁻¹ mod φ(n). Encryption is c = m^e mod n and decryption is c^d mod n. Because e · d = 1 + k · φ(n), Euler's theorem turns m^(e·d) back into m. Anyone who can factor n can compute φ(n) and then d, so security rests on factoring being hard for 2048-bit n. Implementations often use λ(n) = lcm(p − 1, q − 1) instead of φ(n), which gives a smaller d that works the same way.

Textbook RSA is deterministic: the same message always gives the same ciphertext, so an attacker can encrypt guesses and compare. It is also malleable: multiplying two ciphertexts multiplies the messages. Real systems add random padding (<Term id="oaep">OAEP</Term> for encryption, PSS for signatures) and use a library.
</Depth>
