    - A loop moves two indices or a window, such as binary search, partition, two pointers or a sliding window.

    - A stronger invariant is easier to use at the exit but harder to keep in each step. Pick the weakest one that still gives the answer.

    - name: Property-based test

    - name: Strong induction
      how: Assumes every smaller case, not just the previous one. Fits recursion such as quicksort.

## [concept] Induction and loop invariants

**A loop is correct if some statement about its variables is true before the first iteration, stays true after every iteration, and gives the answer when the loop stops. That statement is the loop invariant, and checking it is a proof by induction on the number of iterations.**

<Term id="mathematical-induction">Induction</Term> proves a claim for every n with two steps. Prove it for the first case, then prove that each case passes it on to the next. A <Term id="loop-invariant">loop invariant</Term> applies the same idea to a loop. The first case is the state before the loop, and each iteration is one step. Tests check the inputs someone thought of. An invariant covers every input, including the ones nobody thought of.

<Depth level={2}>
Proving a loop with an invariant takes four checks. **Base case:** the invariant holds after initialisation. **Step:** if it holds at the top of an iteration, it holds at the bottom. **Exit:** the invariant plus the loop condition being false implies the result you promised. **Termination:** some non-negative integer, the <Term id="loop-variant">termination measure</Term>, falls every iteration. Most off-by-one bugs break the base case or the exit, and the bodies of the iterations are usually fine.

Write the invariant as a comment next to the loop. If you cannot state one, you do not yet know why the loop works, and neither will the next reader.
</Depth>

<Depth level={3}>
Ordinary induction, <Term id="strong-induction">strong induction</Term> (assume every smaller case) and the well-ordering principle (every non-empty set of naturals has a least element) prove the same things. MIT's Mathematics for Computer Science shows each can be rewritten as the others. Well ordering is how termination arguments work: if the loop ran forever, the set of measure values would have no least element, which is impossible for naturals. Choose by convenience. Recursion that splits into uneven parts, like quicksort, reads most naturally as strong induction on the input size.
</Depth>

## [problem] A cursor search over an event log

A webhook dispatcher keeps an append-only event log sorted by sequence number, with gaps where old events were compacted. Each consumer stores a cursor: the next sequence number it wants. A page is the events with `seq >= cursor`, found with a binary search for the first such event.

The search was written by hand and reviewed. A nightly batch job calls it with the start of yesterday's range, and it has returned the right page every night for a year.

<Depth level={2}>
This search is a lower bound: the first index whose value is at least the target, or the length of the log when no value is. That last case matters. It is a real answer, not an error, and it means "nothing new".
</Depth>

<Depth level={3}>
Binary search is famous for being easy to describe and hard to get exactly right. Jon Bentley reported in Programming Pearls that most professional programmers he asked could not write a correct one, and the version in Java's standard library had an overflow bug for nine years.
</Depth>

## [pain] Then a change request arrives

**Change request:** webhook consumers stop using the nightly batch and poll every second from their saved cursor.

The marked lines poll in a loop and save `seq + 1` after each delivery. Within a minute, consumers that are caught up start getting the last event again on every poll. A payment-succeeded webhook arrives 3,600 times an hour. The nightly job never asked for a cursor past the last event; a poller asks for little else.

<Depth level={2}>
Walk the code with cursor 132 and a log whose last event is 131. lo = 0, hi = 7. The loop moves lo up to 7 and stops with lo == hi. It returns 7, and the page holds event 131 again. No iteration did anything wrong. The search can never return 8, because hi starts at 7 and only goes down.
</Depth>

<Depth level={3}>
In Rust the same code has a second edge: on an empty log `events.len() - 1` underflows. A debug build panics with "attempt to subtract with overflow", and a release build wraps to `usize::MAX` and panics on the index instead. Both are the same mistake, a starting value that claims something the code never checked.
</Depth>

## [morph] Name what the loop knows

Drag the slider. The picture of "halve until found" becomes a statement the loop keeps: everything left of lo is below the cursor, everything from hi on is at or above it, and the range between is still unknown.

With that statement written down, the bug is visible in the first line. `hi = len(events) - 1` claims the last event is at least the cursor before the loop has looked at it. Starting at `hi = len(events)` makes the known-large side empty, which is true for any cursor. The <Term id="half-open-range">half-open range</Term> [lo, hi) is what makes the base case free.

<Depth level={2}>
Pick one convention and keep it everywhere: half-open ranges with `hi` excluded, `while lo < hi`, `lo = mid + 1`, `hi = mid`. Each line then has a reason. Mixing a closed range with `hi = mid` is how loops end up hanging or skipping an element.
</Depth>

<Depth level={3}>
`lo + (hi - lo) / 2` is always between lo and hi − 1 when lo < hi, so `events[mid]` is a real index and both branches shrink hi − lo by at least one. `(lo + hi) / 2` gives the same value mathematically but can overflow a fixed-width integer when lo + hi does not fit, which is the arithmetic the proof assumed away.
</Depth>

<Depth level={2}>
The same template proves other loops. A ledger loop that sums payments keeps "total equals the sum of the first i payments". A retry loop with a deadline keeps "at most one charge request is in flight and attempts are below the cap"; the measure is the attempts left.
</Depth>

<Depth level={3}>
The well-known fallacy that all horses are the same colour uses an inductive step that works for every n except one. Going from 1 horse to 2, the two overlapping groups of size 1 share no horse, so nothing links their colours. A step that fails for one small n breaks the proof for every n after it. Loops fail the same way: an iteration that is correct for ranges of length 3 and more can still be wrong for length 1.
</Depth>

## [again] The same request, with the invariant

The poller now gets an empty page when it is caught up, and a duplicate never goes out. The test runs every cursor from below the first event to past the last and compares the result with the library's lower bound.

<Depth level={2}>
The test is cheap because the proof told you where to look. The proof separates three kinds of input: below every element, inside the range, and above every element. A test should have at least one cursor of each kind, plus the empty log.
</Depth>

<Depth level={3}>
For two indices, an invariant is easy to check in a test: write a function that evaluates it, call it at the top of each iteration under a debug flag, and run the property test. Rust's `debug_assert!`, Python's `assert` and Go's test-only helpers all do this without a cost in production.
</Depth>
