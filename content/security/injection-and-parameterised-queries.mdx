    - Do not escape or strip characters by hand as the defence. It covers one context, breaks names like O'Brien, and misses the others.

## [concept] Injection and parameterised queries

**Injection happens when input is pasted into text that an interpreter parses, so part of the input is read as code. Keep the code fixed and send the input as values the interpreter never parses.**

For SQL, that means a <Term id="parameterised-query">parameterised query</Term>: the statement has placeholders, and the values travel separately. Whatever the values contain, they can only be compared, stored or returned.

<Depth level={2}>
<Term id="sql-injection">SQL injection</Term> is one member of a family. Shell commands, LDAP filters, file paths, HTML and templates all have a parser on the other side, and each goes wrong the same way. The fix has the same shape everywhere: an API that takes structure and data separately. For the parts of a query that cannot be parameters, such as a column name, use an <Term id="allow-list">allow-list</Term> of values you wrote.
</Depth>

<Depth level={3}>
In PostgreSQL's <Term id="extended-query-protocol">extended query protocol</Term>, the client sends Parse with the statement text, then Bind with the parameter values, then Execute. The parser has finished before any value arrives, so a value cannot change the plan. Some drivers instead interpolate on the client (psycopg 2, or any driver when you pass no parameters), quoting each value correctly for its type. That is also safe, as long as the driver does the quoting and you do not.
</Depth>

## [problem] A customer search built with string formatting

The support tool has a customer search. The handler formats the search text and the sort column into the SQL string and runs it, scoped to the caller's tenant. Only the support team uses it.

It works. Searches return the right customers, sorting by any column works, and nobody types anything strange.

<Depth level={2}>
The mental model behind it: q is a name and sort is a column, because that is what the UI sends. But the database does not see a name and a column. It sees one string of SQL and parses all of it. Whoever controls part of that string controls part of the query.
</Depth>

<Depth level={3}>
The handler also returns the database's error message to the client. That makes debugging easy for the support team, and probing easy for anyone else: a syntax error near the input confirms that the input is being parsed.
</Depth>

## [pain] Then tenant admins get the search too

**Change request:** tenant admins now get the customer search too, not just our support staff.

The first ticket is from a customer: searching for their colleague Siobhan O'Brien returns an error that mentions an unterminated quoted string. Two weeks later another tenant's admin searches for `' OR 1=1 --` and gets three other companies' customers. A UNION in the search box returns the users table with its password hashes. A semicolon starts a second statement that deletes every customer.

<Depth level={2}>
Each attack only rearranges the query. The quote ends the string literal, `OR 1=1` joins the WHERE clause and defeats the tenant check, and `--` comments out the rest of the template so the leftover quote cannot cause an error. UNION adds a second SELECT over any table the database role can read. Whether the stacked DELETE runs depends on the driver: when no parameters are given, many drivers send the text in a way that allows several statements.
</Depth>

<Depth level={3}>
Escaping quotes would have stopped the first three and not the last one. The sort column is not inside a string literal, so `name; DROP TABLE customers --` needs no quote at all. Numeric fields have the same problem, which is why escaping is the wrong idea: it protects one parser context, and a query has several.
</Depth>

## [morph] From one glued string to statement plus values

Drag the slider. The single box where SQL and input were glued together splits into a fixed statement, a set of parameters bound after parsing, and an allow-list for the column name.

The code keeps the same query and changes how it is assembled. Placeholders replace the pasted values, and the sort column comes from a map.

<Depth level={2}>
Tenant isolation deserves a second guard too. PostgreSQL <Term id="row-level-security">row-level security</Term> can filter customers by a tenant setting on the session, so a missing WHERE clause or an injected OR cannot cross tenants. Give the application role only the privileges it needs; it should not be able to drop tables.
</Depth>

<Depth level={3}>
With parameters, PostgreSQL rejects <Term id="stacked-queries">stacked queries</Term> outright: a prepared statement may hold only one command, and the server says "cannot insert multiple commands into a prepared statement". Parameterised code therefore cannot run a second statement even when it has a different bug.
</Depth>

## [walk] Follow one search

The same request, `q=' OR 1=1 --`, through the fixed handler.

<Depth level={3}>
<Term id="second-order-injection">Second-order injection</Term> is the version that gets past reviews. A display name is stored safely through a parameterised INSERT, and months later a reporting job builds SQL from names it reads back out of its own table. <Depth level={2}>

</Depth>

## [lens] How each language passes parameters

Every driver takes the query text and the values separately. The danger in each language is the string feature that looks like a parameter but is not: `fmt.Sprintf`, the f-string, the untagged template literal, `format!`.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Placeholder syntax differs by driver: `$1` for PostgreSQL drivers in Go, Node and Rust, `%s` for psycopg, `?` for sqlite3 and MySQL drivers. Only values can be placeholders. Table names, column names and sort directions come from allow-lists, or from an identifier-quoting helper applied to a fixed name.
</Depth>

<Depth level={3}>
Type systems can help. psycopg 3 annotates queries as `LiteralString` (PEP 675), so a type checker flags an f-string query; sqlx 0.9 accepts only `&'static str` without `AssertSqlSafe`; tagged-template libraries in TypeScript turn every interpolation into a parameter. Go has no type-level guard, so linting and code review carry it.
</Depth>

### Where each kind of input goes

| Part of the query | Example | How to pass it |
|---|---|---|
| A value | a name, an id, a date | A parameter: `$1`, `%s`, `?` |
| A list of values | ids for `IN (...)` | One array parameter (`= ANY($1)` in PostgreSQL), or one placeholder per item |
| An identifier | a sort column, a table | An allow-list of names you wrote |
| A keyword | `ASC` or `DESC` | Map the choice to one of the two literals |
