    - role: Origin check
      example: { go: "http.CrossOriginProtection", python: "CsrfViewMiddleware", typescript: "a Sec-Fetch-Site middleware", rust: "a from_fn middleware" }
      job: Refuses unsafe requests that another origin started.
    - role: CSRF token
      example: a per-session random value in every form
      job: Proves the request came from a page that could read your HTML.
  useWhen:
    - Any site that uses cookies for authentication and has state-changing endpoints.
    - You set SameSite=None for an embed or a third-party flow. Add an origin check or tokens before you ship it.
    - Login and logout forms. Login CSRF signs the victim into the attacker's account.
  avoidWhen:
    - APIs authenticated only by an Authorization header that your own script sets. Browsers do not attach it on their own, so there is nothing to forge.
    - Do not rely on CORS settings. CORS controls which origins may read responses, and a simple request is sent regardless.
    - Do not change state on GET, even behind a token, since tokens leak through URLs and logs.
  tradeoffs:
    - SameSite=Strict blocks the most but logs the user out when they follow a link from email or another site; Lax is the usual default.
    - Tokens work in every browser but need plumbing into every form and fetch; origin checks need none but depend on modern browser headers.
    - XSS on your own origin defeats both, because script on your page can read tokens and send same-origin requests.
  lookalikes:
    - name: Clickjacking
      how: Frames your page under a decoy so the user really clicks your button. Stop it with CSP frame-ancestors or X-Frame-Options.
    - name: CORS
      how: Relaxes the same-origin policy for reading responses. It is not a CSRF defence, and a permissive CORS policy can make things worse.
    - name: Cross-site scripting
      how: Runs the attacker's script inside your origin, where every CSRF defence sees a same-origin request.

## [concept] Cross-site request forgery and the same-origin idea

**A browser attaches your site's cookies to requests that other sites start. So a cookie proves which browser sent a request, not that the user meant to. Accept state changes only from your own pages, and let the browser tell you which those are.**

<Term id="csrf">Cross-site request forgery</Term> needs nothing exotic: a hidden form on a page the user visits, posting to your site. The <Term id="same-origin-policy">same-origin policy</Term> stops that page reading your reply, but the request has already done its work.

<Depth level={2}>
Three tools stop it. The <Term id="samesite">SameSite</Term> attribute tells the browser not to attach the cookie to other sites' requests. The Origin header and the <Term id="fetch-metadata">fetch metadata</Term> header Sec-Fetch-Site tell the server who started the request, and pages cannot forge them. A <Term id="csrf-token">CSRF token</Term> in your own forms proves the page could read your HTML, which other origins cannot. And since every check exempts GET, state must change only on POST, PUT, PATCH or DELETE.
</Depth>

<Depth level={3}>
SameSite works on sites, not origins. An origin is scheme, host and port; a site is scheme and registrable domain (<Term id="site-vs-origin">site and origin</Term>). So a page on community.bank.example is cross-origin but same-site to bank.example, and even Strict sends the cookie. Sec-Fetch-Site distinguishes the two (same-origin versus same-site), which is why an origin check covers what SameSite cannot.
</Depth>

## [problem] A transfer endpoint that trusts the cookie

The banking app's transfer handler reads the user from the session cookie, takes the payee and amount from the form, and moves the money. It has no token and no origin check. Nobody wrote CSRF protection, and nothing has gone wrong.

It is safe today by accident. The session cookie has no SameSite attribute, and the browsers most customers use treat that as Lax, which withholds the cookie from other sites' form posts.

<Depth level={2}>
The mental model behind it: the session cookie authenticates the user, so a request carrying it is the user's request. The cookie authenticates the browser. Anything the browser can be made to send carries it.
</Depth>

<Depth level={3}>
Not every browser treats a missing SameSite as Lax, and Chrome's default has an exception: for two minutes after a cookie without the attribute is set, cross-site top-level POSTs still carry it, so that single sign-on flows keep working. The handler is relying on a browser default it never chose.
</Depth>

## [pain] Then partners embed the account widget

**Change request:** partners want to embed our account widget in their sites, so the session cookie needs SameSite=None.

The widget works. A month later customers report transfers they never made, all to the same account, all from people who had visited one coupon site. That site carries a hidden form that posts to /transfer and submits itself. With SameSite=None the browser attaches the session cookie, and the bank sees a logged-in customer asking for a transfer.

<Depth level={2}>
The attacker did not need to read anything. A form post, an image, a link or a simple fetch all go out from any page. The coupon site cannot see the bank's reply, and does not care: the money moved before the reply was written. Setting CORS headers would not have helped either, because CORS only decides which origins may read responses.
</Depth>

<Depth level={3}>
Some forged requests fail on their own. A fetch with a JSON body is not a simple request, so the browser sends a <Term id="cors-preflight">CORS preflight</Term> first, and the bank's lack of CORS headers stops the real request from being sent. Do not lean on that. The same data sent as a form body needs no preflight, and plenty of endpoints accept both.
</Depth>

## [morph] From trusting the cookie to checking the origin

Drag the slider. The cookie box gains an explicit SameSite=Lax, and an origin check sits in front of the transfer endpoint, refusing anything another origin started. The widget gets its own read-only cookie, so the session cookie no longer has to be sent everywhere.

The code sets SameSite explicitly, keeps transfers on POST, and adds the check: the framework's middleware in Go and Django, a few lines in Express and axum.

<Depth level={2}>
Splitting the cookies is the key move for the change request. A read-only widget can run on a separate cookie with SameSite=None, or on a short-lived token in a URL fragment, while the cookie that can move money stays Lax and the transfer endpoint stays behind the origin check.
</Depth>

<Depth level={3}>
Name the session cookie with the <Term id="cookie-prefix">__Host- prefix</Term>. The browser then refuses it unless it is Secure, has Path=/ and no Domain, so a compromised sibling subdomain cannot plant or overwrite it. That closes the cookie-tossing variant, where a sibling sets a session or token cookie the main site then trusts.
</Depth>

## [walk] Follow one forged transfer

The coupon site's hidden form, sent to the fixed bank, then the customer's own transfer.

<Depth level={3}>
Origin is sent on every cross-origin POST, and Sec-Fetch-Site on every request from current browsers over HTTPS. Requests with neither header come from non-browser clients, which have no victim's cookies to abuse, so the checks let them through. OWASP's cheat sheet treats Sec-Fetch-Site as the primary signal, with Origin as a required fallback.
</Depth>

## [again] The coupon site, the second time

The same coupon site, the same hidden form, against the fixed bank. The browser keeps the Lax cookie at home, so the bank sees an anonymous request and refuses it. A post from a sibling subdomain does carry the cookie and is refused by the origin check. A link to the old GET URL gets a 405. The customer's own transfer goes through.

<Depth level={2}>
Each layer covers a gap in another. SameSite fails for sibling subdomains and old browsers; the origin check fails for state changed on GET; tokens fail if they leak into URLs. Together they leave the attacker nothing to forge.
</Depth>

## [lens] How each framework stops forged requests

Django protects you by default; Go has had a one-line middleware since 1.25; Express and axum leave it to you. All of them exempt GET, HEAD and OPTIONS.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Two designs exist. Token-based protection (Django, gorilla/csrf, csrf-csrf) puts a secret in every form and checks it, and works in every browser. Header-based protection (Go's CrossOriginProtection, the Express and axum middleware above) checks Sec-Fetch-Site and Origin and needs no plumbing. Django does both.
</Depth>

<Depth level={3}>
Whatever you choose, XSS on your own origin defeats it, because injected script runs as your page: it can read the token and send same-origin requests. CSRF defences assume the other origin is the attacker. Output encoding and a Content Security Policy keep that true.
</Depth>
