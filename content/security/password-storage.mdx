## [concept] Storing passwords so a leak is survivable

**Assume the users table will leak one day. Store each password so that the leak costs the attacker years of GPU time per user, by giving every row its own random salt and hashing with a function that is slow on purpose.**

You never need the password back. At login you hash what the user typed the same way and compare. So the stored value only has to be easy to check and expensive to guess.

<Depth level={2}>
A <Term id="salt">salt</Term> is a random value unique to each row, stored next to the hash. It means equal passwords give unequal hashes, so the attacker must attack each user separately and cannot reuse a <Term id="lookup-table">precomputed lookup table</Term>. A <Term id="password-hash">password hash</Term> such as bcrypt, scrypt or Argon2id has a <Term id="work-factor">work factor</Term> that you tune until one hash takes your server a few hundred milliseconds. That same cost lands on every one of the attacker's guesses.
</Depth>

<Depth level={3}>
Argon2id is the RFC 9106 recommendation and the OWASP first choice; scrypt and bcrypt are good where Argon2id is unavailable, and PBKDF2 where FIPS compliance requires it. Argon2id and scrypt are <Term id="memory-hard">memory-hard</Term>: each guess must write and reread megabytes, so a GPU's thousands of cores wait on memory. bcrypt uses only 4 KiB but its access pattern still suits GPUs badly. PBKDF2 is only iterated HMAC, so GPUs run it at full speed and it needs hundreds of thousands of iterations to keep up.
</Depth>

## [problem] An accounts service that hashes with SHA-256

The accounts service was written years ago. It hashes each password with SHA-256 and stores the hex digest. Login hashes the typed password and compares.

It works, and it looks responsible. The column holds no passwords, only 64 hex characters per user, and a security review once ticked the box marked hashed.

<Depth level={2}>
The mental model behind it: a hash is one-way, so nobody can get the password back from it. That is true of the function and false of the system. Nobody inverts SHA-256. They guess, hash the guess, and compare, and SHA-256 was designed to make that loop fast.
</Depth>

<Depth level={3}>
The comparison with `==` is a smaller problem. It stops at the first differing byte, which in theory leaks timing. With hashes of the guess, the attacker learns little from it, but a <Term id="constant-time-comparison">constant-time comparison</Term> costs nothing, and every library verify function does it for you.
</Depth>

## [pain] Then the users table turns up on a paste site

**Change request:** a copy of the users table turned up on a paste site. Tell us how many customers must reset their passwords.

The answer is nearly all of them. With unsalted SHA-256, a lookup table built years ago cracks more than half of the 100,000 rows before the attacker turns on a GPU. One gaming GPU then tries 22 billion guesses a second against every row at once, and by the end of the day 83% of accounts are open. Users who share a password were visible from the start: their rows hold the same hash.

<Depth level={2}>
The damage spreads past your site. People reuse passwords, so every cracked pair goes into <Term id="credential-stuffing">credential stuffing</Term> lists aimed at email, banking and your competitors. You must force resets, notify users and regulators, and tell everyone to change the password wherever else they used it.
</Depth>

<Depth level={3}>
Adding a salt to SHA-256 would not have rescued this. The salt forces one job per user, which multiplies the work by 100,000, and one GPU still cracks half the table in about a quarter of an hour. The fix needs both halves: a salt, and a hash whose every evaluation is expensive.
</Depth>

## [morph] From a fast fingerprint to a slow, salted hash

Drag the slider. The users table stops holding bare fingerprints. A password hash sits between the login code and the table, adding a salt and a cost to every row, and the attacker's rate drops from billions to thousands of guesses a second.

The code swaps SHA-256 for a library password hash that makes the salt, stores the parameters in the string, and verifies in constant time.

<Depth level={2}>
Keep the old rows working while you migrate. Wrap each legacy hash in the new function now (a bcrypt or Argon2id of the old SHA-256 hex), so a leak tomorrow is already slow to attack. Then replace each row with a direct hash of the password when the user next logs in.
</Depth>

<Depth level={3}>
A <Term id="pepper">pepper</Term> adds a server-side secret, usually as an HMAC key applied before the password hash, and keeps it outside the database. A leak of the table alone is then uncrackable. The cost is operational: rotating the pepper needs every user's password again. OWASP also warns against pre-hashing for bcrypt with a raw digest, because digests can contain zero bytes, which some bcrypt implementations treat as the end of the password.
</Depth>

## [walk] Follow one sign-up and one login

One password stored, then checked, with the slow hash in place.

<Depth level={3}>
The encoded string is the PHC string format for Argon2id and scrypt (`$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`) and the modular crypt format for bcrypt (`$2b$12$` followed by 22 characters of salt and 31 of hash). Both are self-describing, which is what lets old and new settings live in one column.
</Depth>

## [again] The leak, the second time

The same paste site, the same 100,000 rows, the same GPU, stored with the slow, salted hash. After a day the attacker has the accounts whose passwords are on every top-thousand list, about one in eight to one in five. Half the users stay safe for decades. You force resets for the weakest tier and notify everyone, and the incident stays an incident.

<Depth level={2}>
The users who still fell are why storage is only one layer. Check new passwords against known-breached lists at sign-up, rate-limit and monitor logins, and offer a second factor. A slow hash buys time; it cannot make 123456 strong.
</Depth>

<Depth level={3}>
Choose the cost from your login budget. At 200 logins a second at peak and 250 ms per hash you need about 50 cores' worth of hashing. Measure on your own servers, set the highest cost you can afford, and plan to raise it every year or two.
</Depth>

## [lens] How each language hashes passwords

Every ecosystem has a library function that does the whole job: salt, cost, encoded string, constant-time verify. The differences are which algorithm is easy to reach for and where the slow work runs.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Go's `x/crypto/bcrypt` and Python's `argon2-cffi` are the easiest complete paths. Node's `argon2` package and Rust's `argon2` crate are equally complete. Go's `x/crypto/argon2` gives only the raw function, so most Go services use bcrypt or a small wrapper library.
</Depth>

<Depth level={3}>
Hashing is deliberately CPU- and memory-heavy, so keep it off threads that serve other requests. Go runs it on the request's goroutine and the scheduler copes. Node pushes it to the libuv pool of four threads. Python holds the GIL inside the C code unless the library releases it (argon2-cffi does). In Rust, wrap it in `spawn_blocking`.
</Depth>
