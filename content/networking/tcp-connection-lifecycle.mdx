  roles:
    - role: SYN
      example: client → server, seq = ISN
      job: Asks to open a connection and carries the client's starting number and options.
    - role: SYN-ACK
      example: server → client, ack = ISN + 1
      job: Accepts, and carries the server's own starting number.
    - role: FIN
      example: either side, on close()
      job: Says "I have nothing more to send". Each direction closes on its own.
    - role: RST
      example: closed port, or a crashed process
      job: Ends the connection at once. No TIME-WAIT, no FIN exchange.
    - role: Connect deadline
      example: { go: "net.Dialer{Timeout: 3 * time.Second}", python: "create_connection(addr, timeout=3)", typescript: "net.connect({ timeout: 3000 }) + destroy()", rust: "tokio::time::timeout(..., TcpStream::connect(addr))" }
      job: The application's own limit on how long the handshake may take.
  useWhen:
    - Set a connect timeout on every outbound connection, a little above the worst round trip you accept times a couple of SYN retries.
    - Set a read or idle timeout as well. A connect timeout does nothing once the connection is up.
    - Turn on keepalive with a short idle time for long-lived connections through NATs and load balancers that drop idle state.
  avoidWhen:
    - Do not set the connect timeout below a round trip or two. A single lost SYN costs a full second, and a tight timeout turns that into an error.
    - Do not treat ECONNRESET after a request as "the request did not run". The server may have done the work before it died.
  tradeoffs:
    - A short connect timeout fails fast but gives up on paths that are only slow.
    - Keepalive probes cost a few packets and can wake idle mobile radios.
    - The side that closes first holds a TIME-WAIT entry for 60 s on Linux; many short connections can use up local ports.

    - name: Read timeout
      how: Bounds how long a read waits for data on an open connection. It does not cover the handshake.

## [concept] TCP handshake and teardown

**TCP opens a connection with a <Term id="three-way-handshake">three-way handshake</Term> (SYN, SYN-ACK, ACK) and closes it with a FIN from each side. The connection is nothing but state kept in the two endpoints.**

No router on the path knows the connection exists. Each end knows only what segments it has seen, so when a segment is lost, each end believes something different until a timer or a later segment fixes it.

<Depth level={2}>
The handshake does two jobs. Each side tells the other its <Term id="initial-sequence-number">initial sequence number</Term>, and the SYNs carry options that last for the whole connection: maximum segment size, window scaling, permission to use selective acknowledgements, and timestamps. Closing is two one-way closes, because each direction of the byte stream ends on its own. A <Term id="rst-segment">RST</Term> skips all of that and ends the connection at once.
</Depth>

<Depth level={3}>
RFC 9293 names eleven states, from LISTEN and SYN-SENT through ESTABLISHED to FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, LAST-ACK and TIME-WAIT, plus CLOSED, which means "no record at all". It asks for initial sequence numbers built from a clock plus a keyed hash of the addresses and ports, so an attacker who is not on the path cannot guess them and old segments do not land inside a new connection's numbers.
</Depth>

## [problem] A database client with no deadline

The orders service opens a connection to its database for each request, runs a query and closes it. Errors become a 503. In testing the database is either up, so the handshake takes a millisecond, or down, so the host answers at once with "connection refused".

Both cases fail fast, so nobody sets a connect timeout. The defaults look fine.

<Depth level={2}>
"Refused" is fast because something answered: the database host's kernel saw a SYN for a port with no listener and sent a RST. The code has only ever met failures that come with an answer.
</Depth>

<Depth level={3}>
None of the four default APIs bounds the handshake: Go's `net.Dial`, Python's `socket.create_connection`, Node's `net.connect` and tokio's `TcpStream::connect` all wait as long as the kernel keeps trying.
</Depth>

## [pain] A firewall that never answers

**Change request:** security puts the orders database behind a firewall that silently drops anything not on its allow list.

A rule change leaves the orders service off the list. Its SYNs now vanish. Nothing comes back, not even a RST, so the kernel cannot tell a firewall from a slow network. It resends the SYN after 1, 2, 4, 8, 16 and 32 seconds, waits 64 more, and gives up: about two minutes per request. Every request piles up behind its own connect, and the service runs out of workers long before the first error appears.

<Depth level={2}>
Refused and timed out are different answers. Refused means a host replied and nothing listens. Timed out means silence: a firewall, a wrong route, a dead host, or a full SYN queue on the server.
</Depth>

<Depth level={3}>
The retry count is `net.ipv4.tcp_syn_retries`, 6 by default. With exponential backoff from a 1 s initial timeout that gives 127 s. The newest kernels add `tcp_syn_linear_timeouts`, which resends the first few SYNs at a steady 1 s before backing off, and documents a final timeout of 131 s. Either way it is minutes, not seconds.
</Depth>

## [morph] Give the handshake a deadline

<Depth level={2}>
The connect timeout should be the application's decision, because only the application knows how long its caller will wait. Pick it from the path: a few round trips plus room for one lost SYN, so 1 to 3 seconds inside a data center. Add a read deadline too; the connect timeout ends when the handshake does.
</Depth>

<Depth level={3}>
<Lang only="go">`DialContext` honours both `Dialer.Timeout` and the context's deadline, and uses whichever is sooner. When it fires, Go closes the socket, and the kernel discards the half-open connection.</Lang>
<Lang only="python">`create_connection` puts the socket in timeout mode before connecting, so `connect` itself raises `TimeoutError` at the limit. The same value then applies to every later operation on the socket.</Lang>
<Lang only="typescript">`net.connect`'s `timeout` option calls `setTimeout` before connecting. When it fires you get an event, not an error; the `destroy` call is what closes the socket and rejects the promise.</Lang>
<Lang only="rust">`tokio::time::timeout` returns `Err(Elapsed)` and drops the connect future. Dropping it closes the socket, which is why the half-open connection disappears with no extra code.</Lang>
</Depth>

## [again] The same firewall mistake, with a deadline

The rule change happens again. Each request now fails after 3 seconds with a timeout error and answers 503. Workers are freed, the error rate shows the problem within a minute, and the alert says "connect timeout", which points at the path rather than at the database.

<Depth level={2}>
Count timeouts and refusals separately. A spike of refusals means the database is down or restarting. A spike of timeouts means something between you and it is dropping packets.
</Depth>

<Depth level={3}>
<Term id="tcp-keepalive">Keepalive</Term> covers the other silent failure: a connection that was established, then went quiet because a NAT or load balancer forgot it. ### Who ends up in TIME-WAIT

The side that sends the first FIN goes through FIN-WAIT-1 and FIN-WAIT-2 and ends in <Term id="time-wait">TIME-WAIT</Term>. The other side goes through CLOSE-WAIT and LAST-ACK and is gone as soon as its FIN is acknowledged. If the last ACK is lost, the other side resends its FIN, and TIME-WAIT is what lets the closer answer it. A connection ended by a RST skips all of this.
