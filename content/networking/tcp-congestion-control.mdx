    options:
      - text: ssthresh becomes 20, the window settles at about 20 after the retransmit, and it grows by one segment per round trip from there.
        correct: true
        why: Right. Duplicate ACKs prove later segments are still getting through, so the path is congested, not dead. Halving is enough (RFC 5681 fast retransmit and fast recovery).
      - text: The window drops to one segment and slow start begins again.
        why: That is the response to a retransmission timeout, when no ACKs come back at all. Three duplicate ACKs avoid it.
      - text: The window stays at 40; TCP only resends the missing segment.
        why: Then loss would never slow anyone down, and a congested queue would stay congested. Every loss cuts the window.
  deep:
    question: Two Reno flows share a bottleneck, start at different windows, and lose packets at the same moments. Why do their shares converge?
    options:
      - text: Halving cuts the larger window by more, and additive increase grows both by the same amount, so the gap between them halves at every loss.
        correct: true
        why: Right. This is the Chiu and Jain argument for AIMD. In the A-against-B plot each loss moves the point toward the origin along a line through it, which brings it closer to the diagonal.
      - text: The router's queue gives each flow an equal number of slots.

    - role: Congestion window (cwnd)
      example: 10 segments on a new Linux connection
      job: The sender's own limit on data in flight. Grows on ACKs, shrinks on loss.
    - role: Receiver window (rwnd)
      example: advertised in every ACK
      job: The receiver's limit. The sender uses the smaller of cwnd and rwnd.
    - role: ssthresh
      example: half the flight at the last loss
      job: Where slow start hands over to congestion avoidance.
    - role: Bottleneck queue
      example: a router or switch buffer
      job: Absorbs bursts above the link rate. When it overflows, the drop is the signal.
    - role: ACK clock
      example: one ACK releases one segment
      job: Paces the sender at the rate the bottleneck delivers.
  useWhen:
    - A service makes short requests to a far-away dependency on new connections. Each one pays the handshake and slow start.
    - Throughput on a long, fast path stays far below the link rate. Check retransmits and cwnd with `ss -ti`.
    - Latency rises under load with no packet loss. A deep queue is absorbing the sawtooth.
  avoidWhen:
    - Do not set `DisableKeepAlives` or build a client per request to work around a flaky upstream. Fix idle timeouts instead.
    - Do not reach for a bigger initial window or a different algorithm before you reuse connections. Reuse removes the problem.
  tradeoffs:
    - Loss-based control fills the bottleneck queue before it backs off, so it adds queueing delay.
    - A small router buffer keeps delay low but leaves the link idle after each halving.
    - Reno shares fairly only between flows with similar round-trip times.
    - Linux resets the window after a connection sits idle longer than one RTO (`tcp_slow_start_after_idle`), so even pooled connections can start cold.
  lookalikes:
    - name: Flow control
      how: The receiver's window protects the receiver's buffer. Congestion control protects the network between them.
    - name: CUBIC and BBR
      how: Newer algorithms. CUBIC (the Linux default) grows along a cubic curve and cuts by 30% instead of 50%. BBR models bandwidth and RTT instead of waiting for loss.
    - name: Retransmission
      how: Retransmission repairs the lost data. Congestion control decides how fast to send after the loss.

## [concept] Congestion control: slow start and AIMD

**A TCP sender is never told how much the path can carry. It finds out by sending more each round trip until something drops, then cutting back and probing again.**

The limit it probes with is the <Term id="cwnd">congestion window</Term>: how much unacknowledged data it allows itself in flight. A new connection starts small, grows fast, then grows gently, and halves when it sees loss.

<Depth level={2}>
Two windows apply at once. The receiver advertises how much it can buffer; the sender keeps its own congestion window; the sender uses the smaller. The window starts at 10 segments on Linux (RFC 6928). In <Term id="slow-start">slow start</Term> every ACK adds a segment, so the window doubles each round trip. At <Term id="ssthresh">ssthresh</Term>, or at the first loss, it switches to congestion avoidance: one segment per round trip. A loss reported by three duplicate ACKs halves the window. A <Term id="rto">retransmission timeout</Term> drops it to one segment.
</Depth>

<Depth level={3}>
The rules come from Van Jacobson's 1988 fix for the congestion collapses of 1986, and are written down in RFC 5681. Growing by one and halving is <Term id="aimd">AIMD</Term>, and Chiu and Jain showed in 1989 that, of the simple linear rules, it is the one that drives competing flows toward full use and equal shares. Once the window is open, each returning ACK lets one new segment out, so the <Term id="ack-clock">ACK clock</Term> paces the sender at the bottleneck's rate. Linux's default is CUBIC (RFC 9438), which keeps slow start but replaces the linear growth with a cubic curve and cuts by 30% instead of half.
</Depth>

## [problem] A price book fetched on a fresh connection

Checkout calls the pricing service on every page and gets back a 200 KB price book. Both run in us-east, a millisecond apart. The code works, the tests pass, and p50 is 4 ms.

Read the client. Every call builds a new connection, sends one request and closes it. With a round trip of 1 ms, nobody can see the cost.

<Depth level={2}>
The mental model behind the code: transfer time is size divided by bandwidth. On a 1 Gbps network, 200 KB is 1.6 ms of wire time, plus one round trip for the answer. Keep-alive was turned off months ago to stop errors from connections the load balancer closed while idle.
</Depth>

<Depth level={3}>
At 1 ms RTT, slow start is invisible: four extra round trips cost 4 ms. TCP's costs are counted in round trips, so they stay hidden until the round trip grows.
</Depth>

## [pain] Then pricing moves to another region

**Change request:** move the pricing service from us-east to eu-west. Checkout in us-east must still get its price book in under 150 ms.

The round trip is now 80 ms, and the price book takes about 400 ms. The link still has gigabits to spare. The marked lines are why: every call starts a new connection, and every new connection starts with a 10-segment window.

<Depth level={2}>
Count round trips. One for the handshake. Then the server may send 10 segments (14.6 KB) and must wait for ACKs. The window doubles to 20, 40, 80: 150 segments after four flights, enough for 200 KB. Five round trips at 80 ms is 400 ms, against the 82 ms the bandwidth model predicts. Bigger machines and faster links change nothing here.
</Depth>

<Depth level={3}>
The window that matters belongs to the sender of the 200 KB: the pricing server's kernel. The client controls it only through the connection: a new connection gets a new window. Linux starts at 10 segments for every connection, even to a host it just talked to, unless the route has an `initcwnd` set.
</Depth>

## [morph] From a pipe to a window that has to grow

Drag the slider. The fat pipe turns into what actually limits the transfer: a sender whose window starts small, a bottleneck it cannot see, and ACKs that let the window grow.

The code moves from one client per call to one pooled client for the whole process. A reused connection keeps the window it already grew.

<Depth level={2}>
Reuse fixes the cold start; it does not change congestion control. A warm connection still halves on loss and still shares the bottleneck with everyone else. What changes is that the four round trips of slow start are paid once per connection instead of once per request.
</Depth>

<Depth level={3}>
Linux keeps a warm window only while the connection is busy. With `net.ipv4.tcp_slow_start_after_idle = 1`, the default, a connection idle for longer than one RTO has its window cut back to the initial window (RFC 2861 behaviour). For bursty traffic, set it to 0 on the sending side or keep connections busy. Senders can also pace: Linux's `fq` qdisc spreads a window over the round trip instead of sending it in one burst.
</Depth>

## [walk] Follow one price book

One request on a cold connection, then the loss that eventually comes, then the next request on the warm connection.

<Depth level={3}>
After a loss Linux does not wait for a full recovery to halve; with SACK it repairs several holes in one recovery, and RACK-TLP (RFC 8985) detects losses by time instead of only by counting duplicate ACKs. The shape stays the same: a cut on loss, then growth.
</Depth>

## [again] The same request, warm

The same 200 KB from eu-west on a pooled connection. The window is already large, so the request goes out and the whole response comes back in one round trip: about 82 ms instead of 400.

<Depth level={2}>
The first request on each new pool connection still pays slow start. A warm-up call at startup moves that cost out of a customer's request. Check the pool's idle timeout against the server's keep-alive timeout, so the client never reuses a connection the server has already closed. Those are the errors that got keep-alive disabled in the first place.
</Depth>

<Depth level={3}>
For responses that must be fast on cold connections, the knobs are on the server: a larger initial window per route (`ip route change ... initcwnd 20`), or HTTP/2 and HTTP/3, which put all requests to a host on one connection so it stays warm.
</Depth>

### Read the window on a live connection

`ss -ti dst <host>` prints each connection's `cwnd`, `ssthresh`, `rtt` and retransmit counts. Run it on the sending side while a transfer runs. A `cwnd` stuck at 10 on every connection means you are paying slow start on each request; a high `retrans` with a small `cwnd` means real loss on the path.
