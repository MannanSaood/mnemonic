      - text: Garbage collection pauses in the server.

  deep:
    question: Without timestamps, why does TCP not take a round-trip sample from the ACK of a segment it sent twice?
    options:
      - text: The ACK may answer either copy, so the sample could be far too long or far too short.
        correct: true
        why: Right. That is Karn's algorithm. TCP also keeps the backed-off RTO until a segment sent only once is acknowledged. With the timestamp option, the echoed timestamp says which copy was answered.
      - text: A resent segment takes a different route, so its round trip is not typical.
        why: TCP does not choose routes, and a resend usually follows the same path. The problem is ambiguity, not the path.
      - text: The ACK of a resent segment is always a duplicate ACK and carries no timing.
        why: It is usually a new cumulative ACK, often a large jump. It is ignored for timing because the sender cannot tell which transmission it answers.

    - Set request timeouts above the kernel's minimum RTO plus the work, or every lost segment becomes an application retry.

## [concept] TCP timeouts and retransmission

**TCP resends data it believes was lost. It decides by waiting a <Term id="rto">retransmission timeout</Term> learned from measured round trips, or sooner, when <Term id="duplicate-ack">duplicate ACKs</Term> show that later data arrived and one segment did not.**

The timer is the fallback. It is never shorter than a floor, 200 ms on Linux, and it doubles every time it fires for the same data. Duplicate ACKs are the fast path, and they need segments after the loss to exist.

<Depth level={2}>
RFC 6298 keeps two numbers per connection. <Term id="srtt">SRTT</Term> is a running average of round-trip samples; <Term id="rttvar">RTTVAR</Term> is a running average of how far each sample is from it. The timeout is SRTT plus four times RTTVAR, so a steady path gets a timeout close to its round trip and a jittery one gets a wide margin. Then the floor applies: the RFC says 1 second, Linux uses 200 ms.
</Depth>

<Depth level={3}>
The update order matters: RTTVAR first, using the old SRTT (RTTVAR = ¾ RTTVAR + ¼ |SRTT − R|), then SRTT = ⅞ SRTT + ⅛ R. Before any sample the RTO is 1 second. Each timeout doubles it (RFC 6298 rule 5.5), and <Term id="karn-algorithm">Karn's algorithm</Term> keeps it doubled, because the ACK of data sent twice gives no usable sample.
</Depth>

## [problem] A client that retries after 50 ms

A checkout service asks the pricing service for each item's price. Both run in the same rack, the round trip is about 1 ms and responses take a few milliseconds. The client gives each attempt 50 ms and tries three times.

On a clean network that is generous. In months of testing, no attempt ever timed out.

<Depth level={2}>
The reasoning behind 50 ms: if a packet is lost, TCP resends it, and that should cost about one more round trip. Fifty round trips of slack feels like plenty.
</Depth>

<Depth level={3}>
The reasoning is right for one kind of loss and wrong for the other. A loss followed by more data is found by duplicate ACKs within a round trip. A loss with nothing after it waits for the timer, and the timer cannot go below its floor however short the path.
</Depth>

## [pain] One segment in a thousand

**Change request:** pricing moves to a shared cluster where, at busy times, about one segment in a thousand is dropped.

Most responses are one or two segments. When the last one is lost, no later segment produces a duplicate ACK, so the server's TCP waits its RTO, at least 200 ms. The client's 50 ms timer fires first. It abandons the connection, sends the request again on a new one, and the server does the work twice. A network that lost 0.1% of its packets now shows up as errors and duplicate load.

<Depth level={2}>
On the host, `ss -ti` shows the evidence: `rto:204` on connections whose `rtt` is about 1 ms, and a growing `retrans` count. The latency histogram has a step just above 200 ms.
</Depth>

<Depth level={3}>
Modern Linux softens this with a tail loss probe (RFC 8985): about two smoothed round trips after the last segment, it resends that segment to provoke an ACK, which often turns the tail loss into a fast recovery. When the probe is lost too, when a resend is lost, or on stacks without probes, the RTO and its floor decide. Client timeouts have to survive that case.
</Depth>

<Term id="sack">SACK</Term> (RFC 2018) lets the receiver list the blocks it holds beyond the cumulative ACK. With several losses in one window, the sender can resend every hole in one round trip; without it, each partial ACK reveals only the next hole.

## [again] The same drop rate, with a budget above one RTO

The cluster drops one segment in a thousand again. A lost tail segment now adds about 200 ms to one attempt, inside its 300 ms limit. The server does the work once, the client sees a slow response instead of an error, and the retry counter stays flat unless a server really fails.

<Depth level={2}>
Count retries per attempt outcome. A rise in attempt timeouts with flat server latency points at the network; a rise in server latency points at the server.
</Depth>

<Depth level={3}>
If 200 ms tails are not acceptable, the fix is in the transport, not in the client's timer: fewer losses, a smaller minimum RTO on paths that stay inside the data center (`ip route ... rto_min`), or hedged requests that send a second copy to another replica after the 99th-percentile latency.
</Depth>

## [lens] How each language bounds a slow response

TCP's retransmissions are invisible to every language: they happen in the kernel and show up only as delay. What each language gives you is a way to bound an attempt, a way to bound the call, and sometimes a way to read the kernel's numbers.

### Reading `ss -ti`

`ss -ti` prints each connection's `rtt:` as SRTT/RTTVAR in milliseconds, its current `rto:`, and `retrans:` as current/total retransmissions. An `rto` far above the `rtt` on a short path is the floor at work. A `backoff:` field appears while the timer is backed off after repeated timeouts.
