## [concept] The TLS handshake

**TLS first agrees on fresh keys with whoever answered, then proves that whoever answered holds the private key of a certificate for the name you asked for. Encryption without the second part protects you from nobody in the middle.**

The handshake does both in one round trip in TLS 1.3, two in TLS 1.2. After it, every byte is encrypted and authenticated.

<Depth level={2}>
The client's first message, ClientHello, carries the versions and ciphers it supports, a key share for <Term id="ecdhe">ECDHE</Term>, the host name in <Term id="sni">SNI</Term> and the application protocols in <Term id="alpn">ALPN</Term>. The server replies with its key share; both sides derive the same secret. Then the server sends its <Term id="certificate-chain">certificate chain</Term> and a <Term id="certificate-verify">CertificateVerify</Term>, a signature over the handshake so far. The client checks the chain against its trust store, the dates, the name, and the signature. Any failure ends the handshake with an alert.
</Depth>

<Depth level={3}>
TLS 1.3 (RFC 8446, 2018) removed RSA key transport, so every full handshake uses an ephemeral key exchange and has <Term id="forward-secrecy">forward secrecy</Term>. It encrypts everything after ServerHello, including the certificate, and every handshake message feeds a running transcript hash. Finished is a MAC over that transcript, so a tampered or downgraded handshake fails. TLS 1.2 (RFC 5246) sent the certificate in plain text and still allowed key exchanges without forward secrecy.
</Depth>

## [problem] A payouts client with verification switched off

The payouts service sends money instructions to a partner API over HTTPS. Staging uses a self-signed certificate, so someone turned verification off to make staging work. The same client runs in production.

It works. The traffic is HTTPS, a packet capture shows only ciphertext, and nothing has gone wrong in a year.

<Depth level={2}>
The mental model behind it: TLS is encryption, and the certificate is a formality that sometimes gets in the way. If the bytes on the wire are unreadable, the connection is safe.
</Depth>

<Depth level={3}>
Every language makes this one flag away: `InsecureSkipVerify`, `verify=False`, `rejectUnauthorized: false`, `danger_accept_invalid_certs`. Each one skips the chain, date and name checks and leaves the key exchange running, so the connection still looks encrypted.
</Depth>

## [pain] Then the egress proxy arrives

**Change request:** all outbound traffic now goes through the new corporate egress proxy, which inspects TLS.

Payouts keep working. Two weeks later security finds the partner's API key in the proxy's request logs, which are shipped to a third-party log service. The marked lines are why. The proxy answers every handshake with a certificate from its own CA, decrypts, logs, and re-encrypts to the partner. A verifying client would have refused it. This one cannot tell the proxy from the partner.

<Depth level={2}>
Every service that verifies broke loudly on day one with an unknown-authority error, and the platform team added the partner host to the proxy's no-inspection list for those. The payouts service never broke, so nobody looked. The key must be rotated, and every payout made in those two weeks was readable on the path.
</Depth>

<Depth level={3}>
The proxy did nothing exotic. It ran a normal TLS 1.3 handshake with the client using its own key, and a second one with the partner. Both connections were encrypted end to end. The only thing that could have exposed it was the certificate check that had been switched off.
</Depth>

## [morph] From an encrypted pipe to an authenticated one

Drag the slider. The single HTTPS box splits into the handshake, the verifier that can abort it, and the proxy that now has to present a certificate the client trusts.

The code turns verification back on and trusts staging's CA explicitly instead.

<Depth level={2}>
Trusting a private CA is a configuration value, not a code path: staging passes its CA bundle, production passes nothing. Verification stays on everywhere, so the staging setup also tests the production code path.
</Depth>

<Depth level={3}>
Most libraries verify the CertificateVerify signature even with verification off. That does not help, because an attacker who brings its own certificate also brings the matching key. Only the chain and name checks tie the key to the partner.
</Depth>

## [walk] Follow one handshake

One new connection through the proxy, traced through TLS 1.3, first while the proxy inspects TLS, then after it tunnels the partner's traffic.

<Depth level={3}>
After the handshake the server usually sends a NewSessionTicket. Next time the client can resume with that ticket: no certificate is sent or checked, because the ticket proves the earlier handshake. With 0-RTT the request can ride in the first flight, but early data can be replayed by an attacker, so servers should accept it only for idempotent requests.
</Depth>

## [again] The proxy, the second time

The same proxy, the same partner, with the fixed client. On day one the handshake fails with an unknown-authority error, the platform team adds the partner to the no-inspection list, and from then on the proxy only tunnels bytes it cannot read. The API key never reaches a log.

<Depth level={2}>
The loud failure is the feature. An error on day one costs an hour; silent interception cost a key rotation and an incident review.
</Depth>

<Depth level={3}>
A related failure looks the same from the outside: a server that sends its leaf but not its intermediate. Browsers often fill the gap from a cache or by fetching the issuer from the address in the certificate; OpenSSL, Go on Linux, Node and rustls do not. The fix is on the server: send the full chain. `openssl s_client -connect host:443 -servername host -showcerts` shows exactly what it sends.
</Depth>

## [lens] How each language configures TLS

Every mainstream client verifies by default. The differences are in where the roots come from, how you add a private CA, and how loud the off switch is.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Go and Rust with rustls use their own TLS implementations; Python and Node use OpenSSL; `native-tls` uses the platform's library. That is why the same broken chain produces different messages, and why a missing intermediate can work on a Mac and fail on Linux.

### Inspect a real handshake

`curl -v https://api.example.com` prints the TLS version, cipher, ALPN result and the certificate's subject, issuer and dates. `openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts` prints the whole chain the server sends, which is the quickest way to spot a missing intermediate.
