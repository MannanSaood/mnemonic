  overview:
    question: A sender puts a number on every message. What do the numbers let the receiver do?
    options:
      - text: Spot a copy it has already seen, and notice a gap where a message is missing.
        correct: true
        why: Right. Without numbers a resent message looks new, and a missing one leaves no trace.
      - text: Tell the sender how fast it may send.
        why: That is flow control, which uses a window the receiver advertises. Numbers identify messages; they do not set a rate.
      - text: Prove that the receiving application processed the message.
        why: No. An ACK for a number proves the receiving protocol has the data. The application may still crash before it acts on it.
  engineer:
    question: Sending a message takes 1 ms and the round trip is 80 ms. A stop-and-wait sender manages about 12 messages a second. Which change raises throughput most and stays reliable?
    options:
      - text: Allow many unacknowledged messages in flight, each with its number and timer.
        correct: true
        why: Right. With a window of 64 the sender keeps sending while ACKs are on their way, about 800 messages a second, and loss handling still works per message.
      - text: Cut the retransmit timer to 10 ms.
        why: The timer only matters when something is lost. Below the round trip it fires before any ACK can arrive, so every message is sent twice and nothing gets faster.
      - text: Stop waiting for ACKs and send every message twice.
        why: Two copies can both be lost, and the receiver now gets duplicates on every good day. This is neither reliable nor cheaper.
  deep:
    question: Selective repeat with sequence numbers 0 to 3 (they wrap) and a window of 3. Packets 0, 1 and 2 arrive, and all three ACKs are lost. What goes wrong?
    options:
      - text: The sender resends 0, and the receiver, now expecting 3, 0 and 1, takes the old 0 for a new message.
        correct: true
        why: Right. The receiver's window has moved on to numbers that overlap the old ones. Selective repeat needs a window of at most half the number space; TCP avoids the problem with 32-bit numbers and timestamps.
      - text: Nothing. Selective repeat ACKs each packet, so the sender learns what arrived.
        why: Those ACKs were lost. The sender times out and resends 0, which the receiver cannot tell apart from the next 0.
      - text: The receiver stops, because its buffer is full.
        why: Its buffer is empty; it delivered 0, 1 and 2. The trouble is that the numbers it now expects include a number the sender is reusing for old data.

  useWhen:
    - You must deliver over a datagram transport (UDP, a radio link, a message bus) and losing or duplicating a message has a cost.
    - You design retries for an RPC or a queue consumer. The same three parts apply: an id, an acknowledgement, a timer.
    - The path is long. Then a window, not a faster timer, is what raises throughput.
  avoidWhen:
    - TCP or QUIC already carries the data. They do all of this with decades of tuning; add an application-level ACK only when you need proof that the work was done.
    - The data is replaced by fresher data every few milliseconds, as with game state or live metrics. Resending stale data wastes the link.
  tradeoffs:
    - A window needs memory for every unacknowledged message at the sender, and selective repeat needs a buffer at the receiver too.
    - Go-back-N keeps the receiver trivial but resends whole tails on every loss.
    - A short timer resends sooner but fires needlessly when the network is merely slow.
    - The receiver must remember which numbers it has seen for as long as copies can still arrive.

## [concept] Building reliability on a lossy link

**A link that loses, delays and copies packets becomes reliable with three parts: a <Term id="sequence-number">sequence number</Term> on every packet, an <Term id="acknowledgement">acknowledgement</Term> for what arrived, and a timer that resends what was not acknowledged.**

That makes delivery correct. Speed is a separate problem. If the sender waits for each ACK before sending the next packet, the link sits idle for a full round trip every time. Keeping a window of packets in flight fixes that.

<Depth level={2}>
Two windowed designs differ in what the receiver does with a packet that arrives after a gap. In <Term id="go-back-n">go-back-N</Term>, it throws the packet away and keeps asking for the missing one, so the sender resends everything from the gap onward. In <Term id="selective-repeat">selective repeat</Term>, it holds the packet and acknowledges it, so the sender resends only what was lost. TCP sits between the two.
</Depth>

<Depth level={3}>
Kurose and Ross build the design one failure at a time: bit errors need checksums and ACKs, lost packets need a timer, a lost ACK makes the resend a duplicate and so needs numbers, and pipelining needs a window. With numbers that wrap, selective repeat also needs a window no larger than half the number space, or an old packet can look like a new one with the same number.
</Depth>

## [problem] A shipper that waits for each ok

A metering service sends one UDP datagram per usage event to the billing collector. The collector records it and replies `ok`. If no `ok` comes back within 500 ms, the shipper sends the event again, up to three times.

In the test environment the collector is in the same rack. The round trip is a fraction of a millisecond and nothing is ever lost, so it ships thousands of events a second and every count matches.

<Depth level={2}>
The design is <Term id="stop-and-wait">stop-and-wait</Term>: one event on the wire, then silence until the answer. It is reliable as long as answers are never lost. Its throughput is one event per round trip, whatever the link's bandwidth.
</Depth>

<Depth level={3}>
The `ok` carries no information about which event it acknowledges. That is safe only while there is exactly one event outstanding and no `ok` is ever delayed past the timeout.
</Depth>

## [pain] The collector moves 80 ms away

**Change request:** the billing collector moves to another region, 80 ms away, and finance wants every usage event counted exactly once.

Two things break at once. Each event now costs a full 80 ms round trip, so the shipper tops out at about 12 events a second and falls behind. And when an `ok` is lost, the shipper cannot tell that from a lost event. It resends, and the collector bills the same usage twice.

<Depth level={2}>
Raising the timeout does not help with either. Throughput is set by the round trip, and a duplicate appears whenever the reply is lost, however long you wait for it.
</Depth>

<Depth level={3}>
At 80 ms and 1 ms per send, the link is busy 1 ms in every 81: about 1% utilisation. Filling it needs about 80 events in flight, the link's <Term id="bdp">bandwidth-delay product</Term> measured in events.
</Depth>

## [morph] From one event in flight to a numbered window

Drag the slider. The single wait becomes a window of numbered events, each with its own send time. The collector gains a set of sequence numbers it has already billed.

Hover a box to see its code.

<Depth level={2}>
The sender no longer asks "did my event arrive?" It asks "which numbers are still unacknowledged, and for how long?" That question has an answer even when ACKs are lost, late or out of order.
</Depth>

<Depth level={3}>
This version is selective repeat: one timer per event and an ACK per number. A <Term id="cumulative-ack">cumulative ACK</Term> ("everything up to 41 arrived") would let one ACK cover for a lost earlier one, at the cost of resending more when data is lost. TCP uses cumulative ACKs and adds selective acknowledgements on top.
</Depth>

## [walk] Follow one event

One event, from the shipper's call to the collector's bill. Step through it with the numbered buttons.

<Depth level={3}>
The collector's set of seen numbers grows forever in this sketch. A real receiver keeps a low-water mark: every number below the oldest unacknowledged one has been seen, so it only needs to remember the numbers above it. That is exactly a receive window.
</Depth>

## [again] The same 80 ms, with a window

The collector is still 80 ms away. With 64 events in flight the shipper sends about 800 a second, and a lost ACK costs one resend that the collector recognises and does not bill. That is an <Term id="exactly-once-effect">exactly-once effect</Term> built from at-least-once delivery.

<Depth level={2}>
Pick the window from the path, not by guessing: round trip times the rate you need. Too small and the link idles; much too large and a burst of loss means many resends and a large buffer.
</Depth>

<Depth level={3}>
TCP does all of this for every connection, with a window set by the receiver and by congestion control. The lesson is still useful above TCP: an RPC retry or a queue redelivery is the same <Term id="retransmission">retransmission</Term> problem one layer up, and it needs the same answer, an id the receiver checks.
</Depth>

### The numbers behind the playground

Each packet takes 2 ms to send and 10 ms to cross, so a round trip is 22 ms. Stop-and-wait keeps the link busy 2 ms in every 22, about 9%. A window of W packets keeps it busy W times as long, until W × 2 ms reaches the round trip; at that point the link is full and a bigger window only adds queueing.
