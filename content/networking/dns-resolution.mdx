    question: api.example.com has a TTL of 3600 s and must move to a new address tomorrow with as little stale traffic as possible. What do you do first?
    options:
      - text: Lower the TTL to 60 s today, wait at least an hour, then change the address.
        correct: true
        why: Right. Copies cached before today still carry 3600 s. Once they have expired, every cache holds the record for 60 s at most, so the move reaches everyone within a minute.
      - text: Change the address and the TTL to 60 s at the same moment.
        why: Resolvers that cached the old record under TTL 3600 keep it for up to an hour. The new TTL only applies to copies fetched after the change.
      - text: Change the address, then flush your own resolver's cache.
        why: That fixes your resolver only. Every other resolver on the internet still holds the old answer until its TTL runs out.
  deep:
    question: The .com servers refer resolvers to ns1.example.com for example.com. Why do they also send ns1.example.com's address, a glue record?
    options:
      - text: Without it, the resolver would need example.com's servers to find the address of example.com's servers.
        correct: true
        why: Right. The name server's name sits inside the zone it serves, so the parent zone hands out its address along with the referral to break the loop.
      - text: Glue records sign the referral so it cannot be forged.
        why: Signing is DNSSEC's job, with RRSIG and DS records. Glue is plain, unsigned address data.
      - text: Glue records let the TLD answer the A query for any name in example.com.
        why: The TLD only knows the delegation and the name servers' addresses. Names inside example.com are answered by example.com's servers.

      example: "ns1.example.com"

  useWhen:
    - A long-running client resolves a name once at startup and keeps the address. It will miss every later change.
    - The first request after a deploy or a quiet period is slow. A cold lookup costs several round trips to far-away servers.

  avoidWhen:

## [concept] DNS: from name to address

**A name is resolved by walking down a tree of servers: the root, then the top-level domain, then the domain's own servers. Every answer along the way comes with a TTL, and is cached for exactly that long.**

You never do the walk yourself. Your program asks a resolver, and the resolver does the walking and keeps what it learns.

<Depth level={2}>
Three roles share the work. The <Term id="stub-resolver">stub resolver</Term> in your process sends one query and waits. The <Term id="recursive-resolver">recursive resolver</Term>, run by your data center, cloud or ISP, follows <Term id="dns-referral">referrals</Term>: the root names the .com servers, the .com servers name example.com's servers, and an <Term id="authoritative-server">authoritative server</Term> finally answers. Each record carries a <Term id="time-to-live">TTL</Term>, and every cache that holds the record may reuse it until the TTL runs out. Common record types: A (IPv4), AAAA (IPv6), <Term id="cname">CNAME</Term> (an alias), MX, TXT, NS and SRV.
</Depth>

<Depth level={3}>
DNS is defined in RFC 1034 (concepts) and RFC 1035 (the wire format). Queries normally go over UDP port 53, and an answer too big for the UDP buffer comes back with the TC bit set, so the resolver repeats the question over TCP. There are 13 root server identities, a to m, each run on many anycast instances. When a zone's name server lives inside the zone (ns1.example.com for example.com), the parent hands out its address with the referral: a <Term id="glue-record">glue record</Term>.
</Depth>

## [problem] A metrics client that looks up its relay once

Every service sends counters over UDP to a metrics relay at metrics.example.com. The client resolves the name when the service starts, then sends to that address for as long as the process lives.

It works. Lookups never show up in a profile, and the relay has had the same address for a year.

<Depth level={2}>
The mental model behind it: a name is an address with a nicer spelling. Look it up once and you know it. Resolving on every send looks wasteful, so the code does it at startup.
</Depth>

<Depth level={3}>
UDP makes the bug quiet. A send to an address where nobody listens usually succeeds locally; the datagram is simply lost. Nothing in the service logs an error.
</Depth>

## [pain] Then the relay moves

**Change request:** the platform team replaces the metrics relay. The new VM has a new address, and they update metrics.example.com with a TTL of 60 s.

Within two minutes the old VM is gone. Dashboards for most services go flat and stay flat. The few services that were redeployed that afternoon keep reporting. The marked lines are why: the address was fixed at startup.

<Depth level={2}>
The DNS change worked. Every resolver handed out the new address within 60 s. The services simply never asked again. The cost is every metric from every long-running process until each one restarts, which for a stable service can be weeks.
</Depth>

<Depth level={3}>
Clients written this way exist in every ecosystem: StatsD and syslog senders, database drivers that pin a primary's address, connection pools that never close connections. Some runtimes add a cache of their own; the JVM's address cache, for example, can keep successful lookups forever when a security manager is installed. An address from DNS is a lease, valid for the TTL.
</Depth>

## [morph] From one fixed answer to a lease

Drag the slider. The single box labelled DNS opens up into the real chain: a recursive resolver with a cache, and three levels of servers it asks in turn.

The code changes to ask again every 30 seconds. Most of those lookups are cache hits at the resolver, so they cost about a millisecond.

<Depth level={2}>
Asking again is cheap because of the resolver's cache, and it is safe because the client keeps the last good address if a lookup fails. The refresh period adds to the TTL: with TTL 60 and a 30 s refresh, a change reaches the client within 90 s.
</Depth>

<Depth level={3}>
Connection-oriented clients need one more thing. A TCP connection opened to the old address stays on the old address however often you resolve, so pools need a maximum connection lifetime too. HTTP clients usually get this for free when the old server closes its connections.
</Depth>

## [walk] Follow one lookup

One refresh, starting from a cold resolver cache, traced through every server it reaches.

<Depth level={3}>
Real resolvers add a few details. They pick among a zone's name servers by measured response time, and they send only as much of the name as each level needs (QNAME minimisation, RFC 9156), so the root sees "com" rather than the full name. They also cache negative answers, so a name that does not exist is not asked about again until the zone's SOA says it may be.
</Depth>

## [again] The relay moves again

The platform team moves the relay a second time. Each service picks up the new address at its next refresh after the resolver's copy expires: within 90 seconds, with no restarts.

<Depth level={2}>
For planned moves the TTL is the lever. Lower it a day ahead, wait out the old TTL, move, then raise it again. The playground lets you try the move both ways.
</Depth>

<Depth level={3}>
If the refresh fails because DNS itself is down, the client keeps sending to the last address it had. That is the right default for a metrics client. For a client where a wrong address is worse than none, fail closed instead.
</Depth>

## [lens] How each language resolves names

Each runtime has its own stub. Some call the C library's `getaddrinfo` on a thread, some speak DNS themselves, and almost none cache answers in the process.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
The difference shows up in failures. A stub that calls `getaddrinfo` follows `/etc/nsswitch.conf`, `/etc/hosts` and the C library's timeouts (5 s per try, 2 tries by default in glibc). A stub that speaks DNS itself reads `/etc/resolv.conf` on its own and may treat those settings slightly differently.
</Depth>
