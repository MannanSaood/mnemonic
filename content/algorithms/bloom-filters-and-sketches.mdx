## [concept] Bloom filters and sketches

**A Bloom filter hashes each item to k bits in a bit array and sets them. A query checks the same k bits: any 0 means "definitely never added", all 1s means "maybe". It never stores the items, so it takes a few bits per item.**

A <Term id="bloom-filter">Bloom filter</Term> is an answer to a question that comes up whenever a lookup is expensive: can I skip it? Put the filter in memory in front of the slow store. A "no" is always right, so it skips the store outright. A "maybe" goes to the store, and is wrong at a <Term id="false-positive-rate">false-positive rate</Term> that you choose when you size the filter.

<Depth level={2}>
Sizing has two knobs: bits per item (m/n) and the number of hash functions k. The rate is about (1 − e^(−kn/m))^k, the chance that all k bits of a new item were already set by others. For a target rate p, the best k is (m/n)·ln 2 and you need about 1.44·log₂(1/p) bits per item: 9.6 bits and 7 hashes for 1%, 14.4 bits and 10 hashes for 0.1%. The size depends on the rate, not on the size of the items.

The same trade, a little error for a lot less memory, gives two more sketches. A <Term id="count-min-sketch">count-min sketch</Term> estimates how often each item occurred, and a <Term id="hyperloglog">HyperLogLog</Term> estimates how many distinct items there were.
</Depth>

<Depth level={3}>
The formula comes from treating the bits as independent. After n items with k hashes each, a given bit is still 0 with probability (1 − 1/m)^(kn) ≈ e^(−kn/m). A new item is a false positive when all k of its bits are 1, which gives (1 − e^(−kn/m))^k. Minimising over k gives k = (m/n)·ln 2, the point where about half the bits are set, and a rate of about 0.6185^(m/n). Kirsch and Mitzenmacher showed in 2006 that two hash functions combined as h1 + i·h2 give the same asymptotic rate as k independent ones, which is what most libraries do.
</Depth>

## [problem] A crawler that remembers every URL

A web crawler parses each page it fetches and offers the links to a frontier. The frontier keeps a set of every URL it has ever queued, so no page is fetched twice. It is the obvious design, and it is exact.

For a site list of a few million pages, the set is a few hundred megabytes and lookups are a hash and a slot read.

<Depth level={2}>
A set of strings costs the strings. A typical URL is 60 to 80 characters, and each entry adds an object header and a hash table slot, so about 100 bytes per URL is a fair estimate in any of the four languages. Memory grows linearly with everything the crawler has ever seen, and it never shrinks.
</Depth>

<Depth level={3}>
The exact set also has to survive restarts and be shared between crawler processes, so in practice it ends up in a database anyway. The in-memory set is a cache of that database, and the question is how small that cache can be.
</Depth>

## [pain] Then a change request arrives

**Change request:** follow every link on every crawled page, not just sitemaps. That is about 2 billion URLs this quarter.

The marked lines offer every link on every page. At 100 bytes per URL the set needs about 200 GB, which no crawler box has. Moving the set to the crawl database makes every link a network round trip: 40 links per page times thousands of pages a second is more lookups than the database can serve. Sharding the set by host spreads the memory but not the total.

<Depth level={2}>
Most of those lookups are for URLs that are new, and the database spends its time saying "never seen it". A structure that can answer "never seen it" locally, without storing the URLs, removes those round trips.
</Depth>

<Depth level={3}>
In TypeScript the set fails before memory does: V8 caps a `Set` at 2^24 entries, about 16.7 million, and throws a RangeError on the next add.
</Depth>

## [morph] Keep bits, not URLs

Drag the slider. The set of strings becomes k hash functions over a bit array, and the database moves behind it.

A link whose bits include a 0 is new for certain, so the frontier skips the database, sets the bits and queues the page. A link whose bits are all 1 is probably a page already queued, and the database confirms it. At 1% false positives, 99 of every 100 new URLs never touch the database, and the filter for 2 billion URLs takes 2.4 GB.

<Depth level={2}>
Size the filter for the most items you expect, not the current count. Past its planned capacity the rate climbs quickly: at twice the planned items a 1% filter is near 16%. Long-running crawlers rotate filters: start a new one when the current one is full and check both, or rebuild from the database during a quiet hour.
</Depth>

<Depth level={3}>
Many crawlers drop the database check and treat "maybe" as "seen". Then a false positive means a page is never crawled, 1% of new URLs, and no database is needed on the hot path at all. Whether that is acceptable is a product decision, and the filter makes the trade explicit: the rate is a number you chose.
</Depth>

## [walk] Follow one link

One new URL, then one already crawled. Use the numbered buttons.

<Depth level={2}>
Never delete by clearing bits. Other items share them, so clearing one item's bits turns some of the others into false negatives, the one error the filter promised never to make. If you need deletes, a <Term id="counting-bloom-filter">counting Bloom filter</Term> keeps a small counter per position, or a cuckoo filter stores short fingerprints that can be removed.
</Depth>

<Depth level={3}>
The same structure sits inside storage engines. RocksDB, LevelDB and Cassandra keep a Bloom filter per sorted file, so a read for a key skips every file whose filter says no and usually touches one file on disk. RocksDB's classic setting of 10 bits per key gives about 1%. PostgreSQL's `bloom` extension builds an index from per-row signatures in the same way.
</Depth>

## [again] The same request, with a filter in front

Two billion URLs now cost 2.4 GB of bits plus the database, which sees one lookup for each already-seen link and for about 1% of the new ones. The test pins the sizing: a filter built for its item count stays near the rate it was built for.

<Depth level={2}>
Counting is the next question a crawler gets: how many times was each URL linked, and how many distinct hosts did we see today? A count-min sketch answers the first with d rows of w counters. Each item increments one counter per row; its estimate is the smallest of those counters. Collisions only add, so the estimate is never too low. HyperLogLog answers the second: Redis's `PFADD` and `PFCOUNT` use 12 KB per key for any number of items, with a standard error of 0.81%.
</Depth>

<Depth level={3}>
HyperLogLog hashes each item and looks at the run of leading zero bits. Seeing a hash that starts with 20 zeros suggests about 2^20 distinct items. One such observation is very noisy, so the hash's first bits pick one of many registers, each register keeps the longest run it has seen, and a harmonic mean of the registers gives the estimate. Two sketches merge by taking the maximum per register, which is why distinct counts can be combined across servers and days.
</Depth>

## [play] Tune a filter in front of the crawl database

Crawl pages and watch each link's bits. Every "no" skips the database; every "maybe" costs a lookup. Change the bits and the hash count and compare the measured rate with the formula. Then try to delete a URL.

## [lens] Filters in each language

None of the four standard libraries has a Bloom filter, and each ecosystem has one well-known package. The structure is small enough to write yourself: a bit vector and two hashes.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
A filter built in one process is only useful to another if both use the same m, k and hash functions with the same seeds. If you persist or share a filter, fix the hash and its seed explicitly, and store them with the bits.
</Depth>

<Depth level={3}>
Several crawler processes can share one filter in Redis with the RedisBloom commands `BF.RESERVE`, `BF.ADD` and `BF.EXISTS`, or merge their local filters periodically by OR-ing bit arrays of the same shape.
</Depth>
