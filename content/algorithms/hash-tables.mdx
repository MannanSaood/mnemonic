        type RenderCache struct {
            mu       sync.RWMutex
            byTenant map[string][]Entry // tenant -> its pages
        }

        func (c *RenderCache) Get(tenant, path string) ([]byte, bool) {
            c.mu.RLock()
            defer c.mu.RUnlock()
            for _, e := range c.byTenant[tenant] { // the map finds the tenant; the path is a scan
                if e.Path == path {
                    return e.HTML, true
                }
            }
            return nil, false
        }

            c.mu.Lock()
            defer c.mu.Unlock()
            pages := c.byTenant[tenant]
            for i := range pages {
                if pages[i].Path == e.Path {
                    pages[i] = e
                    return
                }
            }
            c.byTenant[tenant] = append(pages, e)
        }

        func (c *RenderCache) Purge(tenant string) {
            c.mu.Lock()
            defer c.mu.Unlock()
            delete(c.byTenant, tenant)
        }

            mu      sync.RWMutex
            pages   map[pageKey][]byte
            tenants map[string]map[pageKey]struct{} // for Purge

        func NewRenderCache(expected int) *RenderCache {
            return &RenderCache{

                tenants: make(map[string]map[pageKey]struct{}),

        }

            c.mu.RLock()
            defer c.mu.RUnlock()

checks:
  overview:
    question: A map lookup is described as O(1). What does that depend on?
    options:
      - text: A hash that spreads the keys evenly, and a table that resizes before it gets too full
        correct: true
        why: Right. Cost is the number of slots read. With a good hash and a capped load factor that is one or two; if the keys pile into one slot it is proportional to the number of keys.
      - text: The keys being small, such as integers
        why: Hashing a long string takes longer, but that is per key. The number of slots read does not depend on key size.
      - text: Nothing. Every hash map lookup is one memory read
        why: Collisions mean some lookups read more than one slot, and a bad hash can make every lookup read all of them.
  engineer:
    question: A key type compares two fields for equality but its hash uses only the first. What happens when one value of the first field covers most keys?
    options:
      - text: Lookups still return correct results, but those keys share one hash and every lookup scans them
        correct: true
        why: Right. Equal keys still hash equal, so the map is correct. It just puts every key with that first field in one collision chain, so the cost grows with their number.
      - text: The map returns the wrong value for some keys
        why: The map always confirms with equality after the hash matches, so it finds the right key. It only finds it slowly.
      - text: The map detects the collisions and resizes until they go away
        why: Resizing changes which slot a hash maps to, but keys with the same hash stay together at any size.
  deep:
    question: In an open-addressing table, why does deleting a key leave a tombstone instead of marking the slot empty?
    options:
      - text: An empty slot ends a lookup, so keys placed after it in the same probe run would become unreachable
        correct: true
        why: Right. A lookup walks the probe sequence until it finds the key or an empty slot. A tombstone says keep walking; inserts can reuse it, and a later resize drops it.
      - text: To keep the keys in insertion order
        why: Order is kept separately where it is kept at all (CPython's entries array). Tombstones exist for probe correctness.
      - text: So the table never has to shrink
        why: Tombstones do occupy space until the next rebuild, but that is a cost, not the reason for them.

reference:
  roles:
    - role: Hash function
      example: { go: "the runtime's seeded hash", python: "__hash__ and SipHash for str", typescript: "V8's string hash, random ids for objects", rust: "RandomState (SipHash-1-3)" }
      job: Turns a key into a number. Must agree with equality and spread different keys evenly.
    - role: Slot array
      example: a power-of-two array of buckets or groups
      job: Holds the keys. The hash's low bits pick a home slot.
    - role: Collision handling
      example: chaining, linear probing, Swiss-table groups
      job: Decides where a key goes when its home slot is taken, and so how many slots a lookup reads.
    - role: Resize policy
      example: grow at 2/3 (CPython) or 7/8 (Swiss tables)
      job: Keeps the load factor bounded by doubling and rehashing, which keeps the average cost constant.
  useWhen:
    - Lookup, insert and delete by exact key, where order does not matter. Caches, indexes, counters, dedupe sets, joins in memory.
    - Grouping or counting by a key in one pass over the data.
  avoidWhen:
    - You need keys in order, ranges or the nearest key. Use an ordered map (a B-tree or balanced tree) or a sorted array.
    - Keys come from untrusted input and your hash is fixed and public. Use a seeded hash and cap the input size.
    - Tiny collections that are scanned a few times; a short array is often faster.
  tradeoffs:
    - A lower load cap means fewer probes and more memory.
    - Resizing keeps the average constant but makes some inserts slow; pre-size when you know the count.
    - Open addressing is compact and cache friendly but needs tombstones and degrades sharply near full; chaining degrades gently and costs a pointer per entry.
  lookalikes:
    - name: Ordered map (B-tree, red-black tree)
      how: O(log n) instead of O(1), but keeps keys sorted for ranges and iteration.
    - name: Bloom filter
      how: Hashes keys into bits to answer "maybe present" or "definitely absent" without storing the keys.
    - name: Consistent hashing
      how: Hashes keys to servers instead of slots, and moves few keys when the set of servers changes.
---

## [concept] Hash tables

**A hash table turns a key into a slot index. A lookup costs one hash plus the slots it reads, and that stays at one or two while the hash spreads the keys and the table never gets too full.**

A <Term id="hash-table">hash table</Term> is an array of slots and a <Term id="hash-function">hash function</Term>. To find a key, hash it, take the hash modulo the array size, and look in that slot. Two keys can land in the same slot, a collision, so the table needs a rule for where the second one goes, and a lookup may read a few slots before it finds the key or proves it absent.

<Depth level={2}>
The number that predicts the cost is the <Term id="load-factor">load factor</Term>, keys divided by slots. With <Term id="separate-chaining">separate chaining</Term>, each slot holds a list, and an average list has load-factor many keys. With <Term id="open-addressing">open addressing</Term>, keys live in the array itself and a collision moves on to another slot. Either way, a table that doubles its size whenever the load factor passes a cap keeps the average lookup at a small constant, whatever the number of keys.
</Depth>

<Depth level={3}>
The textbook analysis (CLRS chapter 11) assumes simple uniform hashing: each key is equally likely to land in any slot, independently of the others. Under that assumption a miss in a chained table compares α keys on average and a hit about 1 + α/2, for load factor α. For <Term id="linear-probing">linear probing</Term>, Knuth's result is about ½(1 + 1/(1 − α)) slots for a hit and ½(1 + 1/(1 − α)²) for a miss. At α = 0.5 a miss reads 2.5 slots; at 0.9 it reads about 50.
</Depth>

## [problem] A render cache keyed by tenant

A storefront platform renders product pages and caches the HTML in memory. The cache keeps each tenant's pages together, so purging a tenant after a theme change is one delete. A lookup asks the map for the tenant and then finds the page by path.

Read the code once. It looks like O(1): there is a map right there. Each tenant has a few hundred pages, so the scan never shows up in a profile.

<Depth level={2}>
The map only sees the tenant. In Go and TypeScript the page is found by scanning the tenant's list; in Python and Rust the key type's hash covers only the tenant field, so every page of a tenant collides into one chain inside the map. Either way, the work per lookup grows with the number of pages per tenant, and nothing in the API shows it.
</Depth>

<Depth level={3}>
The Python and Rust versions are legal. A hash only has to give equal keys equal hashes, and two keys with the same tenant still hash the same. The map stays correct: after a hash match it compares the full key. It is just slow, which is the worst kind of bug, because no test fails.
</Depth>

## [pain] Then a change request arrives

**Change request:** move the largest customer, 50,000 storefront pages, onto the shared render cache.

The marked lines warm the new tenant's pages at deploy time. Each put scans every page already stored for that tenant, so warming 50,000 pages costs about 1.25 billion comparisons, and the deploy hangs. Once it is warm, every page view for that tenant scans 25,000 entries on average. Other tenants stay fast, which makes the slowdown look like it is about that customer's traffic.

<Depth level={2}>
Profiles point at the map lookup itself (in Python and Rust) or at the list scan (in Go and TypeScript). Adding servers does not help: every replica has the same table shape. Pre-sizing the map does not help either: a bigger table gives the tenant's pages more empty slots, but they all still hash to one of them.
</Depth>

<Depth level={3}>
This is the same shape as <Term id="hash-flooding">hash flooding</Term>. In 2011 researchers showed that the request parsers of several web platforms put untrusted parameter names into tables with a fixed, public hash, so one request full of crafted names could tie up a CPU core for a long time. Here no one is attacking; the key design produced the collisions on its own.
</Depth>

## [morph] Hash the whole key

Drag the slider. The magic O(1) box becomes the real mechanism: a hash of the whole key, a slot array that stays partly empty, and a resize when it fills up.

The fix is the key, not the map. Hash every field that equality compares, so pages of one tenant land all over the table. Purging a tenant then needs its own index from tenant to keys, a second map that is cheap to keep.

<Depth level={2}>
Know the count? Pre-size the table: `make(map[K]V, n)` in Go, `HashMap::with_capacity(n)` in Rust. Warming then never resizes, which removes the slow inserts from deploys. Python's `dict` and JavaScript's `Map` have no capacity argument; they grow as you insert, which is still O(1) per insert on average.
</Depth>

<Depth level={3}>
Production tables differ from the textbook mostly in collision handling. A <Term id="swiss-table">Swiss table</Term> (Go since 1.24, Rust's hashbrown) splits the hash: the high bits pick a group of 8 or 16 slots, and the low 7 bits are stored in one control byte per slot. A lookup compares its 7 bits against a whole group at once with one wide comparison and only checks the keys whose bytes match. That makes a load factor of 7/8 cheap. CPython uses open addressing with a perturbed probe sequence and resizes at 2/3. V8 chains through an entries array kept in insertion order.
</Depth>

## [walk] Follow one lookup

One get, then one resize, then the big tenant's pages. Use the numbered buttons.

<Depth level={2}>
Resizing is why "O(1) amortised" carries the word amortised. A doubling table moves n keys when it grows from n to 2n slots, so the total moving work over n inserts is at most n + n/2 + n/4 … < 2n. The average per insert is constant, but one insert in the sequence pays for all of it. Latency-sensitive code pre-sizes, or uses a design that grows in pieces: Go splits one 1,024-slot table at a time.
</Depth>

<Depth level={3}>
<Lang only="go">Go map iteration starts at a random position and the hash is seeded per map, so two runs never agree on order. Code that sorts keys before printing or hashing a map is not being fussy.</Lang>
<Lang only="python">A dict lookup hashes the key once and caches it in the entry, so a resize reinserts entries without calling `__hash__` again. Strings also cache their hash on the object.</Lang>
<Lang only="typescript">A string key is hashed once and the hash is cached on the string, so the cost of `keyOf` is building the string, not hashing it repeatedly.</Lang>
<Lang only="rust">hashbrown stores no hash per entry; a resize recomputes each key's hash. A slow hasher makes resizes slow too, which is another reason to `with_capacity` when you can.</Lang>
</Depth>

## [again] The same request, with the whole key hashed

Warming 50,000 pages is now 50,000 puts of one or two slot reads each, a few milliseconds in total. A page view for the big tenant costs the same as for a small one. The test pins the property that matters: keys that differ only in path must not share a hash.

<Depth level={2}>
The tenant index costs one extra set entry per page. That is the price of a cheap purge, and it is paid in memory, not in lookup time. If purges are rare, scanning all keys once on purge is a reasonable alternative.
</Depth>

<Depth level={3}>
A seeded hash also protects this cache from crafted paths. If page paths come from user input and the hash were fixed and public, an attacker could still pick paths that collide. Go, Python, V8 and Rust all seed their default hashes for that reason; a custom hash you write yourself should take a seed too.
</Depth>

## [lens] The map in each language

All four languages ship a hash table, and since Go 1.24 two of them are Swiss tables. What differs is how you make a composite key, how the hash is seeded, and whether you can pre-size.
