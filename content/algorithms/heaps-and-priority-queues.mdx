        // dispatcher.go: a binary min-heap on RunAt, stored in a slice
        type Job struct {
            ID    string
            RunAt time.Time
        }

        type jobHeap []Job // jobHeap[0] is always the earliest

        func (h jobHeap) Len() int           { return len(h) }
        func (h jobHeap) Less(i, j int) bool { return h[i].RunAt.Before(h[j].RunAt) }
        func (h jobHeap) Swap(i, j int)      { h[i], h[j] = h[j], h[i] }
        func (h *jobHeap) Push(x any)        { *h = append(*h, x.(Job)) }
        func (h *jobHeap) Pop() any {
            old := *h
            j := old[len(old)-1]
            *h = old[:len(old)-1]
            return j
        }

        type Dispatcher struct {
            mu   sync.Mutex
            jobs jobHeap
        }

        func (d *Dispatcher) Add(j Job) {
            d.mu.Lock()
            defer d.mu.Unlock()

        // dispatcher.ts: no heap in the standard library, so a small binary min-heap
        interface Job {
          id: string;
          runAt: number; // epoch ms
        }

        class MinHeap<T> {
          private a: T[] = [];
          constructor(private before: (x: T, y: T) => boolean) {}
          peek(): T | undefined { return this.a[0]; }

          push(x: T): void {
            const a = this.a;
            let i = a.push(x) - 1; // the next free leaf
            while (i > 0) {
              const p = (i - 1) >> 1;
              if (!this.before(a[i], a[p])) break;
              [a[i], a[p]] = [a[p], a[i]]; // sift up
              i = p;
            }
          }

          pop(): T | undefined {
            const a = this.a;
            const top = a[0];
            const last = a.pop();
            if (a.length === 0 || last === undefined) return top;
            a[0] = last; // the last leaf takes the root's place
            for (let i = 0; ; ) {
              const l = 2 * i + 1, r = l + 1;
              let c = i;
              if (l < a.length && this.before(a[l], a[c])) c = l;
              if (r < a.length && this.before(a[r], a[c])) c = r;
              if (c === i) return top;
              [a[i], a[c]] = [a[c], a[i]]; // sift down
              i = c;
            }
          }
        }

  overview:
    question: You read a min-heap's array from index 0 to the end. Do you get the jobs in priority order?
    options:
      - text: No. Only the root is guaranteed to be the most urgent; each parent beats its children, but siblings and cousins are in no order
        correct: true
        why: Right. That weaker rule is why the heap is cheap to maintain. To get sorted order you pop repeatedly, which is heapsort.
      - text: Yes, a heap keeps its array sorted
        why: Keeping it sorted would cost what the sorted list costs. A heap only orders each parent against its own children.
      - text: Yes, but only after a pop
        why: A pop repairs one path. The rest of the array stays in heap order, which is not sorted order.
  engineer:
    question: You merge 100 sorted log files of 1 million lines each by timestamp with a heap that holds one line per file. About how many comparisons does it take?
    options:
      - text: About 100 million × log₂ 100, roughly 700 million
        correct: true
        why: Right. Each of the n = 100 million lines is pushed and popped through a heap of k = 100 entries, so the cost is O(n log k), and memory holds just 100 lines.
      - text: About 100 million × log₂ (100 million), as if you sorted everything
        why: That is the cost of concatenating and sorting. The files are already sorted, so the heap only has to choose among 100 heads.
      - text: About 100 million × 100, comparing every head each time
        why: That is a linear scan of the heads. The heap finds the smallest of 100 in about 7 comparisons.
  deep:
    question: Why does building a heap from an unsorted array bottom-up (heapify) take O(n) and not O(n log n)?
    options:
      - text: Most nodes are near the bottom and can only sift down a few levels; summing heights over all nodes gives less than n
        correct: true
        why: Right. About n/2 nodes are leaves and do nothing, n/4 sift at most one level, n/8 at most two, and so on. The sum of h·n/2^(h+1) over all heights converges to about n.
      - text: Heapify only has to sort the bottom level
        why: Heapify touches every internal node, from the last one back to the root. It is cheap because each one sifts down only as far as its own height.
      - text: It is O(n log n) in the worst case; O(n) is only the average
        why: The bound holds in the worst case. Building with n separate pushes is the version that can cost O(n log n).

## [concept] Heaps and priority queues

**A binary heap is a tree stored in an array where every parent is at least as urgent as its children. The most urgent item is always at index 0, and a push or a pop repairs the tree along one path from root to leaf, so both cost O(log n).**

A <Term id="priority-queue">priority queue</Term> hands back the most urgent item, not the oldest. A <Term id="binary-heap">binary heap</Term> is the usual way to build one. It keeps a single rule, the <Term id="heap-property">heap property</Term>, and nothing more: a parent beats its children, while siblings can be in any order. That small rule is cheap to keep and still puts the winner at the root.

<Depth level={2}>
The tree has no pointers. A complete binary tree fills each level left to right, so it fits in an array with the children of index i at 2i+1 and 2i+2 and the parent at (i−1)/2. A push appends at the end and sifts up; a pop moves the last element to the root and sifts down. Peeking is O(1). Building a heap from n items at once is O(n). Searching for an arbitrary item is O(n), because the rule says nothing about where it is.
</Depth>

<Depth level={3}>
The height of a heap with n items is ⌊log₂ n⌋, so <Term id="sift">sift up and sift down</Term> make at most that many swaps. A push of a random priority usually makes far fewer: about half the items are leaves, so a new item is more likely to belong near the bottom, and the expected number of levels it climbs is a small constant. A pop always goes most of the way down, because the item moved to the root came from the bottom.
</Depth>

## [problem] A dispatcher that keeps its queue sorted

A job dispatcher holds scheduled work: report exports, webhook deliveries, emails. Workers ask for the earliest job that is due. The dispatcher keeps its jobs sorted by run time, binary-searches for the insert position, and hands out the first one.

With a few thousand pending jobs it is fast, and the code is easy to read. Binary search makes the insert look like O(log n).

<Depth level={2}>
The search is O(log n); the insert is not. Inserting into the middle of an array moves every later element one place, and taking the first element moves every remaining one. In Python and TypeScript the dispatch is O(n) too (`pop(0)`, `shift()`); in Go the reslice is free, but the insert is still a shift.
</Depth>

<Depth level={3}>
Shifting is a `memmove`, which is fast per byte, so small queues hide it well. At a million 24-byte entries an insert in the middle moves about 12 MB, and a queue taking thousands of adds a second spends its time copying memory.
</Depth>

## [pain] Then a change request arrives

**Change request:** move every tenant's scheduled exports and webhook retries into one dispatcher. That is about 2 million pending jobs.

The marked lines add retries with exponential backoff. Retries are due at all sorts of times, so they land all over the sorted list, not at the end. Each one shifts about a million jobs. Each dispatch in the Python and TypeScript versions shifts all 2 million. The dispatcher's lock is held during every shift, so workers queue up behind it and dispatch latency climbs with the queue length.

<Depth level={2}>
Profiles show the time in `memmove`, `list.insert` or `Array.prototype.sort`, not in your code. Sharding the dispatcher by tenant divides the cost but keeps it linear in the shard size, and the one tenant with a backlog still suffers.
</Depth>

<Depth level={3}>
The TypeScript version is worse: it re-sorts the whole array on every add. V8's TimSort handles an almost sorted array in close to linear time, which is why it survived testing, but that is still O(n) per add.
</Depth>

## [morph] Keep one rule instead of full order

Drag the slider. The sorted list becomes a tree stored in the same array, ordered only from parent to child.

The dispatcher does not need the jobs in order. It needs the earliest one, again and again. A heap gives exactly that: the root is the earliest job, and each add or dispatch repairs one path of at most 21 levels for 2 million jobs.

<Depth level={2}>
Put a sequence number in the key when ties matter. A heap is not stable, so two jobs due at the same instant come out in arbitrary order unless the key says otherwise; `(run_at, seq)` gives first-in, first-out among equals. It also keeps Python from comparing payloads when the priorities tie.
</Depth>

<Depth level={3}>
To cancel or reschedule a job, a binary heap has no cheap way to find it. Either keep each job's index up to date in the Swap method (Go's `container/heap` documentation shows this, with `heap.Fix` to re-sift after a change), or use <Term id="lazy-deletion">lazy deletion</Term>: mark the old entry cancelled, push a new one if needed, and drop stale entries when they reach the root. The Python `heapq` documentation describes exactly that.
</Depth>

## [walk] Follow one retry through the heap

One add, one dispatch, then the same at 2 million jobs. Use the numbered buttons.

<Depth level={2}>
Top-k uses the heap the other way round. To keep the 100 slowest requests out of a stream, keep a min-heap of 100: its root is the fastest of the slow ones. A new latency that beats the root replaces it and sifts down; anything else is dropped after one comparison. That is O(n log k) time and O(k) memory, where sorting everything would be O(n log n) time and O(n) memory.
</Depth>

<Depth level={3}>
<Lang only="go">The Go runtime keeps timers in a 4-ary heap per P: four children per node halves the height, and since the four children sit next to each other in memory, comparing them is cheap.</Lang>
<Lang only="python">`heapq` is written in C in CPython, with a pure Python fallback. Its `heappop` moves the hole down to a leaf first and then sifts the last item up, a trick that saves comparisons because that item usually belongs near the bottom.</Lang>
<Lang only="typescript">Arrays of objects in V8 store pointers, so a swap moves two pointers whatever the job's size. Keep the comparison cheap: compare a number field, not a computed value.</Lang>
<Lang only="rust">`BinaryHeap::pop` also uses the hole technique: it moves the hole to the bottom and then sifts up, so each level costs one move instead of a full swap.</Lang>
</Depth>

## [again] The same request with a heap

Two million jobs, the same retries. Each add and each dispatch costs at most 21 swaps, and the lock is held for microseconds. The test pushes 2 million jobs and checks that dispatches come out earliest first.

<Depth level={2}>
If jobs are cancelled far more often than they run, such as request timeouts, look at a timer wheel. It puts each timer in a bucket by expiry time, so adding and cancelling are O(1), and it trades exact ordering within a bucket for that speed.
</Depth>

<Depth level={3}>
Building the heap from a saved snapshot of 2 million jobs should use heapify (`heap.Init`, `heapq.heapify`, `BinaryHeap::from`), which is O(n), instead of 2 million pushes. Heapify sifts down every internal node from the last one back to the root; most nodes are near the bottom and barely move.
</Depth>

## [lens] Heaps in each language

Python and Rust ship a heap; Go ships the algorithm and asks you for the slice; JavaScript ships nothing. All four are binary heaps in an array.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Mind the direction. `heapq` and `container/heap` (with the usual `Less`) are min-heaps, Rust's `BinaryHeap` is a max-heap, and a hand-written heap is whatever its comparison says. Flipping the comparison is the most common heap bug.
</Depth>
