    question: In a CPU flame graph, what does the width of a box tell you?
    options:
      - text: The share of samples in which that function was on the stack, itself or through the functions it called.
        correct: true
        why: Right. Wide means the function, or something it called, was running in many samples. Its own work is the part not covered by boxes above it.
      - text: How long the function ran, from its first call to its last, left to right in time.
        why: Left to right is alphabetical, so identical stacks merge. A flame chart is the variant that keeps time on the x-axis.
      - text: How many times the function was called.
        why: A sampler does not count calls. A function called a million times for a nanosecond each may never be sampled; one called once for a second will be wide.
  engineer:
    question: An endpoint takes 2 seconds per request, but its CPU flame graph is small and flat and the process uses 15% CPU. What should you look at next?
    options:
      - text: Off-CPU time. Take an off-CPU or wall-clock profile, or trace the request's waits on disk, network and locks.
        correct: true
        why: Right. An on-CPU profiler only samples running threads. If the request spends most of its time waiting, the CPU graph cannot show where.
      - text: Raise the sample rate until the slow function appears.
        why: More samples sharpen the on-CPU picture. They do not add the time the thread spent waiting, which is not sampled at any rate.
      - text: The widest box in the flame graph, since it must be the cause.
        why: The widest box is the biggest share of a small amount of CPU time. Fixing it may save little of the 2 seconds.
  deep:
    question: A flame graph of a native service shows many short towers that end after two or three frames, some labelled with hex addresses. What is the likely cause?
    options:
      - text: The binary was built without frame pointers and without symbols, so the profiler cannot walk past the first frames or name them.
        correct: true
        why: Right. Rebuild with frame pointers (`-fno-omit-frame-pointer`, `-C force-frame-pointers=yes`), or let the profiler unwind with DWARF debug info, and install symbols.
      - text: The functions are very fast, so their callers were never sampled.
        why: Every sample captures the whole stack at that instant, callers included. Short towers mean the walk stopped early.
      - text: The sample rate is too low.
        why: A low rate gives fewer samples, with more noise. It does not shorten the stacks in each one.

  useWhen:
    - Something is slow and you do not know where. Profile before you guess, and before you add timers.
    - CPU is high and you need the code responsible, in production, without a restart.
    - Comparing before and after a change; a differential flame graph colours what grew and shrank.
  avoidWhen:
    - The request is slow while the CPU is mostly idle. An on-CPU flame graph is the wrong tool; profile off-CPU time or trace the waits.
    - You need exact call counts or ordering. Sampling estimates shares; use tracing for every event.
  tradeoffs:
    - Higher rates give finer detail and cost more overhead. 99 Hz on a few cores for 30 seconds is a common default.
    - Round rates such as 100 Hz can fall into step with timers at round periods and over- or under-count them. Odd rates like 99 or 997 avoid it.

    - Off-CPU profiles count waiting threads too, including idle pool threads, so filter to the request path.
  lookalikes:
    - name: Flame chart
      how: Same boxes with time on the x-axis, one request or thread at a time. Shows order; a flame graph shows totals.
    - name: Tracing profiler
      how: Records every call and return, like cProfile. Exact counts, much higher overhead, distorted timings.
    - name: Icicle graph
      how: A flame graph upside down, root at the top. Many viewers, such as speedscope and pprof, can show either.

## [concept] Sampling profilers and flame graphs

**A <Term id="sampling-profiler">sampling profiler</Term> interrupts the program at a fixed rate and records the call stack. Count identical stacks, draw each function as wide as its share of the samples, and you have a <Term id="flame-graph">flame graph</Term>.**

Wide boxes are where the samples landed. Left to right is alphabetical, not time, so the same stack from different moments merges into one box.

<Depth level={2}>
The pipeline has three steps: capture stacks (`perf record -F 99 -g`, pprof, py-spy, the V8 profiler), fold them into <Term id="folded-stack">folded stacks</Term> with a count each, and render. The profile counts only what it samples. An on-CPU profiler samples running threads, so <Term id="off-cpu-time">off-CPU time</Term>, waiting for disk, network or locks, is missing however long it is.
</Depth>

<Depth level={3}>
Stack walking is the fragile part. Profilers follow <Term id="frame-pointer">frame pointers</Term> from frame to frame, or unwind with DWARF debug info, which is slower and copies more stack. Builds that omit frame pointers give short, broken stacks, and missing symbols give hex addresses. Sample rates are odd numbers such as 99 or 997 Hz so that the sampler cannot fall into step with work driven by timers at round periods.
</Depth>

## [problem] An export that someone timed by hand

A billing service lets customers export their orders. The handler loads the orders, formats each row with its currency symbol, writes an audit record for every exported order for compliance, and encodes the result. Someone added two log lines with timers when it felt slow once: the database query, and the total.

Read it with the usual mental model: if something is slow, put timers around the parts you suspect, and the numbers will point at the culprit.

<Depth level={2}>
Timers only measure what you thought to wrap. The two log lines say the query takes 44 ms. They say nothing about the 2,000 calls to `currencySymbol`, which parses the whole currency table every time, or the 2,000 audit writes, each made durable with an fsync.
</Depth>

<Depth level={3}>
The audit log is the subtle part. Each record is small and the write is fast, but making it durable waits for the disk. That wait costs no CPU, so even a profiler can miss it.
</Depth>

## [pain] Then a change request arrives

**Change request:** large customers want a full year of orders in one export. Raise the export limit from 100 orders to 2,000.

The marked line is the only change. Exports for large customers now take 3.1 seconds. The log says the database took 44 ms and the total was 3.1 s, and nothing in between. The timers cannot say where the other 3 seconds went.

<Depth level={2}>
Someone runs a CPU profiler, and the flame graph is clear: `currencySymbol` and the JSON decoding under it are about 73% of the CPU samples. Caching the table cuts CPU time by three quarters. The export gets only about 27% faster, to 2.3 s, because the CPU was busy for 1.1 s of the 3.1 s.
</Depth>

<Depth level={3}>
The remaining 2 seconds are 2,000 fsyncs of about a millisecond each. A thread in fsync is off-CPU, and an on-CPU profiler never samples it, so the flame graph shows `audit.Record` as a sliver.
</Depth>

## [morph] Sample the stacks, then look at both kinds of time

Drag the slider. The hand-placed timers become a sampler, the stacks fold into a flame graph, and the graph's two views point at two different problems: one on-CPU, one off-CPU.

Hover a box in the diagram to see its code.

<Depth level={2}>
Profile first, with no code change: an on-CPU profile for where the CPU goes, then a wall-clock or off-CPU profile when CPU time is well below the request time. Fix the widest frame in each, and measure again.
</Depth>

<Depth level={3}>
Off-CPU flame graphs are built the same way but weighted by time blocked, recorded when a thread is switched out and back in (bcc's `offcputime`). Wall-clock samplers such as `fgprof` and `py-spy --idle` sample waiting threads alongside running ones. Both count idle threads too, so filter to the request's threads or stacks.
</Depth>

## [walk] Follow the samples

From the timer interrupt to the flame graph, and on to the wait it cannot see. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">The Go runtime asks the kernel for a `SIGPROF` signal for every 10 ms of CPU a thread uses (100 Hz); the signal handler records the running goroutine's stack into a buffer that `pprof` reads. `fgprof` instead calls `runtime.GoroutineProfile` about 99 times a second, which captures every goroutine, running or not.</Lang>
<Lang only="python">py-spy reads the interpreter's memory from another process, so the profiled program runs unmodified. It finds each thread's current frame and walks the frame chain. Because it reads memory while the program runs, it can see a stack mid-change; by default it pauses the process briefly for each sample to avoid that.</Lang>
<Lang only="typescript">V8's profiler runs a sampling thread that interrupts the JavaScript thread on each tick and records the JS stack, with names from the JIT's own tables. When the event loop is waiting for I/O there is no JavaScript to record, and the sample is counted as `(idle)`.</Lang>
<Lang only="rust">`perf` programs a CPU timer to interrupt at 997 Hz; the kernel records the user stack, and `cargo flamegraph` asks perf to copy a slice of it and unwind with DWARF, because Rust release builds omit frame pointers by default.</Lang>
</Depth>

## [again] A year of orders, profiled and fixed

The same 2,000 orders. The currency table is parsed once, and the audit records go out in one write with one fsync per export. The export takes about 0.2 s instead of 3.1 s. The test above runs the full export against a real file and asserts it finishes within 300 ms.

<Depth level={2}>
Keep the profiling endpoints on in production, on an internal port. A 30-second profile during an incident beats any number of guesses, and continuous profilers collect the same data all the time.
</Depth>

<Depth level={3}>
Batching the fsync keeps every record durable before the response is sent, so compliance is unchanged. What changed is that 2,000 small waits became one.
</Depth>

### From perf to a flame graph

The classic pipeline on Linux, with Brendan Gregg's FlameGraph scripts:

```
perf record -F 99 -a -g -- sleep 30
perf script | ./stackcollapse-perf.pl > out.folded
./flamegraph.pl out.folded > cpu.svg
```

Each line of `out.folded` is one stack, root first, frames joined by semicolons, then a space and its sample count. Any tool that writes this format, or the pprof format, can feed any viewer.
