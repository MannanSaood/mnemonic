        func hedged[T any](ctx context.Context, after time.Duration, call func(context.Context) (T, error)) (T, error) {
            ctx, cancel := context.WithCancel(ctx)
            defer cancel() // stops the loser
            type result struct {
                v   T
                err error
            }
            out := make(chan result, 2)
            send := func() { v, err := call(ctx); out <- result{v, err} }
            go send()
            select {
            case r := <-out:
                return r.v, r.err
            case <-time.After(after):
                go send()
            }
            r := <-out
            return r.v, r.err
        }

    question: 99 requests take 10 ms and one takes 5 seconds. What are the mean and the median?
    options:
      - text: Mean about 60 ms, median 10 ms.
        correct: true
        why: Right. The one slow request adds 50 ms to the mean, which then describes neither the 99 fast requests nor the slow one. The median ignores it entirely. Only the max or a high percentile shows it.
      - text: Mean 10 ms, median about 60 ms.
        why: Swapped. The median is the middle value, 10 ms. The mean is pulled up by the outlier.
      - text: Both about 60 ms.
        why: The median is the middle value of the sorted list. 99 of the 100 values are 10 ms, so the median is 10 ms.
  engineer:
    question: Two servers behind a load balancer report p99 latencies of 200 ms and 400 ms. What is the p99 of the service?
    options:
      - text: It cannot be computed from those two numbers. Sum the servers' histograms and read the p99 from the sum.
        correct: true
        why: Right. The answer depends on how many requests each server handled and on the shape of each distribution. It can be anywhere from below 200 ms to 400 ms. Bucket counts add up; percentiles do not.
      - text: 300 ms, the average of the two.
        why: That is only right by accident. If the 400 ms server took 1% of traffic, the fleet p99 is close to 200 ms. If it took 90%, it is close to 400 ms.
      - text: 400 ms, the worse of the two.
        why: The worst server's p99 is an upper bound on the fleet's p99, and can be far above it when that server handles little traffic.
  deep:
    question: A load generator sends about 100 requests a second, each only after the previous response. During a 60-second test the server freezes once for 2 seconds. The tool reports a p99 of 12 ms. Why does that hide the freeze?
    options:
      - text: The tool sent nothing during the freeze, so it recorded one slow request where real users, arriving at their own pace, would have produced hundreds.
        correct: true
        why: Right. That is coordinated omission. The tester slowed down with the server and skipped exactly the requests that would have been slow. Open-loop load, or correcting each sample for the requests that should have been sent (HdrHistogram's recordCorrectedValue), restores them.
      - text: 2 seconds is too short to show up in a 60-second test.
        why: At 100 requests a second, a real user population would have sent about 200 requests during the freeze, over 3% of the test, which is well above the 1% the p99 ignores.
      - text: The p99 ignores the slowest 1% of requests by definition.
        why: The p99 is the value that 1% of requests exceed. A 2-second freeze would dominate it if the requests that arrived during it had been measured.

reference:
  roles:
    - role: Percentile
      example: p50, p99, p99.9 of page latency
      job: Says how slow the slowest share of requests were. Report several, plus the max, for the request users wait on.
    - role: Histogram
      example: { go: "prometheus.Histogram", python: "prometheus_client.Histogram", typescript: "prom-client Histogram", rust: "hdrhistogram::Histogram" }
      job: Counts requests per latency bucket. Cheap to record, and sums correctly across threads, pods and time windows.
    - role: Fan-out
      example: one search, 40 shard calls
      job: Turns each backend's rare slow call into a common slow response. With N calls, 1 − (1 − p)^N of requests hit at least one.
    - role: Hedged request
      example: a backup call after the shard's p95
      job: Cuts the tail of a fan-out for a few percent more load, when the slowness comes from the replica rather than the request.
  useWhen:
    - Any latency dashboard or SLO. Show p50 and p99 (or p99.9) for the request users wait for, not only for each backend.
    - Aggregating latency across instances or time. Record histograms and sum their buckets.
    - Designing a fan-out. Budget for the backends' p99, because the page will see it constantly.
  avoidWhen:
    - Averaging percentiles, from different servers or from consecutive minutes. The result is not a percentile of anything.
    - Judging a service by its mean latency alone, or by mean plus two standard deviations; latency is not normally distributed.
    - Hedging calls that are not safe to repeat, or a backend that is slow because it is overloaded. Extra copies add load to the thing that is already struggling.
  tradeoffs:
    - Bucket boundaries set the error. A percentile from buckets is known only to within its bucket; log-spaced or HDR buckets keep that error relative.
    - High percentiles need many samples. A p99.9 from 1,000 requests rests on one value.
    - Hedging trades extra load for a shorter tail. Sending the backup only after the p95 keeps the extra load near 5%.
    - Pre-computed percentiles (summaries) are cheap to read and impossible to aggregate.
  lookalikes:
    - name: Summary metric
      how: Computes quantiles inside each process over a sliding window. Accurate per instance, and cannot be combined across instances.
    - name: Latency heat map
      how: A histogram per time interval, drawn as columns. Shows modes, outliers and drift that a percentile line hides.
    - name: Apdex and SLO error budgets
      how: Count requests slower than a threshold. A threshold count sums across servers, like a histogram bucket.

## [concept] Latency, averages and percentiles

**Latency is a distribution, so describe it with <Term id="percentile">percentiles</Term>: p50 is the typical request, p99 is the slow one in a hundred. The mean describes neither.**

Most requests are fast and a few are very slow. The slow ones are the <Term id="tail-latency">tail</Term>. A user who makes many requests, or a page that waits for many backends, meets the tail far more often than the percentile suggests.

<Depth level={2}>
Three rules follow. Measure the request the user waits for, not only each backend. Record a <Term id="latency-histogram">histogram</Term>, a count of requests per latency bucket, so you can read any percentile later and sum across servers. And expect <Term id="request-fan-out">fan-out</Term> to multiply the tail: if each of N parallel calls is slow with probability p, a request that waits for all of them is slow with probability 1 − (1 − p)^N.
</Depth>

<Depth level={3}>
Latency distributions are skewed and often have several modes: a cache hit hump and a cache miss hump, or a fast path and a slow path. The mean and standard deviation assume one symmetric hump, so "mean plus two standard deviations" is not the p95. A <Term id="hedged-request">hedged request</Term> cuts the tail of a fan-out by racing a second copy of a slow call. Measurements have their own trap, <Term id="coordinated-omission">coordinated omission</Term>, where the measuring tool slows down with the system and skips the slow requests.
</Depth>

## [problem] A search API with a healthy average

A product search page calls the search API, which sends each query to every shard of the index in parallel and merges the hits. Each shard call is timed, and the dashboard shows each shard's mean latency: about 12 ms. The page is fast, and the dashboard agrees.

Read it with the usual mental model: if each shard takes 12 ms on average, the page takes about 12 ms plus the merge.

<Depth level={2}>
The mean is a running sum divided by a count, so it is cheap and easy to chart. It is also blind to rare slow calls. A shard that answers in 10 ms 99 times and stalls for 200 ms once has a mean of 12 ms, which no single call actually took.
</Depth>

<Depth level={3}>
The fleet dashboard also shows a p99, computed by averaging each shard's p99. That number has no meaning: percentiles do not add, and the average ignores how many requests each shard served.
</Depth>

## [pain] Then a change request arrives

**Change request:** the product catalogue has outgrown its 4 search shards. Split the index across 40.

The marked line is the only change. Every shard still averages 12 ms, and its p99 is unchanged. Yet users complain that search is slow, and the page's own latency, once someone measures it, is 200 ms on about one load in three. The mean of the shards cannot explain it, because the page does not wait for an average shard. It waits for the slowest of 40.

<Depth level={2}>
Each shard stalls on 1 call in 100, from a garbage collection pause or a read that misses the cache. With 4 shards, 1 − 0.99⁴ is about 4% of pages. With 40, 1 − 0.99⁴⁰ is about 33%. The shards' 1-in-100 stall now starts at the page's p67. Dean and Barroso give the same arithmetic in The Tail at Scale: a server with a 1-in-100 one-second tail, fanned out to 100 servers, makes 63% of user requests take over a second.
</Depth>

<Depth level={3}>
In that paper's measurements from a real service, the 99th-percentile latency for one leaf request was 10 ms, while waiting for all leaf requests took 140 ms at the 99th percentile. Waiting for the slowest 5% of leaves accounted for half of it.
</Depth>

## [morph] Measure the page, and race the tail

Drag the slider. The shard mean becomes a page timer feeding a histogram, the fleet p99 comes from summed buckets, and slow shard calls get a backup.

Hover a box in the diagram to see its code.

<Depth level={2}>
Two fixes, of different kinds. Measuring the page with a histogram makes the problem visible and makes the fleet percentiles correct. Hedging makes it smaller: a call still waiting at the shard's p95 goes to a second replica, and the first answer wins. Only about 5% of calls get a backup, so the extra load stays near 5%.
</Depth>

<Depth level={3}>
Hedging works when the slowness belongs to the replica (a pause, a busy disk, a noisy neighbour), not to the request. Dean and Barroso report a BigTable benchmark where a hedge after 10 ms cut the 99.9th-percentile latency of reading 1,000 keys from 1,800 ms to 74 ms, for 2% more requests. If the backend is slow because it is overloaded, hedging adds load where there is none to spare; cap it, or skip it.
</Depth>

## [walk] Follow one search

One search through 40 shards: the fan-out, the stall, the histogram and the backup. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Prometheus buckets are cumulative counters, one per upper bound (`le`), so summing them across pods is valid. `histogram_quantile` then interpolates linearly inside the bucket that holds the rank. Native histograms in newer `client_golang` versions pick exponential buckets for you.</Lang>
<Lang only="python">`PAGE.time()` measures wall-clock time across the awaits inside it, which is the time the user waits. `asyncio.wait` with `FIRST_COMPLETED` returns as soon as one copy finishes; cancelling the other stops it at its next await.</Lang>
<Lang only="typescript">`Promise.race` settles with the first copy. Aborting the shared `AbortController` cancels the other `fetch`, so the losing replica stops reading the response.</Lang>
<Lang only="rust">`tokio::select!` polls both futures and drops the one that loses, which cancels it. `tokio::pin!` lets the first call keep running across both `select!` blocks instead of starting again.</Lang>
</Depth>

## [again] 40 shards, measured and hedged

The same 40 shards, each still stalling on 1 call in 100. The page now records its own latency in a histogram, the dashboard reads p99 from summed buckets, and stalled shard calls are hedged at p95. The page p99 drops from about 240 ms to about 35 ms, for about 5% more shard calls. The test above stalls the shards on purpose and asserts the page p99 stays under 50 ms.

<Depth level={2}>
Alert on the page's p99, and keep each shard's histogram too. When the page tail grows, the shard histograms show which shard's tail moved.
</Depth>

<Depth level={3}>
High percentiles need samples. A p99.9 needs thousands of requests in the window to rest on more than a handful of values. For rare, expensive requests, count requests over a threshold instead.
</Depth>

### Fan-out arithmetic

The share of requests that hit at least one slow call, when each of N parallel calls is slow with probability p:

| Calls per request | p = 1 in 1,000 | p = 1 in 100 | p = 1 in 20 |
|---|---|---|---|
| 1 | 0.1% | 1% | 5% |
| 10 | 1% | 10% | 40% |
| 40 | 4% | 33% | 87% |
| 100 | 10% | 63% | 99% |

To read a fleet percentile from Prometheus histograms, sum the buckets first: `histogram_quantile(0.99, sum by (le) (rate(search_page_seconds_bucket[5m])))`.
