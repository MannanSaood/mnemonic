reference:
  roles:
    - role: Client at the call
      example: Payment client, repository
      job: Knows what the outside world's failures mean. Names them as error kinds, retries the transient ones, keeps the original as the cause.
    - role: Middle layer
      example: Order service
      job: Adds what it was doing and passes the error up. Handles an error only if it can do something useful about it.
    - role: Edge
      example: HTTP handler, queue consumer, CLI main
      job: Turns an error into a status and a message, and logs anything unexpected once, with the whole chain.
  useWhen:
    - A request crosses several layers and at least one of them talks to a network, a disk or a database.
    - Customers or callers need different answers for different failures (declined, try later, our fault).
    - On-call engineers need to find the cause of a failure from the logs alone.
  avoidWhen:
    - A short script that you run by hand. Letting the error crash the program with its full trace is the right policy there.
    - Inner helpers with one caller. A layer of wrapping per function adds noise; wrap where the context changes, usually at module or service boundaries.
  tradeoffs:
    - Error kinds are an API. Once callers match on `CardDeclined`, renaming or splitting it is a breaking change.
    - Retries add latency to failures and load to a struggling dependency. Cap them, back off, and retry in one layer only.
    - Messages written at the edge can be vague. The edge must log the full chain, or the detail is lost.
  lookalikes:
    - name: Graceful degradation
      how: One deliberate response to a failure, serving less instead of failing. It is a policy chosen at a boundary, not a catch-all that hides errors.
    - name: Circuit breaker
      how: Stops calling a dependency that keeps failing. It decides whether to call at all, where a retry decides whether to call again.
    - name: Railway-oriented programming
      how: A functional style where each step returns success or failure and failures skip the rest. It is errors-as-values with combinators, as in Rust's `Result` and `?`.

## [concept] Error-handling strategies

**Handle each error once, in the layer that can act on it. Retry next to the call, add context on the way up, translate at the edge, and never swallow.**

When a call fails, the code that sees the failure has a few choices: try again, give up and pass the error up, substitute something and carry on, or turn it into a message for a person. Each layer of a request makes this choice, and the choices add up. One layer that hides a failure makes every layer above it wrong.

<Depth level={2}>
The useful question for each layer is what it knows. The client that called the payment provider knows what a 503 means and whether the call is safe to repeat. The service knows which order it was placing. The handler knows the customer and the protocol. So the client names and retries, the service adds context, and the handler translates. A layer that does someone else's job (a repository writing customer text, a handler parsing driver codes) is where error handling goes wrong.

Robustness and correctness pull in different directions. A video player that skips a corrupt frame is right to carry on. A checkout that carries on after a failed charge ships goods for free. Decide per system which one matters more, write the policy down, and apply it the same way in every layer.
</Depth>

<Depth level={3}>
Steve McConnell's *Code Complete* lists the classic options (return a neutral value, substitute the next valid data, return the previous answer, log a warning, return an error code, call a central handler, shut down) and frames the choice as correctness against robustness. Two newer ideas matter in services. A <Term id="wrapped-error">wrapped error</Term> keeps the original failure inside a new one, so context and cause both survive. And retries are only safe when the operation is idempotent, which for payments means sending an <Term id="idempotency-key">idempotency key</Term>.
</Depth>

## [problem] A checkout written to never break

POST /orders charges the card through a payment provider, then saves the order. The payment client was written so that a network hiccup would not break checkout: it logs the error and returns success. Anything else from the provider becomes the text "payment failed". The handler sends whatever error reaches it back to the customer with a 500.

<Depth level={2}>
Each choice looks reasonable on its own. Not breaking checkout sounds kind. A short error string is easy to write. Returning the error text helps when you test locally. Together they mean that the most important failure, a charge that did not happen, is invisible to the code that saves the order.
</Depth>

<Depth level={3}>
The network error is a <Term id="swallowed-error">swallowed error</Term>. The log line is accurate, which makes it worse: the code looks like it handles the failure, and reviewers move on. Logging is a record, not a decision.
</Depth>

## [pain] Then a change request arrives

**Change request:** declined cards must say so, and a one-second blip at the payment provider must not fail the checkout.

The obvious patch is in the handler, the only place that sees errors. It compares the error text with "payment failed", but a declined card and a provider outage both produce that text, so it cannot tell them apart. The retry goes around the whole order, because that is what the handler can call. When the database times out after a successful charge, the retry charges the card again.

<Depth level={2}>
The information the change needs was thrown away two layers down. The status code was replaced by a string, and the network error was replaced by success. No patch at the top can get it back. The fix has to start at the bottom, where the failure is first seen.
</Depth>

<Depth level={3}>
<Lang only="go">Comparing `err.Error()` with a string breaks the moment someone adds context with `fmt.Errorf`. That is why Go code checks errors with `errors.Is` and `errors.As`, which look through wrapping.</Lang>
<Lang only="python">`str(e) == "payment failed"` matches the message, which anyone may reword. An exception class is a name the type checker and the `except` clause can both see.</Lang>
<Lang only="typescript">`String(e).includes(...)` works on whatever was thrown, including strings and plain objects, and breaks silently when a message changes. A class checked with `instanceof` is a contract.</Lang>
<Lang only="rust">Matching on `String` contents gives up the main thing `Result` offers, an error type the compiler checks. With an enum, the match on error kinds is exhaustive.</Lang>
</Depth>

## [morph] Name the failure where it happens

Drag the slider. The payment client stops hiding failures and names them as error kinds. The service adds context and passes them up. The handler, at the edge, maps kinds to responses and logs anything unexpected once.

Hover a box in the diagram to see its code.

<Depth level={2}>
The kinds are few and chosen by what callers do next, not by what went wrong inside: declined (ask for another card), unavailable (try later, or retry), anything else (our bug). A timeout, a refused connection and a 503 are all "unavailable" to the caller.
</Depth>

<Depth level={3}>
Exceptions and error values are two ways to carry the same information. With exceptions the middle layer can do nothing and the error still arrives; with values it must pass the error on explicitly, which makes the propagation visible in review. Either way the chain should end at one place that logs it.
</Depth>

## [walk] Follow one outage

The provider is down. Step through how the failure travels up, and what each layer does with it.

<Depth level={3}>
<Lang only="go">`%w` stores the wrapped error, and `errors.Is` follows `Unwrap` methods down the chain, including the `Unwrap() []error` form that a multi-`%w` `Errorf` creates. The check is a loop over pointers, cheap enough to run on every request.</Lang>
<Lang only="python">When `raise ... from e` runs, Python sets `__cause__` on the new exception and the traceback module prints both, separated by "The above exception was the direct cause of the following exception". An exception raised inside an `except` block without `from` still records the first one as `__context__`.</Lang>
<Lang only="typescript">`cause` is an own property set by the `Error` constructor. Node's `util.inspect`, and so `console.error`, prints the cause chain; many loggers' error serialisers include it too, but check yours.</Lang>
<Lang only="rust">`?` expands to a match that returns `Err(From::from(e))`. `thiserror` generates the `From` impl for `#[from]` fields and the `source()` method for `#[source]` fields, so the chain is plain data that any logger can walk.</Lang>
</Depth>

## [again] Retry the blip, the second time

The same request, after the refactor. The retry goes into the payment client, next to the one call it repeats. It retries only "unavailable", with a short <Term id="exponential-backoff">backoff</Term>, and sends the order id as an idempotency key. The service and the handler do not change.

<Depth level={2}>
A <Term id="transient-failure">transient failure</Term> is worth retrying. A declined card is not, so the retry checks the kind. Retry in one layer only: if the client, the service and the handler each retry three times, one failing call becomes 27.
</Depth>

<Depth level={3}>
Retries interact with outages. When a dependency is down, every client retrying at once can keep it down. Cap attempts, add jitter, and consider a retry budget or a circuit breaker for calls with heavy traffic. A slow failure is often worse than a fast one, so the retry also respects the request's deadline.
</Depth>
