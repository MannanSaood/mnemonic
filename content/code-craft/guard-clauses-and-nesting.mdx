  overview:
    question: What does a guard clause do?
    options:
      - text: It handles a special or invalid case at the top of a function and returns, so the rest of the function can assume the case does not apply.
        correct: true
        why: Right. Each guard closes one question for good. The reader carries nothing forward from it.
      - text: It wraps the main logic in an if, so the logic only runs when every condition holds.
        why: That is the nested form a guard clause replaces. Every condition stays open around the main logic.
      - text: It catches exceptions so the function never fails.
        why: A guard checks conditions before work begins. Catching and hiding failures is a different thing, and usually a bad one.
  engineer:
    question: A function has two nested loops, and the inner loop body has three nested ifs. What is the best first refactoring?
    options:
      - text: Extract the inner loop body into a named function, and use guard clauses (or continue) inside it.
        correct: true
        why: Right. The extracted function gets a name that says what one item's processing does, and inside it each early return skips one item. Two refactorings that each make the other easier.
      - text: Combine the three if conditions into one long condition with &&.
        why: It removes two levels, but the reader still has to untangle one long condition, and any else branches are lost or duplicated.
      - text: Add comments at each closing brace saying which if it closes.
        why: Comments describe the problem instead of removing it. They also drift when someone moves a block.
  deep:
    question: A function ends with a switch over an order status that returns "unknown" in its default branch. You change it to an exhaustive match. What happens when someone adds a new status next year?
    options:
      - text: The build fails at every match that does not handle the new status, so each one gets a deliberate decision.
        correct: true
        why: Right. In Rust a non-exhaustive match is a compile error; in TypeScript a default that assigns to never does the same job. The default branch hid new cases; exhaustiveness turns each into a to-do list.
      - text: The new status goes to the default branch, as before.
        why: That is what the default branch did. Removing it is the point; without a default there is nowhere for an unhandled case to hide.
      - text: Nothing changes until the new status is seen at runtime.
        why: Exhaustiveness is checked by the compiler from the type's list of cases, before the program runs.

  useWhen:
    - A function validates input or preconditions before doing its work (handlers, commands, parsers).
    - The else branch of an if is a short failure reply and the then branch is the long main logic.
    - You see `else` right after a `return`, or closing braces stacked three or more deep.
  avoidWhen:
    - The branches are two equal alternatives, such as two pricing rules. An if/else shows that they are peers; a guard would make one look like an error.
    - The function must clean up on every exit and the language has no defer, with, finally or Drop to do it. Then several returns can leak a resource. Use the language's cleanup construct first.
  tradeoffs:
    - Guard order is behaviour. When an input fails two checks, the first guard decides the reply, so reordering guards needs tests.
    - Many small guards can hide that a function validates too much. If there are ten, the validation may belong in its own type or function.
    - Several exits make it harder to put one breakpoint or log line at the end. A wrapper or a deferred call usually solves it.
  lookalikes:
    - name: Table-driven methods
      how: Replaces a chain of ifs that choose a value with a lookup in data. Guard clauses keep the ifs and change their shape.
    - name: Replace conditional with polymorphism
      how: For a switch on a type repeated in many places. Each case becomes a method on its own type, so no function has to branch on it.
    - name: Validation layer
      how: Moves the guards out of the handler into a type or schema that parses input once at the boundary, so the handler receives values that are already valid.

## [concept] Guard clauses and nesting

**Handle the special cases first and return early, so the main path reads straight down with nothing left open.**

Every `if` you are inside is a condition you have to remember while you read. Six nested ifs mean six things held in mind on the most important line of the function, and each `else` sits far from the `if` it belongs to. A <Term id="guard-clause">guard clause</Term> checks one special case at the top, answers it, and returns. After it, that case is gone.

<Depth level={2}>
Flattening does not remove decisions. A handler with six checks has seven outcomes before and after. What changes is the reader's load: in the nested form the reader must keep every open condition and match each `else` to its `if` by counting braces. In the flat form each check and its reply sit together, and once read they can be forgotten. Naming a compound condition (`validSignature`) cuts the load again, because the reader can trust the name and skip the detail.

The old rule "one entry, one exit" came from languages where every exit had to free resources by hand. With `defer`, `with`, `finally` or `Drop`, early returns are safe, and they are usually clearer.
</Depth>

<Depth level={3}>
Two metrics measure different things here. <Term id="cyclomatic-complexity">Cyclomatic complexity</Term> counts independent paths, and does not change when you flatten: it tells you how many tests you need. <Term id="cognitive-complexity">Cognitive complexity</Term>, defined by G. Ann Campbell at SonarSource, adds one for each branch plus one for each level of nesting around it, and does not count early returns. The nested handler in the playground scores 29; the flat one scores 6.
</Depth>

## [problem] A webhook handler that checks everything

A payment provider sends webhooks. Before the handler processes an event, it checks five things: the method is POST, the signature is valid and recent, an idempotency key is present, the key has not been seen before, and the body parses. Each check was added as the main logic's guard, by wrapping the existing code in one more `if`.

Read it once. The main path, the three lines that do the work, sits four or five levels deep in the middle of the function. The reply for a wrong method is at the very bottom.

<Depth level={2}>
Nothing here is a bug, and every check is needed. This shape grows naturally: the first version had one if, and each later check wrapped what was there. It is also how many people first learn to write "only do X if Y".
</Depth>

<Depth level={3}>
The signature condition relies on <Term id="short-circuit-evaluation">short-circuit evaluation</Term>: `verify` runs only if the header is not empty, and the age check runs only if `verify` passed. That order matters for cost (HMAC before a cheap comparison would waste work) and for correctness when a later part assumes an earlier one.
</Depth>

## [pain] Then a change request arrives

**Change request:** test-mode events must be rejected in production with a 403.

In the nested shape the new check wraps the main path in one more level. The three lines of real work move right, and a new `else` with the 403 appears below them, between other elses that belong to other ifs. A reviewer has to count braces to see which condition each reply answers.

<Depth level={2}>
The diff touches lines that did not change in meaning, only in indentation. On a busy file that is a merge conflict waiting to happen, and it hides the one line that matters in a wall of moved code.
</Depth>

<Depth level={3}>
<Lang only="go">`gofmt` re-indents the whole block, so the diff shows every line of the main path as changed. `git diff -w` hides whitespace-only changes, but reviewers on the web usually see the full diff.</Lang>
<Lang only="python">In Python the indentation is the structure, so the moved lines are a real change. Get one level wrong and the `return` binds to a different block without any error.</Lang>
<Lang only="typescript">Prettier re-indents the whole block, so the diff shows every line of the main path as changed, and the closing braces at the end become harder to match.</Lang>
<Lang only="rust">`rustfmt` re-indents the block, and because the nested version uses `if` as an expression, the new `else` must also produce a `Reply` or the function stops compiling.</Lang>
</Depth>

## [morph] Invert each check and return

Drag the slider. Each `if` is inverted so that it tests for the failure, answers it and returns. The compound signature condition moves into a named function. The main path ends up at the left margin, last in the function.

Hover a box in the diagram to see its code.

<Depth level={2}>
Do it one check at a time, from the outside in, and run the tests after each. Invert the condition carefully: `!(a && b && c)` is `!a || !b || !c`, and that is where most mistakes happen. Naming the condition first makes the inversion trivial.
</Depth>

<Depth level={3}>
To the compiler both versions are the same control-flow graph: the same blocks and the same edges, laid out differently. Nesting is a property of the source text, not of the machine code. That is why the optimiser is indifferent and the reader is not.
</Depth>

## [walk] Follow one request

A request goes through the guards from top to bottom. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">Each guard ends in a bare `return`. If the handler held a resource, a `defer` placed right after acquiring it would run on every one of these exits.</Lang>
<Lang only="python">If the handler opened a resource, a `with` block around the main path, or `try`/`finally`, runs cleanup on every return inside it.</Lang>
<Lang only="typescript">Each guard returns a `Reply`, so the function's return type checks that every path answers. With `noImplicitReturns` the compiler also flags a path that forgets to.</Lang>
<Lang only="rust">The `else` of a `let ... else` must diverge; the compiler rejects one that falls through. `Drop` runs for every value in scope on each early return, so there is no cleanup to forget.</Lang>
</Depth>

## [again] Test mode, the second time

The same request, after the refactor. The new rule is one more guard after the event is parsed. Nothing moves, and the reply sits next to its condition.

<Depth level={2}>
Where the guard goes still matters. It must come after parsing, because it reads the event, and its position decides the reply for an event that is both test-mode and a duplicate. Write that case down as a test before you choose.
</Depth>

<Depth level={3}>
If guards keep growing, the validation may want to become a type: parse the raw request once into a `VerifiedEvent` that can only be built when all checks pass. The handler then takes that type and has no guards left.
</Depth>

## [lens] How each language writes it
