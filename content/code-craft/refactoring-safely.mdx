# ---------------------------------------------------------------- checks, one per depth
checks:
  overview:
    question: While renaming variables in a function, you spot an off-by-one bug and fix it in the same edit. Is that commit a refactoring?
    options:
      - text: No. The fix changes behaviour. Make it a separate commit, with a test that shows the bug.
        correct: true
        why: Right. A refactoring commit should be one that nobody needs to review for behaviour. Mixing in a fix means every line must be read as a possible behaviour change.
      - text: Yes. It is all tidying the same function.
        why: A refactoring is defined by keeping behaviour the same, not by touching the same lines. The bug fix makes the output different.
      - text: Yes, as long as the tests still pass.
        why: If the tests still pass after a bug fix, they did not cover the bug. Passing tests do not make a behaviour change into a refactoring.
  engineer:
    question: You applied five refactorings, then ran the tests, and one fails. What is the cheapest next move?
    options:
      - text: Revert to the last green commit and redo the steps one at a time, running the tests after each.
        correct: true
        why: Right. Each step is small and named, so redoing them is quick, and the first red run points at one step. Debugging the combined diff means reasoning about five changes at once.
      - text: Read the combined diff until you find the change that broke it.
        why: It can work, but you are searching all five changes by eye for something that looked harmless when you wrote it. That is the slow way to find it.
      - text: Update the failing test to the new value, since refactorings do not change behaviour.
        why: The test says behaviour did change. Changing the test hides a real regression, here a customer paying shipping they should not.
  deep:
    question: A library you publish has an exported function with a misleading name. You rename it with your IDE across the whole repository. Is that a pure refactoring?
    options:
      - text: Not for code outside the repository. Its callers break. Add the new name, keep the old one as a deprecated alias, and remove it in a later major release.
        correct: true
        why: Right. That is a parallel change (expand, migrate, contract). Inside one repository a tool rename is safe because the tool sees every caller; a published API has callers it cannot see.
      - text: Yes. The IDE renamed every call site, so behaviour is unchanged.
        why: Every call site the IDE could see. Users of the library compile against the old name and break on upgrade.
      - text: Yes, if the library is in a dynamic language, because callers look names up at runtime.
        why: Runtime lookup makes it worse. The callers fail when they run, not when they build.

# ---------------------------------------------------------------- reference page
reference:
  roles:
    - role: Smell
      example: magic numbers, a long function, a rule inline where a type should own it
      job: Tells you where to look and which move might help. It is the trigger, not the goal.
    - role: Small step
      example: Extract Function, Rename Variable, Inline Function, Move Function
      job: One named move from the catalogue, small enough to check in seconds and to redo if it goes wrong.
    - role: Test run
      example: the six order-total cases
      job: Confirms behaviour after every step. A red run points at the step just taken.
    - role: Commit
      example: one per green step
      job: A save point you can return to with no thought, and a history that bisects cleanly.
  useWhen:
    - A change request is hard to make because of how the code is shaped. Refactor first, then make the change.
    - You find yourself explaining the same function to every new team member.
    - Code you are about to change has smells and tests that cover it, or tests you can add first.
  avoidWhen:
    - There are no tests and no cheap way to add them. Write characterization tests first, or limit yourself to tool-driven moves the compiler checks.
    - The code is about to be deleted or replaced. Tidying it is waste.
    - The deadline is today and the change is small. Make the change, note the smell, and come back.
  tradeoffs:
    - Small steps feel slow. They are slower than a rewrite that works first time and much faster than one that does not.
    - Refactoring touches code other people are editing. Short-lived branches and small commits keep merge conflicts small.
    - Tests that check how code is structured (mocks of private helpers, assertions on call order) break on every refactoring and make it expensive. Tests that check behaviour survive it.
  lookalikes:
    - name: Rewrite
      how: Replaces the code wholesale and verifies at the end. Behaviour drift is found late and all at once.
    - name: Characterization tests
      how: Tests that record what legacy code does today, so that you have something to refactor against. They come before refactoring when no tests exist.
    - name: Parallel change
      how: The refactoring discipline applied to an interface with callers you cannot change in one commit. Expand, migrate, contract.

## [concept] Refactoring safely

**Change the structure, keep the behaviour, in steps small enough that a red test points at one of them.**

<Term id="refactoring">Refactoring</Term> means changing how code is built without changing what it does. It is done as a series of small named moves, such as Extract Function, Rename Variable, Inline Function and Move Function, with the tests run after each. If a step changes behaviour by mistake, the next test run says so and points at the step you just took.

<Depth level={2}>
The most useful refactoring is done just before a change: make the change easy, then make the easy change. Keep the two in separate commits. A refactoring commit should need no review for behaviour, and a feature commit should be small enough to review for nothing else.

A <Term id="code-smell">code smell</Term> tells you where to start: magic numbers, a long function, a rule written inline where a type should own it, the same condition in three places. The catalogue tells you which move fixes which smell. The tests tell you whether you got it right.
</Depth>

<Depth level={3}>
The names in this lesson come from Martin Fowler's catalogue at refactoring.com, from the second edition of *Refactoring* (2018). Some were renamed from the first edition: Extract Method became Extract Function, Replace Magic Number with Symbolic Constant became Replace Magic Literal, and Rename Function is now part of Change Function Declaration. Steve McConnell's *Code Complete* adds the safety rules this lesson uses: keep a list of steps, change one thing at a time, retest after each, and keep a version to go back to.
</Depth>

## [problem] A pricing function nobody wants to touch

An order-total function works and has six tests. It is sixteen lines, with one-letter names, the bulk rate and shipping threshold as bare numbers, and the gold-tier discount written inline. It has been stable for two years.

<Depth level={2}>
It is not bad code. It is short, it is tested, and anyone can read it in a minute. The smells only matter because a change is coming that touches the discount rule.
</Depth>

<Depth level={3}>
Money is a float here. That is a real problem, but changing the representation is a behaviour change (totals can differ in the last cent), so it does not belong in a refactoring. Note it, and do it later as its own change with its own tests.
</Depth>

## [pain] Then a change request arrives

**Change request:** add a silver tier that gets 2% off.

The developer adds the tier and, while in there, renames the function, moves the rates into a map and names the shipping constants. One commit. CI goes red: an order of exactly 50.00 no longer ships free. The commit has several edits, a feature among them, and nothing says which edit did it.

<Depth level={2}>
The slip is `<` becoming `<=` while the shipping line was being tidied. It reads as the same rule. Found in a diff that also contains a new feature, it takes far longer than it would have alone, because every line is a suspect and the feature legitimately changes totals too.
</Depth>

<Depth level={3}>
`git bisect` cannot help inside one commit. It can only point at commits, so its resolution is exactly the size of your steps.
</Depth>

The order matters. Renames and constants first, because they make everything after easier to read. Extracts next. Moves last, once you can see which data each piece reads. If a step needs more than a minute or two of thought, it is probably two steps.
</Depth>

<Depth level={3}>
Tool-driven refactorings are safer than hand edits because they work on the parsed program, its <Term id="abstract-syntax-tree">abstract syntax tree</Term> and symbol table, rather than on text. A rename changes the symbol and every reference to it, and skips a string or a different variable with the same spelling. Extract Function computes which variables flow in and out. Tools still cannot check a comparison you retyped by hand.
</Depth>

## [walk] Follow the steps

Four steps, each one small, each followed by a test run. Step through them with the numbered buttons.

<Depth level={3}>
<Lang only="go">After each step: `go build ./... && go test ./...`. The build alone catches a missed reference; the tests catch a changed result.</Lang>
<Lang only="python">After each step: `pytest -x`. With no compiler, the tests are the only check that a renamed name was renamed everywhere it is used.</Lang>
<Lang only="typescript">After each step: `tsc --noEmit` and the test runner. The type check catches a missed reference; the tests catch a changed result.</Lang>
<Lang only="rust">After each step: `cargo test`. It builds first, so a missed reference or a borrow problem fails before any test runs.</Lang>
</Depth>

## [again] The silver tier, the second time

The same request, after the refactor. The tier rule lives in one method on the customer, so the feature is two lines there, in a commit of its own. If a test goes red now, the feature did it.

<Depth level={2}>
Not every refactoring pays off on the next change. Refactor the code you are about to change, in the direction the change needs. Tidying code nobody is changing is a cost with no return yet.
</Depth>

<Depth level={3}>
For moves too big for one commit, such as changing a widely used signature, use a <Term id="parallel-change">parallel change</Term>: add the new form beside the old, migrate callers in small commits, then delete the old form. Every commit in between is green and deployable.
</Depth>

### The loop

1. Find the smell nearest to the change you need to make.
2. Pick one move from the catalogue that addresses it.
3. Make the move, with the editor's tool if it has one.
4. Run the tests. Green: commit. Red: revert, do not debug.
5. Repeat until the change is easy, then make it in its own commit.

| Smell | Move from the catalogue |
|---|---|
| Bare numbers with a meaning | Replace Magic Literal |
| Loop body or block that needs a comment | Extract Function |
| Helper used once that adds nothing | Inline Function |
| Rule that reads another type's data | Move Function |
| Name that misleads | Rename Variable, Change Function Declaration |
