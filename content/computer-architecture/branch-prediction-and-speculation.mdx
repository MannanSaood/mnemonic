    - role: Branchless code
      example: masks, conditional moves, SIMD compares
      job: Turns a decision into data, with a fixed cost and nothing to predict.
  useWhen:
    - Hot loops whose branch depends on data with no pattern (filters, comparisons in sorts and searches, parsers on random input).
    - A benchmark that is fast on sorted or synthetic data and slow on production data.
    - Security reviews of code that handles secrets near attacker-controlled indexes.
  avoidWhen:
    - Branches that are predictable (error checks, loop exits, mostly-true conditions). They cost almost nothing; branchless versions can be slower.
    - Branches that skip expensive work. A branchless form does the work every time.

    - Branchless code has a constant cost, a little above a well-predicted branch and far below a mispredicted one.

## [concept] Branch prediction and speculation

**A modern CPU works on many instructions at once in a long pipeline, so it reaches a branch long before it knows which way the branch goes. It does not wait: a <Term id="branch-predictor">branch predictor</Term> guesses, and the core runs ahead on the guess.**

A right guess costs nothing. A wrong one, a <Term id="branch-misprediction">misprediction</Term>, throws away all the work started on the wrong path and refetches, which costs roughly 15 to 20 cycles. So the price of an `if` depends on how predictable its answers are.

<Depth level={2}>
Predictors learn patterns of outcomes per branch. Loop exits, error checks and conditions that are almost always true are predicted nearly perfectly. A branch whose answer depends on random data is right about half the time, and in a tight loop those misses can cost more than all the useful work.
</Depth>

<Depth level={3}>
Running ahead on a guess is <Term id="speculative-execution">speculative execution</Term>. Results are held in the reorder buffer and only made permanent (retired) in program order once every earlier branch is confirmed. On a mispredict, everything younger than the branch is squashed: registers and memory look as if it never ran. Caches, though, are not rolled back.
</Depth>

## [problem] A filter over the nightly export

A risk service sums every order at or above a review threshold. It runs over the nightly export of orders, which comes sorted by amount. The loop is three lines and a benchmark shows it doing about one order per nanosecond.

<Depth level={2}>
The author's picture: the CPU runs one statement after another, so each order costs a compare and maybe an add, whatever the order of the data. The benchmark agrees, because its fixture is the sorted export.
</Depth>

<Depth level={3}>
<Lang only="go">Whether the Go compiler emits a real branch here depends on the shape of the body; with one assignment it may emit a conditional move. Real filters do more in the `if`, and keep the branch.</Lang>
<Lang only="python">In pure Python this loop is interpreter-bound, and the order of the data hardly matters. The service would be written with NumPy, where the same branch effects return.</Lang>
<Lang only="typescript">The amounts are an `Int32Array`, so once V8 optimises the loop it is a tight machine-code loop with a real compare-and-branch per element.</Lang>
<Lang only="rust">In a release build LLVM may if-convert or vectorise this exact loop. A slightly bigger body, or a debug build, keeps the branch.</Lang>
</Depth>

## [pain] The live stream is not sorted

The filter moves to the live order stream, which arrives in random order. The same orders, the same sum, the same code. The batch takes almost four times as long, and CPU profiles point at the `if`.

The marked lines are where it happens. Sorted, the answer is "no" for a long run and then "yes" for a long run, and the predictor is wrong only at the switch. Random, the answer is a coin toss.

<Depth level={2}>
`perf stat -e branches,branch-misses` shows it directly: on the sorted export, almost no misses; on the live stream, about one in four of all branches (half of the `if`s, plus the loop branches that are always right). Each miss flushes the pipeline. The work per order did not change; the waste per order did.
</Depth>

<Depth level={3}>
A <Term id="saturating-counter">2-bit saturating counter</Term> per branch is the classic predictor: it changes its guess only after two wrong answers in a row, so a loop exit costs one miss instead of two. Modern predictors add history: they index tables of counters by the recent pattern of outcomes (gshare, TAGE-style designs), which learns alternating and periodic patterns too. No predictor learns randomness.
</Depth>

## [morph] From one line at a time to guessing ahead

Drag the slider. The block labelled "the CPU" splits into what the core does: the pipeline, the predictor, the fetch that runs ahead on the guess, and the two ways it ends, retire or flush.

Hover a box to see its code.

<Depth level={2}>
The fix is to turn the decision into data. A mask, a multiply by 0 or 1, or a <Term id="conditional-move">conditional move</Term> computes the result of both sides and selects one, with no jump. This is <Term id="branchless-code">branchless code</Term>: a little more work on every element, and nothing to mispredict, so it costs the same in any order.
</Depth>

<Depth level={3}>
Branchless is not always better. On predictable data a branch is cheaper, since the CPU skips the add for free when it guesses right. And a branch that skips real work (a call, a write, a hash) should stay a branch. The rule: remove a branch only when it is hot, data-dependent and unpredictable, and measure with production-like input.
</Depth>

## [walk] Follow the loop's last branch

<Depth level={3}>
The predictor does more than guess the direction. A branch target buffer predicts where taken branches and indirect calls go, and a return stack buffer predicts return addresses. All of them work at fetch time, before the instruction is even decoded, because the pipeline needs the next fetch address every cycle.

## [again] The same live stream, branchless

The same live stream with the branchless loop. The batch takes about the time the sorted export took, and the order of the data stops mattering. `branch-misses` is near zero, because the only branch left is the loop's own.

<Depth level={2}>
The sorted export now runs a little slower than it did with the branch, because the mask is computed for every order. That is the trade: a small constant cost for a large variable one.
</Depth>

<Depth level={3}>
Speculation also explains <Term id="spectre">Spectre</Term> (disclosed in January 2018). An attacker trains a bounds check to predict "in bounds", then passes an out-of-bounds index. The core speculatively reads the secret byte and uses it to index a probe array, loading one cache line. The mispredict is squashed, but the line stays cached, and timing reads of the probe array reveals which one it was. Mitigations include speculation barriers (`lfence` on x86), index masking in compilers and browsers, and process isolation for untrusted code.
</Depth>

## [lens] How each language meets the predictor

The predictor sees machine code, so what matters is how directly each language turns your `if` into a jump, and whether its compiler removes the jump for you.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={3}>
<Lang only="go">Go has no branch hints and no `likely`. Its compiler lays out code using static heuristics (a panic path is assumed unlikely), and profile-guided optimisation, since Go 1.21, mainly drives inlining. Branchless arithmetic on signed integers relies on `>>` being an arithmetic shift, which the Go spec guarantees.</Lang>
<Lang only="python">CPython 3.11 and later specialise bytecodes at run time, which removes some of the interpreter's own type-check branches, but a data-dependent `if` in your loop is still one of many branches per bytecode. Vectorise with NumPy and the branch disappears from your code entirely.</Lang>
<Lang only="typescript">V8 collects type feedback while code runs and optimises for what it has seen. If a hot comparison suddenly sees a new type, the optimised code deoptimises, which costs far more than a mispredict. Keep hot loops monomorphic and on typed arrays.</Lang>
<Lang only="rust">Rust has `#[cold]` to mark unlikely functions, and branch-hint intrinsics on nightly. Parts of the standard library, such as its sorting and binary search, use branchless inner loops where that measured faster.</Lang>
</Depth>

### Measuring it

`perf stat -e branches,branch-misses ./bench` gives the miss rate for a run; `perf record -e branch-misses` finds the branches responsible. Always benchmark with data shaped like production: a sorted or constant fixture hides exactly this cost. Compiler Explorer (godbolt.org) shows whether your `if` became a jump, a conditional move or a vector compare.
