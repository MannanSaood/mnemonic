  roles:
    - role: Sign bit
      example: bit 63 of a float64
      job: 0 for positive, 1 for negative. There is a negative zero, equal to zero.
    - role: Exponent
      example: 11 bits, bias 1023
      job: Picks the power of two, so the same number of significant bits covers tiny and huge values.
    - role: Mantissa (significand)
      example: 52 stored bits plus a hidden leading 1
      job: Holds the significant digits. 53 bits is about 15 to 17 decimal digits; float32's 24 is about 7.
    - role: Rounding
      example: round to nearest, ties to even
      job: Every operation computes the exact result, then rounds it to the nearest representable value.
    - role: Integer minor units or decimal
      example: int64 cents, Decimal
      job: Keeps quantities that must be exact in decimal, such as money, exact.
  useWhen:
    - Measurements and statistics, where the input already has error and relative precision matters (latency, ratios, scores, ML, graphics).
    - Wide ranges, from 10^-300 to 10^300 in a float64.
    - Speed. Float arithmetic is native, vectorised and cheap.
  avoidWhen:
    - Money, quantities with a legal or contractual rounding rule, and anything that must match another system to the cent.
    - Counters and IDs above 2^53 in a double, or above 2^24 in a float32.
    - Equality checks on computed values. Compare with a tolerance suited to the scale instead.
  tradeoffs:
    - float64 has 16 digits where float32 has 7, at twice the memory and bandwidth. It moves errors further out; it does not remove them.
    - Decimal types are exact for decimal fractions but slower, and still round results like 1/3.
    - Integer minor units are fast and exact, but each currency needs its exponent and every percentage needs an explicit rounding rule.
  lookalikes:
    - name: Fixed point
      how: An integer with an agreed scale, like cents or basis points. Exact and fast, with a fixed range.
    - name: Decimal floating point
      how: Base-10 digits with an exponent, like Python's Decimal or IEEE 754 decimal64. 0.1 is exact; 1/3 still rounds.
    - name: Integer overflow
      how: The integer failure mode. Integers are exact until they wrap; floats round from the start.

## [concept] Floating point

**A float stores a number as three fields of bits: a sign, an exponent that picks a power of two, and a mantissa that holds the significant digits. It is scientific notation in binary.**

Only fractions built from powers of two fit exactly. 0.5 and 0.75 do. 0.1 does not: in binary it repeats forever, like 1/3 in decimal, so the float holds the nearest value it can. Every operation then rounds its result again.

<Depth level={2}>
The rules are fixed by <Term id="ieee-754">IEEE 754</Term>, which every mainstream CPU implements. A float64 has 1 sign bit, 11 exponent bits and 52 <Term id="significand">mantissa</Term> bits; a float32 has 1, 8 and 23. Rounding is deterministic: the same operations on the same inputs give the same bits on every machine. Floats are not randomly inexact. They are exactly a different set of numbers from the decimals we write.
</Depth>

<Depth level={3}>
A normal float64 is (−1)^sign × 1.mantissa × 2^(exponent − 1023). The leading 1 is implied, which gives 53 significant bits. The <Term id="exponent-bias">bias</Term> of 1023 keeps the field unsigned, so positive floats order the same way as their bit patterns read as integers. An exponent field of all zeros means zero or a <Term id="subnormal-number">subnormal number</Term>; all ones means infinity or <Term id="nan">NaN</Term>. The distance between neighbouring floats, one <Term id="ulp">ULP</Term>, doubles at every power of two.
</Depth>

## [problem] An invoice service in float64

An invoicing service stores unit prices as floats in dollars. It multiplies by quantity, adds up the lines and applies tax. It shows totals to two decimals, and every invoice looks right.

Reconciliation compares each invoice total with what the payment provider settled.

<Depth level={2}>
The author's picture: a float64 has about 16 significant digits and a price has 2, so there is plenty of precision to spare. Each invoice, printed to two decimals, confirms the picture. The precision is there; what the picture misses is that 0.10 is not one of the values a float can hold.
</Depth>

<Depth level={3}>
<Lang only="go">`float64` is the default for decimal literals in Go, so `UnitPrice: 19.99` compiles without a second thought. `fmt.Sprintf("%.2f", total)` hides every error past the second decimal.</Lang>
<Lang only="python">A literal `19.99` is a `float`, an IEEE 754 double. `f"{total:.2f}"` rounds for display and hides every error past the second decimal.</Lang>
<Lang only="typescript">Every number is a double, so `unitPrice: number` is the only obvious type. `total.toFixed(2)` rounds for display and hides every error past the second decimal.</Lang>
<Lang only="rust">`f64` is the default float type, and `format!("{total:.2}")` rounds for display and hides every error past the second decimal.</Lang>
</Depth>

## [pain] Reconcile to the cent

Finance turns on daily reconciliation. Thousands of invoices a day are flagged as mismatches, though each one looks equal when printed. An invoice with items at $0.10 and $0.20 totals 0.30000000000000004. The settlement says 0.30. `==` says no.

The marked lines are where it happens. Every price is already off by a tiny amount before any arithmetic runs, and the sum and the tax each round again.

<Depth level={2}>
Rounding the total to cents before comparing hides most mismatches, but not all. An amount that should be exactly half a cent can land either side of it, and summing a day's revenue in floats adds up thousands of tiny errors that all lean the same way. Converting with `int(price * 100)` is worse: 4.35 × 100 is 434.99999999999994, which truncates to 434 cents.
</Depth>

<Depth level={3}>
The error grows with the size of the number, not with the count of digits you care about. Near $300,000, neighbouring float32 values are 1/32 of a dollar apart, so adding a cent changes nothing at all. Near $20 trillion, float64 neighbours are about 0.4 cents apart, and every cent you add is stored as three of those steps. Subtracting two close large totals to recover a small amount gives that step size back as the answer: <Term id="catastrophic-cancellation">catastrophic cancellation</Term>.
</Depth>

<Depth level={3}>
IEEE 754 requires +, −, ×, ÷ and square root to be correctly rounded: the result is the exact answer rounded to the nearest representable value, with <Term id="round-to-nearest-even">ties going to the even neighbour</Term>. That is why a float sum is reproducible on one machine and one code path, and why it changes when the order of operations changes. A fused multiply-add (FMA) rounds once instead of twice, so a compiler that fuses `a*b + c` can change the last bit.
</Depth>

## [lens] How each language meets floats

All four languages use the same IEEE 754 hardware. They differ in which exact types they give you and in what the type system stops you from doing.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={3}>
<Lang only="go">Go's untyped constants are exact: `const x = 0.1 + 0.2` is computed with arbitrary precision, then rounded once, so `x == 0.3` is true while the same sum on two `float64` variables is false. `math.Float64bits(x)` shows the bits.</Lang>
<Lang only="python">`(0.1).hex()` gives `'0x1.999999999999ap-4'`, the bits in hexadecimal. `Decimal(0.1)` shows every digit of the stored double. NumPy offers `float32` and `float16` arrays, where the same errors arrive much sooner.</Lang>
<Lang only="typescript">`Math.fround(x)` rounds to the nearest float32, and `Float32Array` stores them. Integers past 2^53 silently lose their last bits, which is why JSON IDs from other systems are often sent as strings.</Lang>
<Lang only="rust">`f32` and `f64` are separate types with no implicit conversion, and `as` casts from float to integer saturate (NaN becomes 0) instead of being undefined behaviour. `x.to_bits()` shows the bits.</Lang>
</Depth>

### Comparing floats

Never use `==` on computed floats. Compare with a tolerance that fits the scale: `abs(a - b) <= rel * max(abs(a), abs(b))` for relative error, plus a small absolute floor near zero. Python has `math.isclose`. Comparing in ULPs (the distance between the bit patterns) is the precise version. NaN is the exception to everything: it is not equal to itself, so `x != x` is a NaN test.
