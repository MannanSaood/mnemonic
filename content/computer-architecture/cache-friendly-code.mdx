  roles:
    - role: Cache line
      example: 64 bytes on x86 and most ARM
      job: The unit of transfer. Every miss moves a whole line, so unused bytes in it are wasted bandwidth.
    - role: L1, L2, L3
      example: 32-48 KiB, 1-2 MiB, tens of MiB
      job: Each level is bigger and slower. Hits cost about 1, 4 and 10-40 ns.
    - role: DRAM
      example: main memory
      job: About 100 ns per miss that reaches it, with high bandwidth for sequential streams.
    - role: Prefetcher
      example: next-line and stride prefetchers
      job: Fetches lines ahead of a regular access pattern, hiding latency. Useless for random or pointer-chasing access.
    - role: Loop order and layout
      example: row order, struct of arrays
      job: The levers you control. Make the inner loop walk consecutive addresses, and put the fields a hot loop reads next to each other.
  useWhen:
    - Hot loops over large arrays, matrices, images, columns of metrics or records.
    - A loop that got far slower when its data grew past a cache size.
    - Data structures you design for heavy reading (indexes, lookup tables, game state, analytics columns).
  avoidWhen:
    - Code that is not hot. Measure first; most code is not limited by cache misses.
    - Splitting records into arrays when most code reads whole records; struct of arrays makes that path slower.
  tradeoffs:
    - Struct of arrays speeds up loops over one field and slows down code that reads whole records.
    - Loop interchange changes the order of floating-point additions, so the last digits of sums can change.
    - Tiling (blocking) helps algorithms that reuse data, such as matrix multiply, at the cost of more complex loops.
  lookalikes:
    - name: TLB misses
      how: Another cache, for address translations. Large strides touch a new page on every read and miss there too.
    - name: False sharing
      how: Two threads writing different variables in one cache line make the line bounce between cores.
    - name: Page cache
      how: The kernel's cache of file pages in RAM, a level below everything in this lesson.

## [concept] Writing cache-friendly code

**The CPU never reads one value from memory. It reads the 64-byte <Term id="cache-line">cache line</Term> around it into a small, fast cache, and a read that misses every cache level waits about a hundred times longer than one that hits.**

So the order in which a loop touches memory decides its speed. Walking consecutive addresses uses every byte of each line it pays for. Jumping around pays for a whole line to use eight bytes of it.

<Depth level={2}>
Two habits of programs make caches work: <Term id="spatial-locality">spatial locality</Term> (using data next to data you just used) and <Term id="temporal-locality">temporal locality</Term> (using the same data again soon). Loop order controls the first. The size of the data a loop touches before it comes back, its <Term id="working-set">working set</Term>, controls the second.
</Depth>

<Depth level={3}>
A typical x86 core has 32-48 KiB of L1 data cache (about 4-5 cycles), 1-2 MiB of L2 (about 12-15 cycles) and a shared L3 of tens of MiB (about 40-70 cycles); DRAM is around 80-100 ns. Exact figures vary by generation, so read them as orders of magnitude. Throughput falls in steps as the working set outgrows each level, the "memory mountain" of CS:APP.
</Depth>

## [problem] A metrics rollup by minute

A monitoring service stores one float64 per host per minute in a flat array, host by host. The dashboard needs a total per minute across the fleet, so the rollup loops over minutes and, for each minute, adds up every host.

With 500 hosts it takes 2 ms. Tests and code review are happy.

<Depth level={2}>
The author's picture: memory is a big array where every read costs the same, so the loop order is a matter of taste. The natural order follows the output, one total per minute. Nothing in the code suggests that the inner loop jumps 11,520 bytes on every read.
</Depth>

<Depth level={3}>
<Lang only="go">The samples are one `[]float64` indexed as `h*minutes+m`, which is row-major: a host's minutes are neighbours. The inner loop varies `h`, the outer index of that layout.</Lang>
<Lang only="python">NumPy arrays are C order (row-major) by default. `samples[:, m]` is a view with a stride of `minutes * 8` bytes, so `.sum()` on it reads one float per cache line.</Lang>
<Lang only="typescript">The samples are one `Float64Array` indexed as `h * minutes + m`, which is row-major: a host's minutes are neighbours. The inner loop varies `h`, the outer index of that layout.</Lang>
<Lang only="rust">The samples are one `&[f64]` indexed as `h * minutes + m`, which is row-major: a host's minutes are neighbours. The inner loop varies `h`, the outer index of that layout, and each index is bounds-checked.</Lang>
</Depth>

## [pain] Forty times the hosts

The fleet grows to 20,000 hosts. The data grows 40 times, to 230 MB. The rollup does not get 40 times slower; it gets 300 times slower, 600 ms per dashboard load.

The marked lines are where it happens. Each read in the inner loop is a whole host row past the last one, so it lands on a different cache line, and the line it lands on was evicted long ago.

<Depth level={2}>
At 500 hosts, one pass down a minute touches 500 lines, 32 KiB, which fits in L1. The next seven minutes are in the same lines, so they hit. At 20,000 hosts a pass touches 1.2 MiB of lines, and by the time the loop returns for the next minute those lines are gone from L1 and L2. Almost every read misses, and each miss fetches 64 bytes to use 8.
</Depth>

<Depth level={3}>
The jump is also 11,520 bytes, almost three 4 KiB pages, so every read lands on a different page and misses the TLB as well. A stride prefetcher can follow a constant stride inside a page, but this stride leaves the page on every read, and its lines still waste seven eighths of the bandwidth.
</Depth>

<Depth level={2}>
The fix is loop interchange: walk hosts in the outer loop and minutes in the inner loop, adding each row into a totals array. Now the inner loop reads consecutive addresses, and the totals, 11 KiB, stay in L1 the whole time. Same reads, same additions, about an eighth of the misses, and the prefetcher can stream the rows.
</Depth>

<Depth level={3}>
When a loop reads one field out of many records, the same idea applies to layout. An array of structs puts every field of a record together, so a loop over prices drags ids and timestamps through the cache too. A <Term id="struct-of-arrays">struct of arrays</Term> keeps all prices together. Column stores (Parquet, Arrow, analytical databases) are this layout at scale. And because the data is in <Term id="row-major-order">row-major order</Term>, the natural fix for a column-first loop is always to make the last index the fastest.
</Depth>

## [walk] Follow one row

One row of samples, followed through the corrected loop. Step through it with the numbered buttons.

<Depth level={3}>
A cache is organised as sets of a few ways. An address splits into an offset within the line (6 bits for 64 bytes), a set index and a tag. Lines whose addresses differ by a multiple of the set count times the line size compete for the same set, which is why strides that are large powers of two can thrash a cache that is mostly empty. The <Term id="hardware-prefetcher">hardware prefetcher</Term> tracks streams of misses and runs ahead of them; it is why a sequential scan reaches memory bandwidth instead of paying full latency per line.
</Depth>

## [again] The same 20,000 hosts, row by row

The same data with the loops swapped. The rollup reads memory front to back, takes about 40 ms, and the dashboard loads well inside its budget. It will keep scaling linearly with the fleet, because the miss rate no longer depends on the number of hosts.

<Depth level={2}>
The totals change in their last digits, because the floats are added in a different order. For a dashboard that does not matter; for anything compared exactly, sum in a fixed order or use integers.
</Depth>

<Depth level={3}>
When both orders are needed, such as a matrix multiply that walks one matrix by rows and the other by columns, interchange alone is not enough. Tiling (blocking) processes small square blocks that fit in L1 or L2, so each block is reused many times while it is cached. Optimised BLAS libraries do this, and more.
</Depth>

## [lens] How each language lays out memory

The cache rules are the same for every language. What differs is whether your data is dense at all, and who decides its layout.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={3}>
<Lang only="go">A struct `{a bool; b int64; c bool}` is 24 bytes in Go because of padding; `{b int64; a, c bool}` is 16. Go never reorders fields for you. Slices of values are dense; maps and slices of pointers are not.</Lang>
<Lang only="python">`array.array('d')` and NumPy arrays store raw doubles; a list of floats stores 8-byte pointers to 24-byte objects. `np.sum(a, axis=0)` and `a.sum(axis=1)` both run at C speed on a C-order array because NumPy orders its inner loop by memory layout.</Lang>
<Lang only="typescript">V8 stores small integers and doubles in arrays specially (packed SMI and double elements) as long as the array stays homogeneous; a single string or hole switches it to generic elements. Typed arrays never change representation.</Lang>
<Lang only="rust">`#[repr(C)]` fixes field order; `#[repr(align(64))]` gives a type its own cache line. Without `repr(C)`, `size_of::<{a: u8, b: u64, c: u8}>()` is 16, because the compiler sorts the fields to cut padding.</Lang>
</Depth>

### Measuring it

Time is the first signal: a loop that slows down far more than its data grew is a cache suspect. On Linux, `perf stat -e cache-references,cache-misses,L1-dcache-load-misses` counts misses for a run, and `perf c2c` finds false sharing. Valgrind's `cachegrind` simulates the caches and reports misses per source line, slowly but exactly.
