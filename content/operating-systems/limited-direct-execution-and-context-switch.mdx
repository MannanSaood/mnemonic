checks:
  overview:
    question: A program runs a loop that never makes a system call. How does the OS get the CPU back?
    options:
      - text: The timer interrupt traps into the kernel every few milliseconds, whatever the program is doing.
        correct: true
        why: Right. The kernel starts the timer at boot. Each tick enters the kernel through the trap table, and the scheduler can then run something else.
      - text: The kernel checks the program between instructions.
        why: No. While the program runs, the kernel is not running at all. It only gets the CPU back through a trap.
      - text: It waits until the program makes its next system call.
        why: That is cooperative scheduling. A program that never makes a call would then keep the CPU until a reboot.
  engineer:
    question: A latency-sensitive proxy shares 4 cores with batch jobs. pidstat -w shows thousands of involuntary context switches a second for the proxy and its p99 is spiky. What is going on?
    options:
      - text: Other runnable threads share its cores, so the timer keeps preempting it and it waits for a slice before it runs again.
        correct: true
        why: Right. Involuntary switches are preemptions. Give the proxy its own cores (cpusets), raise its share, or lower the batch jobs' priority.
      - text: The proxy makes too many system calls, and each one is a context switch.
        why: A system call is a mode switch inside the same thread. It only becomes a context switch if the call blocks, and that counts as voluntary.
      - text: Context switches are free, so the spikes must come from the network.
        why: Each switch costs microseconds directly and more in cold caches, and every preemption adds a wait of up to a slice.
  deep:
    question: During a timer-driven switch from A to B, why are registers saved twice?
    options:
      - text: The hardware saves A's user registers on A's kernel stack at the trap; the kernel's switch routine then saves A's kernel registers in A's task structure.
        correct: true
        why: Right. The first save makes the trap returnable. The second lets the kernel leave A's kernel stack mid-handler and later return to it as if A had just trapped.
      - text: Once for the L1 cache and once for main memory.
        why: No. Both saves go to memory. They hold different registers at different moments.
      - text: The second save is a backup in case the first is lost.
        why: "No. They save different state: user-mode registers at the trap, kernel-mode registers at the switch."

  roles:
    - role: Timer
      example: the local APIC timer on x86
      job: Interrupts the CPU every period, so the kernel runs at least that often.
    - role: Trap table
      example: the interrupt descriptor table on x86
      job: Tells the CPU which kernel handler to run for each trap. Set at boot with a privileged instruction.
    - role: Scheduler
      example: Linux's fair class (EEVDF)
      job: On each trap, decides whether the current task keeps the CPU.
    - role: Switch routine
      example: "Linux's context_switch(), __switch_to()"
      job: Saves one task's kernel registers and stack pointer, loads another's.
    - role: Process or thread
      example: your event loop thread
      job: Runs directly on the CPU in user mode until a trap.
  useWhen:
    - A cooperative runtime (an event loop, asyncio, tokio) runs CPU work that takes more than a few milliseconds. Move it to its own OS thread or process.
    - Latency-sensitive and batch work share cores. Count involuntary switches with pidstat -w or /proc/PID/status.
    - Sizing thread pools. Every thread beyond the core count adds switches, not throughput, for CPU work.
  avoidWhen:
    - The work is short or waits on I/O. A coroutine that awaits often already gives the loop back.
  tradeoffs:
    - A shorter time slice answers waiting tasks sooner but spends more CPU on traps, switches and cold caches.
    - Moving CPU work to another thread or process costs a copy of the input and a hand-off, about tens of microseconds.
    - Cooperative scheduling has no preemption overhead but one stuck task stops everything on its thread.
  lookalikes:
    - name: Mode switch
      how: A system call changes mode within the same task. A context switch changes which task runs.
    - name: Green threads
      how: Goroutines, tokio tasks and coroutines are switched by a user-space runtime, far more cheaply, on top of the kernel's threads.
    - name: Process switch vs thread switch
      how: Switching between threads of one process keeps the page tables and so most TLB entries. Switching processes changes them.

## [concept] Limited direct execution

**The OS runs your program directly on the CPU, and gets the CPU back only when a trap brings it in: a <Term id="system-call">system call</Term>, a device interrupt, or the <Term id="timer-interrupt">timer interrupt</Term>.**

That is <Term id="limited-direct-execution">limited direct execution</Term>. Direct, because your code runs at full speed with no kernel in the way. Limited, because it runs in user mode, and the timer guarantees the kernel a turn every few milliseconds.

<Depth level={2}>
Four parts do the work. The **timer** interrupts the CPU on a fixed period. The **trap table** tells the CPU which kernel handler to run for each kind of trap. The **scheduler**, called from the handler, decides whether the current task keeps the CPU. The **switch routine** saves one task's registers and loads another's. A <Term id="context-switch">context switch</Term> is that last step, and it only happens when the scheduler picks a different task.
</Depth>

<Depth level={3}>
The kernel installs the trap table and starts the timer at boot, while the CPU is still in kernel mode. Both are privileged instructions, so a user program cannot point traps at its own code or stop the timer. Older systems, such as early Mac OS, had no such timer for programs and relied on each program giving up the CPU. On those, an infinite loop meant a reboot.
</Depth>

## [problem] An import handler that parses on the request path

A billing service accepts CSV imports of invoices. The handler reads the body, parses it, validates every row and returns a report. The same process answers `/healthz` for the load balancer.

Imports are capped at 1 MB. A 1 MB file parses in a few tens of milliseconds, and the tests pass.

<Depth level={2}>
The mental model behind it: the OS time-slices everything, so a long request cannot starve the others. That is true of OS threads. It is not true inside a thread. Node's <Term id="event-loop">event loop</Term>, Python's asyncio and tokio's workers schedule your handlers themselves, and they are cooperative: a handler keeps its thread until it awaits.
</Depth>

<Depth level={3}>
The kernel does preempt the event loop thread on its timer. It just has nothing else of yours to run on that thread, so after the slice it resumes the same parse. The kernel shares the CPU between threads. Inside one thread, sharing is up to the runtime.
</Depth>

## [pain] Then a change request arrives

**Change request:** customers may now upload CSV imports of up to 50 MB instead of 1 MB.

The marked line is the only change. The first big import takes several seconds of CPU, and while it runs `/healthz` gets no answer. The load balancer marks the instance unhealthy and restarts it mid-import. Every other request on that instance stalls as well.

<Depth level={2}>
CPU graphs show one core at 100% and the rest idle, so the box does not look overloaded. The thread running the event loop never reaches an `await` during the parse, so the loop never gets to run the `/healthz` handler. For <Lang only="go">Go this does not happen: the runtime preempts the goroutine after 10 ms, and the cost meter stays low.</Lang><Lang only="python">asyncio, the parse holds the loop for its whole length.</Lang><Lang only="typescript">Node, the parse holds the loop for its whole length.</Lang><Lang only="rust">tokio, the parse holds one worker; four concurrent imports on four workers hold them all.</Lang>
</Depth>

<Depth level={3}>
The cost meter shows how long `/healthz` waits while an import runs. It is the parse time, because nothing inside the thread can stop the parse. A runtime with no timer behaves exactly like an OS with no timer interrupt: a task that never yields keeps the CPU.
</Depth>

## [morph] From a time-sliced request to a timer and a trap

Drag the slider. The OS sharing the CPU between requests becomes what it really shares: threads, switched by the kernel when the timer traps. Inside the event loop thread, nothing is switched.

The code moves the parse onto its own OS thread or process, where the kernel's timer does apply.

<Depth level={2}>
<Lang only="go">Go needs no change. Its runtime has a timer of its own: the sysmon thread checks running goroutines and preempts any that has run for 10 ms.</Lang>
<Lang only="python">The parse runs in a `ProcessPoolExecutor`, one process per CPU, each with its own <Term id="gil">GIL</Term>. A thread pool would not help a CPU-bound parse, because the GIL lets one thread run bytecode at a time.</Lang>
<Lang only="typescript">Piscina keeps a pool of `worker_threads`, one fewer than the cores, so the event loop thread always has a core to run on.</Lang>
<Lang only="rust">`spawn_blocking` moves the parse onto tokio's blocking pool, separate OS threads, so the async workers stay free for `/healthz`.</Lang>
</Depth>

<Depth level={3}>
The fix costs a copy of the 50 MB body into the worker, a few milliseconds, and the kernel now switches between the loop thread and the worker. Both are small next to a stalled health check. You could instead yield inside the parse every few thousand rows (`await` a resolved promise, `asyncio.sleep(0)`, `tokio::task::yield_now()`). That is <Term id="cooperative-scheduling">cooperative scheduling</Term> done by hand, and it breaks the day someone adds a loop without a yield.
</Depth>

## [walk] Follow one timer tick

One timer interrupt, from the trap to the thread that runs next. Step through it with the numbered buttons.

<Depth level={3}>
On Linux the tick runs at `CONFIG_HZ`, 100 to 1000 times a second, and tickless kernels skip it on idle CPUs. The scheduler also gets control on a wake-up: when a network interrupt makes a thread runnable, the kernel may preempt the current thread right away if the woken one is owed CPU time. A switch between threads of one process keeps the page tables. A switch between processes loads new ones, and with Meltdown mitigations (KPTI) every trap also switches page tables, which makes each trap dearer.
</Depth>

## [again] 50 MB, the second time

The same import with the parse off the event loop. It takes as long as before, but on a thread the kernel time-slices. `/healthz` answers in milliseconds, the load balancer keeps the instance, and other requests keep flowing.

<Depth level={2}>
Count the switches to see the difference. `/proc/PID/status` shows `voluntary_ctxt_switches` (the thread blocked or yielded) and `nonvoluntary_ctxt_switches` (the timer or a wake-up preempted it). `pidstat -w 1` prints both rates per second.
</Depth>

<Depth level={3}>
A direct switch costs about one to a few microseconds on current hardware. The larger cost is indirect: the incoming thread finds caches and TLB holding the other thread's data. Measurements put that anywhere from a few microseconds to hundreds, depending on the working set. That is why the slice is milliseconds long and not microseconds.
</Depth>

### The time slice trade-off

| Slice | Waiting task waits up to | Switch overhead |
|---|---|---|
| Very short (100 µs) | little, until overhead slows everything | large: tens of percent with cold caches |
| A few ms | a few ms | about 1% |
| Long (50 ms and up) | a whole slice | negligible |

Linux does not use one fixed slice for normal tasks. Its fair scheduler (EEVDF since Linux 6.6) gives each task a base slice of 0.7 ms times one plus log2 of the CPU count, 2.8 ms on 8 CPUs, and picks the next task by how much CPU it is owed. The next lessons show how schedulers choose.
