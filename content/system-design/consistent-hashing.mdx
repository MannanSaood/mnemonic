        // ring.go: a consistent hash ring with virtual nodes
        type Ring struct {
            points []uint32          // sorted positions on the ring
            owner  map[uint32]string // position -> server
            vnodes int
        }

        func NewRing(vnodes int, servers ...string) *Ring {
            r := &Ring{owner: map[uint32]string{}, vnodes: vnodes}
            for _, s := range servers {
                r.Add(s)
            }
            return r
        }

        // Add puts vnodes points for server on the ring. Only keys in the arcs it takes move.
        func (r *Ring) Add(server string) {
            for i := range r.vnodes {
                p := crc32.ChecksumIEEE([]byte(server + "#" + strconv.Itoa(i)))
                r.owner[p] = server
                r.points = append(r.points, p)
            }
            slices.Sort(r.points)
        }

        // Remove takes server's points off. Each of its arcs falls to the next point clockwise.
        func (r *Ring) Remove(server string) {
            r.points = slices.DeleteFunc(r.points, func(p uint32) bool { return r.owner[p] == server })
        }

        // Get returns the owner of the first point at or after hash(key), wrapping at the top.
        func (r *Ring) Get(key string) string {
            h := crc32.ChecksumIEEE([]byte(key))
            i, _ := slices.BinarySearch(r.points, h)
            if i == len(r.points) {
                i = 0
            }
            return r.owner[r.points[i]]
        }

        var ring = NewRing(160, "cache-a:11211", "cache-b:11211", "cache-c:11211", "cache-d:11211")

        func nodeFor(key string) string { return ring.Get(key) }

        // ring.ts: a consistent hash ring with virtual nodes
        import { crc32 } from "node:zlib";

        export class HashRing {
          private points: { pos: number; server: string }[] = []; // sorted by pos

          constructor(private vnodes: number, servers: string[]) {
            servers.forEach((s) => this.add(s));
          }

          add(server: string): void {
            for (let i = 0; i < this.vnodes; i++) this.points.push({ pos: crc32(`${server}#${i}`), server });
            this.points.sort((a, b) => a.pos - b.pos); // only keys in the arcs it takes move
          }

          remove(server: string): void {
            this.points = this.points.filter((p) => p.server !== server); // arcs fall to the next point
          }

          get(key: string): string {
            const h = crc32(key);
            let lo = 0, hi = this.points.length;
            while (lo < hi) {
              const mid = (lo + hi) >>> 1;
              if (this.points[mid].pos < h) lo = mid + 1; else hi = mid;
            }
            return this.points[lo % this.points.length].server; // wrap past the top
          }
        }

      example: a config push, a service registry, gossip
      job: Tells every router which servers are on the ring. Routers that disagree send the same key to different servers.
  useWhen:
    - Spreading cache keys or connections over a set of servers that grows, shrinks and fails.
    - Partitioning data in a store whose nodes come and go, with replicas on the next distinct servers clockwise.
    - Sticky routing in a load balancer, so a client keeps hitting the server that has its state.
  avoidWhen:
    - A fixed number of shards that never changes; plain modulo is simpler.
    - When you need to move data deliberately, shard by shard; fixed hash slots or a lookup table give you that control.
    - Very uneven key popularity. A ring balances keys, not traffic; one hot key still lands on one server.
  tradeoffs:
    - More virtual nodes give a more even spread but a bigger table to store, ship to every router and search.
    - Weights are easy (more points for bigger machines), but each weight change moves keys.

    - name: Rendezvous hashing
      how: Scores every server for each key and picks the highest. Same minimal movement, no ring, but a lookup is O(N).

      how: A few lines of arithmetic and no memory, but buckets are numbered and can only be added or removed at the end.

## [concept] Consistent hashing

**Put servers and keys on the same circle; each key belongs to the next server clockwise, so a server joining or leaving only affects the keys next to it.**

The circle is a <Term id="hash-ring">hash ring</Term>: the output of a hash function with its ends joined. <Term id="consistent-hashing">Consistent hashing</Term> keeps most keys where they are when the fleet changes, which is what a cache fleet or a sharded store needs.

<Depth level={2}>
The ring alone does not balance load. Four servers hashed to four random points split the circle into four random arcs, and one can easily be twice the size of another. Each server therefore places many points, called <Term id="virtual-node">virtual nodes</Term>. Many small arcs per server average out to an even share, and a dead server's arcs fall to many different neighbours.
</Depth>

<Depth level={3}>
Karger and colleagues introduced the idea in 1997 for web caches whose clients each saw a slightly different set of caches. They proved that adding a cache moves only the items that are now closest to its points, with no movement between existing caches, and they gave each cache about log(C) points to keep the load balanced. Their construction maps an item to the closest cache point; most libraries today take the next point clockwise, which behaves the same way.
</Depth>

## [problem] A cache fleet behind hash % N

A web app keeps sessions and rendered fragments in four memcached servers. The client picks a server by hashing the key and taking it modulo the number of servers. Every key lands on one server, every app server agrees which, and the load is even. It has worked for two years.

<Depth level={2}>
Modulo is a fine choice while N never changes. Every key's server depends on N, so the day N changes is the day the scheme shows its cost.
</Depth>

<Depth level={3}>
Memcached servers do not talk to each other. Where a key lives is decided entirely by the client library, so every app server must run the same function over the same server list in the same order.
</Depth>

## [pain] Then a change request arrives

**Change request:** the sale starts Friday. Add a fifth cache server so the fleet has room for the extra traffic.

The marked line adds `cache-e` to the list. A key stays on its server only when `hash % 4` equals `hash % 5`, which holds for 4 out of every 20 hash values. About 80% of keys now point at a server that does not have them. The cache is effectively cold, and every one of those misses goes to the database on the busiest day of the year.

<Depth level={2}>
A crash is no better. Remove one server from the list and every server after it shifts down one place, so most keys move again. The usual workaround is to add servers only at night, warm them slowly, or never remove a dead one from the list. All of them are signs that the placement function is wrong.
</Depth>

<Depth level={3}>
In general, going from N to N+1 servers keeps a key only when its hash gives the same remainder for both, so about N/(N+1) of the keys move. The more servers you have, the worse each change gets.
</Depth>

## [morph] Bend the hash space into a ring

Drag the slider. The modulo disappears: the router hashes each server many times onto a ring and looks up the first point clockwise from the key.

Hover a box in the diagram to see its code.

<Depth level={2}>
Pick the number of points per server once, before data lives on the ring, because changing it moves keys too. 100 to 200 points per server is common. Give bigger machines more points to give them a bigger share.
</Depth>

<Depth level={3}>
The lookup is a binary search over all points: O(log(N × V)) for N servers with V points each. With 50 servers and 200 points that is 10,000 sorted integers, about 14 comparisons. Every router holds its own copy of the ring, so the ring must be built the same way everywhere: same hash, same point names, same server list.
</Depth>

## [walk] Follow one key

One key looked up, then the ring changing under it twice. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`slices.BinarySearch` returns the position where the value would be inserted, which is exactly the first point at or after the key's hash. When it returns `len(points)`, the key is past the last point and wraps to index 0.</Lang>
<Lang only="python">`uhashring` keeps the sorted points and uses `bisect` for the lookup. Its default placement is not the same as libmemcached's ketama; pass `hash_fn="ketama"` if other clients must agree with it.</Lang>
<Lang only="typescript">`zlib.crc32` returns an unsigned 32-bit number, so plain numeric comparison works. `>>> 1` keeps the midpoint an integer without risk of overflow.</Lang>
<Lang only="rust">`HashRing::get` takes any `Hash` value, so the key is hashed with the same hasher as the virtual nodes. Each `VNode` value is a distinct point because its `replica` field differs.</Lang>
</Depth>

## [again] The same change again

The same fifth server with the ring: about a fifth of the keys move, all of them to `cache-e`, and none move between the four old servers. The database sees one server's worth of misses instead of four fifths of the cache. The test above checks both halves of that promise.

<Depth level={2}>
The moved keys are still misses. For a cache, warm the new server or add it at a quiet hour. For a store, moving keys means copying data before the new node takes over its arcs.
</Depth>

<Depth level={3}>
Replication uses the same walk. To keep three copies, take the first three distinct physical servers clockwise from the key, skipping further points of a server you already have. The Dynamo paper (2007) and Cassandra's `num_tokens` both build on this ring with many points per node.
</Depth>

## [play] Grow and break a cache fleet

1,000 keys over four cache servers. Every change you make is applied to both schemes at once, hash % N and the ring, so you can see how many keys each one moves. Change the points per server to see how even the ring is.

## [lens] How each language does it

None of the four standard libraries has a hash ring. Each has a fast hash and a sorted search, and the ring is about thirty lines; libraries add virtual nodes, weights and ketama compatibility.

<Depth level={2}>
Whatever the language, every client must build an identical ring. If one client uses a different hash or point naming, it sends keys to the wrong servers and the cache quietly stops hitting.
</Depth>

### Other ways to get minimal movement

<Term id="rendezvous-hashing">Rendezvous hashing</Term> (Thaler and Ravishankar) needs no ring: score every server with hash(key, server) and pick the highest. <Term id="jump-consistent-hash">Jump consistent hash</Term> (Lamping and Veach, 2014) needs no memory at all, but buckets are numbered, so you can only add or remove the last one. Redis Cluster uses fixed <Term id="hash-slot">hash slots</Term>, CRC16(key) mod 16384, and moves whole slots between nodes when the cluster changes.
