      - text: Leaky bucket
        why: The leaky bucket queues a burst and lets it out at the steady rate. It smooths bursts instead of passing them on.
      - text: Sliding window log
        why: The log allows at most r in any trailing window, whatever happened before.
  engineer:
    question: A fixed window limiter allows 100 requests per minute. How many can a client get through in two seconds?
    options:
      - text: "200"
        correct: true
        why: Right. 100 in the last second of one minute and 100 in the first second of the next. Each window is within its limit.
      - text: "100"
        why: That would be true of a sliding window. The fixed window forgets everything at the boundary.
      - text: About 3
        why: That is the average rate. Fixed windows say nothing about how requests spread inside a window.
  deep:
    question: Two gateways share a Redis counter. Each reads tokens = 1, decides to allow, and writes tokens = 0. What fixes it?
    options:
      - text: Do the read, the decision and the write in one atomic step in Redis, such as a Lua script.
        correct: true
        why: Right. Redis runs a script to the end before any other command, so the second gateway sees the first one's write.
      - text: Put a mutex around the limiter code in each gateway.
        why: A mutex only orders threads inside one process. The two gateways are different processes.
      - text: Use a sliding window log instead of a token bucket.
        why: Any algorithm loses updates if it reads, decides and writes as separate commands from different processes.

    - role: Limiter state
      example: tokens and last time, a count per window, or a log of times
      job: What the algorithm remembers per key. Its size decides memory per client.
    - role: Shared store
      example: Redis, with a Lua script per decision
      job: Lets every gateway enforce one limit. Updates must be atomic.
    - role: Middleware
      example: { go: "an http.Handler wrapper", python: "an ASGI middleware", typescript: "Express middleware", rust: "an axum middleware fn" }
      job: Picks the key (API key, user, IP), asks the limiter, and answers 429 with Retry-After.
    - role: Client back-off
      example: honour Retry-After, back off with jitter
      job: Turns refusals into fewer requests instead of a retry storm.
  useWhen:
    - Token bucket for public APIs, where clients are bursty and you want a steady average with some slack.
    - Leaky bucket or GCRA when the thing behind the limiter needs a smooth rate, and callers can wait.
    - Sliding window counter as a cheap, close-to-exact default for per-key limits in a shared store.
    - Sliding window log when exactness matters and limits are small.
  avoidWhen:
    - A fixed window in front of a backend that cannot take twice the limit in a moment.
    - A per-process limiter when the limit is meant per customer across a fleet.
    - Rate limiting as a security control on its own; it slows abuse, it does not authenticate.
  tradeoffs:
    - Every shared-store limiter adds a network round trip per request. Local limiters are free but multiply the limit by the number of gateways.
    - When the store is down you choose to fail open (risk overload) or closed (refuse everyone). Most APIs fail open.
    - A burst allowance is kindness to clients and a spike for the backend. Size it to what the backend can absorb.
    - The sliding counter assumes requests were spread evenly over the last window, so it under-admits right after a burst.
  lookalikes:
    - name: Load shedding
      how: Refuses work because the server is overloaded right now, whoever sent it. A rate limit refuses because one client exceeded its share.
    - name: Concurrency limit
      how: Caps requests in flight, not requests per second. A slow backend lowers the throughput automatically.
    - name: Backpressure
      how: A full queue slows the producer down instead of refusing it.
    - name: Quota
      how: A budget per day or month, usually billed or enforced by a counter that never refills within the period.

## [concept] Rate limiter algorithms

**A rate limiter keeps per-client state and refuses a request when that state says the client is over its limit. The algorithms differ in what state they keep, and so in what they do with bursts.**

A <Term id="token-bucket">token bucket</Term> lets a quiet client burst. A <Term id="leaky-bucket">leaky bucket</Term> smooths bursts into a steady flow. A <Term id="fixed-window-counter">fixed window counter</Term> counts per clock interval and forgets at each boundary. The <Term id="sliding-window-log">sliding window log</Term> and the <Term id="sliding-window-counter">sliding window counter</Term> look back over the last interval from every request.

<Depth level={2}>
They all agree on steady traffic under the limit. Choose by bursts: can the service behind the limiter take a burst of b at once (token bucket), must it see a steady rate (leaky bucket), or must no interval ever exceed r (sliding log)? A refused request gets HTTP 429 Too Many Requests and a Retry-After header saying when to come back.
</Depth>

<Depth level={3}>
None of these needs a timer per client. The token bucket stores tokens and a timestamp and computes the refill when the next request arrives, a <Term id="lazy-refill">lazy refill</Term>. <Term id="gcra">GCRA</Term> goes further and stores a single timestamp: the earliest time the next request is allowed.
</Depth>

## [problem] Ten requests per second, per clock second

A search API sits behind gateways that share a Redis. Each request increments a counter named after the API key and the current second, the first increment sets a two-second expiry, and anything past 10 gets a 429. It is the counter pattern from the Redis `INCR` documentation, and it is easy to reason about.

<Depth level={2}>
It is cheap: one key per client per second, one round trip. The increment is atomic, so two gateways never lose a count. Its weakness is the boundary. The count for second 41 knows nothing about second 40.
</Depth>

<Depth level={3}>
`INCR` and `EXPIRE` are two commands here. If a gateway dies between them, the key never expires. With one key per second that only leaks memory; with one key per client it would block that client forever. A script or `SET key 0 EX 2 NX` before the increment avoids it.
</Depth>

## [pain] Then a change request arrives

**Change request:** search falls over under spikes. Make 10 requests per second hold for any one-second span, and still let a client that has been quiet send a short burst.

The search cluster logs 20 requests from one key inside 200 ms, many times a day: 10 at the end of one clock second and 10 at the start of the next. The marked line is the usual first fix, halving the limit. Now clients who spread their requests evenly get refused at 6 per second, and a boundary still lets 10 through in a fifth of a second.

<Depth level={2}>
A fixed window promises at most r per clock window, not per second. Any client can get 2r through around a boundary, and retrying clients do it without trying: they get a 429, wait for Retry-After, and all come back at the start of the next window.
</Depth>

<Depth level={3}>
Halving the limit cannot fix this, because the problem is not the number. The state, one count per clock second, cannot express "how many in the last second". The algorithm has to change.
</Depth>

## [morph] Keep a bucket instead of a count

Drag the slider. The per-second counter becomes a token bucket: two numbers per key, refilled lazily and updated by a script that runs inside Redis.

Hover a box in the diagram to see its code.

<Depth level={2}>
Two knobs: the rate r is the long-run average, the burst b is how much a quiet client can spend at once. In any second a client gets at most b + r through, and at most r per second over the long run. Set b from what the backend can absorb, not from what clients want.
</Depth>

<Depth level={3}>
Redis runs a script to the end before it runs any other command, so read, refill, spend and write are one step even with many gateways. The script reads the clock with `TIME`, which is allowed because Redis replicates a script's effects, not the script; using Redis's clock means gateways with skewed clocks still agree.
</Depth>

## [again] The same spikes again

The same client sends 10 at the end of a second and 10 at the start of the next. With a full bucket of 20 it gets all 20, once; after that it gets 10 per second, however it times them. A client that sends evenly at 10 per second is never refused. The test fires 200 requests at once and expects the burst, not more.

<Depth level={2}>
If the backend cannot take 20 at once, lower b, or use a leaky bucket and make callers wait instead. Return Retry-After on every 429, and make your own clients back off with jitter, or the refusals come straight back.
</Depth>

<Depth level={3}>
When Redis is unreachable the middleware above fails open: it lets requests through rather than refuse everyone. For an expensive or abusable endpoint, failing closed or falling back to a per-gateway limiter may be the better choice.
</Depth>

### Five algorithms side by side

- **Token bucket.** Stores tokens and a time. Lets a burst of b through at once; at most b + r in any one window.
- **Leaky bucket.** Stores a queue, or the next free time. Delays a burst to the drain rate, so the output is exact.
- **Fixed window.** Stores one count per window. Up to 2r can pass around a boundary.
- **Sliding log.** Stores a time per admitted request. Never more than r in any window, at the cost of memory.
- **Sliding counter.** Stores two counts. Close to r; it under-admits just after a burst because it assumes the last window was evenly spread.

nginx's `limit_req` uses the leaky bucket method: `burst` is the queue, and `nodelay` passes queued requests on at once while still counting them. By default it answers 503, not 429, unless you set `limit_req_status`.
