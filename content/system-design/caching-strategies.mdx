  overview:
    question: What does a cache give up in exchange for speed?
    options:
      - text: Freshness. It can answer with a copy that is older than the source.
        correct: true
        why: Right. Every caching choice is about how old an answer may be, and how you find out the source changed.
      - text: Durability. Data in the cache is lost when it restarts.
        why: Only for a write-back cache, where the cache holds writes that have not reached the database. A read cache loses nothing the database does not still have.
      - text: Nothing, if the hit ratio is high enough.
        why: A high hit ratio says nothing about whether the hits are current.
  engineer:
    question: A popular key expires every 5 seconds, and each time the database briefly takes dozens of identical queries. What fixes the spikes?
    options:
      - text: Let concurrent misses share one load (single-flight), or refresh the entry just before it expires.
        correct: true
        why: Right. The spike is every reader that arrives during the load starting its own. Coalescing makes them wait for one; early refresh means nobody misses.
      - text: Raise the TTL to one minute.
        why: The spikes become rarer but stay the same size, and the prices stay stale for longer.
      - text: Give the cache more memory.
        why: The key is not being evicted for lack of space. It expires on purpose.
  deep:
    question: The app reads through a cache-aside path and deletes the key after every price update. Yet sometimes the old price sticks for a whole TTL. How?
    options:
      - text: A reader loaded the old row before the update, and stored it in the cache after the delete.
        correct: true
        why: Right. The delete ran while the cache was empty, so it removed nothing, and the late fill put the old value back. Leases or versioned fills refuse such a fill.
      - text: The delete reached Redis before the database committed.
        why: That ordering can cause it too, which is why you delete after the commit. But the code here deletes after the update, and the race still happens.
      - text: Redis evicted the new value under memory pressure.
        why: Eviction removes values. It cannot bring back an older one.

reference:
  roles:
    - role: Cache
      example: Redis, memcached, or an in-process map
      job: Holds copies close to the reader, each with a TTL and a size limit.
    - role: Loader
      example: { go: "singleflight.Group.Do", python: "one asyncio.Task per key", typescript: "a Map of promises", rust: "moka try_get_with" }
      job: Fetches a missing entry from the source once, however many readers are waiting.
    - role: Invalidation
      example: delete the key after the database commit
      job: Tells the cache the source changed, so the next read loads the truth.
    - role: Lease or version
      example: a token checked by the fill script
      job: Refuses a fill that read the source before the latest write.
  useWhen:
    - Data read far more often than it changes, where a slightly old answer is acceptable for a bounded time.
    - Expensive reads (joins, remote calls, rendering) that many users ask for.
    - Shielding a database from read load, as long as you know what happens when the cache is empty.
  avoidWhen:
    - Reads that must reflect the latest write, such as a balance before a payment. Read the source.
    - Data that changes as often as it is read; the cache only adds misses and invalidations.
    - When a cold cache would overload the database and you have no plan to warm it or shed load.
  tradeoffs:
    - A long TTL means few misses and long staleness; a short TTL means fresh data and frequent misses. Invalidation on write lets you keep a long TTL as a backstop.
    - Delete on write is safer than set on write. Two writers that set can land in the wrong order; two deletes cannot.
    - Write-through keeps reads after writes fast, but writes pay for the cache too, and cached data nobody reads wastes memory.
    - Once the database is sized for a 95% hit ratio, the cache is part of your capacity. Losing it is an outage, not a slowdown.
  lookalikes:
    - name: Memoisation
      how: Caches a pure function's results in one process. No invalidation problem, because the inputs fully decide the output.
    - name: CDN or HTTP cache
      how: The same trade-offs one layer out, controlled by Cache-Control headers instead of code.
    - name: Read replica
      how: Another copy of the data that lags the primary, kept current by replication instead of by the application.
    - name: Materialised view
      how: A precomputed query result that the database keeps up to date for you.

## [concept] Caching: where, how, and how it goes stale

**A cache keeps a copy of data close to the reader. It answers fast because it does not ask the source, and that is also why it can be wrong.**

A cache can live in the browser, a CDN, a reverse proxy, the application's memory, a shared store such as Redis, or the database's own buffer pool. Wherever it is, it needs two answers: how entries get in, and how they leave when the source changes. Entries leave by <Term id="time-to-live">TTL</Term>, by eviction when memory runs out, or by invalidation.

<Depth level={2}>
Getting in: with <Term id="cache-aside">cache-aside</Term> the application loads on a miss and fills the cache; with a <Term id="read-through">read-through</Term> cache the cache calls a loader you give it. Writing: with <Term id="write-through">write-through</Term> every write updates the cache too; with <Term id="write-back">write-back</Term> writes land in the cache and reach the database later. The most common setup is cache-aside reads, database writes, and deleting the key after each write.
</Depth>

<Depth level={3}>
A hot key fails in two ways. When it expires, every reader during the load misses at once, a <Term id="cache-stampede">cache stampede</Term>. And when a write lands while a refill is in flight, the refill can store the value it read before the write. <Term id="single-flight">Single-flight</Term> loading and <Term id="early-refresh">early refresh</Term> answer the first; a <Term id="cache-lease">lease</Term> or a version check answers the second.
</Depth>

## [problem] Product prices in Redis for an hour

The product page reads each price through Redis. On a miss it reads the database and stores the price for an hour. Price changes are rare and nobody minds if one takes a while to show. The hit ratio is 99.9% and the database is quiet.

<Depth level={2}>
The hour is doing two jobs: it keeps the database quiet, and it is the only way a price change ever reaches the page. Nothing deletes the key when a price changes.
</Depth>

<Depth level={3}>
The database is now sized for that hit ratio. If Redis were flushed or restarted, every page view would go to the database at once, about a thousand times its usual load for this table.
</Depth>

## [pain] Then a change request arrives

**Change request:** flash sales start next week. Price changes must show on product pages within seconds, not within the hour.

The marked line drops the TTL to 5 seconds. Prices now update within 5 seconds, mostly. But the database graph turns into a comb. Every 5 seconds each popular price expires, and for the few hundred milliseconds it takes to load it again, every page view misses and queries the database for the same row. At 200 views a second and a 300 ms load, that is 60 queries per product per expiry.

<Depth level={2}>
The hit ratio still looks fine, above 90%, because the misses are bunched into short windows. Averages hide stampedes; look at queries per second per key. And a price changed a second after a refill is still stale for almost 5 seconds.
</Depth>

<Depth level={3}>
Shortening the TTL trades staleness for load linearly: halve the TTL, double the misses. Only invalidation on write breaks that trade, by telling the cache exactly when the source changed.
</Depth>

## [morph] Invalidate on write, load once, and refuse late fills

Drag the slider. The TTL goes back to a long backstop, the price update deletes the key, misses share one load per key, and the load holds a lease so that a fill which lost a race with a write is refused.

Hover a box in the diagram to see its code.

<Depth level={2}>
Delete after the database commit, never before: deleting first lets a reader refill the old row before the commit lands. Delete rather than set, so two writers racing cannot leave the older value. Keep a TTL anyway, as the backstop for a delete that never arrives.
</Depth>

<Depth level={3}>
The lease is the trick from the 2013 NSDI paper on scaling memcache: a miss hands out a token, a delete revokes it, and a fill with a revoked token is ignored. Redis has no leases built in, so the code builds one from a `SET NX` key and a fill script that checks it. The same lease can also stop a stampede across processes: a reader that sees someone else's lease waits briefly and retries instead of loading.
</Depth>

## [again] The same flash sale again

Prices change and the next page view shows the new one, because the write deleted the key. Each expiry of a hot price costs one database query per process, not sixty. A refill that read the old price just before a change is refused. The test above starts a slow refill, updates the price in the middle of it, and checks that the cache answers with the new price.

<Depth level={2}>
Measure per key, not on average: misses per second, loads per second, and the age of what you serve. An alert on the age of served prices catches a stuck entry that a hit ratio never will.
</Depth>

<Depth level={3}>
If you can afford a background job, refresh hot keys before they expire instead. Probabilistic early expiration (XFetch) does it without a job: each reader recomputes early with a probability that rises as expiry nears and with how long the load takes, so one reader usually refreshes before anyone misses.
</Depth>

## [lens] How each language does it

Each language has an in-process way to coalesce loads and an in-process cache. None of them helps across processes; that is the shared cache's job, and the lease lives there.

### Where the race comes from

The stale fill needs three steps in one order: a reader misses and reads the old row; a writer updates the row and deletes the key, which is not there; the reader stores the old row. Each step is correct alone. Leases, version numbers stored with the value, or a short TTL as a backstop each shorten or close the window; nothing but checking at fill time closes it completely.
