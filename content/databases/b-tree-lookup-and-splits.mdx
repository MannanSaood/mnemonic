      example: the top of orders_pkey
      job: The single entry point. Its separators split the whole key range into a few hundred children.
    - role: Internal page
      example: the level below the root
      job: Holds separator keys and child page numbers. Routes a search, holds no rows.
    - role: Leaf page
      example: leaf 402
      job: Holds the sorted index entries (key and row pointer), and links to its right neighbour for range scans.
    - role: Separator key
      example: the first key of a new right page
      job: Copied into the parent on a split, so a search knows which child covers a key.
  useWhen:
    - Equality and range lookups on a key, sorted output, uniqueness checks. That is almost every primary key and most secondary indexes.
    - Primary keys that grow over time (identity columns, UUIDv7, timestamps first), which keep inserts at the right edge.
  avoidWhen:
    - A random primary key on a write-heavy table larger than memory. Make the key time-ordered, or keep a random public id in a secondary unique index.
    - Write-mostly data that is rarely read by key, where an LSM tree or an append-only log costs far less per write.
  tradeoffs:
    - Every index is one more tree each insert has to descend and maybe split.
    - A lower fillfactor leaves room for inserts in the middle of the key range and makes the index bigger.
    - Time-ordered ids show creation time to anyone who sees them, and the right edge is one hot page under heavy concurrent inserts.
  lookalikes:
    - name: B-tree (without the plus)
      how: Stores entries in internal nodes too. Database "B-tree" indexes are B+-trees in practice; PostgreSQL's nbtree keeps entries in the leaves only.
    - name: LSM tree
      how: Buffers writes in memory and writes sorted runs, so inserts never split pages. Reads may check several runs.
    - name: Hash index
      how: Equality lookups only, no ranges and no sort order.

## [concept] B+-trees: lookup and splits

**An index is a sorted tree of pages, hundreds of entries wide and only three or four levels deep. A lookup reads one page per level. An insert goes to the one leaf where its key sorts, and splits that page when it is full.**

A <Term id="b-plus-tree">B+-tree</Term> is built from fixed-size <Term id="database-page">pages</Term>, 8 KB in PostgreSQL. Leaf pages hold the index entries in key order: the key and a pointer to the row. Internal pages above them hold only <Term id="separator-key">separator keys</Term> and child page numbers. Each page has hundreds of children, a high <Term id="fan-out">fan-out</Term>, so the tree is very shallow.

<Depth level={2}>
Count it once. A bigint entry in a PostgreSQL index takes about 20 bytes with its line pointer, so a page holds roughly 400, and about 366 when filled to 90%. A root with 366 leaves below it covers 134 thousand rows. Three levels cover 49 million, and four levels cover 18 billion. The root and the second level are touched by every lookup and stay in the buffer cache, so a lookup costs one or two page reads that might miss.
</Depth>

<Depth level={3}>
PostgreSQL's B-tree (nbtree) follows Lehman and Yao: every page has a right-link to its sibling and a high key that bounds what it may hold. A reader that arrives at a page just after a concurrent split sees a key above the high key and follows the right-link, so searches never lock the whole path. Over 99% of the pages in a typical index are leaves, which is why the internal levels fit in memory so easily.
</Depth>

## [problem] Orders with random UUIDs

An order service gives each order a UUID primary key, generated in the application with version 4: 122 random bits. It is a sensible choice. Ids can be made before the insert, they do not leak how many orders exist, and they never collide across services.

Read the code once. Nothing about it looks expensive. The INSERT touches one row and the primary key index.

<Depth level={2}>
The index is the part to watch. Every row adds one entry to orders_pkey, and the entry has to go into the leaf page where its key sorts. A random key sorts to a random leaf. While the whole index fits in memory, that is invisible: every leaf is already cached.
</Depth>

<Depth level={3}>
A random insert also leaves pages fuller in some places than others. With random keys, B-tree leaves settle at about 69% full on average (ln 2, a classic result), because every page that splits starts as two half-full pages and fills up again slowly.
</Depth>

## [pain] Then a change request arrives

**Change request:** backfill 300 million historical orders into the orders table while it keeps taking live traffic.

The backfill starts fast and slows down hour by hour. Live checkouts slow down with it. Selects by id are still fast. The marked line is the fix someone proposes: leave 30% free space in each index page, so fewer inserts cause a split.

<Depth level={2}>
The fillfactor helps a little with splits and does nothing about the real cost. Once orders_pkey is bigger than memory, each random key needs a leaf that was evicted long ago. Every insert reads a page from disk, dirties it, and pushes another useful page out of the cache. A lower fillfactor makes the index bigger, so even fewer leaves fit in memory.
</Depth>

<Depth level={3}>
Each split also writes two pages and updates the parent, and after a checkpoint PostgreSQL logs the full image of every page the first time it is modified (full_page_writes). Random keys modify many different pages per checkpoint, so they also multiply the WAL volume, which the replicas have to replay.
</Depth>

## [morph] Let new keys land in one place

Drag the slider. The flat list turns into a tree of pages, and the new ids find the right edge.

The fix is the key, not the index. A <Term id="uuidv7">UUIDv7</Term> starts with a 48-bit millisecond timestamp and ends with random bits. It is still a UUID, still made in the application, and it sorts by creation time. Every new key is larger than the ones before it, so every insert goes to the rightmost leaf, which is always in memory.

<Depth level={2}>
A bigint identity column has the same effect. Pick UUIDv7 when ids are created outside the database or must not be guessable in sequence. The random bits after the timestamp still keep ids from different servers unique, and keys made in the same millisecond on different servers land on the same one or two pages.
</Depth>

<Depth level={3}>
Ascending keys also change how a page splits. A textbook B+-tree splits a full page in half, which with ascending keys would leave every left page half empty forever. PostgreSQL fills leaf pages to the <Term id="fillfactor">fillfactor</Term> when it extends the index at the right (90% by default), and InnoDB leaves sequentially filled pages about 15/16 full. PostgreSQL also remembers the rightmost leaf and tries it first for the next insert, skipping the descent.
</Depth>

## [walk] Follow one insert down the tree

One random insert, then one time-ordered insert. Use the numbered buttons.

<Depth level={2}>
A <Term id="page-split">page split</Term> is the only way a B+-tree grows sideways, and a root split is the only way it grows taller. That is why every leaf is always at the same depth and every lookup costs the same number of pages.
</Depth>

<Depth level={3}>
PostgreSQL never merges half-empty pages. VACUUM can remove a leaf only once it is completely empty, and never the rightmost page of a level. An index that had many rows deleted from the middle of its key range keeps its size until a REINDEX rebuilds it.
</Depth>

## [again] The same request, with the database making the id

On PostgreSQL 18 the database can generate the id itself with `uuidv7()`. The column default changes once, and inserts read the new id back with `RETURNING id`. The backfill keeps its original ids in their original order, so it should also insert in id order to keep appending at the right edge.

<Depth level={2}>
If the old ids are UUIDv4 and must stay, the backfill can still be cheap: load the rows sorted by id with COPY into a table without the index, then build the index once. CREATE INDEX sorts the entries and writes the pages bottom-up, full to the fillfactor, without a single split.
</Depth>

<Depth level={3}>
UUIDv7 ids have millisecond resolution. Ids generated in the same millisecond by different processes interleave in the low random bits, so their inserts may touch a couple of pages near the right edge. PostgreSQL's `uuidv7()` also puts sub-millisecond timestamp bits after the millisecond, so ids made close together still sort in creation order.
</Depth>

Two indexes take the same number of inserts. Pick a key type for each, insert, and watch which pages each insert writes. The tree is shrunk to 8 keys per page so splits show up quickly.

## [lens] How each language makes a time-ordered id

The index does not care which language made the key, only how it sorts. Each language has a standard random UUID generator and, recently, a UUIDv7 one. What differs is where the v7 function lives and how the driver sends the value.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Send ids as the uuid type, never as text. A uuid key is 16 bytes; the same id as text is 36 characters plus a header, so fewer entries fit per page and the tree is wider and sometimes a level taller.
</Depth>

<Depth level={3}>
In-memory B-trees exist in every language's ecosystem as ordered maps: Rust's `std::collections::BTreeMap` and Go's `github.com/google/btree`. They use small nodes tuned for CPU caches instead of 8 KB disk pages, but split and search the same way.
</Depth>

### What the tree costs in pages

A point lookup reads one page per level. A range scan descends once and then follows the leaf chain sideways, one page per few hundred entries. An insert reads the same path as a lookup and writes one leaf, plus two pages and a parent on a split. Whether those pages are already in memory depends on where the keys land, which is the whole difference between a random and a time-ordered key.
