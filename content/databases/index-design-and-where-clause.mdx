reference:
  roles:
    - role: Access predicate
      example: tenant_id = $1 AND created_at >= $2 on (tenant_id, created_at)
      job: Sets where the index scan starts and where it stops.
    - role: Index filter predicate
      example: tenant_id = 7 on (created_at, tenant_id)
      job: Checked on each index entry inside the scanned range. Saves table fetches, not index reads.
    - role: Table filter
      example: total_cents > 500, or any column inside a function
      job: Checked after fetching the row. The index does nothing for it.
    - role: Planner
      example: PostgreSQL's cost-based optimiser
      job: Compares the index path with a sequential scan and picks the cheaper one, using statistics.
  useWhen:
    - Order columns as equality first, then the one range or sort column.
    - Put the column every query of a feature filters on (tenant_id, account_id) first, and share the index between those queries.
    - Write conditions on the bare column (a half-open range instead of date(col) =), or index the expression itself.
  avoidWhen:
    - One index per column, hoping the planner combines them. It can, but a composite index in the right order reads far fewer entries.
    - Indexes for conditions that match a large share of the table. The planner reads the table instead and the index only slows writes.
  tradeoffs:
    - Every index is updated by every insert and by updates to its columns. More indexes, slower writes.
    - A column order that suits one query can be useless to another. Fewer, well-ordered indexes beat one index per query shape.
    - Expression indexes only help queries that use exactly the same expression.
  lookalikes:
    - name: Covering index
      how: Adds the selected columns to the index so the table is never read. That is the next lesson.
    - name: Partial index
      how: Indexes only the rows matching a condition, such as status = 'open'. Smaller, and only used by queries that imply the same condition.
    - name: Bitmap index scan
      how: PostgreSQL can read several indexes, combine their matches as bitmaps, and fetch rows in table order. Useful when no single index fits.

## [concept] Designing indexes for WHERE

**A composite index is one list sorted by its first column, then by its second within each first-column value, and so on. A query can jump into that list and read a contiguous stretch only for equality on the leading columns plus one range. Everything else is checked entry by entry.**

A <Term id="composite-index">composite index</Term> on (tenant_id, created_at) keeps all of tenant 7's entries together, in date order. A condition that pins tenant_id and gives a date range describes one contiguous stretch of that list. The database seeks to its start, reads to its end, and stops. Those conditions are <Term id="access-predicate">access predicates</Term>.

<Depth level={2}>
The rule is the <Term id="leftmost-prefix">leftmost prefix</Term>. Equality on the leading columns, then at most one range, can narrow the scan. Conditions on columns after the range are <Term id="filter-predicate">filter predicates</Term>: checked on every entry in the scanned stretch, which saves table fetches but not index reads. Conditions on columns the index does not have wait for the table row. Hence the habit of putting equality columns first and the range or sort column last. Selectivity is a weaker rule than this one: a very selective column used with a range still belongs after the equality columns.
</Depth>

<Depth level={3}>
The PostgreSQL documentation states the rule exactly: equality constraints on leading columns, plus any inequality on the first column without an equality constraint, limit the portion of the index scanned; constraints on later columns are checked in the index. The order of conditions inside WHERE never matters; the planner matches them to index columns by name.
</Depth>

## [problem] An index that matches the query

A multi-tenant shop has a dashboard that lists a tenant's orders since a date, newest first. Someone added an index on (created_at, tenant_id), because almost every report filters on a date range, and the query names both columns.

Read the code once. The index contains both columns from the WHERE clause, and EXPLAIN shows an index scan. With 20 tenants the dashboard is fast.

<Depth level={2}>
Look at what the index scan reads. The index is sorted by created_at first, so the range "since December 1" is one stretch of the index, and it holds every tenant's December orders, mixed together. tenant_id = 7 is checked on each of them. With 20 tenants, tenant 7 is about one entry in 20.
</Depth>

<Depth level={3}>
`EXPLAIN (ANALYZE, BUFFERS)` shows it: the index condition contains only created_at, and tenant_id shows up as a filter, or as a second part of the index condition that does not reduce the buffers read. The rows-removed or buffers numbers grow with the number of tenants, not with the result.
</Depth>

## [pain] Then a change request arrives

**Change request:** grow from 20 tenants to 2,000, and keep the tenant order list under 100 ms.

Every new tenant adds its December orders to the stretch every query reads. With 2,000 tenants, the dashboard reads 2,000 entries for every one it shows. The marked line is the obvious fix: add an index on tenant_id.

<Depth level={2}>
The planner may now use the tenant_id index, which reads all of a tenant's orders for every year and fetches each row from the table to check the date. For a large tenant that is worse than before. Or it combines both indexes as bitmaps, which still reads the big December stretch. Two indexes, more write cost, and neither starts and stops on the rows the query wants.
</Depth>

<Depth level={3}>
Each index also costs every INSERT another descent and leaf write. On a table taking thousands of orders per second, an index that no query uses well is pure cost. `pg_stat_user_indexes.idx_scan` shows which indexes are never used.
</Depth>

## [morph] Put the equality column first

Drag the slider. The index entries reorder from date-first to tenant-first, and the scan shrinks to one stretch.

One index on (tenant_id, created_at) replaces both. The equality on tenant_id comes first, so all of tenant 7's entries are together. The range on created_at comes second, so within tenant 7 they are in date order. The scan starts at (7, December 1), reads only matches, and stops at the first entry of tenant 8.

<Depth level={2}>
The same index serves the ORDER BY created_at DESC LIMIT 50: inside tenant 7, entries are already in created_at order, so the database reads the stretch backwards and stops after 50 rows, without a sort. It also serves every query that filters on tenant_id alone, because tenant_id is its leading column.
</Depth>

<Depth level={3}>
Since PostgreSQL 18, a B-tree <Term id="skip-scan">skip scan</Term> can use an index without a condition on its leading column, by searching once per distinct leading value. The documentation notes that the planner only does this when there are few distinct values; otherwise it prefers a sequential scan. MySQL 8.0 has a skip scan too, for queries that read only indexed columns.
</Depth>

## [walk] Follow the query through the index

One seek, a short stretch of leaf entries, then the table. Use the numbered buttons.

<Depth level={2}>
When the matching stretch is a large share of the table, fetching rows one by one in index order costs more than reading the whole table in order. The planner then picks a <Term id="seq-scan">sequential scan</Term> even though a usable index exists. That is a correct decision, not a failure of the index.
</Depth>

<Depth level={3}>
PostgreSQL's cost model charges 1 per sequentially read page and 4 per random page by default (seq_page_cost and random_page_cost), plus small CPU costs per row and per index entry. A bitmap heap scan sorts the row locations first, so its cost per page falls from 4 towards 1 as the share of table pages it touches grows.
</Depth>

## [again] The same request, one calendar day at a time

Support asks for a tenant's orders on one calendar day. The natural SQL is `date(created_at) = $2`, and it turns the index back into a filter, because the index is sorted by created_at, not by date(created_at). The fix is a half-open range on the bare column: created_at from midnight up to, but not including, the next midnight. It seeks just like the dashboard query.

<Depth level={2}>
When the expression is unavoidable, such as `lower(email) = $1` for case-insensitive lookups, index the expression itself: `CREATE INDEX ON users (lower(email))`. An <Term id="expression-index">expression index</Term> only helps queries that use the same expression. MySQL supports the same idea as functional key parts since 8.0.13.
</Depth>

<Depth level={3}>
LIKE 'abc%' is a range in disguise (from abc up to abd) and can use a B-tree. In a database whose collation is not C, PostgreSQL needs the index built with the text_pattern_ops operator class for that. LIKE '%abc' has no fixed prefix, so no B-tree can seek on it.
</Depth>

## [lens] Where the WHERE clause comes from

The index rules are the same in every language. What differs is how each driver types parameters, because a parameter of the wrong type can make PostgreSQL convert the column instead of the value, and a converted column is a column inside a function.

### Reading an index scan in EXPLAIN

In PostgreSQL's `EXPLAIN`, an Index Scan node lists an Index Cond and sometimes a Filter. The Index Cond is what the index can check; only its leading-column part limits the pages read. A Filter line means rows were fetched from the table and then thrown away, and `Rows Removed by Filter` counts them. With `BUFFERS`, the shared hit and read counts show how many pages the scan touched, which is the number to compare between two index designs.
