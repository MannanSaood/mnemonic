## [concept] Isolation levels and anomalies

**An <Term id="isolation-level">isolation level</Term> decides which interleavings of concurrent transactions your code can observe. The weaker ones let some interleavings commit with wrong results. The stronger ones turn those interleavings into an error that you retry.**

Concurrent transactions run statement by statement, interleaved. If every transaction ran alone, one after another, the database would always be right. The isolation level says how far from that ideal the database may go. Each gap has a name: <Term id="read-skew">read skew</Term>, <Term id="lost-update">lost update</Term>, <Term id="write-skew">write skew</Term>.

<Depth level={2}>
PostgreSQL defaults to read committed: every statement sees what was committed when the statement started. Repeatable read gives the whole transaction one snapshot, which is <Term id="snapshot-isolation">snapshot isolation</Term>. Serializable promises the result of some serial order. MySQL's InnoDB defaults to repeatable read, and its repeatable read is not PostgreSQL's: plain SELECTs read a snapshot, but UPDATE and DELETE work on the newest committed rows.
</Depth>

<Depth level={3}>
The SQL standard defines the levels by three phenomena: dirty read, nonrepeatable read and phantom. PostgreSQL's table adds a fourth column, serialization anomaly, and notes that it never allows dirty reads at any level and never allows phantoms at repeatable read. Its read uncommitted behaves like read committed. The standard's definitions miss lost update and write skew, which is why the names vary between databases.
</Depth>

## [problem] A checkout that reads, then writes

A checkout reserves stock inside a transaction: read the stock, check there is enough, write back the stock minus the quantity, commit. It runs at the default level. In tests, with one checkout at a time, it is always right.

Read the code once. Every line does what it says. The transaction even makes the read and the write commit together.

<Depth level={2}>
The value written is computed in the application, from a read made one statement earlier. Between that read and the write, another checkout can commit. At read committed, the UPDATE then lands on the new row with a number computed from the old one.
</Depth>

<Depth level={3}>
When the second UPDATE finds the row locked by the first, read committed waits. When the first commits, PostgreSQL re-checks the UPDATE's WHERE clause on the new version of the row and applies the UPDATE to it. That is exactly right for `SET stock = stock - 2` and exactly wrong for `SET stock = 8`.
</Depth>

## [pain] Then a change request arrives

**Change request:** run a flash sale on one product, with hundreds of checkouts per second competing for the same stock row.

The stock count stops matching the orders. The warehouse ships more items than it had. The marked line is the first fix: run the transaction at SERIALIZABLE.

<Depth level={2}>
The lost updates stop, and errors start. Every checkout that loses a race now fails with SQLSTATE 40001, "could not serialize access", and the handler turns it into a 500. During the sale, that is most checkouts. The level was right; the code was not ready for it.
</Depth>

<Depth level={3}>
A <Term id="serialization-failure">serialization failure</Term> means: this transaction, as it ran, cannot be placed in any serial order with the others. The documentation says to abort and retry the whole transaction from the beginning, reads included, because results read before the error may be wrong.
</Depth>

## [morph] Let the database choose a loser, and retry it

Drag the slider. The lone transaction box turns into two transactions, a conflict check, and a retry.

The fix is a small helper that runs a function inside a serializable transaction and reruns it on 40001. The checkout code moves into that function unchanged. When two checkouts race, PostgreSQL lets the first to commit win and fails the other; the helper runs the loser again, and the second attempt sees the new stock.

<Depth level={2}>
Back off between attempts, cap the number of attempts, and keep the function free of side effects outside the database, since it may run more than once. Repeatable read with the same helper would also fix this checkout. Serializable is needed for the next case, where the two transactions write different rows.
</Depth>

<Depth level={3}>
PostgreSQL implements serializable as <Term id="ssi">Serializable Snapshot Isolation</Term>. It runs snapshot isolation and also records what each transaction read, as SIRead predicate locks. Those locks never block. When two concurrent transactions each read something the other wrote, they form a cycle no serial order can produce, and one of them is rolled back.
</Depth>

## [walk] Follow two checkouts through the race

Two transactions, one row, one conflict. Use the numbered buttons.

<Depth level={2}>
For a single row there are cheaper fixes at read committed. `UPDATE items SET stock = stock - $1 WHERE sku = $2 AND stock >= $1` does the check and the write in one statement, and the row count says whether it worked. `SELECT ... FOR UPDATE` locks the row on the read, so the second checkout waits and then reads the new stock.
</Depth>

<Depth level={3}>
At repeatable read the conflict is detected on the write: updating or locking a row that another transaction changed and committed after your snapshot fails at once. At serializable the same rule applies, and the read/write check runs as transactions read, write and commit.
</Depth>

## [again] The same request, for an on-call rota

The team adds a rule: at least one engineer must stay on call. Two engineers each run the same transaction: count who is on call, and if there are two or more, take themselves off. Each updates only their own row. At repeatable read, both see two people on call in their snapshots, both update, both commit, and nobody is on call. The same serializable helper fixes it with no new code.

<Depth level={2}>
This is write skew: two transactions read an overlapping set of rows and write disjoint ones, based on what they read. Snapshot isolation only checks conflicting writes, so it cannot see it. Without serializable, the fix is to lock the rows you read, with `SELECT ... FOR UPDATE`, or to turn the rule into a single row both transactions must update.
</Depth>

<Depth level={3}>
Phantoms make write skew harder to lock away. If the check is "no other booking overlaps this time slot", there may be no row yet to lock. Serializable's predicate locks cover the range that was read, rows that do not exist included; a plain FOR UPDATE does not.
</Depth>

## [lens] How each driver exposes transactions and isolation

Every driver can run a transaction at any level. They differ in where the level goes (an option, a property, or SQL text), whether a transaction is an object that cleans up after itself, and how the SQLSTATE reaches your code. Those three decide how a retry helper looks.

Switch the language at the top of the page; the code and the note follow.

<Depth level={2}>
Retry the whole function, never a single statement. A statement retried inside a failed transaction gets "current transaction is aborted"; and a retry that reuses values read before the error repeats the bug. Also retry when COMMIT itself fails: under serializable, the conflict can be detected at commit time.
</Depth>

<Depth level={3}>
Connection poolers in transaction mode, such as PgBouncer, hand a connection to one transaction at a time. Session settings like `SET default_transaction_isolation` do not survive between transactions there, so set the level per transaction, in BEGIN or SET TRANSACTION.
</Depth>

### Which anomaly each PostgreSQL level allows

Read committed allows nonrepeatable reads, read skew, lost updates and write skew; each statement sees fresh committed data. Repeatable read allows write skew only; lost updates and changed rows raise 40001. Serializable allows none of them and raises 40001 instead. No PostgreSQL level shows uncommitted data. In MySQL's InnoDB, repeatable read lets a read-modify-write lose an update without an error, because UPDATE works on the newest rows rather than the snapshot.
