          private start = 0;

  tradeoffs:
    - A user-space buffer copies every byte one more time, from the buffer to your variable.
    - Buffered writes sit in your process until flushed, and are lost if it crashes first.

## [concept] The syscall path

**A <Term id="system-call">system call</Term> is a trip into the kernel with a fixed price: load registers, switch mode, dispatch, do the work, switch back.**

That price is the same whether the trip carries 4 bytes or 64 KiB. Make fewer trips that each carry more.

<Depth level={2}>
Five parts do the work. Your code asks for bytes. A buffer, if you have one, answers from memory when it can. The wrapper (libc, or the Go runtime) puts the call number and arguments in registers and executes `syscall`. The kernel's entry code saves your registers and dispatches on the number. The handler, here `vfs_read`, does the work and copies the result back to you.
</Depth>

<Depth level={3}>
On x86-64 the call number goes in `rax` and up to six arguments in `rdi`, `rsi`, `rdx`, `r10`, `r8` and `r9`. The result comes back in `rax`. A value between -4095 and -1 is a negated error number, which libc turns into a return of -1 and a value in `errno`. The `syscall` instruction jumps to an address the kernel wrote into a model-specific register at boot, and the kernel never trusts a pointer you pass: it copies in and out with checked copies.
</Depth>

## [problem] A startup that reads a log one record at a time

A service keeps an index in memory and logs every change to a write-ahead log. At startup it replays the log: a 4-byte length, then the record body, until the end of the file.

The code is short and obviously correct. In tests the log has a few hundred records and startup is instant.

<Depth level={2}>
The author pictured `read` as a function that fetches bytes from the file. With that picture, asking for 4 bytes is cheaper than asking for 64 KiB, and reading exactly what you need is the tidy choice.
</Depth>

<Depth level={3}>
<Lang only="go">An `*os.File` has no buffer, so each `io.ReadFull(f, …)` is one `read(2)` for a regular file.</Lang>
<Lang only="python">`buffering=0` gives a raw `FileIO`, so each `f.read(n)` is one `read(2)`. The comment's reason is a myth: a buffered file's `tell()` already reports the position you have read up to.</Lang>
<Lang only="typescript">`readSync` is a thin layer over libuv and libc: one call, one `read(2)`.</Lang>
<Lang only="rust">`File` implements `Read` directly over the descriptor, so each `read_exact` is at least one `read(2)`.</Lang>
</Depth>

## [pain] Restarts take seconds

In production the log is 100 MB: a million records of 100 bytes. The file is hot in the <Term id="page-cache">page cache</Term>, so no disk is involved, and still the replay burns half a second of CPU, most of it in the kernel. Under strace it takes almost a minute.

`strace -c` gives the reason: two million `read` calls, one per marked line per record.

<Depth level={2}>
A profiler shows the time in the syscall entry and exit code and in `vfs_read`, not in your parsing. Each call moves only a few bytes, so the fixed cost of the trip dominates. A faster disk would not help: there is no disk I/O.
</Depth>

<Depth level={3}>
The fixed cost is roughly a tenth of a microsecond for the crossing and as much again for the file lookup and checks. On CPUs that need <Term id="kpti">KPTI</Term> each crossing also switches page tables, which can make it several times dearer. strace adds a ptrace stop at every entry and exit, each a round trip to the tracer process: tens of microseconds per call.
</Depth>

<Depth level={3}>
A <Term id="mode-switch">mode switch</Term> is not a context switch. The same task keeps running, on its own kernel stack, and returns to the next instruction. A context switch happens only if the call has to wait, for a disk or a socket, and the scheduler runs something else meanwhile.
</Depth>

The copy back uses <Term id="copy-to-user">copy_to_user</Term>-style helpers that check the destination is a user address and recover from a fault on a bad pointer by returning an error.
</Depth>

## [again] The same log, buffered

The same replay, after the one-line change. `strace -c` now counts 1,527 calls instead of 2,000,001, and the replay takes about 30 ms instead of 450.

<Depth level={2}>
Past 64 KiB, bigger buffers barely help: the remaining cost is copying 100 MB, twice (kernel to buffer, buffer to record). To remove the second copy, parse records in place out of the buffer, or map the file with `mmap`.
</Depth>

<Depth level={3}>
Writes have the same shape and one extra risk. A buffered writer holds data in your process until it fills or you flush it, so a crash loses it. Flush at the points where the data must be in the kernel, and call `fsync` where it must be on disk.
</Depth>

## [lens] How each language reads a file

Every language ends in the same `read(2)`. What differs is whether you get a buffer without asking.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={3}>
<Lang only="go">The Go runtime makes raw syscalls on Linux. When a goroutine's call blocks, for example on a slow disk, the scheduler hands the thread's P to another thread so other goroutines keep running. A `read` from the page cache returns too fast for that to matter.</Lang>
<Lang only="python">CPython releases the GIL around the `read(2)` in `FileIO.readinto`, so other threads can run while one waits on a slow file.</Lang>
<Lang only="typescript">The async `fs` functions run each `read(2)` on a libuv thread-pool thread, four by default, and post the result back to the event loop. That adds a thread hop to every call, so small async reads are even dearer than small sync ones.</Lang>
<Lang only="rust">`std::fs::File::read` calls libc's `read`. Async runtimes such as tokio run file reads on a blocking thread pool, so `tokio::io::BufReader` matters there for the same reason.</Lang>
</Depth>

### Calls that never reach the kernel

`clock_gettime`, `gettimeofday`, `time` and `getcpu` run in the <Term id="vdso">vDSO</Term> on x86-64: a small library the kernel maps into every process, reading data the kernel keeps current. They cost about as much as a function call, and strace does not see them. Every other call pays the full trip, so count them with `strace -c` (slow, fine for a test run) or `perf trace -s` (cheap enough for production).
