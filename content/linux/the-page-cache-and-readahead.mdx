      example: the cached pages of index.bin
      job: Holds file contents in RAM, indexed per file by page offset. Every buffered read and write goes through it.
    - role: Readahead
      example: the 4 → 32 page window
      job: Detects sequential access and reads the next pages in one larger I/O, partly in the background.
    - role: Device
      example: NVMe SSD or a network volume

  useWhen:
    - A service reads the same files repeatedly. Leave RAM free for the page cache instead of sizing every byte for the heap.
    - Startup latency matters after a restart. Warm the hot files with a sequential read before taking traffic.
    - A file is read once, in order, by a batch job. Readahead handles it; FADV_SEQUENTIAL can double the window.
  avoidWhen:
    - Your program keeps its own cache of the same data, as databases do. Two caches waste RAM; consider O_DIRECT.
    - A one-off scan of huge files would evict the hot set. Use FADV_DONTNEED after reading, or read with O_DIRECT.
  tradeoffs:
    - The first read of each page pays a full device round trip.
    - Cached file pages count toward a container's memory usage, and are reclaimed under pressure.
    - Benchmarks run warm unless you drop caches; production after a deploy runs cold.
    - Readahead can read pages nobody uses when the access only looks sequential.

    - name: Drive write and read cache
      how: A small cache inside the device. It helps the device, but every request still crosses the bus and the kernel.

    - name: mmap

## [concept] The page cache and readahead

**Linux keeps file data in spare RAM, in the <Term id="page-cache">page cache</Term>. A read finds its page there and copies it out in about a microsecond, or misses and waits for the disk.**

When you read in order, the kernel also reads ahead: it fetches the next pages before you ask, in growing batches. That is <Term id="readahead">readahead</Term>.

<Depth level={2}>
Four parts do the work. The **reader** calls `read` or `pread`. The **page cache** holds each file's pages, indexed by offset, in RAM that would otherwise be idle. **Readahead** watches the access pattern of each open file and, when it looks sequential, turns the next misses into one larger I/O. The **device** answers misses, and charges mostly per I/O: 80 µs or so on a local NVMe SSD, around a millisecond on a network volume. The ratio of hits to all reads is the <Term id="cache-hit-ratio">cache hit ratio</Term>, and it decides your latency more than the disk does.
</Depth>

<Depth level={3}>
Each cached file has one `address_space`, and its pages are indexed in an XArray (a radix tree until Linux 4.20). Since 5.16 the cache is managed in folios, which can hold more than one page. `mmap` and `read` share these pages: a file mapped by one process and read by another is cached once. Readahead state lives per open file, in `struct file_ra_state`, which records the current window's start, size and the async part that triggers the next one.
</Depth>

## [problem] A search service that reads its index per request

A search service keeps a 6 GB index file on local disk. Each lookup reads one 4 KiB block at an offset with `pread`. The pod has 16 GB of RAM, so the whole index fits in the page cache.

In load tests every lookup takes a few microseconds. The index seems to live in memory.

<Depth level={2}>
The load test ran on a machine that had been up for hours. The index was already cached, so the test only ever measured hits. Nothing in the code says what happens when the cache is empty.
</Depth>

<Depth level={3}>
A test that wants the cold path must create it: `echo 1 > /proc/sys/vm/drop_caches` (as root, after `sync`) frees clean cached pages. Use it for benchmarks only. On a server it throws away useful cache for every process.
</Depth>

## [pain] Then a change request arrives

**Change request:** ship fixes during the day. Every replica restarts at peak traffic, several times a day.

Each new pod starts on a node whose page cache has never seen this index. Its first lookups all miss, and each one waits on the disk. In the playground's scale model, 100 lookups wait on the disk 85 times.

<Depth level={2}>
The symptom looks like a slow disk or a bad release: p99 jumps for minutes after each deploy and then recovers on its own as the cache fills. `cachestat` (bcc) or the `cachestat` syscall (Linux 6.5) shows the hit ratio collapsing; `iostat` shows many small reads.
</Depth>

<Depth level={3}>
Random lookups do not trigger readahead, so the cache fills one 4 KiB page per miss. Filling 6 GB that way takes 1.5 million misses. Under load, the misses also queue behind each other on the device and in the runtime's I/O threads.
</Depth>

## [morph] From "it is in memory" to the page cache

Drag the slider. The index stops being a block of memory and becomes what it is: a page cache in front of a disk, with readahead deciding how misses are fetched.

The code gains a warm-up pass. It reads the file once, front to back, before the service reports ready.

<Depth level={2}>
The warm-up reads more data than the lookups would ever touch, and still finishes sooner, because a disk charges per I/O. Readahead turns the sequential pass into large batches; random misses pay one round trip each. <Term id="posix-fadvise">`posix_fadvise`</Term> with `SEQUENTIAL` doubles the window on Linux.
</Depth>

<Depth level={3}>
`POSIX_FADV_WILLNEED` starts reading a range in the background without blocking, but the kernel may read less under memory pressure. Tools such as `vmtouch` warm files the same way. For a hot set much larger than RAM, warming everything just evicts itself; warm the part that is hot.
</Depth>

## [walk] Follow the warm-up read

One sequential pass through the mechanism, then one lookup. Step through it with the numbered buttons.

<Depth level={3}>
In `mm/readahead.c`, a 1-page sequential miss opens a 4-page window. Each next window is 4× the last while small and 2× after that, capped at the device's `read_ahead_kb` (128 KiB unless changed). The first page of the async part carries the `PG_readahead` flag; reading it calls the async path, which submits the next window and returns without waiting. The kernel also checks whether the pages before a miss are cached, so a stream that resumes after a gap can still be seen as sequential.
</Depth>

## [again] The same deploy, warmed

The same restart at peak traffic. The pod reads the index front to back before it reports ready, so the load balancer only sends traffic to a warm cache. In the scale model, 256 pages load in 11 I/Os, and the 100 lookups after them never wait.

<Depth level={2}>
At full size the warm-up is bounded by device bandwidth: 6 GB at about 2 GB/s on local NVMe is 3 seconds; at 250 MB/s on a network volume, about 25 seconds. Put it before the readiness probe goes green, and give the probe enough time.
</Depth>

<Depth level={3}>
Cached file pages count toward the container's memory cgroup. A 6 GB warm-up in a pod with a tight memory limit reclaims its own cache as fast as it fills it. Size the limit for the heap plus the hot files.
</Depth>

### Reading the cache from the shell

`free -h` shows the page cache under `buff/cache`, and `available` counts the part that can be reclaimed. `fincore` (util-linux) and `vmtouch` show how much of a given file is cached. `cachestat` from bcc reports hits and misses per second, and the `cachestat` syscall (Linux 6.5) answers the same question for one file. `/sys/block/<dev>/queue/read_ahead_kb` is the readahead cap for a device.
