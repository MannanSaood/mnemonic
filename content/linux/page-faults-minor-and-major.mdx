  roles:
    - role: MMU and page table
      example: the CPU's page-table walk
      job: Translates each access in hardware. Traps to the kernel when the entry is missing or forbids the access.
    - role: Fault handler
      example: "handle_mm_fault"
      job: Finds the VMA, checks permissions, and resolves the fault or sends SIGSEGV.
    - role: Page cache
      example: file pages in RAM
      job: Serves file pages without I/O. A hit makes the fault minor.
    - role: Disk or swap
      example: index.bin, swap
      job: Source of a major fault. The task sleeps until the read completes.
    - role: Zero page and copy-on-write
      example: fresh heap, pages shared after fork
      job: Share a page read-only until the first write, then give the writer its own copy.
  useWhen:
    - Latency-critical services that map files or allocate large buffers. Prefault at startup and report ready after.
    - Diagnosing slow first requests, slow first runs of a batch job, or RSS that grows after fork.
    - Choosing between read() into the heap and mmap. Both pay for cold pages; mmap pays in faults.
  avoidWhen:
    - Prefaulting data larger than RAM. It evicts other pages and the early ones get dropped again.
    - Prefaulting with mlock without a memory limit plan. Locked pages can never be reclaimed.
  tradeoffs:
    - Prefaulting makes startup slower and uses RAM for pages that may never be read.
    - mmap avoids a copy into the heap, but turns I/O errors into SIGBUS and I/O waits into page faults you cannot see in strace.
    - Copy-on-write makes fork cheap, but every write after fork can cost a copy, and the RSS of parent and child can double.
    - Transparent huge pages cut the number of faults, but a copy-on-write fault on a huge page copies 2 MiB.
  lookalikes:
    - name: Swapping
      how: One cause of major faults, for anonymous memory. File-backed pages fault from their file, with no swap involved.
    - name: TLB miss
      how: The page is mapped, but its translation is not cached. The MMU walks the page table in hardware; there is no fault and no kernel.
    - name: SIGSEGV
      how: A fault the kernel cannot resolve, because no mapping covers the address or it forbids the access.

## [concept] Page faults: minor, major and copy-on-write

**`mmap` and `malloc` only promise memory. The first touch of each page traps into the kernel, a <Term id="page-fault">page fault</Term>, and the kernel maps a page then.**

How long that takes depends on where the page is. Already in RAM: about a microsecond, a <Term id="minor-fault">minor fault</Term>. On disk: the time of a disk read, a <Term id="major-fault">major fault</Term>.

<Depth level={2}>
Four parts are involved. The MMU walks the process's <Term id="page-table">page table</Term> on every access. When an entry is missing or forbids the access, it traps to the kernel's fault handler. The handler finds the mapping (the <Term id="vma">VMA</Term>), and resolves the fault from the <Term id="page-cache">page cache</Term>, the <Term id="zero-page">zero page</Term>, a fresh page, a copy, or the disk. Then the instruction runs again.
</Depth>

<Depth level={3}>
Minor faults come in several kinds: a file page found in the page cache, a read of untouched heap (mapped to the shared zero page), a first write to heap (a fresh zeroed page), and a write to a page shared after fork, which is <Term id="copy-on-write">copy-on-write</Term>. Major faults read from a file or from swap. The kernel counts both per task, which is what `ps -o min_flt,maj_flt` and `getrusage` report.
</Depth>

## [problem] A search service that maps its index

A search service maps its 1.5 GB index file and answers lookups by slicing into the mapping. Startup is instant, and lookups are memory reads.

It passes every test and load test, which all run on a machine where the index was read a minute earlier.

<Depth level={2}>
The author's picture: mmap loads the file into memory, so once it returns, the index is in RAM. That picture explains why the code is fast in tests, and nothing in the code contradicts it.
</Depth>

<Depth level={3}>
<Lang only="typescript">Node has no mmap in core, so the Node version reads each entry with `readSync` at a file offset. It has the same hidden assumption in a different form: that the page cache already holds the index.</Lang>
<Lang only="go">`syscall.Mmap` returns a `[]byte` backed by the mapping. Slicing it allocates nothing and makes no syscall, which is the attraction.</Lang>
<Lang only="python">`mmap.mmap` returns an object you can slice like `bytes`. Each slice copies out of the mapping, which is still only memory access.</Lang>
<Lang only="rust">`Mmap` derefs to `&[u8]`, so the index looks like any other slice to the rest of the program.</Lang>
</Depth>

## [pain] Slow minutes after every deploy

After each deploy, p99 latency jumps from 2 ms to 60 ms, then settles over a few minutes. CPU is low. `ps -o maj_flt` for the process climbs fast in exactly that window, then stops.

The marked lines are where it happens. mmap read nothing. Every lookup that touches a page for the first time waits for the disk, and on a new host or after a reboot, no page is in the page cache.

<Depth level={2}>
The disk is a cloud volume, so each read takes around a millisecond, and a lookup that touches 50 cold pages spends 50 ms waiting. Load tests missed it because they ran right after the index was built, with every page cached.
</Depth>

<Depth level={3}>
Faults are invisible to strace, because no syscall happens. They show up as major-fault counters, as time in the D state, and in `perf trace -F maj` or a page-fault tracepoint. Readahead helps a little: the kernel reads neighbouring pages on a fault in a file mapping, but random lookups defeat it.
</Depth>

## [walk] Follow one lookup

One startup and one lookup through the corrected code. Step through it with the numbered buttons.

<Depth level={3}>
The fault handler is `handle_mm_fault`. For a file page it looks the page up in the page cache, maps it on a hit, and on a miss starts a read and sleeps. For a file mapping it also maps neighbouring pages that are already cached in one go ("fault-around"), so sequential access takes fewer minor faults than pages. A page-table walk on a TLB miss is not a fault at all: the MMU does it in hardware.
</Depth>

The same deploy with the prefault. Startup takes a few seconds longer while the index is read. From the first request, p99 is 2 ms and the major-fault counter does not move while serving.

<Depth level={2}>
Pair it with a readiness check. If the process reports ready before the prefault finishes, the load balancer sends traffic to it anyway and you are back to the pain.
</Depth>

<Depth level={3}>
Copy-on-write is the third kind of fault worth knowing. After fork, parent and child share every private page read-only. The first write by either one faults, and the kernel copies the page (or, if the other side already took its copy, just makes it writable). This is how Redis snapshots a live dataset, and why its memory can nearly double during a busy save.
</Depth>

## [lens] How each language meets page faults

Every runtime's heap is mapped memory, so every language takes minor faults as its heap grows. File mappings, prefaulting and fork vary.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={3}>
<Lang only="go">The Go runtime gets heap memory with `mmap` and returns it with `madvise`, so a Go process faults in pages as the heap grows and can fault again after the scavenger releases them. `GODEBUG=madvdontneed=1` changes how memory is returned, not whether it faults.</Lang>
<Lang only="python">CPython's reference counts are writes. In a forked worker, reading a shared object writes its page and triggers a copy. `gc.freeze()` before fork keeps the collector from touching those objects, which helps, but reference counting still unshares the pages you use.</Lang>
<Lang only="typescript">V8 reserves its heap with mmap and commits pages as it grows, so a growing Node heap takes minor faults. `--max-old-space-size` limits growth, not faulting.</Lang>
<Lang only="rust">Rust has no runtime between you and the allocator. `Vec::with_capacity` reserves address space; the pages fault in as you push. Allocators such as jemalloc and mimalloc return memory with `madvise`, so a freed and reused region can fault again.</Lang>
</Depth>

### Counting faults

`ps -o min_flt,maj_flt -p PID` shows the totals since the process started; sample it twice to get a rate. `perf stat -e minor-faults,major-faults -p PID` counts over an interval. `/usr/bin/time -v cmd` prints both for a whole run. A high minor rate is usually harmless (heap growth); a major rate on a latency-critical service is worth a look every time.
