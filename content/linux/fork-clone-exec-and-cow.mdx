    question: A process calls execve("/usr/bin/pdftotext", …). What happens to it?
    options:
      - text: It keeps its PID and its open descriptors, and its program and memory are replaced by pdftotext's.
        correct: true
        why: Right. exec does not create a process. fork (or clone) creates one; exec changes what runs in it.
      - text: The kernel starts a new process for pdftotext next to it.
        why: No. exec replaces the program in the same process. To get a second process you fork or spawn first.
      - text: pdftotext is loaded into the process next to the old program, which keeps running.
        why: No. The old program's memory and threads are gone after a successful exec. Only a failed exec returns.
  engineer:
    question: "A 20 GiB service shells out with fork and exec, and fork fails with ENOMEM although free shows 6 GiB available. vm.overcommit_memory is 2. Why?"
    options:
      - text: In strict mode the kernel must commit the child's copy of all private writable memory at fork time, 20 GiB more, even though exec would throw it away a moment later.
        correct: true
        why: Right. Strict overcommit counts what could be written, not what is used. A vfork-style spawn commits only the new program's memory.
      - text: fork copies the 20 GiB immediately, and only 6 GiB is free.
        why: No. fork copies page tables and shares the pages. The failure is the commit accounting, not a copy.
      - text: The child inherited the parent's memory limit and hit it.
        why: Limits do not explain ENOMEM from fork itself. The kernel refuses before the child exists.
  deep:
    question: Why is calling malloc in a forked child of a multithreaded program, before exec, dangerous?
    options:
      - text: Only the thread that called fork exists in the child. If another thread held the allocator's lock at that moment, the lock stays held forever and malloc deadlocks.
        correct: true
        why: Right. The child gets a copy of every lock in its state at fork time, with no thread left to release it. Only async-signal-safe calls are safe until exec.
      - text: The child shares the parent's heap, so both processes would allocate from the same memory.
        why: No. After fork the heap is copy-on-write, so the child's allocations land in its own copies.
      - text: malloc is not linked into the child until it calls exec.
        why: No. The child runs the parent's program, libraries included, until it execs.

## [concept] fork, clone, exec and copy-on-write

**<Term id="fork">fork</Term> copies a process's <Term id="page-table">page tables</Term>, not its memory: every private page becomes <Term id="copy-on-write">copy-on-write</Term> in both processes. <Term id="execve">exec</Term> replaces the program in a process. <Term id="clone">clone</Term>'s flags decide what a new task shares.**

So fork is cheap for a small process and not for a big one, and running another program from a big process should borrow its memory instead of copying its tables.

<Depth level={2}>
Three calls make every process and thread. `clone` creates a task; with no sharing flags it is a fork, with `CLONE_VM` and friends it is a thread, with `CLONE_VM|CLONE_VFORK` it is a <Term id="vfork">vfork</Term>: the child borrows the parent's memory and the parent waits until the child execs. `execve` loads a new program into the calling process. <Term id="posix-spawn">posix_spawn</Term> is the two together, done the cheap way.
</Depth>

<Depth level={3}>
glibc's `fork()` is `clone` with only `SIGCHLD` as flags, and its `posix_spawn` (since 2.24) uses `clone(CLONE_VM|CLONE_VFORK)` on a separate stack. `clone3`, added in Linux 5.3, takes the same choices in a struct and can return a pidfd for the child.
</Depth>

## [problem] Running a converter as nobody

A document service keeps 8 GiB of parsed documents in memory. For each upload it runs `pdftotext`, an external tool, and it must not run that tool with the service's own privileges.

The obvious way: ask the process API to start the child and drop privileges in it before exec. Every language offers an option for that. It works in tests, where the service's heap is small.

<Depth level={2}>
The picture behind it: starting a child process costs about the same whatever the parent's size, and a little setup in the child before exec is free.
</Depth>

<Depth level={3}>
<Lang only="go">`SysProcAttr` with `CLONE_NEWUSER` asks the kernel for a new user namespace as the child is created, which is how Go programs sandbox without root.</Lang>
<Lang only="python">`preexec_fn` runs a Python function in the child between fork and exec, which is how setrlimit and setuid calls get into the child.</Lang>
<Lang only="typescript">The `uid` and `gid` options of `child_process` switch the child's user before exec.</Lang>
<Lang only="rust">`CommandExt::uid` and `gid` switch the child's user before exec.</Lang>
</Depth>

## [pain] Stalls on every upload, and ENOMEM

In production each upload stalls the whole service for about 80 ms, and p99 latency follows the upload rate. On hosts with strict overcommit, some uploads fail outright with "cannot allocate memory", while `free` shows gigabytes available.

The marked lines are the cause. Setup that runs in the child, before exec, rules out the cheap spawn, so the runtime makes a real fork of an 8 GiB process.

<Depth level={2}>
A real fork copies page tables for every mapped page: 16 MiB of entries for 8 GiB, in roughly 80 ms on a physical host and much longer on some virtual machines. While it runs, the parent is busy in the kernel. Until the child execs, every page the service writes is shared, so each write faults and copies.
</Depth>

<Depth level={3}>
The ENOMEM comes from commit accounting. With `vm.overcommit_memory=2`, the kernel promises memory only up to a limit, and a fork must commit the child's copy of all private writable memory. The child would exec a millisecond later, but the kernel cannot know that.
</Depth>

<Depth level={2}>
The fix moves the setup out of the gap between fork and exec. The service spawns a tiny wrapper (`setpriv`, `prlimit` or `unshare` from util-linux) with no options that need code in the child, so the runtime can use its vfork-style path. The wrapper drops privileges for itself and execs the real tool.
</Depth>

<Depth level={3}>
A vfork-style child runs on the parent's memory and stack, so it can do almost nothing before exec. That is why runtimes only use it when they need no user code in the child, and why options such as `preexec_fn`, `pre_exec` or uid switches push them back to a real fork.
</Depth>

## [again] The same upload, spawned

The same request after the change. Each upload stalls the service for a fraction of a millisecond, nothing is copied, and strict overcommit has nothing to refuse, because the child never claims the parent's memory.

<Depth level={2}>
When you do need fork, for a child that must see the parent's memory, keep the parent's writes low until the child is done. Redis's snapshot child is the classic case: while it writes the snapshot, every page the parent changes is copied, and a write-heavy instance can nearly double its memory.
</Depth>

<Depth level={3}>
Transparent huge pages make copy-on-write coarser: a write to one byte of a shared 2 MiB page copies all of it. That is why Redis recommends disabling them.
</Depth>

## [lens] How each language starts processes

Every runtime's process API ends in `clone` and `execve`. What differs is whether you can fork at all, and which options push the runtime off its cheap path.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={3}>
<Lang only="go">The Go runtime's threads cannot be copied safely, so Go has no `syscall.Fork`. To get a worker with its own memory you exec a new process, often the same binary with a flag.</Lang>
<Lang only="python">Preforking servers, such as gunicorn with `--preload`, fork workers from a parent that has loaded the app, to share its memory. CPython's reference counts write to every object they touch, so the sharing fades as workers run; `gc.freeze()` before forking keeps the collector from speeding that up.</Lang>
<Lang only="typescript">Each `cluster` worker or `child_process.fork()` child is a fresh Node process that loads your code again; nothing is shared with the parent. `worker_threads` share the process but each has its own V8 heap.</Lang>
<Lang only="rust">`std` never forks for you unless you ask for code in the child. Crates such as `nix` expose `fork()` as `unsafe`, with the same rule as C: only async-signal-safe calls until exec.</Lang>

### What a fork keeps and what exec resets

After fork the child has copies of the parent's descriptors (sharing their file offsets), memory (copy-on-write), signal handlers and working directory, but only the thread that called fork, no pending signals, no timers and no memory locks. After exec the process keeps its PID, parent, descriptors without close-on-exec, and resource limits; it loses its memory, its other threads, its caught signal handlers and its `atexit` handlers. Mark descriptors close-on-exec (`O_CLOEXEC`, the default in Go, Python and Rust) so helpers do not inherit sockets and files they should not see.
