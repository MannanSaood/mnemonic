            tmp := path + ".tmp"
            f, err := os.Create(tmp)
            if err != nil {
                return err

      job: Hold written data until writeback or fsync puts it on the disk.
    - role: Flusher threads
      example: one per backing device
      job: Write dirty pages in the background, when they are older than dirty_expire_centisecs or too much memory is dirty.
    - role: fsync
      example: { go: f.Sync(), python: os.fsync, typescript: fh.sync(), rust: sync_all() }
      job: Writes one file's data and metadata and flushes the device cache, then returns.
    - role: Journal
      example: ext4 or XFS log
      job: Commits metadata such as renames and sizes atomically, every few seconds or on fsync.
  useWhen:
    - You reply, acknowledge or move on based on data being saved. fsync before the acknowledgement.
    - You replace a whole file. Temp file, fsync, rename, fsync the directory.
    - Many small writes need durability. Batch them and fsync once (group commit).
  avoidWhen:
    - Data you can rebuild, such as caches and temp output. Skip fsync and let writeback handle it.
    - Tiny writes one at a time on a hot path. Each fsync costs milliseconds; batch instead.
  tradeoffs:
    - fsync takes milliseconds on SSDs, more on disks without a battery-backed or power-loss-protected cache.
    - Durability depends on the device honouring cache flushes.
    - Writers that fill dirty memory past dirty_ratio are throttled inside write() itself.
    - Errors from writeback show up only at fsync or close, and only once.

    - name: O_SYNC and O_DSYNC

    - name: sync_file_range
      how: Starts or waits for writeback of a range, but does not flush metadata or the device cache. Not a durability guarantee.
    - name: syncfs and sync
      how: Flush a whole file system or all of them. Coarse, and they report errors poorly.

## [concept] Writeback, fsync and durability

**`write()` returns as soon as your data is in the page cache. The kernel writes it to the disk later, in the background. <Term id="fsync">fsync</Term> is how you wait for the disk.**

Until then the data is in <Term id="dirty-page">dirty pages</Term> in RAM, and a power cut loses it.

<Depth level={2}>
Background <Term id="writeback">writeback</Term> runs in flusher threads, one per backing device. They wake every `dirty_writeback_centisecs` (5 s by default) and write pages that have been dirty longer than `dirty_expire_centisecs` (30 s). They also start when dirty memory passes `dirty_background_ratio` (10% of available memory). Past `dirty_ratio` (20%), a process that keeps writing is made to wait inside `write()` itself. Metadata takes a different path: on ext4 the journal commits every 5 seconds by default (the `commit=` mount option).
</Depth>

<Depth level={3}>
Flusher threads per device replaced `pdflush` in Linux 2.6.32. Since 4.13, writeback errors are recorded per file with a sequence counter (`errseq_t`) and reported once to each file descriptor that might have written the data. `fsync` also sends a cache-flush command (or writes with FUA) so the device's own volatile write cache cannot hold the data back.
</Depth>

## [problem] A scheduler that saves on every change

A job scheduler keeps its schedule in `data.json`. Every change through the API rewrites the file, and the handler replies 204 when the write returns.

It works. In years of testing, every save was there after a restart.

<Depth level={2}>
A restart is not a power cut. When the process exits, its writes are already in the page cache, and the kernel finishes writing them out. Only a crash of the whole machine, or a power cut, loses dirty pages.
</Depth>

<Depth level={3}>
The convenience functions all truncate the file first: Go's `os.WriteFile`, Python's `open(path, "w")`, Node's `fs.writeFile`, Rust's `fs::write`. The truncate is metadata, the new contents are data, and the two reach the disk at different times.
</Depth>

## [pain] Then a change request arrives

**Change request:** run the job scheduler on edge sites, where the power fails a few times a year.

After the first outage, one site's `data.json` has 0 bytes and the scheduler refuses to start. At another, the last minute of changes is gone, though every API call got its 204.

<Depth level={2}>
The 0-byte file is the truncate reaching the disk in a journal commit while the new data was still dirty in RAM. The lost changes are writes that were in the page cache when the reply went out, with up to 30 seconds to wait before writeback.
</Depth>

<Depth level={3}>
ext4 hides part of this. With its default `auto_da_alloc` option it starts writing the data when a file is truncated to zero and rewritten, or renamed over an existing file. That is a heuristic for one file system, added after exactly these bug reports in 2009. XFS and others give no such help, and the heuristic still does not make anything durable before you reply.
</Depth>

## [morph] From "write means on disk" to dirty pages and fsync

Drag the slider. The file stops being something `write()` updates on the disk. It becomes dirty pages in the page cache, a directory entry, and a disk that gets each of them at a different time.

The code gains the recipe: write a temp file, fsync it, rename it over the old one, fsync the directory, then reply.

<Depth level={2}>
Each step closes one gap. fsync on the temp file makes its data durable before any name points at it. The <Term id="atomic-rename">atomic rename</Term> means there is never a moment with a half-written `data.json`. fsync on the directory makes the rename itself durable. <Term id="fdatasync">fdatasync</Term> can replace the first fsync when timestamps do not matter.
</Depth>

<Depth level={3}>
The fsync(2) man page says it directly: syncing a file does not sync the directory entry that names it. On ext4 an fsync of the file commits the journal transaction that is open at that moment, which often happens to include an earlier rename. The rename in this recipe comes after the fsync, so it waits for the next commit unless you sync the directory.
</Depth>

One save through the page cache, the journal and the disk. Step through it with the numbered buttons.

<Depth level={3}>
<Lang only="go">`os.Rename` is `rename(2)` on Linux, atomic when both names are in the same file system. Across file systems it fails with `EXDEV`, so keep the temp file in the same directory as the target.</Lang>
<Lang only="python">`os.replace` is `rename(2)` on Linux. Keep the temp file next to the target: a rename across file systems fails with `OSError` (`EXDEV`).</Lang>
<Lang only="typescript">`fs.rename` is `rename(2)`. It fails with `EXDEV` across file systems, which is why the temp file lives in the same directory and not in `os.tmpdir()`.</Lang>
<Lang only="rust">`fs::rename` is `rename(2)` on Linux. A temp file from `std::env::temp_dir()` is often on another file system; create it next to the target instead.</Lang>
</Depth>

## [again] The same power cut, after the fix

The same outage. Wherever it lands, `data.json` holds v1 (and no 204 was sent, so the client retries) or v2 (and the 204 is true). It is never empty.

The price is about 8 ms per save on a typical SSD, mostly the two waits for the disk.

<Depth level={2}>
If saves are frequent, batch them: collect the changes that arrive within a few milliseconds, write them in one file, fsync once, and reply to all of them. That is <Term id="group-commit">group commit</Term>, and it is how databases make thousands of commits per second durable.
</Depth>

<Depth level={3}>
Check every error. A failed `fsync` must fail the save, and the safe reaction is to stop trusting the in-memory state and recover from what is on disk. Retrying the fsync can return success with the data gone.
</Depth>

## [lens] How each language syncs a file

Every language exposes the same three calls: fsync, rename and a way to open a directory. None of the one-line write helpers use them.

Switch the language at the top of the page; the code, the diagram labels and the note follow.

<Depth level={2}>
Python adds a buffer of its own above the page cache, so it needs a `flush()` before the fsync. Node runs fsync on the libuv thread pool. Go and Rust call `fsync` directly on the calling thread.
</Depth>

### Watching writeback

`grep -E 'Dirty|Writeback' /proc/meminfo` shows how much data is waiting. `/proc/sys/vm/dirty_*` holds the thresholds and intervals. `sync` writes everything dirty and waits; it is a tool for operators, not a substitute for fsync in a program, because it reports no per-file errors.
