      example: the pod's container
      job: Counts anon memory, page cache and kernel memory charged to it, and enforces memory.high and memory.max.
    - role: Reclaim
      example: drop cache, then swap
      job: Frees pages when a charge would cross a limit. Runs in the allocating task (direct reclaim) or in kswapd.
    - role: OOM killer
      example: kills the API, exit 137
      job: Runs when reclaim fails. Kills the task with the highest badness, or the whole group with memory.oom.group.
    - role: oom_score_adj
      example: -1000 for the API
      job: Lets you choose who dies first. -1000 exempts a process.
  useWhen:
    - Read memory.stat before calling a full container a leak. Rising anon is a leak; rising file is cache.
    - Set memory.high a little below memory.max to get throttling and a signal before a kill.
    - Tell the runtime about the limit (GOMEMLIMIT, --max-old-space-size, JVM MaxRAMPercentage) so its GC works within it.
  avoidWhen:
    - Do not set every process to -1000. The OOM killer then has no victim inside the group.
    - Do not drop caches to make dashboards look better. It costs disk reads and frees nothing the kernel would not free on demand.
  tradeoffs:
    - Reclaiming hot cache makes reads go back to disk, so latency rises before anything is killed.
    - Swap avoids kills but turns memory pressure into major faults; Kubernetes runs pods without swap by default.
    - memory.high trades a kill for a slowdown that can be just as bad for a latency-sensitive service.
    - Page cache is charged to the cgroup that first read the file, which can surprise shared-file workloads.

## [concept] Memory accounting, reclaim, swap and the OOM killer

**A container's memory is its processes' <Term id="anonymous-memory">anonymous memory</Term> plus the <Term id="page-cache">page cache</Term> it touched. At the limit, the kernel drops cache first, swaps if it may, and only then kills.**

The <Term id="oom-killer">OOM killer</Term> picks the process with the most memory, adjusted by <Term id="oom-score-adj">oom_score_adj</Term>. Who made the last allocation does not matter.

<Depth level={2}>
In cgroup v2, a <Term id="memory-cgroup">memory cgroup</Term> exposes the numbers as files. `memory.current` is the total charged. `memory.stat` splits it, with `anon` and `file` as the two lines to read first. `memory.max` is the hard limit: at it, the allocating task <Term id="reclaim">reclaims</Term>, and if that fails, the OOM killer runs inside the group. `memory.high` is a softer line: above it the group is throttled and pushed to reclaim, and it never invokes the OOM killer. `memory.events` counts each of these moments.
</Depth>

<Depth level={3}>
The kernel scores each candidate in `oom_badness()`: resident pages plus swap entries plus page-table pages, plus `oom_score_adj` times the available memory divided by 1000. In a cgroup OOM, the available memory is the group's limit. `-1000` makes a task exempt. With `memory.oom.group` set, the whole group is killed together.
</Depth>

## [problem] A report service that reads whole files

A report endpoint loads a 300 MB CSV export into memory, parses it into rows and summarizes them. A semaphore lets one report run at a time. The container's limit is 1 GiB, and the dashboards show memory usage near 95% all day.

The team has learned to ignore that graph. Nothing ever got killed.

<Depth level={2}>
The 95% is mostly page cache from export files. It counts toward `memory.current`, and the kernel drops it whenever a report needs heap. The graph shows the cache doing its job.
</Depth>

<Depth level={3}>
Under <Term id="overcommit">overcommit</Term>, reading a 300 MB file into a buffer rarely fails at the allocation. The pages are charged one by one as they are touched, so the limit is hit in the middle of the copy, not at the `malloc`.
</Depth>

## [pain] Then a change request arrives

**Change request:** let the report service run four reports at once instead of one.

One number changes. Four reports need four copies of the file plus four sets of rows, well over 1 GiB of heap. The kernel drops all the cache, finds nothing more to free, and kills the service with SIGKILL. Kubernetes shows `OOMKilled`, exit code 137, and every request in flight fails.

<Depth level={2}>
The node had plenty of free memory. The kill was inside the container's own cgroup. `memory.events` in that cgroup shows the story: `max` counted many times (reclaim made room), then `oom` and `oom_kill` once.
</Depth>

<Depth level={3}>
Before the kill there was a slower phase. Once the cold cache was gone, reclaim took pages the service was still reading, and those reads went back to the disk. Pressure stall information (`memory.pressure`) shows that phase as time tasks spent waiting on memory.
</Depth>

## [morph] From "usage is our heap" to the memory cgroup

Drag the slider. The container stops being one number. It becomes a memory cgroup that charges heap and page cache, a reclaim path that takes back cache first, and an OOM killer that comes last.

The code stops holding whole files. It streams rows, so four reports need a few MiB of heap, and the page cache they create is reclaimed as they move on.

<Depth level={2}>
Two settings close the gap between the runtime and the kernel. Tell the runtime about the limit (`GOMEMLIMIT`, `--max-old-space-size`, the JVM's `MaxRAMPercentage`), so its collector works before the kernel has to. And set `memory.high` a little below `memory.max` if you would rather slow down than die.
</Depth>

<Depth level={3}>
Since Kubernetes 1.28, on cgroup v2, the kubelet sets `memory.oom.group` on each container, so an OOM kills every process in the container at once. Kubernetes 1.32 added the `singleProcessOOMKill` kubelet option to go back to killing one process. The playground models the plain kernel default: one process per kill.
</Depth>

## [walk] Follow one allocation to the limit

One row of one report, through the memory cgroup. Step through it with the numbered buttons.

<Depth level={3}>
Reclaim works on LRU lists of pages, kept per cgroup, separately for anonymous and file pages. Since Linux 6.1 the multi-generation LRU is available as an alternative to the older active and inactive lists. Reclaim that runs in the allocating task is direct reclaim, and its time is added to that allocation's latency. `vm.swappiness` (0 to 200, default 60) sets how the kernel weighs swapping anonymous pages against dropping file pages.
</Depth>

## [again] Four reports, the second time

The same four reports at once. Each holds a read buffer and one row, a few MiB in all. `memory.current` still sits near the limit, because the export files fill the page cache, but `anon` stays flat and nothing is killed.

<Depth level={2}>
Size the limit for the heap you need at peak plus the cache that keeps you fast. If the hot files no longer fit, the service still runs; it just reads from disk more often.
</Depth>

<Depth level={3}>
Page cache is charged to the cgroup that first brought the page in. If a sidecar reads the same files first, the cache counts against the sidecar's container, not yours.
</Depth>

None of these runtimes enforces the cgroup limit for you. Some can be told about it.

### Reading a container's memory

Inside the container's cgroup directory: `memory.current` and `memory.max` for the total and the limit, `memory.stat` for `anon` against `file`, `memory.events` for how often reclaim, throttling and kills happened, and `memory.pressure` for time lost waiting. `/proc/<pid>/oom_score` shows each process's current score, and `dmesg` logs every kill with the cgroup and the scores. On the host, `free` reports `available`, which counts reclaimable cache as usable.
