    question: What makes a failure cascade?
    options:
      - text: The failing part pushes its load or its waiting onto other parts, which then overload and fail in turn.
        correct: true
        why: Right. Survivors take a crashed task's traffic, callers hold workers while they wait, and retries add load. Each step overloads the next component.
      - text: Several unrelated components happen to fail at the same time.
        why: That is a coincidence, not a cascade. In a cascade each failure causes the next.
      - text: A bug is deployed to every service at once.
        why: That is a correlated failure from one change. A cascade spreads through load, even when only one component had a problem.
  engineer:
    question: Ten tasks each run at 80% of capacity. Three crash, and the load balancer spreads their traffic over the other seven. What happens next?
    options:
      - text: Each survivor gets about 114% of its capacity, slows down and starts failing too, unless it sheds load.
        correct: true
        why: Right. 80% × 10 / 7 ≈ 114%. Without shedding, overloaded tasks miss deadlines, fail health checks or crash, and their load moves on to the rest.
      - text: Each survivor runs at about 91%, which is fine.
        why: That spreads three tasks' load as if it were one. Ten tasks' worth of traffic over seven tasks is 10/7 of the load each.
      - text: The load balancer stops sending traffic, so nothing else fails.
        why: Load balancers keep sending to healthy-looking tasks. That is how the load reaches the survivors.
  deep:
    question: The database recovered a minute ago, but checkout is still failing and the database is at full CPU. There are no deadlines. What is it doing?
    options:
      - text: Working through queued queries whose callers gave up long ago, so new queries wait too long, time out and are retried into the same queue.
        correct: true
        why: Right. The backlog keeps every answer late, late answers look like failures, and retries refill the backlog. That is a metastable failure. Deadlines that let the database drop expired work, or cutting load, break it.

        why: Possible in some databases, but the symptom here is explained by the work it is being asked to do.
      - text: Waiting for health checks to mark it healthy again.
        why: Health checks change where traffic goes, not what the database is busy with.

reference:
  roles:
    - role: Load shedding
      example: 503 when all 80 slots are busy
      job: Refuses work early and cheaply so the work it accepts still finishes in time.
    - role: Deadline propagation
      example: { go: "r.Context() all the way down", python: "deadline from the caller, asyncio.timeout(remaining)", typescript: "AbortSignal.any([deadline, timeout])", rust: "Instant deadline, timeout(left)" }
      job: Lets every service stop work for a request whose caller has already given up.
    - role: Retry budget
      example: retries ≤ 10% of requests, per client
      job: Caps how much retries can add to load during an outage.
    - role: Graceful degradation
      example: product pages without stock counts
      job: Keeps a cheaper version of the feature working when its dependency is overloaded.
  useWhen:
    - Any service that calls another service and can be called by more than it can serve.
    - Shared dependencies, where one consumer's spike can starve the rest.
    - Chains of synchronous calls, where every layer holds a resource while it waits.
  avoidWhen:
    - Shedding by a signal that lags the overload (minute-averaged CPU). By the time it triggers the queue is long.
    - Queues sized for the worst burst. The SRE book suggests queues of half the thread pool or less for steady traffic; a long queue only adds latency.
    - Retrying at every layer. Pick one, usually the one directly above the overloaded service.
  tradeoffs:
    - Shedding fails some requests on purpose. It needs monitoring, or it hides a capacity shortfall for weeks.
    - Degraded modes are code paths that rarely run, so they rot. Exercise them, for example by running a few servers near overload.
    - Restarting overloaded servers often makes it worse: new tasks start with cold caches, serve little, and fail health checks.
    - Capacity headroom (N+2) prevents many cascades, but not the ones triggered by retries and backlogs.
  lookalikes:
    - name: Circuit breaker
      how: The caller's version of shedding. It stops calling a failing dependency; shedding stops accepting work you cannot finish.
    - name: Bulkhead
      how: Separate pools per dependency, so one slow dependency cannot use every worker. It contains a cascade's spread sideways.
    - name: Rate limiting
      how: Caps each client's share whether or not anything is overloaded. Shedding reacts to overload whoever sent the work.

## [concept] Cascading failures

**A <Term id="cascading-failure">cascading failure</Term> is overload that spreads. A slow or failed component makes the services that call it hold workers longer and retry more, which overloads them, which does the same to their callers, until parts of the system that never touched the original problem fail too.**

The usual trigger is ordinary: a slow query, a lost zone, a deploy, a traffic spike. The cascade comes from how the rest of the system reacts. Every caller that waits holds a resource, and every caller that retries adds load at the moment there is least capacity for it.

<Depth level={2}>
Three defences cut the loop. <Term id="load-shedding">Load shedding</Term> refuses work early and cheaply when a service is full, so callers fail fast instead of waiting. <Term id="deadline-propagation">Deadline propagation</Term> lets each service stop work nobody is waiting for. A <Term id="retry-budget">retry budget</Term> caps how much retries can add. Together they keep <Term id="goodput">goodput</Term>, the useful work done in time, close to capacity.
</Depth>

<Depth level={3}>
The worst form is a <Term id="metastable-failure">metastable failure</Term>: the trigger ends, but the overload sustains itself. A backlog of abandoned work keeps every new answer late, late answers time out and are retried, and the retries refill the backlog. The SRE book's advice for that state is blunt: reduce load drastically until it drains.
</Depth>

## [problem] An inventory service that waits and retries

Checkout calls inventory to reserve stock, and inventory queries the database. Inventory allows 80 queries at once, and a request waits for a free slot when all are busy. Each attempt gets 500 ms, and it tries three times, because the database is occasionally slow. Checkout and the frontend each retry too. It has handled every load test.

<Depth level={2}>
Each line is defensive on its own: a limit on queries, a timeout, a retry. The problem is what they do together under a slow database. Waiting for a slot has no limit, the timeout starts fresh from `Background`, and three layers that each try three times can turn one checkout into 27 queries.
</Depth>

<Depth level={3}>
The timeout covers the query, not the wait for a slot, so a request can sit in the queue for seconds before its 500 ms even starts. The caller's deadline is lost at the first hop: inventory does not know that checkout gave up long ago.
</Depth>

## [pain] Then a change request arrives

**Change request:** the inventory database had a slow ten seconds and the storefront was down for twenty minutes, browse pages included. Make a slow database cost us checkout, not the site.

The marked lines are the instinctive fix: more slots so requests do not wait, and a longer timeout so the slow database has time to answer. Both make the next incident worse. Every request now holds its caller's worker four times as long, so checkout's pool fills sooner, then the frontend's. Browse pages, which only need the frontend, fail because every frontend worker is waiting on checkout.

<Depth level={2}>
The outage outlived the slowdown because of the queue. When the database recovered, it spent its capacity on queries whose callers had timed out long before. New queries waited behind them, timed out, and were retried into the same queue.
</Depth>

<Depth level={3}>
Little's law makes the arithmetic plain: requests in progress = arrival rate × time each one takes. With 50 checkouts a second and each holding a frontend worker for 6 seconds (three 2-second attempts), the frontend needs 300 workers for checkout alone. It has 200.
</Depth>

## [morph] Fail fast, carry the deadline, budget the retries

Drag the slider. The blocking wait for a slot becomes a try-or-503, the fresh timeout becomes the caller's context with a per-attempt cap, and the retry loop draws from a shared budget.

Hover a box in the diagram to see its code.

<Depth level={2}>
Shed at the service that is short of capacity, with a signal that moves fast: requests in flight, queue length, or event-loop delay. Return a status that says overloaded (503 with Retry-After, or gRPC `RESOURCE_EXHAUSTED`), and make callers treat it as "do not retry" once their budget is spent.
</Depth>

<Depth level={3}>
The SRE book lists the order to prevent overload in: load test to find the limit and the failure mode, serve degraded results, reject when overloaded, reject higher up rather than overload servers, and plan capacity. Changing a queue from FIFO to LIFO, or using CoDel, also drops the requests least likely to still have a caller.
</Depth>

<Lang only="go">`r.Context()` is cancelled when the client disconnects or the server's handler returns, so every query started with it is cancelled too. `database/sql` honours it while waiting for a connection, not only during the query.</Lang>
<Lang only="python">`Semaphore.locked()` is true when no slot is free, so the shed check does not wait. Between the check and `async with` nothing else runs, because asyncio only switches tasks at an `await`.</Lang>
<Lang only="typescript">`AbortSignal.any()` aborts when either the caller's deadline or the 500 ms timeout fires, and the database driver must accept a `signal` for the query itself to stop.</Lang>
<Lang only="rust">`try_acquire` returns at once with `Err` when no permit is free. The permit is released when `_slot` is dropped, on every return path, including when hyper drops the whole future because the client left.</Lang>

## [again] The same slow database again

The same ten-second slowdown with the new code: inventory sheds what it cannot serve, checkout fails fast for those users, and the frontend's pool never fills, so browse pages carry on. Queries whose callers gave up are cancelled, so the database has no backlog when it recovers, and checkout is back the same second. The test fills every slot and checks the next request gets a 503 within 10 ms.

<Depth level={2}>
Show users something better than an error where you can: a product page without stock counts, a cart that says "we will confirm availability by email". That is <Term id="graceful-degradation">graceful degradation</Term>, and it turns shed load into a smaller outage.
</Depth>

<Depth level={3}>
In an emergency, the SRE book's steps are: add capacity if you can, stop health checks from killing overloaded tasks, restart carefully (cold caches make new tasks weak), drop traffic hard until it stabilises, and turn off retries and expensive features.
</Depth>

## [lens] How each language does it

Go, async Python, Node and tokio all make waiting cheap, so there is no small thread pool to run out of. The cascade still happens: it fills connection pools, memory and event loops instead. Each language differs in whether a caller's departure cancels the work below it.

### How a cascade spreads

| Mechanism | What fills up | Defence |
|---|---|---|
| Callers wait on a slow dependency | worker pools, connections, memory up the chain | shed early, bounded waits |
| Retries at several layers | load on the scarce component, multiplied | one retry layer, retry budget |
| Work for callers who left | the slow component's capacity, after it recovers | deadline propagation, LIFO or CoDel queues |
| Survivors take a crashed task's traffic | the remaining tasks, one after another | capacity headroom, shedding |
| Restarts with cold caches | new tasks, which fail health checks | slow, staged restarts |
