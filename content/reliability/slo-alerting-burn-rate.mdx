        // slorules.go: one SLO in, Prometheus rules out
        type window struct {
            Long, Short time.Duration
            Spend       float64 // share of the 30-day budget spent when the long window fires
            Severity    string
        }

        var windows = []window{
            {time.Hour, 5 * time.Minute, 0.02, "page"},
            {6 * time.Hour, 30 * time.Minute, 0.05, "page"},
            {72 * time.Hour, 6 * time.Hour, 0.10, "ticket"},
        }

        const period = 30 * 24 * time.Hour

        // 0.02 × 720 h / 1 h = 14.4
        func burnRate(w window) float64 { return w.Spend * float64(period) / float64(w.Long) }

        func recordingRules(service string) []Rule {
            var rules []Rule
            for _, d := range []string{"5m", "30m", "1h", "6h", "3d"} {
                rules = append(rules, Rule{
                    Record: fmt.Sprintf("%s:error_ratio:rate%s", service, d),
                    Expr:   fmt.Sprintf(`sum(rate(%s_requests_total{code="5xx"}[%s])) / sum(rate(%s_requests_total[%s]))`, service, d, service, d),
                })
            }
            return rules
        }

        func alertRules(service string, slo float64) []Rule {
            var rules []Rule
            for _, w := range windows {
                threshold := fmt.Sprintf("%.4g", burnRate(w)*(1-slo)) // 14.4 × 0.1% = 1.44%

                        service, model.Duration(w.Long), threshold, service, model.Duration(w.Short), threshold),
                    Labels: map[string]string{"severity": w.Severity},
                })
            }
            return rules
        }

# ---------------------------------------------------------------- how it works
walk:
  - text: Recording rules turn the request counters into error ratios over 5 minutes, 30 minutes, 1 hour, 6 hours and 3 days. Every alert reads these.
    nodes: [metrics, context, record]
    edges: [metrics>context, context>record]
    role: record
  - text: Burn rate is the error ratio divided by the budget's rate, 0.1%. At 1× the budget lasts exactly 30 days; at 14.4× it lasts about two days, and one hour spends 2% of it.
    nodes: [record, strategy]
    edges: [record>strategy]
    role: burn
  - text: Each condition pairs a long window, which says the burn is big enough to matter, with a short one, 1/12 as long, which says it is still happening.
    nodes: [strategy, long, short]
    edges: [strategy>long, strategy>short]
    role: windows
  - text: A total outage crosses 14.4× on both 1 h and 5 min within a minute. When errors stop, the 5-minute window clears in 5 minutes and the 30-minute one in half an hour, so the page resets. A 0.3% leak never pages; the 3-day rule files a ticket.
    nodes: [short, page, long, ticket]
    edges: [short>page, long>ticket]
    role: fire

checks:
  overview:
    question: With an SLO of 99.9% over 30 days, what does a burn rate of 1 mean?
    options:
      - text: Errors at exactly 0.1%, which would use the whole budget by the end of the 30 days.
        correct: true
        why: Right. Burn rate is the error rate divided by the rate the SLO allows. At 2× the budget lasts 15 days; at 1,000× (every request failing) about 43 minutes.
      - text: One error per minute.
        why: Burn rate is relative to the allowed error rate, not a count. One error a minute is a burn of 1 only if you serve 1,000 requests a minute.
      - text: The service is down for one hour.
        why: A total outage is a burn rate of 1,000 at 99.9%; it would spend the month's budget in about 43 minutes.
  engineer:
    question: An alert fires when the 1-hour burn rate exceeds 14.4. Why add the condition that the 5-minute burn rate exceeds 14.4 too?
    options:
      - text: So the alert stops about 5 minutes after the errors stop, instead of firing for most of an hour.
        correct: true
        why: Right. The 1-hour average remembers the incident for an hour. The short window confirms the burn is still happening, so the page resets quickly and nobody chases a fixed problem.
      - text: So the alert fires sooner.
        why: The long window still has to cross 14.4×, so detection time is the same. The short window improves the reset.
      - text: To catch slow leaks the 1-hour window misses.
        why: A slow leak has a low burn rate on every window. Catching it takes a lower threshold on a long window, like 1× over 3 days.
  deep:
    question: You want to page when 2% of a 30-day budget is spent in one hour, for an SLO of 99.9%. Above what 1-hour error rate should the alert fire?
    options:
      - text: "1.44%"
        correct: true
        why: Right. Spending 2% of 720 hours' budget in 1 hour is a burn rate of 0.02 × 720 / 1 = 14.4, and 14.4 × 0.1% = 1.44%.
      - text: "0.144%"
        why: That is a burn rate of 1.44, which spends 0.2% of the budget an hour.
      - text: "14.4%"
        why: That is a burn rate of 144, which would spend 20% of the budget in an hour.

# ---------------------------------------------------------------- reference page
reference:
  roles:
    - role: Recording rules
      example: checkout:error_ratio:rate1h
      job: Precompute error ratios over each window, so alert rules are cheap and consistent.
    - role: Burn rate
      example: error ratio ÷ (1 − SLO)
      job: How fast the budget is being spent, relative to spending it exactly over the SLO window.
    - role: Long window
      example: 1 h at 14.4×, 6 h at 6×, 3 d at 1×
      job: Makes sure enough budget has burned to be worth someone's attention.
    - role: Short window
      example: 5 min, 30 min, 6 h (1/12 of the long one)
      job: Confirms the burn is still happening, so alerts reset soon after recovery.
    - role: Severity
      example: page for fast burns, ticket for slow ones
      job: Wakes someone only when the budget will be gone in hours or days.
  useWhen:
    - Any service with an SLO and enough traffic that one failure is a small share of the budget.
    - Replacing alerts on causes (CPU, queue length) with alerts on what users feel.
    - Many services: pick the parameters once, generate rules for all of them.
  avoidWhen:
    - Low-traffic services, where one failed request is a burn rate of 100. Add synthetic traffic, group services, or lengthen the windows.
    - Extreme targets. At 99.999% a total outage spends the month's budget in 26 seconds; design for small blast radius instead of fast alerts.
    - Very low targets. At 90% even a total outage burns at 10× and spends only 1.4% in an hour, so the 2% rule never fires.
  tradeoffs:
    - More windows and thresholds mean more to reason about. Generate them; never hand-tune per service.
    - Long windows cost more to evaluate, which is why ratios are recorded first.
    - When several conditions fire for one incident, suppress the ticket while the page is firing, or on-call gets three notifications.
    - Detection time scales with severity. A total outage pages in under a minute; a 2% error rate takes about 43 minutes.
  lookalikes:
    - name: Threshold alert at the SLO
      how: Fires whenever a short window misses the target. High recall, very low precision; it can page 144 times a day while the SLO is met.
    - name: "Duration clause (for: 1h)"
      how: Requires the condition to hold for a time. Detection no longer scales with severity, and a flapping error rate resets the timer and never fires.
    - name: Anomaly detection
      how: Alerts on change from normal, not on budget spent. Useful for causes, noisy for paging.
---

## [concept] Alerting on SLOs: burn rate and multiple windows

**Page on how fast the error budget is burning. A <Term id="burn-rate">burn rate</Term> of 1 spends the budget exactly over the SLO window; page when a long window shows a high burn and a short window shows it is still going on.**

A good alert has high <Term id="alert-precision">precision</Term> (every page matters) and high <Term id="alert-recall">recall</Term> (every incident that matters pages), detects fast and resets fast. Thresholds on the error rate cannot do all four. Burn rates over two windows can.

<Depth level={2}>
The Site Reliability Workbook's starting point for a 99.9% SLO over 30 days: page when 1 hour and 5 minutes both burn above 14.4× (2% of the budget in an hour), page when 6 hours and 30 minutes both burn above 6× (5% in six hours), and open a ticket when 3 days and 6 hours both burn above 1× (10% in three days). That is a <Term id="multiwindow-alert">multiwindow, multi-burn-rate alert</Term>.
</Depth>

<Depth level={3}>
Every threshold comes from one formula: burn rate = budget share × SLO period ÷ alert window. 0.02 × 720 h ÷ 1 h = 14.4. The time to fire is roughly (1 − SLO) ÷ error ratio × window × burn rate, so a total outage crosses 14.4× on a 1-hour window in under a minute, and a 2% error rate takes about 43 minutes.
</Depth>

## [problem] An alert that fires whenever the SLO is missed

A rule generator in the platform repo reads each service's SLO and writes one Prometheus alert: page when the error ratio over the last 10 minutes reaches the SLO's allowed rate. For checkout's 99.9%, that is 0.1%. It catches every outage within seconds.

<Depth level={2}>
It also pages for anything that touches 0.1% for ten minutes: a deploy's brief error burst, a dependency's hiccup, a bad client. A 10-minute window at exactly the SLO rate spends 0.02% of the month's budget. The rule could page 144 times a day while the SLO is met.
</Depth>

<Depth level={3}>
The rule reads a <Term id="recording-rule">recording rule</Term> over 10 minutes. That part is fine; recorded ratios are how every version of this alert should work. The problem is the threshold and the single window.
</Depth>

## [pain] Then a change request arrives

**Change request:** on-call got 23 pages last month and 20 were noise. Make the SLO alert page only when the SLO is actually at risk.

The marked line is the usual fix: `for: 1h`, page only if the condition holds for an hour. The noise stops. The next month a bad config push fails every checkout for 15 minutes, spending 35% of the budget, and nobody is paged: the condition held for 15 minutes, not 60. A leak that flaps between 0.08% and 0.15% resets the timer every few minutes and never pages either.

<Depth level={2}>
A duration does not scale with severity. A total outage and a 0.2% error rate both wait the same hour, and a total outage for that hour spends 140% of a 30-day budget.
</Depth>

<Depth level={3}>
What the on-call wanted was precision, and what `for:` traded away was recall and detection time. The way to get precision without losing either is to tie the threshold to budget spent: a big burn should fire fast, a small one slowly, a tiny one never.
</Depth>

<Depth level={2}>
Generate the rules from one table and apply it to every service. The workbook warns against tuning windows per service: with a hundred services it becomes toil nobody can reason about. Change the table, regenerate, and every service changes together.
</Depth>

<Depth level={3}>
Alerting at a lower burn for longer windows means one incident can satisfy several rules. A 10% spend in five minutes is also 5% in six hours and 2% in one hour. Route them to one notification with inhibition (Alertmanager's `inhibit_rules`), or on-call gets three.
</Depth>

## [again] The same outage again

The same 15-minute total outage with the generated rules: the page fires about a minute in, after roughly 2% of the budget, and stops about half an hour after recovery, when the 6-hour rule's 30-minute window clears. The blips that made up the 20 noisy pages never get near 14.4×. The 3-day leak opens a ticket about a day in, before it has spent 10%. The test pins the thresholds to the table.

<Depth level={2}>
Count pages per incident and false pages per month as health metrics for the alerting itself. If a rule pages and nobody needs to act, change the table, not the people.
</Depth>

<Depth level={3}>
For services with a few requests an hour, a single failure is a 10% hourly error rate, a burn of 100, and 13.9% of the budget. The workbook's options: synthetic traffic, grouping related low-traffic services into one SLO, changing the product so one failure matters less, or a lower target.
</Depth>
